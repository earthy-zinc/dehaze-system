# 文件管理模块 - 后端实现设计

## 文档概述

文件管理模块在 clarity-java、clarity-go、clarity-python 三端实现，逻辑保持一致。

- API 接口：[API接口.md](./API接口.md)
- 数据库设计：[02-系统架构/03-数据库设计.md](../../../02-系统架构/03-数据库设计.md)

## 架构设计

### 模块分层架构

文件管理模块采用三层架构：表现层(FileController) → 业务层(FileService + PathBuilder) → 存储层(StorageService接口 + MinIO/本地/Nginx静态实现)。

**设计考量**：

- 元数据与物理存储分离，元数据存数据库，物理文件存对象存储
- 策略模式允许运行时切换存储后端，便于开发、生产环境适配
- PathBuilder 统一命名规范，避免路径逻辑散落各处

### 核心组件职责

| 组件           | 职责描述      | 关键能力                                                     |
| -------------- | ------------- | ------------------------------------------------------------ |
| FileController | HTTP 请求处理 | 参数校验、文件流读取、MD5 计算、响应封装                     |
| FileService    | 业务逻辑编排  | MD5 去重判断、元数据 CRUD、事务控制                          |
| PathBuilder    | 存储路径生成  | 日期目录、MD5 命名、扩展名提取                               |
| StorageService | 物理存储抽象  | 上传、下载、删除、存在性检查                                 |

### 存储策略模式

#### 设计原理

存储后端差异大（本地文件系统 vs 对象存储 vs nginx 静态服务），但上层业务逻辑一致。通过策略模式：

1. 定义统一的存储接口契约
2. 不同存储后端实现相同接口
3. 运行时根据 `sys_file.storage` 选后端实例

#### 存储接口契约

| 方法     | 入参           | 出参     | 说明                                                                                                    |
| -------- | -------------- | -------- | ------------------------------------------------------------------------------------------------------- |
| upload   | 文件流、对象名 | 对象名   | 上传文件到存储后端（幂等：相同 objectName 覆盖写入）                                                    |
| download | 对象名         | 文件流   | 获取文件内容流（流式传输，不加载到内存）                                                                |
| delete   | 对象名         | 是否成功 | 删除物理文件（不存在时视为成功）                                                                        |
| exists   | 对象名         | 是否存在 | 检查文件是否存在                                                                                        |
| getUrl   | 对象名         | 完整 URL | 唯一 URL 生成出口：`storage.baseUrl.rstrip("/") + "/" + object_name`，仅在 API 响应序列化时调用，不落库 |

`sys_file` 只存稳定的 `object_name` + `storage`，URL 永远在运行时拼接、不落库，环境迁移只改配置，数据库零改动。三端不得新增任何自行拼接 URL 的代码路径，所有 URL 一律走 `StorageService.getUrl`。返回给前端的 url 必须是带 scheme 与 host 的完整 URL（`http(s)://host/...`），禁止相对路径。

#### 三端接口契约一致性

`StorageService` 接口契约由 Java 端为权威来源，Go/Python 端必须按以下约束严格对齐，确保三后端行为一致：

| 契约维度 | 一致性要求                                                                                                             |
| -------- | ---------------------------------------------------------------------------------------------------------------------- |
| 方法签名 | 方法名、入参顺序与语义、出参类型三端一致（仅语言层面差异，如 Java `InputStream` ↔ Go `io.Reader` ↔ Python `BinaryIO`） |
| 语义契约 | upload 幂等覆盖、delete 不存在视为成功、download 流式传输不加载内存、getUrl 唯一出口——三端行为完全一致                 |
| 异常映射 | 存储后端异常三端统一映射到业务错误码（`B0405` 存储失败 / `B0406` 物理文件丢失），禁止任一端返回原始存储 SDK 异常       |
| 策略选择 | 三端均按 `sys_file.storage` 字段路由后端实例，禁止任一端硬编码存储后端                                                 |

新增存储后端时，三端必须同步实现并在策略工厂注册；契约变更须经 Java 端评审后同步 Go/Python，禁止任一端独立偏离契约。

#### 存储策略清单

| storage 标识   | 存储后端       | baseUrl 配置                                                                      | object_name 示例                               | 适用场景                           |
| -------------- | -------------- | --------------------------------------------------------------------------------- | ---------------------------------------------- | ---------------------------------- |
| `minio`        | MinIO 对象存储 | MinIO 访问地址或下载接口地址                                                      | `upload/20250119/abc.jpg`                      | 用户上传、算法预测结果             |
| `local`        | 本地文件系统   | 本地下载接口地址                                                                  | `upload/20250119/abc.jpg`                      | 开发环境、单机部署                 |
| `nginx-static` | nginx 静态服务 | nginx 静态服务根地址（如 `http://host:19000`，不带 `/datasets` 等资源子路径） | `datasets/AECR-Net/clear/01.jpg`（含资源前缀） | nginx 直服的静态文件（数据集文件） |

nginx 静态服务统一托管多种资源——数据集（`/datasets`）、模型权重（`/models`），将来还可能有 css/js 等。`baseUrl` 配置为服务根地址，`object_name` 自带资源类型前缀（`datasets/...`、`models/...`），新增资源类型无需改配置，只需约定前缀。新增存储后端只需实现 StorageService 接口，并在策略工厂中注册。

## 内部领域对象

### FileBO（文件业务对象）

Service 层内部使用，封装文件上传过程中的中间状态，生命周期仅限于单次请求：

| 字段         | 类型     | 说明                                                              |
| ------------ | -------- | ----------------------------------------------------------------- |
| file         | 临时文件 | 上传的原始文件（处理完成后删除）                                  |
| name         | 字符串   | 原始文件名（用户上传时的名称）                                    |
| objectName   | 字符串   | 存储对象键（含路径，如 `upload/20250119/abc123.jpg`），与环境无关 |
| storage      | 字符串   | 存储后端标识（`minio`/`local`/`nginx-static`），默认按全局配置    |
| extension    | 字符串   | 文件扩展名（小写，如 `jpg`）                                      |
| md5          | 字符串   | MD5 哈希值（32 位十六进制）                                       |
| size         | 长整型   | 文件大小（字节）                                                  |
| userId       | 长整型   | 上传用户 ID（从登录态获取，用于归属校验）                         |
| businessType | 字符串   | 业务类型（`image`/`model`/等），用于按类型校验文件大小上限        |

## 核心业务逻辑

### 关键流程

#### 文件上传流程

Controller 校验文件大小上限（见「核心业务规则」）与安全性 → 计算 MD5 → 构建 FileBO → Service 根据 MD5 查询（事务开始）：MD5 已存在则秒传返回已有记录，不存在则存储物理文件 → 写入元数据记录（object_name + storage + user_id + business_type，不存 url），存储失败事务回滚。

**关键决策点**：

1. **先物理存储，再写元数据**：物理存储在事务内执行。存储失败时事务回滚，不产生孤儿元数据记录。存储成功但 DB 写入失败时产生孤儿物理文件，由孤儿文件清理任务兜底
2. **MD5 计算在 Controller 层**：避免 Service 层依赖文件流，关注点分离
3. **秒传判断在写入前**：减少无效存储操作，命中已有记录时直接返回

#### 文件下载流程

下载接口校验登录态 + 归属（普通用户仅可下载 `create_by=自己` 的文件，管理员全量，越权统一返回 **B0407**）+ 路径安全（`..`、绝对路径、反斜杠拒绝）→ 按 objectName 查 `sys_file`（过滤软删）→ 按 `sys_file.storage` 选后端下载 → 物理文件存在则流式传输（Content-Type 按扩展名推断，Content-Disposition 以 RFC 5987 编码携带原始文件名），不存在则返回 B0406；文件记录不存在则返回 B0401。

下载链路对所有后端统一：按 storage 选 StorageService，调用 download(object_name) 取流转发，无前缀判断、无 302 跳转分支。三端均要求登录（Java 端已取消 download permitAll，Go 端已移入认证路由组）。

#### 文件删除流程

查询文件元数据（过滤软删，不存在返回 B0401）→ 归属校验（同下载，越权 B0407）→ 软删除元数据记录（deleted 写为行 id，事务内）→ 再删除物理文件（事务外，best-effort）。

**设计说明**：软删除配合 MD5 upsert 的 `ON DUPLICATE KEY UPDATE deleted=0` 复活机制——重新上传同 MD5 文件时已软删记录自动复活。物理文件删除失败仅记录日志，产生的孤儿文件由孤儿文件清理任务兜底。不实现引用计数，删除前的引用关系检查由调用方（业务模块）负责。

**批量删除响应**：返回 `{total, succeeded, failed, results}`——不存在的 ID 计入 `failed`，`succeeded` 只按请求 ID 计数（级联删除不计入），`results` 逐 ID 给出明细；空数组返回全 0（不得用 `len(ids)` 假计数）。

### MD5 去重机制

#### 处理流程

| 阶段      | 操作                       | 说明                       |
| --------- | -------------------------- | -------------------------- |
| 1. 计算   | 读取文件流计算 MD5         | 使用流式计算，避免内存溢出 |
| 2. 查询   | `SELECT ... WHERE md5 = ?` | 命中唯一索引，毫秒级响应   |
| 3. 命中   | 返回已有记录               | 秒传，不存储物理文件       |
| 4. 未命中 | 存储文件 + 写入记录        | 首次上传完整流程           |

#### 并发上传同一文件处理

当多个请求同时上传相同文件（MD5 相同）时：

| 场景       | 处理策略                         | 说明                                                                                                                                                           |
| ---------- | -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 并发查询   | 乐观处理                         | 多个请求同时查询 MD5，可能都未命中                                                                                                                             |
| 并发写入   | 唯一索引约束                     | 数据库 MD5 唯一索引保证只有一条记录                                                                                                                            |
| 唯一键冲突 | INSERT … ON DUPLICATE KEY UPDATE | 冲突时复活软删行（deleted=0）并用本次上传的新文件信息覆盖 type/name/object_name/storage/size/size_bytes，避免旧 object_name 指向已被删除的物理文件导致下载失败 |
| 物理文件   | 幂等覆盖                         | 相同对象名重复上传，存储服务幂等处理                                                                                                                           |

**并发安全保证**：即使在 READ COMMITTED 隔离级别下，两个事务可能同时通过 SELECT 检查，但 MD5 唯一索引是最终兜底。冲突时通过 `INSERT … ON DUPLICATE KEY UPDATE` 原子完成"复活 + 覆盖新文件信息"，确保返回的记录 object_name 指向本次实际上传的物理文件。

#### 边界情况

| 场景                                    | 处理方式                                      |
| --------------------------------------- | --------------------------------------------- |
| 0 字节文件                              | 正常计算 MD5，允许上传                        |
| 超大文件（超过对应发布上限）            | Controller 层拦截，抛出文件过大异常（B0402）  |
| MD5 碰撞                                | 理论存在但概率极低（约 2^-128），不做特殊处理 |

### 核心业务规则

| 规则                       | 校验条件                                                                            | 处理方式                                                                                                          | 说明                                                                             |
| -------------------------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 文件大小限制               | 单文件 ≤100MB（三端统一）                                                           | 超限抛出异常（B0402）                                                                                             | -                                                                                |
| 文件类型控制               | —                                                                                   | 文件管理模块不做白名单限制                                                                                        | 由业务模块在调用前控制允许的类型                                                 |
| 文件名安全（三端统一口径） | 先 basename 化剥离路径前缀（`../`、`..\` 不进入存储名），再校验：拒绝空名、`/:*?"<>|` 与控制字符（`\x00-\x1f`）、文件名 >100 字符、扩展名 >20 字符（`sys_file.name`/`object_name` 列宽 varchar(100)） | 非法即拒绝（参数错误），合法路径前缀剥离后保存                                   | 防止路径遍历攻击与入库超长 |
| MD5 唯一性                 | 数据库唯一索引                                                                      | 秒传、去重                                                                                                        | 核心去重逻辑                                                                     |
| 路径规范化                 | 标准化后在基础路径内                                                                | 非法路径拒绝                                                                                                      | 防止目录穿越                                                                     |
| 图片内容校验               | 仅图片扩展名（jpg/jpeg/png/gif/bmp/webp）校验文件头魔数与扩展名一致                 | 不符拒绝（B0403）                                                                                                 | 防止伪装扩展名上传恶意内容；非图片类型不校验                                     |
| 归属校验                   | 普通用户仅可访问 `create_by=自己` 的文件，管理员全量                                | 越权返回 B0407                                                                                                    | 作用于列表、下载、删除、详情；check 秒传预检豁免                                 |

### 事务边界

| 操作     | 事务级别 | 事务范围                         | 说明                                                                |
| -------- | -------- | -------------------------------- | ------------------------------------------------------------------- |
| 文件查询 | 只读事务 | 单次查询                         | 优化数据库连接                                                      |
| 文件上传 | 读写事务 | MD5 查询 → 物理存储 → 元数据写入 | 存储失败回滚，不产生孤儿元数据                                      |
| 文件删除 | 读写事务 | 元数据软删除（写为行 id）        | 物理删除在事务提交后（允许孤儿文件由孤儿文件清理任务兜底）           |
| 批量操作 | 读写事务 | 整批元数据操作                   | 原子性保证                                                          |

**设计考量**：

- **上传事务包含物理存储**：物理存储是外部 I/O 会拉长事务，但上传相对查询属低频操作且单文件存储耗时在秒级，事务持有时间可接受；换来的是存储失败时元数据不入库

### 孤儿文件清理

针对最终一致性删除策略与上传事务回滚产生的孤儿物理文件，由定时对账任务清理。实现由 python 端 xxl-job `cleanupOrphanFiles` 承载（每天凌晨 4 点，扫描 `upload/` 前缀，比对 DB 记录并按保留阈值清理），Java/Go 依赖 python 端运行。

#### 产生场景

| 场景             | 原因                                                 |
| ---------------- | ---------------------------------------------------- |
| 上传事务回滚     | 物理存储成功但 DB 写入失败（事务回滚），物理文件残留 |
| 删除物理文件失败 | 元数据已软删但物理删除失败（best-effort）            |

#### 清理策略

| 清理对象                  | 判定条件                                                         | 处理方式                                                               |
| ------------------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 普通孤儿文件（`upload/`） | 物理文件存在但无未删除元数据引用，且超过保留阈值（默认 48 小时） | 删除物理文件                                                           |
| 去重共享物理文件          | 多元数据引用同一物理文件（同 object_name）                       | 仅当所有引用元数据均已软删时才清理物理文件，避免误删仍被引用的物理文件 |

清理任务分批处理（每批 100 个），避免一次性扫描对存储后端和数据库造成压力。执行参数（Cron、阈值）见配置项。

### 幂等性与并发控制

| 场景             | 问题           | 解决方案                                                     |
| ---------------- | -------------- | ------------------------------------------------------------ |
| 并发删除同一文件 | 双重删除异常   | 删除前查询，记录不存在则返回错误（由调用方决定是否幂等处理） |
| 删除后立即查询   | 查到软删记录   | 元数据软删除（写为行 id），查询自动过滤，走 DB 无延迟        |

### 关键字段约束

### 文件存储路径规则

`object_name`（对象键）按业务来源约定路径前缀，三端一致：

| 路径类型             | 格式                                   | 示例                                    | 存储后端        | 说明                                                                            |
| -------------------- | -------------------------------------- | --------------------------------------- | --------------- | ------------------------------------------------------------------------------- |
| 上传路径             | `upload/{yyyyMMdd}/{md5}.{ext}`        | `upload/20250119/abc123.jpg`            | `minio`/`local` | 按日期分目录，MD5 命名                                                          |
| 导出路径             | `exports/{taskId}.{ext}`               | `exports/550e8400-xxxx.xlsx`            | `minio`/`local` | 导出任务结果文件（通用导入导出框架使用）                                        |
| 导入错误报告         | `imports/{taskId}_errors.{ext}`        | `imports/550e8400-xxxx_errors.xlsx`     | `minio`/`local` | 导入失败行的错误明细报告                                                        |
| 导入上传文件（临时） | `temp/imports/{taskId}/{originalName}` | `temp/imports/550e8400-xxxx/users.xlsx` | `minio`/`local` | 异步导入时暂存的上传文件，任务完成后清理                                        |
| 临时路径             | `temp/{uuid}`                          | `temp/550e8400-e29b...`                 | `minio`/`local` | 处理中的临时文件                                                                |
| 数据集文件           | `datasets/{相对数据集根目录的路径}`    | `datasets/AECR-Net/clear/01.jpg`        | `nginx-static`  | nginx 直服的静态文件，文件已存在于 nginx 目录，仅登记元数据（`saveFileRecord`） |

**命名规则设计考量**：

- 日期目录：便于按时间清理、统计
- MD5 命名：保证唯一性，支持去重（相同 MD5 覆盖写入，天然幂等）
- 扩展名保留：便于识别文件类型、设置 Content-Type

## 缓存设计

文件模块不做缓存设计：文件元数据走数据库主键、唯一索引查询（毫秒级），用户文件列表为分页查询；缓存 TTL 等纯技术参数按配置项设计规范以代码常量承载。

## 安全设计

### 下载鉴权：登录 + 归属校验

下载接口要求登录，普通用户仅可访问 `create_by=自己` 的文件，管理员全量，越权统一返回 **B0407**。责任边界：复杂业务归属规则（数据集文件归属数据集所有者等）由业务模块在自身接口层校验后引用文件。

### 安全防护

| 防护项       | 威胁                   | 实现方式                                                |
| ------------ | ---------------------- | ------------------------------------------------------- |
| 下载路径安全 | 内部路径泄露           | objectName 参数校验：禁止 `..`、绝对路径、反斜杠        |
| 越权访问     | 下载、删除、查询他人文件 | 登录 + create_by 归属校验，越权 B0407                   |
| 伪装扩展名   | 恶意内容上传           | 图片扩展名文件头魔数校验（B0403），非图片类型不校验     |
| MD5 完整性   | 文件篡改检测           | 上传时计算存储，下载时可验证                            |

## 性能目标

### 性能指标

| 接口             | 目标 P99 | 约束条件      | 说明                                   |
| ---------------- | -------- | ------------- | -------------------------------------- |
| 文件上传         | < 3s     | 文件 ≤ 10MB   | 流式上传，主要耗时在网络传输和物理存储 |
| 文件下载         | < 1s     | 首字节时间    | 流式传输，总时间取决于文件大小         |
| MD5 查询         | < 100ms  | —             | 必须走唯一索引                         |
| 文件列表         | < 500ms  | 分页 ≤ 100 条 | 分页查询                               |
| 秒传判断         | < 200ms  | —             | MD5 查询 + 响应封装                    |
| 去重校验         | < 100ms  | —             | 前端预检接口                           |
