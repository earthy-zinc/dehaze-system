# AI 对话模块架构收敛方案

结论：三端各自原生实现同一套新契约，旧协议、旧字段、旧代码与旧数据一次删除。不做迁移、不做双读双写、不做版本协商。推理流仍由 Python 产生，Java 与 Go 负责转发；会话、消息、产物、反馈的读写三端同等实现。

## 目标模型

消息只有一种形状：

    Message {
      id, conversationId, parentMessageId, role,
      status: running | completed | failed | canceled | awaiting_input,
      model, error,
      blocks: Block[],
      plan?, pendingInterrupt?,
      usage,
      artifactIds, memoryIds, suggestions?
    }
    Block { id, kind: text | thinking | tool_use, seq, payload }

`seq` 表示同一消息内同 kind 块的先后。渲染按分区，思考、工具、正文各归各位，不做跨 kind 交错；需求要的分区内保序由此满足，不需要把 index 当时间轴。

`status` 只表达本轮通道，等待确认由 `awaiting_input` 与 `pendingInterrupt` 表达。`plan` 持久化在消息上，修订记录带 actor 与时间。`pendingInterrupt` 持久化并带 `expiresAt`、`actionable`，resume 从持久状态恢复。

产物与反馈是独立资源，消息只存引用。分支是会话级指针加兄弟派生，不进消息。

## 契约与三端实现

契约以 JSON Schema 为唯一来源，生成 TypeScript、Java、Go、Python 的 DTO。三端只写实现，不手抄类型，仓库里出现第二份同名字段即为错误。

三端职责对等：会话与消息的增删改查、历史读模型、产物、反馈都由各自原生实现，共用同一套表与同一套状态机。推理 SSE 仍由 Python 产生，Java 与 Go 只做转发与鉴权，这部分不可能在另外两栈重写。

三端行为靠对拍守住：同一份 fixture 分别打三个端口，逐字段比较响应与事件序列；状态机、错误码、分页、权限、审计字段全部纳入。

## 数据处理

不做迁移。上线前清空 AI 对话域的存量数据：会话、消息、推理步骤、产物、AI 反馈，以及 ES 中对应的消息索引与 trace 记录。清空后由新实现从零写入。

清库是一次性运维动作，脚本放在 `scripts/` 之外，执行前按环境确认目标库。代码里不出现任何兼容旧数据的分支。

## 删除清单

协议：`content_block.start/delta/stop`、`thought`、`message.end` 的旧形状，以及 SDK 里的旧事件分发。

字段：`content`、`tool_calls`、`tool_call_id`、`metadata` 中承载执行态的旧键，`sys_ai_message` 的旧列。

代码：Java 与 Go 的旧会话实现、Python 的旧 router 与旧 reducer、前端五张侧表、`MessageViews`、`useChatVmBinding` 的投影复制、兼容网关里的旧事件解析。

测试：围绕旧模型的用例一并删除，只保留新契约的 golden、对拍与状态机用例。

## 实施顺序

1. 定 JSON Schema，生成四端 DTO，补契约测试骨架。
2. Python 实现新的写入、历史读模型、产物、反馈、中断与计划持久化。
3. Java 与 Go 按同一 Schema 原生实现会话与消息读写；SSE 维持转发。
4. 前端只按新协议重写 transport 与 store，组件保持零 store、零 SDK。
5. 清空存量数据与 ES 索引，切换流量。
6. 删除旧协议、旧字段、旧代码、旧测试与旧文档。

前三步可以并行，但都以 Schema 冻结为起点；第 5 步是切换点，之前不产生新老并存的运行态。

## 验收

三端对同一 fixture 的响应逐字段一致，事件序列一致，错误码与分页边界一致。

同一条消息从流式结束态与刷新后历史读出的 DOM 相同。

中断刷新后能查、能续；超出 `expiresAt` 明确标注不可续。

一百条历史消息、六十帧增量下，前端投影调用不超过 61 次，未变化消息对象引用不变。

仓库内不再出现 `content` 字段、旧事件名与旧类型。

## 风险

清库不可逆，执行前必须确认环境与表清单。三端原生实现的漂移风险靠 Schema 生成与对拍控制，不靠人工同步。发布期间旧页面会因协议不兼容而无法使用，需配合构建版本校验强制刷新；这是明确接受的代价。

## 需要确认

清库范围是否只到 AI 对话域，还是连同 trace、llm_call、计费流水一起清。计费流水涉及账务，默认不动。

切换窗口选在哪个环境先执行，dev、pre、prod 的顺序与回滚方式。

Java 与 Go 的原生实现是否包含管理端审计查询，还是审计单独排期。
