## 待裁决

- `sys_ai_model.image_tokens_per_image` / `concurrency_limit`、`sys_algorithm.recommend_score`：全端零代码引用、仅文档标注为规划功能，疑似真废弃，待裁决是否删除。
- `agentCode` 取值＝子 Agent 名称；稳定 code 需给 schema 加列，属独立立项。
- 产品待确认：权益前端合并粒度（最低剩余 vs 求和）、会员降级宽限期、配额顺延口径、组合支付三端完整链路（依赖余额账户子系统）、聊天历史游标分页后续扩展。
- 火山语音单密钥（X-Api-Key）端到端未打通（待决策）：报文、鉴权实现正确（头名 `X-Api-Key`、v3 端点、`resource-id` 头均被识别），失败点全在环境、账号侧——①默认语音模型不走 volc（`sys_dict ai_model.default_model.tts/asr` 指向 `local-voice` 的 `openai_audio`）；②供应商密钥密文与运行进程加密 key 不一致（解密钥抛 `ValueError: Invalid padding bytes`，临时判定手法：用 `sha256("change-me-to-a-random-secret")` 试解 DB 密文）；③python TLS 无默认 CA（`ssl.create_default_context()`/websockets 连 volc 报 `CERTIFICATE_VERIFY_FAILED`，httpx 走 certifi 不受影响）；④火山账号未开通语音资源（真 key 直连 ASR/TTS 均 403 `requested resource not granted`，扫遍常见 resource-id 全 not granted ⇒ 非 id 写错）。复测前先确认 ①②③ 是否已修。403 会经适配器 `mark_call_failed` 写 Redis `ai:provider_key:{id}:unavailable`（约 30min 自愈）⇒ 复测见"无可用 Key"先看该冷却 key，而非误判为配置问题。
- `clarity-mcp-gateway` 的 venv 与声明依赖漂移（待决策是否 `uv sync`）：网关 `.venv` 实装 `mcp 2.0.0`（`pyproject.toml`/`uv.lock` 要求 `>=1.24.0,<1.25.0`）且缺 `pytest`（`tests/` 在网关自身 venv 里跑不起来；mcp 2.0 已把 `mcp.server.fastmcp` 改名，`server.py` 在该 venv 下导入失败）；网关经 `uv run python server.py` 用自己的 `.venv` 启动（`run.py` 的 mcp 服务项）。判据：静态门禁 `clarity-python/scripts/check.sh` 按声明依赖口径统一走 `clarity-python/.venv`（mcp 1.24 + pytest）、不读网关自身 venv ⇒ 门禁全绿不代表网关运行环境正确，两者不可互相推断；动网关前先确认是否已 `uv sync`。
