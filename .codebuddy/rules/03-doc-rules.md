# 文档编写、整理与优化

> **定位**：本文档是 dehaze 文档体系的元规则，同时约束**体系治理**（分区职责、单一信息源、变更流程、命名、内容禁令）与**撰写操作**（各文档类型边界、引用与评审标准），是二者唯一的规则信息源（原 `dehaze-doc/docs/00-文档治理/` 分区已废止）。文档的新增、修改、评审均须遵循。
>
> **总目标**：每个事实只在唯一定义位置存在（引用而非复制）；文档反映当前契约与代码最新状态；删除状态标记、演进记录、过程校正等低信息量内容，保持信息密度。

## 一、分区职责与归属判定

| 分区            | 职责                                                             | 禁止内容                        |
| --------------- | ---------------------------------------------------------------- | ------------------------------- |
| **01-产品设计** | 产品概述、设计规范、规划（面向产品与体验）                       | 技术实现细节（如具体 API 字段） |
| **02-系统架构** | 技术底座：总体架构、数据库、API 规范、测试、部署、日志           | 单一模块的细节                  |
| **03-模块设计** | 按模块组织：需求规格 / API 接口 / 前端实现 / 后端实现 / 测试用例 | 跨模块的全局规范                |
| **04-项目实现** | 各技术栈架构文档（前端 / 后端 / 算法）                           | 业务需求                        |
| **05-改造计划** | 已决策的改造与升级规划                                           | 未评审的设想                    |

**归属判定**：跨模块、跨端的问题 → 01/02；单一模块的问题 → 03；纯技术栈 → 04。拿不准时按"更高一层"归属，避免碎片化。文档治理规则（本文档）不占 `dehaze-doc` 分区，先于其他分区生效。

模块内文档定位：需求规格 = 做什么（产品视角）、API接口 = 什么契约（接口层面）、后端实现 = 后端怎么做、前端实现 = 前端怎么做、测试用例 = 怎么验证。引用层级：02-系统架构（全局约定）→ 03-模块设计（模块规格）→ 04-项目实现（技术栈架构）。

## 二、单一信息源与内容禁令

### 2.1 定义位置与引用方式

| 事实类型       | 定义位置                                           | 引用方式                       |
| -------------- | -------------------------------------------------- | ------------------------------ |
| 产品术语       | `dehaze-doc/docs/01-产品设计/06-文案与术语规范.md` | 直接引用术语表，不复制定义     |
| 导航与页面层级 | 移动端/桌面端界面设计规范、菜单与页面层级规划      | 引用其层级归属，不另起炉灶     |
| 权限模型       | 权限相关规范（规划中）                             | 各模块权限点引用统一矩阵       |
| 模块能力       | 对应模块的《需求规格》                             | 其他文档引用该规格，不重复描述 |
| API 定义       | 对应模块的《API接口》                              | 前端实现/测试用例引用接口定义  |
| 错误码         | 页面状态与错误码规范（规划中）                     | 前后端文档引用错误码表         |

- 禁止在多份文档中复制同一份定义（术语、权限、错误码、接口字段）；复制导致的口径漂移（同一事物两处定义不一致）视为文档缺陷，评审发现须立即收敛。
- 引用须给出明确文件路径（如 `dehaze-doc/docs/01-产品设计/06-文案与术语规范.md`），禁用"见上文/详见之前"等模糊表述。

### 2.2 状态标记与演进内容禁令

文档只描述**当前契约**（"是什么、为什么这样设计"），禁止混入演进状态与过程记录：

| 禁止项                                           | 正确做法                                                                    |
| ------------------------------------------------ | --------------------------------------------------------------------------- |
| "✅ 已实现 / ⏳ 规划中 / 远期"状态标记           | 删除标记；规划内容迁入 `dehaze-doc/docs/05-改造计划/`，需求规格只写当前契约 |
| "早期需求稿…当前未实现"校正注释                  | 删除；未实现的表述属规划，不入需求规格                                      |
| "本版新增 / 本次改造说明"演进说明                | 删除；版本演进记录不入正式文档                                              |
| 待确认事项混入已定决策                           | 已定决策写入正文；仅真正未决问题保留在待确认事项                            |
| "文档口径 vs 代码现状 / 收敛状态 / 待裁决"登记表 | 删除；实现类文档只写当前口径，收敛台账与待裁决项归 `05-改造计划/`           |

### 2.3 同质化冗余过滤

同一模块目录下，不同文档禁止出现以下同质化内容：

| 冗余模式                           | 正确做法                                   |
| ---------------------------------- | ------------------------------------------ |
| 需求规格和测试用例都列出完整功能点 | 测试用例引用需求规格的功能点编号           |
| API 接口和后端实现都描述参数结构   | API 接口定义契约，后端实现引用 API 接口    |
| 前端实现和后端实现都描述业务流程   | 后端实现描述业务逻辑，前端实现描述交互架构 |
| 各模块文档都重复描述同一个公共组件 | 只在公共模块文档中描述，其他模块引用       |

### 2.4 表述层面禁令（越界黑话 / 常识填充 / 情绪化强调 / 开发日志化）

文档的每一句都应携带信息量。以下表述一律删除或改写：

| 禁止模式      | 反例                                                                                                                  | 正确做法                                                                                                                                  |
| ------------- | --------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 实现黑话越界  | 需求规格/产品文档写"按 `task_tags` 路由分发""经 WebSocket 推送进度""用 Redis 分布式锁"                                | 需求层只写产品行为（"按任务类型自动选模型""进度实时可见"）；实现手段只出现在 API接口 / 后端实现 / 前端实现 / 04-项目实现                  |
| 常识当卖点    | 把"URL 不落库""路径相对仓库根""使用参数化查询"当作约定或亮点单列                                                      | 删除；通用工程常识、框架默认行为不是特色                                                                                                  |
| 应然事项叮嘱  | 额外补一句"注意不要写死机器路径""记得重启服务"                                                                        | 删除；本就应该做到的事无需提醒，属噪声                                                                                                    |
| 情绪化/营销化 | "彻底解决""极致性能""无替代，必须保留""并未下线"（无客观约束支撑时）                                                  | 改为中性事实陈述（"是去雾核心服务"）；仅当存在真实约束/禁令时才用"必须/禁止"                                                              |
| 开发日志化    | 设计/架构文档里写实测耗时、踩坑记录、排障步骤、工具自测入口、日期流水（"2026-10-01 实测…""踩过的坑""自测 75 条断言"） | 只写设计与其取舍；实测数据 / 踩坑 / 排障 / 自测入口属**程序性知识**，进 skill（`dehaze-project-knowledge`）或代码注释，不堆进架构设计文档 |

> 判据：不了解本项目的读者读完该句，是否获得新信息或避免踩坑？否则删除。

## 三、各文档类型边界

| 文档类型        | 写什么                                                                                                                                                                                                  | 不写什么                                                                                                                                                                                                     |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **需求规格**    | 模块定位与价值、角色与权限、功能需求（输入输出/业务规则）、交互规范（只说行为）、性能目标、依赖关系、待确认事项                                                                                         | 技术实现手段（算法/框架/中间件/BCrypt/HTTPS/加密哈希）、接口定义（URL/方法/参数/协议族/WS 指令）、数据库表结构（表名/字段名）、配置键与错误码、类名与适配器规则、代码片段 —— 一律转为"需做 X"的产品表述      |
| **API接口**     | 接口清单（路径/方法/功能描述/权限标识/关联功能点）、权限标识汇总、业务错误码、文档概述（基础路径 + 公共约定引用）                                                                                       | 详细请求/响应结构（在代码中定义，避免手写两套）、实现逻辑（属后端实现）、curl/axios 调用示例、前端调用说明                                                                                                   |
| **后端实现**    | 服务层设计（核心服务接口与方法职责）、核心业务流程（步骤与决策）、安全设计与配置、缓存策略（对象/Key/过期）、配置项及默认值、模块间协作                                                                 | 代码片段、Bug 修复记录与"旧 XX 已删除"、逐日开发日志、ORM 配置/索引建议/SQL 优化等过度细节、待办计划与待裁决/待立项（属 05）、数据库表结构（引用 02-系统架构/03-数据库设计.md）                              |
| **前端实现**    | 组件树与职责划分、状态管理（Store 划分/核心状态与操作）、路由设计（配置/守卫/权限）、数据流（获取/缓存/更新）、关键交互的技术选型与理由、公共组件使用及配置要点                                         | 组件与样式代码、API 调用细节（axios 封装/拦截器）、UI 组件库基础用法、开发日志、工具链配置（属 04-项目实现）、待裁决/待立项（属 05）                                                                         |
| **测试用例**    | 测试目标与覆盖场景、测试前置（数据准备/清理策略/范围含不含）、用例清单（ID/场景/前置/输入/期望输出/优先级）、关键边界与异常、性能与并发、安全性验证点                                                   | UI 测试细节（断点/渲染）、测试框架代码、已在需求规格定义的功能描述（引用即可）、环境搭建步骤（属 02-系统架构/05-测试架构.md）、测试工具使用方法                                                              |
| **04-项目实现** | **必须含至少一幅 Mermaid 架构图**（后端：分层与模块交互；前端：组件分层/数据流/路由；算法：管线与服务交互）、目录结构及分层职责、核心模块职责与技术要点、关键技术决策及理由、设计原则与约束、模块间交互 | 超过 5 行的代码块、Bug 修复记录、开发日志/版本迭代记录、"后续优化方向"（移至 05）、具体模块需求/接口/实现（引用 03）、工具链配置（Maven/Gradle/ESLint/Prettier）、"项目亮点"式罗列、Swagger/Knife4j 在线地址 |

| **数据库设计** | 数据库选型、多库职责划分、ER 关系、**跨表设计决策**（如逻辑删除与唯一键、状态字段编码、缓存键、`tree_path`）、存储规范 | 逐表字段/类型/默认值/索引（权威在 `config/sql/schema/*.sql` 表头注释与列 COMMENT）、单表枚举逐值解释、表结构变更与迁移叙事（属演进记录） |

## 四、文档变更流程

**触发条件**（满足任一即须同步更新文档）：

| 变更                    | 必须更新的文档                                                  |
| ----------------------- | --------------------------------------------------------------- |
| API 请求/响应参数增删改 | 模块《API接口》+ 受影响的前端实现 + 测试用例                    |
| 数据流/架构调整         | 系统架构文档 + 相关模块文档                                     |
| 新增/调整页面或菜单     | 菜单与页面层级规划 + 对应端路由/菜单说明                        |
| 新增模块                | 按模块模板建目录（需求规格/API接口/前端实现/后端实现/测试用例） |
| 术语/文案变更           | 文案与术语规范 + 全端文案                                       |
| 设计规范变更            | 对应规范文档 + 引用该规范的模块文档                             |

**步骤**：① 先全局搜索引用点，定位全部受影响文档（不凭记忆）；② 修改单一信息源处（术语表、API 定义）；③ 同步所有引用方 —— 引用方只更新引用关系，不复制新内容；④ 代码与文档同时提交，禁止"先改代码、文档后补"或反之拖延。

**新增文档准入**：内容有明确归属分区（§一）；优先扩展已有文档而非新建；与现有文档不重复（重复则拒绝，改引用）。

**文档退役**：改造计划落地后，其结论并入对应现状文档（02/03/04），**原改造计划文档删除**；`05-改造计划/` 只保留"未落地 / 在办"内容（已落地项最多在总览留一行记录，不保留整篇设计文档）。已失效的引用、被取代的旧设计一并删除，不做留档。

**侧边栏同步**：新增 / 删除 / 重命名文档必须同步 `dehaze-doc/docs/.vitepress/config.ts` 的 sidebar 分区。sidebar 指向不存在文件（死链）或磁盘文档未登记（孤儿）均视为文档缺陷，评审发现须修复。

**代码一致性**：文档字段名与代码字段名严格一致（改名时全局搜索一并修改，不保留旧字段兼容）；示例请求/响应与真实 API 一致，禁止虚构字段；页面状态（加载/空/错误）、错误码以文档为准、代码对齐；同一 API 在各端（Web/移动/桌面）文档中描述一致。

## 五、命名与引用规范

| 维度       | 规范                                                                                                                                                                                        |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 目录命名   | 序号-名称（如 `01-产品设计`、`02-系统架构`），模块目录用中文功能名                                                                                                                          |
| 文件命名   | 序号-名称.md（如 `06-文案与术语规范.md`）；模块内固定：需求规格/API接口/前端实现/后端实现/测试用例                                                                                          |
| 命名唯一性 | 文件名**区分大小写不视为独立文档**；新增前检索现有文件（含大小写变体），重复或混淆则合并/重命名                                                                                             |
| 标题       | 一级标题 = 文档名；层级 1-3 级，不跳级；编号连续、不跳号；文档须自洽（不得是更大文档的残余片段）                                                                                            |
| 表格与图   | 信息类内容优先表格，表头明确；架构/流程/层级用 Mermaid（已集成 vitepress-plugin-mermaid）                                                                                                   |
| 链接       | 相对路径（`./xxx.md` 或 `../xxx/xxx.md`）；模块文档跨层引用层级固定：同级 `../`、核心模块 → 基础模块 `../../基础模块/`、指向 docs 根 `../../../02-系统架构/`；cleanUrls 生效，不写 .md 后缀 |
| 术语       | 全文使用 `dehaze-doc/docs/01-产品设计/06-文案与术语规范.md` 规范术语                                                                                                                        |

**引用原则：非必要不引用**，以下引用必须删除：

| 禁止场景       | 说明                                                                                |
| -------------- | ----------------------------------------------------------------------------------- |
| 完整信息已内嵌 | 引用的全部内容已在当前文档写完（如已列接口清单又写"详见 API接口.md"）               |
| 锦上添花式引用 | 对理解当前文档无实质帮助（如需求规格末尾"另请参阅 02-系统架构/01-总体架构设计.md"） |
| 引用自身       | 同模块文档间的"详见"而内容本可内嵌                                                  |
| 通用规范引用   | 引用全系统通用约定作免责声明（如"Token 校验失败返回 401，详见 API 规范"）           |
| 转述式引用     | 「XX 由 Y 实现，详见 Z」，而该信息对当前上下文无增益                                |

> 引用应指向**稳定锚点**：**跨文档引用一律给文件级相对路径，禁止带「§x.y」章节号**（章节调整即失效，徒增维护成本）；同文档内小节互引也应最小化。一句话能说清的不引用整篇文档。

## 六、评审与自查

**编写前**：确认内容不存在于其他文档、选对文档类型、不越界。**编写时**：优先表格呈现，引用用相对路径，架构文档从 Mermaid 图出发。**编写后**：对照下表逐项自审通过再提交。

| 检查项      | 通过标准                                                             |
| ----------- | -------------------------------------------------------------------- |
| 边界清晰    | 内容不越界（需求不写实现，API 不写逻辑，测试不写 UI 细节）           |
| 零代码片段  | 无超过 5 行的代码块                                                  |
| 零日志记录  | 无"已修复/已删除/已重构"等历史变更表述                               |
| 零重复内容  | 相同信息不在多份文档出现（引用代替复制）                             |
| 引用最小化  | 无锦上添花式、引用信息已内嵌、免责声明式通用规范引用                 |
| 有架构图    | 04-项目实现 每篇至少一幅 Mermaid 架构图                              |
| 无过度细节  | 无 ORM 配置、SQL 优化、工具链配置等琐碎内容                          |
| 无待办/计划 | 无"待实现/计划中/后续优化"；规划内容只在 05-改造计划                 |
| 无状态标记  | 无"已实现/规划中/远期"标记与"早期需求稿/本版/本次改造"校正或演进记录 |
| 命名与链接  | 命名、分区归属符合 §一/§五，无大小写重复；链接有效、无失效引用       |
