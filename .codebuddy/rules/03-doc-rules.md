# 文档编写、整理与优化

## 一、核心原则

- **单一信息源**：同一事实只写一处
- **引用代替复制**：避免多处维护同一内容
- **按业务领域组织**：不按技术栈拆散同一模块
- **扁平化**：目录深度建议 ≤ 3 层
- **只写设计，不写日志**：文档描述"是什么"和"为什么这样设计"，禁止包含开发过程记录、Bug 修复记录、逐日变更日志
- **最小必要信息**：每个文档仅包含理解该领域设计所必需的、不可替代的关键信息
- **减少不必要的引用**：仅保留对理解当前文档内容必不可少的引用链接。禁止"另请参阅""延伸阅读"等锦上添花式引用；禁止为引用而引用的冗余交叉链接。如果引用的内容读者不看也能理解当前文档，则该引用是多余的

## 二、项目文档位置

所有项目文档存放在 `dehaze-doc/docs/` 目录下

```
dehaze-doc/docs/
├── 01-产品设计/          # 产品概述、UI-UX 设计规范
├── 02-系统架构/          # 总体架构、环境兼容性、数据库设计、API 规范、测试架构、部署架构
├── 03-模块设计/          # 各模块的需求规格、API 接口、后端/前端实现、测试用例
│   ├── 基础模块/
│   └── 核心模块/
├── 04-项目实现/          # 各技术栈的架构文档
│   ├── 前端/
│   ├── 后端/
│   └── 算法/
└── 05-改造计划/
```

### 文档层级与引用关系

```
02-系统架构（全局约定、通用规范）
    ↓ 引用
03-模块设计（各模块的具体规格）
    ├── 需求规格.md      ← "做什么"（产品视角）
    ├── API接口.md       ← "什么契约"（接口层面）
    ├── 后端实现.md       ← "后端怎么做"（后端架构层面）
    ├── 前端实现.md       ← "前端怎么做"（前端架构层面）
    └── 测试用例.md       ← "怎么验证"（测试层面）
    ↓ 引用
04-项目实现（各技术栈的宏观架构与设计决策）
```

## 三、各文档类型撰写标准

### 3.1 需求规格文档

**定位**：从产品视角描述"做什么"与"需要什么"，是产品与开发的共同契约。

#### 允许的内容

| 内容类别 | 说明 | 示例 |
|---------|------|------|
| 模块定位与价值 | 模块解决什么问题、为谁服务 | "用户管理模块为系统提供统一用户身份识别与权限分配" |
| 用户角色分析 | 角色定义、权限矩阵 | "系统管理员拥有全部操作权限" |
| 功能需求 | 功能描述、输入输出、业务规则 | "用户列表支持按部门筛选，包含下级部门" |
| 交互规范 | 页面布局、交互行为（只说行为不说实现） | "点击部门节点后筛选用户并重置到第一页" |
| 性能目标 | 用户可感知的性能指标 | "列表查询响应 < 500ms" |
| 依赖关系 | 本模块依赖/被依赖的其他模块 | "用户管理依赖部门管理模块" |
| 待确认事项 | 产品层面尚未确定的决策 | "用户名是否允许修改？" |

#### 禁止的内容

| 禁止项 | 说明 | 反例 |
|--------|------|------|
| **技术实现细节** | 具体算法、框架、中间件选型 | ❌ "使用 BCrypt 算法加密存储" → 应写 "密码需加密存储" |
| **接口定义** | URL、请求方法、参数结构 | ❌ 定义 POST /api/v1/users → 属于 API接口.md |
| **架构设计** | 分层架构、技术选型 | ❌ "使用 Validation 注解进行参数校验" → 应写 "需进行参数校验" |
| **数据库设计** | 表结构、字段定义 | ❌ 定义 sys_user 表字段 → 属于 02-系统架构/03-数据库设计.md |
| **代码片段** | 任何形式的代码 | ❌ 给出 SQL 示例、Java 代码 |
| **安全实现手段** | 具体的安全技术方案 | ❌ "HTTPS 加密传输" → 应写 "数据传输需加密" |

#### 典型错误与修正

```
错误写法（混入实现）:
  "密码加密：使用 BCrypt 算法加密存储"
  "防重复提交：使用 Token 机制防止重复提交"

正确写法（纯需求）:
  "密码安全：密码不可明文存储"
  "防重复提交：同一操作不可重复提交"
```

### 3.2 API 接口文档

**定位**：该模块 API 契约的唯一权威来源。描述接口"是什么"，不描述"怎么实现"。

#### 允许的内容

| 内容类别 | 说明 |
|---------|------|
| 接口清单 | 路径、方法、功能描述、权限标识、关联功能点 |
| 权限标识汇总 | 模块涉及的所有权限标识及含义 |
| 业务错误码 | 错误码、说明、触发场景 |
| 文档概述 | 基础路径、公共约定引用 |

#### 禁止的内容

| 禁止项 | 说明 | 归属 |
|--------|------|------|
| **详细请求/响应结构** | 可通过 OpenAPI Spec / MCP 查询得到 | 避免手写维护 |
| **实现逻辑说明** | 接口内部如何处理 | 属于后端实现.md |
| **调用示例代码** | curl、axios 等代码示例 | 低价值，容易过期 |
| **前端调用说明** | 哪个页面调用什么接口 | 属于前端实现.md |

#### 接口文档最小结构

```markdown
# [模块名] API 接口

## 1. 文档概述
- 基础路径
- 公共约定引用（→ 02-系统架构/04-API规范.md）

## 2. 接口清单
| 路径 | 方法 | 功能描述 | 权限标识 | 关联功能点 |

## 3. 权限标识汇总
| 权限标识 | 说明 |

## 4. 业务错误码
| 错误码 | 说明 | 触发场景 |
```

### 3.3 后端实现文档

**定位**：描述后端对该模块的设计方案，聚焦**架构层面的决策**，而非代码细节。

#### 允许的内容

| 内容类别 | 说明 | 示例 |
|---------|------|------|
| 服务层设计 | 核心服务接口、方法职责 | "UserService 负责用户 CRUD 及密码管理" |
| 核心业务流程 | 关键业务流程的步骤与决策 | "用户新增流程：校验 → 唯一性检查 → 加密 → 入库 → 角色关联" |
| 数据传输对象 | DTO/VO 的结构与用途（表格式） | UserPageQuery 包含哪些查询字段 |
| 安全设计 | 模块级安全策略与配置 | "密码最小长度 8 位，包含字母和数字" |
| 缓存策略 | 缓存对象、Key 设计、过期策略 | "用户信息缓存 30 分钟" |
| 配置项 | 模块相关可配置参数及默认值 | "默认密码：Dehaze2026" |
| 模块间协作 | 与其他模块的集成方式 | "导入导出由通用框架统一调度" |

#### 禁止的内容

| 禁止项 | 说明 | 反例 |
|--------|------|------|
| **代码片段** | 任何形式的代码块 | ❌ Java 代码示例、SQL 语句 |
| **Bug 修复记录** | 历史问题及修复过程 | ❌ "旧的 ExcelUtils 已全部删除" |
| **开发日志** | 逐日的开发过程 | ❌ "2024-03-01 完成用户列表接口" |
| **过度细节** | 表索引建议、SQL 优化技巧、OR/M 配置细节 | ❌ "合理使用索引覆盖" |
| **待办/计划** | 尚未实现的功能规划 | 属于 05-改造计划 |
| **数据库表结构** | 表字段定义 | 引用 02-系统架构/03-数据库设计.md |

#### 典型错误与修正

```
错误写法（Bug 修复记录）:
  "说明：旧的 ExcelUtils、UserImportListener、UserImportVO、UserExportVO、
   静态模板文件已全部删除，由通用框架替代。"

正确写法（引用设计）:
  "导入导出由通用导入导出框架统一调度，模块侧实现 UserExportHandler 
   和 UserImportHandler 接口，详见[任务管理/后端实现.md]（../任务管理/后端实现.md）。"
```

### 3.4 前端实现文档

**定位**：描述前端对该模块的设计方案，聚焦组件架构、状态管理、路由设计等**架构决策**。

#### 允许的内容

| 内容类别 | 说明 |
|---------|------|
| 组件树设计 | 页面组件层次结构、组件职责划分 |
| 状态管理 | Store 模块划分、核心状态与操作 |
| 路由设计 | 路由配置、导航守卫、权限控制 |
| 数据流 | 数据获取、缓存、更新策略 |
| 交互设计决策 | 关键交互的技术选型与理由 |
| 公共组件的使用 | 使用了哪些公共组件及其配置要点 |

#### 禁止的内容

| 禁止项 | 说明 |
|--------|------|
| **代码片段** | Vue/React 组件代码、样式代码 |
| **API 调用细节** | axios 封装、拦截器实现 |
| **UI 组件库使用** | Element Plus/Ant Design 组件的基础用法 |
| **开发日志** | 功能迭代记录 |
| **重复规范内容** | ESLint、Prettier 等工具链配置（属于项目实现文档） |

### 3.5 测试用例文档

**定位**：定义该模块的测试场景与验收标准。聚焦"测什么"和"期望是什么"，不描述"怎么测"。

#### 允许的内容

| 内容类别 | 说明 |
|---------|------|
| 测试目标 | 验证哪些功能、覆盖哪些场景 |
| 参考文档 | 引用需求规格、API 接口、实现文档 |
| 测试前置 | 测试数据准备、数据清理策略、测试范围（含/不含） |
| 用例清单 | 用例ID、场景、前置条件、输入、期望输出、优先级 |
| 关键边界与异常 | 边界条件和异常场景的测试点 |
| 性能与并发 | 性能指标验证、并发场景 |
| 安全性测试 | 权限控制、注入防护等安全验证点 |

#### 禁止的内容

| 禁止项 | 说明 | 归属 |
|--------|------|------|
| **UI 测试细节** | 响应式断点、组件渲染细节 | 属于前端实现文档 |
| **测试代码** | 测试框架的具体代码 | 代码仓库中 |
| **重复需求内容** | 已在需求规格中定义的功能描述 | 引用即可 |
| **环境配置** | 测试环境搭建步骤 | 属于 02-系统架构/05-测试架构.md |
| **测试工具使用** | Vitest/Jest 等工具的使用方法 | 属于测试架构文档 |

### 3.6 项目实现架构文档（04-项目实现）

**定位**：描述该项目（技术栈）的**宏观架构**与**核心技术决策**。阅读对象是希望理解该项目整体设计的新成员。

#### 必须包含的内容

| 内容类别 | 说明 | 示例 |
|---------|------|------|
| **架构图**（Mermaid） | 系统分层、模块交互、数据流 | 分层架构图、核心流程图 |
| **目录结构** | 项目文件组织及分层职责 | src/main/java 各包职责 |
| **核心模块说明** | 关键模块的职责与技术要点 | "安全认证模块"、"文件管理模块" |
| **关键技术决策** | 重要的技术选型及其理由 | "为什么选择 MinIO 而非 OSS" |
| **设计原则与约束** | 项目遵循的设计原则 | "策略模式统一多存储后端" |
| **模块间交互** | 该技术栈如何与其他端/服务通信 | "通过 RESTful API 调用 Python 算法服务" |

#### 禁止的内容

| 禁止项 | 说明 | 反例 |
|--------|------|------|
| **代码片段** | 超过 5 行的代码块 | ❌ 完整的 Controller 实现代码 |
| **Bug 修复记录** | 历史问题修复过程 | ❌ "修复了 XX 空指针异常" |
| **开发日志/迭代记录** | 逐日/逐版本开发记录 | ❌ "v1.2.0 新增了 XX 功能" |
| **"后续优化方向"** | 尚未实施的优化设想 | 若确有必要记录，移至 05-改造计划 |
| **重复模块设计内容** | 各模块的具体需求/接口/实现 | 引用 03-模块设计 |
| **琐碎配置说明** | Maven/Gradle/ESLint/Prettier 等工具链配置 | 这些是工具使用的常识 |
| **"项目亮点"罗列** | 类似宣传材料的特性枚举 | 应融入架构说明而非独立罗列 |
| **接口文档链接** | Swagger/Knife4j 等在线文档地址 | 这不是架构文档的内容 |

#### 架构图要求

每个项目实现架构文档必须包含至少一幅 Mermaid 架构图：

- **后端文档**：分层架构图（表示层 → 业务层 → 数据层）、核心模块交互图
- **前端文档**：组件分层图、数据流图、路由结构图
- **算法文档**：算法管线图、服务交互图

## 四、文档质量评审机制

### 4.1 自动检查清单

编写或评审文档时，逐项检查：

| 检查项 | 通过标准 |
|--------|---------|
| **边界清晰** | 每个文档的内容不越界（需求不写实现，API不写逻辑，测试不写UI细节） |
| **零代码片段** | 无超过 5 行的代码块 |
| **零日志记录** | 无"已修复""已删除""已重构"等历史变更表述 |
| **零重复内容** | 相同信息不在多份文档中出现（引用代替复制） |
| **引用最小化** | 无锦上添花式引用、无引用信息已内嵌的冗余链接、无免责声明式通用规范引用 |
| **引用有效** | 所有保留的文档间引用路径正确 |
| **有架构图** | 04-项目实现 每个文档包含至少一幅 Mermaid 架构图 |
| **无过度细节** | 不包含 ORM 配置、SQL 优化、工具链配置等琐碎内容 |
| **无待办/计划** | 不包含"待实现""计划中""后续优化"等内容 |

### 4.2 同质化冗余过滤

同一模块目录下，不同文档不应出现以下同质化内容：

| 冗余模式 | 正确做法 |
|---------|---------|
| 需求规格和测试用例都列出完整功能点 | 测试用例引用需求规格的功能点编号 |
| API 接口和后端实现都描述参数结构 | API 接口定义契约，后端实现引用 API 接口 |
| 前端实现和后端实现都描述业务流程 | 后端实现描述业务逻辑，前端实现描述交互架构 |
| 各模块文档都重复描述同一个公共组件 | 只在公共模块文档中描述，其他模块引用 |

### 4.3 低价值内容过滤规则

以下内容视为低价值，评审时直接删除：

1. **工具链/框架基础配置**：如 ESLint 规则、Prettier 配置、Maven 插件配置等（属于工具使用常识，非项目设计）
2. **通用的最佳实践**：如"合理使用索引""避免 SELECT *""使用参数化查询"（这不是项目特有的设计）
3. **接口文档链接**：Swagger/Knife4j 地址（这不是文档内容，是开发工具入口）
4. **项目宣传性内容**：如"项目亮点""系统特色"（融入架构说明即可，无需独立罗列）
5. **重复出现的"缓存策略"通用描述**：无模块特异性的通用缓存设计应集中在系统架构文档中
6. **重复出现的"安全设计"通用描述**：如"SQL注入防护：参数化查询""XSS防护：输出编码"（属于系统架构层面的通用约束）

## 五、文档编写流程

### 5.1 编写前检查

1. 确认所要写的内容是否已在其他文档中存在 → **引用而非重写**
2. 确认内容归属的文档类型 → **需求/API/实现/测试/架构，选对类型**
3. 确认是否越界 → **需求不写实现、实现不写代码、测试不写UI**

### 5.2 编写时约束

1. 每个段落回答"这段内容对理解设计是否有不可替代的价值" → 否则删除
2. 信息优先使用表格呈现，减少叙事性描述
3. 引用路径使用相对路径（`./xxx.md` 或 `../xxx/xxx.md`）
4. 架构文档从 Mermaid 图出发，文字解释图中关键决策

### 5.3 编写后自审

逐项对照 §4.1 检查清单自审，通过后方可提交。

## 六、文档间引用规范

### 6.1 引用原则：必要性优先

引用仅在以下情况允许存在：

| 允许场景 | 说明 | 示例 |
|---------|------|------|
| **内容归属引用** | 读者必须查看被引用文档才能获取本条目的完整信息 | API接口.md 引用需求规格的功能点编号 |
| **避免重复引用** | 内容已在另一文档充分描述，本处只需指向它 | 后端实现.md 引用 02-系统架构/03-数据库设计.md |

以下引用视为**不必要的引用**，必须删除：

| 禁止场景 | 说明 | 反例 |
|---------|------|------|
| **完整信息已内嵌** | 引用的全部内容已经在当前文档中写完 | 文档已列出接口清单，末尾又写"详见 API接口.md" |
| **锦上添花式引用** | 引用的内容对理解当前文档没有实质帮助 | 需求规格末尾写"另请参阅 02-系统架构/01-总体架构设计.md" |
| **引用自身** | 同一模块文档间的"详见"而内容可以内嵌 | 前端实现.md 每个小节末尾都写"详见需求规格第X节" |
| **通用规范引用** | 引用全系统通用的约定作为免责声明 | "Token 校验失败时返回 401，详见 API 规范"（这是常识） |
