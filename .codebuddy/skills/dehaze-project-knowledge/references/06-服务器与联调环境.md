## 1. 跨机取服务的操作纪律（就地操作 / 排查 / 隧道高压线）

- **够不到被拦端口时，默认"就地操作"**：`ssh … 'docker exec redis redis-cli -a <pwd> ping'`、在服务器上跑客户端，只把 stdout 带回本机。**跨机取服务的优先序**：就地执行（ssh 上机跑命令、只回传 stdout）> 域名直连 > 平台授权通道（devcloud 控制台预览 / 映射）> 文件传输（scp/sftp 回收产物）。
- **看到 502 / 连不上，先分辨"代理未放行"还是"服务真挂"，别急着重启容器**：办公网 → DevCloud 的链路侧 HTTP 代理按端口准入，被拦端口会返回 `HTTP/1.1 502 Bad Gateway`（根本不是目标协议），而放行的端口直通真服务；同机自测（`docker exec` / `127.0.0.1` curl）可区分。
- **隧道类做法属安全高压线，默认禁止**：`ssh -R` 绝对禁止（在服务器上开监听＝反向转发，告警重灾区）；`ssh -L` / `-D`、VPN / 代理、frp/ngrok 类穿透**需用户明确授权**才可作为最后手段（且只能本机侧正向发起、不在服务器上开监听）。用户已明确否掉"用 `ssh -L` 把远端端口映射回本机做验证"的做法——需要浏览器验证远端页面时走 IP/域名直连或平台授权通道（如 pre 的 front-vue 用 IP 直连，走域名会被链路准入拦成 403）。
- **远端/无头调用 codebuddy**：非交互形态 `codebuddy -p "<prompt>" -y`，`-y`（`--dangerously-skip-permissions`）是必需参数、等价**取消全部工具确认门** ⇒ 护栏只能靠"收窄爆炸半径"：工作目录限目标仓库的干净分支/worktree、prompt 显式列禁止项（不动别的目录、不重启服务、不 force push、不删数据）；**破坏性/不可逆步骤（删除、`reset --hard`、迁移、`docker compose down`）由人用显式 ssh 执行**，不外包给无人确认的 agent；用 `--output-format stream-json` 换回中间工具调用可见性；收尾再用一条 ssh 自查 `git status` / `git diff` / 是否真落盘。
- **ssh 非交互执行加 `-o BatchMode=yes`** 防交互挂起；需交互登录（如首次确认）时去掉它。
- **改代码的作用域**：本机改代码不会自动影响任何服务器；改完要么在目标机 pull，要么明确说清"改的是哪一份、推哪个 commit"。
- **`pkill -f <模式>` 会连自己一起杀**：模式串出现在承载它的 ssh 远程命令命令行里时，pkill 匹配到该 shell 并终止它——表现为"执行到 pkill 就断"，后续步骤（含 mv/启动）静默不执行。先 `pgrep -f` 取 PID 再 `kill <pid>`，或把模式写成不含自身的形态（如 `[1]9222`），并复核目标进程确已消失。
- **验证 `~/bin` 入口不能只测绝对路径**：交互式 shell 里 `.bashrc` 的 alias 优先于 PATH，会静默遮蔽 `~/bin` 的同名脚本（表现为交互式下报“鉴权失败”、而非交互测绝对路径却全通）⇒ 用 `bash -ic 'type -a <cmd>; <cmd> ...'` 复测，并检查 `~/.bashrc` 是否残留旧 alias。
- **ssh 一律用别名 / 域名，别用 IP 直连**：`ssh earthy-pre`（=21.6.51.87）、`ssh earthy-dev`（=21.91.16.245）别名自带 `Port 36000`，无需显式 `-p`；不带别名时 `earthyzinc.devcloud.woa.com` 有独立 Host 条目（含 36000），而 `earthywu.devcloud.woa.com` 只命中 `*.devcloud.woa.com` 通配段（无 Port）⇒ 连它必须显式 `-p 36000`。域名解析到 `100.12.x.x`（VPC 地址），**IP 直连不匹配 ⇒ 用域名或别名**（sshd 在 36000；22 端口 TCP 可建连但立刻 `Connection closed`，不是 sshd）。
- **Redis 排障必须连对 DB**：dev 后端 `REDIS_DATABASE=1`、pre 用 db2；裸连 db0 看到的冷却计数 / zset / 验证码状态全是假的（验证码明文在 `captcha_code:<key>`）。
- **跨机服务互访零配置，唯一的拦路虎是 CORS 白名单**：同区域两台 DevCloud 机之间 `8989 / 8991 / 8993 / 8994` 等端口直接可达，服务端 curl / SDK / 后端互调无需任何配置；**只有“浏览器页面跨环境调用”才需改白名单**——根 `.env` 的 `CORS_ALLOWED_ORIGINS`（三端共读）默认只有 localhost，且 **Java 在 dev profile 走 `application-dev.yml` 硬编码列表、不读该环境变量**（prod 才读）。
- **relay 隧道已启用 token 鉴权，未连上的三种表现要分清**：`RELAY_AUTH_TOKEN` 三处必须一致（dev/pre 的 `server-relay`、Mac 的 `local-proxy`、本机入口 `~/bin/remote-*` 读的 `~/.relay-token`），换 token 用 `pm2 restart server-relay --update-env`。判别：error 日志每 ~5 秒刷 `鉴权失败，拒绝连接` = 客户端没带 token；`curl 127.0.0.1:9222/json/version` 无响应且 `remote-exec` 报 `No local-proxy connected` = 隧道侧当前无 client；直连 8222 不带 token 被 `close 4001 Unauthorized` = server 侧校验生效（**预期，别为消除噪音放宽鉴权**）。

## 2. K8s 调试：kubectl 流程与坑

- **标准流程与坑速查**（构建 / 推送 → apply（显式 `-n`）→ port-forward（headless Service 必须）→ logs → 用完即删；`can-i` 误报 / 配额按 limits 累加 / 多容器 Pod 状态不发布 / `bash -lc` 重置 PATH）见 `02-系统架构/06-部署架构.md`。
- **保留勿删**：`secret/default-token-r5tx4`、`secret/sa-token-cwjlk`（kubectl 访问凭据）、`configmap/kube-root-ca.crt`（删了断访问）；清理顺序＝先删 Pod 再删 PVC；`kubectl get pods -A` 被拒是设计如此。
- **Pod → 开发机反向联调**：服务监听 `0.0.0.0`、开发机安全组放通端口、DB 授权含节点网段——三个前提缺一不可；**授权别写死单个 IP**（Pod 会被调度到不同节点）。
- 访问 `panshi.woa.com` / `dev.panshi.woa.com` 被拒是**对端准入策略**（来源 / SNI 白名单），不是集群网络限制，`curl -k` 无效。
- 调试兜底容器：`kubectl run tmp -n <ns> --rm -it --restart=Never --image=busybox:1.36 -- sh`（`exec` 要求镜像自带 shell）。

## 3. 镜像构建 / 推送流程与坑

- 集群外先 `docker build` / `docker push` 到内网仓库；命名空间内拉取**必须**带凭据 → Pod 写 `imagePullSecrets`。**拿不到凭据时才退化为"官方镜像 + 代码注入"**。
- **删除镜像前务必确认 tag 名**：仓库不支持 tag 枚举、只能按已知 tag 逐个 `docker manifest inspect` 探测；`DELETE /v2/<repo>/manifests/<digest>` 按 digest 删会连带该 manifest 的所有 tag（返回 202 即成功）。
- **构建入口**：`docker build -f dehaze-<端>/Dockerfile --target test ...`（java/python 复用各自 Dockerfile 的 test 与运行态阶段；go 补了 Dockerfile）；基础镜像现状：仅 `dehaze-service/dehaze-modal|dehaze-voice/Dockerfile.base` 存在，改为测试镜像内 `uv sync --frozen --no-cache --no-install-project --extra test`（**上下文 = 仓库根**，按 `uv.lock` 在镜像内还原依赖 —— 与宿主是否执行过 `uv sync` 无关）。
- **依赖基础镜像的三个坑**：
  - `uv sync` 必须加 `--no-cache`：不加会把数 GB 已下载的轮子留在 `/root/.cache/uv`，后一层再 `rm` 也不会缩小镜像。
  - `uv sync` 必须加 `--extra test`：`respx/mongomock/freezegun/pytest-mock` 在 `[project.optional-dependencies] test` 里，缺它会致部分测试文件收集失败；补装不用重建：容器里 `uv sync --extra test` 后 `docker commit`。
  - 自建基础镜像与宿主 `.venv` 直拷等价（已对照验证）；已建好的臃肿镜像**不必重建**：`docker create` 后 `docker export <容器> | docker import -c 'ENV ...' - <tag>` 可压平为单层，代价是单层推送无并行。
- **服务端布局不可平铺**：三个服务的 `app/config.py` 用 `_find_service_root()` 从 `app/` 向上找 `pyproject.toml` 定服务根，再取 `parents[1]` 作仓库根读 `.env` ⇒ 必须保持 `dehaze-service/<服务名>/` 这一层，平铺到 `/app` 会让 `PROJECT_ROOT` 指错、`.env` 读不到。
- **`dehaze-modal` 测试镜像必须带 `algorithm/` 目录**（测试真实执行 `algorithm.DCP`），编排侧镜像**不得再 COPY `dehaze-python/algorithm`**（已迁至 `dehaze-service/dehaze-modal/algorithm/`，`dehaze-service/dehaze-modal/Dockerfile:16` 已 COPY）。
- **六端单测 Job 的 apply 纪律**：`config/kube/test/` 的 `job-regression.yaml`（18C/24G）与 `job-services.yaml`（10C/20G）**不得同时 apply**——组织配额按 limits 累加（24G + 20G > 32G 必被拒）；`job-smoke.yaml`（编排侧 python + 三推理服务最小用例，4 Pod / 16C/28G）可单独或与任一同时 apply。
- **本机 Docker 没有 buildx**：`docker buildx` = `unknown command`，`RUN --mount=type=cache` 报错（`DOCKER_BUILDKIT=1` 无效）⇒ **不能用 cache mount 加速依赖安装**，依赖层只能靠普通层缓存 + `uv sync --no-cache`。这也是重依赖端要做独立 base 镜像的直接原因。
- **`pgrep -f "docker push ..."` 会匹配到等待循环自身** ⇒ 用它做"等前一个推送完成"的条件会永久空转；改用 `pgrep -f "docker push csighub.*<具体tag>"` 或直接串行执行。
- **测试镜像要带仓库根 `config/`**：三端测试都用 `config/sql` 全量重建测试库；go 镜像漏了它会致建库用例全挂。
- **Dockerfile 里别用 heredoc**：不带 `\` 续行的 heredoc 体会被 Dockerfile 解析吃掉（`settings.xml` 被写成空文件）；改用 `printf '%s\n'` 续行。
- **`.venv` 可搬迁**：`bin/*` shebang 是唯一宿主绝对路径 ⇒ 基础镜像 COPY 后用 `sed` 重建 shebang 即可。
- **测试桶名一律从 `settings.MINIO_BUCKET` 取配置值**，勿硬编码（与产品读写口径不符会假失败）。
- **K8s 清单放 `config/`，别放 `deploy/`**：`**/deploy/` 被 `.gitignore` 忽略（放里面不会进版本控制）；三端单测回归 Job 清单在 `config/kube/test/`。
- **镜像一律走内网仓库 `csighub.tencentyun.com/earthywu/dehaze-system`，勿用 ttl.sh**（实测 1.02GB 镜像 `ContainerCreating` 26 分钟无进展且无失败事件，而内网推 1.68GB 仅 45 秒）；tag 用 **commit SHA、禁 latest**，**依赖基础镜像 tag 用 `uv.lock` 内容指纹** `<服务>-base-$(sha256sum <服务>/uv.lock | cut -c1-12)`（lock 未变即复用，别手工升 v1/v2）。

## 4. 浏览器调试实例与页面测试（远程 / 本地通用）

**先立住两个概念，别按机器名或环境标签猜**：

- **"本机" = 用户当前正在操作（或 agent 当前运行）的那台机器**。用户可能在任意一台设备上操作，机器不固定、不预设、**不要按名单枚举**；指认机器一律用固定标识（IP / 域名），不要用 hostname——同名 hostname 可能出现在多台机器上。判断"是否跨机"要分清「用户操作位置」与「会话进程位置」两件事。
- **同一个端口号在不同机器上含义不同**：9222 在用户 Mac 上是日常 Chrome，在远端机上则是磐石 MCP 的 local-proxy。

**动手前先自检本机四件事**（用实测结果代替推断）：

- `uname -s` ⇒ Darwin = Mac / MINGW·MSYS = Windows / Linux = 服务器。
- **内网接入判定**（三判据，任一命中即算已接入内网）：① 物理网卡 IP 命中 DevCloud/OA 段 ⇒ **直连内网**；② `ifconfig -a | grep -A1 '^utun'` 有带 IPv4 的 utun ⇒ **经 VPN 隧道接入**（iOA 远程办公「驱动模式」特征；此时物理网卡是私网 IP 属正常，**不能据此判成"在外网"**）；③ **本地代理 `127.0.0.1:12639`**（iOA + `com.tencent.NGNApp` 系统扩展常驻提供，即「驱动模式」的本地内网出口；npm 侧体现为 `~/.npmrc` 的 `proxy=`，浏览器侧体现为 whistle 的 `enable://proxyHost`）在监听 ⇒ **经本地代理接入**；判它在不在必须用 TCP 连接或 `netstat -an`，**`lsof` 看不到**（监听进程是 root）。注意 Node 的 `os.networkInterfaces()` 看不到 utun、IPv4 路由表也不体现（默认网关仍是本地路由器、无内网网段路由）⇒ 隧道只能靠 ifconfig 判。
- `curl -s --max-time 2 127.0.0.1:9222/json/version` ⇒ 返回 `Browser` 字段才说明本机有可接管的 Chrome（三个 CLI 可裸调），否则先起 Chrome 并确认该机 cdp 配置。
- `curl -s --max-time 3 -o /dev/null -w '%{http_code}' <被测地址>` ⇒ `000` 或超时 = 本机网络够不到被测环境，**别报成服务故障**。

**实例归属与三个 CLI 的选型 / 入口对照见 `02-系统架构/06-部署架构.md`**：本机 9222 实例裸调三个 CLI 接管；远端项目实例（19222）由 `scripts/chrome-debug/index.mjs` + `local-agent-browser` 接管；跨机操作用户 Mac 的 Chrome 只有 `remote-agent-browser` / `remote-exec` 一条通道（其它机器组合无通道，别假设存在）。

### 4.1 远端视角（agent 跑在 K8s / dev 机）

- 一律用 `scripts/chrome-debug/index.mjs`（setup / check / start / stop / restart / status / view / smoke / vnc-check）管理，**不要手工 `google-chrome --remote-debugging-port` 起临时实例**：headless 无图形桌面、无法经 VNC 人工接管登录与验证码，且 profile 落 `/tmp` 重启即丢。Chrome 本体由发行版软件包安装升级（`PYTHONPATH= dnf -y install google-chrome-stable`，仓库 `/etc/yum.repos.d/google-chrome.repo` → `dl.google.com` 本机可达），工具只做检测，不再有手工升级子命令。
- 产物（profile / 日志 / pid / 截图）统一在 `~/.chrome-debug/`，工具不做迁移：服务器上若还留着旧目录 `<repo>/.chrome/profile`（登录态在里面），首次切换前手工 `mv` 到 `~/.chrome-debug/profile`。
- 服务器上 CDP 端口用 **19222**（这两台机上 9222 属磐石 MCP 工具链的 local-proxy 代理，勿占用）：首次 `setup` 显式传 `--cdp-port=19222`，之后由状态文件记住——工具的默认值是 9222。chrome-devtools MCP 与人工 noVNC（5900 → 6080）共用同一实例与 profile，人工登录一次后 MCP 即为登录态。
- 进程以 setsid 常驻，脚本退出不影响；`stop` / `restart` 会断开 MCP 与 VNC（MCP 自动重连、登录态随 profile 保留，页面标签不自动恢复）。
- 命令行做页面调试另有两条 CLI 入口（版本以 `agent-browser --version` 实测为准）：`local-agent-browser`（固定连本机实例 19222，产物落本机）与 `remote-agent-browser`（经隧道在用户 Mac 上执行，产物落 Mac）；**远端 agent 别裸跑 `agent-browser`**——它会连到用户 Mac 的 9222（用户的日常浏览器），要操作 Mac 的 Chrome 必须走 `remote-agent-browser`。
- **Mac 侧能力与边界**：`remote-exec <cmd>` 直接在**用户 Mac** 上执行命令（token 自动带；产物在 Mac，用 `remote-file` 取回），`remote-agent-browser` 操作**用户 Mac 上可见的 Chrome**（窗口用户看得到）。这些动作都发生在人的工作机上 ⇒ 只做只读或确有必要的事，别乱点页面、别跑破坏性命令。
- **要让用户亲眼看页面**：先在 Mac 上验可达性 `remote-exec curl -sS -I --max-time 8 <url>`（关注端口如 pre/dev 前端 5274 / 5174、后端 8991）。**端口通断随链路策略变化，以当场实测为准，勿照搬旧结论**（按 §4 自检现测；hook 不做跨网探测，避免周期性请求触发安全告警）。

### 4.2 本机视角（agent 跑在当前这台机器上）

- 三个 CLI 的**既定用法是接管常驻调试实例**（工作站上是 9222，用独立 profile 沉淀磐石等登录态，**不是**用户日常浏览器的主 profile）；配置就位时**直接调用即可，不要再带 `--cdp` / `--browser-url`**，也不会另起实例。
- **接管由自包含 shim 兜底**：三个命令名被 `~/.local/bin` 下的 shim 遮蔽——实例不在时 shim 自己拉起（端口、profile、Chrome 路径、启动参数在安装时渲染进 shim），再转发真身，**全程不依赖仓库代码**（把仓库里的工具移走后 shim 仍能拉起实例并执行）；chrome-devtools 的 shim 会先校准 daemon 连接目标；服务器模式下 shim 只转发，实例由 `start` 管理。换端口或换 node 版本后重跑 `install` 刷新，体检用 `check`。Windows 侧 shim 尚未实机验证（当前只在 macOS 验过），首次使用按 `check` 输出核对。
- 该工具零依赖、零安装步骤：clone 下来直接 `node scripts/chrome-debug/index.mjs check|setup` 即可；不要为它引入 npm 依赖或 package.json——它要在"三个 CLI 都起不来"时还能用。
- **它的定位是安装器：装完仓库可删**（移走 `scripts/chrome-debug/` 后三个 CLI 与实例照常）——落点在用户目录：`~/.local/bin` 的三个 shim、shell rc 的 PATH 行、`~/.agent-browser/config.json` 与 `~/.playwright/cli.config.json` 的端口项、`~/.chrome-debug/` 运行时目录。`uninstall` 的边界就两条：删 shim、删 rc 行（配置与 profile 保留，不需要"完整还原"逻辑）。
- **未跑过 setup 的机器不要假设配置已存在**：自检 `curl -s --max-time 2 127.0.0.1:9222/json/version` 返回 `Browser` 字段才说明有可接管的实例，否则先在该机执行 `node scripts/chrome-debug/index.mjs setup` 补齐实例、三工具绑定与 shim。
- `check` 若报一条「shim PATH 优先级」告警（当前 shell 里 `/root/.local/bin` 仍排在 `~/.local/bin` 之后），**新开 shell 即消失，非故障**（`.bashrc` 末尾已前置 `~/.local/bin`，已在跑的 shell 不改）。
- `agent-browser` 的 `open` 默认导航**共享活动 tab**（会覆盖当前页）；多会话要隔离加 `--pin-tab`。
- `playwright-cli` 在 `detach` 后首次 `open` 必报 `Target page, context or browser has been closed`，**重试一次即成功**，脚本要允许重试。
- **多 agent 并行时不要共用同一个"活动 tab"**：agent-browser 用 `--session <name>`（必要时叠加 `--pin-tab`），playwright-cli 用 `-s=<name>`；chrome-devtools 的 daemon 是单例、pageId/uid 属全局状态，不要跨 agent 传递，长链路调试独占实例。
- **同一页面同一时刻只允许一个 agent 操作**：三个 CLI 操作同一浏览器进程与 profile，并发点击/输入会互相穿插；需要真正隔离时按 `--cdp-port` + `--user-dir` 另起一个实例。

### 4.3 平台 browser_use MCP：实例归属由启动配置决定

平台的 `browser_use` MCP server 底层是 `@playwright/cli` 的 `run-mcp-server`，其 Chrome 由 Playwright 自启（随机 CDP 端口、独立 `--user-data-dir`）⇒ **工具参数里没有任何端口 / 实例参数，工具层改不了归属，只能改启动配置**。

- **改挂到项目实例 19222（不新起浏览器）**：用 `browser.cdpEndpoint` 配置键（优先级：命令行 `--cdp-endpoint` > 配置文件 > `PLAYWRIGHT_MCP_CDP_ENDPOINT` 环境变量）；平台唯一 config 是 `/root/.bg-agent/node/playwright-cli.json`，改这一个文件即可全局改挂。生效需先 kill `run-mcp-server`，下次调用工具时才重拉并读新配置。附着后 Playwright 走 `connectOverCDP`、不再自启 Chrome，`browser_navigate` **复用现有活动 tab**（与 `playwright-cli` CLI 的 `open` 新开 tab 不同）。
- **判别某次调用连的是哪个 Chrome**：可靠判据是 `ps aux | grep '[r]un-mcp-server'` 的 daemon-session + `ss -tlnp | grep chrome` 的 `--remote-debugging-port`（`browser_tab_list` 的 URL 不可靠）；knot 场景另有隔离实例 `/root/.bg-agent/isolate-browser-<会话短id>/`，每会话独立 profile。
- **坑**：bundle 被 gzip 压缩，查配置键只能看 `README.md` 的 Configuration schema；平台 playwright-cli（0.0.62）与自装版（0.1.22）子命令表不同，别等同；19222 是共享资源，用完关掉自己开的 tab；配了 `cdpEndpoint` 后 `launchOptions` / `--user-data-dir` 全部失效。

### 4.4 chrome-devtools MCP：只属 test-engineer，主 agent 无浏览器工具

- **归属（2026-10-01 起）**：chrome-devtools MCP 由 `.codebuddy/agents/test-engineer.md` frontmatter 的 inline 私有 `mcpServers` 持有，只在该子代理 session 内创建、结束即销毁 ⇒ **主 agent 没有任何浏览器工具**（直接工具列表与 ToolSearch 两侧都没有，别反复确认），页面操作 / 截图一律派 test-engineer。**别**把 chrome-devtools 写回项目 `.mcp.json`，也别在 frontmatter 里改用名称引用（两者都会让主 agent 重新可见）。
- **test-engineer 内两套命名只差一个分隔符**，用错即“看不见”而误判“没有浏览器工具”：直接可用的是**下划线**版 `mcp__chrome_devtools__*`（22 个，如 `navigate_page` / `take_snapshot` / `click` / `fill` / `fill_form` / `evaluate_script` / `take_screenshot` / `list_pages` / `list_network_requests` / `list_console_messages`）；**连字符**版 `mcp__chrome-devtools__*` 共 8 个（`drag` / `emulate` / `get_console_message` / `lighthouse_audit` / `performance_analyze_insight` / `performance_start_trace` / `performance_stop_trace` / `take_heapsnapshot`）需 ToolSearch 才拿得到。
- **IDE 会话下 inline `mcpServers` 不生效（2026-10-02 实测）**：同一份 md frontmatter 在 CodeBuddy **IDE** 会话里不产出任何 `mcp__` 工具（改 frontmatter 无用）⇒ 需在 IDE 设置页 Agent Tab 为该 subagent 配置 MCP，并留意主 agent 是否被一并放可见（会破坏“私有化”设计，先问用户）。页面验证的设计口径见 `dehaze-doc/docs/02-系统架构/05-测试架构.md` §5.5。
- **chrome-devtools MCP 工具行为（2026-09-23 实测）**：`take_screenshot` 的 `filePath` **必须落在工作区根目录内**（写 `/root/...` 被拒 `not within any of the configured workspace roots`；不传则以内联图片返回）；`resize_page` 受 Chrome 最小窗口宽度限制（请求 390 实际 `innerWidth=500`），要真实移动视口用 `emulate` 的 `viewport:"390x844x3,mobile,touch"`；`emulate` 设 viewport 会**触发页面 reload**（JS 状态清零）；`isMobile` 仿真下页面若无 `<meta name="viewport">`，`innerWidth` 会是默认布局视口 980。

## 5. pre 环境作业与数据 / 提交同步纪律

- **pre 是“只测不开发”的共享环境，集成测试交 dev 侧 agent**：不在 pre 跑集成测试（`dehaze-test/` 等）、不写 `dehaze_pre` / `dehaze_dev` 库；单元测试必须落到独立库 `DEHAZE_TEST_DB=<独立库>`（`tests/conftest.py` 按 `config/sql` 指纹重建该库，与 pre 隔离），临时测试库用完自行 DROP。
- **pre 上不改被 git 跟踪的项目文件**：改代码 / 脚本 / 文档一律本地改 → `git push origin master` → 在 pre `git pull --ff-only` 同步（改完主动回报两边 commit hash）；**例外**：`.gitignore` 覆盖的配置（如 `.env`）与项目目录之外的文件可直接在 pre 改。
- **提交前必须按归属拆分范围**：工作区长期并行多条线（他人 / 其它 agent）的在途改动，**禁止 `git add -A` / `git commit -a` / push / 回退他人改动**；先 `git status` 分类归属，用显式路径清单提交，跨线同文件先协调或做 hunk 级拆分。
- **从 `config/sql/schema/*.sql` 重建库时必须跳过 `xxl_job.sql`**（内含 `DROP DATABASE`）；重建属破坏性 / 不可逆操作，须先经用户确认。
