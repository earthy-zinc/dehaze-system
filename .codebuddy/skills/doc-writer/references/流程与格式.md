# 变更流程与格式

## 变更触发与步骤

触发条件（满足任一即须同步更新文档）：

| 变更 | 必须更新的文档 |
| --- | --- |
| API 请求、响应参数增删改 | 模块《API接口》+ 受影响的前端实现 + 测试用例 |
| 数据流、架构调整 | 系统架构文档 + 相关模块文档 |
| 新增、调整页面或菜单 | 菜单与页面层级规划 + 对应端路由、菜单说明 |
| 新增模块 | 按模块模板建目录（需求规格、API接口、前端实现、后端实现、测试用例） |
| 术语、文案变更 | 文案与术语规范 + 全端文案 |
| 设计规范变更 | 对应规范文档 + 引用该规范的模块文档 |

步骤：① 先全局搜索引用点，定位全部受影响文档（不凭记忆）；② 修改单一信息源处（术语表、API 定义）；③ 同步所有引用方 —— 引用方只更新引用关系，不复制新内容；④ 代码与文档同时提交，禁止"先改代码、文档后补"或反之拖延。

新增文档准入：内容有明确归属分区；优先扩展已有文档而非新建；与现有文档不重复（重复则拒绝，改引用）。

文档退役：改造计划落地后，其结论并入对应现状文档（02、03、04），原改造计划文档删除；`05-改造计划/` 只保留"未落地、在办"内容（已落地项最多在总览留一行记录，不保留整篇设计文档）。已失效的引用、被取代的旧设计一并删除，不做留档。

侧边栏同步：新增、删除、重命名文档必须同步 `clarity-doc/docs/.vitepress/config.ts` 的 sidebar 分区。sidebar 指向不存在文件（死链）或磁盘文档未登记（孤儿）均视为文档缺陷，评审发现须修复。

代码一致性：文档字段名与代码字段名严格一致（改名时全局搜索一并修改，不保留旧字段兼容）；示例请求、响应与真实 API 一致，禁止虚构字段；页面状态（加载、空、错误）、错误码以文档为准、代码对齐；同一 API 在各端（Web、移动、桌面）文档中描述一致。

## 命名规范

| 维度 | 规范 |
| --- | --- |
| 目录命名 | 序号-名称（如 `01-产品设计`、`02-系统架构`），模块目录用中文功能名 |
| 文件命名 | 序号-名称.md（如 `06-文案与术语规范.md`）；模块内固定：需求规格、API接口、前端实现、后端实现、测试用例 |
| 命名唯一性 | 文件名区分大小写不视为独立文档；新增前检索现有文件（含大小写变体），重复或混淆则合并、重命名 |
| 标题 | 一级标题 = 文档名；层级 1-3 级，不跳级；不带章节编号；文档须自洽（不得是更大文档的残余片段） |
| 表格与图 | 信息类内容优先表格，表头明确；架构、流程、层级用 Mermaid（已集成 vitepress-plugin-mermaid） |
| 链接 | 相对路径，统一带 `.md` 后缀（`./xxx.md` 或 `../xxx/xxx.md`）；模块文档跨层引用层级固定：同级 `../`、核心模块 → 基础模块 `../../基础模块/`、指向 docs 根 `../../../02-系统架构/`；禁止站内绝对路径 |
| 术语 | 全文使用 `clarity-doc/docs/01-产品设计/06-文案与术语规范.md` 规范术语 |

## 引用禁令

引用原则：非必要不引用，以下引用必须删除：

| 禁止场景 | 说明 |
| --- | --- |
| 完整信息已内嵌 | 引用的全部内容已在当前文档写完（如已列接口清单又写"详见 API接口.md"） |
| 锦上添花式引用 | 对理解当前文档无实质帮助（如需求规格末尾"另请参阅 02-系统架构/01-总体架构设计.md"） |
| 引用自身 | 同模块文档间的"详见"而内容本可内嵌 |
| 通用规范引用 | 引用全系统通用约定作免责声明（如"Token 校验失败返回 401，详见 API 规范"） |
| 转述式引用 | 「XX 由 Y 实现，详见 Z」，而该信息对当前上下文无增益 |

> 引用应指向稳定锚点：跨文档引用一律给文件级相对路径，禁止带「§x.y」章节号（章节调整即失效，徒增维护成本）；同文档内小节互引也应最小化。一句话能说清的不引用整篇文档。

## 评审与自查

编写前：确认内容不存在于其他文档、选对文档类型、不越界。编写时：优先表格呈现，引用用相对路径，架构文档从 Mermaid 图出发。编写后：对照下表逐项自审通过再提交。

| 检查项 | 通过标准 |
| --- | --- |
| 边界清晰 | 内容不越界（需求不写实现，API 不写逻辑，测试不写 UI 细节） |
| 零代码片段 | 无超过 5 行的代码块 |
| 零日志记录 | 无"已修复、已删除、已重构"等历史变更表述 |
| 零重复内容 | 相同信息不在多份文档出现（引用代替复制） |
| 引用最小化 | 无锦上添花式、引用信息已内嵌、免责声明式通用规范引用 |
| 有架构图 | 04-项目实现 每篇至少一幅 Mermaid 架构图 |
| 无过度细节 | 无 ORM 配置、SQL 优化、工具链配置等琐碎内容 |
| 无待办、计划 | 无"待实现、计划中、后续优化"；规划内容只在 05-改造计划 |
| 无状态标记 | 无"已实现、规划中、远期"标记与"早期需求稿、本版、本次改造"校正或演进记录 |
| 命名与链接 | 命名、分区归属符合分区职责与命名规范，无大小写重复；链接有效、无失效引用 |
| 代码一致 | 字段、示例与代码一致；术语使用规范术语，未引入未登记的新叫法 |

信息密度按 `03-writing-rules` 执行：决策记录留、过程日志删、模块特异性留、通用原则下沉系统架构层。

低价值内容，评审时直接删除：工具链、框架基础配置（ESLint/Prettier/Maven 插件）；通用最佳实践（"合理使用索引""避免 SELECT \*""参数化查询"）；Swagger/Knife4j 地址；"项目亮点、系统特色"式宣传内容；无模块特异性的通用缓存策略与安全设计描述（应集中在系统架构文档）；实现黑话越界（需求、产品文档出现实现手段）；常识当卖点与应然事项叮嘱（如"不要写死机器路径"）；缺乏客观约束的情绪化、营销化强调（"无替代""彻底解决"）；开发日志化（架构、设计文档里的实测耗时、踩坑、排障、自测入口、日期流水——应进 skill 或代码注释）。

走查节点：页面交付前对照设计规范自查清单（移动端、桌面端、菜单规划）；涉及 API、架构、规范的变更，评审时核对变更触发表是否全部满足；新增、删除、重命名文档后核对 sidebar 无死链、孤儿；改造计划落地后按退役规则处理；定期审计复制漂移、失效链接、目录缺失，发现即修复。
