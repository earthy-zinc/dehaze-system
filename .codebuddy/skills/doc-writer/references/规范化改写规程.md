# 规范化改写规程

对已有文档做批量规范化时按本规程执行。范围与归属以 `内容边界.md`、`流程与格式.md` 为准，本文件规定"怎么改"与"怎么验收"。

## 机械项（必须手工处理）

原先由 `.codebuddy/hooks/doc-lint.mjs --fix` 自动处理，该脚本已随旧 hook 套件删除，这几类改为手工过一遍：

- 标题前导编号（`## 1. xxx` → `## xxx`）
- 图形 emoji（含 frontmatter 内的）
- 装饰性水平线
- 样板引用（"本文档介绍…"这类开场）
- 行尾空白
- 因去编号而失效的锚点链接

## 判断项（改写口径）

| 现状 | 改法 |
| --- | --- |
| `§x.y` 章节号引用（如 `（见 §2.1.3）`） | **直接删除该括注**；编号已去除，指针本身失效。指路确有必要的，改写为文件级相对链接（带 `.md`） |
| `✅ / ❌` 等符号 | 改文字：能力矩阵用「支持 / 不支持」，勾选用「是 / 否」，测试覆盖状态用「人工 / 集成」；若是"完成状态"列，整列按状态标记删 |
| 装饰性 `> **说明**：xxx` | 改为普通段落或并入正文；`> [!NOTE]` 提示块与真引文保留 |
| 加粗 | 只留扫一眼必须抓到的约束或危险项，一段最多一处；表格单元格内的加粗全部去掉 |
| 用加粗充当小标题 | 改为普通文本，层级需要时用真标题 |
| 元话语（"本文档定义…""本节介绍…""唯一权威来源"） | 删 |
| 指向项目根 `README.md` 之类的外部说明块 | 删 |
| 状态标记（已实现 / 规划中 / 远期 / 本版 / 本次改造 / 待实现 / 后续优化） | 删句；整段是演进叙述则删段；未落地的规划迁 `05-改造计划/` |
| 日期流水、实测耗时、踩坑、排障、自测入口 | 删 |
| 超过 5 行的代码块 | 删除或压到 5 行内；命令与字段清单改用表格或文字；确属必要的多行命令保留并在回报里说明 |
| 越界内容（需求 / 产品文档出现实现手段、表结构、错误码、类名；API 文档出现请求响应结构、调用示例） | **一律删除**，不做迁移；删除后若 `doc-loss-check` 报出独有标识符丢失，在回报里列出，不要强行补写 |
| 测试用例重复需求规格的功能点 | 改为引用需求规格 |
| 04-项目实现 里出现具体模块的需求 / 接口 / 实现 | 改为引用 `03-模块设计` 对应文档 |
| 用 `/` 当顿号（"组织/部门"） | 改顿号「、」；术语、路径、命令、单位里的 `/` 保留 |
| 中文里夹半角 `,;:?!` | 改全角 |
| 同一事实在多篇逐字重复 | 只留权威处一版，其余删（权威位置见 `内容边界.md`）；判不准的保留并回报 |

## 不要做的过度改写

- **不要压缩 Mermaid 图**。架构与流程用 Mermaid 是规则要求，"代码块 ≤5 行"只约束命令与配置类代码块，mermaid 不受此限（本仓库 lint 已豁免）。cbm hook 若报 mermaid "代码块超 N 行"，忽略。
- **不要为了降低表格行占比把表格改成 bullet 或散文**。测试用例、接口清单、权限矩阵、字段对照、登记表天然以表格为主；"不拿表格代替叙述"指的是别用表格替代本该成段的说明。cbm hook 的"表格占 X% 行"提示忽略。
- **不要把可点击的相对链接降级为纯文本**。链接目标里的中文目录路径（如 `../../基础模块/AI模型管理/后端实现.md`）不是"斜杠当顿号"（lint 已剥离链接目标后再判标点）。
- 跨文件引用上限 8 对总览与索引类文档不适用，超了在回报里说明即可。

## 保真红线

- 不改代码块内容。
- 不丢技术锚点：字段名、接口路径、错误码、表名、枚举值、端口、命令、阈值、权限码、`file:line`。
- 拿不准的保留原样并在回报里列出，不要猜着删。
- 涉及重命名文档或目录时，同步 `clarity-doc/docs/.vitepress/config.ts` 的 sidebar。

## 验收（改完在提交前跑）

```
cd clarity-doc && npm run docs:build   # 最终端到端闸门（抓死链）
```

另外三项原先有脚本兜着，脚本已删，改为人工核对：

- 机械项清单逐条过一遍（见本文开头）
- 代码块与标识符不得丢失：与 `git diff` 逐块比对
- 改过文件名或目录时，全仓搜一遍旧路径，确认没有残留指向

`doc-loss-check` 对"去重删除 / 删越界内容"会报丢失，属预期，但必须逐条确认是重复或越界内容，而非独有信息。

另外：编辑时 CodeBuddy 会用 `cbm-workspace` 的 doc-lint hook 自动给出同规范提示（其检查项与本仓库 lint 已对齐），照它提示改即可，不必忽略。
