# 文档治理

文档体系覆盖产品到实现的完整链路，分区固定，每份文档只服务一种读者视角。核心是单一信息源：一个事实只在一处定义，其余全部引用；复制即缺陷，评审发现立即收敛。

## 分区与归属

分区方案、各分区职责与禁止内容见 `references/内容边界.md`。

归属判定：跨模块、跨端的问题归上层（产品与架构），单一模块的问题归模块层，纯技术栈归实现层；拿不准时按更高一层归属，避免碎片化。治理规则本身不占分区。

模块内同类文档各司其职：需求写做什么，接口写什么契约，后端实现写后端怎么做，前端实现写前端怎么做，测试用例写怎么验证。引用层级自全局约定 → 模块规格 → 技术栈架构。

## 单一信息源

术语、页面层级、权限模型、模块能力、接口定义、错误码各只在一个权威位置定义，其余文档引用，不复制、不另起炉灶。引用必须给出明确文件路径，禁用"见上文""详见之前"这类模糊说法；同一事物的两处口径不一致视为缺陷。

文档只写当前契约，不写演进。已实现、规划中、远期这类状态标记，本版新增、收敛台账、待裁决登记一律删除，未落地的规划归改造计划分区。同一模块内不同文档也不得重复同质内容：功能点、参数结构、业务流程、公共组件都只在一处写。

## 文档类型边界

需求不写实现手段、接口定义、表结构与代码标识；接口不写请求响应结构、实现逻辑与调用示例；后端实现不写代码片段、修复记录、逐日日志与过度细节；前端实现不写组件样式代码、API 调用封装与工具链配置；测试用例不写 UI 细节、框架代码与环境搭建；实现层文档不写长代码块、开发日志与"后续优化方向"。数据库设计的权威是建表脚本，文档只写选型与跨表决策。

表述上，实现黑话不得越界到需求与产品文档，通用工程常识不当卖点，应然事项不叮嘱，情绪化强调改中性事实，实测耗时、踩坑、排障、自测入口与日期流水不进设计文档。判据：不了解本项目的读者读完这句是否获得新信息，否则删除。

## 变更、命名与引用

改 API、架构、页面菜单、模块、术语或设计规范时，先全局搜索引用点，再改单一信息源，最后同步引用方；触发条件与受影响文档见 `references/流程与格式.md`。新增文档须有明确归属、优先扩展已有文档、不与现有内容重复；改造计划落地后退役并入现状文档；新增、删除、重命名文档必须同步站点侧边栏，死链与孤儿都算缺陷。文档字段名与代码严格一致，示例不得虚构字段。

命名用 `序号-名称`，模块目录用中文功能名，模块内文件名固定。表格优先承载信息，架构与流程用 Mermaid，链接用相对路径且带 `.md` 后缀。非必要不引用，禁令清单见 `references/流程与格式.md`；引用给文件级路径，不带章节号。

## 评审

提交前逐项自审，检查表与低价值内容清单见 `references/流程与格式.md`；对已有文档做批量规范化时，改写口径与验收命令见 `references/规范化改写规程.md`。

分区职责、定义位置、状态标记、同质化冗余、表述禁令、文档类型边界六张对照表在 `references/内容边界.md`；变更触发、命名规范、引用禁令、评审自查表在 `references/流程与格式.md`。
