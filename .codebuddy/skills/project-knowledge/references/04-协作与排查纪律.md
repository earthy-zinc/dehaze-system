# 协作与排查纪律

## 排查方法论

- `test/logs/<backend>/detail.log`（NDJSON）按时间序定位首个失败 traceId 及前序请求，不要猜；SDK 登录会话权限快照在 redis `session:{uuid}` 可解码核对；DB 侧用 `clarity-test db_query`/pymysql 直查 `sys_role_menu`。
- 判定"回归"前先排除自身并行造成的资源争用：把 python pytest 与 front-vue vitest 放同一批次并发执行，会让 `test_deep_agent_builder_e2e.py` 3 例偶发失败（单跑即全绿）；`vitest --reporter=basic` 在 vitest 4 不存在（勿误判为测试失败）。
- `-k` 子集运行有跨测试顺序干扰（子集偶发失败、单文件全绿）⇒ 先单文件复跑，终验用全量。
- SDK 集成测试成片 `A0230 会话失效` 先查残留 vitest 进程：`timeout`/工具超时杀掉 pnpm·vitest 父进程后其 worker 可继续跑，与新进程抢同一账号 session（单点互踢）⇒ 跑前 `pgrep -af vitest.mjs` 确认无残留再串行单跑复验（干净串行单跑即全绿）。
- 排查法：编译/资源类批量失败用 git stash 二分逐步恢复 远快于逐个检查文件（`git stash pop` 不恢复 untracked，用 `git show "stash@{0}^3:<path>"` 提取）；Lombok 类海量假错先找第一条真实语法错误（重复注解 `@Valid @Valid` → javac 早失败 → Lombok 整轮失效）；`jdb -attach` + `catch java.lang.StackOverflowError` + `where` 是定位 SOE 自递归的终局手段。
- subagent 报告与任务书均不可轻信：可能虚构用例名、误读配置值、按字段名字面直觉解读语义（`actual_model` 误报）；Python 端"零引用"≠废弃，必须跨端核实。
- 推理类排查：`[runtime not ready]` 前缀表示错误在 JS runtime ready 前的模块加载期 → 优先查入口链模块顶层代码；双端（iOS+Android）同错＝JS bundle 层问题，不是原生链接问题。
- 判定"某目录未动、归我独占"前先跑并发写者探针：`git status --porcelain <dir>` + `find <dir> -type f -newermt '-15 minutes' -printf '%TH:%TM:%TS %p\n'`；有他人近期 mtime ⇒ 停手并上报（派单口径可能已过期）。队友通常跑在隔离 git worktree（`.codebuddy/worktrees/bg-<hash>`、分支 `worktree-bg-<hash>`；若其自行 commit，主工作区 `git status` 会是空的），但也实测出现过队友直接写主工作区同一目录 ⇒ 两种都要按探针判断。核实队友产出：`git worktree list` + 逐 worktree `git status --porcelain` / `git diff master --stat`，主工作区 grep 为空不能作为"没干活"的依据；跨面集成由主 agent 在主工作区做（`git -C <worktree> diff > /tmp/x.patch` 后 `git apply`，未跟踪文件单独拷贝；让队友"不 commit、留未提交改动"便于取 diff）。
- 会话莫名 401 / A0230 先查会话队列：三端共库 `session:user:{userId}` ZSet（上限 admin=10 / 普通=1，登录时按 score 升序踢最早）——任何以同账号登录的套件都会挤掉更早的持有者（SDK 套件每轮都会以 admin 登录，足以打断并行的页面遍历）⇒ `zcard` / `zrange ... WITHSCORES` 核实，不要先怀疑 TTL 或 Redis 清理。
- Java(8989) 全局鉴权过滤器在路由匹配之前：无会话时对任意路径（含不存在的路由）一律返回 `401 A0230`，无法区分"路由不存在"与"缺 token" ⇒ 探测端点是否存在必须带真实会话（从对应 Redis DB 的 `captcha_code:<key>` 取明文登录），并配对照组（如 `/api/v1/ai/models` → 200）才能证明"路由不存在"。
- 超时 / 日志空窗先排除持续性故障再下结论：先用证据区分「持续故障」与「偶发阻塞」，别先假设应用层问题；判定网络类故障最有效的分界是「超时（多为 DROP 隔离）vs 连接拒绝（端口拒绝）」，逐目标在真实运行环境内直连对比更可靠；探测内网域名要在能解析它的主机/Pod 上跑，`curl` 用 `-sS` 并看 `http_code` + exit code（`-s` 吞错会误判"无响应"）；用户给出反证时立即复核自己的结论，不做辩解式重申。

## 协作细则

- append-only 文件（日志/记忆）用 shell `cat >>`/`printf >>` 原子追加，避免并发旧快照写回；未跟踪文件无 git 基线，重写前先 read_file 只增量。
- 误用 `git stash`/`reset` 后的恢复法：`git stash show` 定位 + `git checkout 'stash@{n}' -- <files>` 精准恢复。
- 跨成员细则：同一文件禁并行编辑（stale buffer 回退）；SDK 测试严禁两端同时跑（共享开发库+Redis）；重启只动自己负责的后端；改共享测试文件前先广播；删模块顶层 import 前 grep 全部引用点（含返回类型注解）。
- 越界与非本人改动：越界改动宁可留 diff 噪音也不 `git checkout`；域内非本人改动先按"团队在途中间态"排查，上报不擅自恢复；"同域同时被改 ≠ 同一人"，勿归因幽灵写入者。
- `git commit` 后必须 `git show --stat` 核对（文件名笔误会致 commit 静默缺文件）。
- 命令执行：含 `sleep 50+`/`pgrep` 的复合内联命令易审批超时 ⇒ 写脚本 + 单条 `bash /tmp/x.sh`；跨轮归属用标记文件 + 产物 mtime + 首末请求交叉确认；用户偏好不要多次无意义重试测试/命令。成员触达 500 请求上限暂停后，用 Task 同名 + 同 team_name 重生（会话历史自动载回）。
- subagent 任务粒度不能太大（一个模块/功能点逐个验证）；免费 code agent 并发 9 个时 4 个失败 ⇒ 单独派发 + 任务书强调"直接进入编辑并落盘" + `max_turns 150`。
- 共享工作区禁 `git stash`/`reset`/`checkout`（会卷走队友未提交改动）；越界改动宁可留 diff 噪音也不 `git checkout`；域内非本人改动按"团队在途中间态"排查，上报不擅自恢复（误用后的精准恢复见上文）。
- `TaskOutput(block=true)` 轮询后台 agent 会把它们全部杀掉（等自动回报即可）；`Subagent 'xxx' not found` 通常是 `.codebuddy/agents/*.md` frontmatter 的 `model` 指向已失效的模型 ID（改 ID 后须重启 IDE/会话才在 Task 生效），不是文件缺失或名称问题。
- 范围纪律三条：①不因"顺手"扩大范围——无消费者的预置基建属提前消费（落地前先问"执行者/受害者是谁"）；②跨技术栈不可生搬硬套（taro 底层是 webpack5，`vite preview` 经验套过去不成立；先确认该端实际构建器与产物形态再动手）；③重建 todo 列表不得丢失主线待办（新任务用 `merge=true` 追加；必须重建时先把主线未完成项原样抄进新列表）。
- 架构级 / 跨端改造默认交付物是设计文档（放 `clarity-doc/docs/05-改造计划/`），列明待用户裁决的决策点并声明"未改任何代码，待审核"；用户明确批准后才进入实现，不要"文档写完顺手开改"。
- agent-home 多 worktree 协作纪律：①开工先 `git merge master` 拿阶段基线（不要基于旧基点改）；②严禁把主工作区/别的 worktree 的文件复制进自己 worktree（会镜像污染合并基准）；③合并口径＝每个 worktree 相对 master 的 diff 只含自己任务增量；④同路径同名文件双份产出高危（只保留一份、由 lead 裁定，另一份整包不合入）；⑤判断"改动是否生效"要 grep 主工作区内容（worktree 的 commit 不是 master 祖先，但内容可能已在基线），"是否需再合"用 `git merge-base`——两者结论可相反；⑥worktree 内无 `.env`/`.venv`（需 symlink），pytest conftest 从本 worktree 的 `config/sql` 重建测试库 ⇒ 新列未合入时含新列的 DB 用例会 `Unknown column` 假失败（只跑免 DB 子集自证）。
- 回报"完成"必须自带磁盘证据：worktree 路径 + `git status --porcelain` 原文 + `git rev-parse HEAD` + 关键验证命令的真实退出码 + 显式列出"未做的事"；无磁盘证据的完成不被采信。
- 取退出码必须 `cmd > log 2>&1; echo $?`（`(cmd | tail); echo ${PIPESTATUS[0]}` 拿到的是 `tail` 的码，曾因此作废一轮证据）。
- pre 环境只读与提交同步纪律（不改被 git 跟踪文件、本地改 → `git push origin master` → pre `git pull --ff-only` 同步、按归属拆分提交范围禁 `git add -A` / `git commit -a`）见本 skill `06-服务器与联调环境.md` 的「pre 环境作业与数据 / 提交同步纪律」。

- 环境 / 基础设施级阻塞先做 1–2 次轻量探测就上报，别自行长时间试凑配置：报错指向内网域名 / 代理 / 证书，或需要企业内网地址、VPN、企业凭据时（实例：2026-09-23 `git.code.oa.com` 域名失效致 Go 内部依赖拉不下来、需配 GOPROXY），先用 1–2 次轻量探测（如 `ls-remote`、HTTP discovery）确认事实，随即停下来告知用户并给出可选方案，把精力留在能自主推进的部分。内网服务地址、凭据、VPN 状态掌握在用户侧，靠探测穷举成本高且不可靠。
- imate 项目沉淀仓（dehaze）在 `D:\imate_project-clarity-vision`（工蜂 `IMateTeamGroup/imate_project-clarity-vision`，默认分支 `release`）：形态为 OKF v0.2 concept 文档（frontmatter `type` 必填、`sources` 溯源、`generated`/`verified` 分离）+ markdownlint 零警告（行长 80、表格长行用 `<!-- markdownlint-disable MD013 -->` 局部包裹、中文标签、标题唯一）；分层 `docs/`（管理视角）· `rules/`（技术规约）· `skills/custom/`（Agent 技能，入口 `SKILL.md`）· `memories/`（项目记忆）；写入流程（仓内 `rules/pm/doc-repo-workflow.md` 强制）：从 `release` 拉 `agent/imate-{YYYYMMDD}-{8位uuid}` 分支 → commit → push → 向 `release` 提 MR，同一时刻仅一个在途 MR。项目对开发环境无特殊要求，云桌面只是历史上部分时段用过的环境，任何"本机环境"结论只能作有条件线索。
