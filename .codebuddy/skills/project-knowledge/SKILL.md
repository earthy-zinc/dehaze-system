# 项目知识库

事实只落一处，按性质分流：陈述性知识（架构、接口与数据契约）进项目设计文档库；程序性知识（坑与禁区、命令顺序、校验规则、验收纪律）进本 skill 的 `references/`；强制红线进 `.codebuddy/rules/`；每会话基础口径进 `CODEBUDDY.md`；环境事实进项目文档，个人偏好与跨项目协作纪律进用户级长期记忆。

先按下表 `read_file` 对应参考文件再动手，一次只读与当前任务直接相关的主题。

## 读取元规则

1. 以磁盘代码、编译、实测为唯一裁决依据，成员自述与任务报告口径不可采信。
2. 结论性判断（范围、数量、"零引用 / 未实现"）须实测 + 计数基 + 时间戳，细则见 skill `testing`；python 端"零引用"不等于废弃，必须跨端核实。
3. 本 skill 无记录时，不凭直觉补默认值，先确认设计文档与代码的实际口径。

## 维护约定

1. 准入，三条同时满足才收。①不可推出：读完相关代码、`clarity-doc` 与类型定义仍看不出来（"要翻几个文件才能拼出来"不算）。②会致错：不知道它会写出看着对、实际错的实现（静默错数据、运行炸、跨端不一致、白屏），纯背景与现象解释不收。③能锚定：有守卫测试或权威源锚点。陈述性内容（是什么、为什么、契约、规格、公式）归 `clarity-doc`，通用红线归 `rules/`，本 skill 只留程序性判据。
2. 形态：一条只写"判据一句 + 锚点"。可读事实（启动命令、端口、目录结构、常量值、字段清单）删掉——读代码就有，留着稀释判据。日期流水、"已修复"、进度快照一律删。
3. 写入：只做增量插入或定点替换，禁止整体重写（多 agent 并发整体重写会因旧快照写回静默删除既有条目），写入后 grep 复核关键串。
4. 冲突与守卫：冲突优先级 `rules/` > 本 skill 事实记录，与 docs 或代码冲突时以磁盘代码与实测为准；坑被单测、轮末 hook 或静态检查覆盖后压缩为"判据一句 + 守卫锚点"，声称"已修复"前须找到守卫或实测证据。
