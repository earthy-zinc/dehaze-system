# 排查手册

这一阶段只做定位，别急着改 SDK 或测试代码。

## 先划范围

按响应状态码与现象，问题一般落在这几处：

- 测试代码编写错误：编译报错、指向测试自身的运行错误、用例结构、并发、生命周期、异步等待、mock 与环境
- 测试数据与断言错误：数据构造、清理、唯一性、断言过强或过弱、断言字段不稳定
- SDK 封装问题：params 与 data、path 拼接、header 与 cookie、序列化、响应解包
- 后端代码问题：接口实现、权限、校验、业务逻辑、并发与幂等、异常处理
- 数据库与缓存问题：脏数据、唯一索引冲突、事务与隔离级别、缓存未失效、环境库用错

## 查 SDK 封装

重点看 clarity-sdk-js 的封装：

- GET 请求是否错误地用了 `data` 而非 `params`
- POST / PUT / PATCH 是否错误地用了 `params` 而非请求体
- path 参数拼接是否正确，比如 `/api/v1/users/{id}` 有没有被替换成具体 ID
- header 与 cookie 有没有带上，鉴权 token 未注入、CSRF 或 cookie 丢失
- content-type 是否正确，本该 JSON 却用 form，或上传与二进制处理错误
- 返回值解析层级是否正确，有没有错误地从 `data`、`code`、`message` 里读错层

若后端行为正确但测试失败，优先在这里定位并修复。判断重点是：同一个 token、同一业务意图，相同请求是否一致。

## 查测试用例自身

把测试写法问题与数据、断言问题拆开。

测试代码编写错误的常见信号：

- 忘了 `await`，请求没完成就断言或退出
- 测试依赖执行顺序，单跑通过、全量跑失败
- `beforeAll` / `afterAll` 顺序不对，或共享了可变全局变量
- 清理逻辑跑在断言前，或清理失败不报错
- `afterAll` 没覆盖所有创建的 ID，上一次运行的残留数据影响本次
- 多个用例并发改同一个资源，比如同用户名、同手机号、同一条记录，互相污染

测试数据与断言错误的常见信号：

- 用了非唯一数据，导致重复键冲突或取到别人用例的数据；确认是否用了 `uniqueName`、`uniqueEmail`、`uniqueMobile` 这类唯一数据生成
- 断言了不稳定字段：`createTime`、`updateTime`、`id`、排序未固定的列表、随机内容
- 断言过弱，只 `toBeDefined` 会漏检；或过强，后端允许为空却强制非空
- 用错了预期业务错误的断言助手，把该失败当成功或反之

快速判别：

- 只在全量或并发时失败，优先查隔离、唯一性、清理
- 单接口稳定失败，优先查 SDK 封装或后端逻辑

## 查后端与 DB

前面都排除后再深入，并区分后端代码错误与数据库、缓存问题。

- 用 SQL 查是否存在重复数据、脏数据或唯一约束冲突
- 用 Redis 命令查缓存是否过期或被污染，必要时清对应 key
- 没有 DB 或 Redis 工具时，请用户提供查询结果或后端日志片段，据此判断

后端代码问题的常见信号：

- curl 稳定失败且报错与参数无关，比如 500、空指针、业务 code 异常
- 相同请求不同时间返回不一致，指向业务状态机或并发缺陷
- 权限与鉴权逻辑与文档不符，应 403 却 200 或反之
- 返回结构与 OAS 不一致，字段缺失或类型变化

数据库与缓存问题的常见信号：

- duplicate key、唯一索引冲突，尤其偶现，常由历史脏数据或并发导致
- 删不干净、查到旧数据，多为缓存未失效、读写分离延迟、事务未提交
- 环境库用错，连到共享库或非测试库，数据被别人污染
- 同一请求第一次失败、重试成功，强烈指向缓存、一致性或事务时序
