# 跨端测试基建与举证

java / go / 前端各端与 Stop hook 的测试基建、测试质量红线、验收举证纪律。python 与 SDK 的专有事实见同目录 `python-测试与门禁.md` 与 `sdk-集成测试.md`。

## 各端测试基建

- java 测试基建事实：test-compile 失败会先清空 `target/surefire-reports` ⇒ 转述失败须以报告 mtime + `Tests run` + maven 摘要对齐；改 parent 版本后必须 `mvn clean`（增量编译不重新编译未变更文件 → 陈旧类 `NoSuchMethodError`）；JDK/mockito/byte-buddy/lombok/mapstruct 的版本口径以 `clarity-java/pom.xml` 为单点（JDK 25 上旧版 mockito 全挂）。
- go：`go test ./...`——测试库凭证由 `internal/testutil/mysql.go` 用 `godotenv` 显式读仓库根 `.env`（与 CWD 解耦）的 `MYSQL_USERNAME`/`MYSQL_PASSWORD`；不存在 `DEHAZE_PASSWORD`（根 `.env` 零 `DEHAZE_*` 变量）；库名取 `CLARITY_TEST_DB`、默认 `clarity_test`；`go test -count=1 ./...`；Go build cache 按内容哈希（不需 `touch`），危险的是"纯新增不影响编译"的改动（路由/装配/文档）⇒ 必须 grep 计数复核；`make mocks`（mockery + `.mockery.yaml`），禁 `--name/--dir` CLI（会写进源码目录致双包编译红）；`mock_IAuthService.go` 为 mockery testify 风格，不可用 mockgen 重新生成。
- 测试库构造（conftest / `DROP+CREATE` / `CLARITY_TEST_DB`）见同目录 `python-测试与门禁.md`；集成测试连开发库 `dehaze` 且 schema 变更须手工 ALTER、种子基建见 `02-系统架构/05-测试架构.md`；`clarity-test` 工作台的验证码从 Redis 直读 `captcha_code:{captchaKey}` 免 OCR，其 `utils/api.request` 对 400 会 `raise_for_status` ⇒ 探查原始响应须 httpx 直连。
- 各端门禁口径：front-vue 跑 `pnpm lint` + `pnpm test:unit` + `pnpm exec vue-tsc --noEmit`（`pnpm build` 含 vue-tsc）；taro `tsc --noEmit`、uniapp `vue-tsc --noEmit`；TS 项目类型检查全量纳入轮末检查（纳入口径＝"默认分支类型干净"，不按耗时排除；改 SDK 源码会触发先重建产物、再连带检查所有下游）；react-native `jest.config.js` 已就位（`transformIgnorePatterns` 已放行 `@react-navigation`，`moduleNameMapper` 指向 SDK `dist/index.cjs`）。轮末检查另含四类守卫（go 契约、仓库铁律脚本、eslint 只读分组、上游 dist 陈旧重建）：go 契约守卫（权限与种子/mock 一致、GORM `default:` 零值扫描、`model_type` 跨端值域）、仓库铁律脚本（`scripts/check_dockerfiles.py`）、eslint 只读分组（只报 error；`--fix` 不可自动修复的规则由此在轮末可见，如 front-vue `ai-chat` 四禁 import）、上游 `dist` 陈旧自动重建（避免下游假绿/假错）。
- 本工作区未全量 `pnpm install` 时前端类型检查会出环境性假错：front-vue/front-react 会报 `dotenv`/`ioredis` 的 `TS2307`（声明在 package.json 但未安装）；且 `clarity-sdk-js/dist` 未重建时 front-vue `vue-tsc` 会多报大量 SDK 契约错，`pnpm --filter clarity-sdk-js build` 后即消失 ⇒ 判定此类失败前先分辨"环境" vs "真实回归"（先补 `pnpm install` + 重建 SDK dist 再下结论）。
- java 编译/测试走 /tmp 副本，见 skill `project-knowledge`。
- 前端 e2e（Playwright）口径：权威 lockfile 是仓库根的 `pnpm-lock.yaml`（`pnpm install --frozen-lockfile` 在根跑）；各前端目录内残留的旧 `pnpm-lock.yaml` 非事实源，曾据此误判"版本漂移、要降版本"。Playwright 浏览器缓存与版本强绑定（如 1.61.1 需 `/root/.cache/ms-playwright/chromium-1228`）⇒ 判版本看根 lockfile + `node_modules/.pnpm/playwright-core@*/browsers.json` 的 `revision` 再核对缓存目录；缺浏览器用 `npx playwright install chromium`，勿改 `package.json` 版本。
- 前端页面测试先侦察再动手：先摸清入口端口（front-vue `vite preview --mode test`=5274 / dev=5174）、鉴权方式（HttpOnly cookie `X-Session-Id`，需浏览器内登录）、默认口令 `SEED_PASSWORD`（`clarity-test/utils/config.py`、`clarity-sdk-js/test/config/constant.ts`）；探索/取证用 chrome-devtools MCP（含 `evaluate_script` 兜底 el-switch 等 `click` actionability 失败），确认的问题补成 Playwright 页面级断言入回归，不要只口头报告。

## 环境与已知噪音

- 本工作区（pre）作业口径：pre 是"只测不开发"的共享环境，不在本环境跑集成测试（`clarity-test/` 等，交 dev 环境 agent）；单测必须落独立 `CLARITY_TEST_DB=<独立库>`（勿写 `dehaze_pre`/`dehaze_dev`，`tests/conftest.py` 按 `config/sql` 指纹重建，与 pre 隔离），临时库用完自 DROP；污染 pre 后的复位口径（重建即从 `config/sql` 全量导入，属破坏性操作须先经用户确认）见 `02-系统架构/10-多环境部署实践.md`。
- pre 跑 Python 负向 SDK 套件的已知噪音：prod profile 下 `settings.DEBUG=False`，Python(8991) `app.middleware.ip_blacklist` 会自封回环 IP（统计的是响应 status≥400 的请求数，阈值 100/60s、封 3600s），`pnpm test:python` 前几个文件即可凑满 ⇒ 跑前外挂看门狗轮询 `EXISTS ip:blacklist:127.0.0.1` 以便命中即停；判据 `redis-cli -n 2 TTL ip:blacklist:127.0.0.1` / `ZCARD ip:errors:127.0.0.1`；解封需删键（破坏性，须用户确认，勿擅自做）。
- pre 判定 AI 功能失败前先分"环境缺口"与"真实缺陷"：DB 重建后 `sys_ai_provider_key` 为 0 行（密钥不入 git）、`clarity-llm/voice/modal`（8992/8993/8994）常未启动 ⇒ `A0600 该供应商无可用 API Key` / `A0500 供应商 local-voice 无可用 API Key` 多为环境缺口，非真实缺陷；补 Key 属改数据，须先经用户确认。

## 测试质量红线

- 前端测试禁 `console.warn + return` 伪通过，改为前置断言（`expect(x).toBeGreaterThan(0)`）。
- 语料必须含对抗性脏数据：全半角混杂/CRLF/BOM/零宽/emoji/超长行 + 格式变体 + 参数边界与不变量（固定 seed）+ 文件对抗（0 字节/随机字节/伪装扩展名/GBK）+ 性能烟测。脏语料必须用合法 Unicode 码点（`\U0001F600`），孤立代理 `\ud83d\ude00` 致 DB 驱动 UnicodeEncodeError。
- "断言不存在"守卫须自带检测器自证（负向断言有假绿风险 ⇒ 用"故意写旧键名让 tsc 报错"自证）；新增约束后须回看既有用例是否因约束前置而假绿。

## 验收与举证

- 禁"注解/配置存在"即通过：须"注解 + 触发条件 + 兜底 + 必填性"四层同核 + 摘除反证（删注解→用例必须红）+ 行为级负向用例（断 code + `verifyNoInteractions`）+ 必填/越界各一条"未落库"断言。
- 交接清单与文档陈述必须回代码抽检两类：①数量断言（`ls <dir>/*.java | wc -l`，注意口径——`ui/system/` 顶层 15 文件是 14 Activity + 1 Fragment）②构件名（"已删除 X"先 `git show HEAD:<path>` / `find -iname` 确认曾存在；"零残留"要逐个类名/资源名单独 grep）。这两类会静默腐烂且关键词 grep 抓不到（例：交接文档里的类名从未存在、API 类计数被静默改动）。
- 浏览器 `performance.getEntriesByType('resource')` 有 250 条上限：页面资源多时（本项目 element-plus 数百模块）会丢早期条目 ⇒ 查首屏资源得假空；改用 CDP 网络面板 + 服务端 curl + DOM/CSS 引用三查互证，并注意面板可能残留上一轮加载记录。

## 轮末收口 hook 的排障与改造

设计与检查项见 `clarity-doc/docs/02-系统架构/05-测试架构.md`；以下是排障、改造它与读它回执的操作口径。

- 每个事件都新起 `node` 进程读盘执行 ⇒ 改注册或改脚本即时生效；"看似没生效"先查下面两条，别归因"需重启"。
- `tool_input` 字段名两套都要认（CLI `file_path` / IDE `filePath`，只认一套＝hook 装了却永不登记）；`stop_hook_active` 两侧都是 snake_case；仓库根只认脚本自身位置（IDE 的 `payload.cwd` 恒为 `/root`）。
- 子代理的 Write / Edit 也触发 PostToolUse 且与父同 `session_id` ⇒ 改动台账必须 append-only（`O_APPEND` 原子），"读-改-写"整份 JSON 会互相覆盖丢登记。
- 改检查逻辑的四条硬口径：ruff 要 `--output-format=concise` 且整项目跑；`go vet ./...` 整仓同理；`pyright -p <config> --warnings <文件...>` 只报传入文件但照样解析依赖闭包（唯一可按文件裁剪的项，类型级跨文件连带＝已知盲区）；`tsc` / `vue-tsc` 整项目跑、不按改动文件过滤输出。改上游 `clarity-sdk-js` 必须先重建 dist 再验下游（不重建＝假绿）。
- 排障 `DEHAZE_HOOK_DEBUG=1` 需启动前 export（运行中补设无效），或用 `.codebuddy/.state/debug` 标记文件，日志 `$TMPDIR/clarity-hooks.log`。`codebuddy -p`（headless）不发 SessionEnd ⇒ 状态靠 24h 孤儿回收。
- `prettier --check` 的 warn 走 stderr（`2>/dev/null | grep -c` 会得假绿）；`prettier --write <目录>` 会越界（RN 缺 `.prettierignore` ⇒ 重排 lock 文件）⇒ 只传显式文件清单；Java 用 `mvn -DspotlessFiles=a,b` 逗号批量。
- `verify-write.mjs`（编辑回读校验）：写盘后延迟复核新内容里的长标识片段能否读回，失败以 `[编辑回读校验]` 报错（exit 2）——收到即该次编辑未生效，回读文件并重写。
