## 测试用例编写步骤

在开始编写测试用例前，必须确保：

- 你已了解 [SDK-JS 测试编写规范](./sdk-js-testing.md)
- 已阅读并理解 [dehaze-coder SKILL 主文档](../SKILL.md) 中的 SDK-JS 测试部分
- 确认测试环境准备就绪
    - 后端服务运行
    - 数据库连接
    - 测试配置正确

### Step 1：分析用户需求

当用户要求编写测试用例时，请深入理解其业务背景，准确评估当前业务场景下必要的测试用例及符合场景的测试数据。若用户提供的信息不充分，必须主动提出以下具体疑问：

1. 业务场景: 该接口在业务流程中的作用和核心功能是什么?
2. 接口范围: 明确要测试的具体接口(一次聚焦一个主要接口)
3. 前置条件: 调用该接口需要什么条件(登录态、权限、特定数据等)?
4. 边界条件: 在该业务场景下,哪些边界条件是合理且重要的?

约束说明:

- 可以为一个接口设计多个相关测试用例(成功路径、参数校验等)
- 不要同时为多个不相关的接口编写测试,保持聚焦
- 如果用例数量过多(>10个)，分批编写和验证

### Step 2：生成用例清单文档

为每个被测接口设计用例清单,至少覆盖以下类别:

| 用例类别   | 覆盖要点             | 输出要求                                 |
|--------|------------------|--------------------------------------|
| 成功路径   | 响应结构、关键字段、核心业务语义 | 验证返回数据完整性和业务正确性                      |
| 参数校验   | 必填字段缺失、格式非法、边界值  | 使用 `expectBizErrorOrUndefined` 断言错误码 |
| 权限/鉴权  | 未登录、无权限用户访问      | 验证401/403等鉴权响应                       |
| 幂等/一致性 | 相同条件重复调用结果一致     | 针对查询/无副作用接口                          |
| 列表/分页  | 分页参数、排序、过滤条件     | 验证list结构、total、pageSize              |
| 并发/隔离  | 多用例同时执行无冲突       | 确保数据唯一性和清理策略                         |
| 安全性场景  | SQL注入、XSS、越权等    | 验证安全防护机制(如适用)                        |

**输出要求:**

- 每个用例包含: 标题、前置条件、输入数据、预期结果
- 标记用例依赖关系(如:需要先创建数据再测试更新)
- 规划数据清理策略(哪些用例需要清理、如何记录创建的ID)
- **与用户确认清单后再开始编写**

### Step 3：编写测试用例

**准备工作:**

1. 查看SDK/目标API的OAS接口文档(查看dehaze-sdk-js/src/api目录或使用MCP工具)
2. 查看现有 `test/factories/` 中可用的工厂函数
3. 查看 `test/factories/constants.ts` 中的预置数据

**约束:**

- 每次编写一个完整的 `test()` 块
- 可在同一个 `describe()` 块中编写相关的多个用例
- 不要跳过 lint 和测试验证就去编写下一个用例

### Step 4：修复lint错误

**执行时机:** 编写完每个测试用例后立即检查

```bash
cd dehaze-tool/dehaze-sdk-js && pnpm run lint
```

**重要说明:**

- ⚠️ 在运行 `lint` 之前,不要手动修改可以通过自动化工具修复的格式问题
- 确保没有语法错误或类型错误后,再进行下一步
- 如果 lint 报告的错误影响测试逻辑,需要先修复错误再继续

### Step 5：运行测试用例

**执行时机:** Lint 通过后

为了节约上下文，仅运行当前编写的测试用例，严禁在未完成所有任务时运行所有测试用例，避免造成上下文爆炸。

运行示例：

```bash
# 使用 testNamePattern 运行特定测试
npx vitest run test/user/user.test.ts --testNamePattern="正向测试：获取当前登录用户信息并验证数据完整性"
```

**注意事项:**

- 如果超时,检查测试数据和后端响应时间,不要盲目增加 timeout
- 查看详细错误输出,定位失败原因

### Step 6：修复测试用例问题

如果测试失败,按以下顺序排查:

1. **快速诊断:**

- 是稳定失败还是偶现失败?
- 错误信息是什么(HTTP状态码、业务错误码、断言失败)?
- 是否有并发相关的问题?

2. **进入排查流程:**

- 参考详细的排查文档: [测试失败排查与归因](./sdk-js-test-failure.md)
- 按顺序执行: curl复现 → OAS文档核对 → SDK封装检查 → 测试代码分析 → 后端/DB排查

3. **问题归因:**

- 测试代码问题 → 修复测试数据或断言
- SDK封装问题 → 修复SDK或调整测试调用方式
- 后端bug → 保留失败测试,记录问题,添加注释说明预期行为

4. **后端bug处理:**

- ⚠️ **必须保留**能暴露问题的测试用例
- 使用注释说明预期行为和当前实际行为
- 不要用 `test.skip()` 或注释断言

### Step 7：循环迭代完成所有用例

流程:

1. 回到 **Step 2** 的用例清单
2. 选取下一个用例,执行 **Step 3-6**
3. 重复直到所有用例编写完成并通过测试
4. 最后运行整个测试文件确保无回归:
   ```bash
   npx vitest run test/modules/<domain>/<api>.test.ts
   ```

### Step8：质量检查

- [ ] 所有用例通过测试
- [ ] 无 lint 错误
- [ ] 数据清理策略完整且有效
- [ ] 使用了正确的 factories 和 constants
- [ ] 断言充分且不过度(关键字段断言)
- [ ] 测试并发执行稳定
