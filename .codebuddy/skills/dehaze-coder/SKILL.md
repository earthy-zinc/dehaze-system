# dehaze-coder：统一编码与测试规范

## 适用范围

本 skill 为 dehaze-system monorepo 提供统一的编码与测试约束，根据当前工作的子项目自动加载对应规范。

### 项目结构概览

dehaze-system 是图像去雾系统 monorepo：

| 子项目                      | 定位                 | 优先级               |
| --------------------------- | -------------------- | -------------------- |
| `dehaze-python`             | 核心，去雾模型       | 高                   |
| `dehaze-go`                 | 主推后端（Go/Gin）   | 高                   |
| `dehaze-front-vue`          | 主端 Web（Vue）      | 高                   |
| `dehaze-doc`                | 唯一文档源           | 高                   |
| `dehaze-tool/dehaze-sdk-js` | SDK 工具库           | 高                   |
| `dehaze-java*`              | Java 多版本后端      | 中                   |
| `dehaze-front-react`        | React 端             | 中                   |
| Android/算法研究            | 移动端骨架、研究代码 | 低，未主动提及可忽略 |

## 通用开发规范（所有子项目）

### 代码质量

- 编写高质量、生产就绪的代码，时刻关注代码整洁性和结构合理性
- 杜绝代码重复，注重可读性和可维护性
- 遵循项目现有的代码模式、目录结构、命名规范、代码风格
- 发现问题时主动提出并请求用户确认
- 不重复造轮子，优先推荐成熟的第三方方案

### 代码注释

秉持"代码即文档"的理念，只有在逻辑意图无法通过清晰的命名和结构直观表达时，才补充必要的注释，阐明"为什么"而非"做什么"。

### 文档同步

当代码改动影响了模块接口、数据流或架构设计时，同步更新 `dehaze-doc` 中对应的设计文档。

### 开发前的准备工作

对于涉及模块设计、接口变更、新功能等场景，应查阅 `dehaze-doc` 中的相关文档，仅检索与当前任务直接相关的部分，避免全量阅读。

## 任务拆解与协调规范

当需求涉及跨模块协调或需要拆解为多个子任务时，遵循以下规范。

### 派发分级

**可自动执行（无需确认）：**

- 单模块内的 CRUD 实现
- 有明确 API 契约的接口对接
- 已有类似模式可参考的功能
- 单文件或相邻文件的修改

**需用户确认：**

- 跨 2+ 技术栈模块联动（如前后端 + 数据库）
- 引入项目未使用的框架/依赖
- 数据库表结构变更
- 权限、安全相关修改

### 子任务上下文模板

派发子任务时，提供以下结构化信息：

- **任务目标**：一句话描述要完成什么
- **验收标准**：明确的完成条件
- **相关文件**：需要读取或修改的文件路径
- **依赖约束**：技术栈版本、已有模式、禁止事项
- **边界条件**：输入输出边界、异常处理要求

### 质量审查要点

- **功能完整性**：是否覆盖任务目标的所有要求
- **代码规范**：是否符合本 skill 及对应语言的编码规范
- **边界处理**：异常情况、空值、边界条件是否处理
- **一致性**：与现有代码风格、命名约定是否一致

### 失败恢复策略

1. **首次失败**：分析原因 → 补充更明确的边界条件/示例 → 重试
2. **二次失败**：重新拆解为更小粒度 → 分步执行
3. **三次失败**：升级处理 → 转交用户决策

### 项目文档位置

- 系统架构：`dehaze-doc/docs/项目文档/图像去雾系统/新结构/02-系统架构/`
- 模块设计：`dehaze-doc/docs/项目文档/图像去雾系统/新结构/03-模块设计/`
- API 规范：各模块下的 `API接口.md`

## 通用测试规范（所有子项目）

测试是暴露问题的工具，而非"通过测试"的任务。每次调试 3 次以上时，必须重新阅读本节全部内容。

### 测试工程师行为准则

- 设计结构清晰的测试用例，覆盖正常、边界与异常场景
- 通过断言验证响应结构、状态码及业务逻辑一致性
- 坚持"测试即文档"理念，确保每个测试用例有明确的业务意图
- 始终将"保障代码质量"视为核心职责，而非仅追求测试用例通过

### 严禁行为

在多次调试无果后，必须让用户介入解决：

- 严禁跳过测试规避失败
- 严禁"注释掉断言"以让测试通过
- 严禁修改测试预期以匹配错误的行为
- 严禁在测试内引入不可控的外部依赖（除非本测试本质就是集成测试，且该依赖就是被测目标）

当检测到被测代码 bug（非测试代码引起的 bug），必须：

- 立即通知用户介入解决，**严禁**自行修改测试预期
- 保留"会失败的测试"来持续暴露问题
- 标记 TODO 说明这是待修复的 bug

### 断言规范

- 强断言 + 业务关键字段
- 禁止弱断言（如仅 `toBeDefined`、`not.toBeNull`）

### 参数校验类用例覆盖

- 必填字段缺失
- 格式不合法（邮箱/手机号等）
- 资源不存在（id 不存在）
- 唯一性冲突（username/mobile/email）

### 通用规范

- 测试数据要"有业务含义"，避免无意义随机值
- 仅引入被测类需要的关键依赖与测试需要的依赖
- 提交前应无 unused import

### dehaze-sdk-js（dehaze-tool/dehaze-sdk-js）

#### 环境与目录硬约束

**Vitest 运行环境：**

基于仓库的 Vitest 配置，测试环境具有以下特征：

- `environment: "node"`：测试在 Node 环境执行，不依赖浏览器 DOM。
- `include: ["test/**/*.test.ts"]`：仅该目录与命名规则下的文件会被执行。
- `setupFiles: ["./vitest.setup.ts"]`：登录等全局初始化逻辑集中在 setup 中。
- 配置了较大的 `testTimeout/hookTimeout`，但应优先通过 **数据准备与接口速度** 控制耗时，而非在用例里再叠加超大 timeout。
- 并发：`maxConcurrency: 10` + `fileParallelism: true` → 测试必须在 **并发执行下仍然稳定**，测试数据天然隔离且唯一。

据此，编写或修改测试时必须满足：

- 避免对执行顺序、全局可变状态有隐式依赖。
- 为每个用例生成独立且唯一的数据，避免跨用例/跨文件互相污染。
- 所有外部依赖（后端服务、DB/Redis 等）在并发访问下也应可重复执行。

**目录与职责边界：**

- 用例文件：`dehaze-tool/dehaze-sdk-js/test/modules/**/**.test.ts`。
- 工厂函数：`dehaze-tool/dehaze-sdk-js/test/factories/**`：
  - 固定常量：`test/factories/constants.ts`（如预置 `USERS/ROLES/DEPTS`、固定可见用户数等）。
  - 通用唯一数据生成：`test/factories/common.ts`（如 `uniqueEmail/uniqueMobile/uniqueName`）。
  - 业务表单/查询对象工厂：如 `test/factories/user.ts` 中的 `createUserForm/createUserQuery` 等。

> 约束：测试文件内避免重复手写大量随机/拼接数据；优先复用 factories，保证一致性、唯一性与可复现排查路径。

#### 测试编写规范

- API 测试编写规范：查阅 [SDK-JS 测试编写规范](./references/sdk-js-testing.md)

#### Workflow A：编写/补充测试

"为某个 `UserAPI.xxx`/`RoleAPI.xxx` 等接口新增或补充测试" → 使用 Workflow A。

如在编写测试期间发现接口行为与预期不符，可在完成 A 流程的基础上切换到 Workflow B 进行归因，并在确认是后端问题后固化 bug 用例。

**【重要】**：编写测试时必须查看 [测试用例编写步骤](./references/sdk-js-write-test.md)

#### Workflow B：测试失败排查与归因

目标：当 dehaze-sdk-js API 测试失败、不稳定或行为异常时，按固定顺序判断问题来源（测试代码编写错误/测试数据与断言错误/SDK 封装问题/后端代码/数据库问题），并给出下一步改动建议。

当测试失败时，**必须**按照归因决策树逐步判断，**严禁**跳过任何步骤直接修改测试预期。

**归因决策树：**

```
测试失败
  │
  ├─ 明显语法/逻辑错误？ → 修复测试代码
  ├─ 违反测试规范？ → 修复测试代码
  │
  ├─ CURL 验证
  │   ├─ curl 成功且符合预期 → 检查 SDK 封装
  │   ├─ curl 失败但符合业务逻辑 → 测试正确，无需修改
  │   ├─ curl 失败且违反业务逻辑 → 后端 bug ✅
  │   └─ curl 与测试不一致 → 检查 SDK 封装
  │
  ├─ SDK 封装问题？ → 修复 SDK
  │
  ├─ OAS 文档不一致？ → 对齐文档
  │
  ├─ 并发/环境/数据问题？ → 修复测试数据/清理
  │
  └─ 确认后端 bug → 保留失败测试 + 标记 + 反馈
```

详细排查步骤见 [测试失败排查与归因](./references/sdk-js-test-failure.md)，在非失败排查阶段，请勿查看。
