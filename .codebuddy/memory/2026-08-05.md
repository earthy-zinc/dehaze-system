## dehaze-android 消息 Tab 角标全局状态改造

### 用户反馈
底部导航栏消息 Tab 角标异常：(1) 点开消息后角标才更新；(2) 切 Tab 后角标消失；(3) 未读数逻辑应全局。

### 根因（5 个叠加问题）
1. `MessagesViewModel` 用 Fragment scope（`new ViewModelProvider(this)`），切 Tab 时 ViewModel 销毁，LiveData 重置
2. 从未调用真实 `MessageAPI.getUnreadCount()`，`unreadCount` LiveData 一直是初始值 0
3. `loadMessages()` 加载的是 `TaskAPI`（任务）+ `ModelAPI.listPredictionLogs`（日志），不是真消息
4. `markAsRead`/`markAllRead` 只改本地状态，未调后端 API
5. Badge observer 绑在 `getViewLifecycleOwner()`，切 Tab 时失效

### 修复方案（完整修复）
1. **新建全局 `UnreadMessageViewModel`**（Activity scope）：调 `MessageAPI.getUnreadCount()`，LiveData 暴露未读数
2. **MainActivity** 创建该 ViewModel（Activity scope），observe 未读数更新 `BottomNavigationView` Badge，onResume 刷新
3. **MessagesViewModel 重写**：
   - `loadMessages()` 改调 `MessageAPI.getPage()`，filter 映射后端 type（全部/inbox/announcement/business）
   - `markAsRead(id)` 调 `MessageAPI.markRead(id)`，成功后通过 `markedReadId` LiveData 通知 Fragment
   - `markAllRead(type)` 调 `MessageAPI.markAllRead(type)`，成功后通过 `markedAllRead` LiveData 通知
   - 移除本地 `unreadCount` LiveData（交给全局）
4. **MessagesFragment**：
   - 通过 `new ViewModelProvider(requireActivity()).get(UnreadMessageViewModel.class)` 获取 Activity scope ViewModel
   - 移除 `updateBadge()`，由 MainActivity 统一管 Badge
   - `onResume` 调 `unreadMessageViewModel.refresh()`，从详情页返回时同步
   - markAsRead/markAllRead 成功后触发 `unreadMessageViewModel.refresh()`
5. **MessagesAdapter 适配 MessageVO**（id/type/typeLabel/title/summary/createTime/readStatus），替换旧的内部 `MessageItem`

### 实测验证（模拟器 Medium_Phone_API_36.0）
- 启动时 `MainActivity.onResume` 调 `/api/v1/messages/unread-count` → 角标 93 正确显示
- 切到首页/工具 Tab，角标 93 仍在（**问题 2 修复**）
- 点开消息调 `PATCH /api/v1/messages/1265/_read` → 角标 93→92（**问题 1 修复**）
- 点击"全部已读"调 `PATCH /api/v1/messages/_read-all` → 角标消失，列表全部已读样式（标题 0.6 alpha、dotUnread 隐藏）

### 教训
"**全局状态**"在 Android 中优先用 ViewModelProvider + Activity scope，**不要把跨页面的状态塞到 Fragment scope ViewModel 或绑定 Fragment view lifecycle**。SDK 早就提供了完整消息 API，应用层没用，导致历史实现走了歪路（用任务冒充消息）。

## dehaze-test 联调测试工具集搭建

### 背景
`scripts/debug_helper.py` 是临时脚本，docker exec 依赖本地服务、不可靠。需要模块化测试工具支持多后端、多用户、MySQL/Redis 直连。

### 架构评审决策
- **项目名**：`dehaze-test`（不是 dehaze-debug，与 sdk-js/test 命名一致）
- **形态**：独立项目 `dehaze-test/`，不建独立 venv，复用 `dehaze-python/.venv`（已有 redis 6.4 / pymysql 1.4 / httpx 0.28 / pytest 8.4）
- **结构**：扁平单层包 `utils/` + `tests/` + `scripts/`，对齐 sdk-js/test/utils/
- **入口**：模块化工具函数 + pytest，ad-hoc 脚本只是 utils 的薄封装
- **旧文件**：删除 `scripts/debug_helper.py`、`scripts/debug_helper/`、`scripts/rebuild_mysql.sh`（不保留兼容入口，旧脚本本来就是临时）

### 项目结构
```
dehaze-test/
├── utils/         # config / redis / mysql / auth / api / cleanup
├── tests/         # conftest + test_auth + test_messages + test_compare_backends
└── scripts/       # login / unread_count / cleanup / compare_backends / db_query / rebuild_mysql
```

### 关键设计
- **多后端**：BACKENDS = {java:8989, go:8990, python:8991}，所有函数接受 backend 参数
- **多用户**：`_session_store: dict[(backend, username), session_id]` 内存缓存（不做文件缓存，对齐 sdk-js）
- **验证码**：`captcha_code:{captchaKey}` 从 Redis 直读，避免 OCR
- **成功码**：三端统一 `"00000"`（不是 200！对齐 sdk-js/src/enums/ResultEnum.ts）
- **直连**：pymysql / redis-py 直连远程，不依赖本地 docker

### 网络前提（重要）
- 三端后端通过本机映射端口访问，开箱即用
- **Redis 6379 / MySQL 3306 远程端口不开放**，需要 `ssh -L` 转发后才能直连（端口转发由用户自行管理，属高风险操作）

### 验证结果
- utils 6 模块 import OK，配置从 .env 正确读取
- `compare_backends.py /api/v1/auth/captcha`：java 后端返回 `00000` + captchaKey ✅
- pytest 识别 24 个测试用例
- 修复成功码 bug：`code != 200` → `code != "00000"`（三端统一）

### 迁移内容
- `scripts/rebuild_mysql.sh` → `dehaze-test/scripts/rebuild_mysql.py`（pymysql 直连，去 docker）
