## dehaze-android 编译失败排查

### 现象
`./gradlew installDebug` 报 `processDebugResources FAILED`，所有 drawable（bg_icon_blue、ic_image 等 13 个）报 "not found"。

### 排查过程（低效→高效）
1. 先用 `git stash` 二分法：
   - 纯 modified drawable → 编译通过
   - 加回新增 drawable 前4个 → 失败
   - 加回前2个 → 失败
   - 只加 `bg_btn_brand.xml` → 失败
2. 定位根因：`bg_btn_brand.xml` 第一行 `encoding="utf8"`（缺连字符），AAPT2 解析失败导致**整个 drawable 目录被跳过**
3. 顺带发现 `ic_metrics.xml` 缺 `<?xml ...?>` 声明
4. `git stash pop` 不会恢复 untracked 文件，需用 `git show "stash@{0}^3:<path>"` 提取

### 修复
- `bg_btn_brand.xml`: `encoding="utf8"` → `encoding="utf-8"`
- `ic_metrics.xml`: 补上 `<?xml version="1.0" encoding="utf-8"?>`

### 关键教训
- **一个 XML 文件的编码声明错误会连带整个目录被 AAPT2 跳过**，导致所有 drawable 报 not found
- 二分排除法（stash + 逐步恢复）比逐个检查文件高效得多

## dehaze_flutter Zone mismatch + FlutterError 日志定位修复

### 问题
1. **Zone mismatch 启动崩溃**：`main.dart` 中 `WidgetsFlutterBinding.ensureInitialized()` 在 `runZonedGuarded` 外调用，`runApp` 在内部调用，违反 Flutter "binding 初始化 zone 必须与 runApp zone 一致" 约束，启动时抛 assertion。
2. **FlutterError 日志丢失定位信息**：`FlutterError.onError` 原实现 `errorStack: details.stack?.toString()`，对于布局/渲染错误（如 `RenderFlex overflowed by 73 pixels on the bottom`），stack 仅指向 framework 内部（layout/paint 流程），不指向用户 widget 代码。本地文件/ELK 翻不到源 widget，告警"没有太大作用"。

### 修复
- `WidgetsFlutterBinding.ensureInitialized()` + `SharedPreferences.getInstance()` + `Logger.init` + `FlutterError.onError` + `PlatformDispatcher.onError` + `runApp` 全部移入 `runZonedGuarded` body 内
- Zone 兜底回调增加 `Logger.isInitialized` 守卫，未初始化时 `debugPrint` 降级，避免二次崩溃
- `FlutterError.onError` 改为 `errorStack: details.toString()`：与控制台 `dumpErrorToConsole` 同源，含 `library` 来源、widget 上下文（`informationCollector` 的 Creator 链）、RenderObject 诊断、约束等
- `message` 追加 `library` 标注（`FlutterError [rendering library]: ...`），便于 ELK 按错误来源库过滤

### 关键教训
- Flutter `runZonedGuarded` 必须包裹 `ensureInitialized`，否则 binding 初始化记录的 zone 与 runApp 检查时的 zone 不一致
- Flutter 布局/渲染错误不能用纯 `details.stack` 上报：stack 不指向用户 widget，必须用 `FlutterErrorDetails.toString()`（含 `informationCollector` 输出的 widget 上下文）才能在 ELK/本地日志定位问题源
- 同步更新了 `dehaze-doc/docs/05-改造计划/前端日志监控改造计划.md` §3.3.3 `error_stack` 字段规范，明确 Flutter 端必须使用 `FlutterErrorDetails.toString()`

## Flutter 端日志去重 + 控制台双重输出修复

### 问题
1. Logger 无去重：RenderFlex overflow 在 layout 阶段每帧触发，60fps 下每秒记录 60 条相同错误，刷爆本地文件/ELK
2. 控制台双重输出：`FlutterError.presentError(details)` 输出 `══╡ EXCEPTION CAUGHT BY ... ╞══` 或 `Another exception was thrown:`，与 Logger 的 `ConsoleTransport` 输出（`[dehaze][ERROR] ...`）重复

### 修复
- `Logger.log()` 在 ERROR 级别加 fingerprint 去重：`message + errorStack` 的 hashCode，10s 窗口内相同 fingerprint 只记录一次（同时作用于 transports/本地文件/ELK 上报）
- 不同 trace_id 的 API 错误 fingerprint 不同，不会被误去重
- `FlutterError.onError` 移除 `FlutterError.presentError(details)` 调用：Logger 的 `error_stack` 已含完整诊断（`FlutterErrorDetails.toString()` 与 `dumpErrorToConsole` 同源），信息不丢失，控制台统一为 Logger 一条输出

### 关键教训
- Flutter 设置 `FlutterError.onError` 后，框架不再自动调用 `dumpErrorToConsole`，由 `onError` 决定如何处理；调用 `FlutterError.presentError` 会恢复默认输出，与 Logger 形成双重输出
- ERROR 去重 fingerprint 用 `message + errorStack` 即可：相同布局错误 stack 一致，不同 API 错误 trace_id 不同 → message 不同

## Flutter Logger 字段规范对齐 07-日志架构设计

### 对照结果
对照 `dehaze-doc/docs/02-系统架构/07-日志架构设计.md` §3.5 / §10.4 规范与 Flutter 实际实现，发现 4 处不一致：
1. **`user_id` 字段违反安全约束**（高优先级）：文档 §3.5.1 / §10.3 明确"前端 SDK 不上报 user_id，由后端从会话注入"，JS SDK 已删除该字段，但 Flutter Logger 仍保留 `LogEntry.userId` + `Logger.init` 接受 `userId` 参数 + `toJson` 输出 `user_id`，存在身份伪造风险面
2. **`url` 字段从未传递**（中优先级）：文档 §3.5.2 要求前端上下文含 `url`，Flutter 所有调用点（FlutterError.onError / PlatformDispatcher.onError / Zone 兜底 / TraceInterceptor.onError）均未传，ELK 无法按页面过滤错误
3. **FileTransport 保留策略文档与实现不一致**（低优先级）：§3.6.2 / §10.4 写"7 天"，实际是开发 7 天 + 生产兜底 3 天
4. **去重 + 移除 presentError 未在文档体现**（低优先级）：上一轮新增的 Logger ERROR 去重 + 移除 `FlutterError.presentError` 未同步到 §3.5.4 / §10.4

### 修复
- `log_entry.dart`：删除 `userId` 字段及 `toJson` 中 `user_id` 输出
- `logger.dart`：删除 `init` 的 `userId` 参数与 `_userId` 字段；新增 `attachRouter(GoRouter)` + `_currentRoutePath()`，`log()` 自动取 `routerDelegate.currentConfiguration.last.matchedLocation` 填充 `url`（调用点显式传 url 时优先用调用点的）
- `transports.dart`：`readRecentErrorLogs` 不再解析 `user_id`
- `main.dart`：根 Widget build 时调用 `Logger.instance.attachRouter(router)`
- 同步更新 `07-日志架构设计.md` §3.5.4（追加 ERROR 去重说明）+ §10.4 Flutter 描述（不调用 presentError / 路由自动填 url / 不暴露 user_id / 保留策略区分开发生产）+ §11 变更记录
- 同步更新 `05-改造计划/前端日志监控改造计划.md` §3.6.2 保留策略表 + 变更记录

### 关键教训
- 前端 SDK 设计要彻底移除敏感字段（user_id），不能只在调用点不传——保留 SDK 层接口就是漏洞面
- 全局错误捕获点没有 BuildContext，要填 `url` 字段需通过 router 全局引用（attachRouter 注入），不能用 context-based API

## tools 页面 RenderFlex overflow + macOS 网络沙箱修复

### 问题 1：tools/index.dart:308 RenderFlex overflow 73 像素
- **根因**：`_ToolCard` 的 `GridView` 用 `childAspectRatio: isWide ? 1.15 : 1.05`，窄屏 3 列 cell 宽 ~80，高度 ~76，减去 Padding(16*2) 后可用高度仅 ~44，但子内容（48 图标容器 + spacingS + title + spacingXS + subtitle 2 行）总高度 ~132，溢出 73 像素
- **修复**：`childAspectRatio` 改 `isWide ? 1.0 : 0.82`（让 cell 更高）；`subtitle` 用 `Flexible` 包裹（空间不足时自动省略，不溢出）；`title` 加 `maxLines: 1 + overflow: ellipsis`
- **关键教训**：GridView 的 `childAspectRatio` 要根据子内容实际高度计算，不能凭感觉；可变高度子项（多行 Text）用 `Flexible`/`Expanded` 包裹是防溢出的标准做法

### 问题 2：macOS 端 Dio 连接 127.0.0.1:8989 报 `SocketException: Operation not permitted`
- **根因**：`DebugProfile.entitlements` 有 `network.server`（允许监听）但**缺 `network.client`**（允许出站连接）；`Release.entitlements` 只有 `app-sandbox` 啥网络权限都没有。macOS App Sandbox 阻止出站连接，Dio 无法连后端
- **修复**：两个 entitlements 文件都添加 `<key>com.apple.security.network.client</key><true/>`
- **关键教训**：Flutter macOS 端默认开启 App Sandbox，必须显式声明 `network.client` 才能发起 HTTP 请求；iOS/Android 没有这个限制，所以其他端能正常连接
- **生效方式**：entitlements 改动需要 `flutter clean` + 重新 `flutter run -d macos`（Hot Reload 不重新编译 native）

## home 页面 macOS 桌面端布局塌缩修复

### 问题
- `_buildDesktopStats` 4 个统计卡片 Row 内部 Row 溢出 11 像素（Container 48 + SizedBox 16 = 64 > Card 内部可用宽度 52.8）
- `_buildDesktopQuickActions` 4 个图标标签换行（"图像输入"分两行）
- 整个 home 区域约 800 像素宽，居中显示在 1478 像素窗口里，远小于应有宽度

### 根因（两处叠加）
1. **`_buildDesktopLayout` 的 Column `crossAxisAlignment: CrossAxisAlignment.start`（默认值）**：Column 在水平方向收缩到子内容最小宽度。_buildDesktopStats 是 Row，4 个 Card 等分时最小宽度 = 4 * (Container 48 + SizedBox 16 + 0) + 3 * spacingM = 387.2，导致整个 home 区域只占 387 像素
2. **`_buildDesktopQuickActions` 的 off-by-one**：每个 item 都有 `margin: EdgeInsets.only(right: spacingM)`，包括最后一个（应该是 3 个间距但给了 4 个）；Text 没设 `maxLines: 1`，标签长就换行

### 修复
- `_buildDesktopLayout` Column 改为 `crossAxisAlignment: CrossAxisAlignment.stretch`：让子 widget 在水平方向铺满父级宽度（桌面端 1430 - 48 = 1182）
- `_buildDesktopQuickActions` 改 `asMap().entries.map` + `isLast` 判断，最后一个不加 right padding
- `_buildDesktopQuickActions` Text 加 `maxLines: 1` + `overflow: TextOverflow.ellipsis` + `textAlign: TextAlign.center`
- **不需要修 `_buildStatCard` 内部 Row**：外层 stretch 后 Card 宽度从 85 → 295+，Row 内容（48 + 16 + Expanded）自然够用

### 关键教训
- **Column 默认 `crossAxisAlignment: start` 是布局塌缩常见坑**：Column 在 SingleChildScrollView/ListView 内时，子 widget 不会铺满宽度。桌面端布局必须显式 `CrossAxisAlignment.stretch` 或用 `SizedBox(width: double.infinity, child: ...)` 强制铺满
- **Row + 固定 width + margin 的 off-by-one 错误反复出现**：每个 item 加 right margin 容易写成 N 个间距（应为 N-1），统一改成 `isLast` 判断是防错标准写法
- **Card/Row 内 Text 必须加 `maxLines: 1` + `overflow: ellipsis`**：即使当前宽度够，极窄屏或长翻译文本仍会换行，破坏布局

## dehaze-react-native iOS 构建修复（Pods 缺失 + fmt 11.0.2 consteval）

### 现象
`yarn run ios` 报 `Unable to open base configuration reference file '.../Pods-DehazeReactNative.debug.xcconfig'`。

### 修复链路
1. `ios/Pods` 目录缺失 → `pod install --repo-update`
2. `lottie-ios` 版本冲突：Podfile.lock 锁 4.5.0，lottie-react-native 7.3.8 要求 4.6.0 → `pod update lottie-ios lottie-react-native`
3. 重新构建报 `fmt/format-inl.h:59: error: call to consteval function ... is not a constant expression`（错误实际在 fmt pod 自己的 `Pods/fmt/src/format.cc` 编译中，不是 Yoga）
4. 根因：RN 0.81.4 锁定的 `fmt@11.0.2` 与 Xcode 26 新 Clang 在 C++20 consteval 上不兼容（已知问题 [facebook/react-native#55601](https://github.com/facebook/react-native/issues/55601)）
5. fmt 11.0.2 的 `base.h` 无条件 `#define FMT_USE_CONSTEVAL 0/1`，未用 `#if !defined(FMT_USE_CONSTEVAL)` 包裹，所以设 GCC_PREPROCESSOR_DEFINITIONS 无效
6. **解决方案**：Podfile `post_install` 中把 fmt target 的 `CLANG_CXX_LANGUAGE_STANDARD` 改为 `c++17`，使 `__cpp_consteval` 不定义，FMT_USE_CONSTEVAL 自动走 0 分支
7. 重新 `pod install` + 构建 → `** BUILD SUCCEEDED **`，`yarn run ios` 成功启动 App

### Podfile post_install 修改
```ruby
post_install do |installer|
  react_native_post_install(installer, config[:reactNativePath], :mac_catalyst_enabled => false)
  installer.pods_project.targets.each do |target|
    next unless target.name == 'fmt'
    target.build_configurations.each do |config|
      config.build_settings['CLANG_CXX_LANGUAGE_STANDARD'] = 'c++17'
    end
  end
end
```

### 关键教训
- RN 0.81 + Xcode 26 组合下，fmt 11.0.2 consteval 编译错误是已知问题，临时方案是降 fmt 的 C++ 标准到 c++17
- 不要被错误输出中混在一起的 Yoga 编译命令误导，要 grep `In file included from` 确认错误实际源头是 `Pods/fmt/src/format.cc`
- fmt 11.0.2 base.h 不支持外部覆盖 `FMT_USE_CONSTEVAL` 宏（直接 #define，无 #if !defined 守卫），只能通过降 C++ 标准来禁用 consteval

## dehaze-react-native [runtime not ready]: Cannot read property 'install' of undefined（iOS+Android 双端同错）

### 现象
双端启动报 `[runtime not ready]: TypeError: Cannot read property 'install' of undefined`，栈在 JS bundle 模块加载期。

### 排查弯路（教训）
- 先怀疑 `react-native-gesture-handler` 的 `RNGestureHandlerModule.install()`（init.js:21）→ 排查 Pods/SPM/TurboModule 注册，全是死路
- 验证 iOS 构建产物：`DehazeReactNative.debug.dylib` 里 836 个 RNGestureHandler 符号齐全，原生链接无问题
- **双端同错 = JS bundle 层问题，不是原生链接问题**，应第一时间想到这个判别法

### 真正根因
`src/App.tsx:8` 模块顶层调用 `Logger.install(...)`，但 `node_modules/dehaze-sdk-js/dist/index.js` 是 7月29日的旧构建（不含 Logger 导出），`Logger` import = undefined → `.install` 报错。
- SDK 源码头一天新增了 `src/logger/Logger.ts`（Logger 类），但 dist 未重建
- yarn v1 的 `file:../dehaze-sdk-js` 依赖是**复制到 node_modules**（非软链），SDK 源目录重建 dist 后 node_modules 副本不会自动同步

### 修复
1. `cd dehaze-sdk-js && npx tsup` 重建 dist（产物 51KB → 75KB）
2. `rm -rf node_modules/dehaze-sdk-js` + 手动 `cp -R dehaze-sdk-js/dist` 到 node_modules（yarn install 完整重装被用户中断，手动 cp 更快）
3. 杀 8081 端口旧 Metro，`npx react-native start --reset-cache`
4. `yarn run ios` 重跑 → App 正常连接无错误

### 关键教训
- **dehaze-sdk-js 源码改动后必须 `npx tsup` 重建 + 同步 node_modules 副本**，file: 协议不会自动联动
- `[runtime not ready]` 前缀来自 `JsErrorHandler.cpp:329`，表示错误在 JS runtime ready 之前的模块加载期 → 优先怀疑入口链上的模块顶层代码
- "Cannot read property 'install' of undefined" 不要只盯 native module，应用自己的模块顶层调用（如 Logger.install）同样会触发

## dehaze-sdk-js Logger currentUrl RN 环境崩溃（pathname of undefined）

### 现象
RN App 报 `[runtime not ready]: TypeError: Cannot read property 'pathname' of undefined`，栈在 SDK `currentUrl` → `log` → `error` → `reportFatalError`。

### 根因
`dehaze-sdk-js/src/logger/Logger.ts:41`：
```ts
return typeof window !== "undefined" ? window.location.pathname + window.location.search : "";
```
RN (Hermes) 有全局 `window`（=== globalThis）但**无 `window.location`**，`typeof window !== "undefined"` 判断在 RN 成立 → `undefined.pathname` 崩溃。且这是 Logger 在记录另一个模块加载错误时的二次崩溃，掩盖了原始错误。

### 修复
`Logger.ts:41` 加 `window.location` 存在性判断：`typeof window !== "undefined" && window.location ? ... : ""`。重建 + 同步 node_modules + 重启 App 后无错误。SDK 31 个单测全通过。

### 关键教训
- **RN 环境探测不能用 `typeof window !== "undefined"`**：RN 有 window 但无 DOM API（location/document 等），要直接判断目标属性（window.location、navigator.userAgent）
- RN 的 navigator 只有 `product === "ReactNative"`，无 userAgent（返回 undefined，不崩但字段为空）
- Logger 全局错误 handler 自身崩溃会掩盖原始错误：handler 内部必须防御性编程，任何环境 API 调用都要 try-catch 或存在性判断

## dehaze-react-native 白屏三连修复（SDK RN 兼容重构 + auth 卡死 + react 版本）

### 用户反馈的三个问题
1. loading 卡死（SplashLoading 永远转圈）
2. 白屏不暴露任何错误（Logger 吞错误）
3. SDK 要兼容非浏览器环境，需重构

### 修复 1：SDK RN 环境兼容重构（dehaze-sdk-js）
- 新增 `src/logger/env.ts`：`isBrowser()`（window + addEventListener）/ `isRN()`（navigator.product === "ReactNative"）**运行时函数**

- Logger.ts 五处统一改用 env 函数：currentUrl / currentUserAgent / registerGlobalHandlers / startPerformanceMonitoring ×2
- **ErrorUtils handler 链式调用原 handler**：原实现覆盖 setGlobalHandler 不调原 handler，RN dev 红屏被吞 → 白屏无提示。修复后 `originalHandler?.(error, isFatal)`，红屏恢复（修复后立刻暴露了 react 版本不匹配错误）
- currentUserAgent RN 分支返回 "ReactNative"（RN navigator 无 userAgent）
- 新增 `test/unit/logger/rn-env.test.ts`（2 用例：install 不抛错 + ErrorUtils 链式调用），stub 方式：window===globalThis + navigator.product + resetModules + dynamic import

`src/store/auth.ts` zustand persist `onRehydrateStorage` 回调里 `state.loading = false` 是**直接 mutation，不触发 zustand 通知**，组件不重渲染 → RootNavigator 永远 loading=true → 永久 SplashLoading。改为 `useAuthStore.setState({ loading: false })`。
