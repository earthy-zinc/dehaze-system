# 文档治理规则

> 本文档定义 dehaze-doc 文档体系的**组织方式、单一信息源原则、变更流程与质量要求**，是约束整个文档体系的元规则。所有文档的新增、修改、评审均须遵循本文档。作为顶层治理文档，置于目录 `00-文档治理`，先于其他分区生效。

## 1. 目标

| 目标 | 说明 |
|------|------|
| 单一信息源 | 每个事实只在唯一位置定义，其余文档引用而非复制 |
| 文档与代码一致 | 接口、字段、流程的文档反映代码最新状态，禁止滞后 |
| 口径不漂移 | 术语、规范、模块能力在体系内口径唯一 |
| 结构可预测 | 新增内容有明确归属，不依赖个人习惯放置 |
| 信息密度 | 文档只描述当前契约，删除状态标记、演进记录与过程校正等低信息量内容，保持阅读信息密度 |

## 2. 文档目录与职责划分

| 分区 | 职责 | 禁止内容 |
|------|------|---------|
| **00-文档治理** | 文档体系本身的规则（本文档、命名、评审流程） | 业务功能细节 |
| **01-产品设计** | 产品概述、设计规范、规划（面向产品与体验） | 技术实现细节（如具体 API 字段） |
| **02-系统架构** | 技术底座：总体架构、数据库、API 规范、测试、部署、日志 | 单一模块的细节 |
| **03-模块设计** | 按模块组织：需求规格 / API 接口 / 前端实现 / 后端实现 / 测试用例 | 跨模块的全局规范 |
| **04-项目实现** | 各技术栈架构文档（前端 / 后端 / 算法） | 业务需求 |
| **05-改造计划** | 已决策的改造与升级规划 | 未评审的设想 |

**归属判定**：跨模块、跨端的问题 → 产品设计/系统架构；单一模块的问题 → 模块设计；纯技术栈 → 项目实现。拿不准时按"更高一层"归属，避免碎片化。

## 3. 单一信息源原则

| 事实类型 | 定义位置 | 引用方式 |
|---------|---------|---------|
| 产品术语 | [文案与术语规范](../01-产品设计/06-文案与术语规范) | 模块文档直接引用术语表，不复制定义 |
| 导航与页面层级 | 移动端/桌面端界面设计规范、菜单与页面层级规划 | 模块文档引用其层级归属，不另起炉灶 |
| 权限模型 | 权限相关规范（规划中） | 各模块权限点引用统一矩阵 |
| 模块能力 | 对应模块的《需求规格》 | 其他文档引用该规格，不重复描述 |
| API 定义 | 对应模块的《API接口》 | 前端实现/测试用例引用接口定义 |
| 错误码 | 页面状态与错误码规范（规划中） | 前后端文档引用错误码表 |

**硬性规则**：
- 禁止在多个文档中复制同一份定义（术语、权限、错误码、接口字段）。
- 复制粘贴导致的口径漂移（同一事物两处定义不一致）视为文档缺陷，评审时发现须立即收敛。
- 引用使用相对链接（如 `[术语表](../01-产品设计/06-文案与术语规范)`），不使用"见上文/详见之前"等模糊表述。

### 3.2 状态标记与演进内容

文档描述**当前契约**（"是什么、为什么这样设计"），禁止混入演进状态与过程记录：

| 禁止项 | 正确做法 |
|--------|---------|
| "✅ 已实现 / ⏳ 规划中 / 远期"状态标记 | 删除标记；规划内容迁入 [05-改造计划](../05-改造计划/)，需求规格只写当前契约 |
| "早期需求稿…当前未实现"校正注释 | 删除；未实现的表述属规划，不入需求规格 |
| "本版新增 / 本次改造说明"演进说明 | 删除；版本演进记录不入正式文档 |
| 待确认事项混入已定决策 | 已定决策写入正文；仅真正未决问题保留在待确认事项 |

## 4. 文档变更流程

### 4.1 触发条件（与《通用项目规则》一致并细化）

代码/设计变更满足以下任一条件时，必须同步更新文档：

| 变更 | 必须更新的文档 |
|------|--------------|
| API 请求/响应参数增删改 | 模块《API接口》+ 受影响的前端实现 + 测试用例 |
| 数据流/架构调整 | 系统架构文档 + 相关模块文档 |
| 新增/调整页面或菜单 | 菜单与页面层级规划 + 对应端路由/菜单说明 |
| 新增模块 | 按模块模板建目录（需求规格/API接口/前端实现/后端实现/测试用例） |
| 术语/文案变更 | 文案与术语规范 + 全端文案 |
| 设计规范变更 | 对应规范文档 + 引用该规范的模块文档 |

### 4.2 变更步骤

1. 定位受影响文档（先全局搜索引用点，不凭记忆）。
2. 修改"单一信息源"处（如术语表、API 定义）。
3. 同步所有引用方；引用方只更新引用关系，不复制新内容。
4. 代码与文档同时提交，禁止"先改代码、文档后补"或反之拖延。

### 4.3 新增文档的准入

新增文档前先回答：
- 该内容是否有已有文档可扩展？（优先扩展而非新建）
- 该内容属于哪个分区？（见第 2 节）
- 是否与现有文档重复？（重复则拒绝，改引用）

## 5. 文档与代码一致性

| 规则 | 说明 |
|------|------|
| 字段名一致 | 文档字段名与代码字段名严格一致；改名时全局搜索一并修改，不保留旧字段兼容 |
| 示例真实 | 文档中的示例请求/响应与真实 API 一致，禁止虚构字段 |
| 状态同步 | 页面状态（加载/空/错误）、错误码以文档为准，代码实现对齐 |
| 多端一致 | 同一 API 在前端各端（Web/移动/桌面）文档中的描述一致 |

## 6. 命名与格式规范

| 维度 | 规范 |
|------|------|
| 目录命名 | 序号-名称（如 `01-产品设计`、`00-文档治理`），模块目录用中文功能名 |
| 文件命名 | 序号-名称.md（如 `06-文案与术语规范.md`）；模块内固定：需求规格/API接口/前端实现/后端实现/测试用例 |
| 命名唯一性 | 文件名**区分大小写不视为独立文档**；新增前检索现有文件（含大小写变体），重复或命名混淆则合并/重命名 |
| 标题 | 一级标题 = 文档名；层级 1-3 级，不跳级 |
| 表格 | 信息类内容优先表格；表头明确、不跨页拆义 |
| 图 | 架构/流程/层级用 Mermaid（已集成 vitepress-plugin-mermaid） |
| 链接 | 相对路径链接（cleanUrls 生效，不写 .md 后缀） |
| 术语 | 全文使用 [术语表](../01-产品设计/06-文案与术语规范) 规范术语 |

## 7. 评审与走查

| 节点 | 要求 |
|------|------|
| 设计走查 | 页面交付前对照对应设计规范自查清单（移动端/桌面端/菜单规划） |
| 文档评审 | 涉及 API/架构/规范的变更，评审时核对第 4.1 节触发条件是否全部满足 |
| 定期审计 | 检查是否存在复制漂移、失效链接、目录缺失；发现即修复 |
| 引用校验 | 引用目标的文件必须存在；失效引用视为缺陷 |

## 8. 自查清单

- [ ] 新增/变更已定位全部受影响文档并同步
- [ ] 定义只在单一信息源维护，引用方未复制
- [ ] 文档字段/示例与代码一致，无滞后
- [ ] 术语使用规范术语，未引入未登记的新叫法
- [ ] 文件命名、分区归属符合第 2/6 节，无命名重复（含大小写差异）
- [ ] 链接有效、无失效引用
- [ ] 无重复文档（存在则已收敛为引用）
- [ ] 无状态标记/演进记录/过程校正（"已实现/规划中/本版/本次改造/早期需求稿"扫描通过），规划内容仅在 05-改造计划
