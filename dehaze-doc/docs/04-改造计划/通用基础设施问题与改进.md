## 二、架构设计层面通用问题

### 2.1 [P0] TraceId 全链路追踪缺失，生产无法跨服务排障

**三端现状对比**：

| 端 | TraceId 生成 | MDC/ContextVar 注入 | 日志输出 | 跨服务透传 | 分布式追踪 |
|----|-------------|---------------------|----------|------------|------------|
| **Java** | ❌ 不生成 | ❌ Result.traceId 声明但从不赋值 | ❌ logback pattern 无 `%X{traceId}` | ❌ 无过滤器 | ❌ 无 OTel |
| **Go** | ✅ Trace 中间件 | ✅ context 传播 | ✅ Zap | ⚠️ 多处 `context.Background()` 断裂 | ❌ 无 OTel |
| **Python** | ✅ TraceMiddleware | ✅ ContextVar | ✅ JSON 注入 trace_id | ✅ X-Trace-Id 透传 | ❌ 无 OTel |

**通用问题**：
1. 三端均**未接入 OpenTelemetry / Jaeger / Zipkin**，无法形成跨 Python↔Java↔Go 的可视化全链路
2. Java 端 TraceId 完全缺失，Go 端多处 `context.Background()` 断裂，三端链路不一致
3. 跨服务调用（Java↔Python 算法调用、Go↔Python 推理）不透传 `traceparent` / `X-Trace-Id`

**统一改进建议**：
- 三端统一接入 OpenTelemetry SDK，HTTP 入口自动生成 Span，跨服务调用自动注入 `traceparent` 头
- Java 端优先补齐 TraceIdFilter + MDC + Result 回填 + logback `%X{traceId}`
- Go 端清理 `context.Background()` 调用，统一使用 `c.Request.Context()`
- 定义三端统一的请求头规范：`X-Trace-Id`（兼容 `traceparent` / `sw8`）

### 2.2 [P0] CORS 安全配置缺陷，凭证可被任意网站盗用

**三端现状对比**：

| 端 | AllowedOrigins | AllowCredentials | 问题 |
|----|---------------|-----------------|------|
| **Java** | `*`（allowedOriginPatterns） | `true` | 任意 Origin 反射 + 凭据，凭证盗用 |
| **Go** | `*` | `true` | W3C 违法组合，浏览器拒绝所有带凭据跨域请求 |
| **Python** | 白名单（localhost:3000/5173/8080） | — | ✅ 正确 |

**统一改进建议**：
- 三端统一改为 Origin 白名单，从配置文件读取（按环境区分 dev/prod）
- 生产环境禁止 `AllowOrigins: ["*"]` + `AllowCredentials: true` 组合
- 使用 `AllowOriginFunc` 动态校验来源域名

### 2.3 [P0] 缓存防护体系（L1/布隆/SingleFlight/熔断）未落地

**三端现状对比**：

| 端 | L1 本地缓存 | 布隆过滤器 | SingleFlight | 熔断器 | 空值缓存 |
|----|------------|-----------|-------------|--------|----------|
| **Java** | ❌ 无 Caffeine | ❌ | ❌ | ❌ | ⚠️ 仅 @Cacheable cache-null-values |
| **Go** | ❌ config 未启用 | ❌ 未启用 | ❌ 未启用 | ❌ 未启用 | ❌ 未启用 |
| **Python** | ❌ 无 | ❌ | ❌ | ⚠️ RedisCircuitBreaker 死代码 | ❌ |

**通用问题**：三端架构设计文档均规划了多级缓存 + 四重防护，但实际全部未落地。热 key 无本地缓存，Redis 单点压力无缓解；缓存穿透/击穿/雪崩三大风险无防护。

**统一改进建议**：
- Java 端引入 Spring Cache 多级缓存方案
- Go 端在 config.yaml 补充 `multiLevel` + `protection` 段并启用
- Python 端接入已定义的 `RedisCircuitBreaker` / `with_redis_retry`（删除或激活）
- 灰度策略：先启用 L1 + SingleFlight（低风险），观察后再启用 BloomFilter + CircuitBreaker
- 增加缓存命中率 Prometheus 指标，量化防护效果

### 2.4 [P0] 异步任务可靠性不足（无重试/幂等/死信/持久化）

**三端现状对比**：

| 能力 | Java | Go | Python |
|------|------|-----|--------|
| 任务重试 | ❌ 失败即 FAILED | ❌ nack requeue 无限重投 | ⚠️ 有分级重试延迟但无幂等 |
| 任务幂等 | ❌ UUID 无去重 | ❌ 无 | ❌ 无 |
| 死信队列 | ❌ MQ 全禁用 + 无 DLQ | ❌ 无 DLX 配置 | ⚠️ 有 DLX 但未完善 |
| 任务持久化 | ✅ DB + Redis | ✅ DB | ✅ DB + Redis |
| 进度推送 | ❌ 无 WebSocket（仅轮询） | ❌ 无 | ✅ WebSocket + Redis Pub/Sub |

**通用问题**：
1. 三端均缺乏任务幂等键，客户端重试产生重复任务
2. Java 端 MQ 代码全部禁用但存在（双路径死代码），Go 端无 DLX 导致毒药消息无限重投
3. Java/Go 端任务进度只能轮询，实时性差且增加 DB 负载

**统一改进建议**：
- 任务创建引入客户端幂等键（`Idempotency-Key` 头），三端统一去重逻辑
- RabbitMQ 配置死信交换机 + 死信队列，消息 header 携带 `x-retry-count`，超阈值 reject 入死信
- Java 端启用 MQ
- 三端统一 WebSocket 任务进度推送（Java/Go 对齐 Python 已有实现）
- 失败任务提供重放入口与告警

### 2.5 [P1] 监控端点（Actuator/Metrics）鉴权缺失

**三端现状对比**：

| 端 | 端点 | 鉴权 | 暴露内容 |
|----|------|------|----------|
| **Java** | `/actuator/**` | ❌ permitAll | health, info, prometheus, metrics |
| **Go** | `/metrics` | ❌ 无认证 | HTTP 请求统计、延迟直方图 |
| **Python** | `/metrics` | ⚠️ 条件启用 | HTTP/GPU/推理/任务指标 |

**通用问题**：Prometheus 端点无鉴权可被外部抓取，泄露 JVM/线程/堆/DB 连接池/业务规模等内部指标。

**统一改进建议**：
- `/actuator/health`（Java）/ `/health`（Go/Python）放行，其余监控端点要求 `ROLE_ADMIN`

### 2.6 [P1] 健康检查端点不完整，缺少依赖检查

**三端现状对比**：

| 端 | 健康检查 | DB 检查 | Redis 检查 | Liveness/Readiness 分离 |
|----|----------|---------|------------|------------------------|
| **Java** | `/actuator/health` | ✅ | ✅ | ❌ |
| **Go** | `/health` → 恒 200 | ❌ | ❌ | ❌ |
| **Python** | `/health` + `/health/db` + `/health/redis` | ✅ | ✅ | ❌ |

**通用问题**：Go 端 `/health` 恒返回 200，未检查 DB/Redis/RabbitMQ 连通性，K8s 探针不会重启故障 Pod。三端均未区分 liveness（存活）与 readiness（就绪）。

**统一改进建议**：
- 三端统一健康检查端点规范：
  - `/health`（liveness）：始终 200，仅表示进程存活
  - `/ready`（readiness）：检查 DB/Redis/MQ 依赖，任一不可用返回 503
- Go 端调用 `CacheManager.HealthCheck` + DB ping 补全依赖检查

### 2.7 [P1] 日志集中化管道（Kafka → ES/S3）未落地

**三端现状对比**：

| 端 | 日志输出 | 结构化 JSON | Kafka 管道 |
|----|----------|------------|------------|
| **Java** | 本地文件（纯文本） | ❌ | ❌ 规划中 |
| **Go** | 本地文件（Zap） | ⚠️ 可选 | ❌ 规划中 |
| **Python** | 本地文件 + 控制台 | ✅ 生产环境 | ❌ 规划中 |

**通用问题**：三端日志均为本地文件输出，缺乏集中检索、告警与审计管道。Java 端日志无结构化输出，不利于 ELK/Loki 采集。

**统一改进建议**：
- 三端统一启用结构化 JSON 日志（Java 端 logback 添加 Logstash encoder）
- 实施 Kafka 日志管道：应用日志 → Kafka → Elasticsearch（检索）/ 对象存储（归档）
- 统一日志字段规范：timestamp / level / logger / service / trace_id / message

### 2.8 [P1] 熔断/重试/弹性容错机制缺失或错误

**三端现状对比**：

| 端 | 熔断器 | 重试 | 连接池 |
|----|--------|------|--------|
| **Java** | ⚠️ 自研熔断器计算错误（10 次失败必触发） | ⚠️ Python 调用有重试但无幂等 | ⚠️ RestTemplate 无连接池 |
| **Go** | ❌ 无 | ❌ 无 | ✅ GORM 内置 |
| **Python** | ⚠️ RedisCircuitBreaker 死代码 | ⚠️ redis_fallback 有降级 | ✅ async pool |

**通用问题**：三端对外部服务调用（Python 算法服务、MinIO、Redis）的弹性容错策略不一致且不完善。Java 自研熔断器存在根本性计算错误。

**统一改进建议**：
- Java 端引入 Resilience4j（CircuitBreaker + Retry + Bulkhead）
- Go 端引入 go-resilience 或 sentinel-go
- Python 端激活已定义的 RedisCircuitBreaker
- POST 重试统一加幂等键，防止重复处理

### 2.9 [P1] 多实例/多 Worker 指标聚合问题

**三端现状对比**：

| 端 | 多实例指标 | 问题 |
|----|-----------|------|
| **Java** | ⚠️ Tomcat 多实例 | Prometheus 需配置多 target 抓取 |
| **Go** | ⚠️ 多实例 | 同上 |
| **Python** | ❌ uvicorn 多 Worker | 未配置 `PROMETHEUS_MULTIPROC_DIR`，`/metrics` 仅返回局部数据 |

**通用问题**：Python 端 uvicorn 多 Worker 部署下每个 Worker 独立维护指标，`/metrics` 端点仅返回命中 Worker 的局部数据。XXL-Job executor 端口也存在多 Worker 冲突。

**统一改进建议**：
- Python 端配置 `PROMETHEUS_MULTIPROC_DIR` + `MultiProcessCollector`
- XXL-Job executor 端口在多 Worker 下需确保仅首个 Worker 启动 daemon
- 三端 Prometheus 抓取配置统一规划

## 三、模块业务设计层面通用问题

### 3.1 [P0] 数据权限在异步上下文下被静默绕过（安全漏洞）

**三端现状对比**：

| 端 | 机制 | 异步场景问题 |
|----|------|-------------|
| **Java** | MyDataPermissionHandler（ThreadLocal SecurityContext） | MQ 消费者/@Async/@Scheduled 中权限完全失效 |
| **Go** | DataScope 插件（goroutine-local gin.Context） | GormContextMiddleware 未注册，DataScope 完全不生效 |
| **Python** | SQLAlchemy 查询装饰（规划中） | 后台任务未 set_current_user_id，审计字段为 None |

**通用问题**：三端数据权限均依赖请求上下文（ThreadLocal / goroutine-local / ContextVar），在异步任务（MQ 消费者、@Async、@Scheduled、asyncio.Task）中上下文不传播，**数据权限完全失效**，导致越权访问。审计字段（create_by/update_by）在异步场景同样填充为 null。

**统一改进建议**：
- 异步入口显式传播安全上下文（Java: `DelegatingSecurityContextRunnable`；Go: 传递 context；Python: 传递 user_id 到 ContextVar）
- 为系统任务构造专用 System 身份，明确标注系统操作来源
- 审计字段在异步场景使用系统用户 ID 兜底

### 3.2 [P1] 权限缓存一致性策略缺陷

**三端现状对比**：

| 端 | 缓存方式 | 回填策略 | TTL | 失效策略 |
|----|----------|----------|-----|----------|
| **Java** | Redis Hash | ❌ 回源不回填 | ❌ 无 TTL | ⚠️ 通配符 HDEL 失效（Bug） |
| **Go** | Redis | ✅ | ⚠️ 配置 | 显式刷新 |
| **Python** | Redis `role:perms:{role_code}` | ✅ | 30min | 显式刷新 |

**通用问题**：三端权限缓存策略不统一。Java 端存在严重 Bug（部分命中不回源、回源不回填、通配符删除失效、无 TTL），可能导致权限脏数据或越权。

**统一改进建议**：
- 三端统一权限缓存策略：逐角色判断缺失 → 回源 → 回填 → 设 TTL（如 30min）
- 角色菜单变更时显式刷新对应角色缓存（按 roleCode 精确删除，禁止通配符）
- 引入 SingleFlight 防止缓存击穿

### 3.3 [P1] 任务进度实时推送机制不统一

**三端现状对比**：

| 端 | WebSocket | 任务进度推送 |
|----|-----------|-------------|
| **Java** | 仅聊天（STOMP） | ❌ 仅 DB 轮询 |
| **Go** | ❌ 无 | ❌ 仅 DB 轮询 |
| **Python** | ✅ 原生 + Redis Pub/Sub 跨 Worker | ✅ 推理进度推送 |

**通用问题**：Java/Go 端任务进度只能轮询 `getTaskStatus`，实时性差且增加 DB 负载。Python 端已有 WebSocket + Redis Pub/Sub 实现，Java/Go 未对齐。

**统一改进建议**：
- Java/Go 端对齐 Python 的 WebSocket + Redis Pub/Sub 方案
- 任务进度更新写 Redis 缓存（非每次写 DB），定期或完成时同步 DB
- 定义三端统一的 WebSocket 消息格式（进度百分比、状态变更、完成通知）

### 3.4 [P1] 任务清理机制不一致

**三端现状对比**：

| 端 | 清理 Job | 问题 |
|----|----------|------|
| **Java** | TaskCleanupJob | ❌ Redis key 前缀错 + 状态大小写不匹配，清理逻辑是死代码 |
| **Go** | CleanupJob | ❌ 从未启动（InitJobs 未调用）+ 多个方法为 TODO 桩 |
| **Python** | XXL-Job 3 个任务 | ✅ 已实现（过期清理/僵死回收/模型健康检查） |

**统一改进建议**：
- Java 端修复 TaskCleanupJob 常量引用与大小写问题
- Go 端在 `app.Init()` 中调用 `job.InitJobs()`，补全 TODO 桩
- 三端统一任务清理规则：7 天前已完成/取消任务删除、30 天前所有任务删除、24h 僵死任务标记 failed

### 3.5 [P1] 审计字段自动填充在批量操作与异步场景失效

**三端现状对比**：

| 端 | 机制 | 批量操作 | 异步场景 |
|----|------|----------|----------|
| **Java** | MyMetaObjectHandler | ✅ | ❌ 无安全上下文时为 null |
| **Go** | GORM Callback | ✅ | ❌ 回调未注册 + 中间件未注册 |
| **Python** | SQLAlchemy Event + ContextVar | ❌ before_update 对批量 UPDATE 不触发 | ❌ 后台任务未 set_current_user_id |

**统一问题**：审计字段（create_by/update_by）在批量更新（Core 层 `update().where(...)`）和异步任务中填充失败，数据审计链断裂。

**统一改进建议**：
- 批量更新操作显式设置审计字段，或改用逐条 save 触发事件
- 异步场景传入系统用户 ID 兜底
- Go 端优先注册 GormContextMiddleware + RegisterGormCallbacks

### 3.6 [P2] N+1 查询模式普遍存在

**三端现状对比**：

| 端 | 典型 N+1 |
|----|----------|
| **Java** | 分页内逐条 `algorithmService.getById()`、循环内 `deleteFile`/`removeById` |
| **Go** | `FindUserAuthInfo` 一次登录 4 次 DB 查询 |
| **Python** | 分页内逐条关联查询 |

**统一改进建议**：
- 分页查询使用 JOIN 或批量 `IN()` 预加载关联数据
- 循环内单条操作改为批量 `deleteBatchIds`/`updateBatchById`
- 增加查询数量阈值告警，防止遗漏的 N+1 在数据量增大后爆发
