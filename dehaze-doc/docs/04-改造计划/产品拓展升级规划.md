# 产品拓展升级规划

> 本文档整合多轮架构与产品讨论结论，作为后续升级迭代的方向性依据。
> 涉及具体模块的功能需求，后续应在对应模块的需求规格文档中展开。

---

## 1. 技术架构选型结论

### 1.1 后端

| 维度 | 结论 | 说明 |
|------|------|------|
| **主推后端** | Go（Gin + GORM） | 内存占用低（20-50MB）、冷启动快（<1s）、单二进制部署 |
| **算法服务** | Python（Flask + PyTorch） | 保持独立，专注 AI 推理，不承担 CRUD 业务 |
| **Java 端** | 降级为参考实现 | 不再主动维护，可作为历史参考 |
| **通信方式** | REST + gRPC（Go↔Python） | 现有 gRPC 服务端可直接复用 |

**迁移原则**：Python 服务瘦身为纯算法微服务，所有基础 CRUD 业务统一由 Go 端承接。

### 1.2 前端

| 端 | 选型 | 级别 | 说明 |
|----|------|------|------|
| **Web 主端** | Vue 3 + Element Plus | Tier 1 生产就绪 | 27 个组件、完整测试、i18n、权限指令 |
| **桌面端** | Electron（基于 React） | Tier 2 功能完整 | React 端降级为桌面端专用载体 |
| **移动端** | Flutter | Tier 3 → 目标 Tier 1 | 一套代码覆盖 iOS/Android，图像渲染性能优 |
| **小程序** | uni-app | Tier 2 按需 | 国内小程序生态，轻量触达场景 |
| **鸿蒙端** | HarmonyOS ArkTS | 观望 | 保留 SDK 层，等市场验证后投入 |
| **JS/TS SDK** | dehaze-sdk-js | Tier 1 | 所有 JS/TS 端统一 API 层，已被 Taro/uni-app 引用 |

**关键前置动作**：Vue 主端和 React 端迁移至 `dehaze-sdk-js`，消除各端独立维护的 `utils/request.ts` 和分散 API 模块。

## 3. 产品拓展方向：AI 图像处理平台

### 3.1 扩展可行性评估

当前系统的核心基础设施（文件管理、任务队列、算法管理、用户权限、VIP 体系）是**通用的**，不是去雾专用的。Python 端的模型推理框架只需替换模型权重和预处理逻辑，即可支持其他图像处理任务，扩展边际成本低。

| 扩展方向 | 与现有用户重叠度 | 技术复用度 | 推荐优先级 | 代表模型 |
|---------|---------------|---------|------|------|
| **去雨 / 去雪** | 高 | 极高（同类大气退化问题） | ⭐⭐⭐ 最优先 | MPRNet、DerainNet |
| **低光增强** | 高 | 高 | ⭐⭐⭐ | RetinexNet、Zero-DCE |
| **图像超分辨率** | 高 | 高 | ⭐⭐ | Real-ESRGAN、SwinIR |
| **图像去噪** | 高 | 高 | ⭐⭐ | DnCNN、NAFNet |
| **图像修复（Inpainting）** | 中 | 中 | ⭐ | LaMa、MAT |
| **风格迁移** | 低 | 低 | 暂不推荐 | — |

**去雨/去雪**与去雾属于同一类图像退化问题（大气散射模型），算法结构几乎一致，是风险最低的第一步扩展，且能显著扩大用户场景覆盖（不再局限于雾霾天气）。

### 3.2 与现有系统的兼容性判断

**结论：现有架构天然支持扩展，改造成本可控。**

当前系统的任务队列、文件管理、用户权限、VIP 体系均与具体算法无关，属于通用基础设施。扩展新图像处理类型，主要改动集中在三处：

- **Python 算法服务**：现有推理入口针对去雾单任务硬编码，需改造为按任务类型分发的路由机制。各算法模型遵循统一接口规范，新增算法类型不影响已有逻辑，改造工作量小且风险可控。模型权重按需加载，避免多模型同时占用 GPU 显存。
- **后端任务系统**：任务表当前隐含"去雾"语义，需新增任务类型字段使任务系统与具体算法解耦。改动范围仅限任务创建和分发逻辑，不涉及核心业务流程重构。
- **前端页面**：「去雾处理」页面抽象为通用「图像处理」页面，通过任务类型参数区分不同处理场景（上传提示、参数配置、效果评估指标各自独立配置）。新增任务类型时前端只需新增一份配置，无需改动核心处理流程。

### 3.3 扩展前提条件

**必须先完成**：
1. 去雾核心体验补全（处理历史、进度反馈、用户评分）
2. VIP 体系后端实现（会员/套餐/订单管理模块）
3. Go 后端稳定承接基础 CRUD，任务类型字段改造完成

贸然扩展而核心体验不完善，只会让每个功能都做得半生不熟。

### 3.4 分阶段扩展路径

**阶段一（当前 → 近期）：做深去雾**，目标是去雾体验达到生产级别。补齐处理历史、进度反馈、用户评分；完善 VIP 体系；Go 后端接管基础 CRUD，Python 服务瘦身为纯算法微服务。

**阶段二（近期 → 中期）：横向扩展同类退化**，目标是覆盖更广泛的图像增强场景。增加去雨、去雪、低光增强；算法管理框架新增任务类型维度；产品名可调整为「图像增强系统」。

**阶段三（中期）：AI 图像处理平台**，目标是具备平台规模效应。增加超分辨率、去噪、图像修复；引入模型市场，支持第三方算法接入；OpenAPI 对外开放，自动生成多端 SDK。

## 4. 爬虫数据集功能

### 4.1 可行性结论

**建议实现，但需严格合规管控，优先对接授权数据源。**

| 维度 | 评估 |
|------|------|
| **技术可行性** | 高。Python 端已有图像处理能力，爬虫框架（Scrapy/Playwright）成熟 |
| **业务价值** | 高。自动扩充训练数据集，降低人工标注成本 |
| **合规风险** | 中高。需遵守 robots.txt、版权法、数据隐私法规 |
| **与现有架构契合度** | 高。可复用数据集管理模块、文件管理模块、任务队列 |

### 4.2 数据源分级与选择策略

按合规风险从低到高分为三级，优先实现低风险数据源：

#### Tier 1：官方 API / 授权数据集（优先实现，零法律风险）

| 数据源 | 获取方式 | 图片规模 | 适用场景 |
|--------|---------|---------|--------|
| **Unsplash API** | 官方免费 API，CC0 协议 | 300万+ | 自然风景、城市场景 |
| **Flickr API** | 官方 API，可过滤 CC 授权 | 亿级 | 多样化场景，含雾霾图 |
| **Wikimedia Commons** | MediaWiki API | 千万级 | 地理、自然场景 |
| **RESIDE 数据集** | 学术直链下载 | 13990张 | 去雾标准 benchmark |
| **O-HAZE / Dense-Haze** | 学术直链下载 | 百级 | 真实雾图 benchmark |
| **COCO / ImageNet 子集** | 官方下载 | 百万级 | 清晰图底图，用于合成雾图 |

**实现方式**：调用官方 API，无需爬虫，直接 HTTP 请求 + 分页拉取，接入现有任务队列异步执行。

#### Tier 2：遵守 robots.txt 的受控爬取（谨慎实现，需人工审核）

| 数据源 | 说明 | 风险点 |
|--------|------|-------|
| **500px 公开图库** | 允许非商业爬取，需遵守 ToS | 商业使用需授权 |
| **Pixabay** | 有官方 API，但爬取违反 ToS | 优先用官方 API |
| **气象局/环保局公开图片** | 政府数据，通常可公开使用 | 需确认具体条款 |

**实现方式**：Scrapy + 速率限制（≤1 req/s），严格遵守 robots.txt，爬取前人工确认目标站点条款。

#### Tier 3：通用网页爬取（不建议，仅研究用途）

百度图片、Google 图片等搜索引擎图片，版权归属复杂，**不应用于训练数据集**，尤其是商业化场景。

### 4.3 实现可行性判断

**结论：技术上完全可行，且与现有系统高度契合，无需新建独立子系统。**

爬取任务可直接接入现有任务管理模块，复用异步执行、进度追踪、失败重试等已有能力。爬取结果经图片质量过滤（格式校验、分辨率筛选、模糊度检测、感知哈希去重）后，写入现有数据集管理模块，通过来源类型字段区分人工上传、API 拉取、爬虫采集和合成数据。数据库层面仅需在现有图片表上扩展若干来源追踪字段（原始 URL、授权协议、采集任务关联），改动量极小。

**合成数据增强的优先级高于爬虫**：利用大气散射物理模型，可对任意清晰图片自动合成不同浓度的雾图，清晰图与雾图天然配对，可直接用于有监督训练，无需人工标注，且完全自主可控。这是成本最低、质量最可控的数据扩充方式，应作为数据集建设的首选路径，爬虫采集作为补充。

### 4.4 主要风险与边界

爬虫功能面临的核心挑战不是技术问题，而是**反爬机制决定了数据源的实际可用范围**。

常见的反爬手段（频率限制、UA 检测、动态渲染、图片懒加载）均有对应的技术应对方案，实现成本可接受。但**验证码和人机验证（Cloudflare、reCAPTCHA 等）是硬性障碍**，在合规前提下无法自动化绕过。这意味着 Getty Images、Shutterstock 等主流商业图库实际上无法爬取，爬虫的可用范围被限定在未部署强反爬机制的站点。

此外，爬取图片可能含有水印，会影响训练数据质量，需在入库前进行检测过滤。

**综合判断**：爬虫是有价值的补充手段，但不应作为数据集建设的主要依赖。Tier 1 官方 API 数据源（Unsplash、Flickr、学术数据集）+ 合成数据增强，才是可持续、可控、合规的数据积累路径。

### 4.5 与现有系统的集成方式

- **爬取任务**接入现有任务管理模块，复用异步执行、进度追踪、失败重试能力，无需新建任务系统
- **爬取结果**经预处理 Pipeline 后写入现有数据集管理模块，`source_type=crawl` 区分来源
- **管理端**新增「数据采集」页面，支持配置数据源类型（API/爬虫）、关键词、数量上限、目标数据集
- **白名单机制**：管理员维护允许爬取的域名白名单，爬虫 Worker 启动前校验目标域名，不在白名单内拒绝执行
- **合规审计**：每条爬取记录保留完整的 `source_url` + `license`，支持后续合规审查和数据溯源

## 5. 风险汇总

| 风险 | 等级 | 应对措施 |
|------|------|---------|
| SDK 强耦合：dehaze-sdk-js breaking change 连锁影响所有 JS 端 | 中 | 严格语义化版本 + changelog，主端迁移前充分测试 |
| Python 服务瘦身期间业务中断 | 高 | 灰度迁移，Go 端先并行承接，验证稳定后再下线 Python CRUD |
| Flutter 端从骨架补齐工作量大 | 中 | 参考 Vue 端页面结构 + Android 端 MVVM 架构，复用 SDK |
| 平台扩展后 GPU 资源压力倍增 | 中 | 完善资源调度，多模型按需加载，避免常驻显存 |
| 爬虫功能版权合规风险 | 中高 | 仅爬取明确授权或 CC 协议数据源，保留完整来源记录 |
| 展示型到生产型过渡：半成品端维护成本高 | 中 | 明确各端 Tier 分级，Tier 3 端要么补齐要么果断归档 |
