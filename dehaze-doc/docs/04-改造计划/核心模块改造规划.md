# 核心模块改造规划

## 1. 模块概况与定位分析

核心模块共 6 个，按职责可分为三层：

| 层级 | 模块 | 定位 | 主要技术栈 |
|------|------|------|-----------|
| **基础设施层** | 数据集管理 | 训练/测试数据集的全生命周期管理 | Java 后端为主 |
| **基础设施层** | 算法管理 | 算法模型的注册、版本控制、审核发布 | Java 后端为主 |
| **业务核心层** | 去雾处理 | 调用 Python 算法服务执行去雾推理 | Python 端为主，Java 仅做任务编排 |
| **前端交互层** | 图像输入 | 图片上传、预览、格式校验 | 前端为主，后端为文件存储 |
| **前端交互层** | 算法选择 | 算法浏览、推荐、筛选 | 前端为主，后端为只读查询 |
| **前端交互层** | 效果对比 | 去雾前后对比展示、评估指标可视化 | 前端为主，后端为只读查询 |

---

## 2. 改造优先级与排序

### 2.1 排序依据

- **基础设施层优先**：其他模块依赖其数据（算法列表、数据集列表），必须先稳定
- **Python 端独立迭代**：去雾处理核心算法已集成在 Python 端，Java 侧仅做轻量编排，改造范围有限
- **前端交互层后置**：图像输入/算法选择/效果对比偏前端展示，后端逻辑薄，可与前端开发并行推进

### 2.2 改造阶段

```
阶段一（已完成）              阶段二（当前）               阶段三
┌──────────────────┐    ┌──────────────────┐    ┌──────────────────┐
│  数据集管理       │    │  去雾处理         │    │  图像输入         │
│  算法管理         │    │                  │    │  算法选择         │
│  (后端架构重构)    │    │  (后端轻量改造)    │    │  效果对比         │
└──────────────────┘    └──────────────────┘    │  (前端为主)       │
                                                └──────────────────┘
```

## 3. 各模块改造要点

### 3.1 数据集管理 ✅ 已完成

**改造内容**：后端实现架构重构

- 文件存储委托给文件管理模块（FileService / PathBuilder）
- 批量导出/导入走任务管理模块策略模式
- 消除与基础模块的功能重复

### 3.2 算法管理 ✅ 已完成

**改造内容**：后端实现架构重构

- 模型文件存储委托给文件管理模块
- 批量导出走任务管理模块的 AlgorithmExportStrategy
- 保留算法特有领域逻辑：状态机、版本控制、审核机制、Python 服务集成

### 3.3 去雾处理 🔜 阶段二

**模块特点**：核心计算在 Python 端完成（模型加载、推理、后处理），Java 端职责为任务编排和状态管理。

**后端改造范围**（Java 侧）：

| 改造项 | 说明 | 优先级 |
|--------|------|--------|
| 任务调度复用 | 单张/批量处理任务接入任务管理模块，复用队列、重试、进度回调机制 | P0 |
| 结果文件存储 | 处理结果图存储委托给文件管理模块 | P0 |
| WebSocket 进度推送 | 评估是否复用任务管理模块的进度通知通道，避免重复建设 | P1 |
| VIP 权益校验 | 处理次数限额、优先级队列，属于去雾模块特有业务逻辑，保留独立实现 | P1 |

**不涉及改造的部分**：

- Python 端推理引擎、模型加载、GPU 调度 → 由 Python 端独立迭代
- 算法参数调节逻辑 → 前端 + Python 端协作，Java 仅透传
- 断点续传 → 依赖 Python 端的 checkpoint 机制

### 3.4 图像输入 🔜 阶段三

**模块特点**：后端逻辑极薄，核心是文件上传 + 格式校验。

**后端改造范围**：

| 改造项 | 说明 | 优先级 |
|--------|------|--------|
| 文件上传 | 直接复用文件管理模块，无需独立上传接口 | P0 |
| 图片校验 | 格式/尺寸/大小校验可抽取为文件管理模块的校验策略 | P1 |

**主要工作量在前端**：拍照/相册选择、裁剪预览、拖拽上传等交互逻辑。

### 3.5 算法选择 🔜 阶段三

**模块特点**：后端为只读查询，数据来源于算法管理模块。

**后端改造范围**：

| 改造项 | 说明 | 优先级 |
|--------|------|--------|
| 算法列表/树形查询 | 直接调用算法管理模块的 Service，无需重复建表 | P0 |
| 智能推荐 | 图像特征分析在 Python 端完成，Java 仅做结果聚合和缓存 | P1 |

**主要工作量在前端**：树形展示、卡片交互、对比面板、收藏管理等 UI 逻辑。

### 3.6 效果对比 🔜 阶段三

**模块特点**：后端为只读查询，数据来源于去雾处理的预测日志和评估日志。

**后端改造范围**：

| 改造项 | 说明 | 优先级 |
|--------|------|--------|
| 对比数据查询 | 从 sys_pred_log / sys_eval_log 读取，可由去雾处理模块统一提供 | P0 |
| 评估指标计算 | PSNR/SSIM 等指标由 Python 端计算，Java 仅存储和展示 | - |

**主要工作量在前端**：滑动对比、并排展示、指标雷达图、历史趋势图等可视化。

## 4. 改造收益与风险

### 4.1 预期收益

| 收益项 | 说明 |
|--------|------|
| 减少重复代码 | 文件存储、任务调度统一委托基础模块，预计减少 30%+ 重复逻辑 |
| 降低维护成本 | 修改文件策略或任务机制时只需改一处 |
| 接口一致性 | 所有模块的文件操作、任务操作走统一 API |
| 前后端解耦 | 明确前端交互层模块的后端仅为薄查询层，避免过度设计 |

### 4.2 风险项

| 风险 | 应对措施 |
|------|---------|
| 基础模块成为单点瓶颈 | 文件管理/任务管理模块需要充分的性能测试和容错设计 |
| Python-Java 通信可靠性 | 保留熔断降级机制，Python 端故障不应阻塞 Java 端 |
| 前端交互层改造范围蔓延 | 严格控制后端改造边界，UI 交互变更不触发后端重构 |
