# 分布式锁完整替换方案

统一使用 `redsync`

> 当前状态（2026-07-12 核对）：**方案尚未实施**。
> - `dehaze-go/pkg/cache/types/types.go` 的 `ICache` 接口仍保留 `Lock/Unlock` 方法
> - `dehaze-go/pkg/cache/redis/impl.go` 仍使用 `SetNX` + Lua 脚本（`unlockScript`）实现锁，未引入 `redsync`
> - `go.mod` 未依赖 `go-redsync/redsync/v4`
>
> 本方案的所有步骤仍然适用，可作为下一次基础设施迭代的直接执行清单。

以下方案确保**项目内只有一套锁逻辑**，彻底移除旧的 `SetNX/Del` 式锁实现与调用路径。

### 方案目标
- **锁能力唯一入口**：所有分布式锁都通过 `redsync` 获取与释放  
- **消除共存风险**：移除旧 `Lock/Unlock` 实现与使用点  
- **兼容单机与未来集群**：Redis 客户端统一为 `UniversalClient`

### 具体改造步骤（完整替换）

#### **步骤 1：统一 Redis 客户端（为集群铺路）**
- `InitRedis` 支持 **单机/集群** 两种模式  
- `GetClient` 返回 `UniversalClient`  
- 所有使用 `GetClient` 的地方（如限流中间件、健康检查）同步调整

#### **步骤 2：新增 `redsync` 统一入口**
- 在 `pkg/cache/redis` 增加 `GetRedsync()`  
- 提供 `NewMutex(name, opts...)`，由配置给出默认值  
- 业务侧**禁止直接 new redsync**

#### **步骤 3：配置扩展（锁配置明确化）**
- `cache.redis.lock` 增加默认配置：
  - `expirySeconds`
  - `tries`
  - `retryDelayMillis`

#### **步骤 4：删除旧锁实现**
- 移除 `RedisCache.Lock/Unlock` 的旧逻辑  
- `types.ICache` 中删除 `Lock/Unlock` 接口  
- 更新所有实现（本地缓存、多级缓存）  

> 这样可以从编译期强制禁止旧锁调用

#### **步骤 5：替换所有锁使用点**
- 搜索并替换所有 `Lock/Unlock/SetNX` 的锁用途  
- 统一为 `redsync.NewMutex`  
- 例如清理任务、反重入、幂等控制、任务互斥等

#### **步骤 6：统一锁规范**
- 统一锁 key 前缀规范（例如 `lock:job:cleanup`）  
- 统一超时策略（按任务耗时设置 TTL）  
- 锁失败时**记录日志并跳过执行**（避免资源争用）

#### **步骤 7：依赖与校验**
- 加入 `go-redsync/redsync/v4` 与适配包  
- 编译验证，修复编译与 lint 问题  

### 方案结果
- **锁逻辑完全统一**  
- **不再存在两套锁实现**  
- **未来上集群无需二次设计**  
- **所有锁行为可被集中治理**
