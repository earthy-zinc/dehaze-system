# dehaze-go 架构改造方案

**版本**：v2.0  
**日期**：2026-01-20

---

## 1. 问题诊断

### 1.1 当前架构问题

当前项目存在两个核心架构问题，需要同步改造：

**问题一：缺少 Repository 层**

Service 层直接调用 `global.DB` 操作 GORM，导致数据访问逻辑与业务逻辑混杂。

| 问题                     | 影响                               | 严重程度 |
| ------------------------ | ---------------------------------- | -------- |
| Service 承担数据访问职责 | 违反单一职责原则，代码臃肿         | 🔴 高    |
| GORM 调用散落各处        | 难以统一修改查询逻辑，如软删除条件 | 🔴 高    |
| 无法复用数据访问逻辑     | 相同查询在多个 Service 中重复实现  | 🟡 中    |
| 难以替换 ORM             | 切换 ORM 需修改所有 Service        | 🔴 高    |

**问题二：全局变量依赖**

所有层直接依赖 `global` 包中的全局变量（`DB`、`REDIS`、`LOG`），导致高耦合。

| 问题               | 影响                                   | 严重程度 |
| ------------------ | -------------------------------------- | -------- |
| 无法 Mock 依赖     | 单元测试只能做集成测试，测试慢、不稳定 | 🔴 高    |
| Service 无接口抽象 | API 层紧耦合 Service 实现，无法替换    | 🔴 高    |
| 函数签名隐藏依赖   | 代码可读性差，调试困难                 | 🟡 中    |
| 难以替换基础设施   | 换 Redis 实现需改所有 Service          | 🔴 高    |

### 1.2 问题代码特征

**当前 Service 层典型代码**：

- 空结构体，无任何依赖字段声明
- 直接使用 `global.DB` 调用 GORM，SQL 逻辑与业务逻辑混杂
- 直接使用 `global.REDIS`，缓存操作散落在业务方法中
- 无法通过构造函数注入依赖，无法进行单元测试

**当前 API 层典型代码**：

- 使用包级变量静态绑定 Service 实例
- 依赖值类型而非接口类型

## 2. 改造目标

### 2.1 目标架构

改造后采用**四层架构**：API → Service → Repository → Infrastructure。

```
┌─────────────────────────────────────────────────────────────────┐
│                         API Layer                               │
│   依赖 IUserService、IRoleService 等服务接口                     │
│   职责：请求解析、参数验证、响应封装                              │
└───────────────────────────┬─────────────────────────────────────┘
                            │ 依赖接口
┌───────────────────────────▼─────────────────────────────────────┐
│                       Service Layer                             │
│   依赖 IUserRepository、ICacheService 等仓储/缓存接口            │
│   职责：业务逻辑、事务管理、缓存策略、业务规则校验                 │
└───────────────────────────┬─────────────────────────────────────┘
                            │ 依赖接口
┌───────────────────────────▼─────────────────────────────────────┐
│                     Repository Layer (新增)                     │
│   依赖 *gorm.DB                                                 │
│   职责：数据访问抽象、CRUD 封装、查询构建、软删除处理             │
└───────────────────────────┬─────────────────────────────────────┘
                            │ 依赖具体实现
┌───────────────────────────▼─────────────────────────────────────┐
│                     Infrastructure Layer                        │
│   *gorm.DB    redis.Client    *zap.Logger                       │
│   职责：基础设施连接、配置管理                                    │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 设计原则

- **上层依赖下层接口**：不依赖具体实现，便于替换和 Mock
- **Repository 封装数据访问**：Service 不直接操作 GORM，通过 Repository 接口访问数据
- **依赖注入**：通过构造函数显式声明和注入依赖
- **依赖容器统一组装**：所有依赖关系在 `Container` 中集中管理

### 2.3 改造收益

| 收益             | 说明                                          |
| ---------------- | --------------------------------------------- |
| **可测试性提升** | Service 可通过 Mock Repository 进行纯单元测试 |
| **职责分离**     | Service 专注业务逻辑，Repository 专注数据访问 |
| **代码复用**     | Repository 方法可被多个 Service 复用          |
| **易于维护**     | 修改查询逻辑只需改 Repository，不影响 Service |
| **可替换性**     | 更换 ORM 只需修改 Repository 实现             |

## 4. 改造策略

### 4.1 改造原则

1. **直接废弃和删除旧代码**：不保留兼容构造函数，全量切换到新架构
2. **接口驱动**：先定义 Repository/Service 接口，再实现具体类
3. **自下而上**：先改造 Repository 层，再改造 Service 层，最后改造 API 层
4. **测试先行**：采用 DDD 测试驱动开发，写完业务代码立即撰写单元测试

### 4.2 改造步骤

**Phase 1：Repository 层（Week 1-2）**

创建 Repository 层，封装所有 GORM 操作：

1. 定义 Repository 接口（`internal/repository/interfaces.go`）
2. 实现各实体的 Repository（user_repo、role_repo 等）
3. 统一处理软删除、分页、排序等通用逻辑

**Phase 2：Cache 层（Week 2）**

创建缓存抽象层：

1. 定义缓存接口（`internal/cache/interfaces.go`）
2. 实现 Redis 缓存（生产用）和内存缓存（测试用）

**Phase 3：Service 层改造（Week 3-4）**

重构 Service 层，注入 Repository 和 Cache 依赖：

1. 定义 Service 接口（`service/interfaces.go`）
2. 改造 Service 结构体，声明依赖字段
3. 创建依赖注入构造函数
4. 修改业务方法，使用 Repository 替代 `global.DB`
5. **删除旧的空结构体和全局变量调用代码**

**Phase 4：API 层改造（Week 5-6）**

重构 API 层，注入 Service 依赖：

1. 改造 API 结构体，依赖 Service 接口
2. 创建依赖注入构造函数
3. 修改 router 初始化，使用 Container 获取 API 实例

**Phase 5：清理与验收（Week 7-8）**

1. **删除 `global` 包中的 DB/REDIS/LOG 全局变量**
2. 更新 `main.go`，使用 Container 启动应用
3. 补充单元测试，确保核心功能覆盖率 80%+
4. 运行全量测试，确保无回归

### 4.3 改造对现有功能的影响

| 影响范围          | 改造内容                    | 风险控制                        |
| ----------------- | --------------------------- | ------------------------------- |
| **Repository 层** | 新增，封装所有 GORM 操作    | 新增文件，不影响现有代码        |
| **Service 层**    | 所有 Service 重构为依赖注入 | 逐个模块改造，每个模块独立测试  |
| **API 层**        | 所有 API 重构为依赖注入     | 与 Service 同步改造             |
| **Router**        | 初始化方式变更              | 使用 Container 统一管理         |
| **测试**          | 测试基类重构                | 提供 MockRepository/MockService |
| **全局变量**      | DB/REDIS/LOG 废弃           | 保留 CONFIG 用于配置读取        |

## 5. 接口设计

### 5.1 Repository 接口

定义数据访问契约，隔离 GORM 细节：

- 每个实体对应一个 Repository 接口
- 方法签名使用 `context.Context` 作为第一个参数
- 查询方法返回指针或切片，未找到记录返回 `nil` 而非 error
- 写入方法返回 `error`
- 统一处理软删除条件（`deleted = 0`）

**典型接口**：

```go
type IUserRepository interface {
    FindByID(ctx context.Context, id int64) (*model.SysUser, error)
    FindByUsername(ctx context.Context, username string) (*model.SysUser, error)
    List(ctx context.Context, query *UserQuery) ([]*model.SysUser, int64, error)
    Create(ctx context.Context, user *model.SysUser) error
    Update(ctx context.Context, user *model.SysUser) error
    Delete(ctx context.Context, id int64) error
}
```

### 5.2 Cache 接口

定义缓存操作契约，支持多种后端实现：

- 统一的缓存操作契约
- 键不存在时返回空字符串而非 error
- 支持 TTL、批量操作、分布式锁

### 5.3 Service 接口

定义业务服务契约，供 API 层依赖：

- 方法命名体现业务语义，而非 CRUD
- 返回 VO/BO 而非实体
- 便于 Mock 测试

## 6. 代码示例

### 6.1 Repository 实现

```go
// internal/repository/user_repo.go
type userRepository struct {
    db *gorm.DB
}

func NewUserRepository(db *gorm.DB) IUserRepository {
    return &userRepository{db: db}
}

func (r *userRepository) FindByID(ctx context.Context, id int64) (*model.SysUser, error) {
    var user model.SysUser
    err := r.db.WithContext(ctx).Where("id = ? AND deleted = 0", id).First(&user).Error
    if errors.Is(err, gorm.ErrRecordNotFound) {
        return nil, nil
    }
    return &user, err
}
```

### 6.2 Service 改造

**改造前**（将废弃）：

```go
type UserService struct{}  // 空结构体

func (s *UserService) Login(u *model.SysUser) (*model.UserAuthInfo, error) {
    err := global.DB.Where("username = ?", u.Username).First(u).Error  // ❌ 直接依赖全局变量
}
```

**改造后**：

```go
type UserService struct {
    userRepo repository.IUserRepository
    roleRepo repository.IRoleRepository
    cache    cache.ICacheService
    logger   *zap.Logger
}

func NewUserService(userRepo repository.IUserRepository, ...) *UserService {
    return &UserService{userRepo: userRepo, ...}
}

func (s *UserService) Login(ctx context.Context, username, password string) (*model.UserAuthInfo, error) {
    user, err := s.userRepo.FindByUsername(ctx, username)  // ✅ 使用注入的 Repository
}
```

### 6.3 依赖容器

```go
// internal/container/container.go
func NewContainer(db *gorm.DB, redis redis.UniversalClient, logger *zap.Logger) *Container {
    c := &Container{DB: db, Redis: redis, Logger: logger}

    // Repository
    c.UserRepo = repository.NewUserRepository(db)
    c.RoleRepo = repository.NewRoleRepository(db)
    c.CacheService = cache.NewRedisCache(redis)

    // Service（注入 Repository）
    c.UserService = service.NewUserService(c.UserRepo, c.RoleRepo, c.CacheService, logger)
    c.RoleService = service.NewRoleService(c.RoleRepo, c.CacheService, logger)

    // API（注入 Service）
    c.UserApi = api.NewSysUserApi(c.UserService)
    c.RoleApi = api.NewSysRoleApi(c.RoleService)

    return c
}
```
