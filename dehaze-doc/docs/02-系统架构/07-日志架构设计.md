# 日志架构设计

## 1. 文档概述

### 1.1 文档目的

定义图像去雾系统三端后端（Java / Go / Python）统一的日志设计规范，覆盖日志存储与切割、字段 schema、请求上下文注入机制、日志分类与内容要求、禁止事项；同时记录前端日志（client）的接收链路与字段规范要点，使任意一条日志都能按 `trace_id` 关联到具体请求、按 `method/path` 定位到接口、按结构化字段检索，并支持前后端端到端串联。

### 1.2 适用范围

适用于三端后端所有日志输出 + 前端日志（通过后端接收 API 落盘后进入同一 ELK 链路）。本文档为日志设计的**单一信息源**（存储、字段、注入、分类、保留、前端日志接收链路与字段契约）。日志的**采集链路**（Filebeat → Logstash → ES → Kibana）属部署/监控设施，见 [`06-部署架构.md §7.1`](./06-部署架构.md#71-监控体系)；前端日志接收链路与字段规范见本文档 [§3.5](#35-前端日志client)，前端 SDK 日志模块的实现设计见 [04-项目实现/前端/sdk架构文档.md](../04-项目实现/前端/sdk架构文档.md)。

### 1.3 设计目标

| 目标 | 含义 |
|------|------|
| **可追踪** | 每条日志带 `trace_id`，能沿调用链关联同一请求的全部日志 |
| **可定位** | 每条日志带 `method/path`，无需翻堆栈即可知道来自哪个接口 |
| **可检索** | 状态码/耗时/错误码等机器可读信息为独立 JSON 字段，可字段级过滤 |
| **三端一致** | Java/Go/Python 字段名、注入机制、分类规则完全对齐 |

## 2. 日志存储与切割

### 2.1 存放目录结构

三端后端统一采用按日期分目录 + 按级别分文件 + 按大小分片的存放结构：

```
{项目根}/logs/{yyyy-MM-dd}/{级别}.log        # 当前活动文件
{项目根}/logs/{yyyy-MM-dd}/{级别}.{n}.log    # 超 100MB 后的历史分片（序号递增）
```

| 服务 | 目录示例 |
|------|---------|
| dehaze-go | `dehaze-go/logs/2026-07-29/info.log` |
| dehaze-java | `dehaze-java/logs/2026-07-29/info.log` |
| dehaze-python | `dehaze-python/logs/2026-07-29/info.log` |

服务名靠项目根目录天然区分，日期靠目录层级，文件名只需级别，零冗余。当前活动日志始终写入 `{级别}.log`，单文件超过 100MB 后归档为 `{级别}.{n}.log`（序号递增）并开新活动文件，保证活动文件可被编辑器快速打开。

### 2.2 日志文件级别

| 文件 | 级别范围 | 用途 |
|------|---------|------|
| `info.log` | INFO 及以上（含 WARN/ERROR） | 主日志，JSON 结构化，供 ELK/Loki 采集 |
| `error.log` | 仅 ERROR | 快速排障/告警源（是 info 的子集，ERROR 同时写两份） |
| `console.log` | 控制台输出 | `scripts/run.py` 重定向的启动/控制台日志（追加模式） |

DEBUG 级别不落盘，仅可输出到控制台。

### 2.3 切割与清理

| 维度 | 标准 | 实现 |
|------|------|------|
| 按日期切割 | 每天 00:00 切到新日期目录 | Go `Cutter`、Java `SizeAndTimeBasedRollingPolicy`、Python `DailyDirectoryFileHandler` |
| 按大小切割 | 单文件 100MB，超限归档为 `{级别}.{n}.log` 并开新活动文件 | Go `CutterWithMaxSize`、Java `maxFileSize`、Python `LOG_MAX_BYTES` |
| 保留周期 | 30 天 | 超期日期目录自动清理 |
| 总量上限 | 单服务 5GB | Java `totalSizeCap`；Go/Python 按日期目录清理兜底 |
| dev 启动归档 | 重启时归档当天已存在的活动文件，本次启动写入全新文件 | Go `archive-on-startup`、Java `SystemApplication`、Python `LOG_ARCHIVE_ON_STARTUP`（仅 dev，prod 保持 append 以保留连续日志） |

### 2.4 保留策略

| 日志类型 | 保留周期 |
|---------|---------|
| 应用日志 | 30 天 |
| 访问日志 | 90 天 |
| 错误日志 | 180 天 |
| 审计日志 | 1 年 |

## 3. JSON 字段规范

所有文件日志为 NDJSON（每行一个 JSON 对象）。字段分三组：

### 3.1 基础字段（所有日志，由格式化器注入）

| 字段 | 类型 | 说明 |
|------|------|------|
| `timestamp` | string | ISO8601 UTC 时间戳 |
| `level` | string | INFO / WARNING / ERROR 等 |
| `logger` | string | logger 名称（模块路径） |
| `service` | string | 服务名（如 `Dehaze API`） |
| `thread` | string/int | 线程/协程标识 |
| `message` | string | 人读描述，仅放业务语义，**不放机器可读键值** |

### 3.2 请求上下文字段（请求期间所有日志，自动注入）

| 字段 | 类型 | 出现条件 | 说明 |
|------|------|---------|------|
| `trace_id` | string | 请求期日志 | 请求追踪 ID |
| `method` | string | 请求期日志（非空时） | HTTP 方法 |
| `path` | string | 请求期日志（非空时） | 请求路径（不含 query） |
| `ip` | string | 请求期日志（非空时） | 客户端 IP（优先 `X-Forwarded-For` 首段，适配反代） |
| `user_agent` | string | 请求期日志（非空时） | 客户端 User-Agent |
| `user_id` | int | 认证完成后日志 | 当前用户 ID（认证层写入 `_current_user_id`，匿名/未认证不注入） |

> 启动日志、后台任务等非请求上下文中 `method/path/ip/user_agent` 为空则不注入；`trace_id` 始终注入（可为空串）。
> `user_id` 仅在认证完成后可见：业务/异常日志（认证后）带 `user_id`；访问日志在认证之外执行，`user_id` 可能为空，需经 `trace_id` 关联到同请求的异常日志获取操作者。

### 3.3 场景字段（按日志类型由调用点经 `extra`/结构化参数提供）

| 字段 | 类型 | 出现于 | 说明 |
|------|------|-------|------|
| `status` | int | 访问日志、异常日志 | HTTP 响应状态码 |
| `duration_ms` | float | 访问日志、SQL 审计日志 | 请求/SQL 执行耗时（毫秒） |
| `query` | string | 访问日志（有查询串时） | URL query string |
| `code` | string | 异常日志 | 业务错误码（如 `A0401`） |
| `exc_info` | string | DB/通用异常日志 | 完整 traceback 字符串 |
| `sql` | string | SQL 审计日志 | SQL 语句（占位符形式，不含参数值，避免泄露 PII/密钥） |
| `rows` | int | SQL 审计日志 | 影响/返回行数；`-1` 表示未知（如 SELECT） |
| `threshold_ms` | float | SLOW_SQL（WARN） | 慢查询阈值（毫秒） |

### 3.4 字段样例

```json
// 访问日志（info.log）
{"message":"ACCESS","status":200,"duration_ms":12.3,"query":"pageNum=1",
 "trace_id":"22f785c...","method":"GET","path":"/api/v1/evaluation/logs","ip":"203.0.113.7","user_agent":"Mozilla/5.0",
 "timestamp":"2026-08-01T04:01:50.999305+00:00","level":"INFO","logger":"app.request","service":"Dehaze API"}

// 业务异常（error.log，含操作者）
{"message":"业务异常: 图片下载失败 (403): http://...","code":"A0401","status":400,
 "trace_id":"22f785c...","method":"POST","path":"/api/v1/prediction","ip":"203.0.113.7","user_agent":"dehaze-sdk-js/1.0","user_id":42,
 "timestamp":"...","level":"ERROR","logger":"app.core.exceptions","service":"Dehaze API"}

// 数据库异常（error.log，含堆栈与操作者）
{"message":"数据库异常: No row was found when one was required","code":"B0xxx","status":500,
 "exc_info":"Traceback (most recent call last):\n  File .../app/router/file.py, line 65 ...",
 "trace_id":"110172...","method":"POST","path":"/api/v1/file/upload","ip":"203.0.113.7","user_agent":"curl/8.0","user_id":5,
 "timestamp":"...","level":"ERROR","logger":"app.core.exceptions","service":"Dehaze API"}

// SQL 审计日志（info.log，logger 固定为 sql）
{"message":"SQL","sql":"SELECT id, name FROM sys_user WHERE id = ?","duration_ms":1.23,"rows":1,
 "trace_id":"110172...","method":"POST","path":"/api/v1/file/upload","ip":"203.0.113.7","user_agent":"curl/8.0","user_id":5,
 "timestamp":"...","level":"INFO","logger":"sql","service":"Dehaze API"}

// 慢查询（info.log + error.log，WARN）
{"message":"SLOW_SQL","sql":"SELECT ... FROM prediction_result WHERE ...","duration_ms":320.5,"rows":1000,"threshold_ms":500,
 "trace_id":"110172...","method":"GET","path":"/api/v1/prediction/results",
 "timestamp":"...","level":"WARN","logger":"sql","service":"Dehaze API"}

// SQL 执行错误（info.log + error.log，ERROR）
{"message":"SQL_ERROR","sql":"UPDATE sys_user SET ...","duration_ms":50.2,
 "error":"Deadlock found when trying to get lock; try restarting transaction",
 "trace_id":"110172...","method":"POST","path":"/api/v1/user/update",
 "timestamp":"...","level":"ERROR","logger":"sql","service":"Dehaze API"}
```

## 3.5 前端日志（client）

前端（Web / 移动端）日志通过 SDK 采集，经后端接收 API 落盘后进入同一 ELK 链路，与后端日志共享 filebeat → logstash → ES 基础设施，通过 `trace_id` 实现端到端串联。本节记录接收链路、字段规范、采样限流等**架构契约**；SDK 侧 Logger 模块的 transport 架构与对外 API 实现见 [04-项目实现/前端/sdk架构文档.md](../04-项目实现/前端/sdk架构文档.md)。

### 3.5.1 接收链路

```
前端 SDK Logger
  └─ 批量上报 POST /api/v1/logs/client
        └─ 后端接收（三端同步实现，复用现有限流 + 鉴权）
              └─ NDJSON 写入 logs/{yyyy-MM-dd}/client.log
                    └─ Filebeat filestream input（fields.service: client）
                          └─ Logstash 按 fields.service 分流
                                ├─ service=client → dehaze-client-logs-{yyyy.MM.dd}
                                └─ service=java/python/go → dehaze-logs-{yyyy.MM.dd}
                                      └─ Kibana 检索
```

**关键约束**：
- 接收 API：`POST /api/v1/logs/client`，匿名也允许上报 ERROR（必须带 `trace_id`），已登录用户从会话解析 `user_id` 注入
- 限流：复用各端现有限流机制（Java `@RateLimit` / Python `RateLimitMiddleware` / Go `PathRateLimiter`），不新增限流组件
- 存储：`logs/{yyyy-MM-dd}/client.log`，NDJSON 格式，单文件 100MB 归档为 `client.{n}.log`，保留 30 天（与后端应用日志一致）

### 3.5.2 字段规范要点

前端日志字段 = 后端基础字段（§3.1）+ 前端上下文字段 + 场景字段：

| 字段组 | 字段 | 说明 |
|--------|------|------|
| 基础字段 | `timestamp` / `level` / `message` / `service` | `service` 固定为 `client`（filebeat 注入） |
| 前端上下文 | `app` / `app_version` / `url` / `user_agent` / `trace_id` / `user_id` | `app` 标识前端项目（react/vue/taro/uniapp/rn/flutter/android） |
| 错误场景 | `error_type` / `error_source` / `error_stack` | JS/Dart/Native 异常类型 + 捕获来源 + 完整堆栈 |
| API 场景 | `method` / `path` / `status` / `duration` / `code` | 与后端访问日志对齐 |
| 性能场景 | `metric_name` / `metric_value` / `navigation_type` / `resource_url` | Web Vitals（LCP/INP/CLS 等）+ 页面加载 + 长任务 + 资源错误 |

### 3.5.3 trace_id 端到端串联

```
前端 SDK 生成 trace_id（uuid hex 32 位无连字符）
  └─ 写入请求头 X-Trace-Id
        └─ 后端 TraceIdFilter 优先从上游请求头透传（§4.3 已有逻辑，无需改动）
              └─ 后端响应头回写 X-Trace-Id
                    └─ 前端响应拦截器读取并与本地 trace_id 对齐
                          └─ 写入日志条目 trace_id 字段 → 上报 ELK
                                └─ Kibana 中 trace_id:xxx 可同时检索前端报错日志 + 后端处理日志
```

### 3.5.4 采样与限流

| 级别 | 采样率 | 说明 |
|------|--------|------|
| `ERROR` | 100% | 全量上报 |
| `WARN` | 50% | 采样上报 |
| `INFO` | 0% | 不上报（本地 console 即可） |

单设备 60 秒内最多上报 20 条，超限丢弃；本地队列上限 100 条（Web）/ 500 条（移动端），超出丢弃最旧。

**ERROR 级别去重**：相同 `message + error_stack` fingerprint 在 10s 窗口内只记录一次（含 transports 输出、本地文件、ELK 上报三层），防止布局/渲染错误在每帧重绘时反复触发日志风暴（如 `RenderFlex overflowed` 在 layout 阶段 60fps 触发）。不同 trace_id / 不同 fingerprint 的错误不受影响。

## 4. 请求上下文自动注入机制

### 4.1 核心原则

`trace_id` / `method` / `path` / `ip` / `user_agent` 是**请求级常量**，必须在请求入口由中间件/拦截器一次性写入请求上下文，再由日志格式化器**自动注入**到该请求期间产生的每一条日志。`user_id` 是**认证后才有**的字段，由认证层（解析出用户的位置）写入请求上下文。业务代码与异常处理器**不得手动拼接**这些字段。

```
请求入口中间件
  └─ 写入请求上下文(trace_id, method, path, ip, user_agent)
        │
        └─ 认证层（SessionFilter/JWT 等）
              └─ 写入请求上下文(user_id)
                    │
                    └─ 请求期间任意 logger.xxx()
                          └─ 格式化器自动注入 trace_id / method / path / ip / user_agent / user_id
```

### 4.2 三端实现对照

| 端 | 请求上下文载体 | 入口设置点（trace_id/method/path/ip/user_agent） | 认证层注入点（user_id） | 格式化器注入点 |
|----|--------------|------------------------------------------------|----------------------|---------------|
| **Python** | `ContextVar` | `TraceMiddleware` 调 `set_request_context(ip=, user_agent=)` | `app.models.base._current_user_id` 由认证层 `set_current_user_id()` 写入 | `JsonFormatter.add_fields()` 自动读取所有 ContextVar |
| **Java** | SLF4J `MDC` | `TraceIdFilter` `MDC.put("ip")`/`MDC.put("user_agent")` | `SessionFilter` / `ApiKeyAuthenticationFilter` 解析出用户后 `MDC.put("user_id", ...)`，finally 清理 | Logback JSON 编码器通过 `includeMdcKeyName` 输出 MDC 为字段 |
| **Go** | `context.Context` 携带的请求上下文 | Gin `Trace()` 中间件注入 `trace.WithIP`/`trace.WithUserAgent` | `SessionAuth()` 中间件解析出 Session 后 `trace.WithUserID` 写入 | `logger.WithContext()` 从 context 读取 ip/user_agent/user_id 并追加到 logger |

> 三端必须保证：请求结束时清理上下文（Java `MDC.remove()`、Go context 不可变需逐层传递、Python ContextVar 随请求结束），避免线程/协程复用导致串号。

### 4.3 traceId 生成与透传

- 优先从上游请求头 `X-Trace-Id` / `X-Request-Id` 透传（Java 网关 → Python/Go 算法侧）。
- 无上游头时生成 `uuid hex`（32 位无连字符）。
- 响应头回写 `X-Trace-Id`，供前端/SDK 关联。
- **后台任务**（定时任务、异步导出/导入、MQ 消费）不在 HTTP 请求上下文内，必须在任务入口生成任务级 `trace_id` 并注入请求上下文，禁止后台任务日志 `trace_id` 为空。

## 5. 日志分类与内容规范

### 5.1 访问日志（ACCESS）

- **覆盖范围**：每个进入的 HTTP 请求打印一条 INFO 日志。
- **字段**：`status`、`duration_ms`、`query`（有则带）；`method/path/trace_id` 自动注入。
- **message**：固定 `ACCESS`，不再内联 method/path/status。
- **目的**：正常流量也留痕，事后可按 `trace_id` 反查整条请求轨迹。

### 5.2 异常日志

所有未捕获异常必须由全局异常处理器统一捕获并落日志，**禁止静默返回**。

| 异常类型 | message | 字段 | exc_info |
|---------|---------|------|----------|
| 业务异常（BusinessException） | `业务异常: {detail}` | `code`、`status` | 否 |
| 参数校验异常 | `参数校验失败: {detail}` | `code`、`status` | 否 |
| HTTP 异常 | `HTTP 异常: {detail}` | `code`、`status` | 否 |
| 数据库异常 | `数据库异常: {detail}` | `code`、`status` | **是** |
| 通用兜底异常 | `未处理异常: {detail}` | `code`、`status` | **是** |

- `code` 为业务错误码（独立字段，不内联到 message）。
- `exc_info` 为**字符串 traceback**（见 §6）。
- `method/path/trace_id` 自动注入，异常处理器无需手动拼接。

### 5.3 业务日志

- 关键业务操作（创建/更新/删除、外部调用、状态流转）应在 service 层输出 INFO/WARNING，不得只有异常才落日志。
- 外部调用（HTTP/SDK）失败需在抛出前显式记录一次，不能仅依赖重试分支的日志。

### 5.4 审计日志（请求/响应 body）

- **完整请求 body 与响应 data 不得写入文件日志**：涉及 PII、密钥、体积爆炸、二进制上传。
- 请求/响应 body 的审计由专用审计通道承接：
  - PG `sys_operation_log` 表（已设计 `body` / `resp` 列）。
  - MongoDB `audit_log` 集合（白名单驱动的业务操作审计），当前白名单覆盖以下核心 Service 方法：
    - 会员：`adjustLevel` / `adjustGrowth` / `deductQuota` / `updateStatus`
    - 订单：`create` / `cancel` / `applyRefund` / `approveRefund` / `rejectRefund`
    - 数据集：`batchDeleteDatasets` / `batchDeleteDatasetItemsCascadeWithResult`
    - 角色：`assignMenusToRole` / `updateRoleStatus` / `deleteRoles`
    - 用户：`updatePassword` / `deleteUsers`
- 文件日志只承载轻量结构化字段，body/data 审计走库表。

### 5.5 SQL 审计日志

- **覆盖范围**：每个经 ORM 执行的 SQL（`SELECT/INSERT/UPDATE/DELETE`）由拦截器统一记录，三端对齐。
- **`logger` 固定为 `sql`**，与业务日志区分，便于按字段过滤。
- **三种消息类型**：

  | message | level | 落盘 | 出现条件 |
  |---------|-------|------|---------|
  | `SQL` | INFO | `info.log` | 正常执行 |
  | `SLOW_SQL` | WARN | `info.log` + `error.log` | 执行耗时超过阈值（`threshold_ms`） |
  | `SQL_ERROR` | ERROR | `info.log` + `error.log` | SQL 执行失败 |

- **字段**：`sql`（语句，占位符形式）、`duration_ms`（耗时）、`rows`（影响/返回行数）；慢查询附加 `threshold_ms`；执行错误附加 `error`。
- **message 固定为类型名**，不内联 `sql=/rows=` 等键值（遵循 §7 第 7 条）。
- **安全**：SQL 以占位符形式记录（如 `WHERE id = ?`），**不含参数实际值**，避免 PII / 密码哈希等敏感数据泄露（与 §5.4 审计 body 的动机一致）。
- **请求上下文自动注入**：`trace_id`/`method`/`path`/`ip`/`user_agent`/`user_id` 由现有注入机制自动带出，SQL 日志可经 `trace_id` 关联到具体接口与操作者，无需手动拼接。
- **环境差异化**（通过配置控制级别，不另增日志文件）：

  | 环境 | 级别 | 输出内容 |
  |------|------|---------|
  | dev / test | INFO | 全量 SQL + 慢查询 + 错误 |
  | prod | WARN | 仅慢查询 + SQL 错误 |

  级别由各自框架的 SQL 日志开关控制：Python `SQL_LOG_LEVEL`、Go GORM `log-mode`、Java `dehaze.sql-log.level`。

- **三端实现对照**：

  | 端 | 实现机制 | 配置项 |
  |----|---------|--------|
  | Python | SQLAlchemy `before/after_cursor_execute` 事件监听器 → `logging.getLogger("sql")` | `SQL_LOG_LEVEL`、`SQL_SLOW_THRESHOLD_MS` |
  | Go | GORM `GormLogger.Trace()`，`logger.WithContext(ctx).Named("sql")` | `log-mode`（info/warn），按环境加载见 [Go 架构文档 §3.3](../04-项目实现/后端/02-Go架构文档.md) |
  | Java | MyBatis `StatementHandler` 拦截器（`SqlLogInterceptor`），`StructuredArguments` 输出字段 | `dehaze.sql-log.level`、`dehaze.sql-log.slow-threshold-ms` |

## 6. 堆栈（exc_info）规范

- `exc_info` 统一为**字符串形式**的完整 traceback，由 `exc_info=True`（或等价机制）自动渲染。
- **不采用数组/对象分帧形式**：字符串 traceback 是行业标准，ELK/Loki/Datadog 原生解析；数组化需自写解析且丢失链式异常叙事，属过度设计。
- 如需按异常类型过滤，可低成本增加 `exc_type`（`type(exc).__name__`）字段，而非重构堆栈结构。

---

## 7. 禁止事项

1. **禁止业务点手动拼接** `trace_id` / `method` / `path` —— 由格式化器自动注入。
2. **禁止异常处理器静默返回** —— 必须落日志（含 `code`/`status`/`exc_info`）。
3. **禁止请求级访问日志缺失** —— 每请求必有一条 ACCESS。
4. **禁止文件日志记录完整请求 body / 响应 data** —— 走审计表。
5. **禁止后台任务 `trace_id` 为空** —— 任务入口生成并注入。
6. **禁止 `exc_info` 数组化** —— 保持字符串。
7. **禁止把机器可读键值（status/code/duration）内联进 message** —— 一律独立字段。

## 8. 三端一致性要求

Java / Go 必须与 Python 参考实现对齐以下要点：

1. 请求入口中间件注入 `trace_id` / `method` / `path` / `ip` / `user_agent` 到请求上下文。
   - `ip` 优先取 `X-Forwarded-For` 首段（适配 Nginx 反代），无则取客户端直连 IP。
2. 认证层（SessionFilter/JWT 解析用户处）注入 `user_id` 到请求上下文，未认证时为空。
3. 日志格式化器自动注入上述所有字段为 JSON 字段（非空才输出）。
4. 每请求一条 ACCESS 日志（`status`/`duration_ms`/`query` 为字段；`ip`/`user_agent` 由入口保证存在，`user_id` 可空）。
5. 全局异常处理器统一落日志（`code`/`status` 字段 + 字符串 `exc_info`），不静默。
6. 不在文件日志记录完整 body/data。
7. 后台任务注入任务级 `trace_id`，并传播 `ip`/`user_agent`/`user_id`（若适用）。

> Python 端参考实现：`dehaze-python/app/infrastructure/logging.py`、`app/middleware/trace.py`、`app/middleware/request_log.py`、`app/models/base.py`、`app/core/exceptions.py`。

## 9. 日志采集与检索

文件日志经 Filebeat 采集、Logstash 管道归一化后写入 ES：后端日志入 `dehaze-logs-{yyyy.MM.dd}`，前端日志（`client.log`）入 `dehaze-client-logs-{yyyy.MM.dd}`，两者通过 filebeat `fields.service` 分流（见 §3.5.1）。Kibana 分别建 `dehaze-logs-*` / `dehaze-client-logs-*` 索引模式检索；以 `trace_id:xxx` 可同时跨索引检索到同一请求的前端报错日志与后端处理日志。采集链路配置与服务编排属部署/监控设施，详见 [`06-部署架构.md §7.1`](./06-部署架构.md#71-监控体系)。
