# 部署架构

## 1. 文档概述

### 1.1 文档目的

描述图像去雾系统的部署架构设计，包括部署模式、环境规划、服务编排和监控体系。

### 1.2 适用范围

本文档适用于运维人员、DevOps 工程师和需要进行系统部署的开发人员。

## 7. 监控与告警

### 7.1 监控体系

```
应用服务 → 指标采集(Prometheus) → 存储(TSDB) → 可视化(Grafana)
    ↓
日志输出 → 日志采集(Filebeat) → 管道(Logstash) → 存储(ES) → 分析(Kibana)
    ↓
异常检测 → 告警管理(AlertManager) → 通知(邮件/钉钉)
```

- 指标：Prometheus 抓取三端 `/metrics` 及各 Exporter，Grafana 自动加载 `config/grafana/dashboards/` 下的面板（Dehaze 文件夹）
- 日志：Filebeat 采集三端 `logs/{yyyy-MM-dd}/*.log`（NDJSON 解析）→ Logstash → ES 索引 `dehaze-logs-{yyyy.MM.dd}`，Kibana 建 `dehaze-logs-*` 索引模式即可检索
- 告警：Prometheus 按 `config/prometheus/rules/dehaze-alerts.yml` 评估，推送 AlertManager（`config/alertmanager/alertmanager.yml` 配置邮件通知，支持钉钉/企业微信 Webhook 扩展）

### 7.2 关键告警指标

告警规则已实现于 `config/prometheus/rules/dehaze-alerts.yml`：

| 指标 | 阈值 | 持续 | 级别 |
|------|------|------|------|
| CPU 使用率 | > 85% | 5min | warning |
| 内存使用率 | > 90% | 5min | critical |
| 磁盘使用率 | > 85% | 10min | warning |
| 服务宕机 | up == 0 | 1min | critical |
| Java 5xx 错误率 | > 5% | 2min | critical |
| P99 延迟 | > 5s | 5min | warning |
| MySQL 连接数 | > 80% max | 3min | warning |
| Redis 内存 | > 80% maxmemory | 5min | warning |

> 部署前需将 `config/alertmanager/alertmanager.yml` 中的 SMTP 占位配置替换为真实值。
>
> Alertmanager 已启用 Basic Auth（账号 `admin` / 密码 `${DEHAZE_PASSWORD}`），凭证文件 `config/alertmanager/web.yml` 由 `scripts/init-security.sh` 生成（bcrypt）；Prometheus 在 `prometheus.yml` 中以 `basic_auth` 携带该凭证推送告警（密码经启动脚本从 `__ALERTMANAGER_PASSWORD__` 占位符替换，因 prometheus.yml 不支持环境变量）。

### 7.3 业务指标命名规范

三端业务指标统一 `dehaze_` 前缀，跨端聚合面板（`Dehaze 业务监控`）基于以下命名：

| 维度 | 指标 | 埋点端 |
|------|------|--------|
| 预测 | `dehaze_prediction_total{status}`、`dehaze_prediction_duration_seconds` | Java、Go |
| 推理（算法侧） | `dehaze_inference_requests_total{algorithm,status}`、`dehaze_inference_duration_seconds` | Python |
| 评估 | `dehaze_evaluation_total{status}`、`dehaze_evaluation_duration_seconds` | Java、Go |
| 任务 | `dehaze_task_total{task_type,status}`、`dehaze_task_duration_seconds` | Java、Go、Python |
| 缓存 | `dehaze_cache_hits_total{layer}`、`dehaze_cache_misses_total{layer}`、`dehaze_cache_loader_total` | Go、Python |
| GPU | `dehaze_gpu_*`（利用率/显存/温度/功耗） | Python（算法服务独有） |
| 文件上传 | `dehaze_file_upload_total` | Java |
| HTTP 请求 | `http_server_requests_seconds`（Java/Go）、`http_request_duration_seconds`（Python） | 三端 |

### 7.4 日志规范

日志的存储/切割/保留、字段 schema、请求上下文注入、分类与内容规范统一见 [`07-日志架构设计.md`](./07-日志架构设计.md)。日志采集链路（Filebeat → Logstash → ES → Kibana）见 §7.1。

## 9. 安全加固

### 9.1 网络安全

| 措施 | 说明 |
|-----|------|
| 防火墙规则 | 仅开放必要端口（80/443） |
| 内网隔离 | 数据库等服务仅内网访问 |
| HTTPS | 生产环境强制 HTTPS |
| WAF | Web 应用防火墙防护 |
| Elasticsearch 认证 | `xpack.security.enabled=true`，elastic 超级用户密码 = `${DEHAZE_PASSWORD}`，HTTP 层关闭 SSL 保持内网 http 访问 |
| Alertmanager 认证 | 启用 Basic Auth（账号 `admin` / 密码 `${DEHAZE_PASSWORD}`），容器启动时动态生成 bcrypt 凭证；Prometheus 推送告警需同步配置 `basic_auth` |

### 9.2 部署安全检查清单

- [ ] 修改默认密码（MySQL、Redis、MinIO 等）
- [ ] 配置 HTTPS 证书
- [ ] 限制数据库远程访问
- [ ] 配置防火墙规则
- [ ] 启用日志审计
- [ ] 定期更新系统和依赖
- [ ] 容器使用非 root 用户运行
