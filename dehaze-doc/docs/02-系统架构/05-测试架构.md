# 测试架构

## 1. 目标与范围

### 1.1 测试目标

| 目标                   | 说明                                                           |
| ---------------------- | -------------------------------------------------------------- |
| **保障核心功能正确性** | 确保图像去雾、图像处理、数据集管理等核心流程在各端均能正常运行 |
| **确保系统稳定性**     | 通过多层次测试防止回归问题，保障系统在高负载下的稳定性         |
| **提升代码质量**       | 通过测试驱动开发（TDD）和持续集成提升代码可维护性              |
| **缩短发布周期**       | 自动化测试减少人工回归测试时间，加速版本迭代                   |

### 1.2 测试范围

| 项目                | 技术栈                  | 测试类型               |
| ------------------- | ----------------------- | ---------------------- |
| dehaze-python       | Python/FastAPI/PyTorch  | 单元测试 + 集成测试    |
| dehaze-java         | Java/Spring Boot        | 单元测试 + 集成测试    |
| dehaze-go           | Go/Gin/GORM             | 单元测试 + 集成测试    |
| dehaze-front-vue    | Vue3/TypeScript/Vite    | 单元测试 + E2E 测试    |
| dehaze-front-react  | React/TypeScript        | 单元测试 + E2E 测试    |
| dehaze-sdk-js       | TypeScript/Vitest       | API 集成测试           |
| dehaze-taro         | Taro/TypeScript         | 单元测试               |
| dehaze-uniapp       | UniApp/Vue3             | 单元测试               |
| dehaze-react-native | React Native/TypeScript | 单元测试               |
| dehaze-android      | Android/Kotlin          | 单元测试 + UI 测试     |
| dehaze_flutter      | Flutter/Dart            | 单元测试 + Widget 测试 |
| dehaze-harmony      | HarmonyOS/ArkTS         | 单元测试 + UI 测试     |

### 1.3 不在测试范围内

- 第三方库/框架的内部实现测试
- 模型训练过程（属于 dehaze-algorithm 研究项目）
- 文档项目 dehaze-doc 的内容验证

### 1.4 dehaze-test（开发工作台）

`dehaze-test` 是**开发工作台**（Developer Workbench），面向人的开发活动——联调、数据操作、跨端对比、质量评估；人工触发，产物是数据报告而非 pass/fail 结论，**不承载 CI、产品回归与 SDK 契约测试**。其纪律：

- 复用 `dehaze-python/.venv` 运行，不单建环境。
- 一次性脚本用完即删，不作长期资产。
- 评估发现的硬性不变量必须沉淀回各端 pytest，不在工作台内长期断言。

## 2. 测试分层与策略

### 2.1 测试金字塔

```
                    ┌─────────────────┐
                    │    E2E 测试      │  ← 端到端流程验证（5%）
                   ┌┴─────────────────┴┐
                   │    集成测试        │  ← 模块间交互（20%）
                  ┌┴───────────────────┴┐
                  │      单元测试         │  ← 函数/方法级别（75%）
                 └───────────────────────┘
```

### 2.2 测试类型定义

| 测试类型     | 定义                                         | 执行频率    | 时间目标   |
| ------------ | -------------------------------------------- | ----------- | ---------- |
| **单元测试** | 测试单个函数/方法的逻辑正确性，Mock 外部依赖 | 每次提交    | < 30秒     |
| **集成测试** | 测试多个模块/服务间的交互，使用真实数据库    | 每次合并 PR | < 5分钟    |
| **E2E 测试** | 模拟真实用户操作流程，验证端到端功能         | 每日/发布前 | < 15分钟   |
| **性能测试** | 验证系统在高负载下的响应时间和吞吐量         | 版本发布前  | 视场景而定 |
| **安全测试** | 验证权限控制、数据隔离、注入防护             | 版本发布前  | < 10分钟   |

### 2.3 各端测试分层

## 3. 测试环境与数据策略

### 3.1 测试环境

| 环境类型         | 用途         | 数据库/依赖                                                                                                                                                                            | 特点                                            |
| ---------------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| **本地开发环境** | 开发阶段测试 | 真实 MySQL 测试库（默认 `dehaze_test`，三端共用同一变量 `DEHAZE_TEST_DB` 指定，与开发同实例，schema/种子数据同源于 `config/sql`；Go 端经 `internal/testutil` 指纹重建 + 事务回滚隔离） | 零方言漂移                                      |
| **CI 测试环境**  | 持续集成测试 | MySQL/Redis/MongoDB Docker + 真实三端后端                                                                                                                                              | 与生产环境一致，SDK 集成测试连接 8989/8990/8991 |
| **预发布环境**   | 发布前验证   | 独立测试数据库                                                                                                                                                                         | 模拟生产配置                                    |

### 3.2 测试数据策略

| 原则             | 说明                                 |
| ---------------- | ------------------------------------ |
| **测试数据隔离** | 每个测试用例使用独立的测试数据       |
| **事务回滚**     | 测试结束后自动回滚事务，不污染数据库 |
| **工厂模式**     | 使用工厂函数创建测试数据，保持一致性 |
| **最小化数据**   | 只创建测试所需的最小数据集           |
| **统一前缀**     | 测试数据使用 `test_` 前缀便于清理    |

### 3.3 数据清理策略

| 策略              | 适用场景                  | 实现方式                                                                                                                                              |
| ----------------- | ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| **事务回滚**      | 单元测试、集成测试        | 测试框架自动回滚                                                                                                                                      |
| **afterAll 清理** | 集成测试经 API 创建的资源 | 用例创建即登记 id，套件结束逐个删除；**被后台任务/周期巡检扫描的资源（如 MCP Server）必须清理**——残留会持续消耗后端（巡检每轮耗时随残留条数线性增长） |
| **表截断**        | E2E 测试前置清理          | TRUNCATE TABLE                                                                                                                                        |
| **软删除**        | 需要保留审计日志          | 标记删除状态                                                                                                                                          |
| **定时清理**      | 测试环境数据积累          | 定时任务清理过期数据                                                                                                                                  |

### 3.4 测试并行运行（`DEHAZE_TEST_DB`）

三端数据库测试默认共用 `dehaze_test`，且各自都会重建该库（Java `sql.init` 全量重建、Python 重建、Go 指纹重建），**必须串行**。要并行（三端同时跑、或多套 SDK 测试同时跑），用 `DEHAZE_TEST_DB` 给每套测试分一个独立库：

| 并行任务                                 | 命令                                               | 外部依赖                                                    |
| ---------------------------------------- | -------------------------------------------------- | ----------------------------------------------------------- |
| Java 单元测试（纯 Mockito，不启 Spring） | `mvn test`                                         | 无，可与任何任务并行                                        |
| Java 集成测试（failsafe）                | `DEHAZE_TEST_DB=dehaze_test_java mvn verify`       | MySQL + Mongo（库名跟随变量）+ Redis `DEHAZE_TEST_REDIS_DB` |
| Python 全部测试                          | `DEHAZE_TEST_DB=dehaze_test_py uv run pytest -n 4` | MySQL（Redis/Mongo 为内存桩）                               |
| Go 全部测试                              | `DEHAZE_TEST_DB=dehaze_test_go go test ./...`      | MySQL（Redis 为 miniredis）                                 |
| SDK 集成测试（打真实后端）               | `pnpm test:java` / `test:go` / `test:python`       | 各后端进程各自 8989/8990/8991，写的是**开发库**             |

- 变量单点定义、三端共用：Java `application-test.yml`、Python `tests/conftest.py`、Go `internal/testutil`；不设时一律回落 `dehaze_test`（等于不改变原有串行行为）
- 重建互斥锁与 schema 指纹**按库名区分**（Python/Go 的 `GET_LOCK("{库名}_rebuild")`、库内 `_test_schema_meta`），不同库之间零阻塞
- **Python xdist（`-n N`）自动按 worker 派生库**：conftest 将库名派生为 `{DEHAZE_TEST_DB}_gw{i}`（如 `-n 64` → 64 个库）。根因：多 worker 共库时并发 UPDATE 同一批种子行触发 1213 死锁，服务端回滚整个事务后 `ROLLBACK TO SAVEPOINT` 报 1305（SAVEPOINT does not exist），实测 `-n 64` 下 50×1213 与 50×1305 精确配对；`-n 8` 基本不触发。串行（无 `-n`）保持基础库名不变。worker 库可留存复用（指纹一致免重建），不需要时 `DROP DATABASE dehaze_test_py_gw*` 清理
- SDK 集成测试的并行与后端测试相互独立：它不碰测试库，瓶颈是"同一后端共享开发库数据"与套件内文件串行（`fileParallelism: false`）
- 不再需要的并行库直接 `DROP DATABASE` 清理（如 `DROP DATABASE dehaze_test_py`）

### 5.3 静态检查门禁（dehaze-python）

**唯一执行入口**：`dehaze-python/scripts/check.sh`（依次跑 `ruff check` → `ruff format --check` → 逐子项目 `pyright`，任一非零即失败）。CI 判定只认本脚本，**不认编辑器设置**。

| 项             | 工具                  | 阈值                | 覆盖范围                       | 规则/口径定义处                                                                   |
| -------------- | --------------------- | ------------------- | ------------------------------ | --------------------------------------------------------------------------------- |
| Lint（含告警） | ruff                  | 0                   | `dehaze-python` + 三个推理服务 | 各项目自身 `pyproject.toml` 的 `[tool.ruff]`                                      |
| 代码格式       | ruff format           | 0 处待格式化        | 同上                           | 同上（`line-length = 100`）                                                       |
| 类型检查       | pyright（`standard`） | 0 error / 0 warning | 5 个 Python 子项目（见下表）   | 共享判定标准：仓库根 `pyright.base.json`；检查范围：各子项目 `pyrightconfig.json` |

**ruff 执行方式**：编排侧与各服务都进入自身目录执行，规则自然取自该目录的 `pyproject.toml`。三个推理服务各有独立 venv，但 ruff 只做静态分析、不依赖项目环境，故统一用编排侧的 ruff 可执行文件；`dehaze-mcp-gateway` 未定义 `[tool.ruff]`，不在 ruff 范围内。

**pyright 版本必须固定**（脚本内 `PYRIGHT_VERSION`，与 IDE 的 `ms-pyright` 扩展对齐）。typeshed 结论随版本变化，会导致"IDE 报错、门禁漏检"的口径分裂：升级 IDE 扩展时须同步改脚本内版本号。`--warnings` 不可省——pyright 默认只在**有 error** 时返回非零退出码，"有 warning 也算通过"，而门禁口径是 0 error / 0 warning。

**类型检查口径＝共享判定标准 + 各自检查范围**（不得分散到 `.vscode/settings.json`，否则本机与流水线口径分裂）：

- **共享判定标准单点**：仓库根 `pyright.base.json` 只放与项目无关的判定标准（`typeCheckingMode = "standard"`、`pythonPlatform = "Linux"`、`pythonVersion = "3.11"`），各子项目配置以 `extends` 继承。注意 `extends` 只接受**单个**文件路径，且为**顶层键整体覆盖**（数组字段不做元素级合并）。`pythonVersion` 必须显式声明（5 个 Python 子项目 venv 统一为 3.11）：省略该键时，venv 版本探测失败会回退到 PATH 上的系统解释器版本，把 `X | None`、`datetime.UTC` 等 3.10+ 语法误报为错误。
- **检查范围与解释器**：每个子项目根目录自持一份 `pyrightconfig.json`，只描述自己的 `include` / `venv` / `extraPaths`：

| 子项目                                    | venv                  | include / 特殊项                                                                                     |
| ----------------------------------------- | --------------------- | ---------------------------------------------------------------------------------------------------- |
| `dehaze-python`                           | 自身的 `.venv`        | `app`、`tests`；`ignore` `logs`                                                                      |
| `dehaze-mcp-gateway`                      | `dehaze-python/.venv` | `server.py`、`tests`；`extraPaths` 挂网关目录（`import server`）与 `dehaze-python`（`import app.*`） |
| `dehaze-service/dehaze-{llm,voice,modal}` | 各自的 `.venv`        | `app`、`tests`；modal 额外 `ignore` `algorithm`                                                      |

- **为什么逐子项目执行**：`venvPath` / `venv` 是 pyright 的全局顶层字段，**不允许写进 `executionEnvironments`**，即一个 pyright 进程只绑定一个解释器；子目录的 `pyrightconfig.json` 也不会被自动拾取（自动查找行为跨版本不一致）。要落实"每个子项目按自己声明的依赖做类型检查"，只能 `pyright -p <子项目>/pyrightconfig.json` 逐个起进程。
- **仓库根 `pyrightconfig.json`** 只服务"以仓库为单根打开 IDE"的场景（`include` 列全 5 个子项目，`executionEnvironments` 区分各自的导入搜索根与 `app` 包归属），**不参与 check.sh**；它与各子项目配置共享同一份 `pyright.base.json`，判定标准一致，但解释器错位：pyright 一个进程只能绑定一个 venv，根配置绑定编排侧 `.venv`，而三个推理服务的重依赖（`llama_cpp`/`funasr`/`piper`/`torch`/`pyiqa`/`pynvml`/`lameenc`）只装在各自 `.venv`，故根模式下这些 import 会报 `reportMissingImports`——属已知限制，服务的类型检查结论以 check.sh 逐项目结果为准。新增 Python 子项目时同步三处：子项目自身 `pyrightconfig.json`、根 `include` + `executionEnvironments`、`check.sh` 的 `PYRIGHT_PROJECTS`。
- **测试代码同样纳入类型检查**（各子项目 `include` 均含 `tests`）：测试里的取值链可能为 None、替身与真契约漂移，都是真实缺陷来源。
- **用 `ignore` 而非 `exclude`**：`ignore` 的文件不被分析但导入仍可解析，`exclude` 会让 `import` 它的文件报错。运行期日志目录与论文复现实现（经 importlib 动态加载）属后者语义，故用 `ignore`。
- **`--warnings` 不可省**：pyright 默认只在**有 error** 时返回非零退出码，"有 warning 也算通过"；门禁口径是 0 error / 0 warning，必须显式加 `--warnings`，否则告警静默累积。

**抑制注释纪律**（禁止"用兜底/静默跳过消告警"，否则问题被隐藏、后续排查困难）：

| 允许           | 形式与条件                                                                                                                                                 |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 行级、负向用例 | `# pyright: ignore[规则名]  # 负向用例：故意构造非法值` —— 仅用于"故意传非法值以断言被拒绝"的用例，必须写明理由                                            |
| 行级、测试替身 | `cast(真类型, 替身)  # 测试替身：仅实现 X/Y 行为` —— 仅限 tests/，且必须写明替身实现了哪些行为；**优先改为真类型子类或真对象实例，能删就删**               |
| **禁止**       | 文件级 `# pyright: ignore` / `# type: ignore`；把 `Any`/`object` 当消音器；靠文件级排除或全局降 severity 让检查变绿；`app/` 内使用 `cast` 掩盖自有类型问题 |

### 5.4 轮末收口：格式化 + 静态检查（CodeBuddy hooks）

hook 分两段：编辑期间只**登记**改动文件（毫秒级、零副作用），轮末在 `Stop` 一次性**批量格式化 + 静态检查**，检出新增问题时把摘要回灌给 agent 让其修复。它**不是门禁**：任何异常静默放行，判定仍只看 §5.3 的 `check.sh`（Go 看 `make test`、Java 看 `mvn verify`）。

| 事件        | 脚本                 | 职责                                                                     |
| ----------- | -------------------- | ------------------------------------------------------------------------ |
| PostToolUse | `track-changes.mjs`  | 把 `Write/Edit` 的 `file_path` 追加进 `.codebuddy/.state/<session>.json` |
| Stop        | `verify-on-stop.mjs` | 批量格式化 → 静态检查 → 有新增问题时写 stderr 并 `exit 2`                |
| SessionEnd  | `cleanup-state.mjs`  | 删除本会话登记，并回收 7 天前的孤儿状态                                  |

**格式化放在轮末而非"编辑后"**：① 编辑期不落盘 ⇒ agent 的 `old_string` 不失配、写了一半的 import 不被删、Python 热重载不被空转触发；② 批量单次进程调用（eslint 单次启动约 8-10s、`mvn` 约 2s，逐文件调用是 N 倍开销）；③ 顺序可控——必须先 format 再 check，否则纯排版问题（`E501`）会淹没真错误。代价是回合中断（Esc/超时/强杀）本轮不格式化、轮末有一次集中停顿（只对改动语言付费），均可接受。

**检查范围**（无改动立即退出；除 pyright 外都按"该项目整项目"诊断，"只报新增"由指纹去重承担）：

| 语言          | 检查项                                                     | 说明                                                                                                                      |
| ------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Python        | `ruff check .`（只读，不加 `--fix`）                       | 整项目跑 ⇒ 跨文件连带（未定义名、未用导入等）能看到                                                                       |
| Python        | `pyright -p <子项目>/pyrightconfig.json --warnings <文件>` | **唯一按文件裁剪的项**（全项目太贵）⇒ 类型级跨文件连带是已知盲区，由 `check.sh` 兜；版本从 `check.sh` 读，同一份 typeshed |
| Go            | `go vet ./...`                                             | 整仓 vet ⇒ 改公共结构体打挂别的包也能看到                                                                                 |
| Java          | 仅 `spotless:apply`（多文件一批）                          | 不做 `mvn compile/test`：会重写 `target/classes`，与运行中的 `spring-boot:run` 不可并存                                   |
| 前端 6 项目   | 仅 `eslint --fix` + `prettier` + `stylelint`               | 类型检查见下一行；react-native 的 jest 配置已就位（`jest.config.js`）                                                     |
| 6 个 TS 项目  | `tsc --noEmit` / `vue-tsc --noEmit`                        | 纳入口径只有"该项目类型干净"一条，**不按耗时排除**（agent 本来也要跑一遍）                                                |
| Markdown/Dart | 仅纯排版                                                   | —                                                                                                                         |

**pyright 为什么必须传文件列表**：`pyright -p <config> --warnings <files...>` 仍解析依赖闭包（结论不打折），但**只报传入文件的错** ⇒ 天然滤掉存量告警，耗时也从全项目压到秒级。

**跨文件 / 跨项目连带**（"存量清零"换来的关键能力）：

- 诊断不按"改动文件"过滤，而是**整项目/整仓跑完、交给指纹去重** ⇒ "改 A 打挂 B"（B 本轮没被改）同样被报出。ruff、`go vet ./...`、`tsc`/`vue-tsc` 都走这条口径；pyright 因成本按文件裁剪，是明文已知盲区。
- **上游库（`dehaze-sdk-js`）变更会连带检查所有下游**：下游按 SDK 的**构建产物 `dist/index.d.ts`** 校验类型 ⇒ hook 检测到上游 `src/**` 或 `package.json` 变更时，先 `pnpm --filter dehaze-sdk-js build` **重建产物**，再把所有依赖它的项目一并纳入本轮检查；不重建就是拿旧 d.ts 做检查（假绿）。依赖关系从各项目 `package.json` 的 `workspace:` / `file:` 声明推导，不写死。

**反馈契约**（防死循环与噪音）：

- 只报**新增指纹**（`文件:行:规则:消息`），同一问题不重复提醒；诊断范围＝改到的项目整项目 + 连带的下游项目。
- **存量清零是"只报新增"成立的前提**：`reported` 指纹只活在本会话，新会话第一次改到某文件会收到该文件的**全部**诊断（含历史遗留）。各语言存量体检口径：`bash dehaze-python/scripts/check.sh`、`go vet ./...` + `gofmt -l`（dehaze-go）、`mvn spotless:check`（dehaze-java）、`dart format --set-exit-if-changed`（dehaze_flutter）、各前端 `pnpm lint`、全仓 `.md` 用 `dehaze-doc` 的 `prettier --check`（`.agent/`、`.venv/`、`.pytest_cache/` 等不入库目录不计）。
- **续跑轮（`stop_hook_active === true`）同样复验**（否则"报错 → 修复"的最后一跳没人验收）；防死循环靠指纹去重 + 同一续跑链最多反馈 2 轮（`MAX_REPORTS_PER_CHAIN`），新的用户轮链计数归零。
- 报告 ≤20 行，写 **stderr** 并置退出码 2（Stop 的 exit 2 是把 stderr 注入下一条消息，不是阻止回合）；文案声明"不是门禁"并限定"只修这些位置，不要顺手重构"。

**格式化口径（按路径分派）**：

| 路径                                                                              | 工具与口径来源                                                                                                                                                                                       |
| --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dehaze-python`、`dehaze-service/dehaze-{llm,voice,modal}`                        | `ruff check --fix` + `ruff format`（带 `--force-exclude`，尊重各项目 `[tool.ruff]` 的 exclude），与 §5.3 同一套 ruff                                                                                 |
| `dehaze-go`                                                                       | `gofmt -w`（本仓无 golangci 配置）                                                                                                                                                                   |
| `dehaze_flutter`                                                                  | `dart format`（默认 80 列）；跳过 `*.g.dart`、`*.freezed.dart`、`lib/generated/`                                                                                                                     |
| `dehaze-java`                                                                     | `mvn spotless:apply -DspotlessFiles=<逗号分隔的文件清单>`，一次 maven 启动处理整批；风格口径在 `dehaze-java/pom.xml`（Palantir，4 空格 / 120 列）                                                    |
| 6 个 Node 项目（front-vue / front-react / taro / uniapp / sdk-js / react-native） | 各自 `node_modules/.bin/{eslint,prettier,stylelint}`，每个工具一次调用处理该项目整批文件，顺序同各自 `lint-staged`；配置取各项目 `.eslintrc*` / `eslint.config.*`、`.prettierrc.*`、`.stylelintrc.*` |
| 全仓 `.md`                                                                        | `dehaze-doc` 的 prettier + `dehaze-doc/.prettierrc.json`（`proseWrap: preserve`，不重排中文段落）；前端各项目 `.prettierignore` 均排除 `*.md`，故 md 口径单点放在 dehaze-doc                         |

**未覆盖**：`dehaze-test`、`dehaze-algorithm`、根 `scripts/` 下的 Python（无 `[tool.ruff]`，与 §5.3 的 ruff 范围一致；`dehaze-mcp-gateway` 只做 pyright 类型检查），以及 `.mdc`、`.sh`、`.yaml`、`.ipynb`。

#### 6.4.2 数据库：真实 MySQL 测试库 `dehaze_test`

- **同实例同版本**：与开发共用 MySQL（凭证来自根目录 `.env`），零方言漂移。不使用 SQLite 内存库（DECIMAL 精度/外键/行锁/UPSERT/collation 多层漂移，计费断言会假绿）
- **schema/种子**：session 级从 `config/sql/{schema,data}` DROP+CREATE 全量重建，与开发库构建同源（三端共享的 schema 事实来源）
- **数据隔离**：`db` fixture 外部事务 + SAVEPOINT 回滚——被测代码内 `async with get_db_session()` 的 commit 只释放 SAVEPOINT，测试结束整体 ROLLBACK
- **运行**：`uv run pytest`；conftest 自动 `APP_ENV=testing`（`TestingSettings.MYSQL_DATABASE=dehaze_test`、`REDIS_PORT=6390`）；并行隔离用 `DEHAZE_TEST_DB` 覆盖（见 §3.4）
- **重建按指纹跳过**：库内 `_test_schema_meta` 存 `config/sql` 全部 `sys_*.sql` 的 SHA-256（与 dehaze-go `internal/testutil` 同源），指纹一致即复用现有库——这是 `-n auto` 多 worker 与多进程并行不互相 DROP 表的前提（需要全量重置时手动 `DROP DATABASE` 即可）

#### 6.4.3 Redis / MongoDB

- **Redis**：`mock_redis` fixture **autouse** 三层防线——①patch 中心入口 `app.dependencies.redis` 的 get_redis_client/get_redis；②动态扫描 sys.modules 替换所有顶层 from-import 持有者；③`REDIS_PORT=6390` 无人监听端口兜底（**勿用端口 0**：redis-py 把 0 当默认 6379 会连真实实例）
- **MongoDB**：`mongo_db` fixture **autouse**，与 Redis 同构两层 patch——①中心入口 `app.dependencies.mongo.get_mongo_client`（mongo 仓储经 `from app.dependencies import mongo` 模块属性延迟引用，单点生效）；②动态扫描 sys.modules 替换 `from app.dependencies.mongo import get_mongo_client` 直接引用持有者（如 `app/router/health.py`）。落地为 mongomock-motor 内存库，测试一律不触达真实 MongoDB（否则测试数据会写脏开发库的 login_log / ai_api_call_log）
- **MongoDB 必须 autouse**：真实 motor client 是进程级单例，其 io loop 在首次使用时绑定并永久缓存；pytest-asyncio 每用例新建事件循环 ⇒ 只要有用例真实触达 Mongo，其后用例复用该单例即拿到已关闭的 loop（`RuntimeError: Event loop is closed`），且故障点会漂移到"下一个真实写入的用例"（审计写入是 fire-and-forget 且异常被吞成 warning）

#### 6.4.4 替身规范（核心原则：只替身外部世界）

| 依赖                    | 规范                                                                                                                                                                                                             |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 仓储                    | **构造注入**（`__init__` 参数 + 模块单例默认值）；测试注入 `SimpleNamespace(get_x=AsyncMock(...))` 显式配方法（**AsyncMock(return_value=X) 的子方法返回子 mock 而非 X**）；单例方法 patch 允许，模块属性替换禁止 |
| 外部 HTTP（LLM/连通性） | respx 传输层拦截，**必须 `assert_all_mocked=True`**（全离线）                                                                                                                                                    |
| Elasticsearch           | **index 模块函数边界 mock**（vector_search/bulk_index_chunks 等）——ES async 客户端走 aiohttp，respx（httpx 层）拦不到；备选 patch `es_client._client`                                                            |
| 存储                    | 业务层依赖 `StorageService` 抽象（上传 `get_storage_service()`、按记录标识 `get_storage_by_name()`）；测试注入 `LocalStorageService(base_dir=tmp_path)` 断言真实文件效果                                         |
| RabbitMQ                | 直接测 handler + patch 依赖；需要时 patch `aio_pika.connect_robust`                                                                                                                                              |
| 故障注入                | 允许且必要（broken client 抛异常测降级/回落分支），不属于反模式                                                                                                                                                  |

**自写自读单测会掩盖跨端断裂**：内存替身（miniredis / 内存桩）只验证本端写入本端读回，三端共享的缓存与集合结构必须另有"**另一端写入的夹具 → 本端读**"的互认用例，否则键名 / 序列化格式不一致会在端到端才暴露。

#### 6.4.5 反模式清单（禁止）

1. 手写 `run_coro`/`async_ret`；2. `StubAsyncSession`/`NullDBSession` 等会话桩做传递占位（故障注入除外）；3. monkeypatch 模块级单例**属性**替换（用构造注入）；4. god-mock 替换整个链路 + 断言调用序列（应断言业务结果：落库状态/返回值）；5. 测试文件重复绑定 Redis 入口；6. `test_xxx_gaps`/`test_xxx_repro` 补丁式命名堆积；7. respx 不带 `assert_all_mocked`（会真实发出网络请求）；8. 因环境未就绪（模型未加载/引擎不可用/前置资源缺失/后端待重启）条件跳过用例——环境故障必须让用例**失败**暴露（引擎自带自动下载/冷加载的，用事件驱动等待 + 充足超时覆盖），skip 只允许用于"功能确认未实现（规划中）"或"依赖能力在设计上不存在"两类；9. 测试里硬编码**随环境变化**的取值（典型：存储 bucket 写死 `dehaze`，而产品读写走 `settings.MINIO_BUCKET`，多环境改造后 pre=`dehaze-pre`/dev=`dehaze-dev` 即必挂）——取值一律从 `settings` 读，禁止复制一份环境取值到测试里

#### 6.4.6 Marker 分层

`api`（router 全部）/ `requires_db`（db fixture 用户，无 MySQL 环境可 `-m "not requires_db"` 跳过）/ `slow`（call 实测 >2s；session 级 setup 耗时不标——跳过无分层收益）；`unit` 默认省略、`integration` 预留、`requires_redis` 因 fakeredis 全局接管闲置。

### 6.5 dehaze-go 分页端点守卫（`internal/api/pagination_sweep_test.go`）

Go 侧分页解析只有 `parsePaginationNamed/WithSize/parsePagination` 一处实现，该用例把"越界必拒 + 边界放行"逐端点钉死（**非 AI 域 34 个端点清单与 python 依据行号见 [Go 架构文档](../04-项目实现/后端/02-Go架构文档.md)**）：

- 打真实 handler 而非 parser：探针以 ROOT claims 越过权限门禁、**不注入 service**——越过参数校验后必然在调用 service 时空指针 panic，"是否 panic"即"是否通过校验"（放行侧断言）；拒绝侧断言响应 body 为 `A0400`。
- 结构体绑定型端点（`ShouldBindQuery` + DTO 自持分页字段）单独一组：分页字段须标 `form:"-"`，否则 `pageNum=abc` 走绑定层兜底成 `B0001`、`pageSize=0/101` 被 service 静默钳制。
- 默认值不能只测 parser：调用点把 python 的 20 写成 10 时 parser 仍返回 10，故默认值用例用 recording service/mock repository 断言 handler **真实透传**的分页值。
- **每处新增校验都必须做摘除反证**（移除校验 ⇒ 对应用例必然失败）；`pageSize=-1` 这类还须断言"不会让 `LIMIT` 失效"。

### 6.6 前端页面级测试（冻结预览基座）

页面级测试跑**构建产物**而非 dev server：dev server 会在源码或 SDK 产物变动时整页 reload，把用例打断在任意中间状态，结果不可复现。基座以 `mode=test` 串联构建与预览，登录走接口而非登录 UI，从根上消除"验证码看图试错"与"HMR 重置登录态"两类成本（交互式浏览器工具仅保留用于开发调试，不承担回归）。

### 6.7 dehaze-sdk-js 测试报告（compact-reporter）

SDK 集成测试通过 `test/config/compact-reporter.ts` 输出双份报告（`brief.json` 面向大模型查阅的失败摘要、`detail.log` 面向问题排查的完整请求/响应与堆栈），保留最近 10 份历史。

报告按日志分组落盘：集成测试为 `test/logs/<后端名>/`（由 `BACKEND_URL` 端口推导），unit 测试为 `test/logs/unit/`（`vitest.unit.config.ts` 设置 `SDK_TEST_LOG_GROUP`），互不轮转。

全量集成测试串行、单文件含登录等初始化钩子、单轮耗时长，故 reporter 在运行期向 **stderr** 输出进度（stdout 仅保留一行 brief JSON 供脚本/大模型解析）：起始行、文件开始/完成行（含通过/失败/跳过与耗时）、失败与慢用例（≥5s）即时行、30s 心跳；距上次进展达超时阈值时追加卡死提示，用于区分"后端不可达 / 钩子卡住 / 正常慢"。

### 6.8 门禁与巡检脚本（只读校验）

测试链路有两个"前提条件"此前只写在文档与注释里、靠人记，踩中后错误都在远端才暴露，现由两个只读脚本兜住（**不构建镜像、不启动服务、不写库**；退出码统一 `0` 通过 / `1` 命中问题 / `2` 用法或环境错误）。

#### 6.8.1 `scripts/check_dockerfiles.py`（测试镜像三条铁律）

扫描仓库内全部 `Dockerfile` / `Dockerfile.*`，逐条断言三条铁律：

1. **`uv sync` 的两个必需参数**
   - `--no-cache`：不加会把已下载的轮子留在 `/root/.cache/uv` 永久占住镜像层（实测 10.2G → 19.7G），后一层再 `rm` 也缩不回去；
   - `--extra test`：仅要求**测试阶段（`FROM ... AS test`）**且该项目把测试依赖声明在 `[project.optional-dependencies].test` 时 —— dehaze-python 缺它会少 respx/mongomock/freezegun/pytest-mock（6 个测试文件收集失败）。测试依赖声明在 `[dependency-groups].dev` 的项目（推理服务即此形态，uv 默认安装）**不需要**该参数，故本项按项目实际声明判定、不做一刀切；阶段内没有 COPY 该项目 `pyproject.toml`（无法判定）时按违规报出，不静默放过。
2. **测试镜像必须 COPY 仓库根 `config/`**：三端测试都用 `config/sql` 全量重建测试库，go 镜像漏了它会 104 个建库用例全挂。判定方式＝该阶段 COPY 进镜像的源码里若出现 `config/sql` 引用（脚本会打印证据 `文件:行`），则必须有一条 COPY 来源指向仓库根 `config`。
3. **Dockerfile 禁用 heredoc**（`<<EOF` / `<<-'EOF'`）：不带 `\` 续行的 heredoc 体会被 Dockerfile 解析吃掉（`settings.xml` 被写成空文件），改用 `printf '%s\n'` 续行。

```bash
python scripts/check_dockerfiles.py                    # 扫全部
python scripts/check_dockerfiles.py dehaze-go/Dockerfile   # 只查指定文件
```

命中即打印 `文件:行` + 现况 + 修法，退出码 1。

**触发时机**：已接入轮末收口 hook（§5.4）——本轮改动命中 `Dockerfile*` 时自动执行，违规以 `dockerfile-rule` 进轮末报告，无需人工调用。

#### 6.8.2 `scripts/check_schema_drift.py`（开发库 schema 漂移）

集成测试连的是**开发库**（根 `.env` 的 `MYSQL_DATABASE`），schema 变更须手工 ALTER；库落后于 `config/sql/schema/*.sql` 时，缺列会让整套件在 beforeAll 报 500 并大面积 skip，只能事后从 `1054 Unknown column` 反推。脚本把 `config/sql/schema/sys_*.sql` 的表/列集合与目标库 `information_schema` 对账，输出**缺表 / 缺列 / 多余列 / 多余 `sys_*` 表**清单（含 DDL 定义位置），有漂移即 exit 1：

```bash
dehaze-python/.venv/bin/python scripts/check_schema_drift.py
```

- **只报告不自动改库**：脚本只发 `SELECT`；改 schema 仍走 `config/sql/schema/*.sql` + `config/sql/migration/*.sql` 的人工路径（迁移均为手工 `mysql <` 执行，见 §6.4.2 与《10-多环境部署实践》§3.2）。
- **触发时机**：属 on-demand 连库命令，**不进轮末收口 hook**（hook 不依赖活库/网络）——部署前 / 大改 schema 后手动执行。
- **适用范围**：连接参数读仓库根 `.env` 的 `MYSQL_*`（环境变量优先），目标库取 `MYSQL_DATABASE`（当前 dev 为 `dehaze_dev`）；脚本只发 `information_schema` 的 `SELECT`，不会写入。
- 只比对**列名集合**，不比对类型/默认值/索引；`xxl_job.sql`（调度中心独立库，已移出 `config/sql/schema/`）不参与。

> `check_dockerfiles.py` 已接入轮末收口 hook（改动命中 `Dockerfile*` 即执行）；`check_schema_drift.py` 为按需调用。两者均未接入自动化流水线；部署检查清单已登记其用法（见《06-部署架构》§6.3、§6.5）。

### 6.9 跨端契约验收（parity）

A 类端点在 java / go / python 各自原生实现，验收以 **python 为基准逐参数对拍**：python 有界而它端无界＝缺口（修），它端反向加界＝主动偏离（两端同改）；默认值也逐端点对；"service 层等价拦截且错误码 / 文案一致"不算缺口。同名参数在不同端点语义常不同（如 `status`），跨端点类推必错。

- **清查"某模式的全部实现"须按实现形态穷举**：逐参解析 / `ShouldBindQuery` + `Normalize()` / service 归一化 / DTO 自持分页字段（绕过分页 helper）。只按特征串 grep 会整类漏掉。核 python 分页须追 `Depends()` 模型继承链（系统模块 router 内联 `Query(default=N)`、AI 域 schema 继承 `BasePageQuery`），"router 里 grep 不到 ≠ 无分页"。
- **字段约束验收＝可观测行为**（非"注解存在"）：注解 + 触发条件（使用处 `@Valid` / `@Validated`）+ 兜底 + 必填性四层同核；补触发条件须单列验收项并做摘除反证；`@RequestBody List<T>` 元素校验须 `@Valid List<@Valid T>`。
- **参数校验两档测法不可互抄**：字段级（DTO + `@Valid`）用 standalone MockMvc + `LocalValidatorFactoryBean`；方法级（裸 `@RequestParam` + 类级 `@Validated`）须 `MethodValidationPostProcessor` 包装代理，否则全绿却未验任何东西。
- **举证要求**：负向用例断 `$.code` + `verifyNoInteractions(mapper/service)`；范围 / 计数声明必须实测并附"计数基 + 时间戳"；判"缺口 / 丢失"前先自问检索式是否漏（`grep -nE 'status|Min|Max'` 匹配不到 `@NotNull`）、输出是否被 `| head` 截断。
- **跨端对拍脚本只断 `code + status`，不断 `msg`**：java 用中文注解文案、python 用英文 pydantic 文案，`msg` 天然不一致。
- **枚举 / `Literal` 取值校验留在 service 层单一信息源**，不搬成 DTO 的 `@Pattern` / 枚举注解，避免同一约束两处维护、错误码与文案漂移。

## 7. 缺陷管理与回归策略

### 7.1 缺陷分级（严重度）

> 缺陷严重度分级（P0-P3）与 §4.1 测试覆盖优先级（P0-P3）含义不同，注意区分。

| 级别        | 描述                         | 响应时间  | 修复时间   |
| ----------- | ---------------------------- | --------- | ---------- |
| **P0-阻断** | 系统无法使用，核心功能不可用 | 1 小时内  | 4 小时内   |
| **P1-严重** | 主要功能受损，无 workaround  | 4 小时内  | 24 小时内  |
| **P2-一般** | 功能异常，有 workaround      | 24 小时内 | 3 工作日   |
| **P3-轻微** | 边缘功能问题，体验影响       | 3 工作日  | 版本内修复 |

### 7.2 缺陷处理流程

```
发现缺陷 → 创建 Issue → 分级定优先级 → 分配开发者
    ↓
修复代码 → 编写回归测试 → Code Review → 合并代码 → 验证修复 → 关闭 Issue
```

### 7.3 回归测试策略

| 场景         | 回归范围                        | 执行时机   |
| ------------ | ------------------------------- | ---------- |
| **Bug 修复** | 相关模块单元测试 + 相关功能 E2E | 修复后     |
| **功能变更** | 变更模块全部测试                | 变更后     |
| **版本发布** | 全量单元测试 + 核心 E2E         | 发布前     |
| **紧急修复** | 相关单元测试 + P0 E2E           | 修复后立即 |

### 7.4 测试用例维护原则

| 原则             | 说明                              |
| ---------------- | --------------------------------- |
| **Bug 必有测试** | 每个 Bug 修复必须附带回归测试用例 |
| **测试先行**     | 新功能开发前先定义测试用例        |
| **持续更新**     | 需求变更时同步更新测试用例        |
| **定期清理**     | 移除过时、失效的测试用例          |
