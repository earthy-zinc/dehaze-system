# 测试架构

## 1. 目标与范围

### 1.1 测试目标

| 目标 | 说明 |
|------|------|
| **保障核心功能正确性** | 确保图像去雾、算法处理、数据集管理等核心流程在各端均能正常运行 |
| **确保系统稳定性** | 通过多层次测试防止回归问题，保障系统在高负载下的稳定性 |
| **提升代码质量** | 通过测试驱动开发（TDD）和持续集成提升代码可维护性 |
| **缩短发布周期** | 自动化测试减少人工回归测试时间，加速版本迭代 |

### 1.2 测试范围

| 项目 | 技术栈 | 测试类型 | 状态 |
|------|--------|---------|------|

## 2. 测试分层与策略

### 2.1 测试金字塔

```
                    ┌─────────────────┐
                    │    E2E 测试      │  ← 端到端流程验证（5%）
                   ┌┴─────────────────┴┐
                   │    集成测试        │  ← 模块间交互（20%）
                  ┌┴───────────────────┴┐
                  │      单元测试         │  ← 函数/方法级别（75%）
                 └───────────────────────┘
```

### 2.2 测试类型定义

| 测试类型 | 定义 | 执行频率 | 时间目标 |
|---------|------|---------|---------|
| **单元测试** | 测试单个函数/方法的逻辑正确性，Mock 外部依赖 | 每次提交 | < 30秒 |
| **集成测试** | 测试多个模块/服务间的交互，使用真实数据库 | 每次合并 PR | < 5分钟 |
| **E2E 测试** | 模拟真实用户操作流程，验证端到端功能 | 每日/发布前 | < 15分钟 |
| **性能测试** | 验证系统在高负载下的响应时间和吞吐量 | 版本发布前 | 视场景而定 |
| **安全测试** | 验证权限控制、数据隔离、注入防护 | 版本发布前 | < 10分钟 |

### 2.3 各端测试分层

#### 2.3.1 后端测试分层（Java/Go/Python）

| 层级 | 测试重点 | 示例 |
|------|---------|------|
| **Controller 层** | 请求参数校验、响应格式、权限控制 | API 接口测试 |
| **Service 层** | 业务规则、事务边界、异常处理 | 业务逻辑测试 |
| **Repository 层** | CRUD 操作、查询条件、数据完整性 | 数据访问测试 |

#### 2.3.2 前端测试分层（Vue/React）

| 层级 | 测试重点 | 工具 |
|------|---------|------|
| **E2E 测试** | 完整用户流程、跨页面交互 | Playwright |
| **组件测试** | 组件渲染、Props/Events、用户交互 | Vitest + Testing Library |
| **Store 测试** | 状态初始化、Actions、Getters | Vitest |
| **工具函数测试** | 纯函数逻辑、边界条件 | Vitest |

#### 2.3.3 SDK API 测试分层（dehaze-sdk-js）

| 层级 | 测试重点 |
|------|---------|
| **API 集成测试** | 真实后端 API 调用、请求/响应格式、业务错误码 |
| **CRUD 流程测试** | 创建→查询→更新→删除、数据一致性、级联测试 |
| **边界与异常测试** | 参数校验、权限控制、业务规则约束 |

#### 2.3.4 SDK 测试失败报告（compact-reporter）

SDK 集成测试通过 `test/config/compact-reporter.ts` 输出双份报告（`brief.json` 面向大模型查阅的失败摘要、`detail.log` 面向问题排查的完整请求/响应与堆栈），保留最近 10 份历史。请求/响应捕获与轮转策略详见 `dehaze-sdk-js/test/` 目录实现。

## 3. 测试环境与数据策略

### 3.1 测试环境

| 环境类型 | 用途 | 数据库/依赖 | 特点 |
|---------|------|------------|------|
| **本地开发环境** | 开发阶段测试 | SQLite/H2 内存库（Java/Go），真实 MySQL（SDK 集成测试） | 快速启动 |
| **CI 测试环境** | 持续集成测试 | MySQL/Redis/MongoDB Docker + 真实三端后端 | 与生产环境一致，SDK 集成测试连接 8989/8990/8991 |
| **预发布环境** | 发布前验证 | 独立测试数据库 | 模拟生产配置 |

### 3.2 测试数据策略

| 原则 | 说明 |
|------|------|
| **测试数据隔离** | 每个测试用例使用独立的测试数据 |
| **事务回滚** | 测试结束后自动回滚事务，不污染数据库 |
| **工厂模式** | 使用工厂函数创建测试数据，保持一致性 |
| **最小化数据** | 只创建测试所需的最小数据集 |
| **统一前缀** | 测试数据使用 `test_` 前缀便于清理 |

### 3.3 数据清理策略

| 策略 | 适用场景 | 实现方式 |
|------|---------|---------|
| **事务回滚** | 单元测试、集成测试 | 测试框架自动回滚 |
| **表截断** | E2E 测试前置清理 | TRUNCATE TABLE |
| **软删除** | 需要保留审计日志 | 标记删除状态 |
| **定时清理** | 测试环境数据积累 | 定时任务清理过期数据 |

## 4. 覆盖范围与优先级

### 4.1 测试优先级划分

> 本节优先级（P0-P3）指**测试覆盖优先级**，与 §7.1 缺陷分级（P0-P3）含义不同，注意区分。

| 优先级 | 描述 | 覆盖率要求 | 适用模块 |
|--------|------|-----------|---------|
| **P0** | 核心功能，影响核心业务流程 | ≥ 90% | 图像上传/去雾处理/算法调用 |
| **P1** | 重要功能，影响用户体验 | ≥ 80% | 用户认证/权限控制/数据集管理 |
| **P2** | 一般功能，影响部分用户 | ≥ 60% | 系统配置/日志记录/字典管理 |
| **P3** | 边缘功能，影响极少用户 | ≥ 40% | 导出功能/统计报表 |

### 4.2 核心模块测试优先级

| 模块 | 优先级 | 必测场景 |
|------|--------|---------|
| **图像输入** | P0 | 上传成功/格式校验/大小限制/MD5 校验 |
| **去雾处理** | P0 | 算法调用/进度反馈/结果返回/超时处理 |
| **效果对比** | P0 | 对比显示/指标计算/图片加载 |
| **AI 对话** | P0 | 会话管理/消息收发/流式输出/工具调用/长对话摘要 |
| **数据集管理** | P1 | CRUD 操作/批量操作/权限控制 |
| **算法管理** | P1 | 算法列表/状态切换/参数配置 |
| **用户管理** | P1 | 登录/注册/权限验证/Token 刷新 |
| **角色管理** | P1 | 角色 CRUD/权限分配/菜单绑定 |
| **会员与套餐** | P1 | 会员开通/等级成长/配额扣减/套餐购买 |
| **收藏与推荐** | P1 | 收藏增删/列表查询/推荐规则/采纳反馈 |
| **AI 知识库** | P1 | 知识库 CRUD/文档解析/分块检索 |
| **消息通知** | P1 | 消息生成/已读/推送/公告分发 |
| **菜单管理** | P2 | 菜单树/路由生成/缓存更新 |
| **部门管理** | P2 | 部门树/人员关联 |
| **字典管理** | P2 | 字典 CRUD/缓存更新 |
| **反馈评价** | P2 | 评价提交/低分告警/反馈回复 |
| **订单与支付** | P2 | 订单创建/支付回调/退款流程 |

### 4.3 测试场景覆盖矩阵

每个模块应覆盖以下测试场景：

| 场景类型 | 描述 | 示例 |
|---------|------|------|
| **正常流程** | Happy Path，标准输入输出 | 正常登录成功 |
| **边界条件** | 极值、临界条件 | 用户名长度为 1/最大长度 |
| **异常输入** | 非法参数、错误格式 | 邮箱格式错误 |
| **并发场景** | 多用户/多线程同时操作 | 并发修改同一数据 |
| **权限控制** | 越权访问、无权操作 | 普通用户访问管理接口 |
| **缓存一致性** | 数据更新后缓存同步 | 修改后查询返回新数据 |
| **事务完整性** | 操作失败后数据回滚 | 部分失败全部回滚 |

### 5.1 代码提交门禁

| 检查项 | 阈值 | 阻断级别 |
|--------|------|---------|
| 单元测试通过率 | 100% | 🔴 阻断合并 |
| 代码覆盖率（新增代码） | ≥ 80% | 🔴 阻断合并 |
| 代码覆盖率（整体） | ≥ 60% | 🟡 警告 |

| 检查项 | 阈值 | 阻断级别 |

## 7. 缺陷管理与回归策略

### 7.1 缺陷分级（严重度）

> 缺陷严重度分级（P0-P3）与 §4.1 测试覆盖优先级（P0-P3）含义不同，注意区分。

| 级别 | 描述 | 响应时间 | 修复时间 |
|------|------|---------|---------|
| **P0-阻断** | 系统无法使用，核心功能不可用 | 1 小时内 | 4 小时内 |
| **P1-严重** | 主要功能受损，无 workaround | 4 小时内 | 24 小时内 |
| **P2-一般** | 功能异常，有 workaround | 24 小时内 | 3 工作日 |
| **P3-轻微** | 边缘功能问题，体验影响 | 3 工作日 | 版本内修复 |

### 7.2 缺陷处理流程

```
发现缺陷 → 创建 Issue → 分级定优先级 → 分配开发者
    ↓
修复代码 → 编写回归测试 → Code Review → 合并代码 → 验证修复 → 关闭 Issue
```

### 7.3 回归测试策略

| 场景 | 回归范围 | 执行时机 |
|------|---------|---------|
| **Bug 修复** | 相关模块单元测试 + 相关功能 E2E | 修复后 |
| **功能变更** | 变更模块全部测试 | 变更后 |
| **版本发布** | 全量单元测试 + 核心 E2E | 发布前 |
| **紧急修复** | 相关单元测试 + P0 E2E | 修复后立即 |

### 7.4 测试用例维护原则

| 原则 | 说明 |
|------|------|
| **Bug 必有测试** | 每个 Bug 修复必须附带回归测试用例 |
| **测试先行** | 新功能开发前先定义测试用例 |
| **持续更新** | 需求变更时同步更新测试用例 |
| **定期清理** | 移除过时、失效的测试用例 |
