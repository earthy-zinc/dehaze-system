# 测试架构

## 1. 目标与范围

### 1.1 测试目标

| 目标 | 说明 |
|------|------|
| **保障核心功能正确性** | 确保图像去雾、算法处理、数据集管理等核心流程在各端均能正常运行 |
| **确保系统稳定性** | 通过多层次测试防止回归问题，保障系统在高负载下的稳定性 |
| **提升代码质量** | 通过测试驱动开发（TDD）和持续集成提升代码可维护性 |
| **缩短发布周期** | 自动化测试减少人工回归测试时间，加速版本迭代 |

## 2. 测试分层与策略

### 2.1 测试金字塔

```
                    ┌─────────────────┐
                    │    E2E 测试      │  ← 端到端流程验证（5%）
                   ┌┴─────────────────┴┐
                   │    集成测试        │  ← 模块间交互（20%）
                  ┌┴───────────────────┴┐
                  │      单元测试         │  ← 函数/方法级别（75%）
                 └───────────────────────┘
```

### 2.2 测试类型定义

| 测试类型 | 定义 | 执行频率 | 时间目标 |
|---------|------|---------|---------|
| **单元测试** | 测试单个函数/方法的逻辑正确性，Mock 外部依赖 | 每次提交 | < 30秒 |
| **集成测试** | 测试多个模块/服务间的交互，使用真实数据库 | 每次合并 PR | < 5分钟 |
| **E2E 测试** | 模拟真实用户操作流程，验证端到端功能 | 每日/发布前 | < 15分钟 |
| **性能测试** | 验证系统在高负载下的响应时间和吞吐量 | 版本发布前 | 视场景而定 |
| **安全测试** | 验证权限控制、数据隔离、注入防护 | 版本发布前 | < 10分钟 |

### 2.3 各端测试分层

#### 2.3.1 后端测试分层（Java/Go/Python）

| 层级 | 测试重点 | 示例 |
|------|---------|------|
| **Controller 层** | 请求参数校验、响应格式、权限控制 | API 接口测试 |
| **Service 层** | 业务规则、事务边界、异常处理 | 业务逻辑测试 |
| **Repository 层** | CRUD 操作、查询条件、数据完整性 | 数据访问测试 |

#### 2.3.2 前端测试分层（Vue/React）

| 层级 | 测试重点 | 工具 |
|------|---------|------|
| **E2E 测试** | 完整用户流程、跨页面交互 | Playwright |
| **组件测试** | 组件渲染、Props/Events、用户交互 | Vitest + Testing Library |
| **Store 测试** | 状态初始化、Actions、Getters | Vitest |
| **工具函数测试** | 纯函数逻辑、边界条件 | Vitest |

#### 2.3.3 SDK API 测试分层（dehaze-sdk-js）

| 层级 | 测试重点 |
|------|---------|
| **API 集成测试** | 真实后端 API 调用、请求/响应格式、业务错误码 |
| **CRUD 流程测试** | 创建→查询→更新→删除、数据一致性、级联测试 |
| **边界与异常测试** | 参数校验、权限控制、业务规则约束 |

#### 2.3.4 SDK 测试失败报告（compact-reporter）

SDK 集成测试通过 `test/config/compact-reporter.ts` 输出双份报告（`brief.json` 面向大模型查阅的失败摘要、`detail.log` 面向问题排查的完整请求/响应与堆栈），保留最近 10 份历史。请求/响应捕获与轮转策略详见 `dehaze-sdk-js/test/` 目录实现。

## 3. 测试环境与数据策略

### 3.1 测试环境

| 环境类型 | 用途 | 数据库/依赖 | 特点 |
|---------|------|------------|------|
| **本地开发环境** | 开发阶段测试 | 真实 MySQL 测试库 `dehaze_test`（Python/Java/Go 三端，与开发同实例，schema/种子数据同源于 `config/sql`；Go 端经 `internal/testutil` 指纹重建 + 事务回滚隔离） | 零方言漂移 |
| **CI 测试环境** | 持续集成测试 | MySQL/Redis/MongoDB Docker + 真实三端后端 | 与生产环境一致，SDK 集成测试连接 8989/8990/8991 |
| **预发布环境** | 发布前验证 | 独立测试数据库 | 模拟生产配置 |

### 3.2 测试数据策略

| 原则 | 说明 |
|------|------|
| **测试数据隔离** | 每个测试用例使用独立的测试数据 |
| **事务回滚** | 测试结束后自动回滚事务，不污染数据库 |
| **工厂模式** | 使用工厂函数创建测试数据，保持一致性 |
| **最小化数据** | 只创建测试所需的最小数据集 |
| **统一前缀** | 测试数据使用 `test_` 前缀便于清理 |

### 3.3 数据清理策略

| 策略 | 适用场景 | 实现方式 |
|------|---------|---------|
| **事务回滚** | 单元测试、集成测试 | 测试框架自动回滚 |
| **表截断** | E2E 测试前置清理 | TRUNCATE TABLE |
| **软删除** | 需要保留审计日志 | 标记删除状态 |
| **定时清理** | 测试环境数据积累 | 定时任务清理过期数据 |

## 4. 覆盖范围与优先级

### 4.1 测试优先级划分

> 本节优先级（P0-P3）指**测试覆盖优先级**，与 §7.1 缺陷分级（P0-P3）含义不同，注意区分。

| 优先级 | 描述 | 覆盖率要求 | 适用模块 |
|--------|------|-----------|---------|
| **P0** | 核心功能，影响核心业务流程 | ≥ 90% | 图像上传/去雾处理/算法调用 |
| **P1** | 重要功能，影响用户体验 | ≥ 80% | 用户认证/权限控制/数据集管理 |
| **P2** | 一般功能，影响部分用户 | ≥ 60% | 系统配置/日志记录/字典管理 |
| **P3** | 边缘功能，影响极少用户 | ≥ 40% | 导出功能/统计报表 |

### 4.3 测试场景覆盖矩阵

| 场景类型 | 描述 | 示例 |
|---------|------|------|

### 6.4 dehaze-python 测试架构（2026-08-23 全面重构后）

> 原 `dehaze-python/tests/README.md` 已按"单一信息源"原则并入本节。实现细节以 `dehaze-python/tests/conftest.py` 与 `tests/stubs/` 包为准。

#### 6.4.1 目录结构（镜像源码包路径）

```
tests/
├── conftest.py              # 共享 fixtures：db（MySQL 测试库）/ mongo_db / mock_redis（autouse）
├── stubs/                   # 测试桩包（按职责三拆分，无 re-export）
│   ├── fakes.py             # 仿真假件（StubAsyncSession/NullDBSession/FakeGraph/LLMChunk/RecorderEmitter 等）
│   ├── factories.py         # 数据工厂（fake_redis/make_conv/make_member/make_user_context 等）
│   └── mocks.py             # 外部世界边界打桩辅助（patch_reasoning_boundaries）
├── router/                  # HTTP 接口契约测试（ASGITransport，marker: api）
├── middleware/              # app/middleware 测试
├── infrastructure/          # 镜像 app/infrastructure/（a2a/llm/provider/sse）
├── service/                 # service 单测（ai/ 五子包镜像源码；顶层模块测试落根）
└── repository/              # SQL 语义测试（真实 MySQL，marker: requires_db）
```

#### 6.4.2 数据库：真实 MySQL 测试库 `dehaze_test`

- **同实例同版本**：与开发共用 MySQL（凭证来自根目录 `.env`），零方言漂移。SQLite 内存库方案已否决（DECIMAL 精度/外键/行锁/UPSERT/collation 双层漂移，计费断言可能假绿）
- **schema/种子**：session 级从 `config/sql/`（74 schema + 26 data）DROP+CREATE 全量重建，与开发库构建同源（三端共享的 schema 事实来源；Alembic 已删除）
- **数据隔离**：`db` fixture 外部事务 + SAVEPOINT 回滚——被测代码内 `async with get_db_session()` 的 commit 只释放 SAVEPOINT，测试结束整体 ROLLBACK
- **运行**：`uv run pytest`；conftest 自动 `APP_ENV=testing`（`TestingSettings.DB_NAME=dehaze_test`、`REDIS_PORT=6390`）；并行隔离用 `DB_NAME=dehaze_test_x` env 覆盖
- 注意：UPDATE 后 identity map 不自动刷新须 `db.refresh(entity)`；mongomock/BSON 读回 naive UTC datetime

#### 6.4.3 Redis / MongoDB

- **Redis**：`mock_redis` fixture **autouse** 三层防线——①patch 中心入口 `app.dependencies.redis` 的 get_redis_client/get_redis；②动态扫描 sys.modules 替换所有顶层 from-import 持有者；③`REDIS_PORT=6390` 无人监听端口兜底（**勿用端口 0**：redis-py 把 0 当默认 6379 会连真实实例）
- **MongoDB**：`mongo_db` fixture（mongomock-motor）；mongo 仓储经 `from app.dependencies import mongo` 模块属性延迟引用，patch `app.dependencies.mongo.get_mongo_client` 单点生效

#### 6.4.4 替身规范（核心原则：只替身外部世界）

| 依赖 | 规范 |
|------|------|
| 仓储 | **构造注入**（`__init__` 参数 + 模块单例默认值）；测试注入 `SimpleNamespace(get_x=AsyncMock(...))` 显式配方法（**AsyncMock(return_value=X) 的子方法返回子 mock 而非 X**）；单例方法 patch 允许，模块属性替换禁止 |
| 外部 HTTP（LLM/连通性） | respx 传输层拦截，**必须 `assert_all_mocked=True`**（全离线） |
| Elasticsearch | **index 模块函数边界 mock**（vector_search/bulk_index_chunks 等）——ES async 客户端走 aiohttp，respx（httpx 层）拦不到；备选 patch `es_client._client` |
| 存储 | 业务层依赖 `StorageService` 抽象（上传 `get_storage_service()`、按记录标识 `get_storage_by_name()`）；测试注入 `LocalStorageService(base_dir=tmp_path)` 断言真实文件效果 |
| RabbitMQ | 直接测 handler + patch 依赖；需要时 patch `aio_pika.connect_robust` |
| 故障注入 | 允许且必要（broken client 抛异常测降级/回落分支），不属于反模式 |

#### 6.4.5 反模式清单（禁止）

1. 手写 `run_coro`/`async_ret`；2. `StubAsyncSession`/`NullDBSession` 等会话桩做传递占位（故障注入除外）；3. monkeypatch 模块级单例**属性**替换（用构造注入）；4. god-mock 替换整个链路 + 断言调用序列（应断言业务结果：落库状态/返回值）；5. 测试文件重复绑定 Redis 入口；6. `test_xxx_gaps`/`test_xxx_repro` 补丁式命名堆积；7. respx 不带 `assert_all_mocked`（会真实发出网络请求）；8. 因环境未就绪（模型未加载/引擎不可用/前置资源缺失/后端待重启）条件跳过用例——环境故障必须让用例**失败**暴露（引擎自带自动下载/冷加载的，用事件驱动等待 + 充足超时覆盖），skip 只允许用于"功能确认未实现（规划中）"或"依赖能力在设计上不存在"两类

#### 6.4.6 Marker 分层

`api`（router 全部）/ `requires_db`（db fixture 用户，无 MySQL 环境可 `-m "not requires_db"` 跳过）/ `slow`（call 实测 >2s；session 级 setup 耗时不标——跳过无分层收益）；`unit` 默认省略、`integration` 预留、`requires_redis` 因 fakeredis 全局接管闲置。

## 7. 缺陷管理与回归策略

### 7.1 缺陷分级（严重度）

> 缺陷严重度分级（P0-P3）与 §4.1 测试覆盖优先级（P0-P3）含义不同，注意区分。

| 级别 | 描述 | 响应时间 | 修复时间 |
|------|------|---------|---------|
| **P0-阻断** | 系统无法使用，核心功能不可用 | 1 小时内 | 4 小时内 |
| **P1-严重** | 主要功能受损，无 workaround | 4 小时内 | 24 小时内 |
| **P2-一般** | 功能异常，有 workaround | 24 小时内 | 3 工作日 |
| **P3-轻微** | 边缘功能问题，体验影响 | 3 工作日 | 版本内修复 |

### 7.2 缺陷处理流程

```
发现缺陷 → 创建 Issue → 分级定优先级 → 分配开发者
    ↓
修复代码 → 编写回归测试 → Code Review → 合并代码 → 验证修复 → 关闭 Issue
```

### 7.3 回归测试策略

| 场景 | 回归范围 | 执行时机 |
|------|---------|---------|
| **Bug 修复** | 相关模块单元测试 + 相关功能 E2E | 修复后 |
| **功能变更** | 变更模块全部测试 | 变更后 |
| **版本发布** | 全量单元测试 + 核心 E2E | 发布前 |
| **紧急修复** | 相关单元测试 + P0 E2E | 修复后立即 |

### 7.4 测试用例维护原则

| 原则 | 说明 |
|------|------|
| **Bug 必有测试** | 每个 Bug 修复必须附带回归测试用例 |
| **测试先行** | 新功能开发前先定义测试用例 |
| **持续更新** | 需求变更时同步更新测试用例 |
| **定期清理** | 移除过时、失效的测试用例 |
