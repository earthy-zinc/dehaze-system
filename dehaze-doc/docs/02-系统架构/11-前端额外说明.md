## 前端多端架构分析

### 一、全景盘点

你的前端共有 **10 个客户端实现** + **2 个 SDK 层**：

| 项目 | 技术栈 | 成熟度 | 定位 |
|------|--------|--------|------|
| `dehaze-front-vue` | Vue 3 + Element Plus + Pinia | ★★★★★ 完善 | Web 主端（27 个组件、10 个业务页面、i18n、权限指令、__tests__、Storybook、E2E） |
| `dehaze-front-react` | React + Ant Design + Redux Toolkit | ★★★★☆ 较完善 | Web 副端（15 个组件、Electron 桌面端支持、Storybook） |
| `dehaze-android` | 原生 Android (Java) + Retrofit + ViewModel | ★★★★☆ 较完善 | 原生 Android（MVVM 完整、8 个业务模块、Repository 层） |
| `dehaze-taro` | Taro 3 + React + Redux | ★★★☆☆ 中等 | 小程序端（微信/抖音，完整页面路由和组件体系） |
| `dehaze-uniapp` | uni-app + Vue 3 + uView Plus | ★★★☆☆ 中等 | 跨平台小程序/H5（完整页面和 composables） |
| `dehaze-react-native` | React Native + React Navigation | ★★☆☆☆ 起步 | iOS/Android 跨平台（脚手架搭好、Storybook 集成、业务功能待开发） |
| `dehaze_flutter` | Flutter + Dart | ★☆☆☆☆ 骨架 | 全平台（6 平台目录完整，但只有 1 个测试文件、业务代码几乎为零） |
| `dehaze_harmory` | HarmonyOS ArkTS | ★☆☆☆☆ 骨架 | 鸿蒙端（仅 Index.ets 单页面、EntryAbility 脚手架） |
| `dehaze-demo` | 原生 HTML/JS（无框架） | ★★★☆☆ 中等 | 独立演示站（11 个模块，纯前端演示去雾效果） |
| `dehaze-sdk-js` | TypeScript + Axios | ★★★★★ 完善 | **JS/TS 端统一 SDK**（10 个 API 模块、完整测试套件、工厂模式测试数据） |
| `dehaze-sdk-harmony` | ArkTS | ★★★☆☆ 中等 | **鸿蒙端 SDK**（10 个 API 模块、HTTP/Token 管理、Model 层） |
| *dehaze-android/sdk* | Android Java | ★★☆☆☆ | Android 原生 SDK（内嵌在 android 项目中） |

### 二、核心问题

**1. 与后端三端冗余同构的问题**

前端的多端冗余甚至比后端更严重。和后端三套 CRUD 的问题一样，前端同样在 **每个客户端内独立实现** 了：
- 请求封装（`utils/request.ts`）
- 类型定义（`typings/global.d.ts`）
- 枚举常量（`enums/CacheEnum.ts` 等，几乎逐字相同）
- 状态管理（user/permission/settings 三套 store，Vue 用 Pinia、React 用 Redux、Taro 用 Redux）
- 路由配置和权限守卫

**2. SDK 层做对了一半**

你已经有 `dehaze-sdk-js` 统一了 API 调用层，并且 **Taro 和 uni-app 都已经依赖了它**（从 node_modules 中看到 `dehaze-sdk-js` 链接）。这是正确的方向。但：

- Vue 和 React 两个主端 **没有使用 SDK**，仍然各自维护 `utils/request.ts` + 分散的 API 调用
- `dehaze-sdk-harmony` 作为鸿蒙独立 SDK 存在，但和 JS SDK 的 API 模型定义完全手工同步
- Android 原生端完全自建了 Retrofit 通信层，也没有共享机制

### 三、架构建议

│  │  主端   │ │(Web)  │ │(小程序)│ │app │ │    │ │      │  │

#### 具体策略

**第一优先级：让所有 JS/TS 端统一使用 dehaze-sdk-js**

- Vue 和 React 主端目前各自维护请求和类型，应该迁移到 SDK
- SDK 已经被 Taro、uni-app 引用，证明架构可行
- 迁移后可以删除各端 `utils/request.ts`、各自的 API 模块和重复类型定义
- 收益最大、风险最低

**第二优先级：确立主端 + 决定退役端**

基于成熟度判断：
- **Web 主端**：Vue（最完善、i18n、权限指令、完整测试）。React 可作为 Electron 桌面端的载体继续维护，或降级为参考实现
- **小程序端**：Taro 和 uni-app 二选一。从生态看，uni-app 在国内小程序场景更成熟；从统一性看，Taro 用 React 和 React 主端一致。建议按团队技术栈选一个主推
- **移动端**：Android 原生已较完善，保留。RN 和 Flutter 都在骨架阶段——如果要投产，Flutter 一套代码覆盖 iOS/Android/Desktop 更合理，RN 与 Taro/React 技术栈一致更好维护。同样二选一
- **鸿蒙端**：保留，但业务代码应基于 `dehaze-sdk-harmony` 开发而非从零写
- **demo 端**：作为独立的纯前端演示保留即可，定位清晰

**第三优先级：原生端 SDK 从 OpenAPI 自动生成**

后端统一使用 Go（上次讨论的结论），确保 Swagger/OpenAPI 文档完整后：
- Android SDK 可用 OpenAPI Generator 自动生成 Retrofit 接口
- Flutter SDK 可自动生成 Dart 客户端
- HarmonyOS SDK 目前无成熟生成工具，但可以从 OpenAPI Schema 生成 Model 类型

这样 API 变更时不再需要手动同步多套 SDK。

### 四、关于"展示型项目"的特别建议

如果核心目的是展示多端技术能力，那所有端都保留是合理的。但建议在文档中明确分级：

| 级别 | 含义 | 客户端 |
|------|------|--------|
| **Tier 1 - 生产就绪** | 功能完整、有测试、持续维护 | Vue Web、dehaze-sdk-js |
| **Tier 2 - 功能完整** | 核心功能可用、缺少部分测试 | React Web、Android 原生、Taro/uni-app |
| **Tier 3 - 技术预研** | 骨架/原型阶段 | Flutter、React Native、HarmonyOS |
| **独立** | 独立演示用途 | dehaze-demo |

这样新人接手时一目了然，不会对着 Flutter 项目的空目录困惑半天。

### 五、风险提示

- **SDK 强耦合风险**：所有端依赖同一个 SDK，SDK 出 breaking change 会连锁影响。需要严格遵循语义化版本 + changelog
- **展示型到生产型的过渡成本**：如果后续真要投产，Flutter/RN 骨架端要么补齐要么果断砍掉，半成品维护成本最高
- **枚举和类型同步**：dehaze-sdk-harmony 和 dehaze-sdk-js 之间的模型目前是手动同步的，长期会 diverge。如果鸿蒙端正式投入开发，需要建立 Schema-first 的开发流程

## 生产环境前端选型建议

**结论：Vue (Web) + Flutter (移动端)**

### Web 端：Vue

没有悬念，`dehaze-front-vue` 是当前完成度最高的端：

- 27 个组件、10 个业务页面、完整的 i18n、权限指令、单测 + E2E
- Pinia 状态管理 + 完整路由守卫，已具备生产级工程化水平
- Element Plus 在国内 B 端生态成熟，组件丰富

React 端虽然也较完善，但功能覆盖度不如 Vue，且两套 Web 端同时维护到生产级没有必要。React 端可降级为 Electron 桌面版专用，或作为参考实现归档。

### 移动端：Flutter

移动端候选有四个：Android 原生、React Native、Flutter、Taro/uni-app（小程序）。

**选 Flutter 而非 Android 原生的原因：**

- 去雾系统的移动端核心是**图像展示 + 任务管理**，不依赖深度原生能力（蓝牙、NFC 等），跨平台方案完全胜任
- Flutter 一套代码覆盖 iOS + Android + Web + Desktop，投入产出比远高于原生双端开发
- Dart 的图像处理和自定义渲染能力强，适合去雾效果的高质量图像展示
- Android 原生端虽然完善，但只覆盖 Android 一个平台，生产环境不可能放弃 iOS

**不选 React Native 的原因：**

- 当前 RN 端和 Flutter 端都在骨架阶段，起点相同
- Flutter 的渲染性能和跨平台一致性优于 RN（自绘引擎 vs 桥接原生组件）
- 图像密集型应用场景下 Flutter 的 Skia/Impeller 渲染引擎优势明显

### 小程序端：按需选择，非必须

小程序端（Taro / uni-app）是否需要取决于业务场景。如果去雾系统主要面向专业用户，Web + 移动 App 已足够。如果需要轻量级触达（微信生态分享等），选 **uni-app**——国内小程序生态更成熟、多端编译稳定性更好。

### 鸿蒙端：观望

当前骨架阶段，且鸿蒙生态仍在发展中。保留 SDK 层即可，等市场验证后再投入。

### 关键前置动作

1. **Vue 端接入 dehaze-sdk-js**：消除独立维护的 API 层和类型定义
2. **Flutter 端从骨架补齐业务功能**：参考 Vue 端的页面和 Android 原生端的 MVVM 架构
3. **Go 后端确保 OpenAPI 文档完整**：Flutter 端的 Dart SDK 可自动生成
