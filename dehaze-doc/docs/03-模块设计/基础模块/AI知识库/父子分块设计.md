# 父子分块设计（Small-to-Big 结构感知检索）

> 状态：已实施（2026-09-12，数据层/写入侧/检索链路，上下文注入锚点已接入 AI 对话工具层）。
> 设计要点已同步至
> [后端实现-文档管理.md](后端实现-文档管理.md)（分块引擎）、
> [后端实现-检索引擎.md](后端实现-检索引擎.md)（检索重组）、
> [测试用例.md](测试用例.md)，本文档转为决策记录。

## 1. 问题分析

### 1.1 现状（2026-09-12 分块质量工程结论）

知识库分块为**单层结构**：chunk 既是最小检索单元也是上下文注入单元。三轮评估基线
（`dehaze-test/kb_eval/reports/`，三轮 raw 归档可重放）量化了单层结构的固有矛盾——
**块大小两难**：

| 版本 | 块 token 中位数 | 围栏切断/篇 | 检索命中（宽松口径） |
|---|---|---|---|
| 原始（token 硬剁） | 472 | 2.69 | 0.462 |
| 原子独立 | 206 | 0.41 | 0.462（块信息量不足，MRR 劣化） |
| 结构感知装箱（现行） | 432 | 0.41 | 0.462（折中点） |

小块向量区分度高但上下文不足；大块上下文完整但检索钝。装箱版是折中，不是解。

### 1.2 量化依据（模拟验证）

用装箱版检索 raw 数据（39 用例×4 策略）零成本模拟 small-to-big 上限——
"Top-5 中存在与期望节重合度 ≥0.1 的块"（即只要检索碰到节的一部分，节扩展即可命中）：

| 策略 | 当前块级命中（≥0.5） | 父子模拟上限（≥0.1） | 增益 |
|---|---|---|---|
| fixed（装箱） | 0.462 | 0.744 | **+0.282** |
| recursive | 0.474 | 0.737 | +0.263 |
| table | 0.538 | 0.744 | +0.205 |
| semantic | 0.487 | 0.538 | +0.051（其瓶颈是零召回，父子不解决） |

增益全部来自"装箱块部分命中节（重合度 0.1~0.5）"的场景——检索已找到节的一部分，
只差扩展到整节。**测试集的期望命中单元是 Markdown 小节**，节扩展与命中判定天然对齐。

### 1.3 目标

检索单元与上下文单元解耦：小块（child）用于向量匹配，大块（parent=小节）用于
上下文注入，消除单层折中。

## 2. 方案概述

```
文档 → Markdown 标题树解析 → 小节 Section（= Parent）
         ↓
节内装箱切 Child（复用现有装箱逻辑，作用域从"文档"缩小为"小节"）
         ↓
Child 向量化入 ES（附 section_index / section_path 元数据）—— 向量粒度与现状相同
         ↓
检索：向量召回 Top-2K child → 按 (document_id, section_index) 分组
      → 组内最高分作节代表分 → 节排序取 top_k → 去重
         ↓
取 Parent（该节全部 child 按 chunk_index 拼接）→ 注入 LLM 上下文
（带"文档标题 > 节路径"锚点；超预算按 child 分数优先保留）
```

## 3. 设计决策记录

### D1 parent 虚拟化（不物化存储）

parent 是 `(document_id, section_index)` 的逻辑分组，内容 = 该组 child 按序拼接。
- 对比 LangChain ParentDocumentRetriever 的物化 parent（独立成行 + parent_id 外键）：
  避免双份存储与 reprocess 双写一致性维护；代价是读取时一次分组查询（in 查询，非瓶颈）
- 不选 LlamaIndex AutoMerging 多层树：评估未显示需要句子级第三层；层数增加管道复杂度

### D2 parent = 语义结构单元（Markdown 小节为第一实现），而非任意大小切分

节是作者组织的语义完整单元，与评估测试集的期望命中单元天然对齐（§1.2 增益来源）。
任意窗口切分的 parent 无此对齐关系。**结构信号的来源是格式相关的，但"节"的语义
与分块逻辑格式无关**：格式解析层（document_parser）负责把各格式统一为带结构标记的
文本（Markdown 中间表示），分块层只消费中间表示——新增知识源格式只需解析层适配
（§4.2 格式矩阵），不触及分块与检索层。无结构信号格式的 fallback 是语义分段节，
不降级为单节。

### D3 section_index 为分组键、section_path 为锚点（均随 child 冗余存储）

- `section_index`：child→parent 的外键 + **ES 内聚合分组键**（检索结果直接分组不回表）；
  用稳定序号而非标题文本（标题可重复、可改动）
- `section_path`：上下文注入锚点（`【文档名 > 4.7 类似问题推荐】`），随 child 存 ES+MySQL
  保证命中即得、读取单跳；同节 child 冗余相同值是刻意的（换读取零回表）

### D4 不引入 LangChain 检索框架

- 对话编排（deepagents/langgraph）已复用框架——复杂度在编排，复用正确
- 分块算法复杂度在细节（字符对齐/围栏原子/装箱，评估证明值 0.464→0.659 的质量），
  LangChain 分块器为字符级且无这些能力，引入即质量回退
- ParentDocumentRetriever 本质约百行胶水，无分组去重/节代表分/截断逻辑；引入需适配
  docstore 抽象并重接计费/低质量反馈/测试集/评估钩子，集成成本 > 自建增量
- `parse_sections` 吸收 MarkdownHeaderTextSplitter 思想，算法细节自研

### D5 child 不跨节

装箱边界被节边界约束：短节=单 child，长节=多 child，child→parent 映射干净。
qa 的 Q/A、table 的表格原子归属所在节的 child（Q/A 语义标记保留）。

## 4. 详细设计

### 4.1 数据模型

`sys_knowledge_chunk` 加 2 列（migration SQL 一份，测试库 conftest 自动重建）：

```sql
section_index int NOT NULL DEFAULT 0 COMMENT '所属小节序号(文档内递增,0=无标题文档整篇)',
section_path  varchar(255) NULL COMMENT '小节标题路径(如 "4 核心设计 > 4.2 检索引擎",注入上下文作锚点)'
```

ES chunk 索引 mapping 同步加 `section_index`（keyword，用于聚合分组）。

### 4.2 分块引擎（文档管理域）

- 新增 `parse_sections(text) -> list[Section]`：按**结构信号**切节，节标题路径随层级累积。
  **Markdown 是中间表示而非绑定格式**——结构信号按知识源格式分两层提供：

  | 知识源 | 结构信号来源 | 说明 |
  |---|---|---|
  | md / txt | 文本内 `#`~`####` 标题标记 | 现状直接支持 |
  | docx | 解析层提取 Heading 样式 → 转 `#` 标记 | **补解析层缺口**：当前 `_parse_docx` 丢弃样式（type 恒为 text），补 `paragraph.style` Heading 1-9 → `"#"*level + " " + text`，分块层零改动 |
  | xlsx / pptx | 无节语义（表格/页为天然单元） | 表格原子化已覆盖，节=表格组 |
  | pdf（fast/ocr） | 无结构信号 | 走语义分段 fallback |
  | pdf（hi_res） | 字号/加粗启发式标题检测 | 规划中（业界公认难题） |

  **无结构信号的 fallback 按剩余信号逐级降级**（每级复用已有逻辑）：

  | 级别 | 剩余信号 | 节边界来源 |
  |---|---|---|
  | 1 | `#` 标题 | 标题树 |
  | 2 | 双换行段落 | 段落聚类节（`_merge_small_paragraphs` 复用，小段合并到目标节大小） |
  | 3 | 仅句末标点（连续长文本无空行） | **句子贪心聚类节**：`_split_at_sentences` 切句后按目标节大小（~1500 token）聚合切节，节边界取句边界 |
  | 4 | 无任何信号 | 单节 + 超预算截断兜底（child 走 token 硬切含字符对齐，检索可用，节扩展收益归零） |

- `_chunk_fixed`（装箱）作用域改为节内执行——`_scan_atomic_segments` /
  `_take_budget_text` / `_atomic_chunks` 原样复用，仅外层套节循环
- chunk_index 变为节内序号；`_postprocess` 不变

### 4.3 检索链路（检索引擎域）

- 向量检索候选扩大到 `top_k × 2`（分组去重后仍够 top_k 个节）
- 分组：ES 返回 child 后按 `(document_id, section_index)` 分组 → 组内 max 分作节代表分
  （**可调点 A**：可加组内命中数加权，评估数据定参数）
- 节排序取 top_k → MySQL `WHERE document_id IN ... AND section_index IN ... ORDER BY
  chunk_index` 一次 in 查询拉节内容
- hybrid 的 keyword 分支同分组规则；rerank 改为对节代表文本重排
- 检索响应 VO 加 `sectionPath`；**API 无破坏性变更**（仅字段新增）

### 4.4 上下文注入

命中节以 `【{文档名} > {节路径}】` 锚点 + 节全文注入；节内容超上下文预算时按组内
child 分数降序保留、超出截断并标记（**可调点 B**：截断保留策略）。

### 4.5 迁移

全局切换、不做兼容层（仓库规范）：存量库文档 reprocess 全量重建（section 元数据
需重算）。开发库 migration + reprocess；计费口径不变（embedding 按查询 token）。
AI 域 python 单端，无三端同步。

## 5. 验证计划

1. pytest：parse_sections（标题树/无标题/深层级/重复标题）、child 不跨节、
   分组去重、节截断、混合检索分组一致性
2. kb_eval：collect 一轮 before/after（预期 fixed 命中从 0.462（宽松口径）/0.659
   （Recall@5 口径）向上限 0.744 / 更高靠拢；节分排序质量为首要观察点）
3. 评估发现的硬性不变量沉淀回 `tests/service/test_kb_chunking.py`

## 6. 风险与可调参数

| 风险 | 缓解 |
|---|---|
| 节代表分（组内 max）排序质量劣化 | 可调点 A：max + 组内命中数加权，评估数据定 |
| 超长节挤占上下文 | 可调点 B：按 child 分数截断 + 标记 |
| 无标题文档退化为整文档单节 | 占比低（dehaze-doc 语料 94% 有多级标题）；截断兜底 |
| 多 child 命中同节重复注入 | 分组去重（核心设计已覆盖） |

## 7. 工作量

解析器+引擎节内化 0.5d / schema+repo 0.5d / 检索分组重组+注入 0.5d / 测试+kb_eval
验证+文档同步 1d，合计约 2.5 天。
