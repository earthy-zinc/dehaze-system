# AI 知识库模块 - 后端实现设计（检索引擎）

## 1. 文档概述

本文档描述 F-KB-004 检索引擎和 F-KB-005 知识图谱增强（远期）的后端实现。

## 2. 检索接口

### 2.1 内部检索接口

AI 对话模块通过内部接口调用检索（同步调用，不直接暴露 HTTP）：

```
SearchService.search(knowledgeBaseId, query, options)
    ↓
参数:
  - knowledgeBaseId: 指定知识库（可为空，检索所有知识库）
  - query: 用户查询文本（或 AI 对话自动提取的关键词）
  - options: { topK, threshold, filters, enableRerank, enableMMR }
    ↓
返回: List<SearchResult>
  - { chunkId, content, metadata, score, documentTitle, chunkIndex }
```

### 2.2 检索 API

对外提供 HTTP API 供前端和第三方调用：

| 路径 | 方法 | 功能描述 | 权限标识 |
|------|------|---------|---------|
| `/api/v1/kb/search` | POST | 知识库检索（支持多知识库检索） | - |
| `/api/v1/kb/{id}/retrieve/test` | POST | 检索测试（知识库管理页面的检索测试工具） | - |

## 3. 混合检索

### 3.1 混合检索编排

使用 ES 8.x 内置 `retriever` API 的 RRF（Reciprocal Rank Fusion）融合，单次查询完成向量 + 关键词混合检索，避免手写分数归一化和加权融合：

```
SearchService.hybridSearch(knowledgeBaseId, query, weight)
    ↓
调用 EmbeddingService.embed(query) → queryVector
    ↓
ES retriever 查询（单次请求）:
  - vector retriever: kNN(content_vector, queryVector), num_candidates=K*2
  - keyword retriever: multi_match(content, doc_title), standard retriever
  - 融合: RRF算法（rank_constant=60），各 retriever 权重可配
    ↓
返回 RRF 融合排序后的 Top-K 结果
    ↓
无需手写 z-score/最大最小值归一化
```

> 选用 ES 8.x RRF 而非手写加权融合：消除手动分数归一化代码（约 60 行），减少不同检索器分数不可比的误差。需要 ES ≥ 8.14（retriever/RRF API GA 版本）。

### 3.2 落地说明（多库 embedding 分组、阈值口径、缓存）

检索编排（SearchService）的工程落地要点：

- **多库 embedding 分组 + 并发检索**：多库检索时各库可能使用不同 embedding 模型
  （provider+model），向量维度不兼容。实现按 `(embedding_provider, embedding_model)`
  分组，同组库共享一次 `embed_text` 的 query 向量；再按各库 `search_strategy`
  （vector/keyword/hybrid）分派底层原语。同组内多库用 `asyncio.gather` 并发检索，
  避免多库延迟线性叠加（单库检索内部已降级返回列表，不会抛异常）。keyword 策略无需
  query 向量。
- **阈值过滤口径**（`_search_one_kb`）：
  - vector：分数为 cosine 相似度（0-1），低于库 `score_threshold` 的结果丢弃；
  - keyword：BM25 分数无界，不适用 cosine 阈值；
  - hybrid：RRF 融合分数不可比，不适用阈值（启用 rerank 时按 rerank relevance 过滤）。
- **结果缓存**：键 `kb:search:{库ID集合哈希}:{查询参数哈希}`，TTL 5 分钟。库集合排序后
  哈希（顺序无关）；命中直接返回。超时/ES 异常导致的降级空结果**不写缓存**，避免将一次
  临时降级放大为 5 分钟降级（§6 语义）；正常无匹配空结果仍可缓存。文档/库变更未接入
  跨模块缓存失效钩子，由 5 分钟自然过期兜底。内部注入接口 `search_internal`
  （无用户上下文，仅检索公共库）复用同一缓存与编排逻辑。
- **返回结构**：`{query, knowledgeBaseIds, results: [{chunkId, content, score,
  documentTitle, documentId, chunkIndex, metadata}]}`（见 §5.1）。

## 4. 检索后处理

### 4.1 Rerank 重排序

知识库启用 `enable_rerank=1` 时，检索后进行二次排序：

```
混合检索返回 Top-K × 2 结果
    ↓
RerankService.rerank(query, results)
    ↓
调用 Rerank 模型（Cross-Encoder，如 bge-reranker-v2-m3）：
  - 输入: (query, result.content) 对
  - 输出: 精细相关性分数
    ↓
按 Rerank 分数重新排序
    ↓
取 Top-K 最终结果
```

**适用条件**：知识库 `enable_rerank=1` 且 `rerank_model` 已配置。

### 4.2 MMR 多样性优化

当检索结果高度相似时，使用 MMR 算法去除冗余，保留多样性：

```
检索后处理:
  - 输入: 候选结果列表（已按分数排序）
  - 参数: λ（0-1，多样性调节因子，默认 0.5）
    ↓
MMR 算法:
  - 选择分数最高的结果加入最终列表
  - 对每个剩余候选，计算:
    MMR = λ × relevance(candidate) - (1-λ) × max(cosine(candidate, selected))
    relevance 取候选自身检索分数（候选集内归一化）——跨库 embedding 模型异构，
    单一 query 向量对不同模型的候选不可比，故用候选自身分数表达 query 相关度；
    多样性项使用候选与已选集的 embedding 向量余弦相似度
  - 选择 MMR 最高的候选加入最终列表
  - 重复直到选满 Top-K
    ↓
返回多样性排序后的结果
```

### 4.3 元数据过滤

检索前通过检索条件过滤缩小范围（过滤不参与分数计算）：按知识库、文档类型、标签、时间范围、关联算法等元数据维度过滤，仅保留满足条件的候选片段。

## 5. 检索注入接口

AI 对话模块调用检索时，返回符合 LLM prompt 注入格式的结果：

### 5.1 检索结果结构

检索结果包含：查询文本、知识库 ID、结果列表（每项含分块 ID/内容/匹配分数/来源文档标题与 ID/分块序号/元数据[页码/段落/关联算法]）。

### 5.2 LLM Prompt 注入格式

AI 对话模块将检索结果注入 LLM prompt 时的格式：

```
以下是来自知识库的相关知识片段，请参考这些知识回答问题：

[来源: 去雾算法对比手册, 第3页, 段落2.1]
RIDCP 算法基于颜色衰减先验的去雾算法，适用于非均匀雾霾场景。
典型指标 PSNR 28.5db，SSIM 0.92。
参数说明: strength(强度) 0-100, saturation(饱和度) 0-200。

[来源: 算法最佳实践, 第5页, 段落3.2]
对于夜景低光照场景的去雾处理，推荐 RIDCP 算法，
建议参数: strength=70, saturation=120。
该算法在噪声抑制方面优于 FFA-Net 和 DCP。

请基于以上知识回答用户的问题。
```

### 5.3 引用溯源展示

前端展示检索来源引用：

```
助手回复中标注引用编号 [1][2]...
回复末尾展示引用列表:
  [1] 去雾算法对比手册 - 第3页 段落2.1
  [2] 算法最佳实践 - 第5页 段落3.2
```

**引用跳转**：引用编号 [1][2] 支持点击跳转，前端根据检索结果的 `documentId + metadata.page + metadata.paragraph` 定位到来源文档原文对应位置并高亮展示，提升引用可信度与可验证性。跳转依赖解析层保留的页码/段落元数据（见后端实现-文档管理 §3.5）。

## 6. 检索超时降级

| 场景 | 处理 |
|------|------|
| 检索接口超时（默认 2s） | AI 对话降级为无知识回复（不注入知识片段，仅基于模型自身能力回答） |
| ES 不可用 | 同上，降级为无知识回复 |
| 降级告警 | 记录告警日志，前端提示"知识库检索暂不可用，回复未引用专业知识" |
| 主流程影响 | 降级不影响对话主流程，仅丢失知识增强能力 |

## 7. 召回测试工具与反馈闭环

### 7.1 召回测试工具

知识库管理页提供"召回测试"面板，将检索调试接口升级为可量化的评估工具（对应需求规格 §2.4.5）：

```
管理员在知识库管理页打开"召回测试"
    ↓
输入问题 → 调用检索接口（POST /api/v1/kb/{id}/retrieve/test）
    ↓
展示召回段落 + 相似度分数
    ↓
管理员标注"应命中段落"（must_include）→ 记录命中/未命中
    ↓
测试集管理：一组"问题 + 期望命中段落"的集合，可重复执行
    ↓
版本对比：调整分块/检索参数后重跑同一测试集
  - 对比 Recall@K（应命中段落是否在 Top-K 中）
  - 对比命中率（库外问题是否低分/空结果）
  - 输出对比报告，量化评估检索质量
```

| 能力 | 说明 |
|------|------|
| 单次召回测试 | 输入问题 → 展示召回段落 + 相似度，标注应命中段落 → 记录命中/未命中 |
| 测试集管理 | 一组"问题 + 期望命中段落"的集合，可重复执行，作为评估基线 |
| 版本对比 | 调整分块/检索参数后重跑同一测试集，对比 Recall@K 与命中率 |
| 库外问题验证 | 测试集可含"库外问题"，验证低分/空结果，配合提示词拒答 |

### 7.2 反馈闭环落地

用户点赞/点踩数据关联到具体检索片段，沉淀为"低质量片段"标记，反哺检索优化：

```
用户对 AI 回复点赞/点踩
    ↓
反馈数据关联到回复引用的检索片段（chunk_id）
    ↓
标记"低质量片段"（点踩片段）：
  - 记录到 sys_knowledge_chunk 的 metadata 或独立反馈表
  - 统计片段被点踩次数
    ↓
管理员在召回测试工具中查看被点踩片段
    ↓
针对性调整分块策略 / 清理低价值文档 / 调整检索参数
```

| 反馈项 | 说明 |
|--------|------|
| 反馈关联 | 点赞/点踩数据关联到具体检索片段（chunk_id），而非仅关联回复 |
| 低质量片段标记 | 点踩片段沉淀为"低质量片段"标记，统计被点踩次数 |
| 优化反哺 | 管理员在召回测试工具中查看被点踩片段，针对性调整分块策略或清理低价值文档 |

## 8. 知识图谱增强（F-KB-005，中期规划）

### 8.1 设计思路

参考 Microsoft GraphRAG 的"实体提取 → 社区检测 → 社区摘要"流水线，构建覆盖多模态/CV/NLP/代码分析能力域的知识图谱，检索时融合图结构信息。**中期规划**：随着算法研究持续引入论文算法、多模态、计算机视觉、自然语言处理、代码分析等能力，全局综合推理/跨文档聚合问题将常态化，知识图谱是支撑这类问题的核心能力。按三阶段渐进引入（见需求规格 §2.5.1）。

### 8.2 实体与关系定义

| 实体类型 | 说明 | 属性 |
|---------|------|------|
| Algorithm | 算法 | name, type, paper_url |
| Paper | 论文 | title, authors, year, venue |
| Task | 任务 | name, description（如"去雾"、"超分"、"检测"） |
| Scene | 场景 | name, description（如"非均匀雾霾"、"夜景低光照"） |
| Metric | 指标 | name, unit（如"PSNR"、"SSIM"、"LPIPS"） |
| Dataset | 数据集 | name, description |
| CodeModule | 代码模块 | name, language, repo |
| Experience | 经验条目 | scene, algorithm, params, metric, score |

| 关系类型 | 说明 | 来源 |
|---------|------|------|
| SUITABLE_FOR | 算法/经验适用于场景 | 算法文档、历史处理统计 |
| ACHIEVES | 算法达到指标 | 评估报告 |
| REQUIRES | 场景/算法依赖 | 知识提炼 |
| CITES | 论文引用 | 论文文档 |
| COMPARES | 算法对比 | 对比文档 |
| EVALUATED_ON | 在数据集上评估 | 评估报告 |
| IMPLEMENTS | 代码实现算法 | 代码分析 |
| DEPENDS_ON | 代码模块依赖 | 代码分析 |
| RECOMMENDS | 经验推荐算法/参数 | 经验复用闭环 |

### 8.3 三阶段实现

#### 阶段 1：结构化关系数据底座（近期）

强化 `sys_knowledge_chunk.metadata` 的实体/关系字段，检索时按关系维度过滤：

- 分块入库时同步提取实体（algorithm_id/task/scene/metric/dataset）写入 metadata
- 检索时通过元数据过滤实现关系维度查询（"只看夜景场景的算法"）
- 复用现有元数据过滤能力，成本极低，为阶段 2/3 预留数据基础

#### 阶段 2：轻量关系索引（中期）

基于 ES 的实体/关系独立索引，支持实体间关系检索：

```
实体/关系抽取（离线 LLM 批量）:
  - 从文档分块中提取实体与关系
  - 实体消歧（同一实体不同名称合并，LLM 处理）
  - 关系置信度过滤（min_relation_confidence 阈值）
    ↓
图构建（基于 ES 关系检索，不引入 Neo4j）:
  - 实体 → 节点（写入 ES，作为 kb_chunks 的扩展字段或独立关系索引）
  - 关系 → 边（以关系记录存储，复用 ES 检索能力）
    ↓
关系检索:
  - "哪些算法适用于夜景" → 按 SUITABLE_FOR 关系检索
  - "RIDCP 依赖哪些预处理模块" → 按 DEPENDS_ON 关系检索
  - 关系检索结果与向量/关键词检索结果 RRF 融合
```

#### 阶段 3：社区检测 + 社区摘要（中期偏后）

完整 GraphRAG 流水线，支撑全局综合推理：

```
社区检测（Leiden 算法，离线计算）:
  - 将紧密关联的实体聚类为社区
  - 每个社区代表一个知识领域
  - max_cluster_size 从 10 开始，根据评测结果调整
    ↓
社区摘要（LLM）:
  - 为每个社区生成自然语言摘要
  - 描述该领域的关键算法、适用场景、典型指标
    ↓
检索增强:
  - 用户查询时先检索社区摘要（全局视角）
  - 再检索具体实体（局部精度）
  - 社区摘要 + 实体详情共同注入 LLM prompt
```

### 8.4 触发条件与成本控制

- **触发条件**：全局综合推理常态化 + 知识规模突破 10 万分块 + 关系密度显著上升（见需求规格 §2.5.3）
- **成本控制**：实体抽取采用分层策略（小模型初抽 + 大模型验证），增量更新只处理新文档/受影响子图，避免重建整个图谱
- **延迟控制**：全局推理场景异步执行（离线报告/管理后台分析），实时问答仍走向量 + 关键词混合检索，规避秒级延迟

> **不引入 Neo4j 图数据库**，实体/关系基于 ES 关系检索实现，与系统架构技术栈（Elasticsearch/MySQL/Redis/MongoDB）对齐。近期优先实现向量 + 关键词混合检索 + 结构化元数据增强（阶段 1）。
