# 消息通知模块 - 后端实现设计

## 1. 文档概述

本文档描述消息通知模块的后端设计方案：分层架构、核心业务逻辑（发送幂等/模板渲染/推送决策）、缓存与定时任务、实时推送与安全设计。接口契约见 [API接口.md](./API接口.md)。

---

## 2. 架构设计

### 2.1 模块分层架构

| 层级 | 职责 |
|------|------|
| Controller | 用户端消息接口、公告管理、模板管理、通知设置 |
| Service | 消息核心逻辑（发送/查询/已读/删除）、公告、模板、通知偏好 |
| 推送分发 | 异步遍历可用渠道分发；由线程池异步执行，不经消息队列 |
| 渠道层 | 站内信、APP推送、邮件、短信四类推送渠道实现（见 §6） |
| WebSocket | 在线用户实时推送 `new_message` 事件，跨实例经 Redis Pub/Sub 广播 |
| Job | 过期消息清理、定时公告发送、免打扰延迟推送补发、未读数刷新 |

消息生成为同步落库，推送分发异步执行，两者互不阻塞：站内信写入成功即视为消息送达，外部渠道失败不回滚消息。

### 2.2 推送渠道接口（MessagePushChannel）

| 方法 | 入参 | 出参 | 说明 |
|------|------|------|------|
| getChannelType | 无 | String | 渠道类型（inbox/push/email/sms） |
| send | message, recipientId | void | 执行推送 |
| isAvailable | 无 | boolean | 渠道是否可用 |

接口不返回发送结果：渠道发送失败仅记录错误日志，不重试、不影响其他渠道（站内信已保证必达）。

## 3. 核心业务逻辑

### 3.1 消息发送流程（send）

```
业务模块调用 send（title/content 或 templateCode+variables + recipientIds）
    ↓
1. 幂等检查：bizModule 与 bizId 均非空时，按接收人查询已存在消息
   - 已存在 → 幂等返回已有 messageIds（跳过该接收人）
   - 未传幂等键 → 不防重，允许重复生成
    ↓
2. 模板渲染（templateCode 非空时）：校验模板存在且启用 → 扫描
   title_template/content_template 的 {varName} 占位符，variables 须覆盖全部占位符
   → 正则替换渲染；未使用模板时 title/content 必填
    ↓
3. 计算过期时间：alert 7 天、critical_alert 90 天、其余 30 天
    ↓
4. 逐接收人写入 sys_message（每接收人独立事务提交）
    ↓
5. 每写入一条：失效未读数缓存 → 推送 new_message 事件 → 异步分发外部渠道
```

**幂等机制**：前置查询负责提前失败，`(biz_module, biz_id, recipient_id)` 唯一约束作为并发兜底。MySQL 唯一索引对 NULL 不生效，因此仅当 bizModule 与 bizId 均非空时才具备防重能力。

### 3.2 消息列表查询（getPage/search）

- 查询范围：`recipient_id` = 当前登录用户且 `deleted=0`
- 筛选维度：getPage 按消息类型、已读状态筛选；search 按标题/正文模糊匹配
- 支持按 `create_time` 时间范围过滤，供离线增量拉取使用（见 §7）
- 排序：未读优先置顶，同已读状态下按 `create_time` 倒序

### 3.3 已读与删除

| 操作 | 实现要点 |
|------|---------|
| 消息详情 | 按 id + recipient_id 查询，越权视为不存在；仅查询，不自动标记已读（由前端显式调标记接口） |
| 标记单条已读 | 条件更新 `read_status`、`read_time`，带 recipient_id 与未读条件；影响 0 行时幂等静默成功 |
| 全部标记已读 | 按 recipient_id + 可选 type 批量更新未读，返回影响条数 |
| 删除消息 | 按 ID 列表 + 当前用户软删除（`deleted=1`，记录保留） |
| 缓存联动 | 上述操作影响行数 >0 时删除未读数缓存，由下次查询重建 |

到期消息的物理删除由定时任务执行（见 §5.2）。

### 3.4 公告管理

| 操作 | 实现要点 |
|------|---------|
| 创建 | 定时发送时间必须为未来时间；设置了发送时间则置"待发送"，否则置"草稿"，sent_count=0 |
| 编辑 | 仅草稿/待发送可编辑 |
| 发送 | 解析接收人（全体/按会员等级/指定用户）→ 接收人为空报错 → 按 500 人/批调用消息发送接口（type=announcement、bizModule=system、bizId=公告ID、priority 按重要性映射：重要 3 / 普通 2），每批独立提交 |
| 发送容错 | 单批失败不阻塞其他批次，公告保持"待发送"，由定时任务下一轮扫描重试；已成功接收人经 bizModule+bizId 幂等去重，不会重复收到 |
| 取消 | 仅待发送可取消 |
| 删除 | 按 ID 物理删除 |

### 3.5 推送决策逻辑（PushChannel）

推送分发器遍历可用渠道，PushChannel 按用户通知偏好依次决策，任一条不通过即不推送：

1. APP 推送总开关关闭（`push_enabled=0`）
2. 该消息类型在用户偏好中关闭推送（`typeChannels.{type}.push=false`）
3. 该触发模块在用户偏好中关闭推送（`moduleSwitches.{biz_module}=false`）
4. 处于免打扰时段且非严重告警（priority<4）→ 进入延迟队列 `msg:delayed_push:{userId}`，免打扰结束后补发

**免打扰时段判断**（支持跨天）：`dndStart < dndEnd` 时，当前时间落在 [dndStart, dndEnd] 内即免打扰；`dndStart ≥ dndEnd`（如 22:00-次日 08:00）时，当前时间 ≥ dndStart 或 ≤ dndEnd 即免打扰。

## 5. 缓存与定时任务

### 5.1 缓存设计

| 缓存对象 | Key 格式 | TTL | 更新策略 |
|---------|---------|------|---------|
| 未读消息数 | `msg:unread:{userId}` | count=0 → 5 分钟；count>0 → 1 小时 | 消息生成/标记已读/全部已读/删除未读消息时删除缓存；每小时全量刷新 |
| 公告缓存 | `msg:announcement` | 1 小时 | 公告发布/取消时失效 |

未读数查询为「缓存未命中则查库回填」：命中直接返回；未命中执行 COUNT，结果 >0 按 1 小时缓存，结果为 0 写入空值缓存（5 分钟）以拦截零未读用户的高频查询。Redis 不可用时降级直查数据库。

消息列表、通知偏好与消息模板均不缓存，每次直接查库。

**未读数竞态**：「全部已读置 0」与「新消息 +1」并发时可能出现角标短暂少 1，由每小时全量刷新任务兜底修正。

### 5.2 定时任务清单

| 任务 | 实现类 | 执行时机 | 说明 |
|------|--------|---------|------|
| 过期消息清理 | MessageCleanupJob | 每天凌晨 4 点 | 分批（500 条/批）物理删除 `expires_at<NOW` 的消息，循环至清完；无论是否已读、`deleted` 为 0 或 1 均清理 |
| 定时公告发送 | AnnouncementScheduleJob | 每分钟 | 扫描"待发送"且发送时间已到的公告逐条发送，兼作发送失败重试 |
| 免打扰延迟推送 | DelayedPushJob | 每分钟 | 扫描 `msg:delayed_push:*`，仍在免打扰时段则跳过，结束后弹出补发（弹出不回滚，避免重复推送） |
| 未读数缓存刷新 | UnreadCountRefreshJob | 每小时 | 扫描活跃用户重算未读数写入缓存 |

## 6. 推送渠道接入现状

| 渠道 | 实现类 | isAvailable | 说明 |
|------|--------|:---:|------|
| 站内信 | InboxChannel | ✅ | 消息已由 MessageService 写入，渠道侧仅记录日志（必达） |
| APP推送 | PushChannel | ✅ | 决策逻辑完整（总开关/类型偏好/模块开关/免打扰），`doPush` 未对接真实推送平台 |
| 邮件 | EmailChannel | ❌ | 依赖第三方邮件服务，未接入 |
| 短信 | SmsChannel | ❌ | 依赖第三方短信服务，未接入 |

### 6.1 通知偏好默认值（三端统一）

| 配置项 | 默认值 |
|--------|--------|
| pushEnabled（APP推送总开关） | true |
| dndEnabled（免打扰开关） | false |
| dndStart / dndEnd | 22:00:00 / 08:00:00 |
| typeChannels.announcement.push | true |
| typeChannels.business.push | **false** |
| typeChannels.member.push | true |
| moduleSwitches.prediction / feedback / announcement | true |

默认偏好仅覆盖 announcement/business/member 三种类型；未显式配置的类型（alert/critical_alert）推送决策时按 push=true 处理；站内信不可关闭。

留存天数、批次大小、缓存 TTL、免打扰默认时段、优先级映射均为代码常量，非配置文件可调项；定时任务频率由调度器（XXL-Job/APScheduler/cron）注册决定。

## 7. WebSocket 实时推送设计

| 项 | 说明 |
|----|------|
| 协议 | Java 端 STOMP/SockJS；Python/Go 端原生 WebSocket |
| 鉴权 | 连接时携带 Session ID（URL query 或 Cookie），服务端查询 Redis 验证 |
| 跨实例广播 | Redis Pub/Sub 频道（Java `dehaze:ws:broadcast`） |
| 消息格式 | 三端一致推送 `new_message` 事件（id/type/title/priority/createTime） |
| 投递目标 | Java `/queue/message`（任务事件走 `/queue/task`） |
| 离线补偿 | 不设服务端离线推送队列；客户端重连后按本地 `last_read_time` 经消息列表接口按时间范围增量拉取未读消息 |

WebSocket 推送与推送分发器相互独立：WebSocket 用于在线用户实时 UI 更新（角标/提示），不受用户通知偏好影响；推送分发器负责 APP 推送/邮件/短信等外部渠道，受通知偏好控制。

## 8. 安全设计

### 8.1 数据权限

| 操作 | 权限规则 |
|------|---------|
| 查看消息 | 仅能查看自己的消息，越权视为不存在 |
| 标记已读/删除 | 仅能操作自己的消息（更新条件强制带 recipient_id） |
| 通知设置 | 仅能查看/修改自己的设置 |
| 消息防篡改 | 消息生成后仅 `read_status`、`deleted` 可更新 |

### 8.2 权限校验实现

公告管理与模板编辑接口按 [API接口.md](./API接口.md) 定义的权限标识鉴权，三端分别通过 Java `@PreAuthorize`、Python `@require_permission`、Go 中间件实现。消息发送接口无独立权限标识，登录即可调用，由业务模块内部使用。

## 9. 三端实现说明

Java 端为契约定义方，Go/Python 端对齐 Java 端的接口契约与业务逻辑，三端共享契约测试保证请求/响应结构与业务行为一致。

### 9.1 Java 端

| 组件 | 实现类 |
|------|--------|
| Controller | MessageController / AnnouncementController / MessageTemplateController / NotificationSettingController |
| Service | MessageServiceImpl / AnnouncementServiceImpl / MessageTemplateServiceImpl / NotificationSettingServiceImpl |
| Dispatcher | MessagePushDispatcher（`@Async("pushTaskExecutor")`） |
| Channel | InboxChannel / PushChannel / EmailChannel / SmsChannel |
| WebSocket | WebSocketConfig / WebSocketMessageRelay（STOMP + Redis Pub/Sub 中继） |
| Job | MessageCleanupJob / AnnouncementScheduleJob / DelayedPushJob / UnreadCountRefreshJob（XXL-Job） |

### 9.2 Python 端

| 组件 | 实现文件 |
|------|---------|
| Router | `app/router/message.py` / `announcement.py` / `message_template.py` / `notification_setting.py` |
| Service | `app/service/message_service.py` / `announcement_service.py` / `message_template_service.py` / `notification_setting_service.py` |
| WebSocket | `app/service/websocket_service.py`（Redis Pub/Sub 跨实例投递） |

### 9.3 Go 端

| 组件 | 实现文件 |
|------|---------|
| Handler/Service | `internal/service/message/`（message_handler / message_service） |
| Repository | `message_repository.go` |
| WebSocket | `pkg/websocket/`（连接管理 + Redis Pub/Sub） |
| Job | 过期清理 / 未读数刷新定时任务 |

### 9.4 跨模块协作契约

业务模块通过消息发送接口接入，关键契约字段：

| 字段 | 用途 | 取值示例 |
|------|------|------|
| bizModule | 触发模块标识；与 bizId 组合作为幂等键，同时驱动模块级推送开关（`moduleSwitches`） | `member`/`feedback`/`prediction`/`order`/`system` |
| bizId | 业务事件唯一标识；同一业务事件发给不同接收人不去重 | 会员变更记录ID/反馈ID/任务ID/订单ID/公告ID |
| templateCode | 消息模板编码，驱动标题/内容模板渲染；不使用模板时传 title/content | `member_upgrade`/`feedback_low_score` |

已接入的业务场景：

| bizModule | 触发场景 | 消息类型 | bizId 取值 |
|-----------|---------|---------|-----------|
| member | 会员升级/降级/到期预警 | member | 会员等级变更记录 ID |
| feedback | 低分评价告警 | alert / critical_alert | 反馈记录 ID |
| system | 系统公告发布 | announcement | 公告 ID |
