## 2. 架构设计

### 2.1 模块分层架构

```
Controller 层（dehaze-java / dehaze-go / dehaze-python）
└── RecommendationController / recommendation router
    ├── POST   /api/v1/recommendations/analyze     # 图像特征分析
    ├── GET    /api/v1/recommendations/algorithms  # 获取算法推荐
    ├── POST   /api/v1/recommendations/feedback    # 推荐反馈
    ├── GET    /api/v1/recommendations/rules       # 规则查询（管理员）
    ├── PUT    /api/v1/recommendations/rules       # 规则新增/更新（管理员）
    └── GET    /api/v1/recommendations/report      # 效果报表（管理员）

Service 层
└── RecommendationServiceImpl / RecommendationService（单服务类承载全部逻辑）
    ├── analyze()                      # 图像特征分析（Java/Go: 调用 Python 服务提取真实特征；Python: 本端实现）
    ├── getAlgorithmRecommendations()  # 场景规则匹配 + 推荐记录落库
    ├── submitFeedback()               # 显式反馈写入
    ├── getRules() / updateRule()      # 规则查询/新增/更新 + 缓存刷新
    └── getReport()                    # 推荐效果统计
```

> 单一服务类承载全部逻辑。Java 端 `analyze()` 通过 `PythonAlgorithmClient.analyzeImage` 调用 Python 图像特征分析服务获取真实特征；Go 端通过 `pkg/algorithm.Client.AnalyzeImage` 调用同一服务；Python 端本端即实现。Java/Go 端 Python 服务不可用时均返回错误，不降级为伪特征。

### 2.2 核心组件职责

| 组件 | 职责描述 | 关键能力 |
|------|---------|---------|
| analyze | 图像特征分析 | 校验 imageUrl 格式；Java/Go 调用 Python 服务提取真实 7 维特征；Python 服务不可用时返回错误，不降级伪特征 |
| getAlgorithmRecommendations | 算法推荐 | 已发布算法候选池、启用规则匹配、匹配度计算、推荐记录落库、回填 recommendationId |
| submitFeedback | 推荐反馈 | 按 recommendationId 校验推荐记录、写入 feedback（1 有用/2 无用） |
| getRules/updateRule | 规则管理 | 规则查询（weight 升序）、新增（id=0）/更新、权重校验、内存缓存刷新 |
| getReport | 效果度量 | 推荐总量/采纳率/满意度/覆盖率/冷启动成功率/按日趋势统计 |

## 3. 数据模型设计

> 表结构与字段定义详见 [03-数据库设计.md](../../../02-系统架构/03-数据库设计.md)。本节仅说明实际写入情况与设计决策。

### 3.1 推荐记录（sys_recommendation）

**设计决策**：推荐记录为只追加，不使用逻辑删除，过期数据通过定时任务物理清理。`top_algorithms` 和 `analysis_result` 使用 JSON 存储避免拆子表。

**实际写入情况**：

| 字段 | 写入情况 |
|------|---------|
| user_id | 当前登录用户 ID（未登录回退系统用户） |
| image_md5 | 分析接口返回的图像 MD5（Java/Go: 由 Python 特征分析服务计算返回） |
| target_type | 固定 "algorithm" |
| top_algorithms | 推荐算法列表（Top 3：algorithmId/algorithmName/matchScore） |
| analysis_result | 当前不写入（Analyze 结果返回客户端但不持久化到推荐记录） |
| feedback | 0=未反馈；1=有用；2=无用 |
| adopted_algorithm_id | 当前不写入 |

### 3.2 推荐规则（sys_recommendation_rule）

**设计决策**：`enabled` 为运行时启用/禁用开关（1=启用，0=禁用）；`deleted` 为逻辑删除标记，三端查询均过滤 `deleted = 0`。当前模块仅暴露启用/禁用（enabled），未暴露显式删除规则的接口。

## 4. 核心业务流程

### 4.1 图像特征分析（analyze）

```
接收 AnalyzeForm（imageId / imageUrl）
    ↓
resolveImageUrl：
  - imageId > 0 → 抛业务异常"imageId方式暂不支持，请使用imageUrl"（A0401）
  - imageUrl 为空 → 抛参数错误（A0400）
    ↓
validateImageFormat：校验扩展名（jpg/jpeg/png/webp/bmp/tiff/tif，忽略 query string）
  - 不合法 → 抛 A0701 文件格式不支持
    ↓
Java 端：调用 PythonAlgorithmClient.analyzeImage(imageUrl)
Go 端：调用 pkg/algorithm.Client.AnalyzeImage(imageUrl)
  → HTTP POST /api/v1/recommendations/analyze 到 Python 服务
  → 返回真实 7 维特征（PyTorch 场景分类 + OpenCV 暗通道/直方图/边缘检测）
  → Python 服务不可用 → 抛业务异常（Java: C0001 / Go: B0001），不降级为伪特征
    ↓
映射为 ImageFeatureAnalysisVO 返回（imageMd5 等 7 维特征）
```

> Java/Go 端特征基于真实图像内容，由 Python 服务提取；Python 端本端直接调用特征分析实现。三端 `analyze` 返回真实图像特征，结果一致。

### 4.2 算法推荐（getAlgorithmRecommendations）

```
输入 analysisId / imageMd5
    ↓
1. 候选池：已发布算法（status=4）
2. 启用规则：Java/Go 从内存缓存加载启用规则（enabled=1 且 deleted=0，缓存为空时回源并回填）；Python 实时查询
3. 场景确定：
   - analysisId > 0 → 查推荐记录 analysis_result.sceneType（当前不写入，落空）
   - imageMd5 → 查最近推荐记录 analysis_result.sceneType（当前不写入，落空）
   - 默认 "urban"
4. 规则匹配：scene_type 相同 → 按 weight 降序 → 聚合 algorithm_ids 候选集
5. 候选过滤：候选集 ∩ 已发布算法
6. 匹配度：该算法在匹配规则中的最高权重（min(100, maxWeight)）
7. 构建 VO：algorithmId/algorithmName/matchScore/reason（场景模板）/effectDescription（模板）
   - rating / estimatedTime 当前置 null，待真实评分与耗时数据采集后填充
8. 排序：matchScore 降序 → 截取 TOP_N（3）
9. 落库：写入 sys_recommendation（target_type="algorithm"、top_algorithms、feedback=0）
10. 回填 recommendationId 到各 VO
    ↓
返回推荐列表
```

**推荐理由模板**（`算法名 + 场景理由`）：

| sceneType | 理由模板 |
|-----------|---------|
| urban | 处理速度快，对城市雾霾效果出色 |
| landscape | 在自然场景下表现稳定，色彩还原度高 |
| building | 深度模型，对建筑场景处理能力强 |
| night | 低光照增强组合，避免过度暗化 |
| backlight | HDR预处理提升暗部细节 |
| indoor | 室内场景适配，细节保留好 |

> **落库与并发**：每次调用均写入新记录（非幂等）。同用户、同 imageMd5 短时间内的重复请求会产生多条推荐记录，需由调用方防抖去重，避免重复落库。

### 4.3 推荐反馈（submitFeedback）

```
接收 recommendationId + useful
    ↓
按 recommendationId 查询推荐记录
  - 不存在 → 抛 A0401
    ↓
feedback = useful ? 1 : 2
更新记录
```

> 三端均严格按 recommendationId 校验推荐记录，不存在按 algorithmId 回退匹配的兜底逻辑。采纳（adopted_algorithm_id）当前不写入。

### 4.4 规则管理（getRules / updateRule）

**getRules**：查询全部规则（deleted=0），按 weight 升序返回。

**updateRule**：
```
id 为 0 → 新增（ruleName/sceneType/algorithmIds/weight/enabled）
id 非 0 → 更新（规则不存在 → A0401）
权重校验：null 或 <0 或 >100 → A0500"规则权重必须在0-100之间"
Java/Go 端在新增/更新后刷新内存规则缓存（Python 端无缓存，无需刷新）
```

### 4.5 效果报表（getReport）

```
输入 startDate / endDate（yyyy-MM-dd，可空）
    ↓
统计：
- totalRecommendations = COUNT(全部推荐记录)
- usefulCount = COUNT(feedback=1)
- feedbackTotal = COUNT(feedback!=0)
- adoptedDistinct = COUNT(DISTINCT adopted_algorithm_id)（当前恒 0）
- publishedCount = COUNT(已发布算法)
    ↓
指标：
- adoptionRate = usefulCount / feedbackTotal（无反馈则 0）
- satisfactionRate = adoptionRate（简化，有用即满意）
- coverageRate = adoptedDistinct / publishedCount（当前恒 0）
- coldStartSuccessRate = 0.0（无冷启动机制）
- trend = 按日采纳率（date + adoptionRate）
```

## 5. 推荐策略

### 5.1 冷启动策略

当前无冷启动机制，新算法通过规则配置加入候选集后即可被推荐。

### 5.2 推荐结果字段

rating/estimatedTime 字段置 null（无硬编码假数据），待真实数据采集后填充。

| 字段 | 值 | 说明 |
|------|-----|------|
| rating | null | 待真实评分数据采集后填充 |
| estimatedTime | null | 待真实处理耗时数据采集后填充（毫秒） |
| effectDescription | "该算法在{scene}场景下表现稳定" | 模板 |
| TOP_N | 3 | 常量，不可配置 |

### 6.2 与 Python 算法服务的集成

| 端 | 集成状态 | 说明 |

## 7. 推荐效果度量

| 指标 | 实际计算方式 | 目标值 | 说明 |
|------|---------|--------|------|
| 推荐采纳率 | useful / feedbackTotal | ≥ 40% | 以"有用"反馈近似采纳 |
| 推荐满意度 | = 采纳率（简化） | ≥ 70% | 有用即满意 |
| 推荐覆盖率 | adoptedDistinct / publishedCount | ≥ 60% | 当前恒 0（采纳未记录） |
| 冷启动成功率 | 0.0 | ≥ 3 次 | 无冷启动机制 |
| 趋势 | 按日采纳率 | - | 报表趋势图数据 |

## 8. 缓存设计

| 缓存对象 | 实现 | 更新策略 |
|---------|------|---------|
| 启用规则（Java 端） | `CopyOnWriteArrayList` 内存缓存（enabled=1 且 deleted=0） | updateRule 后全量刷新 |
| 启用规则（Go 端） | `ruleCache` 切片 + `sync.RWMutex` 内存缓存，读时双检（缓存为空则回源并回填） | updateRule 后全量刷新 |
| 启用规则（Python 端） | 无缓存，实时查询 | - |

> 当前仅缓存启用规则；图像特征（image_md5）、算法评分、用户偏好画像等均未缓存。
