# 套餐管理模块 - 后端实现设计

## 1. 文档概述

本文档描述套餐管理模块（平台**商品中心**）的后端实现方案，包括商品类型模型、数据传输对象、服务层设计、核心业务逻辑（商品管理 / 价格计算 / 促销活动 / 优惠券 / 销售统计）与缓存设计。Java/Go/Python 三后端 API 契约完全一致（Java 权威，Go/Python 对齐）。

- **需求规格**：[需求规格.md](./需求规格.md)
- **API 接口**：[API接口.md](./API接口.md)
- **数据库设计**：[02-系统架构/03-数据库设计.md](../../../02-系统架构/03-数据库设计.md) §4.5；表结构以 `config/sql/schema/sys_package.sql`、`sys_promotion_package.sql`、`sys_promotion.sql`、`sys_coupon.sql`、`sys_user_coupon.sql` 为准

**模块边界**：本模块是商品定义与售卖中心，覆盖商品的类型、定价、营销、上下架与销售统计，**不实现履约**：

| 交易环节 | 承接模块 |
|---------|---------|
| 商品交易（订单创建/支付/退款/自动续费） | [订单管理/后端实现.md](../订单管理/后端实现.md) |
| 会员卡履约（等级变更/权益生效/成长值） | [会员管理/后端实现.md](../会员管理/后端实现.md) |
| 积分卡履约（积分到账/流水） | [AI计费管理/后端实现.md](../AI计费管理/后端实现.md) |

## 2. 商品类型模型

### 2.1 商品类型

商品是"打包售卖"的抽象，通过 `package_type` 区分履约目标，**创建后不可修改**：

| 商品类型 | 编码 | 差异化字段 | 履约目标 |
|---------|------|-----------|---------|
| **会员卡** | `vip` | 等级/周期/有效期/权益覆盖 | 会员等级与权益（会员管理模块） |
| **积分卡** | `credit` | 可得积分 | 积分余额到账（AI 计费模块，AI 加量包） |

- 会员卡字段：`levelCode`（等级）、`period`（计费周期）、`periodDays`（有效期天数）、`benefitOverrides`（权益覆盖项，JSON）
- 积分卡字段：`creditAmount`（可得积分）；等级/周期/有效期/权益覆盖项均为 NULL，无周期/有效期/权益覆盖概念
- 两类型共用：名称/原价/促销价/描述/排序值/上下架状态/销量

### 2.2 积分卡定价锚点

积分卡以标准兑换率（**1 元 = 100 积分**）为衡量锚：档位可在此锚上做**量价优惠**（大额档位单价更低，通过促销价体现），鼓励大额加购。兑换率锚仅作档位设计与用户比价参考，**不构成定价硬约束**（后端不做 1:100 强校验）。

### 2.3 通用能力

定价（原价+促销价）、营销（促销活动与优惠券适用于**任意商品类型**）、价格快照、上下架、销售统计（含按商品类型维度）均为商品通用能力，不因类型分叉实现。

### 3.5 展示指标计算策略

三端统一：

| 指标 | 适用类型 | 计算方式 |
|------|---------|---------|
| 日均价格 | 会员卡 | `dailyPrice = (2 × salePrice + periodDays) / (2 × periodDays)`（整数运算四舍五入到分）；`periodDays ≤ 0` 返回 0 |
| 每积分单价 | 积分卡 | `creditUnitPrice = salePrice / creditAmount`（整数运算向下取整到分，单位：分/积分）；`creditAmount ≤ 0` 返回 0 |

### 3.6 计费周期显示名称

三端统一映射：`monthly → 月卡`、`quarterly → 季卡`、`yearly → 年卡`。

## 5. 核心业务逻辑

### 5.1 商品新增逻辑

1. **类型校验**：packageType 必填且为 vip/credit（否则"商品类型非法"）
2. **参数校验**：促销价 ≤ 原价（否则"促销价不能高于原价"）；按类型差异化——会员卡校验等级/周期（monthly/quarterly/yearly，否则"计费周期非法"）/有效期天数（1-365）；积分卡校验可得积分 > 0（否则"积分卡可得积分必须大于0"），等级/周期/有效期天数为 NULL 不校验
3. **名称唯一校验**：查询同名记录（**含软删行**），命中即抛"商品名称已被历史记录占用，无法重复创建"
4. **默认状态**：`status` 缺省为 0（下架）
5. **销量初始化**：sales_count = 0
6. **权益覆盖序列化**：benefit_overrides 存 JSON（会员卡）
7. **缓存失效**：删除在售列表缓存

### 5.2 商品修改逻辑

1. 存在性校验（不存在抛"商品不存在"）
2. **类型锁定**：packageType 以库中值为准，修改请求携带的 packageType 被忽略（**创建后不可修改**，避免履约语义错乱）
3. 参数校验（同新增，按库中商品类型校验对应差异化字段）
4. 名称唯一校验：**仅当名称发生变更时**查重
5. 字段更新：按商品类型更新差异化字段——会员卡更新 levelCode/period/periodDays/benefitOverrides；积分卡更新 creditAmount；两类共用 name/originalPrice/salePrice/description/sort（sort 仅传入时更新）
6. **忽略 form.status**：上下架状态只能通过 `updateStatus` 接口修改
7. 缓存失效：删除详情缓存

### 5.3 商品上下架逻辑

1. 存在性校验
2. **下架促销校验（事务内）**：status=0 时开启事务，在事务内查询进行中活动（promotion.status=1 且当前时间在活动期），存在则抛"商品参与进行中促销活动，无法下架"；校验通过后于同一事务内更新 status，避免校验与更新之间存在活动绑定导致的 TOCTOU 竞态
3. 缓存失效

### 5.4 商品删除逻辑

1. 存在性校验（单个校验，任一不存在即抛）
2. **订单关联校验**：统计该商品关联的订单实体记录数，>0 抛"商品已存在订单，无法删除"
3. 逻辑删除（deleted=1）
4. 缓存失效

### 5.5 价格计算逻辑（calculatePrice）

只读预览接口，适用全部商品类型，按以下步骤计算应付金额：

1. **读取商品促销价**：以商品促销价作为计算基数。
2. **新用户专享校验**：若商品关联 new_user 类型活动，校验购买者无历史付费订单，否则抛"该商品仅限新用户购买"。
3. **促销折扣计算**：遍历促销-商品关联实体中 status=1 且时间有效的活动，按活动类型计算折扣——percent 按 `salePrice × discount_value / 100`、fixed 按固定金额、full_reduction 按满减门槛（多档位取命中最高档）；同时段多活动不叠加，取最大折扣值为 discount_amount。
4. **优惠券抵扣**（userCouponId 非空时）：校验券实例归属本人且状态为未使用/已锁定、模板启用且适用商品包含当前商品（含按商品类型限定）、有效期未过；按类型抵扣——full_reduction 满减、discount 比例、no_threshold 面值；trial 类型不走价格计算，直接激活权益（仅会员卡）。抵扣金额超过促销后价时截断为促销后价。
5. **计算应付金额**：应付金额 = 促销价 - 促销折扣 - 优惠券抵扣，结果为负时按 0 处理。
6. **返回计算明细**：包含促销价、折扣明细、优惠券抵扣、应付金额与商品 ID/类型，供前端预览展示。

> **价格快照与下单一致性**：calculatePrice 仅用于前端预览；订单创建时须在**事务内重新调用同一计算逻辑**生成明细，并将计算明细与商品 ID/类型/等级/周期/有效期/可得积分写入订单快照字段（积分卡订单记录 creditAmount），支付按快照金额收款（见 [订单管理后端实现](../订单管理/后端实现.md)）。会员卡续费叠加校验最大有效期 1095 天，超限拒绝；积分卡无有效期，不参与续费叠加。

### 5.6 优惠券领取逻辑（receive）

1. **模板校验**：券存在且启用（status=1）
2. **有效期校验**：fixed 类型且当前时间超过 valid_end → 已过期
3. **频率限制**：Redis INCR `coupon:receive:rate:{userId}`（限频 5 次/60 秒，可配置），超限抛限流
4. **限领校验**：用户已领数量 < per_user_limit，否则抛"超过每人限领数量"
5. **库存乐观锁**：条件更新 `issued_qty = issued_qty + 1`（status=1 且总量不限或未领完），0 行影响抛"优惠券已领完"
6. **生成实例**：插入 sys_user_coupon，计算 expire_time（relative → receive_time + valid_days；fixed → valid_end）
7. **事务保证**：库存扣减与实例生成同一事务

### 5.7 批量发放逻辑（batchDistribute）

1. 校验券存在且启用
2. **解析目标用户**：all（全部启用用户）/ level（指定等级会员）/ users（指定用户）
3. **分批处理**：目标用户按 500/批分页加载，每批独立事务执行发放（避免长事务锁竞争）；"all" 场景异步执行，接口立即返回任务 ID，结果通过任务查询获取
4. 逐用户发放：重复执行领取逻辑中的限领/库存校验，单用户失败记 failCount 不中断
5. 返回成功/失败数量

### 5.8 销售统计逻辑（getSalesStats）

1. **订单过滤**：仅统计 status in (2,3)（已支付/已完成）的订单，排除退款中/已退款
2. **总额**：totalSales = 订单数；totalRevenue = SUM(paid_amount)
3. **商品维度**：按 package_id 分组统计销量与实付金额
4. **商品类型维度**：按订单冗余的 package_type 分组（会员卡 / 积分卡各自销量、销售额）
5. **等级维度**：按订单 package_level 分组，等级名称关联权益配置
6. **周期维度**：JOIN 商品表按 period 分组（月/季/年，会员卡）
7. **优惠券统计**：totalIssued = Σissued_qty、totalUsed = Σused_qty、usageRate = used / issued（无发放时 0）

## 6. 缓存设计

| 缓存对象 | 缓存 Key | 过期时间 | 实现端 |
|---------|---------|---------|--------|
| 在售商品列表 | package:onsale | 5 分钟 | Python 端 |
| 商品详情 | package:detail:{id} | 10 分钟 | Python 端 |
| 缓存失效 | 商品变更或关联促销活动变更时删除对应 Key | - | Python 端（Java 端无商品缓存） |

> **说明**：Java 端商品查询无缓存（直查数据库）；Python 端缓存不可用时通过 Redis 降级回退逻辑直查。**无**促销活动/用户优惠券缓存。

## 7. 安全设计

| 防护项 | 实现方式 |
|--------|---------|
| 商品类型锁定 | packageType 创建后不可修改（修改请求忽略该字段），避免会员卡/积分卡履约语义错乱 |
| 商品上下架控制 | 上下架状态只能通过 updateStatus 接口修改（save/update 忽略 form.status）；下架前事务内校验进行中促销活动，存在则拒绝（避免 TOCTOU 竞态）；下架商品不可购买（getDetail 抛"商品已下架"，listOnSale 仅返回 status=1） |
| 价格一致性校验 | calculatePrice 仅用于前端预览；订单创建时在事务内重新调用同一计算逻辑生成价格快照，支付按快照金额收款，不信任前端传入金额；价格修改不影响已生成订单（订单冗余存储商品名称/类型/价格） |
| 优惠券库存扣减 | 领取时条件更新 issued_qty，0 行影响抛"优惠券已领完"；库存扣减与实例生成同一事务 |
| 优惠券防刷 | 领取频率限制（Redis INCR，5 次/60 秒，可配置）+ 每人限领数量校验 |
| 新用户专享校验 | 购买 new_user 活动关联商品时校验购买者无历史付费订单，非新用户抛"该商品仅限新用户购买" |
| 后台权限控制 | 商品/优惠券/促销后台管理仅管理员可操作（package:* 权限标识） |

| coupon.receive-rate-limit | 优惠券领取频率限制（次/窗口） | 5 |
| coupon.receive-rate-window | 领取限频窗口（秒） | 60 |

> 商品/优惠券/促销的其余规则为代码常量（如商品类型枚举、计费周期枚举、促销折扣计算），非配置文件可调项。
