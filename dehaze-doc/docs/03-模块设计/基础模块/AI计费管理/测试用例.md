## 3. 测试前置

### 3.1 测试数据

| 数据类型 | 准备内容 | 说明 |
|---------|---------|------|
| **VIP 等级用户** | 4 个测试用户（普通/VIP1/VIP2/SVIP），前缀 `test_billing_` | 各等级已分配对应日/月限额 |
| **模型配置数据** | 3 个模型（含不同输入/输出/缓存计费比例，含降级链配置） | 用于计费比例与降级计费测试 |
| **配额初始值** | 按测试用例需要预置日/月配额已用值 | 每次测试前设置初始值 |

### 3.2 数据清理策略

- 测试用户前缀 `test_billing_` 标识，测试结束后按前缀清理计费记录与配额缓存
- 不退还不清理配额（数据由定时任务处理）
- 测试消息在测试结束后级联删除

### 3.3 测试范围

**包含的功能点：**
- F-MB-001：积分计量（基本换算、缓存折扣、降级计费、工具/子智能体计费分离）
- F-MB-002：配额管理（日/月限额、预扣实扣、差额退补、并发扣减、配额重置）
- F-MB-003：计费预估
- F-MB-004：异常检测与告警

**不包含的功能点：**
- 管理员计费统计仪表盘（管理端功能，暂未实现）
- 第三方模型供应商账单对账（未实现功能）

## 4. 用例清单

### 4.1 积分计量 (F-MB-001)

| 用例ID | 场景 | 前置条件 | 输入 | 期望输出 | 优先级 |
|--------|------|---------|------|---------|--------|
| T-BL-001 | Token按模型计费比例正确换算为积分 | 用户已登录，选择gpt-4o模型（inputRate=1.0, outputRate=4.0, cachedRate=0.5） | 发送消息"什么是暗通道先验？"；LLM返回inputTokens=1000, cachedInputTokens=200, outputTokens=500 | sys_ai_message.credits=1000×1.0+200×0.5+500×4.0=3100；sys_ai_billing.credits=3100 | P0 |
| T-BL-002 | 不同模型计费比例不同 | 同一用户发送相同消息"什么是PSNR？"，分别用gpt-4o和gpt-4o-mini | 两条消息各1000 input + 500 output | gpt-4o credits=1000×1.0+500×4.0=3000 >> gpt-4o-mini credits=1000×0.2+500×0.5=450 | P0 |
| T-BL-003 | 缓存命中按折扣价计费，credits_saved正确计算 | 首条消息已建立缓存前缀（system_prompt+工具定义）；第二条消息发送 | 第二条消息"RIDCP适用场景"；cachedInputTokens=200 | credits_saved=200×(1.0-0.5)=100；credits=(inputTokens×inputRate)+(cached×cachedRate)+(output×outputRate) | P0 |
| T-BL-004 | 模型不支持Prompt Cache时cached=0, saved=0 | 选择supports_prompt_cache=0的模型simple-model | 发送消息 | cached_input_tokens=0；credits_saved=0 | P1 |
| T-BL-005 | 主模型降级按实际降级模型计费 | gpt-4o（outputRate=4.0）fallback→gpt-4o-mini（outputRate=0.5）；Mock gpt-4o返回429 | 用户选择gpt-4o发送消息，触发降级 | sys_ai_billing.model="gpt-4o-mini"；actual_model="gpt-4o"；credits按gpt-4o-mini比例计算 | P0 |
| T-BL-006 | 多级降级A→B→C，按最终成功模型计费 | A（fallback→B），B（fallback→C）；Mock A和B返回5xx，C成功 | 发送消息 | model="C"；actual_model="A"；credits按C的计费比例 | P1 |
| T-BL-007 | 降级链全部失败不计费 | 所有模型（含fallback链）全部返回5xx | 发送消息 | 无计费记录或credits=0；配额恢复发送前水平 | P1 |
| T-BL-008 | 工具调用中的LLM Token分离记录 | 发送需要工具调用的消息"帮这张图去雾" | ReAct循环产生多步推理 | sys_ai_billing中至少有一条bill_type="message"；若ReAct observe调用LLM则有bill_type="tool_llm"记录；tool_credits>0 | P0 |
| T-BL-009 | 子智能体独立计费+主Agent汇总 | 发送触发2个子智能体并行执行的消息 | 两条子智能体各自LLM调用 | bill_type="subagent"记录数=2；主Agent消息credits=SUM(子智能体credits)+主Agent自身credits；配额扣减以汇总credits为准 | P0 |

## 5. 关键边界与异常场景

| 场景 | 测试点 | 期望行为 |
|------|--------|---------|
| **计费比例变更** | 管理员更新sys_ai_model.inputRate，缓存过期后生效 | 缓存过期后新消息使用更新后的计费比例，旧消息credits不变 |
| **计费比例缓存失效** | Redis不可用时查询计费比例 | 降级直接查询MySQL，响应时间<100ms |
| **配额缓存不可用** | Redis宕机 | 降级查询MySQL + 内存计数器，继续正常服务（最多1秒延迟） |
| **LLM调用异常时预扣退还** | 发送消息后LLM网络超时 | 预扣1,000→LLM失败→退还1,000→消息status=3→sys_ai_message.credits=0 |
| **用户中途取消流式计费** | 发送消息LLM生成约300 token后点击停止 | credits=inputTokens×inputRate+300×outputRate（已生成token按实际计费） |
| **VIP降级后超额暂停** | 用户VIP到期降级后已用量超过新限额 | 下次发送消息时quota校验失败，提示配额已达上限（需等待重置） |
| **跨月份配额查询** | 1月31日23:59和2月1日00:01的quota key不同 | 跨月正确切换Redis key，查询到对应月份的配额已用 |
| **大量计费记录查询** | 单个用户有100,000+条计费记录 | 分页查询响应时间<500ms |

## 6. 性能与并发测试

### 6.1 关键操作性能目标

| 指标 | 目标值 | 测试方法 |
|------|--------|---------|
| **配额校验响应时间** | <50ms | Redis读取+阈值判断 |
| **预扣操作响应时间** | <100ms | Redis DECR×2（日+月）+ 阈值检查 |
| **实扣操作响应时间** | <100ms | Redis INCR差额 + MySQL insert |
| **积分换算响应时间** | <10ms | 本地计算（乘法+加法） |
| **计费记录写入响应时间** | <200ms | MySQL insert single row |
| **计费预估响应时间** | <50ms | Redis读取历史Token均值 + tiktoken编码 |

### 6.2 并发场景

| 场景 | 并发数 | 验证点 |
|------|--------|--------|
| **并发配额预扣** | 10请求/用户 | Redis DECR原子性，不超扣，后续请求正确被拒绝 |
| **并发差额退还** | 5请求/用户 | Redis INCR原子性，退还不丢（不会少退） |
| **并发计费写入** | 20请求 | MySQL insert正确，每条记录credits/inputTokens/outputTokens配对正确 |
| **并发配额查询** | 100请求 | 响应稳定，无超时错误 |

### 6.3 配额缓存同步验证

| 场景 | 验证点 | 期望行为 |
|------|--------|---------|
| **预扣后立即查询** | Redis配额已用+预估 | Redis已用立即反映预扣值 |
| **实扣后立即查询** | Redis配额已用+actual-预估 | Redis已用立即反映实扣后的正确值（差额退补） |
| **Redis宕机降级查询MySQL** | MySQL中近3次计费记录+sum | 降级后配额已用与Redis恢复前差值<一次消息的credit |

## 7. 安全性测试

| 测试项 | 验证方式 | 预期结果 |
|--------|---------|---------|
| **用户配额隔离** | 用户A的配额扣减不应影响用户B | 用户B的Redis配额key不变化 |
| **手动绕过配额** | 直接调用LLM不经过计费模块 | 被API网关拦截，未通过计费模块的调用拒绝 |
| **预扣负值注入** | 传入负数预估消耗 | 被校验拒绝，预估消耗必须>0 |
| **Redis配额篡改** | 直接SET Redis配额值 | Redis密码保护，外部不可访问 |

## 8. 数据一致性测试

### 8.1 计费记录一致性

| 场景 | 验证点 | 期望行为 |
|------|--------|---------|
| **消息实际credits与配额扣减一致** | sys_ai_message.credits vs sys_ai_billing.quota_consumed | 两者相等 |
| **消息totalTokens与token三字段一致** | sys_ai_billing.input+output vs 消息展示total | 一致 |
| **工具调用token分离正确** | tool_llm类记录的credits不重复计入message类记录 | message类credits+tool_llm类credits+subagent类credits=会话总消耗 |
| **降级不丢计费记录** | 降级链中每个实际执行的模型都有计费记录 | 最终成功的那一级模型有计费记录，前N-1级无（未实际执行LLM调用） |

### 8.2 事务回滚测试

| 场景 | 触发条件 | 验证点 |
|------|---------|--------|
| **MySQL写入失败** | 模拟sys_ai_billing insert失败 | 配额已扣不退（不一致状态），异常告警触发；重试补偿后恢复一致 |
| **Redis操作失败** | 模拟Redis DECR失败临时不可用 | 降级查询MySQL，不丢失配额信息 |

## 9. 高风险用例标注

以下用例若实现错误可能导致**财务损失**（少扣/多扣积分），被标记为高风险，在每次发布前必须全部通过：

| 用例ID | 风险说明 |
|--------|---------|
| T-BL-001 | 积分换算错误→全平台用户计费批量偏差 |
| T-BL-005 | 降级计费错误→用户为服务降级多付积分 |
| T-BL-013 | 差额退还错误→用户多付积分不可撤回 |
| T-BL-016 | 并发超扣→单用户配额被扣超过限额，财务损失 |
| T-BL-019 | VIP升级后quota refresh失败→付费用户权益不生效 |
