# AI 计费管理模块 - 后端实现设计

## 1. 文档概述

本文档描述 AI 计费管理模块的后端实现，包括积分计量与换算、配额与余额双控的预扣实扣、多步推理滚动预算、子智能体配额协调、欠费熔断、异常检测告警、账单生成与跨模块协作。

> 数据模型（sys_ai_billing、sys_ai_credit_log、credits_balance 字段）详见 [02-系统架构/03-数据库设计.md](../../../02-系统架构/03-数据库设计.md) §4.7，本文档不重复定义表结构。

## 2. 架构设计

### 2.1 分层架构

```
Controller 层
├── BillingController           # 配额查询、计费明细查询
├── BillingStatController       # 计费统计（管理员）
└── BillController              # 账单查询与下载

Service 层
├── BillingService              # 计费总入口（计量 + 预扣/实扣协调 + 记录）
├── QuotaService                # 配额管理（预扣/实扣/退还/查询，日/月限额）
├── EstimateService             # 积分预估（输入/输出 Token 预估，应用预估系数）
├── BalanceService              # 余额账户管理（预扣/实扣/回补，Redis 原子 + MySQL 乐观锁）
├── RechargeService             # 充值与赠送（积分包/VIP赠送/试用/管理员调整）
├── RefundService               # 退款补偿（审核/余额回补/流水）
├── BillingRecordService        # 计费记录 CRUD 与多维查询
├── BillingStatService          # 计费统计（按用户/模型/降级/缓存维度）
├── BillService                 # 月结账单生成与查询
└── BillingAnomalyService       # 异常检测与告警

内部组件
├── QuotaCache                  # Redis 配额缓存（日/月限额，原子操作）
├── BalanceCache                # Redis 余额缓存（预扣/实扣原子操作 + 欠费标记）
├── RateProvider                # 计费比例查询（sys_ai_model 只读缓存，表归 AI 对话模块）
└── AnomalyDetector             # 异常规则引擎
```

### 2.2 核心组件职责

| 组件 | 职责 |
|------|------|
| BillingService | 计费总入口：计量（Token→积分）→ 预扣（配额+余额）→ 实扣（差额退补）→ 记录（sys_ai_billing）；多步推理滚动预算与子智能体配额协调 |
| QuotaService | 配额原子操作（Redis INCR/DECR/Lua 脚本）、日/月限额校验、预扣/退还 |
| EstimateService | 基于历史 Token + 当前消息长度预估本次积分消耗（当前消息 Token 应用 estimate-input-factor 系数） |
| BalanceService | 余额账户预扣/实扣/回补（Redis 原子 + MySQL credits_balance 乐观锁 CAS）；欠费标记管理 |
| RechargeService | 积分包购买、VIP 按月赠送、新用户试用赠送、管理员手动调整；充值到账后清除欠费标记 |
| RefundService | 误扣退款审核、余额回补、流水记录（关联原计费记录） |
| BillingRecordService | 计费记录 CRUD、按用户/会话/消息/类型多维查询 |
| BillingStatService | 按用户/模型/降级/缓存命中率维度的统计聚合 |
| BillService | 月结账单生成（定时任务汇总上月消耗/充值/退款/余额变动）、账单查询与下载 |
| BillingAnomalyService | 异常规则匹配、告警触发、异常标记 |
| RateProvider | 从 sys_ai_model 只读缓存读取计费比例（表归 AI 对话模块，只读引用），支持降级模型比例查询 |
| QuotaCache | Redis 数据结构：`ai:quota:daily:{userId}:{date}`（日）、`ai:quota:monthly:{userId}:{month}`（月） |
| BalanceCache | Redis 数据结构：`ai:balance:{userId}`（余额）、`ai:arrears:{userId}`（欠费标记） |

## 4. 计费流程

### 4.1 预校验（配额 + 余额 + 欠费熔断）

```
before_agent 钩子触发预校验
    ↓
1. 欠费熔断：读取 ai:arrears:{userId}
   - 标记存在 → 直接拒绝调用（欠费状态用户禁止推理）
    ↓
2. 配额校验：QuotaService.checkQuota(userId)
   - 读取 VIP 等级 → sys_member_benefit.ai_credits_daily / ai_credits_monthly
   - 从 Redis 读取已用：ai:quota:daily:{userId}:{date}、ai:quota:monthly:{userId}:{month}
   - 日已用 + 预估 > 日限额 → 拒绝（配额不足）
   - 月已用 + 预估 > 月限额 → 拒绝（配额不足）
    ↓
3. 余额校验：BalanceService.checkBalance(userId, estimatedCredits)
   - 余额 < 预估积分 → 拒绝（余额不足，提示充值）
    ↓
校验通过 → 进入预扣减
```

> 配额、余额、欠费三项任一不满足均拒绝调用，确保 LLM 调用前已完成全部前置校验，避免欠费或零余额用户发起调用。

### 4.2 预扣减（配额 + 余额）

```
EstimateService.estimateCredits(userId, conversationId, content)
    ↓
预估输入 Token：
  - 历史上下文 Token：Redis 读取会话近 10 轮消息 Token 均值 × 0.8
  - 当前消息 Token：tiktoken 编码 content × estimate-input-factor（默认 1.2）
  - 记忆注入 Token：估算 200
  - 工具定义 Token：估算 500
  - 预估输入 = 上下文 + 当前消息 × 1.2 + 记忆 + 工具
    ↓
预估输出 Token：模型 max_output_tokens × estimate-output-factor（默认 0.3）
    ↓
预估积分 = 预估输入 × inputRate + 预估输出 × outputRate
    ↓
QuotaService.preDeduct(userId, estimatedCredits)
  - Redis DECR 日配额、月配额
  - 任一返回负数 → 回滚 INCR → 返回配额不足
    ↓
BalanceService.preDeduct(userId, estimatedCredits)
  - Redis DECR ai:balance:{userId}
  - 返回负数 → 回滚配额 INCR + 余额 INCR → 返回余额不足
    ↓
创建 PreDeductContext（budgetPool = estimatedCredits，remainingBudget = estimatedCredits）
记录 sys_ai_billing.pre_deduct = estimatedCredits
```

### 4.3 实扣减与差额退补

```
after_agent 钩子触发实扣
    ↓
获取 LLM 实际 Token 用量 → RateProvider.getRates(actualModel)
    ↓
actualCredits = inputTokens × inputRate
              + cachedInputTokens × cachedRate
              + outputTokens × outputRate
    ↓
差额退补：difference = estimatedCredits - actualCredits
    ↓
  - difference > 0（预估 > 实际，多扣）：
      Redis INCR 日/月配额 + difference（退还多扣配额）
      BalanceService.refund(userId, difference)（退还多扣余额）
    ↓
  - difference < 0（实际 > 预估，少扣）：
      额外扣减 = |difference|
      QuotaService.preDeduct(额外扣减)（校验日/月限额，超限则扣至限额上限）
      BalanceService.deduct(额外扣减)（余额不足 → 扣至 0，标记欠费 ai:arrears:{userId}）
    ↓
更新 sys_ai_message.credits = actualCredits
    ↓
写入 sys_ai_billing：
  - bill_type = chat / tool_llm / kb_inject / asr / tts
  - credits = actualCredits（本记录自身 LLM Token 积分，不含其他 bill_type 记录）
  - quota_consumed = actualCredits
  - credits_saved = cachedInputTokens × (inputRate - cachedRate)
  - tool_llm 类型记录的 tool_credits 单独记录工具 LLM Token 积分
```

### 4.4 多步推理滚动预算

针对 ReAct/Plan-and-Execute/Reflexion 等长链路推理，预扣阶段一次性预扣总预算，推理过程中滚动校验剩余预算，避免单次预扣不足以覆盖多步消耗：

```
Agent 启动时（before_agent）：
  - 总预算 = estimatedCredits（已含多步推理的保守预估）
  - 预扣总预算到配额 + 余额（见 §4.2）
  - PreDeductContext.budgetPool = 总预算
    ↓
每步推理前（before_model 钩子）：
  - remainingBudget = budgetPool - 已累计实扣
  - 单步预估 > remainingBudget → interrupt(type=quota) 中止推理
    ↓
每步推理后（after_model 钩子）：
  - 累计本步实际 Token 消耗，滚动扣减 remainingBudget
    ↓
推理结束（after_agent）：
  - 统一实扣：按总实际消耗结算，退还未用预算（见 §4.3）
```

> 滚动预算基于预扣的总预算池，不再逐步预扣配额/余额（避免逐步预扣的并发开销与配额碎片）。预算不足时通过 LangGraph interrupt 中止推理，保留上下文供用户升级后恢复。

### 4.5 子智能体配额协调

子智能体并行执行时，主 Agent 统一管理预算池，子智能体向主 Agent 申请配额，避免各自独立预扣导致超扣：

```
主 Agent 预扣总预算（含所有子智能体预估消耗，见 §4.2）
    ↓
子智能体执行前：向主 Agent 申请配额分配（从 budgetPool 划拨子预算）
  - 主 Agent 校验 remainingBudget >= 子智能体预估
  - 不足 → 子智能体不启动，主 Agent 触发 interrupt(type=quota)
    ↓
子智能体独立执行，各自记录 Token 消耗
  - 每个子智能体的 LLM 调用独立写入 sys_ai_billing（bill_type=chat/tool_llm，关联同一会话）
  - 子智能体消耗从其子预算扣减，超支时向主 Agent 申请追加（主 Agent 统一判断）
    ↓
主 Agent 统一实扣（after_agent）：
  - totalCredits = SUM(子智能体 actualCredits) + 主 Agent 自身 actualCredits
  - 差额退补基于"总预算 vs 总实际"统一结算（见 §4.3）
  - 配额 + 余额统一扣减，更新 sys_ai_message.credits = totalCredits
```

> 子智能体不独立预扣配额/余额，仅向主 Agent 申请子预算；实扣由主 Agent 统一完成，确保并行执行下配额扣减的原子性与一致性。

### 4.6 降级计费

```
模型路由降级发生时
    ↓
BillingService 获取实际降级模型（fallback_model_id 链最终成功模型）
    ↓
RateProvider.getRates(actualModel) → 降级模型的计费比例
    ↓
按降级模型比例换算积分（实际消耗 = 降级模型价格，用户不亏）
    ↓
sys_ai_billing.model = 降级模型
sys_ai_billing.actual_model = 用户原选模型（NULL 不可）
```

### 4.7 异常检测

```
after_agent 钩子 + 定时任务
    ↓
AnomalyDetector.check(billingRecord)
    ↓
规则匹配：
  1. 单次超高：credits > 月限额 × 10% → 告警
  2. 突发峰值：5 分钟内总消耗 > 日限额 × 50% → 告警 + 触发日限额限流
  3. 连续不足：24 小时内配额不足触发 > 10 次 → 告警（可能异常使用，需人工核查）
  4. 空回复高耗：outputTokens==0 && inputTokens > 10000 → 告警
    ↓
触警处理：
  - 写入 AnomalyEvent 到 ELK（tag=ai_billing_anomaly）
  - 告警计数更新 Redis：incr ai:anomaly:count:{ruleType}:{userId}
  - 突发峰值：告警 + 触发日限额限流（不调整 TPM/RPM，TPM 由 API 网关层统一控制）
```

## 5. 余额账户与充值退款

### 5.1 余额扣减流程

余额扣减与配额扣减协同，分预扣与实扣两阶段：

```
预扣阶段（before_agent）：
  - Redis DECR ai:balance:{userId}（原子，保证并发不超扣）
    ↓
实扣阶段（after_agent）：
  - 差额结算：difference > 0 退还多扣；difference < 0 额外扣减（见 §4.3）
    ↓
MySQL 落库：
  - credits_balance 更新采用 version 字段乐观锁 CAS
    - 更新条件：user_id 匹配 且 version = 当前读取版本号
    - 更新内容：credits_balance = credits_balance - 扣减值，version = version + 1
    - CAS 失败重试读取最新余额重算（与会员管理 growth_value 一致）
  - 写入 sys_ai_credit_log（source=consume，related_id=计费记录ID）
```

> Redis 原子操作保证预扣并发安全；MySQL 乐观锁保证最终落库的余额一致性。Redis 为准实时权威，MySQL 为持久化权威，二者最终一致。

### 5.2 欠费状态与熔断

```
欠费标记触发（实扣阶段，difference < 0 且余额不足）：
  - 余额扣至 0，差额部分记录为欠费金额
  - 设置 Redis ai:arrears:{userId} = 1（欠费标记）
  - 写入 sys_ai_credit_log（source=consume，记录欠费金额）
    ↓
欠费熔断（预校验阶段，见 §4.1）：
  - 检测到 ai:arrears:{userId} → 直接拒绝调用
  - 前端提示"账户欠费，请充值后使用"
    ↓
欠费解除（充值/赠送到账）：
  - RechargeService.recharge 成功后清除 ai:arrears:{userId}
  - 用户恢复调用能力
```

> 欠费熔断确保余额耗尽后用户无法继续调用 AI 能力，避免欠费累积。充值到账后自动解除，无需人工干预。

### 5.3 充值与赠送

```
充值/赠送触发
    ↓
RechargeService.recharge(userId, amount, source)
  - source: recharge（积分包购买）/ vip_gift（VIP赠送）/ trial（试用）/ admin_adjust（管理员调整）
    ↓
BalanceService.increase(userId, amount)
  - Redis INCR ai:balance:{userId}
  - MySQL credits_balance += amount（乐观锁 CAS）
  - 写入 sys_ai_credit_log（source, amount, balance_after, operator_id, reason）
  - 清除欠费标记 ai:arrears:{userId}（若存在）
    ↓
VIP 赠送月末清零：定时任务每月最后一天 23:59 统计当月赠送余额未用部分，清零并记录流水（source=vip_gift_expire）
```

### 5.4 退款补偿

```
退款触发（用户申请/系统检测误扣）
    ↓
RefundService.refund(userId, billingId, amount, reason)
  - 校验原计费记录存在且未退款
    ↓
BalanceService.increase(userId, amount)
  - 余额回补（Redis INCR + MySQL 乐观锁 CAS）
  - 写入 sys_ai_credit_log（source=refund，related_id=billingId，reason）
    ↓
不重置日/月限额已用计数（避免绕过限额防滥用）
```

## 6. 账单生成

### 6.1 月结账单

| 组件 | 职责 |
|------|------|
| BillService | 月度账单生成、查询、下载 |
| BillGeneratorTask | 定时任务，每月 1 日生成上月账单 |

```
每月 1 日 00:30 触发（Asia/Shanghai）
    ↓
扫描上月有 AI 能力消耗/充值/退款记录的用户
    ↓
BillService.generateMonthlyBill(userId, month)
  - 汇总消耗：SUM(sys_ai_billing.credits) 按 bill_type 分组
  - 汇总充值/退款：SUM(sys_ai_credit_log.amount) 按 source 分组
  - 余额变动：上月末余额 → 本月末余额
  - 生成 BillVO（itemSummary 按 bill_type 维度细分）
    ↓
缓存到 Redis：ai:bill:{userId}:{month}（TTL 90 天）
    ↓
推送站内通知（账单可查询）
```

> 账单基于 sys_ai_billing + sys_ai_credit_log 聚合生成，不重复存储明细（单一信息源）。账单可按需重新生成（幂等），缓存失效时从原始记录重算。

### 6.2 账单查询与下载

| 能力 | 说明 |
|------|------|
| 按月查询 | 用户查询指定月份账单汇总（BillVO） |
| 明细下钻 | 从账单汇总下钻到计费明细/流水明细（链接 sys_ai_billing / sys_ai_credit_log 查询） |
| 账单下载 | 导出 PDF/Excel（含消耗/充值/退款/余额变动） |

## 7. 缓存策略

| 缓存对象 | 缓存 Key | TTL | 更新策略 |
|---------|---------|------|---------|
| 日配额已用 | `ai:quota:daily:{userId}:{date}` | 至当日 0 点 | 每次预扣/实扣更新 |
| 月配额已用 | `ai:quota:monthly:{userId}:{month}` | 至当月 1 日 | 每次预扣/实扣更新 |
| 模型计费比例 | `ai:rate:{modelId}` | 30 分钟 | 模型速率更新时失效 |
| 会话 Token 均值 | `ai:ctx:avg:{conversationId}` | 10 分钟 | 每次消息完成后更新 |
| 异常告警计数 | `ai:anomaly:count:{type}:{userId}` | 24 小时 | 每次异常触发 incr |
| 积分余额 | `ai:balance:{userId}` | 1 小时 | 充值/扣减/退款时更新；与 MySQL credits_balance 最终一致 |
| 欠费标记 | `ai:arrears:{userId}` | 无（持久） | 余额不足时设置；充值到账时清除 |
| 月结账单 | `ai:bill:{userId}:{month}` | 90 天 | 每月生成；缓存失效时从原始记录重算 |

## 10. 三后端一致性约束

Java/Go/Python 三后端计费逻辑一致，Java 权威，Go/Python 对齐：

- 预校验三端一致：欠费熔断 → 配额校验 → 余额校验，任一失败拒绝调用
- 配额与余额预扣三端均使用 Redis 原子操作（INCR/DECR/Lua 脚本），并发不超扣
- 余额 MySQL 落库三端均采用 credits_balance version 字段乐观锁 CAS，CAS 失败重试
- 差额退补三端一致：difference > 0 退还多扣；difference < 0 额外扣减，余额不足标记欠费
- 欠费熔断三端一致：欠费标记 Redis key 与清除时机一致
- 积分换算公式、bill_type 枚举（chat/tool_llm/kb_inject/asr/tts）、降级计费规则三端一致
- 多步推理滚动预算与子智能体配额协调逻辑三端一致
- 配额重置时区 Asia/Shanghai（日限额每日 0 点、月限额每月 1 日）三端一致
- 月结账单生成时机与聚合口径三端一致
- 计费记录只追加策略三端一致
