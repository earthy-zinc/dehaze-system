# AI 计费管理模块 - 后端实现设计

## 1. 文档概述

本文档描述 AI 计费管理模块的后端实现设计：收入线（Token/时长/字符计量 → 积分换算 → 余额与日/月限额双控的预扣实扣）与成本线（模型调用真实成本异步核算并回填 `sys_ai_billing.cost`）的架构决策与流程设计。

> **数据模型**：`sys_ai_billing`、`sys_ai_credit_log`、`sys_ai_refund`、`sys_ai_model_cost`、`sys_ai_model_cost_detail` 归本模块；`sys_ai_model_price`(+`sys_ai_model_price_detail`) 归 AI 模型管理模块，本模块只读引用。完整表结构见 [02-系统架构/03-数据库设计.md](../../../02-系统架构/03-数据库设计.md) §4.7，本文档不重复定义表结构。

## 2. 架构设计

### 2.1 分层架构

**控制层（Controller）**：

| 组件 | 职责 |
|------|------|
| BillingController | 余额/配额查询、消耗汇总查询、计费明细查询、流水查询（用户侧） |
| BillingStatController | 计费统计查询、异常记录清单查询（管理员） |
| CostController | 成本单价维护（管理员） |
| CostStatController | 成本-利润统计（管理员） |
| BillController | 账单查询与下载 |

**服务层（Service）**：

| 组件 | 职责 |
|------|------|
| BillingService | 计费总入口：计量（Token→积分）→ 预扣（配额+余额）→ 实扣（差额退补）→ 记录；多步推理滚动预算；子 Agent 实报实销结算（settle_subagent，§4.5）。对外通过 AgentHooks 接入推理流程（before_agent / after_agent / before_model / after_model），不硬编码到推理链路 |
| QuotaService | 配额管理：日/月限额原子操作（预扣/实扣/退还/查询），Redis 原子操作保证并发不超扣；**fail-closed**——无会员记录、权益未配置或已停用时配额校验/预扣一律拒绝（详见 §4.1） |
| EstimateService | 积分预估：基于历史上下文与当前消息长度预估本次消耗 |
| BalanceService | 余额账户扣减/回补：Redis 原子操作 + MySQL `credits_balance` 乐观锁 CAS，欠费标记管理 |
| CreditAccountService | 积分到账：多来源（recharge 积分卡履约 / vip_gift / trial / admin_adjust），按关联业务记录幂等 |
| RefundService | 积分回退与补偿：积分卡退款回退（按订单事件扣回未消耗积分）与误扣补偿（按审核结果回补余额） |
| BillingRecordService | 计费记录查询（按用户/会话/消息/类型多维条件） |
| BillingStatService | 计费统计聚合（按用户/模型/降级/缓存命中率维度，缓存命中率仅基于 chat 类记录）与用户端消耗汇总（日/月趋势、模型分布、节省汇总，仅统计 chat 类记录） |
| CostService | 成本单价维护（模型-供应商维度，价格版本化）与成本核算（异步任务回填 `sys_ai_billing.cost`） |
| CostStatService | 成本-利润统计（整体双口径毛利 + 模型/供应商成本分组分解）与供应商调价影响模拟 |
| BillService | 月结账单生成（定时任务）与查询下载 |
| BillingAnomalyService | 异常规则匹配、告警触发、异常标记、异常记录清单查询（管理员） |

**内部组件**：

| 组件 | 职责 |
|------|------|
| QuotaCache | Redis 日/月配额缓存，原子操作（INCR/DECR/Lua 脚本） |
| BalanceCache | Redis 余额缓存（预扣/实扣原子操作）与欠费标记 |
| PriceProvider | 用户售价只读缓存（`sys_ai_model_price` + `_detail`），按价格版本 + 时段档位 + 上下文分段三维匹配单价，支持降级模型售价 |
| CostProvider | 成本单价只读缓存（`sys_ai_model_cost` + `_detail`），与 PriceProvider 共用价格版本选择与时段判定逻辑，各自独立缓存与更新 |
| AnomalyDetector | 异常规则引擎 |

## 3. 核心数据结构

> 字段定义以数据库表结构为准，本节只说明查询/返回对象的组织方式与派生语义。

### 3.1 计费明细查询

| 对象 | 说明 |
|------|------|
| BillingRecordQuery | 计费明细分页查询：按用户/会话/计费类型/模型/时间范围过滤 |
| BillingRecordVO | 明细字段对应 `sys_ai_billing`；额外派生 refundStatus（无/待审核/已通过/已驳回），由关联 `sys_ai_refund` 得出 |

> **计量口径注意**：asr/tts 类型记录的 `input_tokens` 存储的是音频秒数/合成字符数（非 token），token 类统计需按 bill_type 过滤——summary（用户端消耗汇总）与缓存命中率统计已固定仅统计 chat 类记录（chat + chat_subagent，子 Agent 口径见 §4.5）；asr/tts 独立计量字段（如 quantity）的彻底解决列入语音交互模块批次待办规划。KB embedding/rerank 记录的 `input_tokens` 虽为 token 口径，但消耗归属知识库动作（向量化/重排序）而非对话消息，同样不纳入 chat 类 token 统计（§4.9）。

### 3.2 余额与流水

| 对象 | 说明 |

| CreditLogVO | 余额变动流水（source 取值见需求规格 §2.2，月末清零另记 `vip_gift_expire`；recharge 的 related_id 关联积分卡订单） |

### 3.3 统计与账单

| 对象 | 说明 |
|------|------|
| BillingStatVO | 管理端统计聚合，groupBy 支持 user / model / billType / day；缓存命中率仅基于 chat 类记录计算 |
| BillingSummaryVO | 用户端消耗汇总（日/月趋势、模型分布、缓存与降级节省），仅统计 chat 类记录，仅返回本人数据，不含成本字段 |
| AnomalyRecordVO | 异常事件记录（single_high / burst / consecutive_quota_fail / empty_high_output），支撑管理员清单与趋势查询 |
| BillVO | 月结账单汇总（消耗/到账/回退/余额变动），明细按 bill_type 细分 |

| CostStatResult | 成本-利润统计返回元素，`metric`∈[overall（整体毛利官方口径）, ai（AI 参考口径）]，口径含义见需求规格 §2.10.3；groupBy=model/provider 时为分组行，仅返回 dimension + cost（订单实收无法按模型/供应商归因，不返回收入/毛利/口径） |

### 3.4 预扣上下文（内部）

| 对象 | 说明 |
|------|------|
| PreDeductContext | 贯穿预扣→滚动预算→实扣全流程；budgetPool 为多步推理总预算，remainingBudget 随每步消耗递减 |

### 3.5 退款申请（对应 `sys_ai_refund`）

| 对象 | 说明 |
|------|------|
| RefundApplyVO | 误扣补偿申请（status：1 待审核 / 2 已通过 / 3 已驳回）；同一 billing_id 仅允许一条待审核申请 |

## 4. 计费流程

### 4.1 预校验（配额 + 余额 + 欠费熔断）

before_agent 钩子触发预校验，按序执行三项检查，任一不满足即拒绝调用：

1. **欠费熔断**：读取欠费标记（`ai:arrears:{userId}`），存在则直接拒绝
2. **配额校验（fail-closed）**：按用户 VIP 等级读取 `sys_member_benefit.ai_credits_daily` / `ai_credits_monthly`，从 Redis 读取日/月已用量，校验"已用 + 预估 ≤ 限额"，任一超限则拒绝；**无会员记录、权益未配置或已停用（权益数据缺失）时一律拒绝**（安全优先：配额护栏缺省拒绝，而非视为无限额），提示 AI 权益未生效；已配置等级的限额值为 0 表示不限额。会员档案由注册与登录兜底初始化（见会员管理 §4.6），无档案误报"配额不足"属档案缺失而非额度耗尽
3. **余额校验**：余额 < 预估积分则拒绝

### 4.2 预扣减（配额 + 余额）

1. **预估积分**：预估输入 Token = 历史 10 轮平均上下文 × 0.8 + 当前消息 Token × 1.2 + 记忆注入 200 + 工具定义 500；预估输出 Token = 模型 `max_output_tokens` × 0.3；按当前时段/分段档位单价换算为预估积分（保守系数见 §8 配置项）
2. **配额预扣**：Redis 原子扣减日配额与月配额已用量，任一扣减返回负数则回滚（INCR 补偿）并返回配额不足
3. **余额预扣**：Redis 原子扣减余额，返回负数则回滚配额与余额并返回余额不足
4. 创建 PreDeductContext（budgetPool = estimatedCredits），记录 `sys_ai_billing.pre_deduct = estimatedCredits`

### 4.3 实扣减与差额退补

after_agent 钩子触发实扣：

1. 获取 LLM 实际 Token 用量，按**实际使用模型**三维匹配单价（价格版本 → 时段档位 → 上下文分段，规则见需求规格 §2.4.2）
2. 计算实际积分：输入未命中 / 缓存命中 / 输出分别 × 对应档位单价 ÷ 1,000,000，Decimal 精确计算后四舍五入取整，单次至少 1 积分
3. **差额退补**：difference = 预估积分 − 实际积分
   - difference > 0（预估偏大）：退还多扣部分——配额 INCR 退还 + 余额回补
   - difference < 0（预估偏小）：额外扣减——校验日/月限额（超限则扣至限额上限），余额不足则扣至 0 并标记欠费
4. 更新消息积分（`sys_ai_message.credits`），写入计费记录：bill_type 分类（chat/asr/tts；**tool_llm/kb_inject 暂不计费**——工具调用与知识库注入的 Token 已随对话输入/输出计量在 chat 记录中，独立计费类型属超前设计，需求出现时另行立项；`sys_ai_billing.tool_credits` 字段保留不动）、credits_saved（缓存节省）

### 4.4 多步推理滚动预算

针对 ReAct/Plan-and-Execute/Reflexion 等长链路推理，采用"一次性预扣总预算 + 滚动校验"：

- Agent 启动（before_agent）：总预算 = 预估积分，一次性预扣到配额与余额，写入 PreDeductContext.budgetPool
- 每步推理前（before_model）：计算 remainingBudget = budgetPool − 已累计实扣，单步预估超剩余预算则通过 LangGraph interrupt(type=quota) 中止推理
- 每步推理后（after_model）：累计本步实际消耗，滚动扣减 remainingBudget
- 推理结束（after_agent）：按总实际消耗统一实扣，退还未用预算

滚动预算基于预扣的总预算池，不逐步预扣配额/余额，避免并发开销与配额碎片；预算不足中止时保留上下文，供用户升级会员或加购积分卡后恢复。

### 4.5 子 Agent 计费口径（父预扣 + 子实报实销）

主图（含 Team 多子图协作的外层 run）持有标准预扣-结算链路（§4.2-§4.4 不变）；子 Agent（deepagents task 工具拉起的子图 run，含嵌套子图）不预扣、实报实销：

- 主图 before_agent：欠费熔断 + 预估 + 配额/余额预扣 + 创建预扣记录（bill_type=chat），滚动预算护栏仅在主图生效（子图无 billing_context，不参与滚动预算校验，静态步数/Token 护栏仍生效）
- 子图 before_agent：跳过预扣——run 运行时上下文携带 is_subagent 标记（经 run_context 子 Agent 作用域注入），不重复预扣配额/余额
- 子图 after_agent：实报实销（`BillingService.settle_subagent`）——按实际 token 用量、实际路由模型换算积分，直接扣减配额与余额（余额不足扣至 0 并标记欠费），创建**独立计费记录 bill_type=chat_subagent**（pre_deduct=0、quota_consumed=实际积分）
- 归属：子记录归属主会话用户/消息（user_id/conversation_id/message_id 继承主 run）；子图 LLM 调用明细聚合在主消息过程链（sys_ai_llm_call）中，经 message_id 关联主 trace
- 不重复结算保证：子记录 bill_type=chat_subagent 不会被主图结算的 `_find_chat_billing`（按 bill_type=chat 匹配预扣记录）复用，主图差额退补只基于自身预扣记录
- 子图异常/超时（未完成）：after_agent 未执行，不产生半条计费记录
- 不发布对话完成事件（激励成长值按主消息结算一次）、不做异常检测（子图消耗随主消息聚合观测）；成本归因字段（request_id/provider_id/error_code/latency_ms）照常透出

统计聚合：chat_subagent 与 chat 同口径聚合（CHAT_BILL_TYPES）——用户端 summary、管理员统计 token 类列均包含子记录，保证统计口径与实际扣减一致；月结账单明细按 bill_type 分组单列 chat_subagent。

### 4.6 降级计费

计费记录 `model` = 实际降级模型（降级链最终成功模型），`actual_model` = 用户原选模型（NULL 表示未降级），按实际降级模型的售价档位计费；降级链全部失败（无实际 LLM 调用）不计费，配额恢复发送前水平。

### 4.7 异常检测

after_agent 钩子 + 定时任务触发规则匹配（规则见需求规格 §2.7.1）：

- 触警处理：写入异常事件（tag=ai_billing_anomaly，含关联计费记录与触发详情）、Redis 告警计数递增；突发峰值额外触发日限额限流（TPM/RPM 由 API 网关层统一控制，本模块不调整）
- 异常记录落库可查询：管理员经异常清单接口按异常类型/时间范围筛选

### 4.8 成本核算（成本线，异步）

计费记录落库后由异步任务核算真实成本并回填 `sys_ai_billing.cost`，**不阻塞用户结算主链路**：

1. 计费记录落库（含 token 明细、request_id、provider_id、调用时刻）
2. 异步任务（消息队列 + 定时补偿）判断调用时刻时段（Asia/Shanghai 高峰/空闲），按 provider + model 查成本单价，三维匹配档位（价格版本 → 时段档位 → 上下文分段）
3. 按需求规格 §2.10.2 公式核算成本（元），回填 `sys_ai_billing.cost`
4. 未配置成本单价 → cost 置 0 并标记"待配置成本价"，异常检测告警提示管理员补充；失败进入定时补偿队列重试
5. asr/tts 为本地能力（无外部供应商采购），cost 保持 0

### 4.9 知识库 embedding/rerank 计费（动作后扣费）

知识库向量化（文档索引 + 检索查询向量化）与重排序按输入 token 计费，bill_type=embedding / rerank，归属知识库动作而非对话消息。与对话两阶段预扣（§4.2-§4.3）不同，单次金额小且用量在动作前不可精确预估，采用语音同款**后扣费**（调用前预估校验 + 调用后实扣），由 `KbBillingService`（kb_billing_service.py）承载。

**计量口径**：

| 动作 | 计量 |
|------|------|
| 文档向量化 | 分块器精确 token 数求和（chunk token_count，tiktoken） |
| 检索查询向量化 | query 近似 token（非 ASCII 1:1、ASCII 4:1，与 chat 预扣 `_approx_tokens` 同口径） |
| rerank | query + 全部候选文档近似 token 求和 |

**链路与计费主体**：

| 动作 | 触发点 | 计费主体 |
|------|--------|---------|
| 文档向量化 | 文档处理流水线：调 embed_texts 前 ensure、向量索引成功后 charge（失败不扣，文档标记 failed） | 知识库 owner |
| 用户检索（/kb/search、retrieve/test） | 查询向量化 ensure→调用→charge；rerank ensure→调用→charge | 发起用户 |
| 对话内部注入（search_internal） | **不计费**——消耗已随主消息 chat 计费覆盖，独立计费即双扣 | — |
| 测试集回归评估 | **不计费**（内部质量工具，与 search_internal 同口径，search 传 bill=False） | — |
| 检索缓存命中 | **不计费**（计费点在实际模型调用后，缓存命中无调用） | — |
| provider=local 本地模型 | **不落计费记录**（零边际成本），但 ensure 权益预校验照常执行 | — |

**口径细节**：

- 预校验 fail-closed（欠费熔断 → 配额 → 余额，顺序与 §4.1 一致），不满足抛 QUOTA_INSUFFICIENT；检索链路对该错误码**透传拒绝而非降级为空结果**（防欠费用户误判库无内容）
- 实扣走 quota/balance deduct（不足扣至 0 并标记欠费，与 chat 实扣一致）；落 `sys_ai_billing`（pre_deduct=0、quota_consumed=credits、token 记 input_tokens）+ consume 流水
- 单价读 `sys_ai_model_price` 用户售价（与 chat 同源同换算函数，peak/idle 档位生效）；**未配置售价 warn 回退 0（免费）不拒绝**——与 chat 未配置抛错不同：文档向量化是后台任务，计费配置缺失不应让文档永久卡失败；本地模型零边际成本天然无售价配置，口径自洽
- 统计：不进 CHAT_BILL_TYPES（用户端 summary 趋势/模型分布仍 chat-only，与 asr/tts 同处理）；月结账单按 bill_type 全量分组自动纳入；计费明细可按 bill_type 过滤

## 5. 积分账户与到账回退

### 5.1 积分到账（多来源）

各来源的有效期与流水 source 见需求规格 §2.2（月末清零另记 source=`vip_gift_expire`）。到账的触发方式与幂等设计：

| 来源 | 触发方式 | 幂等依据 |
|------|---------|---------|
| 积分卡到账 | 订单支付成功同事务履约（可得积分 credit_amount 由订单冗余字段承载，本模块不查询商品表） | 积分卡订单号 |
| VIP 赠送 | 会员管理按月发放事件（每月 1 日） | 会员等级 + 发放月份 |
| 免费试用 | 新用户注册事件 | 用户注册 |
| 管理员调整 | 管理员手动调整（补扣/补偿） | 调整单号 |

**积分卡到账流程**：订单支付成功（completePayment 事务内）→ 订单管理**同事务调用**本模块到账服务（单体架构，订单与计费同库同进程，非异步消息；携带订单号、用户、商品类型、credit_amount）→ 余额增加（Redis INCR + MySQL 乐观锁 CAS）→ 写入流水 source=recharge（related_id=积分卡订单号）→ 清除欠费标记（若存在）。到账按订单号幂等，与订单支付事务**强一致**（到账失败则订单事务回滚）。

**VIP 赠送月末清零**：定时任务每月最后一天统计当月赠送未用部分，清零并记录流水（source=vip_gift_expire），次月重新发放。

### 5.2 余额扣减与一致性

余额扣减与配额扣减协同，分预扣与实扣两阶段：

- 预扣阶段：Redis 原子扣减余额（保证并发不超扣）
- 实扣阶段：差额结算（多扣退还 / 少扣补扣）
- MySQL 落库：`credits_balance` 更新采用 version 字段乐观锁 CAS，CAS 失败重试读取最新余额重算；写入流水（source=consume，related_id=计费记录 ID）

Redis 原子操作保证预扣并发安全，MySQL 乐观锁保证最终落库的余额一致性；Redis 为准实时权威，MySQL 为持久化权威，二者最终一致。

### 5.3 欠费状态与熔断

- **欠费标记触发**（实扣阶段，实际消耗超出余额）：余额扣至 0，差额记录为欠费金额，设置 Redis 欠费标记（`ai:arrears:{userId}`）
- **欠费熔断**（预校验阶段）：检测到欠费标记直接拒绝调用，前端提示充值/加购后使用
- **欠费解除**：任一来源到账成功后自动清除欠费标记，无需人工干预

### 5.4 积分回退与补偿

**积分卡退款回退**（承接订单管理履约）：

1. 积分卡退款审核通过（订单管理，折算口径按用量）→ 发布退款事件（含未消耗积分）
2. 本模块消费事件（按积分卡订单号幂等）→ 从余额扣回**未消耗积分**（Redis 原子 + MySQL CAS）；已消耗部分不退
3. 写入流水 source=refund（related_id=积分卡订单号）

**误扣补偿**（用户申请 / 系统检测）：

1. 用户申请或系统检测到误扣，创建退款申请（`sys_ai_refund`，billing_id 关联原计费记录，同一 billing_id 仅一条待审核申请）
2. 管理员审核（核对误扣原因与金额）
3. 审核通过 → 余额回补 → 写入流水 source=refund（related_id=原计费记录 ID）
4. 补偿不重置日/月限额已用计数

## 6. 账单生成

### 6.1 月结账单

- 定时任务每月 1 日 00:30（Asia/Shanghai）触发，扫描上月有 AI 消耗/到账/回退记录的用户
- BillService 按用户聚合：消耗（Σ `sys_ai_billing.credits` 按 bill_type 分组）、到账/回退（Σ `sys_ai_credit_log.amount` 按 source 分组）、余额变动（上月末 → 本月末）

## 10. 三后端一致性约束

Java/Go/Python 三后端实现一致，Java 权威，Go/Python 对齐（计费口径层面的一致性约束见需求规格 §6）：

- 预校验顺序（欠费熔断 → 配额校验 → 余额校验）、预扣实扣流程与差额退补规则三端一致
- 配额与余额预扣三端均使用 Redis 原子操作（INCR/DECR/Lua 脚本）；余额 MySQL 落库三端均采用 `credits_balance` version 乐观锁 CAS
- 欠费标记的 Redis key 与清除时机三端一致
- 成本核算的三维档位匹配与高峰时段判定（`ai.billing.peak-hours`）、双口径收入与 `ai.billing.membership-ai-ratio` 三端一致
- 多步推理滚动预算与子智能体配额协调逻辑三端一致
- 积分到账/回退幂等策略（按订单号/业务记录幂等）三端一致
- 月结账单生成时机与聚合口径三端一致

### 10.1 Go 端原生实现（2026-09-17）

Go 侧 18 个端点全部原生实现（`internal/service/ai/billing_service.go`、`cost_service.go` + `internal/api/ai_billing.go` + `internal/router/ai_billing.go`），路径前缀 `/api/v1/ai-billing`：

| 端点分组 | 权限 | 说明 |
|---------|------|------|
| `/balance`、`/summary`、`/records`、`/credit-logs`、`/bills/{month}`、`/bills/{month}/download`、`POST /refunds` | 登录用户 | 查询他人数据（`userId` 下钻）需 `ai:billing:stat`，越权 `A0301`；账单下载保持 JSON 信封 |
| `/refunds`(GET)、`POST /refunds/{id}/audit` | `ai:billing:refund` | 审核通过回补余额并写 `source=refund` 流水；同一计费记录仅一条待审核申请（`A0680`），已审核不可重复处理（`A0681`） |
| `/stats`、`/anomalies` | `ai:billing:stat` | 聚合维度 `user/model/billType/day`，token 列仅 chat 类口径 |
| `POST /adjust` | `ai:billing:adjust` | amount=0 报 `A0400`，用户不存在报 `A0401`；余额增加清欠费标记 |
| `/costs`(GET/POST/PUT/DELETE)、`/cost-stats`、`POST /reconcile/import` | `ai:billing:cost` | 同模型同供应商生成新价格版本；成本统计整体口径返回 `overall`/`ai` 两行毛利 |

实现要点：

- 权限校验在 handler 内、参数绑定之后执行（对齐 FastAPI 校验顺序）。
- Redis 键与 TTL 与 python 完全一致（§7）：`ai:balance:{userId}`（1 小时，回填一律整数化）、`ai:arrears:{userId}`（无 TTL，到账清除）、`ai:quota:daily|monthly:*`、`ai:bill:{userId}:{month}`（90 天）。
- 余额落库走 `sys_user.credits_balance` 乐观锁 CAS（`credits_version`），Redis 预增失败必须回滚，避免余额永久背离。
- 计费域实体（`sys_ai_credit_log`/`sys_ai_refund`/`sys_ai_model_cost`/`sys_ai_model_cost_detail`）的 `create_time` 字段显式声明 `autoCreateTime` **必须保留**：这些实体未内嵌 `BaseModel`，GORM 仅识别 `CreatedAt` 自动填充，缺标签时插入零值时间在 MySQL 严格模式下报 `Error 1292`，会直接打断到账/退款/成本新增链路。
- 单测：`internal/service/ai/billing_test.go`（miniredis 驱动余额/欠费/配额视图与到账流水，真实 MySQL 覆盖退款审核、汇总账单、分维度统计、成本版本管理）。

## 11. 安全设计

| 防护项 | 实现方式 |
|--------|---------|
| 计费记录不可篡改 | 计费记录（`sys_ai_billing`）与流水（`sys_ai_credit_log`）只追加不修改不删除（财务审计要求），过期数据通过定时任务物理清理 |
| 回退安全 | 积分卡退款回退仅由订单管理退款审核通过事件触发（按订单号幂等）；误扣补偿需管理员审核（关联原计费记录核对原因），同一计费记录仅一条待审核申请 |
| 成本与统计数据隔离 | 成本单价维护、成本-利润统计需 `ai:billing:cost`，异常清单需 `ai:billing:stat`；成本数据（`sys_ai_billing.cost` / `sys_ai_model_cost`）不向用户侧任何接口暴露，用户端消耗汇总仅返回本人收入线数据 |
