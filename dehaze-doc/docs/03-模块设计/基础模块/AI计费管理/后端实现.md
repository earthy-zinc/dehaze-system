# AI 计费管理模块 - 后端实现设计

## 1. 文档概述

本文档描述 AI 计费管理模块的后端实现设计。模块是 AI 用量的**计量与核算中枢**，聚焦三件事：积分账户（多来源到账 / 扣减 / 回退）、用量计量计费（Token→积分）、模型调用成本核算。采用**双线并行**架构：

- **收入线（面向用户）**：AI 能力消耗的 Token/时长/字符计量、积分换算、积分账户管理与配额扣减（余额账户 + 日/月限额双控，预扣 + 实扣）
- **成本线（面向管理员）**：模型调用真实成本核算（异步回填 `sys_ai_billing.cost`），与收入线对比形成毛利，支撑成本控制与定价决策

收入线与成本线**数据同源**（基于同一计费记录 `sys_ai_billing` 的 token 明细，不重复计量），计量单位与管理对象完全分离：用户只见积分，成本属商业机密仅管理员可见。

> **定位收敛**：本模块**不再定义可售商品**。积分卡商品的定义、定价与营销由[套餐管理模块](../套餐管理/需求规格.md)承接；积分卡交易、支付与退款审核由[订单管理模块](../订单管理/需求规格.md)承接，本模块仅承接**积分卡履约**（支付成功到账 / 退款回退未消耗积分）；VIP 赠送积分的等级与额度依据由会员管理提供。

> **毛利口径（关键）**：毛利核算采用**双口径**——**整体毛利（官方口径）**：收入 = 全部订单实收（积分卡 + 会员卡），成本 = Σ AI 调用成本（`sys_ai_billing.cost`），为经营决策主依据；**AI 参考毛利（辅助口径）**：收入 = 积分卡实收 + 会员卡实收 × AI 分摊比例（运营配置 `ai.billing.membership-ai-ratio`），仅用于 AI 定价决策参考。**不按"积分消耗 × 兑换率"确认收入**。1 元 = 100 积分仅为**积分价值锚**（积分卡定价基准与存量积分负债估值），不参与收入核算；积分卡量价优惠/赠送作为**营销成本**。

> **数据模型**：`sys_ai_billing`、`sys_ai_credit_log`、`sys_ai_refund`、`sys_ai_model_cost`、`sys_ai_model_cost_detail` 归本模块。数据库已落地：`sys_ai_credit_log.source` 扩展支持 recharge（关联积分卡订单）；`sys_ai_billing.cost` 已有。完整表结构见 [02-系统架构/03-数据库设计.md](../../../02-系统架构/03-数据库设计.md) §4.7，本文档不重复定义表结构。

> **需求规格**：功能需求与业务规则见 [需求规格.md](./需求规格.md)，本文档仅描述实现层面的架构决策与流程设计。

## 2. 架构设计

### 2.1 分层架构

**控制层（Controller）**：

| 组件 | 职责 |
|------|------|
| BillingController | 余额/配额查询、消耗汇总查询、计费明细查询、流水查询（用户侧） |
| BillingStatController | 计费统计查询、异常记录清单查询（管理员） |
| CostController | 成本单价维护（管理员） |
| CostStatController | 成本-利润统计（管理员） |
| BillController | 账单查询与下载 |

**服务层（Service）**：

| 组件 | 职责 |
|------|------|
| BillingService | 计费总入口：计量（Token→积分）→ 预扣（配额+余额）→ 实扣（差额退补）→ 记录；多步推理滚动预算与子智能体配额协调 |
| QuotaService | 配额管理：日/月限额原子操作（预扣/实扣/退还/查询），Redis 原子操作保证并发不超扣 |
| EstimateService | 积分预估：基于历史上下文与当前消息长度预估本次消耗 |
| BalanceService | 余额账户扣减/回补：Redis 原子操作 + MySQL `credits_balance` 乐观锁 CAS，欠费标记管理 |
| CreditAccountService | 积分到账：多来源（recharge 积分卡履约 / vip_gift / trial / admin_adjust），按关联业务记录幂等 |
| RefundService | 积分回退与补偿：积分卡退款回退（按订单事件扣回未消耗积分）与误扣补偿（按审核结果回补余额） |
| BillingRecordService | 计费记录查询（按用户/会话/消息/类型多维条件） |
| BillingStatService | 计费统计聚合（按用户/模型/降级/缓存命中率维度）与用户端消耗汇总（日/月趋势、模型分布、节省汇总） |
| CostService | 成本单价维护（模型-供应商维度，价格版本化）与成本核算（异步任务回填 `sys_ai_billing.cost`） |
| CostStatService | 成本-利润统计（收入=订单实收、成本=Σcost、毛利）与供应商调价影响模拟 |
| BillService | 月结账单生成（定时任务）与查询下载 |
| BillingAnomalyService | 异常规则匹配、告警触发、异常标记、异常记录清单查询（管理员） |

**内部组件**：

| 组件 | 职责 |
|------|------|
| QuotaCache | Redis 日/月配额缓存，原子操作（INCR/DECR/Lua 脚本） |
| BalanceCache | Redis 余额缓存（预扣/实扣原子操作）与欠费标记 |
| PriceProvider | 用户售价只读缓存（`sys_ai_model_price` + `_detail`，表归 AI 模型管理模块），按价格版本 + 时段档位 + 上下文分段三维匹配单价，支持降级模型售价 |
| CostProvider | 成本单价只读缓存（`sys_ai_model_cost` + `_detail`，表归本模块），与 PriceProvider 共用价格版本选择与时段判定逻辑 |
| AnomalyDetector | 异常规则引擎 |

### 2.2 核心组件职责要点

| 组件 | 设计要点 |
|------|---------|
| BillingService | 计量与扣减的唯一入口：预估 → 预扣 → 实扣 → 差额退补 → 计费记录落库；对外通过 AgentHooks 接入推理流程（before_agent / after_agent / before_model / after_model） |
| CreditAccountService | 到账按来源分流处理，均以关联业务记录幂等（积分卡订单号 / 会员等级月 / 用户注册 / 调整单号），重复事件不重复到账 |
| RefundService | 两类回退共用余额扣减/回补底座：积分卡退款回退按订单事件扣回未消耗积分（已消耗部分不退）；误扣补偿按审核结果回补余额（不重置日/月限额已用计数） |
| CostStatService | 毛利核算采用双口径：**整体毛利（官方口径）**收入 = 全部订单实收（积分卡 + 会员卡），**AI 参考毛利（辅助口径）**收入 = 积分卡实收 + 会员卡实收 × AI 分摊比例（`ai.billing.membership-ai-ratio`）；成本均为同周期 Σ `sys_ai_billing.cost`；毛利 = 收入 − 成本，不按"积分消耗 × 兑换率"核算；积分卡量价优惠/赠送作为营销成本 |
| PriceProvider / CostProvider | 两表结构完全对称，共用同一套"价格版本 → 时段档位 → 上下文分段"三维匹配与缓存失效逻辑；用户售价与成本单价各自独立缓存、独立更新 |

## 4. 计费流程

### 4.1 预校验（配额 + 余额 + 欠费熔断）

before_agent 钩子触发预校验，按序执行三项检查，任一不满足即拒绝调用，确保 LLM 调用前完成全部前置校验：

1. **欠费熔断**：读取欠费标记（`ai:arrears:{userId}`），存在则直接拒绝（欠费状态用户禁止推理，提示充值/加购）
2. **配额校验**：按用户 VIP 等级读取 `sys_member_benefit.ai_credits_daily` / `ai_credits_monthly`，从 Redis 读取日/月已用量，校验"已用 + 预估 ≤ 限额"，任一超限则拒绝（配额不足，引导升级会员或加购积分卡）
3. **余额校验**：余额 < 预估积分则拒绝（余额不足，提示加购积分卡）

### 4.2 预扣减（配额 + 余额）

1. **预估积分**：EstimateService 按预估算法输出预估积分（算法见需求规格 §2.6.1）
2. **配额预扣**：Redis 原子扣减日配额与月配额已用量，任一扣减返回负数则回滚（INCR 补偿）并返回配额不足
3. **余额预扣**：Redis 原子扣减余额，返回负数则回滚配额与余额并返回余额不足
4. 创建 PreDeductContext（budgetPool = estimatedCredits），记录 `sys_ai_billing.pre_deduct = estimatedCredits`

### 4.3 实扣减与差额退补

after_agent 钩子触发实扣：

1. 获取 LLM 实际 Token 用量，按**实际使用模型**三维匹配单价（价格版本 → 时段档位 → 上下文分段，规则见需求规格 §2.4.2）
2. 计算实际积分：输入未命中 / 缓存命中 / 输出分别 × 对应档位单价 ÷ 1,000,000，Decimal 精确计算后四舍五入取整，单次至少 1 积分
3. **差额退补**：difference = 预估积分 − 实际积分
   - difference > 0（预估偏大）：退还多扣部分——配额 INCR 退还 + 余额回补
   - difference < 0（预估偏小）：额外扣减——校验日/月限额（超限则扣至限额上限），余额不足则扣至 0 并标记欠费
4. 更新消息积分（`sys_ai_message.credits`），写入计费记录：bill_type 分类（chat/tool_llm/kb_inject/asr/tts）、credits_saved（缓存节省）、tool_credits（工具 LLM Token 积分，仅 tool_llm 类型）

### 4.4 多步推理滚动预算

针对 ReAct/Plan-and-Execute/Reflexion 等长链路推理，采用"一次性预扣总预算 + 滚动校验"：

- Agent 启动（before_agent）：总预算 = 预估积分，一次性预扣到配额与余额，写入 PreDeductContext.budgetPool
- 每步推理前（before_model）：计算 remainingBudget = budgetPool − 已累计实扣，单步预估超剩余预算则通过 LangGraph interrupt(type=quota) 中止推理
- 每步推理后（after_model）：累计本步实际消耗，滚动扣减 remainingBudget
- 推理结束（after_agent）：按总实际消耗统一实扣，退还未用预算

滚动预算基于预扣的总预算池，不逐步预扣配额/余额，避免并发开销与配额碎片；预算不足中止时保留上下文，供用户升级会员或加购积分卡后恢复。

### 4.5 子智能体配额协调

子智能体并行执行时由主 Agent 统一管理预算池，子智能体不独立预扣配额/余额：

- 主 Agent 预扣总预算（含所有子智能体预估消耗）
- 子智能体执行前向主 Agent 申请子预算（从 budgetPool 划拨），不足则不启动并触发 interrupt(type=quota)
- 子智能体独立执行，各自 LLM 调用独立写入计费记录（bill_type=chat/tool_llm，关联同一会话），消耗从其子预算扣减，超支时向主 Agent 申请追加
- 主 Agent 统一实扣：totalCredits = Σ 子智能体实际积分 + 主 Agent 自身实际积分，差额退补基于"总预算 vs 总实际"统一结算

### 4.6 降级计费

模型路由降级时按**实际使用的降级模型**计费，用户不为服务降级多付积分：

- 计费记录 `model` = 实际降级模型（降级链最终成功模型），`actual_model` = 用户原选模型（NULL 表示未降级）
- 按降级模型售价换算积分；统计层对比"用户期望成本 vs 实际成本"
- 降级链全部失败（无实际 LLM 调用）不计费，配额恢复发送前水平

### 4.7 异常检测

after_agent 钩子 + 定时任务触发规则匹配，规则见需求规格 §2.7.1：

- 单次超高消耗、突发峰值、连续配额不足、空回复高消耗四类规则
- 触警处理：写入异常事件（tag=ai_billing_anomaly，含关联计费记录与触发详情）、Redis 告警计数递增；突发峰值额外触发日限额限流（不调整 TPM/RPM，TPM 由 API 网关层统一控制）
- 异常记录落库可查询：管理员经异常清单接口按异常类型/时间范围筛选，支撑异常监控面板

### 4.8 成本核算（成本线，异步）

计费记录落库后由异步任务核算真实成本并回填 `sys_ai_billing.cost`，**不阻塞用户结算主链路**：

1. 计费记录落库（含 token 明细、request_id、provider_id、调用时刻）
2. 异步任务（消息队列 + 定时补偿）判断调用时刻时段（Asia/Shanghai 高峰/空闲），按 provider + model 查成本单价，三维匹配档位（价格版本 → 时段档位 → 上下文分段）
3. 核算 cost = 输入未命中 × input 单价 + 缓存命中 × cached 单价 + 输出 × output 单价（元），回填 `sys_ai_billing.cost`（十进制，元）
4. 未配置成本单价 → cost 置 0 并标记"待配置成本价"，异常检测告警提示管理员补充；失败进入定时补偿队列重试
5. asr/tts 为本地能力（无外部供应商采购），cost 保持 0

**实际账单对账**：管理员导入供应商账单后，以 request_id / 模型 / token 明细与估算成本逐笔核对，差异归因（价格配置过期 / 供应商折扣 / 计量口径差异），反哺成本单价配置修正。

### 4.9 配额不足处理

配额不足（限额不足或余额不足）时暂停 Agent 执行并保留上下文：

- 暂停 Agent，保留对话上下文
- 前端展示配额不足提示与加购引导（升级会员或加购积分卡）
- 用户加购积分卡 / 升级 VIP → 余额或配额刷新 → 恢复推理；用户等待重置 → 上下文保留至重置；用户放弃 → 清除上下文

## 5. 积分账户与到账回退

### 5.1 积分到账（多来源）

| 来源 | 触发方式 | 有效期 | 流水 source | 幂等依据 |
|------|---------|--------|-------------|---------|
| 积分卡到账 | 订单支付成功同事务履约（可得积分 credit_amount 由订单冗余字段承载，本模块不查询商品表） | 永久有效 | recharge（related_id=积分卡订单号） | 积分卡订单号 |
| VIP 赠送 | 会员管理按月发放事件（每月 1 日） | 当月有效，月末清零未用部分 | vip_gift / vip_gift_expire | 会员等级 + 发放月份 |
| 免费试用 | 新用户注册事件 | 永久有效 | trial | 用户注册 |
| 管理员调整 | 管理员手动调整（补扣/补偿） | 实时生效 | admin_adjust（含 operator_id、reason） | 调整单号 |

**积分卡到账流程**：订单支付成功（completePayment 事务内）→ 订单管理**同事务调用**本模块到账服务（单体架构，订单与计费同库同进程，非异步消息；携带订单号、用户、商品类型、credit_amount）→ 余额增加（Redis INCR + MySQL 乐观锁 CAS）→ 写入流水 source=recharge（related_id=积分卡订单号）→ 清除欠费标记（若存在）。到账按订单号幂等，与订单支付事务**强一致**（到账失败则订单事务回滚）。充值积分**永久有效**，不影响会员身份与权益。

**VIP 赠送月末清零**：定时任务每月最后一天统计当月赠送未用部分，清零并记录流水（source=vip_gift_expire），次月重新发放（月度额度语义）。

### 5.2 余额扣减与一致性

余额扣减与配额扣减协同，分预扣与实扣两阶段：

- 预扣阶段：Redis 原子扣减余额（保证并发不超扣）
- 实扣阶段：差额结算（多扣退还 / 少扣补扣）
- MySQL 落库：`credits_balance` 更新采用 version 字段乐观锁 CAS，CAS 失败重试读取最新余额重算；写入流水（source=consume，related_id=计费记录 ID）

Redis 原子操作保证预扣并发安全，MySQL 乐观锁保证最终落库的余额一致性；Redis 为准实时权威，MySQL 为持久化权威，二者最终一致。

### 5.3 欠费状态与熔断

- **欠费标记触发**（实扣阶段，实际消耗超出余额）：余额扣至 0，差额记录为欠费金额，设置 Redis 欠费标记（`ai:arrears:{userId}`）
- **欠费熔断**（预校验阶段）：检测到欠费标记直接拒绝调用，前端提示充值/加购后使用
- **欠费解除**：任一来源到账成功后自动清除欠费标记，无需人工干预

欠费熔断防止余额耗尽后继续调用造成积分负债无限累积。

### 5.4 积分回退与补偿

**积分卡退款回退**（承接订单管理履约）：

1. 积分卡退款审核通过（订单管理，折算口径按用量，见 [订单管理/需求规格.md §4](../订单管理/需求规格.md)）→ 发布退款事件（含未消耗积分）
2. 本模块消费事件（按积分卡订单号幂等）→ 从余额扣回**未消耗积分**（Redis 原子 + MySQL CAS）；已消耗部分不退
3. 写入流水 source=refund（related_id=积分卡订单号）

**误扣补偿**（用户申请 / 系统检测）：

1. 用户申请或系统检测到误扣，创建退款申请（`sys_ai_refund`，billing_id 关联原计费记录，同一 billing_id 仅一条待审核申请）
2. 管理员审核（核对误扣原因与金额）
3. 审核通过 → 余额回补 → 写入流水 source=refund（related_id=原计费记录 ID）
4. 补偿**不重置**日/月限额已用计数（避免绕过限额防滥用机制）

## 10. 三后端一致性约束

Java/Go/Python 三后端计费逻辑一致，Java 权威，Go/Python 对齐：

- 预校验三端一致：欠费熔断 → 配额校验 → 余额校验，任一失败拒绝调用
- 配额与余额预扣三端均使用 Redis 原子操作（INCR/DECR/Lua 脚本），并发不超扣
- 余额 MySQL 落库三端均采用 `credits_balance` version 字段乐观锁 CAS，CAS 失败重试
- 差额退补三端一致：difference > 0 退还多扣；difference < 0 额外扣减，余额不足标记欠费
- 欠费熔断三端一致：欠费标记 Redis key 与清除时机一致
- 积分换算公式、bill_type 枚举（chat/tool_llm/kb_inject/asr/tts）、降级计费规则三端一致
- 多步推理滚动预算与子智能体配额协调逻辑三端一致
- 积分到账/回退幂等策略三端一致（按订单号/业务记录幂等，重复事件不重复到账/回退）
- 配额重置时区 Asia/Shanghai（日限额每日 0 点、月限额每月 1 日）三端一致
- 月结账单生成时机与聚合口径三端一致
- 计费记录只追加策略三端一致
- 成本核算公式（token 类型 × 上下文分段 × 时段档位三维匹配）、高峰时段判定（`ai.billing.peak-hours`）、价格版本选择规则三端一致
- 价格档位模型（sys_ai_model_cost/price 版本主表 + *_detail 档位明细）结构与价格版本化逻辑三端一致
- 收入口径三端一致：毛利核算双口径（整体毛利官方口径 = 全部订单实收 − Σ成本；AI 参考毛利 = 积分卡实收 + 会员卡实收 × AI 分摊比例 − Σ成本），不按"积分消耗 × 兑换率"核算；AI 分摊比例配置项（`ai.billing.membership-ai-ratio`）三端一致

## 11. 安全设计

| 防护项 | 实现方式 |
|--------|---------|
| 配额原子性 | 配额预扣/实扣/退还均使用 Redis 原子操作（INCR/DECR），并发不超扣；任一配额扣减返回负数时回滚（INCR 补偿） |
| 余额一致性 | Redis 原子操作保证预扣并发安全；MySQL `credits_balance` 字段乐观锁 CAS 落库，CAS 失败重试读取最新余额重算；Redis 为准实时权威，MySQL 为持久化权威，二者最终一致 |
| 欠费熔断 | 实扣阶段余额不足时扣至 0 并设置欠费标记；预校验阶段检测到欠费标记直接拒绝调用；任一来源到账后自动清除欠费标记 |
| 计费记录不可篡改 | 计费记录（`sys_ai_billing`）与流水（`sys_ai_credit_log`）只追加不修改不删除（财务审计要求），过期数据通过定时任务物理清理 |
| 回退安全 | 积分卡退款回退仅由订单管理退款审核通过事件触发（按订单号幂等）；误扣补偿需管理员审核（关联原计费记录核对原因），同一计费记录仅一条待审核申请；补偿不重置日/月限额已用计数 |
| 到账幂等 | 积分到账按积分卡订单号/会员发放月/注册事件幂等，重复支付成功回调不重复到账 |
| 异常检测 | 单次超高消耗（> 月限额 10%）告警；突发峰值（5 分钟内 > 日限额 50%）告警 + 触发日限额限流；连续配额不足（24h > 10 次）告警；空回复高消耗告警 |
| 成本数据隔离 | 成本单价维护与成本-利润统计仅管理员可见（权限 `ai:billing:cost`），成本数据（`sys_ai_billing.cost` / `sys_ai_model_cost`）不向用户侧任何接口暴露 |
| 用户端汇总隔离 | 用户端消耗汇总（`/summary`）仅返回本人收入线数据（趋势/分布/节省），不含任何成本字段；异常清单仅管理员（`ai:billing:stat`）可查询 |
