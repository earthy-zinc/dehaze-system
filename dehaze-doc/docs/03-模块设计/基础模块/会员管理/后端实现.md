## 2. 架构与模块边界

### 2.1 模块边界

本模块定位为商业化体系的**身份与权益中枢**：不定义商品、不承接交易；权益表达采用"后台精细配置、前端按服务类目合并展示"。

| 职责边界 | 说明 |
|---------|------|
| 本模块负责 | 会员等级、多服务权益配置与校验依据、成长值、生命周期管理、权益前端合并表达、试用引导与状态展示 |
| 套餐管理承接 | 会员卡/积分卡商品定义、定价、营销（体验券 / 新用户专享） |
| 订单管理承接 | 商品交易；支付成功 / 退款成功回调触发本模块履约与成长值变动 |
| AI 计费承接 | AI 积分计量与余额账户、赠送积分到账（source=vip_gift/trial）、AI 限额的读取与执行 |

### 2.2 跨模块协作

| 协同模块 | 协作内容 | 触发方式 |
|---------|---------|---------|
| 订单管理 | 会员卡支付成功履约、积分卡支付成功仅累积成长值、退款成功成长值扣减与覆盖权益回退（见 §4.1、§4.2） | 同事务调用（completePayment / 退款成功） |
| AI 计费 | 权益配置提供 AI 限额与 VIP 赠送积分依据；服务类目聚合查询读取积分余额与今日已用 | 本模块配置，AI 计费读取执行 |
| AI 计费 | AI 对话完成成长值激励（`ai_consume`） | 消费 `ai.chat.completed` 事件 |
| 套餐管理 | 试用引导读取体验券激活状态、新用户专享可用性 | 同步调用 |
| 图像处理 / 效果对比 | 处理前权益校验，完成后成长值回调（`process` / `evaluate`） | 事件 |

## 4. 核心业务流程

### 4.1 会员卡履约（订单支付回调触发）

订单支付成功（completePayment 事务内）由会员模块同事务处理：

1. **等级与有效期**：等级取 max(现等级, 卡等级)，**只升不降**（需求 §3.1.1 会员卡期间享有较高者——高成长值用户购买低级会员卡不降级，等级/配额按成长值等级维持）；`level_source=purchase`，有效期在原到期时间上叠加（续费叠加，上限 3 年）
2. **权益生效**：各服务额度取 `benefit_overrides` 覆盖值与现等级权益的**较高值**，覆盖项即时生效，未覆盖项取等级权益
3. **配额刷新**：按卡权益/覆盖项与现等级权益的较高值同步刷新全部任务类型配额
4. **成长值累积**：按订单实付金额 1:1 写入 `consume`（1 元 = 100 成长值）
5. **通知**：支付成功站内信

> 积分卡支付成功仅累积成长值（`consume`），不改变会员等级与权益；积分到账由 AI 计费承接（source=recharge）。

### 4.2 成长值变动与等级检查

成长值变动采用**原子自增 + 乐观锁**保证并发安全：签到、处理、评估、消费、AI 对话、退款等多回调并发触发时，CAS 失败重试读取最新余额重算，避免丢失更新；扣减后余额不低于 0（低于 0 按 0 处理，实际变动值按差额计算）。每次变动写入流水（`change_type`：sign_in / sign_in_bonus / rating / process / evaluate / consume / ai_consume / refund_deduct / admin_adjust），并触发等级检查：

- **自动升级不限来源**：成长值达到更高等级阈值即升级，`level_source` 保持不变
- **自动降级受来源与有效期约束**：仅 `level_source=growth` 或会员卡已到期的会员在成长值低于等级下限时降级

> **等级口径统一**：成长值累积（任何来源：签到 / 评分 / 购买消费 / AI 对话等）必触发升级检查，这是成长值体系的核心规则，各来源路径行为一致；购买类操作（会员卡履约）额外遵循等级只升不降（max(现等级, 卡等级)，见 §4.1）。因此"积分卡购买仅累积成长值并触发升级检查"与"会员卡履约取 max 防降级"是同一口径在两条路径上的体现，并不冲突。

AI 使用激励（`ai_consume`）消费 AI 计费发布的 `ai.chat.completed` 事件，每次 AI 对话完成 +1，每日上限 10 次（Redis 计数，与 `process` 对称；一次对话内的多步推理 / 子智能体多次 LLM 调用仅发布一次事件），上限为三端代码常量；`ai_consume` 不参与退款扣减。

### 4.3 权益前端合并表达（服务类目聚合）

后台按 8 类任务配额 + AI 限额 + 功能开关精细配置不变；用户端权益概览按服务类目合并展示，聚合规则：

| 服务类目 | 聚合规则 | 明细 |
|---------|---------|------|
| 图像处理 | 7 类图像任务（dehaze / derain / desnow / lowlight / super_resolution / denoise / inpaint）各自剩余取**最低值** | 各任务类型 quota / used / 剩余 |
| 评估 | 评估任务剩余 = quota - used | — |
| AI | 积分余额（AI 计费余额账户）、今日已用、日/月限额 | 日/月限额、消费明细 |

实现要点：

- 图像处理 / 评估类目由本模块从会员月度配额字段计算（含会员卡覆盖后的合并额度）
- AI 类目数据由 AI 计费模块提供（余额账户、今日已用），限额字段取自权益配置
- 聚合结果整体缓存（短 TTL），明细随聚合结果一并返回，前端展开展示

### 4.4 试用转化漏斗（F-MM-015）

本模块提供统一试用入口与状态展示，载体逻辑由对应模块承接：

| 试用载体 | 状态数据来源 |
|---------|-------------|
| 体验券 | 套餐管理（激活状态 / 到期时间、有效期配置） |
| AI 试用积分 | AI 计费（trial 来源积分余额与赠送额度配置） |
| 新用户专享 | 套餐管理促销（无历史付费订单校验） |

本模块仅查询并展示上述状态，不实现体验券激活 / 收回、试用积分赠送、新用户校验等载体逻辑。试用到期后展示会员卡权益对比与购买入口，衔接付费转化。

### 4.5 VIP 赠送积分联动

权益配置提供 `vip_gift_credits`（各等级差异化，0 表示该等级不赠送），本模块仅提供等级与赠送额度依据；按月发放到账、月末未用部分清零均由 AI 计费承接（source=vip_gift）。

### 4.6 权益校验与扣减

查询会员等级（缓存优先）→ 检查会员状态（冻结抛 A0511）→ 按请求 taskType 取生效配额（已购会员卡取覆盖值与等级权益较高值）→ 校验当月已用 < 配额 → Redis 原子扣减（缓存剩余与生效配额漂移时自动校正）→ 同步落库。DB 路径使用原子行级条件更新（`used < quota`）防并发超扣，落库失败回补 Redis 计数保持两侧一致；配额回补带 `used > 0` 下限，重复回补不产生负数。

会员记录初始化仅复活软删记录（`deleted != 0` 时复活重建为 level_0 并清空月度配额、保留累计消费），活跃会员记录不做降级或清零。

初始化入口有两处：注册流程（新用户）与登录流程兜底（种子账号 root/admin、后台管理界面创建的用户不走注册；幂等，已有活跃档案直接跳过）。Java 端注意：`initMember` 的 upsert 冲突分支会降级 level_0，仅可对确认无活跃档案的用户调用，登录兜底必须先查活跃行（`ensureMemberProfile`）。种子数据为 admin 预置 level_0 会员行与 10 万积分余额（`sys_user.credits_balance`）。

### 4.7 月度配额重置

扫描到达个人重置时点的会员（默认当月 1 日，冻结顺延的会员为当月 1 日 + 顺延天数）：先将上月各任务类型使用情况归档至历史表，再按当前等级（含会员卡覆盖）刷新配额字段并清零已用。幂等由 `quota_reset_month` 条件保证，分批处理（每批 500），单条失败不影响其他会员，处理后失效配额缓存。重置后不推送通知。

### 4.8 冻结 / 解冻

- 冻结：`status=0`，记录冻结原因与时间；冻结期间权益校验拦截
- 解冻：`status=1`，保留冻结历史便于追溯；会员卡到期时间顺延冻结天数，当月配额重置时点按冻结天数顺延

### 4.9 升级 / 降级 / 保级

- 升级：成长值达标或购买会员卡，立即生效；`level_source` 仅记录来源，不影响自动升级；购买会员卡时等级取 max(现等级, 卡等级) 只升不降（见 §4.1）
- 降级：定时扫描到期会员（`expire_time < NOW()` 且来源非 growth），按成长值重算等级（到期回落为成长值阈值推导等级，非延续卡等级），置 `level_source=growth`、清空 `expire_time`、刷新配额；退款扣减成长值触发的降级在回调事务内即时执行
- 保级：会员卡到期但成长值达标，保持等级，来源切换为 growth，不出现权益空窗
- 到期预警：降级后权益对比由等级权益配置计算得出
- **管理员显式覆盖**：后台等级调整直接写入目标等级与 `level_source=admin`（可选自定义到期时间），不受会员卡期间 max(较高者) 约束，也不改变成长值；此后自动升降级规则照常适用

### 4.10 管理端详情弹窗数据接口

会员详情弹窗除基本信息（`getDetail`）外，提供目标会员维度的数据接口（均需 `member:list` 权限）：

| 接口 | 数据来源 |
|------|---------|
| GET /{userId}/growth-logs | 复用成长值流水查询（admin 视角按 userId） |
| GET /{userId}/consumption-records | 复用订单查询 `list_my`（返回订单列表 VO，含订单号/商品/金额/支付时间/状态） |
| GET /{userId}/benefit-usage | 复用 `getBenefitSummary` 按目标会员计算（与用户端权益概览同构的服务类目聚合） |
| GET /{userId}/operation-logs | Mongo 审计日志按 `target_type=member + target_id` 查询（create_time 倒序，转本地时间展示） |

**详情接口越权口径**：`GET /{userId}` 默认仅本人可见（userId≠当前用户且无 `member:list` 权限时返回 A0301）；持 `member:list` 权限可查任意会员（管理端列表/详情弹窗入口）。

## 6. 缓存策略

| 缓存对象 | 缓存 Key | TTL | 更新策略 |
|---------|---------|-----|---------|
| 会员档案 | member:profile:{userId} | 10 分钟 | 等级 / 成长值 / 状态变更时删除 |
| 会员等级 | member:level:{userId} | 10 分钟 | 等级变更时删除 |
| 权益配置 | member:benefit:{levelCode} / member:benefit:all | 30-60 分钟 | 配置修改时同时删除两个 Key |
| 当月配额 | member:quota:{userId}:{taskType} | 至次月 1 日 0 点 | 扣减时 DECR，落库失败回补 INCR，重置/归还时同步 |
| 权益概览聚合 | member:benefit-summary:{userId} | 5 分钟 | 等级变更 / 权益配置修改时删除 |

> 成长值不缓存（实时查询数据库，确保数值准确）；签到记录落库由唯一索引防重，不设缓存。

## 8. 三后端一致性约束

Java 权威，Go/Python 对齐。以下事实三端必须完全一致：`ai_credits_daily` / `ai_credits_monthly` / `multimodal_limit` / `max_devices` 字段（名称、类型、含义）及数据初始化默认值（`config/sql/data/sys_member_benefit.sql` 种子梯度 `max_devices` = 1/3/5/10，列定义 `int NOT NULL DEFAULT 1`，三端实体同名映射，管理端权益配置表单/列表同步暴露）、`change_type` 枚举与 AI 使用激励口径、等级升降级规则、服务类目聚合规则、试用引导状态字段、权益校验与配额扣减的原子性实现、月度重置幂等与冻结顺延逻辑。

## 9. 配置项与常量

### 9.1 营销激励参数（sys_dict 配置）

签到成长值、连续签到奖励、评价成长值（单次 / 每日上限）属于营销激励参数，运营有明确调整动机，统一由字典配置 `sys_dict`（字典类型 `member_growth_rules`）维护，反馈评价模块的成长值激励参数合并于此：

| 字典键 | 说明 | 默认值 |
|--------|------|--------|
| `sign_in_value` | 每日签到获得成长值 | 3 |
| `sign_in_streak_bonus` | 连续签到奖励（连续 7 天额外获得） | 20 |
| `rating_growth_value` | 单次评价获得成长值 | 5 |
| `rating_growth_daily_limit` | 每日评价获得成长值次数上限 | 5 |

### 9.2 代码常量

无管理员/运营需动态调整场景的参数为代码常量（Java `static final` / Go `const` / Python 模块常量）：

| 常量 | 说明 | 值 |
|------|------|-----|
| 月度重置批次大小 | 月度配额重置每批处理用户数 | 500 |
| AI 使用激励每日上限 | `ai_consume` 每日激励次数上限 | 10 |
