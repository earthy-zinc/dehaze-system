# 认证管理模块 - 后端实现设计

## 1. 文档概述

本文档描述认证管理模块的后端实现方案，包括认证流程、Session 机制、验证码生成等核心业务逻辑的实现要点。

- **API 接口规范**：参见 [API接口.md](./API接口.md)
- **需求规格**：参见 [需求规格.md](./需求规格.md)
- **数据库设计**：参见 [02-系统架构/03-数据库设计.md](../../../02-系统架构/03-数据库设计.md)

## 2. 数据传输对象

### 2.1 登录响应对象 (LoginResult)

| 字段 | 类型 | 说明 |
|------|------|------|
| sessionId | String | 会话ID（Web端通过Cookie传递，移动端通过X-Session-Id请求头） |
| user | Object | 用户基本信息（id、username、nickname） |

### 2.2 验证码响应对象 (CaptchaResult)

| 字段 | 类型 | 说明 |
|------|------|------|
| captchaKey | String | 验证码缓存键 |
| captchaBase64 | String | 验证码图片 Base64 字符串 |

## 3. 架构设计

### 3.1 认证流程图

```
客户端                              服务端
  |                                   |
  |-------- 1.获取验证码 -----------> |
  |                                   |  生成验证码图片
  |                                   |  缓存验证码文本
  |<------- 2.返回图片+Key ------------|
  |                                   |
  |------ 3.登录请求(user/pass) -----> |
  |                                   |  校验验证码
  |                                   |  校验用户名密码
  |                                   |  生成 sessionId
  |                                   |  Redis 存储 session
  |<-- Set-Cookie: X-Session-Id ------|
  |                                   |
  |-- 4.业务请求(Cookie自动携带) ----->|
  |                                   |  [SessionFilter]
  |                                   |  从Cookie/Header取sessionId
  |                                   |  查Redis session存在?
  |                                   |  注入SecurityContext
  |                                   |  TTL<1天则滑动续期
  |<------ 5.业务响应 ----------------|
  |                                   |
  |------ 6.注销请求 ---------------> |
  |                                   |  删除Redis session
  |                                   |  清除Cookie
  |<------ 7.注销成功 ----------------|
```

### 3.2 过滤器链路

```
HttpServletRequest
      ↓
[TraceIdFilter]              ← 生成/传播 TraceId
      ↓
[CorsFilter]                 ← 跨域处理
      ↓
[RequestLogFilter]           ← 请求日志记录
      ↓
[SessionFilter]              ← Session 校验 + SecurityContext 注入 + 滑动续期
      ↓
[UsernamePasswordAuthenticationFilter]
      ↓
[ExceptionTranslationFilter]
      ↓
FilterSecurityInterceptor
      ↓
HttpServletResponse
```

## 4. 核心业务逻辑

### 4.1 用户认证流程

#### 4.1.1 登录认证

**入口**：`AuthServiceImpl.login(String username, String password)`

**执行流程**：

1. **用户名预处理**
   - 转换为小写：`username.toLowerCase().trim()`
   - 统一用户名格式，避免大小写敏感问题

2. **认证请求构建**
   - 创建 `UsernamePasswordAuthenticationToken` 对象
   - 封装用户名和密码凭证

3. **认证执行**
   - 调用 `AuthenticationManager.authenticate()`
   - 触发 `UserDetailsService.loadUserByUsername()`
   - 从数据库加载用户信息（`SysUserDetailsService`）
   - 使用 `BCryptPasswordEncoder` 校验密码

4. **Session 创建**（认证成功后）
   - 生成 sessionId = UUID
   - 构建 Session JSON：userId、username、deptId、dataScope、authorities、nickname
   - Redis 存储：`session:{sessionId}`，TTL=604800（7天）
   - Set-Cookie：`X-Session-Id={sessionId}; HttpOnly; Secure; SameSite=Lax; Path=/api`

5. **返回登录结果**
   - 封装 `LoginResult` 对象
   - 包含 `sessionId` 和 `user` 基本信息

#### 4.1.2 请求认证（过滤器）

**入口**：`SessionFilter.doFilterInternal()`

**执行流程**：

1. **SessionId 提取**
   - 优先从 Cookie 读取 `X-Session-Id`
   - 兜底从请求头 `X-Session-Id` 读取（移动端）

2. **Redis 查询**
   - 查询 `session:{sessionId}`
   - 不存在 → 返回 401

3. **用户信息构建**
   - 解析 Session JSON
   - 提取 userId、username、deptId、dataScope、authorities
   - 构建 `SysUserDetails` 对象
   - 创建 `Authentication` 设置到 SecurityContext

4. **滑动续期**
   - 检查 Redis TTL，若剩余 < 1天则续期为 7 天

5. **异常处理**
   - Session 不存在：返回 401
   - 白名单路径（登录、验证码等）：跳过过滤

### 4.2 验证码生成与校验

#### 4.2.1 验证码生成

**入口**：`AuthServiceImpl.getCaptcha()`

**执行流程**：

1. **验证码类型选择**
   - 根据配置 `captcha.type` 选择生成器：
     - `CIRCLE`：圆圈干扰验证码
     - `GIF`：GIF 动态验证码
     - `LINE`：干扰线验证码
     - `SHEAR`：扭曲干扰验证码

2. **参数配置**
   - 图片尺寸：`width` × `height`（默认 120×40）
   - 干扰元素个数：`interfereCount`（默认 2）
   - 字符长度：`code.length`（算术类型表示运算位数）
   - 字体：`font.name`、`font.weight`、`font.size`
   - 透明度：`textAlpha`（默认 0.8）

3. **生成验证码**
   - 使用 `CodeGenerator` 生成验证码文本
   - 生成验证码图片
   - 转换为 Base64 编码字符串

4. **缓存存储**
   - 生成唯一缓存键：`captchaKey = IdUtil.fastSimpleUUID()`
   - Redis 缓存键：`captcha_code:{captchaKey}`
   - 缓存内容：验证码文本（明文）
   - 过期时间：`captcha.expire-seconds`（默认 120 秒）

5. **返回结果**
   - `captchaKey`：用于后续校验
   - `captchaBase64`：客户端显示的图片

#### 4.2.2 验证码校验

**入口**：`CaptchaValidationFilter.doFilterInternal()`

**触发条件**：仅对 `/api/v1/auth/login` POST 请求

**执行流程**：

1. **参数提取**
   - `captchaCode`：用户输入的验证码
   - `captchaKey`：验证码缓存键

2. **兼容性处理**
   - 如果 `captchaCode` 为空，放行（兼容无验证码版本）

3. **缓存查询**
   - 从 Redis 获取：`captcha_code:{captchaKey}`
   - 如果缓存不存在，返回 `VERIFY_CODE_TIMEOUT` 错误

4. **验证码比对**
   - 调用 `codeGenerator.verify(cacheVerifyCode, captchaCode)`
   - 支持大小写不敏感比对
   - 校验失败返回 `VERIFY_CODE_ERROR` 错误
   - 校验成功后继续过滤器链

**状态流转**：
```
生成 → 缓存(120s) → 校验成功/超时
                ↓
            使用后删除（一次性有效）
```

### 4.3 注销

**入口**：`AuthServiceImpl.logout()`

**执行流程**：

1. **SessionId 提取**
   - 从 Cookie 或 `X-Session-Id` 请求头提取 sessionId

2. **Redis 删除**
   - 删除 `session:{sessionId}`，会话立即失效

3. **上下文清理**
   - 调用 `SecurityContextHolder.clearContext()`

### 4.4 会话续期机制

Session 模式无需客户端主动续期。`SessionFilter` 在每次请求时检查 Redis 中 session 的 TTL：

1. 若 TTL < 1天（86400秒），自动续期为 7 天（604800秒）
2. 连续 7 天无操作，session 自然过期

此机制对前端完全透明，用户持续使用即自动续期。

### 4.5 API Key 认证

API Key 面向机器对机器（M2M）调用场景，是默认永不过期的长期身份凭证，详细设计参见 [API Key认证.md](./API%20Key认证.md)。

#### 4.5.1 API Key 创建

**入口**：`ApiKeyService.create(String name, LocalDateTime expiresAt)`

**执行流程**：

1. **凭证生成**
   - 生成随机字符串并拼接固定前缀 `dhak_`，得到 API Key 明文
   - 同时截取前缀片段（`keyPrefix`）用于列表辨识

2. **哈希存储**
   - 计算明文的 SHA-256 哈希值
   - 数据库仅存储哈希值、名称、前缀、归属用户、过期时间，**不存储明文**

3. **返回结果**
   - 仅在创建响应中返回一次明文 `apiKey`
   - 后续任何接口均无法再获取明文

#### 4.5.2 API Key 校验（过滤器分支）

**入口**：`JwtValidationFilter.doFilterInternal()`

**执行流程**：

1. **凭证提取**
   - 从 `Authorization` 请求头获取凭证，移除 "Bearer " 前缀

2. **类型识别**
   - 凭证以 `dhak_` 前缀开头时，进入 API Key 校验分支
   - 否则忽略，交由 SessionFilter 处理 Session 认证

3. **哈希比对**
   - 计算凭证明文的 SHA-256 哈希值
   - 与数据库存储的哈希值比对，定位 API Key 记录

4. **有效性检查**
   - 校验 Key 是否存在、是否已过期（`expiresAt`）
   - 校验失败返回 `A0301` 访问未授权

5. **用户信息构建**
   - 以 Key 所属用户身份构建 `SysUserDetails`
   - 创建 `Authentication` 设置到 SecurityContext，继续后续鉴权

#### 4.5.3 跨后端共享

API Key 存储于共享数据库，**Java / Go / Python** 三个后端服务复用同一份 Key 数据，校验逻辑保持一致：

| 后端 | 校验入口 | 说明 |
|------|---------|------|
| Java | 认证过滤器链 | 识别 `dhak_` 前缀走 API Key 分支 |
| Go | 认证中间件 | 共享数据库，校验逻辑一致 |
| Python | 认证依赖/中间件 | 算法服务复用同一 Key 体系 |

#### 4.5.4 API Key 删除/吊销

**入口**：`ApiKeyService.delete(Long id)`

**执行流程**：

1. **归属校验**：仅允许删除当前用户自己创建的 Key
2. **物理删除**：删除数据库记录，Key 立即失效
3. **即时生效**：删除后使用该 Key 的请求即刻被拒绝

## 5. 缓存设计

### 5.1 Redis 缓存策略

| 缓存对象 | 缓存 Key | 数据类型 | 过期时间 | 更新策略 |
|---------|---------|---------|---------|---------|
| 验证码文本 | `captcha_code:{captchaKey}` | String | 120 秒 | 使用后自动删除 |
| 用户会话 | `session:{sessionId}` | String (JSON) | 7 天 | 每次请求滑动续期，注销时删除 |
| 用户权限 | `role_perms:{userId}` | Hash/Set | 30 分钟 | 角色变更时删除 |

### 5.2 缓存失效策略

| 失效触发场景 | 失效方式 | 说明 |
|-------------|---------|------|
| 验证码校验成功 | 自然过期 | 不主动删除，依赖 TTL |
| 验证码超时 | 自动过期 | Redis TTL 到期自动清理 |
| 会话注销 | 主动删除 | 立即删除 Redis key |
| 会话自然过期 | 自动过期 | 7 天无操作后 TTL 到期 |
| 会话滑动续期 | TTL 重置 | 每次请求 TTL<1天时续期为7天 |

## 6. 安全设计

### 6.1 密码安全

| 策略项 | 配置值 | 实现方式 |
|--------|--------|---------|
| 加密算法 | BCrypt | `BCryptPasswordEncoder` |
| 工作因子 | 10（默认） | BCrypt 内置盐值，抗彩虹表攻击 |
| 密码比对 | `matches(raw, encoded)` | 每次比对自动加盐 |
| 密码存储 | Hash + Salt | 不存储明文密码 |

**密码校验流程**：
```
用户输入密码 → BCryptPasswordEncoder.matches()
                    ↓
            从数据库取出加密密码
                    ↓
            自动加盐 + 比对 Hash 值
                    ↓
            返回 true/false
```

### 6.2 Session Cookie 安全

| 安全措施 | 实现方式 | 说明 |
|---------|---------|------|
| HttpOnly | `true` | JavaScript 无法读取，彻底防 XSS |
| Secure | `true` | 仅 HTTPS 传输 |
| SameSite | `Lax` | 防止跨站请求携带 Cookie |
| Path | `/api` | 仅 API 路径携带，减少暴露面 |
| 即时吊销 | Redis 删除 | 注销时立即删除，无滞后 |
| SessionId 随机 | UUID | 不可预测，防暴力猜解 |

### 6.3 防暴力破解

| 防护措施 | 实现方式 | 说明 |
|---------|---------|------|
| 验证码 | 图形验证码 | 防止自动化脚本攻击 |
| 验证码有效期 | 120 秒 | 限制验证码使用窗口 |
| 验证码一次性 | 使用后失效 | 防止重放攻击 |
| 用户名规范 | 小写 + 去空格 | 统一格式，避免枚举 |

### 6.4 CSRF 防护

当前 CSRF 配置已禁用：
```java
http.csrf(AbstractHttpConfigurer::disable)
```

**理由**：
- Session Cookie 使用 `SameSite=Lax`，跨站请求不会携带 Cookie
- CORS 白名单限制 + `allowCredentials=true` 仅允许可信 Origin
- 移动端使用 `X-Session-Id` 请求头，不受 CSRF 影响

## 7. 并发控制

### 7.1 登录并发控制

**当前状态**：未实现登录并发限制

**潜在风险**：
- 同一账号多地登录，多个 Session 并存

**扩展建议**：
1. 实现 Session 设备绑定（Device ID）
2. 单点登录机制（SSO）
3. 登录历史记录与告警

### 7.2 验证码并发控制

**机制**：基于 UUID 的验证码 Key 实现隔离
- 每次获取验证码生成独立 Key
- 客户端需携带 Key 才能校验
- 多次获取验证码互不影响

## 10. 性能优化

### 10.1 数据库查询优化

- `UserDetailsService` 仅查询必要字段（用户名、密码、状态）
- 角色权限信息加载使用 JOIN 查询或缓存
- 索引：`sys_user.username` 唯一索引

### 10.2 缓存优化

- 验证码缓存短期存储（120 秒），减少 Redis 内存占用
- Session 基于 TTL 自动过期，避免数据堆积
- 权限信息缓存（30 分钟），减少数据库查询

### 10.3 认证流程优化

- Session 校验仅一次 Redis GET 操作，性能高
- 过滤器链仅对必要接口执行校验

## 11. 扩展性设计

### 11.1 多因素认证扩展点

当前为用户名+密码+验证码三因素认证，可扩展：

1. **短信验证码**：替换或补充图形验证码
2. **邮箱验证码**：密码重置场景
3. **TOTP 动态口令**：高安全场景
4. **OAuth2 第三方登录**：微信、钉钉等

### 11.2 认证类型扩展

支持多种认证类型：
- **Session**：当前实现（Redis 存储，滑动续期）
- **API Key**：机器对机器调用（已实现，参见 4.5 节）

### 11.3 认证方式扩展

支持多种认证方式：
- **用户名密码认证**：当前实现
- **手机号验证码认证**：无密码登录
- **第三方认证**：OAuth2 / SAML

扩展需实现 `AuthenticationProvider` 接口。

## 12. 事务边界

认证模块主要涉及只读操作，事务边界如下：

| 操作 | 事务类型 | 说明 |
|------|---------|------|
| 用户登录 | 无事务 | 读取用户信息，创建 Session |
| 验证码校验 | 无事务 | Redis 读取 |
| 注销 | 无事务 | Redis 写入，不需要数据库事务 |

**注意**：
- 认证模块不涉及用户数据变更
- 密码修改等操作由用户管理模块负责
- 登录日志记录建议异步处理

## 13. 监控与日志

### 13.1 关键日志点

| 日志点 | 级别 | 说明 |
|--------|------|------|
| 登录成功 | INFO | 记录用户名、IP、时间 |
| 登录失败 | WARN | 记录失败原因（密码错误、账号禁用等） |
| Session 验证失败 | WARN | 记录 Session 异常（不存在、过期） |
| 验证码校验失败 | DEBUG | 记录客户端 IP、频率 |
| 注销操作 | INFO | 记录注销用户、时间 |

### 13.2 监控指标

| 指标 | 说明 | 告警阈值 |
|------|------|---------|
| 登录失败率 | 失败次数/总次数 | > 30% |
| Session 验证失败率 | 无效或过期 Session | > 10% |
| 验证码生成速率 | 每秒生成次数 | > 100/s（可能刷验证码） |

## 15. 异步与批量场景的权限与审计注意事项

### 15.1 异步任务的数据权限降级

三端数据权限均依赖请求上下文（Java ThreadLocal / Go context / Python ContextVar），异步任务（MQ 消费者、`@Async`、`asyncio.Task`）需要显式处理上下文传播，否则数据权限会降级：

| 端 | 异步路径 | 当前实现 | 状态 |
|---|---|---|---|
| Java | `@Async` | `AsyncConfig.asyncContextTaskDecorator` 同时传播 `SecurityContext` 和 MDC | 已修复 |
| Java | MQ 消费者 | `RabbitMQConsumer.processMessage` 调用 `SystemSecurityContext.setSystemContext()`，以系统身份执行（系统用户拥有全部数据权限） | 有意降级为系统身份 |
| Go | 主队列 | `app.go` 明确声明 Go 不消费 export 主队列（由 Java/Python 执行任务），只消费 DLQ 更新任务状态 | 不适用 |
| Go | DLQ 消费者 | `consumer.go` 仅注入 `userID`，未设置 `DataScope`；GORM Callback 中 `GetDataScope` 未设置时返回 `DataScopeAll`（全部数据），是有意为之的安全默认值 | 有意降级 |
| Python | MQ handler | `handlers.py` 通过 `set_current_user_id(user_id)` 从消息体恢复 user_id 到 ContextVar；但 Python 无 dataScope ContextVar，需要数据权限时主动调用 `RoleService.get_maximum_data_scope` 查 DB | 部分修复 |

**改进方向**：若异步任务需以原用户身份执行细粒度数据权限（而非系统身份），可从消息头恢复原始用户身份及其 dataScope；当前以系统身份执行的方案能满足导出/下载等系统级任务需求。

### 15.2 审计字段在批量操作中的填充

审计字段（create_by/update_by）在批量更新场景下需要特别处理，因为 ORM 框架的批量更新 API 通常不会触发字段自动填充：

| 端 | 审计填充器 | 批量场景处理 | 状态 |
|---|---|---|---|
| Java | `MyMetaObjectHandler`，无安全上下文时回退 `SystemConstants.SYSTEM_USER_ID` | MyBatis-Plus `LambdaUpdateWrapper` 不触发 `updateFill`，所有调用点已显式 `.set(updateBy, currentUserId)` | 已修复 |
| Go | `RegisterGormCallbacks` 在 MySQL/Postgres/SQLite 三种 driver 初始化时均注册，支持 struct / slice / map 形态 | GORM Callback 直接拦截批量更新 | 已修复 |
| Python | `base.py` 提供 `get_audit_update_values()` 工具函数，无 user_id 时回退 `SYSTEM_USER_ID` | SQLAlchemy ORM `before_update` 事件对 Core `update()` 不触发是框架固有限制，所有 Core update 调用点已显式调用 `get_audit_update_values()` 注入审计字段 | 已有 workaround |

**结论**：三端审计字段填充均已覆盖批量与异步场景，无需额外改进。
