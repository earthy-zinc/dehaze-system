# 认证管理模块 - 后端实现设计

## 1. 文档概述

本文档描述认证管理模块的后端实现方案，包括认证流程、Session 机制、验证码生成等核心业务逻辑的实现要点。

- **API 接口规范**：参见 [API接口.md](./API接口.md)
- **需求规格**：参见 [需求规格.md](./需求规格.md)
- **数据库设计**：参见 [02-系统架构/03-数据库设计.md](../../../02-系统架构/03-数据库设计.md)

## 2. 数据传输对象

### 2.1 登录响应对象 (LoginResult)

| 字段 | 类型 | 说明 |
|------|------|------|
| sessionId | String | 会话ID（Web端通过Cookie传递，移动端通过X-Session-Id请求头） |
| user | Object | 用户基本信息（id、username、nickname） |

### 2.2 验证码响应对象 (CaptchaResult)

## 3. 架构设计

### 3.1 认证流程图

```
客户端                              服务端
  |                                   |
  |-------- 1.获取验证码 -----------> |
  |                                   |  生成验证码图片
  |                                   |  缓存验证码文本
  |<------- 2.返回图片+Key ------------|
  |                                   |
  |------ 3.登录请求(user/pass/rememberMe) -----> |
  |                                   |  校验验证码
  |                                   |  校验用户名密码
  |                                   |  生成 sessionId
  |                                   |  Redis 存储 session
  |<-- Set-Cookie: X-Session-Id + Max-Age ------|
  |                                   |
  |-- 4.业务请求(Cookie自动携带) ----->|
  |                                   |  [SessionFilter]
  |                                   |  从Cookie/Header取sessionId
  |                                   |  查Redis session存在?
  |                                   |  注入SecurityContext
  |                                   |  TTL<1天则滑动续期
  |<------ 5.业务响应 ----------------|
  |                                   |
  |------ 6.注销请求 ---------------> |
  |                                   |  删除Redis session
  |                                   |  清除Cookie
  |<------ 7.注销成功 ----------------|
```

```

      ↓

      ↓

      ↓

```

## 4. 核心业务逻辑

### 4.1 用户认证流程

#### 4.1.1 登录认证

**入口**：`AuthServiceImpl.login(String username, String password, boolean rememberMe)`

**执行流程**：

1. **用户名预处理**
   - 转换为小写：`username.toLowerCase().trim()`
   - 统一用户名格式，避免大小写敏感问题

2. **认证请求构建**
   - 创建 `UsernamePasswordAuthenticationToken` 对象
   - 封装用户名和密码凭证

3. **认证执行**
   - 调用 `AuthenticationManager.authenticate()`
   - 触发 `UserDetailsService.loadUserByUsername()`
   - 从数据库加载用户信息（`SysUserDetailsService`）
   - 使用 `BCryptPasswordEncoder` 校验密码

4. **Session 创建**（认证成功后）
   - 生成 sessionId = UUID
   - 构建 Session JSON：userId、username、deptId、dataScope、authorities、nickname
   - Redis 存储：`session:{sessionId}`，TTL=604800（7天，始终为 7 天滑动续期，与是否记住我无关）
   - 写入用户会话索引 `session:user:{userId}`（Set 结构，元素为 `sessionId:deviceType`）
   - Set-Cookie：`X-Session-Id={sessionId}; HttpOnly; Secure; SameSite=Lax; Path=/api; Max-Age={rememberMe ? 604800 : -1}`

5. **返回登录结果**
   - 封装 `LoginResult` 对象
   - 包含 `sessionId` 和 `user` 基本信息

#### 4.1.2 请求认证（过滤器）

**入口**：`SessionFilter.doFilterInternal()`

**执行流程**：

1. **SessionId 提取**
   - 优先从 Cookie 读取 `X-Session-Id`
   - 兜底从请求头 `X-Session-Id` 读取（移动端）

2. **Redis 查询**
   - 查询 `session:{sessionId}`
   - 不存在 → 返回 401

3. **用户信息构建**
   - 解析 Session JSON
   - 提取 userId、username、deptId、dataScope、authorities
   - 构建 `SysUserDetails` 对象
   - 创建 `Authentication` 设置到 SecurityContext

4. **滑动续期**
   - 检查 Redis TTL，若剩余 < 1天则续期为 7 天

5. **异常处理**
   - Session 不存在：返回 401
   - 白名单路径（登录、验证码等）：跳过过滤

> **权限时效保障**：Session 内嵌 authorities/dataScope 作为快照加速鉴权，角色变更时通过 `session:user:{userId}` 索引联动失效受影响 Session（详见 5.2），确保权限在角色调整后立即刷新，不存在 7 天滑动期内持有旧权限的越权风险。

### 4.2 验证码生成与校验

#### 4.2.1 验证码生成

**入口**：`AuthServiceImpl.getCaptcha()`

**执行流程**：

1. **验证码类型选择**
   - 根据配置 `captcha.type` 选择生成器：`CIRCLE`/`GIF`/`LINE`/`SHEAR`

2. **参数配置**
   - 图片尺寸、干扰元素个数、字符长度、字体、透明度等均通过 `captcha.*` 配置项控制

3. **生成验证码**
   - 使用 `CodeGenerator` 生成验证码文本
   - 生成验证码图片
   - 转换为 Base64 编码字符串

4. **缓存存储**
   - 生成唯一缓存键：`captchaKey = IdUtil.fastSimpleUUID()`
   - Redis 缓存键：`captcha_code:{captchaKey}`
   - 缓存内容：验证码文本（明文）
   - 过期时间：`captcha.expire-seconds`（默认 300 秒，即 5 分钟）

5. **返回结果**
   - `captchaKey`：用于后续校验
   - `captchaBase64`：客户端显示的图片

#### 4.2.2 验证码校验

**入口**：`AuthServiceImpl.login()` / `AuthServiceImpl.register()`

**说明**：验证码校验逻辑已内联到登录和注册方法中，不再使用独立的 `CaptchaValidationFilter`。

**执行流程**：

1. **参数提取**
   - `captchaCode`：用户输入的验证码
   - `captchaKey`：验证码缓存键

2. **缓存查询**
   - 从 Redis 获取：`captcha_code:{captchaKey}`
   - 如果缓存不存在，返回 `VERIFY_CODE_TIMEOUT` 错误

3. **验证码比对**
   - 调用 `codeGenerator.verify(cacheVerifyCode, captchaCode)`
   - 支持大小写不敏感比对
   - 校验失败返回 `VERIFY_CODE_ERROR` 错误
   - 校验成功后删除缓存（一次性有效）

**状态流转**：
```
生成 → 缓存(5min) → 校验成功/超时
                ↓
            校验成功后删除（一次性有效）
```

### 4.3 注销

**入口**：`AuthServiceImpl.logout()`

**执行流程**：

1. **SessionId 提取**
   - 从 Cookie 或 `X-Session-Id` 请求头提取 sessionId

2. **Session 删除**
   - 删除 `session:{sessionId}`，会话立即失效

3. **索引与缓存清理**
   - 从 `session:user:{userId}` 索引移除当前端元素（`sessionId:deviceType`）
   - 清理用户信息缓存 `user:info:{userId}` 和用户权限缓存 `user:perms:{userId}`（下次请求重建）

4. **上下文清理**
   - 调用 `SecurityContextHolder.clearContext()`

> 多端会话共存策略下，注销仅清理当前端 Session 与索引元素，不影响该用户其他端的活跃会话。清理 `user:info`/`user:perms` 属缓存失效，不影响其他端会话有效性。

### 4.4 会话续期机制

Session 模式无需客户端主动续期。`SessionFilter` 在每次请求时检查 Redis 中 session 的 TTL：

1. 若 TTL < 1天（86400秒），自动续期为 7 天（604800秒）
2. 连续 7 天无操作，session 自然过期

此机制对前端完全透明，用户持续使用即自动续期。

### 4.5 API Key 认证

API Key 面向机器对机器（M2M）调用场景，是默认永不过期的长期身份凭证，详细设计参见 [API Key认证.md](./API%20Key认证.md)。

#### 4.5.1 API Key 创建

**入口**：`ApiKeyService.create(String name, LocalDateTime expiresAt)`

**执行流程**：

1. **凭证生成**
   - 生成随机字符串并拼接固定前缀 `dhak_`，得到 API Key 明文（前缀 `dhak_` 占 5 字符，明文总长 53 字符）
   - 截取前缀片段（`keyPrefix`，9 字符，如 `dhak_a1b2`）用于列表辨识

2. **哈希存储**
   - 计算明文的 SHA-256 哈希值
   - 数据库仅存储哈希值、名称、前缀、归属用户、过期时间，**不存储明文**

3. **返回结果**
   - 仅在创建响应中返回一次明文 `apiKey`
   - 后续任何接口均无法再获取明文

#### 4.5.2 API Key 校验（独立过滤器）

**入口**：`ApiKeyAuthenticationFilter`（Java）/ `ApiKeyAuthMiddleware`（Go）/ `ApiKeyAuthMiddleware`（Python）

**执行流程**：

1. **凭证提取**
   - 从 `Authorization` 请求头获取凭证，移除 "Bearer " 前缀

2. **类型识别**
   - 凭证以 `dhak_` 前缀开头时，进入 API Key 校验分支
   - 否则交由后续 `SessionFilter` 走 Session Cookie 认证流程

3. **哈希比对（带缓存）**
   - 计算凭证明文的 SHA-256 哈希值
   - 优先查询 Redis 缓存 `apikey:hash:{hash}` 获取 userId，命中则跳过 DB 查询
   - 未命中时与数据库存储的哈希值比对，定位 API Key 记录，命中后回写缓存（TTL 10 分钟）

4. **有效性检查**
   - 校验 Key 是否存在、是否已过期（`expiresAt`）
   - 校验失败返回 `A0301` 访问未授权

5. **用户信息构建**
   - 以 Key 所属用户身份构建 `SysUserDetails`
   - 创建 `Authentication` 设置到 SecurityContext，继续后续鉴权

#### 4.5.3 跨后端共享

API Key 存储于共享数据库，**Java / Go / Python** 三个后端服务复用同一份 Key 数据，校验逻辑保持一致：

| 后端 | 校验入口 | 说明 |
|------|---------|------|
| Java | `ApiKeyAuthenticationFilter`（独立 Filter） | 识别 `dhak_` 前缀走 API Key 分支 |
| Go | `ApiKeyAuthMiddleware`（独立中间件） | 共享数据库，校验逻辑一致 |
| Python | `ApiKeyAuthMiddleware`（独立 ASGI 中间件） | 算法服务复用同一 Key 体系 |

#### 4.5.4 AI 计费配额协作

API Key 认证通过后，userId 随 `SecurityContext` 注入请求上下文。AI 计费模块在处理 M2M 调用时，从上下文提取 userId 校验调用配额，配额超限时拒绝请求。此约定确保 M2M 调用既完成身份认证又受配额约束，三端后端在认证通过后均以相同方式注入 userId。

#### 4.5.5 API Key 删除/吊销

**入口**：`ApiKeyService.delete(Long id)`

**执行流程**：

1. **归属校验**：仅允许删除当前用户自己创建的 Key
2. **物理删除**：删除数据库记录，Key 立即失效
3. **缓存清理**：删除 Redis 中对应的 `apikey:hash:{hash}` 缓存
4. **即时生效**：删除后使用该 Key 的请求即刻被拒绝

#### 4.5.6 Redis 降级策略（Python 端）

API Key 认证依赖 Redis 缓存加速权限查询（`role:perms:{roleCode}`、`apikey:hash:{hash}`）。Redis 不可用时，`data_scope` 与 `perms` 均采用**最小权限**降级方向，避免 Redis 故障期间获得越权访问：

| 字段 | Redis 可用 | Redis 不可用（降级） | 说明 |
|------|-----------|-------------------|------|
| `data_scope` | 查询角色最大数据范围 | `1`（仅本人） | 降级为最小数据范围，与 `perms` 降级方向一致 |
| `perms` | 查询角色权限标识集合 | `set()`（空集） | 无任何操作权限 |

> **设计原则**：Redis 故障且无法获取角色权限时，API Key 请求应仅能访问本人数据（`data_scope=1`）且无细粒度操作权限。此前 Python 端 `data_scope` 降级为 `0`（全部数据），与 `perms` 降级为空集的方向矛盾，已在改造中修正为 `1`。此降级策略与 §2 行级数据权限过滤协同——`data_scope=1` 经 `apply_data_scope` 过滤后仅返回本人创建的数据，收敛 Redis 故障期间的越权风险。

## 5. 缓存设计

### 5.1 Redis 缓存策略

| 缓存对象 | 缓存 Key | 数据类型 | 过期时间 | 更新策略 |
|---------|---------|---------|---------|---------|
| 验证码文本 | `captcha_code:{captchaKey}` | String | 5 分钟 | 校验成功后立即删除 |
| 账户绑定验证码 | `verify_code:{type}:{account}` | String | 5 分钟 | 校验成功后立即删除 |
| 用户会话 | `session:{sessionId}` | String (JSON) | 7 天 | 每次请求滑动续期，注销时删除 |
| 用户会话索引 | `session:user:{userId}` | Set | 7 天 | 登录写入元素、注销/踢出移除元素、角色变更时清空 |
| 登录失败计数 | `login:fail:{ip}:{username}` | String | 30 分钟 | 成功登录清零；锁定期内累计 |
| 角色权限 | `role:perms:{roleCode}` | String (JSON 数组) | 30 分钟 | 角色变更时删除重建 |
| API Key 哈希映射 | `apikey:hash:{hash}` | String (userId) | 10 分钟 | 首次认证写入；Key 删除/吊销时主动删除 |

### 5.2 缓存失效策略

| 失效触发场景 | 失效方式 | 说明 |
|-------------|---------|------|
| 验证码校验成功 | 主动删除 | 立即删除缓存键，一次性有效 |
| 验证码超时 | 自动过期 | Redis TTL 到期自动清理 |
| 会话注销 | 主动删除 | 立即删除 Redis key 并从索引移除 |
| 会话自然过期 | 自动过期 | 7 天无操作后 TTL 到期 |
| 会话滑动续期 | TTL 重置 | 每次请求 TTL<1天时续期为7天 |
| 会话踢出 | 主动删除 | 管理员踢出后立即删除并从索引移除 |
| 角色变更（权限调整/角色删除/角色禁用） | 主动删除 | 查询该角色下所有用户，通过 `session:user:{userId}` 索引定位其全部 Session，批量删除 `session:{sessionId}` 并清空索引；同时删除 `role:perms:{roleCode}` 缓存 |

> **角色变更权限联动**：Session 内嵌 authorities/dataScope 作为鉴权快照，角色变更时必须联动失效受影响用户的全部 Session，确保权限即时刷新。此机制依赖 `session:user:{userId}` 索引，由用户管理/角色管理模块在角色调整时触发，认证模块提供索引维护与 Session 清除能力。

## 6. 安全设计

### 6.1 密码安全

| 策略项 | 配置值 | 实现方式 |
|--------|--------|---------|
| 密码存储 | 加密存储（自带盐值） | 不存储明文密码 |
| 工作因子 | 10（默认） | 抗彩虹表攻击 |
| 密码比对 | 加密比对 | 每次比对自动加盐 |

**密码校验流程**：
```
用户输入密码 → 从数据库取出加密密码 → 自动加盐并比对哈希值 → 返回是否匹配
```

### 6.2 Session Cookie 安全

| 安全措施 | 实现方式 | 说明 |
|---------|---------|------|
| HttpOnly | `true` | JavaScript 无法读取，彻底防 XSS |
| Secure | `true`（生产）/ `false`（开发） | 仅 HTTPS 传输；开发环境 HTTP 需关闭 |
| SameSite | `Lax` | 防止跨站请求携带 Cookie |
| Path | `/api`（生产）/ `/`（开发） | 仅 API 路径携带；开发环境 Vite 代理需用 `/` |
| Max-Age | `604800`（记住我）/ `-1`（非记住我） | 记住我：7天持久化；非记住我：浏览器关闭即清除 |
| 即时吊销 | Redis 删除 | 注销时立即删除，无滞后 |
| SessionId 随机 | UUID | 不可预测，防暴力猜解 |

> Redis Session TTL 在两种记住我模式下均为 7 天滑动续期，区别仅在 Cookie 生命周期：非记住我时浏览器关闭后 Cookie 被清除，但服务端 Session 仍存活至 TTL 到期或主动注销。

### 6.3 防暴力破解

| 防护措施 | 实现方式 | 说明 |
|---------|---------|------|
| 验证码 | 图形验证码 | 防止自动化脚本攻击 |
| 验证码有效期 | 5 分钟 | 限制验证码使用窗口 |
| 验证码一次性 | 使用后失效 | 防止重放攻击 |
| 登录失败锁定 | 同一 IP 对同一用户名连续 5 次失败锁定 30 分钟 | Redis key `login:fail:{ip}:{username}` 双维度计数，防同一 IP 对不同用户名爆破；锁定期内拒绝登录（含正确密码）；中途成功登录计数清零；非凭证类异常不计入 |
| 用户名规范 | 小写 + 去空格 | 统一格式，避免枚举 |

### 6.4 CSRF 防护

当前 CSRF 防护已禁用。

**理由**：
- Session Cookie 使用 `SameSite=Lax`，跨站请求不会携带 Cookie
- CORS 白名单限制 + `allowCredentials=true` 仅允许可信 Origin
- 移动端使用 `X-Session-Id` 请求头，不受 CSRF 影响

## 7. 并发控制

### 7.1 多端会话共存控制

**策略**：多端会话共存（不互踢）。同一账号在 Web + 移动端 + 小程序 + 桌面端同时登录时，各端独立持有 Session，互不踢出；Session 按 deviceType 区分存储。管理员可通过会话管理接口手动踢出指定会话。

| 端 | 实现要点 | 说明 |
|-----|---------|------|
| Java | `AuthServiceImpl` 登录时按 deviceType 创建独立 Session，写入 `session:user:{userId}` 索引（Set 结构） | 不再删除旧端 Session |
| Go | `auth_service.Login` 同上，按 deviceType 创建独立 Session 并写入索引 | 不再删除旧端 Session |
| Python | `AuthService.login` 同上，按 deviceType 创建独立 Session 并写入索引 | 不再删除旧端 Session |

**会话索引**：Redis 维护 `session:user:{userId}`（Set 结构，元素为 `sessionId:deviceType`），登录时写入、注销/踢出时移除对应元素、角色变更时清空整组。

**同端重复登录**：同一 deviceType 重复登录时，默认替换同端旧 Session（删除旧 Session 并从索引移除），避免同端会话堆积。

**管理员踢出**：管理员调用 `DELETE /api/v1/auth/sessions/{sessionId}` 踢出指定会话，后端删除对应 `session:{sessionId}` 并从 `session:user:{userId}` 索引移除；超级管理员会话不可被踢出。

### 7.2 验证码并发控制

**机制**：基于 UUID 的验证码 Key 实现隔离
- 每次获取验证码生成独立 Key
- 客户端需携带 Key 才能校验
- 多次获取验证码互不影响

## 10. 事务边界

认证模块主要涉及只读操作，事务边界如下：

| 操作 | 事务类型 | 说明 |
|------|---------|------|
| 用户登录 | 无事务 | 读取用户信息，创建 Session |
| 验证码校验 | 无事务 | Redis 读取 |
| 注销 | 无事务 | Redis 写入，不需要数据库事务 |

**注意**：
- 认证模块不涉及用户数据变更
- 密码修改等操作由用户管理模块负责
- 登录日志记录建议异步处理

## 12. 异步与批量场景的权限与审计注意事项

### 12.1 异步任务的数据权限传递

三端数据权限均依赖请求上下文（Java 线程局部 / Go context / Python ContextVar），异步任务（MQ 消费者、异步方法、异步任务）需显式处理上下文传播：

| 端 | 异步路径 | 处理方式 |
|---|---|---|
| Java | 异步方法 | 异步装饰器同时传播登录上下文与日志上下文 |
| Java | MQ 消费者 | 以系统身份执行（系统用户拥有全部数据权限），满足导出/下载等系统级任务需求 |
| Go | DLQ 消费者 | 从消息体注入用户 ID；数据权限未设置时按安全默认值（全部数据）处理 |
| Python | MQ handler | 从消息体恢复用户 ID 到上下文；需要数据权限时查询用户最大数据范围 |

> 设计取舍：异步系统级任务（导出/下载）以系统身份执行，若需以原用户身份执行细粒度数据权限，可从消息头恢复原始用户身份及其数据范围。

### 12.2 审计字段在批量操作中的填充

审计字段（创建人/更新人）在批量更新场景下需要显式填充（ORM 框架的批量更新 API 通常不触发自动填充），三端处理方式：

| 端 | 处理方式 |
|---|---|
| Java | 无安全上下文时回退系统用户，批量更新调用点显式设置操作人字段 |
| Go | 数据库回调在初始化时注册，直接拦截批量更新注入审计字段 |
| Python | 提供审计字段工具函数，无用户 ID 时回退系统用户，Core 更新调用点显式调用注入 |

## 13. 三端实现差异对比

### 13.1 完整对比表

| 特性 | Java | Go | Python | 差异说明 |
|------|------|-----|--------|---------|
| **验证码校验入口** | `AuthServiceImpl.login()/register()` 内联 | `auth_service.Login()/Register()` 内联 | `AuthService.login()/register()` 内联 | 三端一致 ✓ |
| **API Key 认证入口** | `ApiKeyAuthenticationFilter`（独立 Filter） | `ApiKeyAuthMiddleware`（独立中间件） | `ApiKeyAuthMiddleware`（独立 ASGI 中间件） | 三端一致 ✓ |
| **Session 配置方式** | `SecurityConstants` 统一常量 | `middleware/session.go` 统一常量 | `dependencies/auth.py` 统一常量 | 三端一致 ✓ |
| **防暴力锁定** | IP + 用户名双纬度 Redis 计数 `login:fail:{ip}:{username}` | 同左 | 同左 | 三端一致 ✓ |
| **多端会话共存** | 按 deviceType 创建独立 Session + `session:user:{userId}` 索引 | 同左 | 同左 | 三端一致 ✓（多端不互踢，管理员可踢出） |
| **验证码错误计入失败次数** | ✓（验证码校验在 login 方法内） | ✓（验证码校验在 Login 方法内） | ✓（验证码校验已下沉到 login 方法内） | 三端一致 ✓ |
| **API Key 前缀长度** | `dhak_` + 48 字符，keyPrefix 9 字符 | `dhak_` + 48 字符，keyPrefix 9 字符 | `dhak_` + 48 字符，keyPrefix 9 字符 | 三端一致 ✓ |
| **API Key 哈希缓存** | `apikey:hash:{hash}` → userId，TTL 10 分钟 | 同左 | 同左 | 三端一致 ✓ |
| **验证码生成方式** | Hutool Captcha（4种类型） | base64Captcha（digit driver） | Pillow + Redis | 生成方式不同，互不影响的独立实现 |
| **Session TTL 续期** | Redis `getExpire` + `expire` | Redis `TTL` + `Expire` | Redis `ttl` + `expire` | 逻辑一致 |
| **注销清理范围** | 删除 `session:{sessionId}`，从 `session:user:{userId}` 索引移除当前端，清理 `user:info:{userId}` + `user:perms:{userId}` | 同左 | 同左 | 三端一致 ✓（多端共存下仅清理当前端，不影响其他端会话） |
| **记住我 Cookie Max-Age** | 记住我 604800 / 非记住我 -1 | 同左 | 同左 | 三端一致 ✓ |
