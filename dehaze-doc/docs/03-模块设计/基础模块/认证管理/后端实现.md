# 认证管理模块 - 后端实现设计

## 1. 文档概述

本文档描述认证管理模块的后端实现方案，包括认证流程、Session 机制、验证码生成等核心业务逻辑的实现要点。

- **API 接口规范**：参见 [API接口.md](./API接口.md)
- **需求规格**：参见 [需求规格.md](./需求规格.md)
- **数据库设计**：参见 [02-系统架构/03-数据库设计.md](../../../02-系统架构/03-数据库设计.md)

## 2. 数据传输对象

### 2.1 登录响应对象 (LoginResult)

| 字段 | 类型 | 说明 |
|------|------|------|
| sessionId | String | 会话ID（Web端通过Cookie传递，移动端通过X-Session-Id请求头） |
| user | Object | 用户基本信息（id、username、nickname） |

### 2.2 验证码响应对象 (CaptchaResult)

| 字段 | 类型 | 说明 |
|------|------|------|
| captchaKey | String | 验证码缓存键 |
| captchaBase64 | String | 验证码图片 Base64 字符串 |

## 3. 架构设计

### 3.1 认证流程图

```
客户端                              服务端
  |                                   |
  |-------- 1.获取验证码 -----------> |
  |                                   |  生成验证码图片
  |                                   |  缓存验证码文本
  |<------- 2.返回图片+Key ------------|
  |                                   |
  |------ 3.登录请求(user/pass) -----> |
  |                                   |  校验验证码
  |                                   |  校验用户名密码
  |                                   |  生成 sessionId
  |                                   |  Redis 存储 session
  |<-- Set-Cookie: X-Session-Id ------|
  |                                   |
  |-- 4.业务请求(Cookie自动携带) ----->|
  |                                   |  [SessionFilter]
  |                                   |  从Cookie/Header取sessionId
  |                                   |  查Redis session存在?
  |                                   |  注入SecurityContext
  |                                   |  TTL<1天则滑动续期
  |<------ 5.业务响应 ----------------|
  |                                   |
  |------ 6.注销请求 ---------------> |
  |                                   |  删除Redis session
  |                                   |  清除Cookie
  |<------ 7.注销成功 ----------------|
```

### 3.2 过滤器链路

```
HttpServletRequest
      ↓
[TraceIdFilter]              ← 生成/传播 TraceId
      ↓
[CorsFilter]                 ← 跨域处理
      ↓
[RequestLogFilter]           ← 请求日志记录
      ↓
[SessionFilter]              ← Session 校验 + SecurityContext 注入 + 滑动续期
      ↓
[UsernamePasswordAuthenticationFilter]
      ↓
[ExceptionTranslationFilter]
      ↓
FilterSecurityInterceptor
      ↓
HttpServletResponse
```

## 4. 核心业务逻辑

### 4.1 用户认证流程

#### 4.1.1 登录认证

**入口**：`AuthServiceImpl.login(String username, String password)`

**执行流程**：

1. **用户名预处理**
   - 转换为小写：`username.toLowerCase().trim()`
   - 统一用户名格式，避免大小写敏感问题

2. **认证请求构建**
   - 创建 `UsernamePasswordAuthenticationToken` 对象
   - 封装用户名和密码凭证

3. **认证执行**
   - 调用 `AuthenticationManager.authenticate()`
   - 触发 `UserDetailsService.loadUserByUsername()`
   - 从数据库加载用户信息（`SysUserDetailsService`）
   - 使用 `BCryptPasswordEncoder` 校验密码

4. **Session 创建**（认证成功后）
   - 生成 sessionId = UUID
   - 构建 Session JSON：userId、username、deptId、dataScope、authorities、nickname
   - Redis 存储：`session:{sessionId}`，TTL=604800（7天）
   - Set-Cookie：`X-Session-Id={sessionId}; HttpOnly; Secure; SameSite=Lax; Path=/api`

5. **返回登录结果**
   - 封装 `LoginResult` 对象
   - 包含 `sessionId` 和 `user` 基本信息

#### 4.1.2 请求认证（过滤器）

**入口**：`SessionFilter.doFilterInternal()`

**执行流程**：

1. **SessionId 提取**
   - 优先从 Cookie 读取 `X-Session-Id`
   - 兜底从请求头 `X-Session-Id` 读取（移动端）

2. **Redis 查询**
   - 查询 `session:{sessionId}`
   - 不存在 → 返回 401

3. **用户信息构建**
   - 解析 Session JSON
   - 提取 userId、username、deptId、dataScope、authorities
   - 构建 `SysUserDetails` 对象
   - 创建 `Authentication` 设置到 SecurityContext

4. **滑动续期**
   - 检查 Redis TTL，若剩余 < 1天则续期为 7 天

5. **异常处理**
   - Session 不存在：返回 401
   - 白名单路径（登录、验证码等）：跳过过滤

### 4.2 验证码生成与校验

#### 4.2.1 验证码生成

**入口**：`AuthServiceImpl.getCaptcha()`

**执行流程**：

1. **验证码类型选择**
   - 根据配置 `captcha.type` 选择生成器：
     - `CIRCLE`：圆圈干扰验证码
     - `GIF`：GIF 动态验证码
     - `LINE`：干扰线验证码
     - `SHEAR`：扭曲干扰验证码

2. **参数配置**
   - 图片尺寸：`width` × `height`（默认 120×40）
   - 干扰元素个数：`interfereCount`（默认 2）
   - 字符长度：`code.length`（算术类型表示运算位数）
   - 字体：`font.name`、`font.weight`、`font.size`
   - 透明度：`textAlpha`（默认 0.8）

3. **生成验证码**
   - 使用 `CodeGenerator` 生成验证码文本
   - 生成验证码图片
   - 转换为 Base64 编码字符串

4. **缓存存储**
   - 生成唯一缓存键：`captchaKey = IdUtil.fastSimpleUUID()`
   - Redis 缓存键：`captcha_code:{captchaKey}`
   - 缓存内容：验证码文本（明文）
   - 过期时间：`captcha.expire-seconds`（默认 120 秒）

5. **返回结果**
   - `captchaKey`：用于后续校验
   - `captchaBase64`：客户端显示的图片

#### 4.2.2 验证码校验

**入口**：`AuthServiceImpl.login()` / `AuthServiceImpl.register()`

**说明**：验证码校验逻辑已内联到登录和注册方法中，不再使用独立的 `CaptchaValidationFilter`。

**执行流程**：

1. **参数提取**
   - `captchaCode`：用户输入的验证码
   - `captchaKey`：验证码缓存键

2. **缓存查询**
   - 从 Redis 获取：`captcha_code:{captchaKey}`
   - 如果缓存不存在，返回 `VERIFY_CODE_TIMEOUT` 错误

3. **验证码比对**
   - 调用 `codeGenerator.verify(cacheVerifyCode, captchaCode)`
   - 支持大小写不敏感比对
   - 校验失败返回 `VERIFY_CODE_ERROR` 错误
   - 校验成功后删除缓存（一次性有效）

**状态流转**：
```
生成 → 缓存(120s) → 校验成功/超时
                ↓
            校验成功后删除（一次性有效）
```

### 4.3 注销

**入口**：`AuthServiceImpl.logout()`

**执行流程**：

1. **SessionId 提取**
   - 从 Cookie 或 `X-Session-Id` 请求头提取 sessionId

2. **Redis 删除**
   - 删除 `session:{sessionId}`，会话立即失效

3. **上下文清理**
   - 调用 `SecurityContextHolder.clearContext()`

### 4.4 会话续期机制

Session 模式无需客户端主动续期。`SessionFilter` 在每次请求时检查 Redis 中 session 的 TTL：

1. 若 TTL < 1天（86400秒），自动续期为 7 天（604800秒）
2. 连续 7 天无操作，session 自然过期

此机制对前端完全透明，用户持续使用即自动续期。

### 4.5 API Key 认证

API Key 面向机器对机器（M2M）调用场景，是默认永不过期的长期身份凭证，详细设计参见 [API Key认证.md](./API%20Key认证.md)。

#### 4.5.1 API Key 创建

**入口**：`ApiKeyService.create(String name, LocalDateTime expiresAt)`

**执行流程**：

1. **凭证生成**
   - 生成随机字符串并拼接固定前缀 `dhak_`，得到 API Key 明文
   - 同时截取前缀片段（`keyPrefix`）用于列表辨识

2. **哈希存储**
   - 计算明文的 SHA-256 哈希值
   - 数据库仅存储哈希值、名称、前缀、归属用户、过期时间，**不存储明文**

3. **返回结果**
   - 仅在创建响应中返回一次明文 `apiKey`
   - 后续任何接口均无法再获取明文

#### 4.5.2 API Key 校验（过滤器分支）

**入口**：`SessionFilter.doFilterInternal()`（Java）/ `SessionAuth()` 中间件（Go）/ `get_current_user()` 依赖（Python）

**执行流程**：

1. **凭证提取**
   - 从 `Authorization` 请求头获取凭证，移除 "Bearer " 前缀

2. **类型识别**
   - 凭证以 `dhak_` 前缀开头时，进入 API Key 校验分支
   - 否则继续走 Session Cookie 认证流程

3. **哈希比对**
   - 计算凭证明文的 SHA-256 哈希值
   - 与数据库存储的哈希值比对，定位 API Key 记录

4. **有效性检查**
   - 校验 Key 是否存在、是否已过期（`expiresAt`）
   - 校验失败返回 `A0301` 访问未授权

5. **用户信息构建**
   - 以 Key 所属用户身份构建 `SysUserDetails`
   - 创建 `Authentication` 设置到 SecurityContext，继续后续鉴权

#### 4.5.3 跨后端共享

API Key 存储于共享数据库，**Java / Go / Python** 三个后端服务复用同一份 Key 数据，校验逻辑保持一致：

| 后端 | 校验入口 | 说明 |
|------|---------|------|
| Java | 认证过滤器链 | 识别 `dhak_` 前缀走 API Key 分支 |
| Go | 认证中间件 | 共享数据库，校验逻辑一致 |
| Python | 认证依赖/中间件 | 算法服务复用同一 Key 体系 |

#### 4.5.4 API Key 删除/吊销

**入口**：`ApiKeyService.delete(Long id)`

**执行流程**：

1. **归属校验**：仅允许删除当前用户自己创建的 Key
2. **物理删除**：删除数据库记录，Key 立即失效
3. **即时生效**：删除后使用该 Key 的请求即刻被拒绝

## 5. 缓存设计

### 5.1 Redis 缓存策略

| 缓存对象 | 缓存 Key | 数据类型 | 过期时间 | 更新策略 |
|---------|---------|---------|---------|---------|
| 验证码文本 | `captcha_code:{captchaKey}` | String | 120 秒 | 使用后自动删除 |
| 用户会话 | `session:{sessionId}` | String (JSON) | 7 天 | 每次请求滑动续期，注销时删除 |
| 角色权限 | `role:perms:{roleCode}` | String (JSON 数组) | 30 分钟 | 角色变更时删除重建 |

### 5.2 缓存失效策略

| 失效触发场景 | 失效方式 | 说明 |
|-------------|---------|------|
| 验证码校验成功 | 自然过期 | 不主动删除，依赖 TTL |
| 验证码超时 | 自动过期 | Redis TTL 到期自动清理 |
| 会话注销 | 主动删除 | 立即删除 Redis key |
| 会话自然过期 | 自动过期 | 7 天无操作后 TTL 到期 |
| 会话滑动续期 | TTL 重置 | 每次请求 TTL<1天时续期为7天 |

## 6. 安全设计

### 6.1 密码安全

| 策略项 | 配置值 | 实现方式 |
|--------|--------|---------|
| 密码存储 | 加密存储（自带盐值） | 不存储明文密码 |
| 工作因子 | 10（默认） | 抗彩虹表攻击 |
| 密码比对 | 加密比对 | 每次比对自动加盐 |

**密码校验流程**：
```
用户输入密码 → 从数据库取出加密密码 → 自动加盐并比对哈希值 → 返回是否匹配
```

### 6.2 Session Cookie 安全

| 安全措施 | 实现方式 | 说明 |
|---------|---------|------|
| HttpOnly | `true` | JavaScript 无法读取，彻底防 XSS |
| Secure | `true` | 仅 HTTPS 传输 |
| SameSite | `Lax` | 防止跨站请求携带 Cookie |
| Path | `/api` | 仅 API 路径携带，减少暴露面 |
| 即时吊销 | Redis 删除 | 注销时立即删除，无滞后 |
| SessionId 随机 | UUID | 不可预测，防暴力猜解 |

### 6.3 防暴力破解

| 防护措施 | 实现方式 | 说明 |
|---------|---------|------|
| 验证码 | 图形验证码 | 防止自动化脚本攻击 |
| 验证码有效期 | 120 秒 | 限制验证码使用窗口 |
| 验证码一次性 | 使用后失效 | 防止重放攻击 |
| 用户名规范 | 小写 + 去空格 | 统一格式，避免枚举 |

### 6.4 CSRF 防护

当前 CSRF 防护已禁用。

**理由**：
- Session Cookie 使用 `SameSite=Lax`，跨站请求不会携带 Cookie
- CORS 白名单限制 + `allowCredentials=true` 仅允许可信 Origin
- 移动端使用 `X-Session-Id` 请求头，不受 CSRF 影响

## 7. 并发控制

### 7.1 登录并发控制

**当前状态**：

| 端 | 实现状态 | 说明 |
|-----|---------|------|
| Java | 已实现 | `AuthServiceImpl.handleMultiPointSession` 通过 `system.use-multi-point` 配置开关控制；开关为 `true` 时新登录删除旧 Session，`false` 时允许多设备并存 |
| Go | 已实现 | `auth_service.go` 中 `handleMultiPointSession` 通过 `system.use-multi-point` 配置开关控制；新登录时删除旧 Session，保留最新 |
| Python | 已实现 | `AuthService._handle_multi_point_session` 通过 `USE_MULTI_POINT` 配置开关控制；开关为 `true` 时新登录删除旧 Session，`false` 时允许多设备并存 |

**配置方式**：

| 端 | 配置项 | 开发环境 | 生产环境 | 配置路径 |
|----|--------|---------|---------|---------|
| Java | `system.use-multi-point` | `false` | `true` | `application-dev.yml` / `application-prod.yml` |
| Go | `system.use-multi-point` | `false` | - | `config.yaml` |
| Python | `USE_MULTI_POINT` | `False` | - | `config.py`（`.env` 可覆盖） |

三端统一使用 `session:user:{username}` Redis key 记录当前活跃 Session ID，开关关闭时不写入该索引，允许多设备同时登录。

### 7.2 验证码并发控制

**机制**：基于 UUID 的验证码 Key 实现隔离
- 每次获取验证码生成独立 Key
- 客户端需携带 Key 才能校验
- 多次获取验证码互不影响

## 10. 性能优化

### 10.1 数据库查询优化

- `UserDetailsService` 仅查询必要字段（用户名、密码、状态）
- 角色权限信息加载使用 JOIN 查询或缓存
- 索引：`sys_user.username` 唯一索引

### 10.2 缓存优化

- 验证码缓存短期存储（120 秒），减少 Redis 内存占用
- Session 基于 TTL 自动过期，避免数据堆积
- 权限信息缓存（30 分钟），减少数据库查询

### 10.3 认证流程优化

- Session 校验仅一次 Redis GET 操作，性能高
- 过滤器链仅对必要接口执行校验

## 11. 扩展性设计

### 11.1 多因素认证扩展点

当前为用户名+密码+验证码三因素认证，可扩展：

1. **短信验证码**：替换或补充图形验证码
2. **邮箱验证码**：密码重置场景
3. **TOTP 动态口令**：高安全场景
4. **OAuth2 第三方登录**：微信、钉钉等

### 11.2 认证类型扩展

支持多种认证类型：
- **Session**：当前实现（Redis 存储，滑动续期）
- **API Key**：机器对机器调用（已实现，参见 4.5 节）

### 11.3 认证方式扩展

支持多种认证方式：
- **用户名密码认证**：当前实现
- **手机号验证码认证**：无密码登录
- **第三方认证**：OAuth2 / SAML

扩展需实现 `AuthenticationProvider` 接口。

## 12. 事务边界

认证模块主要涉及只读操作，事务边界如下：

| 操作 | 事务类型 | 说明 |
|------|---------|------|
| 用户登录 | 无事务 | 读取用户信息，创建 Session |
| 验证码校验 | 无事务 | Redis 读取 |
| 注销 | 无事务 | Redis 写入，不需要数据库事务 |

**注意**：
- 认证模块不涉及用户数据变更
- 密码修改等操作由用户管理模块负责
- 登录日志记录建议异步处理

## 15. 异步与批量场景的权限与审计注意事项

### 15.1 异步任务的数据权限传递

三端数据权限均依赖请求上下文（Java 线程局部 / Go context / Python ContextVar），异步任务（MQ 消费者、异步方法、异步任务）需显式处理上下文传播：

| 端 | 异步路径 | 处理方式 |
|---|---|---|
| Java | 异步方法 | 异步装饰器同时传播登录上下文与日志上下文 |
| Java | MQ 消费者 | 以系统身份执行（系统用户拥有全部数据权限），满足导出/下载等系统级任务需求 |
| Go | DLQ 消费者 | 从消息体注入用户 ID；数据权限未设置时按安全默认值（全部数据）处理 |
| Python | MQ handler | 从消息体恢复用户 ID 到上下文；需要数据权限时查询用户最大数据范围 |

> 设计取舍：异步系统级任务（导出/下载）以系统身份执行，若需以原用户身份执行细粒度数据权限，可从消息头恢复原始用户身份及其数据范围。

### 15.2 审计字段在批量操作中的填充

审计字段（创建人/更新人）在批量更新场景下需要显式填充（ORM 框架的批量更新 API 通常不触发自动填充），三端处理方式：

| 端 | 处理方式 |
|---|---|
| Java | 无安全上下文时回退系统用户，批量更新调用点显式设置操作人字段 |
| Go | 数据库回调在初始化时注册，直接拦截批量更新注入审计字段 |
| Python | 提供审计字段工具函数，无用户 ID 时回退系统用户，Core 更新调用点显式调用注入 |

## 16. 三端实现差异对比

### 16.1 完整对比表

| 特性 | Java | Go | Python | 差异说明 |
|------|------|-----|--------|---------|
| **验证码校验入口** | `AuthServiceImpl.login()/register()` 内联 | `auth_service.Login()/Register()` 内联 | `AuthService.login()/register()` 内联 | 三端一致 ✓ |
| **API Key 认证入口** | `ApiKeyAuthenticationFilter`（独立 Filter） | `ApiKeyAuthMiddleware`（独立中间件） | `ApiKeyAuthMiddleware`（独立 ASGI 中间件） | 三端一致 ✓ |
| **Session 配置方式** | `SecurityConstants` 统一常量 | `middleware/session.go` 统一常量 | `dependencies/auth.py` 统一常量 | 三端一致 ✓ |
| **防暴力锁定** | IP + 用户名双纬度 Redis 计数 | IP + 用户名双纬度（可配置） | IP + 用户名双纬度（可配置） | 三端一致 ✓ |
| **多点登录控制** | `handleMultiPointSession` + `use-multi-point` 开关 | `handleMultiPointSession` + `UseMultiPoint` 开关 | `_handle_multi_point_session` + `USE_MULTI_POINT` 开关 | 三端一致 ✓ |
| **验证码错误计入失败次数** | ✓（验证码校验在 login 方法内） | ✓（验证码校验在 Login 方法内） | ✓（验证码校验已下沉到 login 方法内） | 三端一致 ✓ |
| **API Key 前缀长度** | `dhak_` + 48 字符，前缀 9 字符 | `dhak_` + 48 字符，前缀 16 字符 | `dhak_` + 48 字符（urlsafe），前缀 12 字符 | 生成方式略不同但功能等价 |
| **验证码生成方式** | Hutool Captcha（4种类型） | base64Captcha（digit driver） | Pillow + Redis | 生成方式不同，互不影响的独立实现 |
| **Session TTL 续期** | Redis `getExpire` + `expire` | Redis `TTL` + `Expire` | Redis `ttl` + `expire` | 逻辑一致 |
| **注销清理范围** | 删除 `session:{sessionId}` + `session:user:{username}` | 额外清理用户状态缓存 `username` key | 仅删除 `session:{sessionId}` | Go 端额外清理了业务缓存 |
