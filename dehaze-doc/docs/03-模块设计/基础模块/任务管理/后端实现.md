# 任务管理模块 - 后端实现设计

## 1. 文档概述

描述任务管理模块的后端实现方案：架构设计（策略模式 + 消息队列）、核心业务逻辑、外部服务集成、缓存设计、异步任务设计。接口路径、错误码等契约以 [API接口.md](./API接口.md) 为准。

## 2. 架构设计

### 2.1 模块分层架构

采用**策略模式 + 消息队列**实现任务执行的解耦：

- **生产消费分离**：API 层只负责入队，执行逻辑由独立消费者驱动，两端独立伸缩
- **策略模式**：不同任务类型执行逻辑差异大（导出 ZIP、下载单文件、调用算法等），统一接口 + 多实现，新增类型无需改动调度器

调用链路：TaskController → TaskService + TaskStrategyFactory → TaskExecutor（发布消息）→ RabbitMQ → TaskConsumer → AsyncTaskExecutor → 具体 TaskStrategy → TaskMapper + 缓存服务。消息队列承载持久化、重试与削峰填谷。

### 2.2 核心组件职责

| 组件 | 职责描述 | 关键能力 |
|------|---------|---------|
| TaskService | 任务管理入口 | 任务创建（幂等）、状态查询、取消任务（CAS）、重试任务 |
| TaskExecutor | 任务发布与执行器 | 发布 TaskMessage 到 RabbitMQ、执行策略、状态流转 |
| TaskStrategyFactory | 策略工厂 | 启动时自动注册策略、按任务类型查找策略实例 |
| TaskStrategy | 策略接口 | 定义任务执行的统一契约 |
| ProgressCallback | 进度回调 | 更新进度（节流）、检测取消信号、跨实例 WebSocket 推送；默认实现 DefaultProgressCallback 同步进度到 Redis |

### 2.3 核心接口契约

#### TaskStrategy 策略接口

| 方法 | 入参 | 出参 | 说明 |
|------|------|------|------|
| getTaskTypes | 无 | List&lt;String&gt; | 返回策略支持的任务类型列表（一个策略可处理多个 taskType，如通用导出策略处理所有 `*_export` 类型） |
| execute | task, params, callback | TaskResult | 执行任务核心逻辑 |
| cancel | task | void | 取消任务，清理中间资源 |
| validateParams | params | void | 验证任务参数，失败抛异常 |

#### ProgressCallback 进度回调接口

| 方法 | 入参 | 出参 | 说明 |
|------|------|------|------|
| updateProgress | current, total, message | void | 更新任务进度（自动计算百分比），可携带进度消息（如"正在处理第 3/10 个文件"） |
| isCancelled | 无 | boolean | 检查任务是否被用户取消 |

#### TaskResult 任务结果对象

| 字段 | 类型 | 说明 |
|------|------|------|
| success | boolean | 任务是否执行成功 |
| data | string | 结果数据（导出文件的**对象键** `object_name`，路径规则见 §6.2） |
| errorMessage | string | 失败时的错误信息 |
| metadata | map | 附加元数据（如文件大小、处理数量） |

### 2.4 策略工厂机制

**扩展点**：新增任务类型只需实现 TaskStrategy 接口并在 `getTaskTypes()` 中声明类型，工厂启动时扫描所有实现并建立 taskType → 策略映射；查找未注册的类型直接抛异常。已注册类型列表可用于创建时的类型校验。

### 2.5 策略注册表

| 策略名称 | 任务类型 | 功能描述 | 依赖服务 |
|---------|---------|---------|---------|
| GenericExportStrategy | 全部 `*_export` 类型（含 `dataset_export`） | 通用导出策略，通过 `ExportHandlerRegistry` 路由到各模块的 `ExportHandler` 执行导出 | 文件存储服务、ExportHandlerRegistry |
| GenericImportStrategy | 全部 `*_import` 类型 | 通用导入策略，通过 `ImportHandlerRegistry` 路由到各模块的 `ImportHandler` 执行导入 | 文件存储服务、ImportHandlerRegistry |

> 通用策略本身不包含模块特定逻辑，仅负责文件生成/解析、进度回调、结果上传、状态更新等通用流程；各模块的导出/导入业务逻辑由对应的 `ExportHandler`/`ImportHandler` 实现，按 `module` 从注册表查找。

### 2.6 Consumer → Strategy 调用协议

调用链路：TaskConsumer 收到消息 → 反序列化 → AsyncTaskExecutor.execute → StrategyFactory.getStrategy → validateParams → execute。

**module 参数推导**：`ImportExportService` 创建任务时显式注入 `params.module`；通用端点创建任务时 params 可能不含 module，策略从 `taskType` 自动推导（如 `user_export` → `user`），三端（Java/Python/Go）行为一致。

## 3. 内部领域对象

### 3.1 TaskMessage（消息体）

RabbitMQ 消息载体，生产者构建、消费者解析，三端统一：

| 字段 | 类型 | 说明 |
|------|------|------|
| db_task_id | long | 数据库主键 ID |
| task_id | string | 任务 UUID（对外标识） |
| task_type | string | 任务类型标识，用于路由到对应策略 |

> 消息体不携带完整参数，消费者通过 `db_task_id` 从 DB 加载 `sys_task.params` 重建任务上下文，避免消息体过大与参数不一致。

### 3.2 TaskContext（执行上下文）

AsyncTaskExecutor 构建，传递给策略执行时的运行时上下文：

| 字段 | 类型 | 说明 |
|------|------|------|
| task | TaskEntity | 数据库任务实体 |
| params | object | 解析后的任务参数 |
| callback | ProgressCallback | 进度回调实例 |
| cancelFlag | func() bool | 取消检测函数，读取缓存标志位 |

## 4. 核心业务逻辑

### 4.1 状态流转

状态机为：待执行 → 执行中 → 已完成/失败/已取消，失败任务经用户重试回到待执行。后端存储值与技术约束：

| 状态 | 存储值 | 说明 |
|------|--------|------|
| 待执行 | 1（`PENDING`） | 任务已创建，等待消息队列消费 |
| 执行中 | 2（`PROCESSING`） | 消费者已取出消息，正在执行策略 |
| 已完成 | 3（`COMPLETED`） | 任务执行成功，结果可下载 |
| 已失败 | 4（`FAILED`） | 执行失败，记录错误信息 |
| 已取消 | 5（`CANCELLED`） | 任务被用户主动取消 |

> `status` 存储值统一为数字 1-5（`sys_task.status` tinyint），三端枚举对齐（Java `TaskStatusEnum`、Python `TaskStatus`、Go `int8`），API 层返回数字。

**MQ 重试对状态机透明**：任务在 PROCESSING 期间发生可重试错误时，消息 NACK 后重新投递，任务仍处于 PROCESSING；只有重试耗尽后才流转到 FAILED。

### 4.2 关键流程

#### 任务创建流程

1. 幂等检查：携带 `Idempotency-Key` 时查询已有任务（DB 唯一索引 + Redis 缓存 TTL 24h），命中直接返回
2. 并发限制校验：同用户同类型执行中任务数达上限（默认 5）则拒绝创建
3. 任务类型校验：校验 taskType 在已注册策略列表中，类型非法直接拒绝创建（不产生任务记录）
4. 生成 UUID taskId，保存任务记录（status=1 PENDING, progress=0），缓存任务状态
5. 事务提交后通过 `afterCommit` 钩子发布 TaskMessage 到 RabbitMQ（`dehaze.tasks` → `task.export`），避免异步线程读不到未提交数据
6. MQ 未启用时（测试环境）fallback 同步执行

#### 任务执行流程

消费者从队列获取消息 → 反序列化 → 更新状态为 PROCESSING → 获取策略实例 → 校验参数 → 执行策略 → 更新结果状态。策略执行期间通过 callback 定期更新进度和检测取消，异常分流见 §9.4。

**关键决策点**：无论成功或失败，只有在确定最终处理结果后才 ACK/NACK，崩溃时消息未 ACK 由 RabbitMQ 自动重投。

#### 任务取消流程

1. 校验任务归属（`create_by`）与状态（COMPLETED/FAILED/CANCELLED 不可取消）
2. CAS 更新状态为 CANCELLED（`WHERE status IN (PENDING, PROCESSING)`），失败返回状态不允许
3. 设置缓存取消标志位（TTL 5min），执行中策略下次检查时检测并退出
4. WebSocket 推送取消通知（Redis Pub/Sub 跨实例投递）

**取消检测机制**：队列等待中的任务由 DB 状态 CAS 直接置为 CANCELLED，消费者取出后按状态跳过执行；执行中的任务由策略通过 `callback.isCancelled()` 读取缓存标志位，检测到后抛出取消异常。

### 4.3 核心业务规则

| 规则 | 校验条件 | 触发时机 | 错误码 |
|------|---------|---------|--------|
| 任务类型校验 | type 在已注册策略列表中 | 创建任务时 | 不支持类型（Java A0500 / Python B0304） |
| 并发限制校验 | 同用户同类型执行中任务数未达上限（默认 5） | 创建任务时 | 并发超限（B0307 / B0308） |
| 目标资源存在性 | targetId 对应资源存在 | 策略执行前 | - |
| 数据集非空校验 | 数据集包含至少一个数据项 | 导出策略执行前 | - |
| 取消状态校验 | 当前状态为 PENDING 或 PROCESSING（CAS 更新） | 取消任务时 | 状态不允许（Java A0500 / Python B0303） |
| 重试状态校验 | 当前状态为 FAILED | 重试任务时 | 状态不允许（Java A0500 / Python B0303） |
| 幂等校验 | Idempotency-Key 唯一（DB 唯一索引） | 创建任务时 | 命中直接返回已有任务 |
| 任务归属校验 | 操作者为任务创建者（`create_by`） | 查询/取消/下载/重试时 | 无权操作（Java A0500 / Python B0302） |

### 4.4 事务边界

| 操作 | 事务级别 | 事务范围 | 说明 |
|------|---------|---------|------|
| 创建任务 | REQUIRED | 并发限制查询 + 任务记录写入 | 写入后立即提交，MQ 发布在事务外 |
| 更新状态 | REQUIRED | 单表 CAS 更新 | 状态变更立即可见 |
| 批量清理 | REQUIRES_NEW | 独立事务 | 清理失败不影响其他业务 |

MQ 发布失败时补偿标记为 FAILED 并同步刷新缓存；状态更新统一使用 CAS（`WHERE status = ?`）避免并发覆盖；定时清理分批提交。

### 4.5 幂等性与并发控制

消息可能被重复投递，消费者取出消息后先检查状态：非 PENDING 则跳过（已在执行或已完成），因此消费者崩溃重启后的自动重投不会造成重复执行。

## 7. 缓存设计

### 7.1 缓存 Key 规范

| 缓存对象 | Key 格式 | TTL | 用途 |
|---------|---------|------|------|
| 任务状态 | `task:running:{taskId}` | 24 小时 | 存储任务完整状态（含进度），支持高频查询 |
| 取消标志 | `task:cancel:{taskId}` | 5 分钟 | 标记任务被取消，执行中策略检测 |
| 幂等键映射 | `idempotency:task:{key}` | 24 小时 | 幂等键 -> taskId 映射（Java） |
| 任务统计 | `task:stat:{userId}` | 10 分钟 | 异步刷新 |
| 用户任务列表 | - | 不缓存 | 查询条件多变（状态/类型/时间），直接查库 |

> 任务状态缓存 TTL 与数据库 `expires_at` 对齐，避免缓存比数据存活更久；取消标志 TTL 覆盖单批次处理时长。

### 7.2 缓存更新与一致性

采用 Write-Through：创建任务、状态变更、进度更新均在写 DB 后立即覆盖 `task:running:{taskId}`；取消任务额外写入 `task:cancel:{taskId}`；任务过期清理时删除上述两个 Key。

**状态查询流程**：优先查缓存 → 命中直接返回 → 未命中查数据库 → 写入缓存后返回 → 不存在写入空值缓存（5min）。

## 8. 安全设计

### 8.1 数据权限

所有任务操作（查看、列表、取消、重试、下载结果）统一校验 `create_by`：系统用户仅能操作自己创建的任务；系统管理员通过角色标识识别，绕过归属校验可操作全量任务并支持按用户筛选，用于运维监控。

三端实现一致。Java/Python 无接口级权限标识；Go 端读写操作额外配置权限标识 `sys:task:add`（重试）、`sys:task:delete`（取消）。

## 9. 异步任务设计

### 9.1 消息队列拓扑

| 组件 | 名称 | 类型 | 说明 |
|------|------|------|------|
| 主交换机 | `dehaze.tasks` | direct | 任务专用交换机，按 routing key 分发 |
| 死信交换机 | `dehaze.tasks.dlx` | direct | 独立死信交换机，主交换机名 + `.dlx` 后缀 |
| 主队列 | `task.export` | classic + TTL | 任务执行主队列，持久化 + 手动 ACK，x-message-ttl=24h，routing key = 队列名，DLX→`task.export.dlx` |
| 重试队列 | `task.export.retry.0/1/2` | classic + TTL | 分级延迟重试（TTL 5s/30s/300s），DLX 指回 `dehaze.tasks`，dead-letter-routing-key = `task.export` |
| 死信队列 | `task.export.dlx` | classic | 重试耗尽或过期的失败任务，标记 FAILED 便于人工介入，绑定 `dehaze.tasks.dlx` |

> 所有队列均开启持久化（durable=true）；三端（Java/Python/Go）声明相同的交换机/队列/绑定参数，任一端启动均不产生 PRECONDITION 冲突。

### 9.2 消费者架构

消费者启动时幂等声明 Exchange、队列与绑定关系；运行期从 `task.export` 拉取消息分发到 AsyncTaskExecutor，由 prefetch 限制单节点并发。收到 SIGTERM 后停止拉取新消息，等待执行中的策略完成（默认 60s 超时），未完成消息因未 ACK 由 RabbitMQ 自动重投。

| 参数 | 默认值 | 说明 |
|------|--------|------|
| prefetch | 10（Java） | 每次预取消息数，控制单节点并发任务数 |
| concurrency | 3~10（Java concurrent/maxConcurrent） | 并发消费线程数 |
| ackMode | manual | 手动 ACK，确保处理完成后再确认 |
| defaultRequeueRejected | false | 拒绝的消息不自动重投，进入 DLX |
| shutdown.timeout | 60s | 优雅关闭等待时间 |

### 9.3 进度回调机制

进度由 current/total 计算百分比，**每 2 秒或进度变化 >5% 时才实际写入缓存**（避免高频写），每次 `updateProgress` 调用时顺带检查取消标志位。

### 9.4 失败重试机制

策略抛出异常后按三类分流：

| 错误类别 | 处理 | 典型场景 |
|---------|------|---------|
| 不可重试 | ACK + 状态置 FAILED | 资源不存在、参数校验失败等业务错误 |
| 可重试且未达上限 | NACK（requeue=false）→ 进入对应级别重试队列，TTL 到期回投主队列 | 网络超时、外部服务不可用、文件存储写入失败等临时性错误 |
| 可重试但已达上限 | ACK + 状态置 FAILED + 进入死信队列 | 重试 3 次仍失败，需人工介入 |

重试次数上限 3 次，延迟级别由重试队列的分级 TTL 决定（见 §9.1）。

### 9.5 定时任务

**过期任务清理**（每日凌晨 3 点）：查询 `expires_at < NOW()` 的任务，每批 100 条处理——删除结果文件 → 删除缓存 → 删除任务记录，文件删除失败不阻塞后续处理。

**僵尸任务修复**（每 30 分钟）：`status = PROCESSING AND updated_at < NOW() - INTERVAL 30 MINUTE` 的任务标记为 FAILED。

**推理日志僵尸修复**（每 60 秒）：`sys_pred_log`/`sys_eval_log` 中 `status='processing'` 且 `update_time < NOW() - 10 MINUTE` 的记录标记为 failed。这类任务经 @Async/goroutine 提交、不经 MQ，无法通过重投恢复，只能标记失败。

**Python 端后台任务追踪**：预测、评估、对比三个推理服务通过 `asyncio.create_task` 提交后台执行，提交后注册到 `TaskTracker`（`task_id` 形如 `pred:{log_id}` / `eval:{log_id}` / `compare:{task_id}`，`task_type` 为 `prediction`/`evaluation`/`compare`），与导出/下载任务统一管理。`TaskTracker.initiate_shutdown()` 在 30s 超时窗口内等待任务完成，避免 Worker 重启时结果文件半写入；注册失败降级为日志告警，不影响主流程。

### 9.6 服务重启恢复

PENDING 与 PROCESSING 状态的任务，其消息均因"ACK 在执行完成后"而尚未确认，服务或 MQ 重启后由 RabbitMQ 自动重投（队列与消息持久化），消费者按状态幂等处理；极端情况下由僵尸任务定时修复在 30 分钟内兜底标记 FAILED。

## 11. 配置项与常量

本模块无管理员/运营需动态调整的配置项，任务参数均为代码常量（Java `static final` / Go `const` / Python 模块常量），非配置文件可调项：

| 常量 | 说明 | 值 |
|------|------|-----|
| `task.expire.hours` | 任务/结果过期时间（小时） | 创建时 24h，完成后 7 天 |
| `task.cache.prefix` | 任务状态缓存 Key 前缀 | `task:running:`（应用配置，环境变量 `TASK_REDIS_KEY_PREFIX` 可覆盖） |
| `task.cancel.prefix` | 取消标志 Key 前缀 | `task:cancel:` |
| `task.progress.update.interval` | 进度更新最小间隔（毫秒） | 2000 |
| `task.cleanup.cron` | 过期清理 Cron 表达式 | `0 0 3 * * ?` |
| `task.zombie.cron` | 僵尸任务修复 Cron 表达式 | `0 */30 * * * ?` |
