## 2. 架构设计

### 2.1 模块分层架构

采用**策略模式 + 消息队列**实现任务执行的解耦。核心思想：

- **生产消费分离**：API 层只负责入队，执行逻辑由独立消费者驱动
- **策略模式**：不同任务类型实现统一接口，新增类型无需修改调度器

架构组件：API层(TaskController) → Service层(TaskService + TaskStrategyFactory) → 消息队列层(TaskProducer + RabbitMQ + TaskConsumer) → 执行层(AsyncTaskExecutor) → 策略层(GenericExportStrategy/GenericImportStrategy等) → 数据层(TaskMapper + 缓存服务)

**设计考量**：
- **消息队列调度**：通过 RabbitMQ 实现任务异步调度，支持持久化、重试、削峰填谷
- **生产消费分离**：TaskService 发布消息，AsyncTaskExecutor 消费执行，独立伸缩
- **策略模式**：不同任务类型执行逻辑差异大（导出 ZIP、下载单文件、调用算法等），统一接口 + 多实现
- **工厂模式**：TaskStrategyFactory 启动时自动发现并注册策略，新增类型零改动

### 2.2 核心组件职责

| 组件 | 职责描述 | 关键能力 |
|------|---------|---------|
| TaskService | 任务管理入口 | 任务创建（幂等）、状态查询、取消任务（CAS）、重试任务 |
| TaskExecutor | 任务发布与执行器 | 发布 `{db_task_id, task_id, task_type}` 消息到 RabbitMQ、执行策略、状态流转 |
| TaskStrategyFactory | 策略工厂 | 自动注册策略、根据类型获取策略实例（未注册抛异常） |
| TaskStrategy | 策略接口 | 定义任务执行的统一契约 |
| ProgressCallback | 进度回调 | 更新进度（节流）、检测取消信号、WebSocket 推送 |
| DefaultProgressCallback | 默认进度回调实现 | 进度节流（≥5% 或 ≥2s）、Redis 缓存同步、跨实例推送 |

### 2.3 核心接口契约

#### TaskStrategy 策略接口

| 方法 | 入参 | 出参 | 说明 |
|------|------|------|------|
| getTaskTypes | 无 | List&lt;String&gt; | 返回策略支持的任务类型列表（支持一个策略处理多个 taskType，如通用导出策略处理所有 `xxx_export` 类型） |
| execute | task, params, callback | TaskResult | 执行任务核心逻辑 |
| cancel | task | void | 取消任务，清理中间资源 |
| validateParams | params | void | 验证任务参数，失败抛异常 |



#### ProgressCallback 进度回调接口

| 方法 | 入参 | 出参 | 说明 |
|------|------|------|------|
| updateProgress | current, total, message | void | 更新任务进度（自动计算百分比） |
| isCancelled | 无 | boolean | 检查任务是否被用户取消 |

#### TaskResult 任务结果对象

| 字段 | 类型 | 说明 |
|------|------|------|
| success | boolean | 任务是否执行成功 |
| data | string | 结果数据（导出文件的**对象键** `object_name`，如 `exports/550e8400-xxxx.zip`） |
| errorMessage | string | 失败时的错误信息 |
| metadata | map | 附加元数据（如文件大小、处理数量） |



### 2.4 策略工厂机制

| 职责 | 实现方式 | 说明 |
|------|---------|------|
| 策略注册 | 启动时自动扫描 | 收集所有 TaskStrategy 实现，按 `getTaskTypes()` 返回的多个 taskType 建立映射 |
| 策略获取 | 类型映射查找 | 根据任务类型返回策略实例，未找到则抛异常 |
| 类型查询 | 返回注册列表 | 提供所有已注册的任务类型，用于前端展示或校验 |

**扩展点**：新增任务类型只需实现 TaskStrategy 接口并在 `getTaskTypes()` 中声明类型，工厂自动发现并注册。

### 2.5 已实现的策略

| 策略名称 | 任务类型 | 功能描述 | 依赖服务 |
|---------|---------|---------|---------|
| GenericExportStrategy | `user_export`/`role_export`/`dept_export`/`menu_export`/`dict_export`/`dataset_export`/`algorithm_export` | 通用导出策略，通过 `ExportHandlerRegistry` 路由到各模块的 `ExportHandler` 执行导出 | 文件存储服务、ExportHandlerRegistry |
| GenericImportStrategy | `user_import`/`role_import`/`dept_import`/`menu_import`/`dict_import`/`algorithm_import` | 通用导入策略，通过 `ImportHandlerRegistry` 路由到各模块的 `ImportHandler` 执行导入 | 文件存储服务、ImportHandlerRegistry |

> **说明**：通用策略本身不包含模块特定逻辑，仅负责文件生成/解析、进度回调、结果上传、状态更新等通用流程。各模块的导出/导入业务逻辑由对应的 `ExportHandler`/`ImportHandler` 实现，通过注册表查找。

### 2.6 Consumer → Strategy 调用协议

消费者从队列获取消息后，路由到策略实例并传递参数：TaskConsumer 收到消息 → 反序列化 → AsyncTaskExecutor.execute → StrategyFactory.getStrategy → validateParams → execute

**关键约定**：
- 消息体为三端统一契约 `{db_task_id, task_id, task_type}`（见 §3.1），消费者通过 `db_task_id` 从 DB 加载 `sys_task.params` 重建任务参数
- 策略通过 `getTaskTypes()` 返回支持的类型列表，工厂启动时为每个 taskType 建立到策略实例的映射（一个策略可映射多个 taskType）
- 未注册的 taskType 立即标记 FAILED，不进行重试
- **module 参数推导**：通用导入导出策略通过 `params.module` 路由到对应的 `ExportHandler`/`ImportHandler`。`ImportExportService` 创建任务时显式注入 module；通用端点（`POST /api/v1/tasks`）创建任务时 params 可能不含 module，策略会从 `taskType` 自动推导（如 `user_export` → `user`），三端（Java/Python/Go）行为一致

## 3. 内部领域对象

> API 层 DTO（Query/Form/VO）定义详见 [API接口.md](./API接口.md)

### 3.1 TaskMessage（消息体）

RabbitMQ 消息载体，生产者构建、消费者解析。**三端统一消息契约**：仅三个字段（`db_task_id` + `task_id` + `task_type`），用于消费者从 DB 重新加载任务实体并路由到策略：

| 字段 | 类型 | 说明 |
|------|------|------|
| db_task_id | long | 数据库主键 ID（消费者据此重新加载任务实体） |
| task_id | string | 任务 UUID（对外标识） |
| task_type | string | 任务类型标识，用于路由到对应策略 |

> 消息体内不携带完整参数，消费者通过 `db_task_id` 从 DB 加载 `sys_task.params` 重建任务上下文，避免消息体过大与参数不一致。

### 3.2 TaskContext（执行上下文）

AsyncTaskExecutor 构建，传递给策略执行时的运行时上下文：

| 字段 | 类型 | 说明 |
|------|------|------|
| task | TaskEntity | 数据库任务实体 |
| params | object | 解析后的任务参数 |
| callback | ProgressCallback | 进度回调实例 |
| cancelFlag | func() bool | 取消检测函数，读取缓存标志位 |

## 4. 核心业务逻辑

### 4.1 状态流转

任务状态机：PENDING(待执行) → PROCESSING(执行中) → COMPLETED(已完成)/FAILED(失败)/CANCELLED(已取消)。PENDING 和 PROCESSING 均可被取消。

#### 状态定义

| 状态 | 存储值 | 说明 | 可流转到 |
|------|--------|------|---------|
| 待执行 | 1（`PENDING`） | 任务已创建，等待消息队列消费 | `PROCESSING`、`CANCELLED` |
| 执行中 | 2（`PROCESSING`） | 消费者已取出消息，正在执行策略 | `COMPLETED`、`FAILED`、`CANCELLED` |
| 已完成 | 3（`COMPLETED`） | 任务执行成功，结果可下载 | - (终态) |
| 已失败 | 4（`FAILED`） | 执行失败，记录错误信息 | `PENDING`（重试） |
| 已取消 | 5（`CANCELLED`） | 任务被用户主动取消 | - (终态) |

> `status` 存储值统一为数字 1-5（`sys_task.status` tinyint），三端枚举对齐（Java `TaskStatusEnum`、Python `TaskStatus`、Go `int8`），API 层返回数字。

#### 状态转换规则

| 转换 | 触发条件 | 前置检查 |
|------|---------|---------|
| PENDING → PROCESSING | 消费者从队列取出消息并开始执行 | 无 |
| PROCESSING → COMPLETED | 策略执行成功返回 | 无 |
| PROCESSING → FAILED | 策略异常且重试次数已达上限 | retryCount ≥ maxRetry |
| PROCESSING → CANCELLED | 策略执行期间检测到取消标志位 | 无 |
| PENDING → CANCELLED | 用户取消尚未被消费的任务 | 任务仍在队列中 |
| FAILED → PENDING | 用户手动重试（F-TM-006） | 状态为 FAILED、操作者为任务创建者 |

**重试与状态的关系**：重试对状态机透明。任务在 PROCESSING 期间如果发生可重试错误，消息 NACK 后重新投递，消费者重新消费时任务仍处于 PROCESSING 状态。只有重试耗尽后才流转到 FAILED。

### 4.2 关键流程

#### 任务创建流程

1. 幂等检查：携带 `Idempotency-Key` 时查询已有任务（DB 唯一索引 + Redis 缓存 TTL 24h），命中直接返回
2. 生成 UUID taskId，保存任务记录(status=1 PENDING, progress=0)，缓存任务状态
3. 事务提交后发布 TaskMessage（`{db_task_id, task_id, task_type}`）到 RabbitMQ（`dehaze.tasks` → `task.export`）
4. MQ 未启用时（测试环境）fallback 同步执行

**关键决策点**：
1. **UUID 作为任务 ID**：避免自增 ID 可猜测性，提升安全性
2. **事务提交后发布**：通过 `afterCommit` 钩子在事务提交后再发布消息，避免异步线程读不到未提交数据
3. **幂等键先行**：Idempotency-Key 命中即返回，避免重复创建
4. **创建即提交**：简化用户操作，创建后立即入队异步执行

#### 任务执行流程

消费者从队列获取消息 → 反序列化 → 更新状态为 PROCESSING → 获取策略实例 → 校验参数 → 执行策略 → 更新结果状态。策略执行期间通过 callback 定期更新进度和检测取消。异常按三类处理：不可重试(ACK+FAILED)、可重试未耗尽(NACK+重投)、可重试已耗尽(ACK+FAILED+死信)。

**关键决策点**：
1. **ACK 在任务完成后**：无论成功或失败，只有在确定最终处理结果后才 ACK/NACK。崩溃时消息未 ACK，RabbitMQ 自动重投
2. **重试对状态机透明**：可重试错误时回退状态为 PENDING，NACK 让消息重新入队。从外部看不到"重试中"状态
3. **三类错误分流**：不可重试（ACK + FAILED）、可重试且未耗尽（NACK + 重投）、可重试但已耗尽（ACK + FAILED + 死信）
4. **进度轮询检测取消**：每次更新进度时检查取消标志

#### 任务取消流程

1. 校验任务归属（`create_by`）与状态（COMPLETED/FAILED/CANCELLED 不可取消）
2. CAS 更新状态为 CANCELLED（`WHERE status IN (PENDING, PROCESSING)`），失败返回状态不允许
3. 设置缓存取消标志位(TTL 5min)，执行中策略下次检查时检测并退出
4. WebSocket 推送取消通知（Redis Pub/Sub 跨实例投递）

取消检测机制：队列等待中通过 DB 状态 CAS；执行过程中通过缓存标志位定期检查；终态直接拒绝。

**取消检测机制**：

| 阶段 | 检测方式 | 处理行为 |
|------|---------|---------|
| 队列等待中 | DB 状态 CAS | 直接更新为 CANCELLED，消费者取出后检查状态跳过执行 |
| 执行过程中 | 缓存标志位 | 策略通过 callback.isCancelled() 定期检查，检测到后抛出取消异常 |
| 已完成/失败 | 状态判断 | 拒绝取消，返回错误提示 |

### 4.3 核心业务规则

| 规则 | 校验条件 | 触发时机 | 错误码 |
|------|---------|---------|--------|
| 任务类型校验 | type 在已注册策略列表中（`TaskStrategyFactory` 未注册即抛异常） | 策略执行时 | 不支持类型（Java A0500 / Python B0304） |
| 目标资源存在性 | targetId 对应资源存在 | 策略执行前 | - |
| 数据集非空校验 | 数据集包含至少一个数据项 | 导出策略执行前 | - |
| 取消状态校验 | 当前状态为 PENDING 或 PROCESSING（CAS 更新） | 取消任务时 | 状态不允许（Java A0500 / Python B0303） |
| 重试状态校验 | 当前状态为 FAILED | 重试任务时 | 状态不允许（Java A0500 / Python B0303） |
| 幂等校验 | Idempotency-Key 唯一（DB 唯一索引） | 创建任务时 | 命中直接返回已有任务 |
| 任务归属校验 | 操作者为任务创建者（`create_by`） | 查询/取消/下载/重试时 | 无权操作（Java A0500 / Python B0302） |

> **并发限制**：单用户并发任务数上限常量与对应错误码已定义，创建流程当前未执行并发校验（见 [需求规格 §10 待确认事项](./需求规格.md)）。

### 4.4 事务边界

| 操作 | 事务级别 | 事务范围 | 说明 |
|------|---------|---------|------|
| 创建任务 | REQUIRED | 并发限制查询 + 任务记录写入 | 写入后立即提交，MQ 发布在事务外 |
| 更新状态 | REQUIRED | 单表 CAS 更新 | 状态变更立即可见 |
| 批量清理 | REQUIRES_NEW | 独立事务 | 清理失败不影响其他业务 |

**设计考量**：
- MQ 发布在事务提交后执行。若发布失败，补偿标记为 FAILED
- 状态更新使用 CAS（`WHERE status = ?`），避免并发覆盖
- 定时清理使用独立事务，分批提交

### 4.5 幂等性与并发控制

| 场景 | 问题 | 解决方案 |
|------|------|---------|
| 消息重复投递 | 任务重复执行 | 消费者检查状态：非 PENDING 则跳过（已在执行或已完成） |
| 并发取消同一任务 | 状态混乱 | DB CAS 更新 `WHERE status IN (PENDING, PROCESSING)` |
| 重复创建相同任务 | 资源浪费 | `Idempotency-Key` 唯一索引 + Redis 映射，命中返回已有任务 |
| 消费者崩溃重启 | 消息丢失 | 消息未 ACK 自动重投，消费者幂等处理 |
| MQ 发布失败（未启用） | 任务无人消费 | 测试环境 fallback 同步执行 |

## 6. 外部服务集成

任务策略执行时依赖多个外部服务，需要明确调用协议和降级策略。

### 6.1 服务依赖清单

| 依赖服务 | 依赖方 | 调用方式 | 说明 |
|---------|--------|---------|------|
| 文件存储服务 | 所有策略 | 内部接口调用 | 上传导出结果、读取源文件、读取导入文件 |
| ExportHandlerRegistry | GenericExportStrategy | 内部接口调用 | 按模块获取 ExportHandler |
| ImportHandlerRegistry | GenericImportStrategy | 内部接口调用 | 按模块获取 ImportHandler |
| 各模块 Service | 各 ExportHandler/ImportHandler | 内部接口调用 | 查询/写入模块数据（如 SysUserService、SysDatasetService 等） |

### 6.2 文件存储服务集成

任务结果文件通过文件管理模块的存储服务接口写入，路径规则参见 [文件管理/后端实现.md](../文件管理/后端实现.md)。

| 调用场景 | 使用的接口 | 超时 | 重试 |
|---------|-----------|------|------|
| 上传导出 ZIP | StorageService.upload | 60s | 1 次 |
| 读取源文件流 | StorageService.download | 30s | 1 次 |
| 检查文件存在 | StorageService.exists | 5s | 0 次 |
| 删除过期结果 | StorageService.delete | 10s | 0 次 |

**任务结果存储路径**：`exports/{taskId}.{ext}`（如 `exports/550e8400-xxxx.zip`），作为 `object_name` 写入 `sys_task.result`。下载 URL 运行时拼接，不落库。

### 6.3 降级策略

| 场景 | 检测方式 | 降级行为 | 对任务的影响 |
|------|---------|---------|-------------|
| 文件存储不可用 | 连接/上传超时 | 标记为可重试错误，触发延迟重试 | 任务延迟完成 |
| 数据集服务查询失败 | 查询异常 | 标记为可重试错误，触发延迟重试 | 任务延迟完成 |
| 算法服务不可用 | 调用超时/错误 | 标记为可重试错误，触发延迟重试 | 任务延迟完成 |
| 源文件不存在 | 404 响应 | 标记为不可重试错误，直接 FAILED | 任务永久失败 |
| 数据集不存在 | 记录不存在 | 标记为不可重试错误，直接 FAILED | 任务永久失败 |

## 7. 缓存设计

### 7.1 缓存 Key 规范

| 缓存对象 | Key 格式 | TTL | 用途 |
|---------|---------|------|------|
| 任务状态 | `task:running:{taskId}` | 24 小时 | 存储任务完整状态，支持高频查询（Java/Go `task:running:`、Python `task:running:cache:`） |
| 取消标志 | `task:cancel:{taskId}` | 5 分钟 | 标记任务被取消，执行中策略检测 |
| 进度信息 | 随任务状态缓存更新 | 24 小时 | 进度写入任务状态缓存，无独立 key（Python 另有 `task:running:progress:`） |
| 幂等键映射 | `idempotency:task:{key}` | 24 小时 | 幂等键 → taskId 映射（Java） |

**设计考量**：
- 任务参数不单独缓存，通过 TaskMessage 在 MQ 中传递，消费者直接使用
- 任务状态缓存 TTL 与数据库 `expires_at` 对齐，避免缓存比数据存活更久
- 取消标志 TTL 5 分钟，覆盖单批次处理时长（每批次处理完检查取消标志）

### 7.2 缓存更新规则

| 操作 | 缓存行为 |
|------|---------|
| 创建任务 | 写入 `task:running:{taskId}` |
| 更新状态 | 覆盖 `task:running:{taskId}` |
| 更新进度 | 覆盖任务状态缓存中的进度字段 |
| 取消任务 | 写入 `task:cancel:{taskId}` |
| 任务过期清理 | 删除 `task:running:{taskId}`、`task:cancel:{taskId}` |

### 7.3 缓存一致性策略

| 场景 | 问题 | 解决方案 |
|------|------|---------|
| DB 更新后缓存未同步 | 查询到旧状态 | Write-Through，更新 DB 后立即更新缓存 |
| MQ 发布失败补偿 | 缓存仍为 PENDING | 补偿逻辑中同步更新缓存为 FAILED |
| 缓存雪崩 | 大量缓存同时失效 | TTL 随机化（±10%） |
| 缓存穿透 | 查询不存在的任务 | 空值缓存 5 分钟 |

**状态查询流程**：优先查缓存 → 命中直接返回 → 未命中查数据库 → 写入缓存后返回 → 不存在写入空值缓存(5min)。

## 9. 异步任务设计

### 9.1 消息队列拓扑

Exchange(`dehaze.tasks`, type: direct) + 死信交换机(`dehaze.tasks.dlx`) → 主队列(`task.export`) + 分级延迟重试队列(`task.export.retry.0/1/2`, TTL 到期后转发回主队列) + 死信队列(`task.export.dlx`)。所有队列均开启持久化。

| 组件 | 名称 | 类型 | 说明 |
|------|------|------|------|
| 主交换机 | `dehaze.tasks` | direct | 任务专用交换机，按 routing key 分发 |
| 死信交换机 | `dehaze.tasks.dlx` | direct | 独立死信交换机，主交换机名 + `.dlx` 后缀 |
| 主队列 | `task.export` | classic + TTL | 任务执行主队列，持久化 + 手动 ACK，x-message-ttl=24h，DLX→`task.export.dlx` |
| 重试队列 | `task.export.retry.0/1/2` | classic + TTL | 分级延迟重试（TTL 5s/30s/300s），DLX 指回主交换机（routing key `task.export`） |
| 死信队列 | `task.export.dlx` | classic | 重试耗尽或过期的失败任务，标记 FAILED 便于人工介入 |

**队列属性**：
- 所有队列均开启持久化（durable=true），主队列 routing key = `task.export`（路由键 = 队列名）
- 重试队列 `task.export.retry.{i}`（i=0/1/2）配置 dead-letter-exchange 指回 `dehaze.tasks`，dead-letter-routing-key 为 `task.export`
- 死信队列绑定死信交换机 `dehaze.tasks.dlx`，routing key = `task.export.dlx`
- 三端（Java/Python/Go）声明相同的交换机/队列/绑定参数，任一端启动均不产生 PRECONDITION 冲突
- 消息体统一契约 `{db_task_id, task_id, task_type}`（见 §3.1）

### 9.2 消费者架构

#### 消费者生命周期

| 阶段 | 行为 | 说明 |
|------|------|------|
| 启动 | 声明 Exchange + 队列 + 绑定关系 | 确保基础设施存在（幂等操作） |
| 运行 | 从 `task.export` 拉取消息，分发到 AsyncTaskExecutor | prefetch 限制并发 |
| 关闭 | 停止接收新消息，等待正在执行的任务完成 | graceful shutdown |

#### Graceful Shutdown

收到 SIGTERM → 停止拉取新消息 → 等待执行中的策略完成(默认 60s 超时) → 未完成消息未 ACK 由 RabbitMQ 自动重投 → 关闭连接。

#### 消费者配置

| 参数 | 默认值 | 说明 |
|------|--------|------|
| prefetch | 10（Java） | 每次预取消息数，控制单节点并发任务数 |
| concurrency | 3~10（Java concurrent/maxConcurrent） | 并发消费线程数 |
| ackMode | manual | 手动 ACK，确保处理完成后再确认 |
| defaultRequeueRejected | false | 拒绝的消息不自动重投，进入 DLX |
| shutdown.timeout | 60s | 优雅关闭等待时间 |

### 9.3 进度回调机制

| 职责 | 说明 |
|------|------|
| 进度计算 | 根据 current/total 计算百分比 |
| 频率控制 | 每 2 秒或进度变化 >5% 时才实际写入缓存 |
| 取消检测 | 每次 updateProgress 调用时检查取消标志位 |
| 消息记录 | 可选的进度消息（如"正在处理第 3/10 个文件"） |

**频率控制的必要性**：前端轮询间隔通常为 2-5 秒，更新过频无意义，且增加缓存写入压力。

### 9.4 失败重试机制

策略抛出异常 → 判断可重试性 → 不可重试：ACK + FAILED；可重试且未超上限：NACK（requeue=false）→ 消息进入对应级别的 `task.export.retry.{i}` 重试队列（TTL 到期后回投主队列重新消费）；可重试但超上限：ACK + FAILED + 进入死信队列 `task.export.dlx`。

**重试延迟策略**（通过消息 TTL 实现）：

| 重试次数 | 延迟时间 | 说明 |
|---------|---------|------|
| 1 | 5s | 第一次快速重试 |
| 2 | 30s | 短暂等待后重试 |
| 3 | 5min | 较长等待后重试 |
| >3 | 不重试 | 进入死信队列，人工介入 |

**可重试/不可重试错误分类**：

| 错误类型 | 是否重试 | 说明 |
|---------|---------|------|
| 网络超时 | ✅ 是 | 临时性问题 |
| 外部服务不可用 | ✅ 是 | 临时性问题 |
| 文件存储写入失败 | ✅ 是 | 可能是临时性问题 |
| 资源不存在 | ❌ 否 | 业务错误，重试无意义 |
| 参数校验失败 | ❌ 否 | 业务错误 |
| 策略未注册 | ❌ 否 | 配置错误 |

### 9.5 定时任务

| 任务 | Cron 表达式 | 说明 |
|------|------------|------|
| 过期任务清理 | `0 0 3 * * ?` | 每天凌晨 3 点，清理过期任务记录和结果文件 |
| 僵尸任务修复 | `0 */30 * * * ?` | 每 30 分钟，检查长时间 PROCESSING 的任务 |

#### 过期清理流程

定时任务 → 查询过期任务(expires_at < NOW(), LIMIT 100) → 分批处理：删除结果文件 → 删除缓存 → 删除任务记录 → 继续下一批。

**清理策略**：分批处理，每批 100 条；先删文件后删记录，文件删除失败不阻塞。

#### 僵尸任务修复

检测条件：`status = 'PROCESSING' AND updated_at < NOW() - INTERVAL 30 MINUTE`，标记为 FAILED。

预测/评估日志僵尸任务：检测 `sys_pred_log`/`sys_eval_log` 中 `status='processing'` 且 `update_time < NOW() - 10 MINUTE` 的记录，标记为 failed。由定时任务每 60 秒扫描（Java `PredLogRecoveryTask`/`EvalLogRecoveryTask`、Go `pred_log_recovery.go`/`eval_log_recovery.go`、Python `log_recovery.py`）。与 sys_task 僵尸修复的区别在于：触发场景为 @Async/goroutine 进程重启，无法通过 MQ 重投恢复，仅标记 failed。

### 9.6 服务重启恢复

| 场景 | 恢复机制 | 说明 |
|------|---------|------|
| PENDING 状态任务 | 消息仍在队列中未 ACK，RabbitMQ 重投 | 自动恢复 |
| PROCESSING 状态任务 | 消息未 ACK（因 ACK 在执行完成后），RabbitMQ 重投 | 自动恢复，消费者按状态幂等处理 |
| MQ 自身重启 | 队列和消息均持久化 | 自动恢复 |
| 极端情况 | 僵尸任务定时修复兜底 | 30 分钟内标记 FAILED |

### 10.2 优化措施

| 优化项 | 实现方式 | 收益 |
|--------|---------|------|
| 状态缓存 | Redis 缓存任务状态 | 查询 QPS 提升 10x |
| 进度频率控制 | 每 5s 更新一次 | 减少缓存写入 |
| 分批清理 | 定时任务分批处理 | 避免长事务 |
| MQ 异步 | RabbitMQ 消息队列 | 创建接口快速返回、削峰填谷 |
| 消息持久化 | durable + persistent | 服务重启不丢任务 |
| prefetch 限流 | 消费者预取限制 | 防止单节点过载 |
