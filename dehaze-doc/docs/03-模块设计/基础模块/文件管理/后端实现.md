# 文件管理模块 - 后端实现设计

## 1. 文档概述

### 1.1 文档目的

本文档描述文件管理模块的后端实现方案，包括分层架构设计、存储策略模式、MD5 去重机制、分片上传与断点续传、签名 URL 下载鉴权、核心业务流程、事务边界与孤儿文件清理等。

## 2. 架构设计

### 2.1 模块分层架构

文件管理模块采用三层架构：表现层(FileController) → 业务层(FileService + PathBuilder) → 存储层(StorageService接口 + MinIO/本地/Nginx静态实现)。

**设计考量**：
- 元数据与物理存储分离，元数据存数据库，物理文件存对象存储
- 策略模式允许运行时切换存储后端，便于开发/生产环境适配
- PathBuilder 统一命名规范，避免路径逻辑散落各处

### 2.2 核心组件职责

| 组件 | 职责描述 | 关键能力 |
|------|---------|---------|
| FileController | HTTP 请求处理 | 参数校验、文件流读取、MD5 计算、签名 URL 校验、响应封装 |
| FileService | 业务逻辑编排 | MD5 去重判断、分片合并、签名 URL 生成、元数据 CRUD、事务控制 |
| PathBuilder | 存储路径生成 | 日期目录、MD5 命名、扩展名提取 |
| StorageService | 物理存储抽象 | 上传、下载、删除、存在性检查 |

### 2.3 存储策略模式

#### 设计原理

存储后端差异大（本地文件系统 vs 对象存储 vs nginx 静态服务），但上层业务逻辑一致。通过策略模式：

1. 定义统一的存储接口契约
2. 不同存储后端实现相同接口
3. 运行时根据 `sys_file.storage` 选后端实例

#### 存储接口契约

| 方法 | 入参 | 出参 | 说明 |
|------|------|------|------|
| upload | 文件流、对象名 | 对象名 | 上传文件到存储后端（幂等：相同 objectName 覆盖写入） |
| download | 对象名 | 文件流 | 获取文件内容流（流式传输，不加载到内存） |
| delete | 对象名 | 是否成功 | 删除物理文件（不存在时视为成功） |
| exists | 对象名 | 是否存在 | 检查文件是否存在 |
| getUrl | 对象名 | 完整 URL | 唯一 URL 生成出口：`storage.baseUrl.rstrip("/") + "/" + object_name`，仅在 API 响应序列化时调用，不落库 |

> **URL 永远运行时拼接、永不落库**。`sys_file` 只存稳定的 `object_name` + `storage`，环境迁移只改配置，数据库零改动。三端不得新增任何自行拼接 URL 的代码路径，所有 URL 一律走 `StorageService.getUrl`。返回给前端的 url 必须是带 scheme+host 的完整 URL（`http(s)://host/...`），禁止相对路径。

#### 三端接口契约一致性

`StorageService` 接口契约由 **Java 端为权威来源**，Go/Python 端必须按以下约束严格对齐，确保三后端行为一致：

| 契约维度 | 一致性要求 |
|---------|-----------|
| 方法签名 | 方法名、入参顺序与语义、出参类型三端一致（仅语言层面差异，如 Java `InputStream` ↔ Go `io.Reader` ↔ Python `BinaryIO`） |
| 语义契约 | upload 幂等覆盖、delete 不存在视为成功、download 流式传输不加载内存、getUrl 唯一出口——三端行为完全一致 |
| 异常映射 | 存储后端异常三端统一映射到业务错误码（`B0405` 存储失败 / `B0406` 物理文件丢失），禁止任一端返回原始存储 SDK 异常 |
| 策略选择 | 三端均按 `sys_file.storage` 字段路由后端实例，禁止任一端硬编码存储后端 |

> 新增存储后端时，三端必须同步实现并在策略工厂注册；契约变更须经 Java 端评审后同步 Go/Python，禁止任一端独立偏离契约。

#### 存储策略清单

| storage 标识 | 存储后端 | baseUrl 配置 | object_name 示例 | 适用场景 |
|--------|---------|------|------|---------|
| `minio` | MinIO 对象存储 | MinIO 访问地址或下载接口地址 | `upload/20250119/abc.jpg` | 用户上传、算法预测结果 |
| `local` | 本地文件系统 | 本地下载接口地址 | `upload/20250119/abc.jpg` | 开发环境、单机部署 |
| `nginx-static` | nginx 静态服务 | nginx 静态服务**根地址**（如 `http://host:9000`，不带 `/datasets` 等资源子路径） | `datasets/AECR-Net/clear/01.jpg`（含资源前缀） | nginx 直服的静态文件（数据集文件） |

> nginx 静态服务统一托管多种资源——数据集（`/datasets`）、模型权重（`/models`），将来还可能有 css/js 等。`baseUrl` 配置为服务根地址，`object_name` 自带资源类型前缀（`datasets/...`、`models/...`），新增资源类型无需改配置，只需约定前缀。

**扩展点**：新增存储后端只需实现 StorageService 接口，并在策略工厂中注册。

## 3. 内部领域对象

### 3.1 FileBO（文件业务对象）

Service 层内部使用，封装文件上传过程中的中间状态，生命周期仅限于单次请求：

| 字段 | 类型 | 说明 |
|------|------|------|
| file | 临时文件 | 上传的原始文件（处理完成后删除） |
| name | 字符串 | 原始文件名（用户上传时的名称） |
| objectName | 字符串 | 存储对象键（含路径，如 `upload/20250119/abc123.jpg`），与环境无关 |
| storage | 字符串 | 存储后端标识（`minio`/`local`/`nginx-static`），默认按全局配置 |
| extension | 字符串 | 文件扩展名（小写，如 `jpg`） |
| md5 | 字符串 | MD5 哈希值（32 位十六进制） |
| size | 长整型 | 文件大小（字节） |
| userId | 长整型 | 上传用户 ID（用于签名 URL 归属校验，从登录态获取） |
| businessType | 字符串 | 业务类型（`image`/`model`/等），用于按类型校验文件大小上限 |

## 4. 核心业务逻辑

### 4.1 关键流程

#### 文件上传流程

Controller 按 `business_type` 校验文件大小上限（见 §4.5）/ 安全性 → 计算 MD5 → 构建 FileBO → Service 根据 MD5 查询（事务开始）：MD5 已存在则秒传返回已有记录，不存在则按文件大小路由：`size ≥ 50MB` 走分片上传合并流程（见 §4.2），否则直接存储物理文件 → 写入元数据记录（object_name + storage + user_id + business_type，不存 url），存储失败事务回滚。

**关键决策点**：

1. **先物理存储，再写元数据**：物理存储在事务内执行。存储失败时事务回滚，不产生孤儿元数据记录。存储成功但 DB 写入失败时产生孤儿物理文件，由孤儿文件清理任务兜底（见 §4.7）
2. **MD5 计算在 Controller 层**：避免 Service 层依赖文件流，关注点分离
3. **秒传判断在写入前**：减少无效存储操作，命中已有记录时直接返回

#### 文件下载流程

业务模块调用签名 URL 生成接口（传入 fileId，从登录态取 userId）→ Service 校验调用方对该文件的访问权限并生成签名 URL（含 fileId + userId + 过期时间 + 签名，见 §4.3）→ 前端持签名 URL 发起下载请求 → 下载接口校验签名有效性 + 时效 + 归属 → 按 `sys_file.storage` 选后端下载 → 物理文件存在则流式传输(设置 Content-Type/Content-Disposition)，不存在则返回 B0406；文件记录不存在则返回 B0401。

> 下载链路对所有后端统一：按 storage 选 StorageService，调用 download(object_name) 取流转发，无前缀判断、无 302 跳转分支。签名校验失败统一返回 B0407（签名无效或已过期）。

#### 文件删除流程

查询文件元数据 → 存在则软删除元数据记录（deleted=1，事务内）→ 再删除物理文件（事务外，best-effort）。

**设计说明**：软删除配合 MD5 upsert 的 `ON DUPLICATE KEY UPDATE deleted=0` 复活机制——重新上传同 MD5 文件时已软删记录自动复活。物理文件删除失败仅记录日志，产生的孤儿文件由孤儿文件清理任务兜底（见 §4.7）。不实现引用计数，删除前的引用关系检查由调用方（业务模块）负责。

### 4.2 分片上传与断点续传

#### 触发与分片策略

| 维度 | 规则 |
|------|------|
| 触发条件 | 文件 `size ≥ 50MB` 启用分片上传；`< 50MB` 走普通上传流程（见 §4.1） |
| 分片大小 | 默认 5MB/片（可配置 `file.chunk.size`），前端按固定大小切片 |
| 分片编号 | 从 1 开始连续编号，合并时按序拼接 |
| 秒传整合 | 初始化时若 MD5 命中已存在物理文件，直接返回秒传，跳过整个分片流程 |

#### 持久化数据

分片上传过程需持久化两类数据（表结构详见 [数据库设计.md](../../../02-系统架构/03-数据库设计.md)）：

| 数据类别 | 关键字段 | 用途 |
|---------|---------|------|
| 上传会话 | uploadId（前端生成）、文件 MD5、总分片数、business_type、userId、状态、创建时间 | 跟踪一次分片上传的整体进度，断点续传的恢复依据 |
| 已上传分片记录 | uploadId、分片序号、分片 MD5、objectName（分片存储对象键）、大小 | 记录断点，避免重复上传已完成分片 |

> 上传会话与分片记录在合并成功后清理；超时未完成的会话由清理任务删除（见 §4.7）。

#### 核心流程

1. **初始化**：前端计算文件 MD5 → 调用 MD5 校验接口（F-FM-004），物理文件已存在则秒传返回；否则请求初始化分片上传（传 uploadId + MD5 + 总分片数 + business_type）→ 后端创建上传会话记录，返回已上传分片列表（断点续传：若该 uploadId 已有历史分片记录则返回，前端跳过这些分片）
2. **分片上传**：前端逐片上传（uploadId + 分片序号 + 分片数据 + 分片 MD5）→ 后端校验分片 MD5 一致性 → 存储分片物理文件至 `temp/chunks/{uploadId}/{partNumber}` → 写入分片记录 → 返回该分片成功
3. **断点续传**：上传中断后重新初始化时，后端按 uploadId 返回已上传分片列表，前端仅上传缺失分片，适配移动端/小程序弱网环境
4. **合并存储**：所有分片上传完成 → 前端请求合并 → 后端按分片序号顺序合并为完整文件 → 计算整体 MD5 与初始化时声明的 MD5 比对（不一致则丢弃合并结果并返回 B0405）→ 创建 `sys_file` 元数据记录（object_name + storage + user_id + business_type）→ 删除分片物理文件和会话记录

**关键决策**：

- **分片 MD5 二次校验**：每片上传时校验分片 MD5，防止传输过程中分片损坏；合并后再校验整体 MD5，确保合并结果完整
- **合并失败不产生孤儿元数据**：合并结果 MD5 不一致时丢弃合并文件，不写入 `sys_file`，分片保留供前端重试合并
- **分片存储隔离**：分片临时存储在 `temp/chunks/` 下，与正式 `upload/` 路径隔离，合并成功后清理

### 4.3 签名 URL 生成与校验

#### 设计目标

下载链路采用签名 URL 机制实现鉴权：业务模块在生成签名 URL 时完成归属校验，下载接口校验签名 + 时效 + 防篡改，避免越权下载。

#### 签名 URL 生成

| 维度 | 设计 |
|------|------|
| 触发方 | 业务模块调用签名 URL 生成接口（传入 fileId，userId 从登录态获取） |
| 归属校验 | 生成时校验调用方对该文件的访问权限：基础规则为 `sys_file.user_id == 当前 userId`（上传者归属）；业务模块若有更复杂归属规则（如数据集文件归属数据集所有者），由业务模块在调用前自行校验 |
| 签名内容 | `fileId + userId + expireTime`（expireTime = 生成时间戳 + 有效期） |
| 签名算法 | HMAC-SHA256，密钥由 `file.download.signSecret` 配置（三端共享同一密钥） |
| URL 格式 | `{baseUrl}/api/v1/files/download/{fileId}?userId={userId}&expire={expireTime}&sign={signature}` |
| 有效期 | 默认 30 分钟（可配置 `file.download.signExpireMinutes`） |

> 归属校验在生成时完成；下载接口不再重复查询业务归属，仅校验签名 + 时效。签名本身绑定 userId，篡改 userId 会导致签名不匹配。

#### 签名 URL 校验（下载接口）

| 校验项 | 失败处理 | 说明 |
|--------|---------|------|
| 签名有效性 | B0407 | 重新计算 HMAC 与传入 sign 比对，不一致即拒绝 |
| 时效校验 | B0407 | 当前时间 > expireTime 则过期 |
| 文件存在性 | B0401 | fileId 对应的 `sys_file` 记录不存在或已软删 |
| 物理文件存在性 | B0406 | 元数据存在但物理文件丢失 |

> 校验通过后按 `sys_file.storage` 路由 StorageService 取流，流式传输逻辑与普通下载一致。

#### 安全约束

- 签名密钥 `file.download.signSecret` 三端必须一致，密钥泄露需立即轮换
- 签名 URL 在有效期内可重复使用（非一次性），有效期到期后需业务模块重新生成
- 下载接口仅接受带签名的请求，禁止以 objectName 直接取流

### 4.4 MD5 去重机制

#### 处理流程

| 阶段 | 操作 | 说明 |
|------|------|------|
| 1. 计算 | 读取文件流计算 MD5 | 使用流式计算，避免内存溢出 |
| 2. 查询 | `SELECT ... WHERE md5 = ?` | 命中唯一索引，毫秒级响应 |
| 3. 命中 | 返回已有记录 | 秒传，不存储物理文件 |
| 4. 未命中 | 存储文件 + 写入记录 | 首次上传完整流程 |

#### 并发上传同一文件处理

当多个请求同时上传相同文件（MD5 相同）时：

| 场景 | 处理策略 | 说明 |
|------|---------|------|
| 并发查询 | 乐观处理 | 多个请求同时查询 MD5，可能都未命中 |
| 并发写入 | 唯一索引约束 | 数据库 MD5 唯一索引保证只有一条记录 |
| 唯一键冲突 | INSERT … ON DUPLICATE KEY UPDATE | 冲突时复活软删行（deleted=0）并用本次上传的新文件信息覆盖 type/name/object_name/storage/size/size_bytes，避免旧 object_name 指向已被删除的物理文件导致下载失败 |
| 物理文件 | 幂等覆盖 | 相同对象名重复上传，存储服务幂等处理 |

**并发安全保证**：即使在 READ COMMITTED 隔离级别下，两个事务可能同时通过 SELECT 检查，但 MD5 唯一索引是最终兜底。冲突时通过 `INSERT … ON DUPLICATE KEY UPDATE` 原子完成"复活 + 覆盖新文件信息"，确保返回的记录 object_name 指向本次实际上传的物理文件。

#### 边界情况

| 场景 | 处理方式 |
|------|---------|
| 0 字节文件 | 正常计算 MD5，允许上传 |
| 超大文件（超过 business_type 对应上限） | Controller 层拦截，抛出文件过大异常（B0402） |
| MD5 碰撞 | 理论存在但概率极低（约 2^-128），不做特殊处理 |

### 4.5 核心业务规则

| 规则 | 校验条件 | 处理方式 | 说明 |
|------|---------|---------|------|
| 文件大小限制（按 business_type） | `image`: ≤100MB；`model`: ≤500MB；其他类型: ≤100MB | 超限抛出异常（B0402） | 上限按 business_type 区分，可通过 `file.maxSize.image` / `file.maxSize.model` 配置调整 |
| 文件类型控制 | — | 文件管理模块不做白名单限制 | 由业务模块在调用前控制允许的类型 |
| 文件名安全 | 不含 `../`、`\0`、特殊字符 | 过滤或拒绝 | 防止路径遍历攻击 |
| MD5 唯一性 | 数据库唯一索引 | 秒传/去重 | 核心去重逻辑 |
| 路径规范化 | 标准化后在基础路径内 | 非法路径拒绝 | 防止目录穿越 |
| 文件类型嗅探 | 扩展名 + MIME 内容嗅探 | 不匹配时拒绝 | 防止恶意文件伪装 |

### 4.6 事务边界

| 操作 | 事务级别 | 事务范围 | 说明 |
|------|---------|---------|------|
| 文件查询 | 只读事务 | 单次查询 | 优化数据库连接 |
| 文件上传 | 读写事务 | MD5 查询 → 物理存储 → 元数据写入 | 存储失败回滚，不产生孤儿元数据 |
| 文件删除 | 读写事务 | 元数据软删除(deleted=1) | 物理删除在事务提交后（允许孤儿文件由孤儿文件清理任务兜底，见 §4.7） |
| 批量操作 | 读写事务 | 整批元数据操作 | 原子性保证 |

**设计考量**：

- **上传事务包含物理存储**：物理存储是外部 I/O 会拉长事务，但上传相对查询属低频操作且单文件存储耗时在秒级，事务持有时间可接受；换来的是存储失败时元数据不入库

### 4.7 孤儿文件清理

针对最终一致性删除策略与上传事务回滚产生的孤儿物理文件，由定时对账任务清理。

#### 产生场景

| 场景 | 原因 |
|------|------|
| 上传事务回滚 | 物理存储成功但 DB 写入失败（事务回滚），物理文件残留 |
| 删除物理文件失败 | 元数据已软删但物理删除失败（best-effort） |
| 分片上传未完成 | 上传会话超时未合并，分片物理文件残留 |

#### 清理策略

| 清理对象 | 判定条件 | 处理方式 |
|---------|---------|---------|
| 普通孤儿文件（`upload/`） | 物理文件存在但无未删除元数据引用，且超过保留阈值（默认 48 小时） | 删除物理文件 |
| 去重共享物理文件 | 多元数据引用同一物理文件（同 object_name） | 仅当所有引用元数据均已软删时才清理物理文件，避免误删仍被引用的物理文件 |
| 分片上传会话残留 | 上传会话超过保留阈值（默认 24 小时）未完成合并 | 删除会话记录 + 分片记录 + 分片物理文件 |

> 清理任务分批处理（每批 100 个），避免一次性扫描对存储后端和数据库造成压力。执行参数（Cron、阈值）见 §10 配置项。

### 4.8 幂等性与并发控制

| 场景 | 问题 | 解决方案 |
|------|------|---------|
| 并发删除同一文件 | 双重删除异常 | 删除前查询，记录不存在则返回错误（由调用方决定是否幂等处理） |
| 删除后立即查询 | 查到已删除记录 | 元数据软删除（deleted=1），查询自动过滤，走 DB 无延迟 |

### 6.3 文件存储路径规则

`object_name`（对象键）按业务来源约定路径前缀，三端一致：

| 路径类型 | 格式 | 示例 | 存储后端 | 说明 |
|---------|------|------|---------|------|
| 上传路径 | `upload/{yyyyMMdd}/{md5}.{ext}` | `upload/20250119/abc123.jpg` | `minio`/`local` | 按日期分目录，MD5 命名 |
| 导出路径 | `exports/{taskId}.{ext}` | `exports/550e8400-xxxx.xlsx` | `minio`/`local` | 导出任务结果文件（通用导入导出框架使用） |
| 导入错误报告 | `imports/{taskId}_errors.{ext}` | `imports/550e8400-xxxx_errors.xlsx` | `minio`/`local` | 导入失败行的错误明细报告 |
| 导入上传文件（临时） | `temp/imports/{taskId}/{originalName}` | `temp/imports/550e8400-xxxx/users.xlsx` | `minio`/`local` | 异步导入时暂存的上传文件，任务完成后清理 |
| 分片临时路径 | `temp/chunks/{uploadId}/{partNumber}` | `temp/chunks/abc123/1` | `minio`/`local` | 分片上传的临时分片文件，合并成功后清理（见 §4.2） |
| 临时路径 | `temp/{uuid}` | `temp/550e8400-e29b...` | `minio`/`local` | 处理中的临时文件 |
| 数据集文件 | `datasets/{相对数据集根目录的路径}` | `datasets/AECR-Net/clear/01.jpg` | `nginx-static` | nginx 直服的静态文件，文件已存在于 nginx 目录，仅登记元数据（`saveFileRecord`） |

**命名规则设计考量**：

- 日期目录：便于按时间清理、统计
- MD5 命名：保证唯一性，支持去重（相同 MD5 覆盖写入，天然幂等）
- 扩展名保留：便于识别文件类型、设置 Content-Type

## 7. 缓存设计

### 7.1 缓存策略

| 缓存对象 | 缓存 Key | TTL | 更新策略 |
|---------|---------|-----|---------|
| 文件元数据 | `file:meta:{fileId}` | 30 分钟 | 元数据变更（上传/删除）时失效 |
| 用户文件列表 | - | 不缓存 | - |
| 签名 URL | `file:url:{fileId}` | 根据配置（默认 1 小时） | 过期自动刷新 |

> 文件元数据缓存用于下载鉴权时的元数据查询，减少数据库主键查询压力。签名 URL 缓存避免同一文件频繁生成签名，TTL 对齐 `file.download.signExpireMinutes` 配置。用户文件列表为分页查询，不缓存。

## 8. 安全设计

### 8.1 下载鉴权：签名 URL 机制

生成与校验链路见 §4.3。责任边界：业务模块在调用签名 URL 生成接口前完成业务归属校验（基础规则为上传者归属 `sys_file.user_id`，数据集/任务等复杂归属规则由业务模块自行实现）；文件管理模块只负责签名生成与校验，不实现业务权限控制。

### 8.2 安全防护

| 防护项 | 威胁 | 实现方式 |
|--------|------|---------|
| 下载路径安全 | 内部路径泄露 | objectName 参数校验：只允许合法路径格式，禁止 `..` 等特殊序列 |
| 签名 URL 防篡改 | 越权下载 | 下载链接含 HMAC 签名（绑定 fileId + userId + 过期时间），篡改任一参数导致签名不匹配 |
| MD5 完整性 | 文件篡改检测 | 上传时计算存储，下载时可验证 |

> 文件大小限制、文件名安全、路径规范化、文件类型嗅探见 §4.5；分片 MD5 校验见 §4.2。

### 8.3 存储与访问安全补充

| 防护项 | 威胁 | 实现方式 |
|--------|------|---------|
| 私有桶权限 | 未授权直接访问存储桶 | 存储桶设为私有读写，仅通过应用层签名 URL 访问，禁止公开直接访问 |
| 防盗链 | 第三方站点盗用文件 URL | 签名 URL 绑定 userId + 过期时间，篡改任一参数导致签名不匹配；可选配置 Referer 白名单 |
| 租户隔离 | 跨用户文件越权访问 | 文件元数据记录 user_id，签名 URL 生成时校验调用方归属（见 §4.3） |
