## 1. 模块概述

### 1.1 模块定位

语音交互模块是系统级的语音输入输出能力模块，提供语音识别（ASR）和语音合成（TTS）能力。语音识别的文本直接进入 AI 对话模块的消息管道，由 LLM 统一处理意图理解和指令执行，不单独维护语音指令解析逻辑——重复造轮子且 LLM 的自然语言理解远超规则匹配。状态：⏳ 规划中（远期阶段交付）。

### 1.2 技术选型

| 能力 | 方案 | 模型/服务 | 理由 | 状态 |
|------|------|---------|------|------|
| **ASR（语音识别）** | 本地部署 FunASR 语音识别引擎（dehaze-python 进程内，CPU） | 流式：SenseVoice-Small（分段增量伪流式）；离线：SeACo-Paraformer-Large（热词增强版） | 中文准确率高，CPU 即可运行不占用 GPU 资源，无 API 成本 | ✅ Python 端已实现 |
| **TTS（语音合成）** | 本地部署 Piper 语音合成引擎（dehaze-python 进程内，CPU） | zh_CN-huayan-medium 音色（piper-voices 开源库） | 零外部 API 依赖、无 API 成本与配额限制、模型仅约 60MB 自动下载 | ✅ Python 端已实现 |

> 选型核心逻辑：项目 GPU 是图像处理的核心资源，语音识别与合成均在 CPU 上运行即可满足需求，与本地 LLM 体系（Qwen3-0.6B）共同构成零外部依赖部署形态。与 [后端实现 §1.1](./后端实现.md) 一致。

### 1.3 核心价值

| 价值维度 | 具体内容 | 状态 |
|---------|---------|------|
| **降低输入门槛** | 用户可通过语音完成操作，无需手动打字 | ⏳ 规划中 |
| **流式实时识别** | 用户说话过程中实时显示识别结果，边说边出字 | ⏳ 规划中 |
| **自然语音回复** | LLM 回复通过本地 TTS 合成为自然语音播报 | ⏳ 规划中 |
| **多轮语音对话** | 支持上下文连续语音对话，结合 AI 对话模块管理上下文 | ⏳ 规划中 |

| 模块 | 依赖说明 | 状态 |
|------|---------|:----:|

## 2. 用户角色与权限

### 2.1 主要用户角色

| 角色 | 描述 | 主要职责 |
|------|------|---------|
| 普通用户 | 所有登录用户 | 语音输入、语音播报、多轮语音对话、管理个人用户级热词 |
| 管理员 | 系统后台管理人员 | 配置全局热词、监控 ASR/TTS 服务运行状态 |

### 2.2 权限矩阵

| 功能点 | 普通用户 | 管理员 |
|--------|:------:|:------:|
| 语音识别（ASR） | ✅ | ✅ |
| 语音合成（TTS） | ✅ | ✅ |
| 多轮语音对话 | ✅ | ✅ |
| 用户级热词管理 | ✅（仅自己的） | ✅ |
| 全局热词管理 | ❌ | ✅ |
| 服务运行监控 | ❌ | ✅ |

> 权限标识：`voice:hotword:view` / `voice:hotword:edit`（热词管理）；ASR/TTS 使用为系统基础能力，登录用户均可使用，无特殊权限标识。

### 2.3 多端能力差异

各端录音能力受运行环境影响，权限申请流程统一：进入语音功能 → 触发权限申请 → 用户授权 → 开始录音；拒绝授权时提示引导至系统设置开启。

| 端 | 录音技术 | 权限申请 | 说明 |
|----|---------|---------|------|
| Web（Vue/React） | Web Audio API / MediaRecorder | 浏览器权限弹窗（getUserMedia） | 仅 HTTPS 环境下可用；需处理浏览器兼容性 |
| 桌面端（Electron） | Electron 录音 API（基于 Chromium） | 系统麦克风权限 | 同 Web 端实现 |
| 移动端 APP（Android/Flutter/RN） | 原生录音 API | 运行时动态申请麦克风权限（Android RECORD_AUDIO） | 需在系统设置授权 |
| 小程序（Taro/UniApp） | 小程序录音 API（`wx.getRecorderManager`） | 小程序授权 `scope.record` | 录音时长受限（单次最长 60s，与 §3.1.4 上限一致） |

> 录音采样参数全端统一：16kHz、16bit、单声道 PCM，匹配 FunASR 输入要求。

## 3. 功能需求

### 3.1 语音识别 (F-VS-001)

#### 3.1.1 功能描述

将用户语音输入转换为文本。基于本地部署的 FunASR 引擎，支持流式实时识别和离线批量识别两种模式。⏳ 规划中。

#### 3.1.2 功能要求

| 要求 | 说明 |
|------|------|
| 语言支持 | 中文（普通话），支持中英混杂 |
| 实时识别 | 流式推音频块，边说边出字（延迟 < 100ms） |
| 离线识别 | 支持完整音频文件提交后返回识别结果（离线高精度模型，准确率更高） |
| 识别准确率 | 普通环境下 ≥ 95%，带背景噪声下 ≥ 90% |
| 标点符号 | 自动添加标点和断句 |
| 热词 | 支持配置领域热词（算法名、专业术语），提升专业词汇识别率（见 §3.4） |

#### 3.1.3 识别模式

| 模式 | 模型 | 场景 | 延迟 |
|------|------|------|------|
| 流式实时 | SenseVoice-Small | 实时对话、边说边出字 | < 100ms |
| 离线高精 | Paraformer-Large | 完整音频提交后识别 | 音频时长 × 0.3 |

#### 3.1.4 录音时长与静音超时

| 限制 | 值 | 说明 |
|------|------|------|
| 最长连续识别 | 60 秒 | 超时自动结束录音 |
| 静音自动结束 | 3 秒 | 静音 3 秒自动结束录音 |
| 取先到者 | — | 最长时长与静音超时取先到者结束录音 |

### 3.2 语音合成 (F-VS-002)

#### 3.2.1 功能描述

将文本转换为语音，调用本地 Piper TTS 引擎（dehaze-python 进程内，CPU）。AI 对话回复可选择语音播报，用户可开关和控制语速。⏳ 规划中。

#### 3.2.2 功能要求

| 要求 | 说明 |
|------|------|
| 语言支持 | 中文（普通话） |
| 音色选择 | 支持音色切换（当前提供 huayan 中文女声，音色目录可扩展） |
| 语速控制 | 慢速 0.8x / 正常 1.0x / 快速 1.2x |
| 流式合成 | 支持流式 TTS，边合成边播放（减少首播延迟，规划项） |
| 输出格式 | mp3 / wav / pcm，采样率 8000/16000/24000/48000 Hz |
| 可选开关 | 用户可选择是否开启语音回复（默认关闭） |

#### 3.2.3 TTS 缓存策略

| 缓存策略 | 说明 |
|---------|------|
| 缓存 Key | `SHA256(text + voiceId + speed)` |
| 缓存位置 | 文件管理（sys_file） |
| TTL | 24 小时过期自动清理 |
| 最大缓存数 | 单用户 100 条，LRU 淘汰 |

> 缓存适合场景：AI 对话常见开场语（"您好，请上传图片"、"处理完成，请查看结果"）、系统提示语。

#### 3.2.4 TTS 降级策略

TTS 不可用时降级为纯文本回复，作为必备功能需求：

| 异常 | 处理 |
|------|------|
| 本地 TTS 引擎不可用（依赖缺失/模型加载失败） | 返回错误提示，前端展示纯文本回复 |
| 合成失败（推理异常/空音频） | 返回错误提示，不存储不扣费 |
| 音频存储失败 | 返回错误提示 |

### 3.3 多轮语音交互 (F-VS-003)

#### 3.3.1 功能描述

支持上下文连续语音对话，语音输入结合 AI 对话模块管理上下文，LLM 维护多轮会话状态，不单独维护语音会话上下文。⏳ 规划中。

#### 3.3.2 功能要求

| 要求 | 说明 |
|------|------|
| 上下文连续 | 同一会话内多轮语音输入共享上下文，LLM 维护对话历史 |
| 会话超时 | 60 秒无新语音输入自动结束会话 |
| 会话管理 | 由 AI 对话模块统一管理会话 ID 与上下文（语音交互模块不维护会话状态） |
| 混合输入 | 同一会话支持语音与文本混合输入 |

### 3.4 热词配置 (F-VS-004)

#### 3.4.1 功能描述

管理员/用户配置领域热词（算法名、专业术语），提升 ASR 对专业词汇的识别率。⏳ 规划中。

#### 3.4.2 功能要求

| 要求 | 说明 |
|------|------|
| 管理界面 | 管理员通过热词管理界面配置全局热词；普通用户管理个人用户级热词 |
| 生效范围 | 全局热词（所有用户生效）/ 用户级热词（仅当前用户生效） |
| 注册接口 | `registerHotWords` 接口注册热词到 FunASR 模型配置，提升匹配优先级 |
| 热词示例 | RIDCP、FFA-Net、PSNR、SSIM、去雾、暗通道先验 |

## 4. 用户交互流程

### 4.1 语音输入流程

用户点击麦克风 → 申请录音权限 → 开始录音 → 流式推送音频块到 FunASR → 实时显示识别文本 → 用户松手 / 静音 3 秒 / 达到 60 秒 结束 → 文本填入输入框 → 用户确认/编辑后发送 → ASR 文本直接进入 AI 对话模块的消息管道，由 LLM 统一理解意图并执行

### 4.2 语音回复流程

AI 对话回复生成 → 用户开启语音播报 → 调用本地 Piper TTS 引擎合成 → 返回音频 URL 播放（流式合成为规划项）

## 5. 非功能需求

### 5.1 性能要求

| 指标 | 目标值 | 说明 |
|------|--------|------|
| ASR 流式延迟 | < 100ms | 流式识别增量文本返回延迟 |
| ASR 离线识别 | 音频时长 × 0.3 | 离线高精度模型识别耗时 |
| ASR 并发会话 | ≥ 50 | 同时进行流式 ASR 的会话数 |
| TTS 首播延迟 | ≤ 1s | 文本到首段音频播放的延迟 |
| TTS 流式合成延迟 | ≤ 200ms | 流式合成增量音频返回延迟 |

### 5.2 并发与容量

| 指标 | 要求 | 说明 |
|------|------|------|
| ASR 并发会话上限 | 50 | 超过上限拒绝新会话并提示 |
| ASR 连接超时 | 60s | WebSocket 空闲超时自动关闭，回收资源 |
| 资源回收 | 会话结束/超时后释放 FunASR 连接 | 避免连接泄漏 |
| TTS 引擎内存 | 每 Worker 约 300MB | 本地引擎进程内运行（多 Worker 各持一份模型） |
| TTS 限流 | 单用户 QPS 限流 | 防止滥用 |

### 5.3 安全要求

| 方面 | 措施 | 状态 |
|------|------|:----:|
| 音频数据不持久化 | ASR 音频流处理完即删，不落盘存储 | ⏳ 规划中 |
| 录音权限授权 | 录音前申请用户授权（流程见 §2.3） | ⏳ 规划中 |
| 传输加密 | ASR/TTS 数据传输 HTTPS 加密 | ⏳ 规划中 |
| 音频缓存加密 | TTS 缓存音频加密存储 | ⏳ 规划中 |
| 会话隔离 | 用户 ASR 会话相互隔离，不可跨用户访问 | ⏳ 规划中 |

### 5.4 可用性要求

| 方面 | 要求 |
|------|------|
| 降级 | TTS 不可用时降级为纯文本（见 §3.2.4） |
| 容错 | ASR 单会话异常不影响其他会话 |
| 资源隔离 | ASR（CPU）与图像处理（GPU）资源隔离，互不影响 |

## 6. 业务规则

### 6.1 WebSocket 方案关系

语音 ASR 使用独立 WebSocket 端点 `/ws/asr`，与系统消息通知 WebSocket（`new_message` 事件通道）并存，两通道独立，不复用连接：

| 通道 | 端点 | 用途 |
|------|------|------|
| 语音 ASR | `/ws/asr` | 流式音频推送与识别结果返回 |
| 消息通知 | 系统消息通知 WebSocket | `new_message` 事件推送（详见 [消息通知/后端实现 §7](../消息通知/后端实现.md)） |

### 6.2 三后端契约

Java/Go 后端通过 WebSocket/HTTP 调用 Python FunASR 微服务（流式 ASR 经 WebSocket、离线 ASR 经 HTTP），TTS 引擎（Piper）运行于 dehaze-python 进程内。三后端对外 API 契约完全一致（Java 权威，Go/Python 对齐）：

| 能力 | 三后端对外接口 | 内部调用 |
|------|--------------|---------|
| ASR | `POST /api/v1/voice/asr/stream-session`、`POST /api/v1/voice/asr/offline`、`GET /api/v1/voice/asr/result/{sessionId}` | 调用 Python FunASR 微服务（WebSocket/HTTP） |
| TTS | `POST /api/v1/voice/tts`、`GET /api/v1/voice/tts/voices` | 调用 Python Piper TTS 引擎（进程内） |

### 6.3 AI 计费关联

ASR/TTS 调用计入 AI 积分，与 AI 计费管理模块挂钩：

| 能力 | 计费维度 | 说明 |
|------|---------|------|
| ASR | 按秒计费 | 按音频时长累计积分 |
| TTS | 按字符计费 | 按合成文本字符数累计积分 |

> 计费单价由 AI 计费管理模块统一定义；调用前校验用户 AI 积分余额，余额不足时拒绝并提示。

### 6.4 录音时长规则

最长 60 秒连续识别，静音 3 秒自动结束，两者取先到者（与 §3.1.4 一致）。

## 7. 依赖关系

### 7.1 依赖模块

| 模块 | 依赖说明 | 状态 |
|------|---------|:----:|
| **AI 对话模块** | ASR 文本进入对话消息管道，回复可语音播报；多轮上下文由 AI 对话模块管理 | ⏳ 规划中 |
| **AI 计费管理** | ASR/TTS 调用计入 AI 积分（ASR 按秒、TTS 按字符） | ⏳ 规划中 |

### 7.2 外部依赖

| 依赖 | 说明 |
|------|------|
| **本地 FunASR 引擎** | dehaze-python 进程内运行，CPU 推理（流式 SenseVoice-Small / 离线 SeACo-Paraformer-Large），主依赖随 `uv sync` 安装，模型懒加载并自动从 ModelScope 下载缓存；硬件要求：4 核（流式）/8 核（离线）、2GB/4GB 内存（多 Worker 部署时每 Worker 各持一份模型）、无需 GPU |
| **本地 Piper TTS 引擎** | dehaze-python 进程内运行，CPU 推理（zh_CN-huayan-medium，约 60MB），主依赖（piper-tts/lameenc）随 `uv sync` 安装，模型懒加载并自动从 hf-mirror 下载缓存；内存增量约 300MB/Worker、无需 GPU |
