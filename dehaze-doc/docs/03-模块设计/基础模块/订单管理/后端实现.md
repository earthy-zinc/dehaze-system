# 订单管理模块 - 后端实现设计

## 1. 文档概述

本文档描述订单管理模块的后端实现方案。该模块是平台**统一交易中枢**：所有商品（会员卡 / 积分卡）统一经订单管理完成下单、支付、回调处理、超时取消等交易行为，交易行为对全部商品类型一致，差异仅收敛在**履约**与**退款**两个环节。模块在 dehaze-java、dehaze-python、dehaze-go 三端实现，三端 API 契约一致（Java 权威，Go/Python 对齐）。

- **API 契约**：参见 [API接口.md](./API接口.md)
- **需求规格**：参见 [需求规格.md](./需求规格.md)
- **数据库设计**：参见 [03-数据库设计.md](../../../02-系统架构/03-数据库设计.md)（sys_order 含 package_type、credit_amount 字段，package_level/period_days 允许 NULL）
- **Schema 文件**：`config/sql/schema/sys_order.sql`、`sys_payment_record.sql`、`sys_refund_record.sql`、`sys_auto_renew.sql`

## 3. 服务层设计

### 3.1 订单服务 (OrderService)

> 售后（退款）与自动续费逻辑内聚于 OrderService，无独立 RefundService/AutoRenewService。

| 方法名 | 职责 |
|--------|------|
| create | 创建订单（防重锁 + 价格计算 + 锁定优惠券 + 商品信息冗余） |
| pay | 发起支付（渠道统一下单返回支付参数 / 余额直接生效），全部商品类型一致 |
| handlePaymentCallback | 支付回调（验签 + 幂等 + 按商品类型履约分流） |
| cancel | 取消订单（释放优惠券），全部商品类型一致 |
| listMy | 我的订单分页 |

| getPage | 后台订单分页（含商品类型筛选） |
| applyAfterSale | 售后申请（原因类型必选 + 按商品类型折算金额） |
| listRefunds | 售后审核列表分页（含原因类型筛选） |
| approveRefund / rejectRefund | 售后审核通过（原因成立性 + 折算金额双审核）/ 驳回 |
| getStats | 订单统计（含商品类型维度、售后原因分布） |
| updateAutoRenewConfig / getAutoRenewConfig | 自动续费配置读写（仅会员卡） |
| expireOrders / executeRenewal / completeExpiredOrders / expireUserCoupons / retryFailedRefunds | 定时任务入口 |

### 3.2 支付渠道抽象 (PaymentChannelService)

|------|---------|------|

| AlipayService | alipay | 同上（precreate），`payment.alipay.enabled=false` 时 mock |
| 平台余额 | balance | 由 BalanceAccountService 处理（见 §3.3） |

### 3.3 余额账户服务 (BalanceAccountService)

平台余额账户为**人民币交易媒介**（充值 / 支付 / 退款退回），封装冻结、解冻、扣减、退款回充操作，供 OrderService 的支付、退款、超时取消流程调用。余额流水类型与表结构见 [需求规格 §3.5](./需求规格.md)。

> **职责分离**：余额账户与 AI 计费模块的积分账户职责分离——余额管人民币资金流转，本模块**不感知积分消耗**；积分到账（source=recharge）与回退（source=refund）由 AI 计费模块处理。

| 方法名 | 职责 | 事务与并发边界 |
|--------|------|--------------|
| freeze | 校验可用余额 ≥ 金额，frozen_balance += amount | 乐观锁（version）单行 UPDATE，失败重试 ≤3 次 |
| unfreeze | frozen_balance -= amount（超时取消/支付失败解冻） | 与订单状态变更同一事务 |
| deduct | 扣减冻结余额出账（balance -= amount、frozen_balance -= amount） | 与 completePayment 同一事务 |
| refund | 退款回充可用余额（balance += amount） | 与售后审核同一事务 |

**余额退款（充值余额退回）**：用户提交余额退款申请（金额 = 可用余额，不含冻结余额）→ 管理员审核（金额/原路渠道核对）→ 按原充值渠道原路退回（微信/支付宝，无法原路由管理员指定渠道）→ 退款成功：balance -= 金额、流水 change_type=refund、写退款记录。余额退款仅针对充值余额本身，**不触发任何订单履约回退**，与 §4 售后流程隔离（规则见 [需求规格 §3.5.5](./需求规格.md)）。

## 4. 核心业务逻辑

### 4.1 订单创建（create）

1. **参数校验**：payMethod ∈ {wechat, alipay, balance, combined}（否则 A0400）；商品存在且在售（会员卡 / 积分卡均可购买）
2. **防重复下单**：Redis 分布式锁（`order:lock:{userId}:{packageId}`，waitTime=0、leaseTime=5s），获取失败抛 A0539
3. **价格计算**：调套餐服务 `calculatePrice(packageId, couponId)`，取 originalPrice/discountAmount/couponAmount/payableAmount
4. **优惠券锁定**：条件 UPDATE `sys_user_coupon SET status=4 WHERE id=? AND status=1`（0 行影响抛 A0525）；支付成功后再核销
5. **生成订单**：订单号 `DH + yyyyMMddHHmmss + 6位随机数`；商品信息冗余（packageName/packageType/packageLevel/periodDays/creditAmount）；积分卡订单 packageLevel/periodDays 为 NULL、creditAmount 冗余可得积分；expire_time = NOW()+30min；status=pending；is_auto_renew=0
6. **事务保证**：订单创建与优惠券锁定同一事务
7. **职责分离**：create 不触发渠道下单，支付链接由 pay 获取；**不校验用户当前等级**（任何用户可购买任意商品）

### 4.2 发起支付（pay）—— 交易行为对所有商品类型一致

1. 越权校验：订单归属本人（非本人抛 A0530）
2. 状态校验：status=pending（已支付/已完成抛 A0533"订单已支付，请勿重复支付"；已取消/退款中/已退款抛 A0531）；未超时（否则 A0532）
3. **balance**：BalanceAccountService.freeze 冻结应付金额（不足抛 BALANCE_INSUFFICIENT）→ 触发 completePayment → 返回 paid=true
4. **wechat/alipay**：调渠道 `unifiedOrder` → 失败抛 C0001 → 创建支付记录（处理中）→ 返回 payUrl/qrCode
5. **combined**：冻结 balanceAmount（不足抛 BALANCE_INSUFFICIENT）→ 第三方应付 = payableAmount - balanceAmount → 调渠道统一下单；回调成功后触发 completePayment

### 4.3 支付回调处理（handlePaymentCallback）—— 履约分流

1. 渠道验签（`verifyCallback`；渠道未启用时 mock 直接信任）
2. 查询订单；订单不存在返回失败
3. 金额校验：回调金额 > 0 且 ≠ 订单应付金额时记录日志并抛 **A0538**（三端统一）
4. 获取订单级分布式锁 `payment:lock:{orderNo}`（waitTime=0、leaseTime=10s），获取失败视为重复回调，幂等返回成功
5. 状态判断：已支付/已完成幂等返回成功；非待支付返回失败
6. **completePayment**（按商品类型履约分流）：

| 步骤 | 处理 | 商品类型 |
|------|------|---------|
| 1 | 订单置 paid，写入 paidTime/effectiveTime/paidAmount；创建支付记录 | 全部 |
| 2 | **履约分流**：vip → 激活会员权益（等级→商品等级、来源=package、到期时间叠加、月度配额按商品等级权益配置）；credit → 调 AI 计费积分到账（credits_balance += creditAmount，流水 source=recharge，不影响会员身份） | 按类型 |
| 3 | 记录成长值（change_type=consume，按实付金额 1:1） | 全部 |
| 4 | 核销优惠券（status 4→2、used_order_id 写入、模板 used_qty+1） | 全部 |
| 5 | 扣减冻结余额（balance/combined） | 全部 |
| 6 | 累加商品销量 | 全部 |
| 7 | **终态**：credit → 订单置 completed（无有效期，一次性商品）；vip → 保持 paid 至到期归档 | 按类型 |
| 8 | 删除订单详情缓存；发送支付成功通知 | 全部 |

> **分流原则**：下单、支付、超时、取消等交易行为对所有商品类型一致；差异仅存在于履约（上表步骤 2/7）与退款（§4.5/§4.6）。

### 4.4 取消订单（cancel）

1. 越权校验（A0530）；状态校验（status=pending，否则 A0531）
2. 置 status=cancelled、写入 cancel_reason
3. 释放优惠券（status 4→1）
4. 删除订单详情缓存

### 4.5 售后申请（applyAfterSale）

**政策前提**：退款是平台兜底保障而非用户常规权益，默认不可随意退；申请通道即售后申请，原因类型必选。

1. 越权校验（A0530）；状态校验：status ∈ {paid, completed}（否则 A0531）
2. 原因类型必选：after_sale（售后问题）/ force_majeure（不可抗原因）/ merchant（商家原因）/ other（其他）（否则 A0400）
3. 主观原因拦截：不想要/买错了/用不着等主观原因不进入售后流程，前端提示"该商品为虚拟商品，不支持随意退款；如有售后问题请提交售后申请"
4. 唯一性校验：已存在售后记录抛 A053A（退款记录订单 ID 唯一约束兜底）
5. **按商品类型折算金额**：

| 商品类型 | 折算规则 |
|---------|---------|
| 会员卡（按天） | used_days = max(1, ceil((NOW() - paid_time) / 86400))；remaining_days = period_days - used_days；remaining_days ≤ 0 时退款金额为 0；否则 refund_amount = paid_amount × remaining_days / period_days（向下取整到分） |
| 积分卡（按用量） | 未消耗积分 = creditAmount - 已消耗积分（消耗由 AI 计费模块提供）；refund_amount = paid_amount × 未消耗积分 / creditAmount（向下取整到分）；已消耗积分不退 |
| 商家原因 | 运营决策，可全额退款（不适用折算） |

6. 插入退款记录（refund_no、status=refunding、channel=订单支付方式、reason_type、refund_amount、used_days/used_credits）；订单置 status=refunding
7. 通知管理员审核

### 4.6 售后审核（approveRefund / rejectRefund）

**双审核**：
- **原因成立性**：售后问题 / 不可抗原因 / 商家原因三类明确原因快速审核是否成立；"其他"原因由管理员人工裁量（制度从严、执行从宽）
- **折算金额**：按商品类型折算是否合理（商家原因可全额，运营决策）

**approveRefund（通过）**：
1. 校验售后记录存在且 status=refunding
2. 按原支付方式退款：wechat/alipay 调渠道退款（同步）；balance 余额回充；combined 按余额/第三方比例拆分（余额退款金额 = refund_amount × (balanceAmount / paidAmount)，第三方退款金额 = refund_amount - 余额退款金额）
3. 退款成功：退款记录 status=refunded、订单 status=refunded；**按商品类型回退履约**：

| 商品类型 | 回退内容 |
|---------|---------|
| vip | 扣减成长值（change_type=refund_deduct，扣减值 = 该单消费累积成长值 × 未使用比例，与退款折算比例一致，最低为 0）→ 退回未使用优惠券（status 2→1，已使用不退回）→ 调整到期时间 = paid_time + used_days → 基于扣减后成长值重算会员等级 |
| credit | 调 AI 计费扣减未消耗积分（流水 source=refund） |

4. 发送退款成功通知；写入审核信息
5. 退款失败：退款记录 status=refund_failed + error_message，订单恢复 paid/completed，定时任务自动重试（≤3 次）

**rejectRefund（驳回）**：退款记录 status=refund_failed + 审核信息，订单恢复 paid/completed，记录驳回原因。

### 4.7 自动续费（仅会员卡）

- **配置读写**：`updateAutoRenewConfig` 校验商品存在（仅会员卡），upsert（`(user_id, package_id)` 唯一）写入 pay_method/status/fail_count=0；next_renew_time 初始为 NULL——首次开启不触发扣款；`getAutoRenewConfig` 未配置时返回 enabled=false
- **积分卡无自动续费**：一次性商品，无续费能力、无到期归档
- **executeRenewal（定时任务）**：扫描启用且 next_renew_time <= NOW 的配置 → 校验商品在售 → 价格 = sale_price × 0.95 → 扣款并履约：
  - **balance**：直接扣减 → 激活会员（有效期叠加）+ 记录成长值 → 创建已支付续费订单（is_auto_renew=1）→ 更新 next_renew_time = 新到期时间、fail_count=0
  - **wechat/alipay（半自动语义）**：当前无真实代扣（需签约委托扣款协议，属远期）——到期自动创建**待支付**续费订单（95 折）→ 引导用户主动支付 → 支付成功回调后续费生效；用户未支付则订单按 30 分钟超时取消 → fail_count+1 → 2 小时后自动重试（新单）→ 达 3 次关闭配置（status=0、close_reason 记录）
  - 扣款/支付失败：fail_count+1，未达 3 次 next_renew_time = NOW()+2h 重试，达 3 次关闭配置（status=0、close_reason 记录）

### 4.8 定时任务

| 任务名 | 执行时机 | 扫描条件 | 处理 | 商品类型 |
|--------|---------|---------|------|---------|
| 订单超时取消 | 每 5 分钟 | pending 且 expire_time < NOW | 渠道关单（失败仅告警）→ 置 cancelled → 释放券 → 解冻余额 | 全部 |
| 自动续费扣款 | 每 1 小时 | 启用且 next_renew_time <= NOW | 见 §4.7 | 仅会员卡 |
| 订单到期归档 | 每 1 小时 | paid 且 package_expire_time < NOW | 置 completed | 仅会员卡（积分卡支付即 completed，无归档） |
| 优惠券过期 | 每 1 小时 | 未使用且已过期 | 置已过期 | - |
| 售后退款失败重试 | 每 30 分钟 | refund_failed 且 retry_count < 3 | 重新调渠道退款；成功置 refunded，失败 retry_count+1，达 3 次标记最终失败 | 全部 |

## 5. 数据访问层与缓存策略

> 表结构与索引定义见 [03-数据库设计.md](../../../02-系统架构/03-数据库设计.md) 及 Schema 文件。sys_order 已落地 package_type、credit_amount 字段（package_level/period_days 允许 NULL，积分卡为空）。查询关注点：订单表按用户+状态（我的订单）、按状态+过期时间扫描（定时任务）、按商品类型筛选（后台）；退款表按订单号唯一约束（一单仅一次售后）、按状态扫描（重试）；支付流水表按订单号查询；自动续费表按用户+商品唯一约束（仅会员卡）。

| 防重复下单锁 | order:lock:{userId}:{packageId} | 5 秒（leaseTime） | 自动过期 |

## 6. 三端实现一致性

三端 API 契约完全一致（Java 权威，Go/Python 对齐）。订单锁、支付回调锁三端统一使用 Redis 分布式锁（Java Redisson / Go go-redis / Python redis-py）；回调金额校验统一抛 A0538、越权统一抛 A0530；履约分流（会员卡激活 / 积分到账）、售后原因类型、按类型折算与回退规则三端一致，详见 §4。

## 7. 安全设计

### 7.1 支付安全

| 防护项 | 实现方式 |
|--------|---------|
| 签名验证 | 渠道验签（未启用时 mock 直接信任） |
| 金额校验 | 回调金额与订单应付金额一致，不一致抛 A0538（三端统一） |
| 幂等处理 | 订单级分布式锁 + 状态判断 + 支付流水唯一索引（三重保障） |
| 防重复下单 | 订单级分布式锁（用户+商品，5 秒） |
| 敏感信息 | 支付流水号脱敏展示，回调原始报文存库不对外 |

### 7.2 权限控制

| 权限标识 | 控制范围 |
|---------|---------|
| order:refund:approve | 售后审核通过/驳回（后端接口校验） |
| order:list | 后台订单分页列表（后端接口校验） |
| order:refund:list | 后台售后审核列表（后端接口校验） |
| order:stats | 订单统计（后端接口校验） |

> 后台订单列表与售后审核列表属后台运营数据，收紧为按钮权限（order:list / order:refund:list，挂于订单管理菜单下）。详情接口由用户端越权校验（§7.3）管控。

### 7.3 用户端越权校验

getDetail/cancel/pay/applyAfterSale 接口校验 `order.userId == 当前用户ID`，非本人操作返回 A0530（不泄露订单是否存在）；订单详情缓存命中时同样校验缓存 VO 归属。

### 7.4 售后安全

| 防护项 | 实现方式 |
|--------|---------|
| 政策口径 | 退款为兜底保障非常规权益，默认不可随意退；原因类型必选，主观原因拦截提示 |
| 唯一性 | 每订单仅一次售后（退款记录订单 ID 唯一约束 + 前置检查，重复抛 A053A） |
| 折算校验 | 会员卡按天、积分卡按用量、商家原因可全额（运营决策），向下取整到分 |
| 双审核 | 原因成立性 + 折算金额双审核，通过后按商品类型回退履约 |
| 退款联动 | vip：扣成长值/退券/调整到期/重算等级；credit：扣减未消耗积分（source=refund） |

### 7.5 并发控制

| 场景 | 实现方式 |
|--------|---------|
| 优惠券锁定原子性 | 条件 UPDATE status=1→4，0 行影响抛 A0525；与订单创建同一事务 |
| 余额扣减原子性 | 乐观锁（version 字段）单行 UPDATE，失败重试 ≤3 次 |
| 订单超时取消 | 定时任务每 5 分钟扫描，关单 + 释放券 + 解冻余额 |
| 支付回调幂等 | 订单级分布式锁 + 状态判断 + 支付流水唯一索引（三重保障） |
| 防重复下单 | 用户+商品粒度分布式锁（5 秒），获取失败抛 A0539 |

## 8. 配置项

| 配置项 | 说明 | 默认值 |
|--------|------|--------|
| 订单支付超时时间 | 创建后多少分钟超时 | 30 分钟 |
| 自动续费扣款重试 | 失败重试次数（仅会员卡） | 3 |
| 自动续费重试间隔 | 重试间隔 | 2 小时 |
| 自动续费折扣 | 续费价格折扣 | 0.95 |
