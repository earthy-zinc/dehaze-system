### 3.4 核心业务逻辑

#### 订单创建逻辑

1. **参数校验**：套餐存在且在售、优惠券可用、payMethod ∈ {wechat, alipay, balance, combined}
2. **防重复下单**：Redisson 锁（key: `order:lock:{userId}:{packageId}`，waitTime=0, leaseTime=5秒，非阻塞，获取失败抛 DUPLICATE_ORDER）
3. **价格计算**：调用 `PackageService.calculatePrice`，originalPrice 取 `pkg.original_price`
4. **金额校验**：应付金额 ≥ 0
5. **优惠券锁定**：条件UPDATE `UPDATE sys_user_coupon SET status=4 WHERE id=? AND status=1` 防止并发超发，检查影响行数，为0抛 COUPON_ALREADY_USED。锁定时仅设 status=4，不设 used_order_id（核销时再设）。
6. **生成订单**：订单号格式 `DH + yyyyMMddHHmmss + 6位随机数`，插入 `sys_order`，expire_time = NOW() + 30min
7. **事务保证**：订单创建与优惠券锁定同一事务
8. **职责分离**：create() 不触发渠道下单，仅创建订单记录；由 pay() 调用渠道统一下单返回支付链接

#### 支付回调处理（核心幂等逻辑）

```
接收渠道回调（路径：/api/v1/orders/payment/{channel}/callback）
    ↓
验签校验（签名+金额）
    ├─ 失败 → 记录日志，返回失败
    └─ 成功 → 继续
    ↓
Redisson 分布式锁（key: payment:lock:{orderNo}，waitTime=0 非阻塞，leaseTime=10秒）
    ├─ 获取失败 → 直接返回成功（视为重复回调）
    └─ 成功 → 继续
    ↓
查询订单状态
    ├─ paid/completed → 幂等返回成功
    ├─ 非 pending → 记录异常，返回失败
    └─ pending → 继续
    ↓
金额校验（回调金额 > 0 且与订单应付金额一致）
    ↓
插入支付流水（唯一索引 uk_payment_no 防重）
    ↓
更新订单状态为 paid
    ↓
触发权益生效（同事务）：
    - 更新 sys_member 等级与到期时间
    - 增加成长值（consume 类型）
    - 核销优惠券（status=2, used_order_id）
    - 推送支付成功通知
    ↓
释放分布式锁
    ↓
返回成功
```

#### 订单超时取消（定时任务）

1. **触发时机**：每5分钟
2. **扫描条件**：`status=1 AND expire_time < NOW()`
3. **取消流程**：
   - 调用渠道关单接口（防延迟支付）
   - 更新订单状态为 cancelled
   - 释放优惠券（status=1）
   - 记录 cancel_reason="超时未支付"

#### 退款申请逻辑

1. **越权校验**：`order.userId == 当前用户ID`，非本人操作抛 ORDER_NOT_FOUND
2. **状态校验**：订单状态为 paid(2) 或 completed(3)，否则抛 ORDER_STATUS_INVALID
3. **唯一性校验**：uk_order_id 阻止重复申请
4. **退款金额**：全额退款（`refund_amount = paid_amount`）
5. **used_quota**：固定为 0
6. **订单状态变更**：paid/completed → refunding(5)
7. **创建退款记录**：插入 `sys_refund_record`，refund_no = `RF + 订单号生成规则`，status = refunding(1)
8. **退款原因拼接**：customReason 非空时以 `reason + ":" + customReason` 拼接后写入 reason 字段（三端统一）

#### 退款审核逻辑

```
审核通过：
    - 调用渠道退款接口
    - 等待渠道回调（异步）
    - 回调成功 → 订单 refunded(6)，退款记录 status=2，权益回收，扣减成长值
    - 渠道退款失败 → 退款记录 status=3（refund_failed），订单恢复为 paid(2)，记录 error_message，人工重试

审核驳回：
    - 订单恢复 paid
    - 记录驳回原因
    - 通知用户
```

#### 自动续费执行（定时任务）

1. **触发时机**：每小时
2. **扫描条件**：`status=1 AND next_renew_time <= NOW()`
3. **续费流程**：
   - 创建新订单（is_auto_renew=1），originalPrice 取 `pkg.original_price`
   - **95折优惠**：`payable_amount = sale_price * 0.95`（截断取整），`discount_amount = sale_price - payable_amount`
   - 调用渠道代扣接口
   - 扣款成功 → 续费订单叠加有效期，fail_count 重置为 0
   - 扣款失败 → fail_count+1，next_renew_time = NOW() + 2小时（重试间隔），重试（最多3次）
   - 3次失败 → status=0，next_renew_time 置空，关闭自动续费

### 3.5 事务管理

| 操作类型 | 事务级别 | 说明 |
|---------|---------|------|
| 查询操作 | 只读事务 | 优化性能 |
| 订单创建 | 读写事务 | 订单+优惠券锁定 |
| 支付回调 | 读写事务 | 流水+订单+权益+成长值 |
| 退款执行 | 读写事务 | 退款记录+订单+权益回收 |
| 自动续费 | 读写事务 | 新订单+扣款+有效期叠加 |

**长事务拆分**：支付回调中的外部调用（MinIO 通知、推送）拆出事务外，避免连接池耗尽。

### 5.1 refundRetryTask 退款失败重试

三端（Java/Python/Go）均已实现，CRON 为 `0 0/30 * * * ?`（每 30 分钟）。

- **扫描条件**：`sys_refund_record` 中 `status=3`（退款失败）且 `retry_count < 3` 的记录
- **重试上限**：最大重试次数 3 次，达到上限后标记为最终失败（`error_message` 追加"已达重试上限，转为最终失败"）
- **处理逻辑**：
  1. 查询订单信息，跳过订单不存在的记录
  2. 递增 `retry_count`
  3. 余额支付渠道（`pay_method='balance'`）直接标记成功；其他渠道调用支付网关退款接口
  4. 退款成功：更新退款记录 `status=2`、`refund_time=NOW()`，订单状态置为 `6`（已退款）
  5. 退款失败：更新 `error_message`，`retry_count` 达上限时标记最终失败
- **数据库字段**：`sys_refund_record.retry_count`（tinyint，默认 0，自动重试次数）
- **参考实现**：Java `OrderServiceImpl.retryFailedRefunds`、Python `OrderService.retry_failed_refunds`、Go `OrderService.RetryFailedRefunds`

## 7. 安全设计

### 7.1 支付安全

| 防护项 | 实现方式 |
|--------|---------|
| 签名验证 | 渠道公钥验签 |
| 金额校验 | 回调金额与订单金额一致 |
| 幂等处理 | Redis 锁 + 唯一索引双重保证 |
| 防重复下单 | Redis 锁（用户+套餐，5秒） |
| 敏感信息 | 支付流水号脱敏展示 |

### 7.2 权限控制

| 权限标识 | 控制范围 |
|---------|---------|
| order:refund:approve | 退款审核 |
| order:refund:reject | 退款驳回 |
| order:list | 后台订单列表 |
| order:detail | 订单详情 |
| order:stats | 订单统计 |

**用户端越权校验**：getDetail、cancel、pay、applyRefund 接口必须校验 `order.userId == 当前用户ID`，非本人操作返回 ORDER_NOT_FOUND（避免泄露订单是否存在）。
