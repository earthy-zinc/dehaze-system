# 订单管理模块需求规格

> **模块边界说明**：本模块是平台**统一交易中枢**，覆盖所有商品（会员卡 / 积分卡）的订单创建、支付对接、回调处理、退款申请/审核、自动续费、余额账户管理、对账与订单统计；**商品定义与定价**由[套餐管理模块](../套餐管理/需求规格.md)承接，**会员卡履约（等级变更与成长值）**由[会员管理模块](../会员管理/需求规格.md)承接，**积分卡履约（积分到账）**由[AI 计费管理模块](../AI计费管理/需求规格.md)承接。
>
> **设计基线**：本模块遵循[商业化体系总体架构](../../../01-产品设计/07-商业化体系总体架构.md)的产品思想——所有可售商品统一经订单管理完成交易，商品类型差异集中在履约与退款。
>
> **三后端契约**：Java/Go/Python 三后端 API 契约完全一致，Java 权威，Go/Python 对齐。

## 1. 模块概述

### 1.1 模块定位

订单管理模块是平台商业化体系的**统一交易中枢**，负责处理用户购买商品（会员卡 / 积分卡，未来可扩展）的完整交易流程，包括订单创建、支付对接、履约生效、退款处理、自动续费、余额账户管理与订单状态全生命周期管理。该模块连接套餐管理（商品）、支付渠道（资金）、余额账户（钱包）、会员管理（会员卡履约）与 AI 计费（积分卡履约）。

商品类型决定交易链路的差异点（仅履约与退款分流），下单、支付、超时、取消等交易行为对所有商品类型一致。

### 1.2 核心价值

| 价值维度 | 具体内容 |
|---------|---------|
| **统一交易** | 所有商品（会员卡 / 积分卡）统一经订单管理交易，交易链路复用 |
| **交易闭环** | 从下单到权益生效的完整流程自动化，用户无需人工干预 |
| **支付安全** | 对接主流支付渠道（微信/支付宝，未启用时 mock 回退），保证交易安全和资金准确 |
| **状态透明** | 订单状态实时可查，支付结果即时反馈 |
| **余额账户** | 平台余额充值、余额支付、组合支付，资金可流转 |
| **退款兜底** | 退款定位为特殊原因兜底保障（非随意退），审核含原因成立性与金额折算 |
| **资金对账** | 每日与支付渠道对账，差异告警 |

### 1.3 业务目标

#### 功能目标

- 实现商品购买的完整订单流程（创建→支付→履约→完成）
- 对接微信支付、支付宝两大主流支付渠道（渠道配置未启用时走 mock）
- 支持平台余额支付（余额校验、冻结、扣减）
- 支持组合支付（余额 + 第三方渠道）
- 提供退款申请、审核的全流程管理，按商品类型折算退款金额，特殊原因兜底
- 支持自动续费的定时扣款（会员卡，见 §3.4）
- 支付成功/退款结果通知用户
- 每日与支付渠道对账

#### 性能目标

| 指标 | 目标值 | 说明 |
|-----|--------|------|
| 订单创建 | <200ms | 下单接口响应时间 |
| 支付回调处理 | <3s | 从收到回调到权益生效的延迟 |
| 订单列表查询 | <500ms | 用户端和后台分页查询 |
| 支付超时取消 | 30min | 未支付订单自动取消时间 |
| 余额扣减 | <100ms | 余额支付/组合支付中余额扣减延迟 |

## 2. 订单状态机设计

### 2.1 订单状态定义 (F-OM-001)

| 状态 | 状态码 | 说明 | 后续可能状态 |
|------|--------|------|------------|
| 待支付 | `pending` | 订单已创建，等待用户支付 | 已支付 / 已取消 |
| 已支付 | `paid` | 支付成功，履约已生效 | 已完成 / 退款中 |
| 已完成 | `completed` | 会员卡有效期结束归档；积分卡支付后即完成 | 退款中 |
| 已取消 | `cancelled` | 用户取消或超时自动取消 | - |
| 退款中 | `refunding` | 用户提交售后申请，等待审核 | 已退款 / 已支付 |
| 已退款 | `refunded` | 退款完成 | - |

> **商品类型与状态**：会员卡订单按有效期推进（paid → 到期 completed）；积分卡为一次性商品，无有效期，**支付成功后即置 completed**（履约=积分到账）。

### 2.2 状态流转图

```mermaid
stateDiagram-v2
    [*] --> 待支付
    待支付 --> 已支付: 支付成功
    待支付 --> 已取消: 用户取消
    待支付 --> 已取消: 超时取消
    已支付 --> 退款中: 售后申请通过初筛
    已支付 --> 已完成: 会员卡到期 / 积分卡支付即完成
    退款中 --> 已退款: 审核通过
    退款中 --> 已支付: 审核驳回
    已完成 --> [*]
    已取消 --> [*]
    已退款 --> [*]
```

### 2.3 状态流转规则

| 流转 | 触发条件 | 处理逻辑 |
|------|---------|---------|
| pending → paid | 支付渠道回调成功（微信/支付宝）、余额支付或组合支付完成 | 更新订单状态、按商品类型履约、记录成长值、核销优惠券 |
| pending → cancelled | 用户主动取消 | 释放优惠券（状态 4→1）、解冻余额（组合支付）、记录取消原因 |
| pending → cancelled | 30 分钟未支付 | 定时任务扫描（每 5 分钟），调用渠道关单后自动取消 |
| paid → completed | 会员卡有效期到期；积分卡支付即完成 | 定时任务扫描归档（会员卡）；积分卡支付时直接完成 |
| paid → refunding | 用户提交售后申请 | 创建退款记录，等待审核 |
| refunding → refunded | 审核通过 | 执行退款、按商品类型回退履约（扣成长值/退券/调整到期/回退未消耗积分）、重新计算会员等级 |
| refunding → paid | 审核驳回 | 恢复订单状态（会员卡未到期） |

## 3. 订单创建与支付

### 3.1 订单创建 (F-OM-002)

#### 3.1.1 功能描述

用户选择商品（会员卡 / 积分卡）后创建订单，生成订单号并关联商品信息、价格、优惠券。

#### 3.1.2 创建流程

```
用户选择商品（会员卡 / 积分卡）+ 选择优惠券（可选）+ 选择支付方式
    ↓
前端调用订单创建接口
    ↓
后端校验：
    ├─ 商品是否在售
    ├─ 支付方式是否合法（wechat/alipay/balance/combined）
    ├─ combined 支付：校验 balanceAmount > 0 且 < payableAmount
    ├─ 防重复下单（Redis 分布式锁，用户+商品粒度，5 秒，三端统一实现）
    └─ 价格计算（原价 - 促销折扣 - 优惠券抵扣）
    ↓
锁定优惠券（状态改为已锁定，支付成功后才核销）
    ↓
生成订单号（DH + yyyyMMddHHmmss + 6位随机数）
    ↓
记录订单信息（商品信息冗余存储，含商品类型与类型差异化信息），expire_time = 创建时间 + 30min
    ↓
返回订单信息（create 不触发渠道下单，由 pay 发起）
```

> **说明**：订单创建时**不校验用户当前等级**（任何等级可购买任意商品）；**不调用渠道下单**，仅创建订单记录（职责分离），支付链接由 pay 接口获取。

#### 3.1.3 订单字段

| 字段 | 说明 |
|------|------|
| orderNo | 订单号（DH + 时间戳 + 6位随机数） |
| userId | 用户ID |
| productId | 商品ID（关联套餐管理商品） |
| productName | 商品名称（冗余存储，防止商品改名） |
| productType | 商品类型（会员卡 / 积分卡） |
| productLevel | 商品对应会员等级（会员卡） |
| periodDays | 有效期天数（会员卡） |
| creditAmount | 可得积分数量（积分卡） |
| originalPrice | 原价（分） |
| discountAmount | 促销折扣金额（分） |
| couponId | 用户优惠券实例ID |
| couponAmount | 优惠券抵扣金额（分） |
| payableAmount | 应付金额（分） |
| paidAmount | 实付金额（分，支付成功前为 0） |
| payMethod | 支付方式 |
| balanceAmount | 余额支付金额（分，仅组合支付时使用，记录余额支付部分金额） |
| status | 订单状态（1-6） |
| expireTime | 支付超时时间（创建时间 + 30min） |
| effectiveTime | 权益生效时间 |
| productExpireTime | 会员卡到期时间（积分卡为 NULL） |
| paidTime | 支付成功时间 |
| cancelReason | 取消原因 |
| isAutoRenew | 是否自动续费订单（仅会员卡） |

### 3.2 支付对接 (F-OM-003)

#### 3.2.1 支付方式

| 支付方式 | 编码 | 说明 |
|---------|------|------|
| 微信支付 | `wechat` | 统一下单（native 扫码），返回二维码 URL；渠道未配置时 mock 返回 |
| 支付宝 | `alipay` | 统一下单，返回支付链接；渠道未配置时 mock 返回 |
| 平台余额 | `balance` | 校验余额充足→冻结→支付成功扣减、支付失败解冻 |
| 组合支付 | `combined` | 余额 + 第三方渠道组合支付，余额部分先扣减，剩余走第三方渠道 |

> **说明**：渠道配置通过 `payment.wechat.enabled`/`payment.alipay.enabled` 控制，未启用时统一下单/验签/退款/关单全部 mock（便于本地联调）。

#### 3.2.2 支付流程

```
用户选择支付方式
    ↓
├─ 微信/支付宝：
│   后端调用支付渠道统一下单接口（pay）
│   返回支付参数（二维码URL / 支付链接）
│   记录支付流水（status=1 处理中）
│   用户完成支付 → 支付渠道异步回调通知后端
│
├─ 平台余额：
│   校验余额 >= 应付金额（不足抛 BALANCE_INSUFFICIENT）
│   冻结余额（frozen_balance += payableAmount）
│   触发 completePayment（置已支付 + 按商品类型履约 + 扣减冻结余额）
│
└─ 组合支付（余额 + 第三方）：
    校验余额 >= balanceAmount（不足抛 BALANCE_INSUFFICIENT）
    冻结余额（frozen_balance += balanceAmount）
    第三方应付金额 = payableAmount - balanceAmount
    调渠道统一下单（第三方部分）→ 返回支付参数
    用户完成第三方支付 → 回调成功后触发 completePayment（扣减冻结余额 + 按商品类型履约）
```

#### 3.2.3 支付回调处理

```
收到支付渠道异步回调（微信/支付宝）
    ↓
验证签名 → 确保回调来源可信（未启用渠道时直接信任）
    ↓
查询订单 → 订单不存在返回失败
    ↓
金额校验 → 回调金额与订单第三方应付金额不一致：
  三端统一抛 A0538（记录日志 + 返回失败）
    ↓
获取订单级分布式锁（payment:lock:{orderNo}）→ 获取失败视为重复回调，幂等返回成功
    ↓
检查订单状态 → 已支付/已完成幂等返回成功；非待支付返回失败
    ↓
completePayment：
  1. 更新订单状态为 paid、记录支付流水
  2. 按商品类型履约：
     会员卡 → 激活会员权益（等级→商品等级、来源=package、到期时间叠加、月度配额按任务类型配置）
     积分卡 → 积分到账（credits_balance += creditAmount，流水 source=recharge）
  3. 记录成长值（change_type=consume，按实付金额 1:1）
  4. 核销优惠券（status 4→2，used_order_id 写入，模板 used_qty+1）
  5. 扣减冻结余额（组合支付/余额支付场景）
  6. 累加商品销量
  7. 积分卡订单置 completed（无有效期，一次性商品）
  8. 删除订单详情缓存
  9. 发送支付成功通知（站内信）
    ↓
返回成功响应给支付渠道
```

> **权益生效内容（会员卡）**：更新会员等级/来源（package）/到期时间（在原到期时间上叠加）/月度配额（按商品等级权益，含商品覆盖项）。
> **积分到账（积分卡）**：积分余额增加（充值来源，永久有效）、积分流水记录；**不影响会员身份与权益**。
> **成长值**：所有商品按实付金额 1:1 记录成长值（`consume` 类型）；支付成功后发送站内信通知。

#### 3.2.4 幂等设计

- 支付渠道回调可能重复发送，后端做幂等处理
- **幂等手段**：订单级分布式锁（`payment:lock:{orderNo}`，非阻塞，三端统一实现）+ 订单状态判断（已支付/已完成直接返回成功）
- 支付流水 `payment_no` 唯一索引防重
- 并发回调仅一个执行完整业务，其余返回成功

### 3.3 支付超时处理 (F-OM-004)

#### 3.3.1 功能描述

订单创建后 30 分钟内未支付，自动取消订单（定时任务，每 5 分钟），对全部商品类型一致。

#### 3.3.2 处理流程

```
定时任务扫描（每 5 分钟）
    ↓
查询 status=pending AND expire_time < NOW() 的订单
    ↓
逐条处理：
    ├─ 微信/支付宝 → 调用渠道关单接口（失败仅告警，不中断）
    ├─ 组合支付 → 调用渠道关单 + 解冻余额（frozen_balance -= balanceAmount）
    ├─ 余额支付 → 解冻余额（frozen_balance -= payableAmount）
    ├─ 更新订单状态为 cancelled
    ├─ 释放优惠券（状态 4→1）
    └─ 记录取消原因："系统超时自动取消"
```

### 3.4 自动续费扣款 (F-OM-005)

#### 3.4.1 功能描述

开启自动续费的用户，会员卡到期时自动创建续费订单并扣款；仅会员卡适用（积分卡为一次性商品，无续费）。

#### 3.4.2 扣款流程

```
定时任务扫描（每小时执行）
    ↓
查询 status=启用 且 next_renew_time <= NOW() 的自动续费配置（仅会员卡）
    ↓
逐条执行续费：
    ├─ 校验商品在售
    ├─ 价格：payable = sale_price × 0.95（95折），discount = 差价
    ├─ 余额支付 → 校验余额、冻结、扣减
    ├─ 微信/支付宝 → 调渠道代扣接口（微信实际走统一下单+用户主动支付，无真实代扣）
    ├─ 扣款成功 → 激活会员权益（有效期叠加）→ 记录成长值（consume）→ 创建已支付续费订单（is_auto_renew=1）
    │          → 更新 next_renew_time = 新到期时间，fail_count 归零
    └─ 扣款失败 → fail_count+1
        ├─ 未达 3 次 → next_renew_time = NOW() + 2 小时（重试）
        └─ 达 3 次 → 关闭自动续费（status=0），记录关闭原因
```

> **说明**：
> - **扣款时机为到期时**（`next_renew_time <= NOW()`）
> - **首次开启自动续费不触发扣款**：配置开启时 `next_renew_time` 未设置（NULL），需下次续费/购买后才有扣款时间
> - 微信渠道 `autoDeduct` 实际走"统一下单+用户主动支付"流程
> - 续费成功后发送站内信通知

### 3.5 余额账户管理 (F-OM-015)

#### 3.5.1 功能描述

平台余额账户支持用户充值、查询余额、余额支付与组合支付。

> **职责边界**：本账户为**人民币交易媒介**（充值 / 支付 / 退款）；积分（AI 消耗计量）属 AI 计费模块的积分账户，两账户职责分离，本模块不感知积分消耗。

#### 3.5.2 余额账户表设计

| 字段 | 类型 | 说明 |
|------|------|------|
| id | Long | 主键 |
| userId | Long | 用户ID（唯一） |
| balance | Long | 可用余额（分） |
| frozenBalance | Long | 冻结余额（分，支付处理中冻结的金额） |
| version | Integer | 乐观锁版本号 |
| deleted | Integer | 逻辑删除（0-未删除，1-已删除） |
| createBy/createTime/updateBy/updateTime | - | 审计字段 |

> **并发控制**：余额扣减使用乐观锁（`UPDATE ... SET balance=balance-?, version=version+1 WHERE id=? AND version=?`），避免并发扣减超卖。

#### 3.5.3 充值流程

```
用户选择充值金额 + 选择支付方式（微信/支付宝）
    ↓
后端创建充值订单（type=recharge，记录充值金额）
    ↓
调渠道统一下单 → 返回支付参数
    ↓
用户完成支付 → 渠道回调
    ↓
充值成功：balance += 充值金额，记录余额流水（change_type=recharge）
    ↓
发送充值成功通知
```

#### 3.5.4 余额流水

每笔余额变动记录流水（sys_balance_log），包含：用户ID、变动类型（recharge充值/consume消费/refund退款退回/freeze冻结/unfreeze解冻）、变动金额、变动后余额、关联订单号、时间。

#### 3.5.5 余额退款（充值余额退回）

充值后未消费的平台余额支持退回（用户权益保障），不设退款时限（仅无进行中的支付冻结时可退）。

| 规则项 | 说明 |
|--------|------|
| 申请条件 | 用户可用余额 > 0，且无进行中的支付冻结（frozen_balance 为 0） |
| 退回金额 | 可用余额（不含冻结余额），全额退回 |
| 退回渠道 | 原路退回：按余额充值时对应的原支付渠道退回（微信/支付宝）；无法原路的由管理员指定 |
| 审核流程 | 用户提交余额退款申请 → 管理员审核（金额/渠道核对）→ 渠道退款 → 可用余额扣减 + 流水记录（change_type=refund） |
| 与订单售后隔离 | 余额退款仅针对充值余额本身，不涉及积分卡/会员卡的订单售后退款（后者走 §4 售后流程），也不触发任何履约回退 |

## 4. 退款处理

### 4.1 退款政策 (F-OM-006)

#### 4.1.1 政策定位

退款是平台的**兜底保障**，而**不是用户的常规权益**。商品为虚拟服务/优惠商品，**不支持用户因主观原因（不想要、买错了、用不着）随意退款**——随意退款会击穿促销价/日常价的价格体系。

**政策口径**：默认不可随意退；仅在特殊原因下兜底。

#### 4.1.2 可退情形（特殊原因）

| 原因类型 | 含义 | 示例 |
|---------|------|------|
| 售后问题 | 商品无法正常使用或未生效 | 会员权益未生效、积分未到账、功能故障不可用 |
| 不可抗原因 | 平台或外部不可控 | 平台服务停摆、政策/合规要求下架 |
| 商家原因 | 平台自身过错 | 误扣款、系统错误、重复扣款 |

#### 4.1.3 执行弹性

政策口径从严，执行保留弹性：用户提交售后申请时可选择上述明确原因，也可选择"其他原因"——其他情形进入**管理员人工裁量**（基于用户历史、平台责任、体验考量酌情处理），三类明确原因走快速审核通道。**制度给底线、执行有弹性**，兼顾价格体系保护与用户体验。

### 4.2 退款申请 (F-OM-007)

#### 4.2.1 功能描述

用户对已支付的订单可提交**售后申请**；退款定位为"特殊原因兜底"策略。

#### 4.2.2 申请条件

| 条件 | 规则 |
|------|------|
| 订单状态 | 已支付（2）/已完成（3）可申请 |
| 原因必选 | 售后问题 / 不可抗原因 / 商家原因 / 其他 |
| 主观原因提示 | 用户选择"不想要/买错了"类原因时，提示"该商品为虚拟商品，不支持随意退款；如有售后问题请提交售后申请" |
| 退款次数 | 每个订单仅可退款一次（唯一约束 + 前置检查） |

#### 4.2.3 申请流程

```
用户进入订单详情 → 点击"售后申请"
    ↓
选择原因类型（售后问题 / 不可抗原因 / 商家原因 / 其他）+ 补充说明
    ↓
主观原因（不想要/买错了）→ 提示不支持随意退款，引导联系客服
    ↓
提交售后申请（reason + ":" + customReason 拼接）
    ↓
校验订单归属/状态/退款次数
    ↓
按商品类型折算退款金额（见 §4.3）
    ↓
创建退款记录（refund_amount = 折算后金额，used_days = 已使用天数 / used_credits = 已消耗积分）
    ↓
订单状态变为 refunding
    ↓
通知管理员审核（后台退款审核列表查询）
```

### 4.3 退款金额计算（按商品类型折算）

#### 4.3.1 会员卡（按天折算）

| 项目 | 计算方式 |
|------|---------|
| 已使用天数 | `used_days = max(1, ceil((NOW() - paid_time) / 86400))`（至少 1 天） |
| 剩余天数 | `remaining_days = period_days - used_days` |
| 退款金额 | `remaining_days <= 0` 时退款金额为 0（已用完不可退）；否则 `refund_amount = paid_amount × remaining_days / period_days`（向下取整到分） |
| 已使用部分 | `paid_amount - refund_amount`（不退） |

> **退款策略**：未使用部分（剩余天数）按比例全额退，已使用部分（已过天数）不退。退款金额记录在 `sys_refund_record.refund_amount`，已使用天数记录在 `used_days` 字段。

#### 4.3.2 积分卡（按用量折算）

| 项目 | 计算方式 |
|------|---------|
| 已消耗积分 | 订单到账积分中已消耗部分（消耗记录由 AI 计费模块提供） |
| 未消耗积分 | `creditAmount - 已消耗积分` |
| 退款金额 | `refund_amount = paid_amount × 未消耗积分 / creditAmount`（向下取整到分）；已消耗积分不退 |
| 积分回退 | 审核通过后，未消耗积分从积分余额扣减（流水 source=refund） |

#### 4.3.3 商家原因（平台过错）

商家原因（误扣款、系统错误、重复扣款）由运营决策，**可全额退款**（不适用按天/按用量折算）。

#### 4.3.4 组合支付订单退款金额拆分

组合支付订单退款时，按余额/第三方支付比例拆分退款金额：

| 拆分项 | 计算方式 |
|--------|---------|
| 余额退款金额 | `refund_amount × (balanceAmount / paidAmount)` |
| 第三方退款金额 | `refund_amount - 余额退款金额` |

### 4.4 退款审核 (F-OM-008)

#### 4.4.1 功能描述

管理员审核售后申请，决定通过或驳回；采用"原因成立性 + 折算金额"双审核。

#### 4.4.2 审核流程

```
后台退款审核列表（可按状态/订单号/用户名/申请时间/原因类型筛选）
    ↓
查看退款详情（订单信息、原因类型与说明、退款金额、已使用天数/已消耗积分）
    ↓
双审核：
  ├─ 原因成立性：特殊原因是否成立（三类明确原因快速判断；"其他"原因由管理员裁量）
  └─ 折算金额：按商品类型折算是否合理（商家原因可全额）
    ↓
├─ 审核通过：
│   调用支付渠道退款接口（余额支付/组合支付余额部分直接退回余额）
│   ├─ 退款成功 → 更新订单为 refunded，退款记录 status=2
│   │   → 扣减成长值（change_type=refund_deduct，扣减值=该单消费累积成长值×未使用比例，最低为 0）
│   │   → 退回优惠券（未使用则 status 2→1，已使用不退回）
│   │   → 按商品类型回退履约：
│   │       会员卡：调整到期时间 = paid_time + used_days，重新计算会员等级（基于扣减后成长值）
│   │       积分卡：扣减未消耗积分（source=refund）
│   │   → 发送退款成功通知
│   └─ 退款失败 → 退款记录 status=3（refund_failed），订单恢复为已支付/已完成，记录错误信息，待自动重试
│
└─ 审核驳回：
    退款记录 status=3（refund_failed），订单恢复为已支付/已完成，记录驳回原因，引导联系客服
```

> **说明**：
> - 渠道退款为**同步调用**（无退款异步回调处理）
> - 退款成功**扣减成长值**（`refund_deduct` 类型，扣减值 = 该订单消费获取的成长值 × 未使用比例，与退款折算比例一致），并基于扣减后成长值重新计算会员等级（会员卡）
> - 退款成功**退回优惠券**：优惠券未使用（订单核销后未用于其他消费）则 status 2→1 退回；已使用不退回
> - **退款失败自动重试**：定时任务每 30 分钟扫描 status=3 且 retry_count<3 的记录重试，达上限标记"已达重试上限，转为最终失败"（见 §5）

### 4.5 退款渠道

| 原支付方式 | 退款方式 |
|-----------|---------|
| 微信支付 | 调微信退款接口（原路退回） |
| 支付宝 | 调支付宝退款接口（原路退回） |
| 平台余额 | 余额退回（balance += refund_amount，记录余额流水 change_type=refund） |
| 组合支付 | 余额部分退回余额 + 第三方部分调渠道退款（按 §4.3.4 拆分） |

### 5.1 对账机制 (F-OM-016)

#### 5.1.1 对账流程

```
定时任务每日 02:00 执行
    ↓
查询前一日所有支付成功的支付流水
    ↓
调渠道对账接口下载渠道账单（微信/支付宝）
    ↓
逐笔比对：
    ├─ 系统有、渠道有 → 金额一致则通过，不一致记录差异（金额不符）
    ├─ 系统有、渠道无 → 记录差异（系统多单）
    └─ 渠道有、系统无 → 记录差异（渠道多单）
    ↓
差异写入 sys_reconciliation_diff 表
    ↓
差异告警通知运营（站内信 + 邮件）
```

#### 5.1.2 对账差异表设计

| 字段 | 说明 |
|------|------|
| reconciliationDate | 对账日期 |
| orderId/paymentNo | 订单ID/支付流水号 |
| systemAmount | 系统记录金额 |
| channelAmount | 渠道账单金额 |
| diffType | 差异类型（amount_mismatch/system_only/channel_only） |
| status | 处理状态（pending/resolved） |
| handleRemark | 处理备注 |

| 下单成功 | 跳转支付页，展示支付参数（二维码/支付链接）与倒计时 |
| 支付成功 | 跳转订单详情页，状态更新为已支付 |
| 取消订单 | 二次确认"确认取消该订单吗？"，确认后状态置为已取消 |
| 售后申请提交 | 提示"售后申请已提交，等待审核"，状态置为退款中 |
| 退款审核结果 | 通过则提示"退款已退回原账户"；驳回则提示"审核未通过：{原因}，如有疑问请联系客服" |
| 余额充值成功 | 余额数字更新，提示"充值成功" |

### 8.4 错误提示文案规范

| 场景 | 提示文案 |
|------|---------|
| 余额不足 | "余额不足，请充值或选择其他支付方式" |
| 优惠券不可用 | "该优惠券不适用于当前商品" |
| 商品已下架 | "商品已下架，无法购买" |
| 重复下单 | "请勿重复提交，稍后重试" |
| 主观原因退 | "该商品为虚拟商品，不支持随意退款；如有售后问题请提交售后申请" |

## 9. 非功能需求

### 9.1 性能需求

| 指标 | 要求 | 实际 |
|-----|------|------|
| 支付回调处理 | <3s 完成履约 | 同事务完成，无外部阻塞调用 |
| 订单超时扫描 | 每 5 分钟执行，单次扫描 <30s | 逐条处理，订单量小时即时完成 |
| 自动续费扫描 | 每小时执行，单次扫描 <60s | 逐条处理 |
| 订单列表查询 | 分页查询 <500ms，支持万级订单 | 索引覆盖（user_id+status/status/expire_time 等） |
| 订单详情查询 | Redis 缓存（10 分钟），越权校验 | `order:detail:{orderNo}` |
| 余额扣减 | <100ms，乐观锁 | 单行 UPDATE，无外部调用 |
| 对账任务 | 每日 02:00，单次 <5min | 逐笔比对，分渠道并行 |

### 9.2 安全需求

| 方面 | 措施 |
|-----|------|
| 支付签名验证 | 渠道回调验签（渠道未启用时 mock 信任） |
| 金额校验 | 回调金额与订单应付金额一致，三端统一抛 A0538 |
| 幂等处理 | 订单级分布式锁 + 状态判断 + 支付流水唯一索引 |
| 防重复下单 | 订单级分布式锁（用户+商品，5 秒），三端统一实现 |
| 余额并发安全 | 乐观锁（version 字段），扣减时校验版本号 |
| 越权防护 | 用户端操作校验订单归属（非本人返回 A0530，不泄露订单存在性） |
| 敏感信息 | 支付流水号等不对外展示原始渠道报文 |

### 9.3 可靠性需求

| 方面 | 要求 | 实际 |
|-----|------|------|
| 回调重试 | 支付渠道回调失败时自动重试（渠道侧） | 依赖渠道重试；系统内幂等不重复生效 |
| 退款容错 | 退款失败时记录错误信息并自动重试 | 定时任务重试（上限 3 次） |
| 超时关单 | 超时取消前调用渠道关单接口 | 关单失败仅告警不中断 |
| 对账差异 | 每日对账发现差异时告警 |

### 9.4 并发处理

| 场景 | 处理策略 |
|------|---------|
| 并发支付回调 | 订单级分布式锁（`payment:lock:{orderNo}`），三端统一实现 |
| 优惠券并发使用 | 条件 UPDATE（status=1 → 4）+ 唯一约束 |
| 防重复下单 | 订单级分布式锁（`order:lock:{userId}:{productId}`，5 秒），三端统一实现 |
| 余额并发扣减 | 乐观锁（version 字段），扣减失败重试（最多 3 次） |
| 自动续费并发 | 逐条处理 + 异常隔离（单条失败不影响其余） |

> **三后端一致性**：订单锁、支付回调锁三端统一使用 Redis 分布式锁实现（Java Redisson / Go go-redis / Python redis-py）。
