# 订单管理模块需求规格

## 1. 模块概述

### 1.1 模块定位

订单管理模块负责处理用户购买 VIP 套餐的完整交易流程，包括订单创建、支付对接、履约生效、退款处理及订单状态全生命周期管理。该模块是商业化体系的交易中枢，连接套餐管理（商品）、支付渠道（资金）和会员管理（权益履约）。

### 1.2 核心价值

| 价值维度 | 具体内容 |
|---------|---------|
| **交易闭环** | 从下单到权益生效的完整流程自动化，用户无需人工干预 |
| **支付安全** | 对接主流支付渠道，保证交易安全和资金准确 |
| **状态透明** | 订单状态实时可查，支付结果即时反馈 |
| **退款保障** | 完善的退款流程，支持全额和部分退款 |

### 1.3 业务目标

#### 功能目标

- 实现套餐购买的完整订单流程（创建→支付→履约→完成）
- 对接微信支付、支付宝两大主流支付渠道
- 支持平台余额支付和组合支付
- 提供退款申请、审核、执行的全流程管理
- 支持自动续费的定时扣款

#### 性能目标

| 指标 | 目标值 | 说明 |
|-----|--------|------|
| 订单创建 | <200ms | 下单接口响应时间 |
| 支付回调处理 | <3s | 从收到回调到权益生效的延迟 |
| 订单列表查询 | <500ms | 用户端和后台分页查询 |
| 支付超时取消 | 30min | 未支付订单自动取消时间 |

## 2. 订单状态机设计

### 2.1 订单状态定义 (F-OM-001)

| 状态 | 状态码 | 说明 | 后续可能状态 |
|------|--------|------|------------|
| 待支付 | `pending` | 订单已创建，等待用户支付 | 已支付 / 已取消 |
| 已支付 | `paid` | 支付成功，权益已生效 | 已完成 / 退款中 |
| 已完成 | `completed` | 套餐有效期结束，订单归档 | - |
| 已取消 | `cancelled` | 用户取消或超时自动取消 | - |
| 退款中 | `refunding` | 用户申请退款，等待审核 | 已退款 / 已支付 |
| 已退款 | `refunded` | 退款完成，权益已回收 | - |

### 2.2 状态流转图

```
                    ┌──────────┐
                    │  待支付   │
                    │ pending  │
                    └────┬─────┘
                         │
            ┌────────────┼────────────┐
            ▼            ▼            ▼
     ┌──────────┐ ┌──────────┐ ┌──────────┐
     │  已支付   │ │  已取消   │ │ 超时取消  │
     │   paid   │ │cancelled │ │cancelled │
     └────┬─────┘ └──────────┘ └──────────┘
          │
     ┌────┼────────────┐
     ▼                 ▼
┌──────────┐    ┌──────────┐
│  退款中   │    │  已完成   │
│refunding │    │completed │
└────┬─────┘    └──────────┘
     │
     ├─── 审核通过 ──▶ ┌──────────┐
     │                 │  已退款   │
     │                 │ refunded │
     │                 └──────────┘
     │
     └─── 审核驳回 ──▶ ┌──────────┐
                       │  已支付   │
                       │   paid   │
                       └──────────┘
```

### 2.3 状态流转规则

| 流转 | 触发条件 | 处理逻辑 |
|------|---------|---------|
| pending → paid | 支付渠道回调成功 | 更新订单状态、激活会员权益、记录成长值 |
| pending → cancelled | 用户主动取消 | 释放优惠券（如使用）、关闭渠道订单 |
| pending → cancelled | 30 分钟未支付 | 定时任务扫描，自动取消 |
| paid → completed | 套餐有效期到期 | 定时任务扫描，归档订单 |
| paid → refunding | 用户申请退款 | 创建退款记录，等待审核 |
| refunding → refunded | 审核通过 | 执行退款、回收权益、扣减成长值 |
| refunding → paid | 审核驳回 | 恢复订单状态，通知用户 |

## 3. 订单创建与支付

### 3.1 订单创建 (F-OM-002)

#### 3.1.1 功能描述

用户选择套餐后创建订单，生成订单号并关联套餐信息、价格、优惠券。

#### 3.1.2 创建流程

```
用户选择套餐 + 选择优惠券（可选）
    ↓
前端调用 POST /api/v1/orders
    ↓
后端校验：
    ├─ 套餐是否在售
    ├─ 用户当前等级是否允许购买该套餐
    ├─ 优惠券是否有效且属于该用户
    └─ 价格计算（原价 - 促销折扣 - 优惠券抵扣）
    ↓
生成订单号（格式：DH + yyyyMMddHHmmss + 6位随机数）
    ↓
写入订单表 + 订单明细表
    ↓
锁定优惠券（状态改为已使用）
    ↓
返回订单信息 + 支付参数
```

#### 3.1.3 订单字段

| 字段 | 说明 |
|------|------|
| orderNo | 订单号（DH20260727143025000123） |
| userId | 用户ID |
| packageId | 套餐ID |
| packageName | 套餐名称（冗余存储，防止套餐改名） |
| packageLevel | 套餐对应会员等级 |
| periodDays | 有效期天数 |
| originalPrice | 原价 |
| discountAmount | 促销折扣金额 |
| couponId | 优惠券ID |
| couponAmount | 优惠券抵扣金额 |
| payableAmount | 应付金额 |
| paidAmount | 实付金额 |
| payMethod | 支付方式 |
| status | 订单状态 |
| expireTime | 支付超时时间（创建时间 + 30min） |
| effectiveTime | 权益生效时间 |
| packageExpireTime | 套餐到期时间 |

### 3.2 支付对接 (F-OM-003)

#### 3.2.1 支付方式

| 支付方式 | 编码 | 说明 |
|---------|------|------|
| 微信支付 | `wechat` | 支持扫码支付、JSAPI 支付、APP 支付 |
| 支付宝 | `alipay` | 支持扫码支付、WAP 支付、APP 支付 |
| 平台余额 | `balance` | 使用平台充值余额支付 |
| 组合支付 | `combined` | 余额 + 第三方支付组合 |

#### 3.2.2 支付流程

```
用户选择支付方式
    ↓
├─ 微信/支付宝：
│   后端调用支付渠道统一下单接口
│   返回支付参数（二维码URL / 支付链接 / APP调起参数）
│   前端展示支付界面
│   用户完成支付
│   支付渠道异步回调通知后端
│
├─ 平台余额：
│   后端校验余额是否充足
│   余额充足 → 直接扣减 → 支付成功
│   余额不足 → 返回错误 → 引导充值或换支付方式
│
└─ 组合支付：
    先扣减平台余额
    剩余金额通过第三方支付
    两部分都成功后订单支付完成
```

#### 3.2.3 支付回调处理

```
收到支付渠道异步回调
    ↓
验证签名 → 确保回调来源可信
    ↓
验证金额 → 回调金额与订单应付金额一致
    ↓
检查订单状态 → 仅 pending 状态可处理
    ↓
┌─ 金额一致 + 状态正确：
│   更新订单状态为 paid
│   记录支付流水
│   触发权益生效（调用会员管理模块）
│   记录成长值（按支付金额 1:1）
│   返回成功响应给支付渠道
│
└─ 异常情况：
    金额不一致 → 记录告警日志，返回失败
    订单已处理 → 幂等返回成功（防止重复回调）
    订单已取消 → 记录异常，人工处理
```

#### 3.2.4 幂等设计

- 支付渠道回调可能重复发送，后端必须做幂等处理
- 幂等键：订单号 + 支付渠道流水号
- 已处理的回调直接返回成功，不重复执行业务逻辑
- Redis 分布式锁防止并发回调冲突

### 3.3 支付超时处理 (F-OM-004)

#### 3.3.1 功能描述

订单创建后 30 分钟内未支付，自动取消订单。

#### 3.3.2 处理流程

```
定时任务每 5 分钟扫描
    ↓
查询 status=pending AND expire_time < NOW() 的订单
    ↓
逐条处理：
    ├─ 调用支付渠道关单接口（防止延迟支付）
    ├─ 更新订单状态为 cancelled
    ├─ 释放优惠券（状态恢复为未使用）
    └─ 记录取消原因：超时未支付
```

### 3.4 自动续费扣款 (F-OM-005)

#### 3.4.1 功能描述

套餐到期前 24 小时自动创建续费订单并发起扣款。

#### 3.4.2 扣款流程

```
定时任务扫描（每小时执行）
    ↓
查询开启自动续费且套餐 24 小时内到期的用户
    ↓
创建续费订单（同套餐、同支付方式）
    ↓
调用支付渠道代扣接口
    ├─ 扣款成功 → 回调处理 → 权益叠加生效
    ├─ 扣款失败 → 重试（最多 3 次，间隔 2 小时）
    └─ 3 次均失败 → 取消自动续费 → 通知用户手动续费
```

## 4. 退款处理

### 4.1 退款申请 (F-OM-006)

#### 4.1.1 功能描述

用户可对已支付的订单发起退款申请。

#### 4.1.2 退款条件

| 条件 | 规则 |
|------|------|
| 退款时限 | 支付成功后 7 天内可申请 |
| 使用次数 | 本月去雾/评估已用次数 < 总配额的 50% |
| 促销套餐 | 限时特价套餐不支持退款 |
| 退款次数 | 每个订单仅可退款一次 |

#### 4.1.3 申请流程

```
用户进入订单详情 → 点击"申请退款"
    ↓
展示退款规则和退款金额
    ↓
选择退款原因（下拉选择 + 补充说明）
    ↓
提交退款申请
    ↓
订单状态变为 refunding
    ↓
通知管理员审核
```

#### 4.1.4 退款金额计算

| 场景 | 退款金额 |
|------|---------|
| 未使用任何权益 | 全额退款 |
| 已使用部分权益 | 应付金额 × (1 - 已用次数 / 总配额) |
| 已使用超过 50% | 不支持退款 |

### 4.2 退款审核 (F-OM-007)

#### 4.2.1 功能描述

管理员审核退款申请，决定通过或驳回。

#### 4.2.2 审核流程

```
后台退款审核列表
    ↓
查看退款详情（订单信息、退款原因、退款金额、权益使用情况）
    ↓
├─ 审核通过：
│   调用支付渠道退款接口
│   退款成功 → 更新订单状态为 refunded
│   回收会员权益（降级到成长值对应等级）
│   扣减成长值（按支付金额等额扣减）
│   释放优惠券不退回（已使用）
│   通知用户退款成功
│
└─ 审核驳回：
    更新订单状态恢复为 paid
    记录驳回原因
    通知用户退款被驳回及原因
```

### 4.3 退款执行 (F-OM-008)

#### 4.3.1 退款渠道

| 原支付方式 | 退款方式 |
|-----------|---------|
| 微信支付 | 原路退回至微信 |
| 支付宝 | 原路退回至支付宝 |
| 平台余额 | 退回平台余额 |
| 组合支付 | 余额部分退余额，第三方部分原路退回 |

#### 4.3.2 退款状态

| 状态 | 说明 |
|------|------|
| 退款中 | 退款请求已发送，等待渠道处理 |
| 退款成功 | 渠道确认退款完成 |
| 退款失败 | 渠道退款失败，需人工介入 |

## 7. 非功能需求

### 7.1 性能需求

| 指标 | 要求 |
|-----|------|
| 支付回调处理 | <3s 完成权益生效，避免用户等待 |
| 订单超时扫描 | 每 5 分钟执行，单次扫描 <30s |
| 自动续费扫描 | 每小时执行，单次扫描 <60s |
| 订单列表查询 | 分页查询 <500ms，支持万级订单 |

### 7.2 安全需求

| 方面 | 措施 |
|-----|------|
| 支付签名验证 | 所有支付回调必须验证渠道签名 |
| 金额校验 | 回调金额与订单金额必须一致 |
| 幂等处理 | 支付回调、退款回调均做幂等 |
| 防重复下单 | 同一用户同一套餐 5 秒内禁止重复下单 |
| 敏感信息 | 支付流水号等敏感信息脱敏展示 |

### 7.3 可靠性需求

| 方面 | 要求 |
|-----|------|
| 回调重试 | 支付渠道回调失败时自动重试（渠道侧） |
| 补偿机制 | 定时任务扫描支付成功但权益未生效的异常订单 |
| 退款容错 | 退款失败时记录异常并告警，支持人工重试 |
| 数据备份 | 订单数据每日备份，保留 90 天 |

### 7.4 并发处理

| 场景 | 处理策略 |
|------|---------|
| 并发支付回调 | Redis 分布式锁（订单号粒度） |
| 优惠券并发使用 | 乐观锁 + 唯一索引 |
| 余额并发扣减 | Redis 原子操作 + 异步落库 |
| 自动续费并发 | 用户维度串行处理 |
