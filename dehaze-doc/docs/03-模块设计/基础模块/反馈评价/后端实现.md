#### MQ 队列与路由

三端统一使用队列名/路由键 `feedback.low_rating`。评价创建时若 `rating ≤ 2`，异步发布评价事件到该队列，由低分告警服务消费并执行告警判断。

#### 告警接收人

低分告警通知接收人为 `ROOT` 和 `ADMIN` 两种角色用户（通过 `sys_role` 关联 `sys_user_role` 查询，过滤 `status=1` 的启用用户）。

#### 告警消息字段

三端统一的告警消息字段（通过 `MessageService.send` 发送站内信）：

| 字段 | 普通告警 | 紧急告警 | 严重告警 |
|------|---------|---------|---------|
| bizModule | `feedback` | `feedback` | `feedback` |
| type | `alert` | `critical_alert` | `critical_alert` |
| priority | 3 | 1 | 2 |

> priority 数字越小越紧急：紧急=1，严重=2，普通=3。紧急和严重告警统一使用 `critical_alert` 类型。

### 3.4 核心业务逻辑

#### 评价创建逻辑

1. **参数校验**：评分1-5、文字≤500字符、图片≤3张
2. **图片安全**：校验URL为MinIO域名，文件类型为 jpg/jpeg/png/webp
3. **处理记录校验**：根据 `predLogId` 查询处理记录，不存在抛 `PREDICTION_LOG_NOT_FOUND`
4. **状态校验**：处理记录状态必须为已完成（`predLog.status == COMPLETED`），否则抛 `OPERATION_NOT_ALLOW`
5. **归属校验**：处理记录必须属于当前用户（`predLog.userId == 当前用户ID`），否则抛 `OPERATION_NOT_ALLOW`
6. **唯一性校验**：`uk_pred_log_id` 唯一索引防止重复评价，已评价抛 `RATING_ALREADY_EXISTS`
7. **时限校验**：基于处理记录的 `update_time`（完成时间）判断，超过 30 天抛 `RATING_EXPIRED`
8. **事务写入**：在单一事务中执行——插入 `sys_rating` + 调用 `MemberService.adjustGrowth` 发放成长值（+5，change_type=rating）
9. **每日上限校验**：用户当日评价成长值获取 ≤5 次，超限不发放成长值但不影响评价创建
10. **触发低分告警**：评价提交后异步消息队列发送告警判断（rating ≤ 2）

> 输入参数校验（步骤1-2）必须在业务校验（步骤3-7）之前执行，避免通过非法输入探测处理记录是否存在。

#### 评价修改逻辑

1. **参数校验**：评分1-5、文字≤500字符、图片≤3张
2. **图片安全**：校验URL为MinIO域名，文件类型为 jpg/jpeg/png/webp
3. **评价存在校验**：根据 `ratingId` 查询评价，不存在抛 `RATING_NOT_FOUND`
4. **归属校验**：评价必须属于当前用户（`rating.userId == 当前用户ID`），不通过抛 `RATING_NOT_FOUND`（不暴露评价是否存在，与反馈详情隔离策略一致）
5. **更新写入**：更新 `rating`/`comment`/`tags`/`image_urls`/`is_anonymous` 字段

> 评价修改**不校验30天时限**（时限仅约束评价创建）。修改不增加成长值。

#### 反馈创建逻辑

1. **参数校验**：标题5-50字符、内容10-1000字符、图片≤5张且≤5MB
2. **图片安全**：类型校验+大小校验
3. **频率限制**：每用户每日 ≤5条（Redis 计数，先 GET 判断当日已发数再创建后 Incr，避免高并发竞态）
4. **写入反馈**：插入 `sys_feedback`，默认 status=pending
5. **通知**：推送管理员待处理提醒

#### 评价按处理记录查询的数据隔离

按处理记录查评价接口（`GET /api/v1/feedback/ratings/by-prediction/{predictionLogId}`）的数据隔离规则：

1. **归属校验**：校验 `predLog.userId == 当前用户ID`，不通过抛 `OPERATION_NOT_ALLOW`（防止越权枚举他人评价）
2. **匿名信息隐藏**：当 `isAnonymous == 1` 时，`userId`/`username`/`userAvatar` 字段返回 null（三端统一）

> 三端均需在 Service 层接收 `userId` 参数并执行归属校验，Controller 层从安全上下文获取当前用户 ID 传入。

#### 反馈详情数据隔离

反馈详情接口（`GET /api/v1/feedback/{id}`）的数据隔离规则：

1. **归属校验**：非管理员时校验 `feedback.userId == 当前用户ID`，不通过抛 `FEEDBACK_NOT_FOUND`（不暴露反馈是否存在）
2. **联系方式隐藏**：非管理员时隐藏 `contact` 字段（联系方式仅管理员可见），管理员返回完整 `contact`。三端统一：仅在 `isAdmin == true` 时设置 `contact` 字段，非管理员（含反馈所有者）不返回 `contact`

#### 低分告警判断逻辑

```
评价创建成功（rating ≤ 2）
    ↓
异步消息队列发送评价事件
    ↓
判断评分：
    ├─ rating=2 → 触发普通告警
    └─ rating=1 → 触发普通告警 + 进一步判断
    ↓
查询同算法24小时内低分评价数量：
    ├─ ≥3条 → 触发紧急告警（站内信+邮件）
    └─ <3条 → 仅普通告警
    ↓
查询当日全局低分率：
    ├─ >20% → 触发严重告警（站内信+邮件+短信）
    └─ ≤20% → 不触发
    ↓
告警延迟 <10s
```

#### 反馈状态流转

```
pending（待处理，status=1）
    ├─ assignFeedback → processing（处理中，status=2）
    │   ※ 仅 pending 状态会流转为 processing
    ├─ replyFeedback → replied（已回复，status=3）
    └─ closeFeedback → closed（已关闭，status=4）

processing（处理中，status=2）
    ├─ assignFeedback → 仅更新 assignee_id，状态不回退
    ├─ replyFeedback → replied（已回复，status=3）
    └─ closeFeedback → closed

replied（已回复，status=3）
    ├─ assignFeedback → 仅更新 assignee_id，状态不回退（已回复状态不回退为处理中）
    ├─ supplementFeedback → processing（用户补充重新打开，status=2）
    └─ closeFeedback → closed
```

> `assignFeedback` 仅在 `status==1`（pending）时才置为 `2`（processing），其余状态仅更新 `assignee_id` 和 `assigned_time`，不回退状态。

> `supplementFeedback` 在 `status==3`（replied）时必须将状态置为 `2`（processing），实现反馈重新打开。三端统一实现此状态流转。

### 3.5 跨用户越权错误处理统一规范

| 接口 | 越权场景 | 统一错误码 | 说明 |
|------|---------|-----------|------|
| 修改评价 `PUT /ratings/{id}` | 评价属于其他用户 | `RATING_NOT_FOUND` | 不暴露评价是否存在 |
| 按处理记录查评价 `GET /ratings/by-prediction/{id}` | 处理记录属于其他用户 | `OPERATION_NOT_ALLOW` | 防止枚举他人评价 |
| 反馈详情 `GET /feedback/{id}` | 反馈属于其他用户（非管理员） | `FEEDBACK_NOT_FOUND` | 不暴露反馈是否存在 |
| 补充说明 `POST /feedback/{id}/supplement` | 反馈属于其他用户 | `FEEDBACK_NOT_FOUND` | 不暴露反馈是否存在 |

> 越权场景统一返回 `NOT_FOUND` 类错误码，避免通过错误码差异探测资源是否存在。

## 4. 数据访问层设计

### 4.1 查询优化

#### 评价分页查询

- 索引 `idx_algorithm_id` 优化按算法筛选
- 索引 `idx_rating` 优化按评分筛选
- 索引 `idx_create_time` 优化时间范围
- 关联 `sys_user` 获取用户信息（匿名时跳过）

#### 反馈分页查询

- 复合索引 `idx_priority_status` 优化优先级+状态筛选
- 索引 `idx_assignee_id` 优化处理人维度查询

#### 统计聚合查询

- 按算法分组聚合平均评分
- 按时间分组聚合评分趋势
- 缓存统计结果（10分钟）

### 4.2 缓存策略

| 缓存对象 | 缓存 Key | 过期时间 | 更新策略 |
|---------|---------|---------|---------|
| 评价统计（全局） | rating:stats:global | 10 分钟 | 评价创建/修改时删除 |
| 评价统计（算法） | rating:stats:algorithm:{id} | 10 分钟 | 新评价时删除 |
| 反馈统计 | feedback:stats | 10 分钟 | 新反馈时删除 |
| 算法评价聚合 | algorithm:rating:{id} | 30 分钟 | 新评价时删除 |
| 用户评价频率 | rating:daily:{userId}:{date} | 25 小时 | 自动过期 |
| 用户反馈频率 | feedback:daily:{userId}:{date} | 25 小时 | 自动过期 |

> **缓存失效范围**：仅评价创建、评价修改、反馈创建会改变统计数据，需删除统计缓存。`hideRating`（隐藏评价）、`replyRating`（回复评价）、`replyFeedback`、`closeFeedback`、`assignFeedback`、`updateFeedbackTags` 等操作不改变统计聚合字段（评分值/标签/总数），**不需要**删除统计缓存。

## 6. 文件上传设计

### 6.1 图片上传流程

1. 前端调用文件上传接口
2. 后端校验文件类型（image/jpeg, image/png, image/webp）
3. 校验文件大小（≤5MB）
4. 上传至 MinIO，bucket: `feedback-images`
5. 返回访问URL
6. 前端在创建评价/反馈时携带URL

### 6.2 文件清理

- 评价/反馈删除时，关联图片从 MinIO 删除
- 定时任务清理无引用的孤立文件（每日）
