# 去雾处理模块 - 后端实现设计

## 1. 文档概述

### 1.1 文档目的

本文档描述图像处理（去雾处理）模块的后端实现方案，包括服务层设计、核心业务流程（单张图像任务、取消任务、参数预设管理、图像输入历史）、积分计费、模块间协作、缓存策略与安全设计。

---

## 2. 架构设计

### 2.1 模块分层架构

图像处理模块是用户处理流程的编排中心，负责串联图像输入、图像模型选择、统一模型路由调用与结果存储。模块本身不直接执行推理，通过 WPXNet 预查询拦截器链调用编排侧图像模型链路完成处理（编排侧另有 Redis MD5 缓存加速重复请求，见 §6）。

编排侧（dehaze-python）亦不执行推理与指标计算：图像推理（调用 dehaze-modal `POST /v1/images/edits`）与指标计算（`POST /v1/metrics`）经 HTTP 外置到 `dehaze-service/dehaze-modal`，编排侧保留状态机、拦截器链、结果缓存、计费与结果落库（归属划分见[AI 能力链路协作设计](../../../02-系统架构/09-AI能力链路协作设计.md)）：

```
Controller 层
├── ImageTaskController
├── PresetController
├── InputHistoryController
└── EvaluationController

Service 层
├── SysPredLogService
├── SysPresetService
├── SysInputHistoryService
└── SysEvalLogService

执行层
├── ImageTaskAsyncTask（异步执行器）
└── EvalLogAsyncTask

依赖模块
├── ImageModelClient（经统一模型注册表调用图像模型）
├── AiBillingService（AI计费管理，按张扣积分）
├── MemberService（会员管理，月赠积分/批量上限）
├── FavoriteService（收藏管理）
└── RecommendService（推荐管理）
```

### 2.2 核心组件职责

| 组件                   | 职责描述           | 关键能力                                                                      |
| ---------------------- | ------------------ | ----------------------------------------------------------------------------- |
| SysPredLogService      | 图像任务编排服务   | 单张任务编排、取消任务（终止推理+幂等）、任务历史分页查询（按模型筛选）       |
| SysPresetService       | 参数预设管理       | system/custom 预设 CRUD、系统预设只读保护、本人自定义预设归属校验             |
| SysInputHistoryService | 图像输入历史管理   | 分页查询（状态/来源筛选）、单删/批删/清空                                     |
| SysEvalLogService      | 评估编排服务       | 评估提交（免费）、评估日志管理                                                |
| ImageTaskAsyncTask     | 图像任务异步执行器 | 经统一模型路由调用图像模型、轮询任务状态（2s 间隔、300s 超时）、更新完成/失败 |
| EvalLogAsyncTask       | 评估异步执行器     | 调用编排侧评估、更新评估结果                                                  |

## 3. 核心业务流程

### 3.1 单张图像任务流程

去雾处理模块作为业务编排层，委托统一模型链路执行实际推理：

```
用户提交流程（model + fileId/imageUrl）
    ↓
SysPredLogService 校验模型存在（model_type=image_edit）、解析图片来源
    ↓
构建 PredictionContext → 拦截器链 intercept（MD5 缓存 / WPXNet 预查询）
    ↓
命中缓存：直接返回已完成结果（resultUrl + status=2），不计费
    ↓
未命中：提交前校验积分余额（不足返回 A0515，不预扣）→ 写入 sys_pred_log（status=1 处理中）
    ↓
ImageTaskAsyncTask.execute（异步）：
  - 经统一模型路由调用图像模型（model → 供应商 fallback/Key 轮换 → OpenAiImageAdapter /v1/images/edits）
  - 轮询任务状态（2s 间隔，300s 超时）
  - 完成 → 更新 sys_pred_log（status=2 + predUrl + time）→ 按张实扣积分
  - 失败 → 更新 sys_pred_log（status=3 + errorMessage），不产生积分扣减
    ↓
返回 taskId + status=1 给前端，前端轮询任务状态直至完成
```

> **积分计费**：图像任务按张消耗 AI 积分（`bill_type='image'`、`quantity_unit='image'`），提交前仅做余额校验（`ensure_balance`）不预扣，成功后按张实扣；命中缓存/WPXNet 拦截器、失败、取消均不计费。不使用按任务类型的月度配额路径（`check_and_deduct_quota`）。

### 3.2 批量处理

| 阶段         | 处理内容                                                    | 关键决策                                                                                               |
| ------------ | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 数量校验     | 校验图片数量是否超过会员等级批量上限                        | Java `getBatchLimit`：level_0 默认 5 张，VIP 按 `benefit.batchLimit`（50/200/1000 张），超限返回 A0500 |
| 图片来源校验 | 逐项校验每张图片的 fileId/imageUrl 至少提供一个             | 与单张任务一致，不满足返回 A0410"图片来源不能为空"                                                     |
| 任务提交     | 由 SDK 封装为多次单张任务提交（逐张循环 `submitImageTask`） | 每张独立执行，单张失败不影响其他（该张 status=3），积分按张独立校验与实扣                              |
| 结果聚合     | 前端聚合各子任务结果                                        | 后端无批量端点，整体进度由前端聚合各子任务状态展示                                                     |

> 无后端批量端点 `/prediction/batch`；批量 = 多次提交单张任务。

### 3.3 参数预设管理流程

参数预设分为系统预设和用户自定义预设两种类型（`sys_preset.type`：`system`/`custom`）：

| 预设类型   | 来源           | 可见范围     | 管理权限                    |
| ---------- | -------------- | ------------ | --------------------------- |
| 系统预设   | 系统管理员预置 | 所有用户可见 | 只读（修改/删除返回 A0502） |
| 用户自定义 | 用户自行保存   | 仅本人可见   | 本人可增删改（归属校验）    |

> 预设数据结构（`sys_preset` 表，按模型标识 `model` 关联）见 [03-数据库设计.md](../../../02-系统架构/03-数据库设计.md)。当前无预设数量上限限制；系统预设由管理员通过数据维护或 AI 模型管理侧维护。

### 3.4 取消任务流程

用户提交任务后可通过取消接口终止任务，由 `SysPredLogService.cancel(taskId)` 承载，对应需求 F-M04-001：

```
接收取消请求（taskId）
    ↓
查询任务并校验归属（create_by ≠ 当前用户 → A0401，与不存在同口径防枚举）
    ↓
状态判断：
  - 处理中(1)：执行取消流程 ↓
  - 已完成(2)/已失败(3)/已取消(4)：直接返回当前状态（幂等）
    ↓
终止后台推理（编排侧经 TaskTracker 取消任务协程）
    ↓
状态流转 sys_pred_log.status = 4（带 processing 前置条件的数据库更新，并发取消仅一个生效）
    ↓
返回当前状态
```

> 取消接口幂等：对非处理中状态的任务直接返回当前状态，不重复终止推理。积分仅在任务成功后实扣，取消不产生扣减也无需回补。后台推理在取消后完成时，其结果写入带 processing 前置条件校验，不会把已取消状态覆盖回已完成。

### 3.5 图像输入历史管理

图像输入历史由 `SysInputHistoryService` 承载，记录用户的图片输入（上传/拍照/样例）并支持重新处理，对应需求 F-M04-007：

| 能力     | 说明                                                                  |
| -------- | --------------------------------------------------------------------- |
| 分页查询 | 支持状态筛选（1成功/2失败/3处理中）与来源筛选（upload/camera/sample） |
| 删除管理 | 支持单删/批量删除/清空                                                |
| 重新处理 | 按记录的模型任务标签复用原图 URL 发起重新处理                         |

> 历史清理按会员权益 `history_retention`（100/500/2000/10000）配置保留条数；数据结构（`sys_input_history` 表）见 [03-数据库设计.md](../../../02-系统架构/03-数据库设计.md)。

## 4. 模块间协作

### 4.1 与 AI 模型管理模块的接口调用

| 调用场景 | 调用接口                                           | 说明                                                                                  |
| -------- | -------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 提交任务 | `ImageModelClient.submit(model, imageUrl, params)` | 经统一模型注册表解析（供应商 fallback/Key 轮换），本模块内维护拦截器链与 sys_pred_log |
| 轮询任务 | `ImageModelClient.getTaskStatus(taskId)`           | ImageTaskAsyncTask 轮询编排侧异步任务                                                 |
| 终止任务 | `ImageModelClient.cancelTask(taskId)`              | 取消流程终止编排侧推理进程                                                            |
| 提交评估 | `ImageModelClient.evaluate(...)`                   | EvalLogAsyncTask 调用评估服务（免费）                                                 |

> 任务执行（拦截器链、模型调用、日志落库、积分计费）在图像处理模块内完成，AI 模型管理模块提供模型注册表（`sys_ai_model`/`sys_ai_provider`）与统一模型路由（`model_registry` + 协议适配器）。

### 4.2 与收藏管理模块的集成

| 集成点       | 触发时机                         | 实现方式                                                      |
| ------------ | -------------------------------- | ------------------------------------------------------------- |
| 收藏事件触发 | 用户在任务历史或对比页面点击收藏 | 调用 FavoriteService.favorite(userId, "result", recordId)     |
| 取消收藏     | 用户取消收藏                     | 调用 FavoriteService.unfavorite(userId, "result", recordId)   |
| 收藏状态查询 | 加载任务历史列表时               | 批量查询 FavoriteService.isFavorited() 标记每条记录的收藏状态 |

收藏能力由收藏管理模块统一管理（`sys_favorite` 表，`target_type='result'`）。

### 4.3 与推荐管理模块的集成

| 集成点             | 说明                                                                                                                                                                                              |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 推荐模型一键使用   | 图像模型选择页面的推荐结果中，用户点击"立即使用"后携带 `recommendedBy`（推荐记录 ID）进入处理流程                                                                                                 |
| recommendedBy 记录 | 任务请求携带 `recommendedBy` 字段，三端落库到 `sys_pred_log.recommended_by`（单张/缓存命中路径均记录），任务历史列表透出；推荐管理模块效果报表以此统计采纳率（带推荐来源的任务记录数 / 推荐总数） |

### 4.4 与消息通知模块的集成

> 处理完成/失败通知不接入，处理进度经实时推送获知。任务流程不发送消息通知（`ImageTaskAsyncTask` 仅更新日志与指标，无 MessageService 调用），通知能力由消息通知模块提供。

### 4.5 与会员 / 计费模块的集成

| 集成点   | 说明                                                                                                                                                                           |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 余额校验 | 任务提交时按图像模型价格（按张）校验积分余额，不足返回 A0515（仅校验不预扣）                                                                                                   |
| 积分实扣 | 任务成功后按张实扣；失败/取消/缓存/拦截器命中不计费                                                                                                                            |
| 批量上限 | 批量处理校验 `getBatchLimit(member)`：level_0 默认 5，VIP 按 `benefit.batchLimit`                                                                                              |
| 月赠积分 | 会员月度赠送积分由月度任务 `grantVipMonthlyGift` 发放（`sys_member_benefit.vip_gift_credits`），`monthly_*_quota` 不作为消耗/计费口径（列保留、种子值置 0，读写通道仍在） |

### 4.6 与任务管理模块的关系

| 任务管理状态       | 图像任务状态（`sys_pred_log.status`） |
| ------------------ | ------------------------------------- |
| PENDING/PROCESSING | 1（处理中）                           |
| COMPLETED          | 2（已完成）                           |
| FAILED             | 3（失败）                             |
| CANCELLED          | 4（已取消）                           |

当前图像任务不进入 `sys_task` 表，在 `sys_pred_log` 维护四态状态机（1处理中/2已完成/3失败/4已取消）。状态 4（已取消）由取消流程触发（见 §3.4），伴随推理终止；积分仅在成功后实扣，取消不产生扣减。

## 6. 缓存策略

### 6.1 快速返回缓存（双层）

任务请求的快速返回由两层缓存构成：

**① Java/Go/编排侧拦截器链（WPXNet 预查询）**

任务请求先经过拦截器链（`PredictionContext` + `PredictionInterceptor`），命中拦截器则跳过模型推理直接返回结果：

| 拦截器              | 作用                                            | 命中条件                                                         |
| ------------------- | ----------------------------------------------- | ---------------------------------------------------------------- |
| WPXNet 预查询拦截器 | 标准数据集图片（WPXNet 系列）直接返回预处理结果 | 模型标识以 `wpxnet-` 前缀识别且原图 MD5 在 `sys_wpx_file` 映射表 |

拦截器链可扩展（实现 `PredictionInterceptor` 接口 + `@Component` 自动注册），当前仅注册 WPXNet 预查询拦截器。

**② 编排侧 Redis MD5 缓存**

编排侧在任务流程内实现 MD5 缓存：下载原图后计算**内容** MD5，查 Redis `image:{model}:{originMd5}`（24h TTL），命中则直接返回结果，不调用模型推理；未命中执行推理后写入缓存。

缓存值只存与环境无关的对象标识 `{storage, objectName, resultMd5, resultThumbnailUrl, format}`，结果 URL 在命中时由 `StorageService.get_url(objectName)` 按当前存储配置拼接。对象 URL 随环境（各环境存储域名不同）变化，缓存落绝对 URL 会在换环境后返回不可达地址。缺 `objectName` 的缓存值按未命中处理，重新走推理。

**特性**：

- 命中缓存时响应时延降至毫秒级（`sys_pred_log` 直接写入已完成记录）
- **缓存命中不计费**

### 6.2 参数预设查询

参数预设列表直接查询 MySQL（`sys_preset`），当前无缓存；数据量小、查询频率低，缓存收益有限。

### 6.3 任务结果与任务状态缓存

| 缓存对象 | 缓存 Key                | TTL     | 更新策略       |
| -------- | ----------------------- | ------- | -------------- |
| 任务结果 | `image:result:{taskId}` | 1 小时  | 处理完成时写入 |
| 任务状态 | `image:status:{taskId}` | 5 分钟  | 状态变更时更新 |
| 预设配置 | `image:preset:{userId}` | 30 分钟 | 预设变更时失效 |

## 7. 安全设计

### 7.1 积分与防超扣

| 防护措施   | 说明                                                                     |
| ---------- | ------------------------------------------------------------------------ |
| 提交前校验 | 提交任务时按模型价格（按张）校验余额，不足返回 A0515，不预扣             |
| 成功后实扣 | 任务完成后按张实扣；缓存/失败/取消不计费（见 §3.1/§3.4）                 |
| 状态机防重 | 取消与失败/完成的并发竞争由状态机条件更新收敛，终态不可被覆盖（见 §7.4） |

### 7.2 参数校验

| 校验项       | 规则                                                      | 错误码 |
| ------------ | --------------------------------------------------------- | ------ |
| 模型有效性   | `model` 对应的 `model_type=image_edit` 模型必须存在且启用 | A0401  |
| 图片来源     | fileId 与 imageUrl 至少提供一个，来源可解析               | A0410  |
| 批量上限     | 批量图片数量不超过会员等级批量上限（`getBatchLimit`）     | A0500  |
| 预设名称冲突 | 同一用户下自定义预设名称不可重复（与系统预设同名亦冲突）  | A0501  |
| 预设归属     | 仅本人自定义预设可修改/删除；系统预设只读                 | A0502  |
| 预设存在性   | 操作不存在的预设                                          | A0401  |

### 7.3 数据隔离

- 任务状态查询（`GET /images/tasks/{taskId}`）与取消（`POST /images/tasks/{taskId}/cancel`）仅限任务本人（`sys_pred_log.create_by` 归属校验，他人任务与不存在任务同样返回 A0401 防枚举）
- 任务历史列表仅返回当前用户记录（`create_by` 过滤）
- 参数预设仅能管理自己的自定义预设（系统预设只读）
- 所有接口校验用户身份与资源归属

### 7.4 任务状态机约束

图像任务状态遵循四态状态机：1 处理中 -> 2 已完成 / 3 已失败 / 4 已取消。状态流转校验拒绝非法跳跃（如从已完成回退到处理中），取消操作仅对处理中状态生效，对终态任务幂等返回当前状态（见 §3.4）。

状态流转以数据库条件更新实现（`UPDATE ... WHERE status = 1`）：仅处理中状态可流转到终态，终态记录不可被并发写入覆盖——取消后后台推理完成的结果、失败与取消的并发竞争均不会破坏终态，且以此作为「仅成功才实扣」的判定依据。

### 7.5 推理超时与 SSRF 防护（编排侧）

| 防护项       | 实现方式                                                                                                                                                                |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 单图推理超时 | 编排侧调用 `dehaze-modal` 带 30s 超时阈值（`INFERENCE_TIMEOUT_SECONDS`），超时任务标记失败且不计费（对齐需求）；服务侧同阈值自限并返回 504，两条路径同按失败处理 |
| 指标计算超时 | 编排侧调用 `dehaze-modal` 的 `/v1/metrics` 带 120s 上限（首次评估需加载 pyiqa 指标模型），超时按失败处理                                                                |
| 图片来源防护 | 外部图片 URL 禁止指向内网/回环/链路本地/保留地址（DNS 解析后逐 IP 校验）；系统存储下载经 base_url 前缀识别不受影响；不支持本地路径与非 HTTP(S) 协议                     |

### 7.6 并发控制

| 控制项           | 规则                                             |
| ---------------- | ------------------------------------------------ |
| 单用户并发任务数 | 限制单用户同时处于处理中的任务数量，超限拒绝提交 |
| 批量上限         | 按会员等级校验批量处理图片数量（见 §3.2）        |

### 7.7 资源回收

| 场景     | 回收策略                                               |
| -------- | ------------------------------------------------------ |
| 失败任务 | 清理推理产生的临时文件，保留失败日志记录               |
| 取消任务 | 终止推理进程后清理临时文件（见 §3.4）                  |
| 超时任务 | 轮询超时（300s）后标记失败，触发失败任务的资源回收流程 |

### 7.8 模型调用安全

| 防护项   | 实现方式                                                  |
| -------- | --------------------------------------------------------- |
| 超时控制 | 编排侧调用设置轮询超时（300s），超时标记任务失败          |
| 熔断降级 | 模型路由连续失败触发熔断，熔断期间返回缓存结果或 503 错误 |
| 调用隔离 | 任务异步执行（ImageTaskAsyncTask），避免阻塞主线程        |

## 8. 常量

以下均为代码常量，不可配置：

| 常量             | 说明                                                                         | 实际值 |
| ---------------- | ---------------------------------------------------------------------------- | ------ |
| 任务轮询间隔     | ImageTaskAsyncTask 轮询任务状态间隔                                          | 2s     |
| 任务轮询超时     | 任务状态轮询超时                                                             | 300s   |
| 单图推理超时     | 编排侧单图推理超时阈值（超时任务标记失败且不计费；推理由 dehaze-modal 执行） | 30s    |
| 指标计算超时     | 编排侧调用 dehaze-modal `/v1/metrics` 的上限（指标逐项隔离失败）             | 120s   |
| 批量兜底上限     | 非 VIP（level_0）用户的批量上限                                              | 5      |
| 历史记录配额兜底 | 图像输入历史（`sys_input_history`）默认条数兜底                              | 100    |

> 轮询间隔/超时为纯技术参数，无运营调整动机。**批量兜底上限与历史记录配额兜底仅防御权益配置缺失时的默认值**，正常值由会员权益配置（`sys_member_benefit` 的 `batchLimit`/`history_retention`）驱动，权益配置存在时以权益值为准。
>
> 任务结果保留时长、日志保留策略遵循 `sys_pred_log` 清理定时任务。
