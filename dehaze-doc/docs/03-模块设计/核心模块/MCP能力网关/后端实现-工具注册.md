# MCP 能力网关 - 后端实现设计（工具注册）

## 1. 文档概述

本文档描述 F-M07-002 API 自动发现与工具注册的后端实现，包括 OpenAPI 文档解析、API → `@mcp.tool()` 动态注册、描述增强、变更检测与通知。

## 2. 发现流程

### 2.1 启动时全量发现

```
网关启动
    ↓
MCPServer 初始化（SDK 内置 Streamable HTTP + JSON-RPC 2.0）
    ↓
ApiDiscoverer.discoverAll()
    ↓
读取 OpenAPI 文档（配置项 mcp.openapi.url）
    ↓
支持的 OpenAPI 规范版本：3.0 / 3.1
    ↓
解析每个 API → 动态构造 @mcp.tool() 装饰的函数
    ↓
注册到 MCPServer（SDK 自动接管 tools/list + tools/call + 参数校验）
    ↓
NamespaceBuilder.build() → 按 OpenAPI tags 聚合生成命名空间摘要
    ↓
启动完成，网关开始接受 MCP 请求
```

### 2.2 定时增量同步

```
每 5 分钟触发（mcp.openapi.sync-interval）
    ↓
ApiDiscoverer.discoverDiff()
    ↓
重新读取 OpenAPI → 解析
    ↓
与当前 MCPServer 已注册的 tool 对比：
  - added: 新 API → 动态注册新的 @mcp.tool() 函数到 MCPServer
  - removed: 删除 API → 从 MCPServer 注销
  - changed: API 参数变更 → 重新注册（SDK 自动更新 inputSchema）
    ↓
ToolRegistry.applyDiff(diff)

如果有任何变更（added/removed/changed）：
  NotificationHandler.push("tools/list_changed")
  （使已连接的 AI 对话模块 MCP 客户端得知变更）
```

### 2.3 手动刷新

管理员在管理端触发 `POST /admin/mcp/refresh`：

```
立即执行 ApiDiscoverer.discoverAll()
    ↓
ToolRegistry.replaceAll(...)
    ↓
NotificationHandler.push("tools/list_changed")
    ↓
返回刷新结果：{toolsCount, resourcesCount, promptsCount, diff}
```

## 3. API 过滤

### 3.1 多级过滤管道

```
OpenAPI 所有 paths
    ↓
Filter 1: 路径前缀白名单
  - 仅保留 /api/v1/** 开头的路径
  - 排除 /api/admin/** /api/internal/**
    ↓
Filter 2: 认证方式过滤
  - 仅保留 requirements.security 包含 "apiKey" 或 "bearer" 的 API
  - 跳过无认证或 Session 认证的 API（LLM 无法提供 Session Cookie）
    ↓
Filter 3: HTTP 方法过滤
  - 排除 DELETE（危险操作）

  - 保留 GET / POST / PUT / PATCH
    ↓
Filter 4: 参数类型过滤
  - 排除参数含 format=byte / type=file 的 API（二进制上传）
    ↓
Filter 5: 标签过滤
  - 排除 tags 含 "internal" / "deprecated" 的 API
    ↓
Filter 6: 显式排除列表（配置文件）
  - mcp.exclude-paths: ["/api/v1/auth/login", "/api/v1/users/{id}/password"]
    ↓
最终保留的 API 列表
```

### 3.2 排除列表配置

通过配置维护排除/包含路径列表：默认排除登录/注册等认证接口与文件上传接口（二进制上传不适合 LLM 工具），其余路径默认纳入；包含列表为空表示全部通过。

## 4. API 分类

### 4.1 自动分类规则

```
过滤后的 API
    ↓
分类引擎：根据 HTTP method + 路径特征 + 是否有副作用标记

rule 1: GET + 无副作用(非创建/更新/删除等标记) → resource
  - 单条：GET /algorithms/{id} → resource uri: algo://{id}
  - 列表：GET /algorithms → resource uri: algo://list
  - 其他：自动生成 resource URI

rule 2: POST/PUT/PATCH → tool
  - POST /predict/dehaze → tool name: predict_dehaze

rule 3: 配置文件指定的 prompt 模板 → prompt
  - mcp.prompts 配置列表中定义的模板
  - 示例：dehaze-evaluation → 去雾效果评估报告模板
```

### 4.2 Prompt 模板配置

Prompt 是预定义的文本模板，不在 OpenAPI 中自动发现，而是通过配置手动定义（模板名、描述、模板内容与参数列表，参数支持必填声明）。示例：去雾效果评估报告模板（按 PSNR/SSIM 指标、主观视觉效果、处理速度评估指定算法）。

## 5. Tool 生成规则

### 5.1 动态工具注册

利用函数闭包动态构造工具函数并注册到工具服务：

```
为每个待注册的 POST/PUT API 动态生成工具函数：
  - 函数签名与类型注解由 OpenAPI 参数/请求体转换而来
  - 函数文档由 OpenAPI 描述填充
  - 函数体调用请求转发器完成 HTTP 转发
  - 按工具名与描述注册到工具服务（SDK 自动提取入参结构与文档）
```

**关键点**：
- SDK 从 `tool_func.__annotations__` 和 `tool_func.__doc__` 自动提取 inputSchema 和 description
- OpenAPI `parameters`（query/path）→ 函数参数 + 类型注解
- OpenAPI `requestBody` → 展平到函数参数
- SDK 自动 JSON Schema 校验，无需自建 ParamValidator

| HTTP Method | Path | Tool Name |
|------------|------|-----------|
| POST | `/api/v1/predict/dehaze` | `predict_dehaze` |
| GET | `/api/v1/algorithms/{id}` | `get_algorithm_by_id` |
| PUT | `/api/v1/algorithms/{id}` | `update_algorithm` |
| GET | `/api/v1/algorithms` | `list_algorithms` |

**转换规则**：
- `{method}_{path_segments_joined}` 作为 tool name
- path 中的 `{placeholder}` 替换为 `by_xxx`（如 `{id}` → `by_id`）
- 避免下划线重叠和非法字符

### 5.2 命名规则与类型注解转换

| OpenAPI 来源 | MCP tool 字段 | 转换说明 |
|-------------|-------------|---------|
| `{method}_{path}` | `name` | 语义化命名（`predict_dehaze`），path `{placeholder}` → `by_xxx` |
| `summary` + `description` | `description` | 自然语言描述供 LLM 理解用途 |
| `parameters` + `requestBody` | `inputSchema` | SDK 从 Python 类型注解自动生成 JSON Schema |

**类型注解转换示例**：

```
OpenAPI 参数 → Python 类型注解（SDK 自动转 JSON Schema）：

parameters[{name: "algorithm", type: string}] → algorithm: str
requestBody.properties[{fileId: integer}]     → fileId: int
requestBody.properties[{strength: integer}]   → strength: int = 70  # 有 default
```

**描述来源**：配置文件覆盖 > OpenAPI summary + description > 自动生成。SDK 从 `tool_func.__doc__` 自动提取到 tool 的 `description` 字段。

## 6. Resource 生成规则

### 6.1 URI 模板

| API Path | Resource URI |
|---------|-------------|
| `GET /algorithms` | `algo://list` |
| `GET /algorithms/{id}` | `algo://{id}` |
| `GET /algorithms/{id}/versions` | `algo://{id}/versions` |

**转换规则**：
- 提取 path 中的固定段作为 URI 前缀（`algorithms` → `algo`）
- 使用 `://` 分隔资源类型和标识符
- 保留 `{placeholder}` 作为 URI 模板参数

### 6.2 Resource 内容提供

```
resources/read: uri = "algo://15"
    ↓
生成后端请求：GET /api/v1/algorithms/15
    ↓
后端返回 JSON
    ↓
转换为 MCP content:
  contents: [{
    uri: "algo://15",
    mimeType: "application/json",
    text: "{...}"
  }]
```

## 7. 变更通知

### 7.1 通知时机

| 触发条件 | 通知行为 |
|---------|---------|
| 定时同步发现 diff（新增/删除/变更） | 推送 `notifications/tools/list_changed` |
| 管理端手动刷新 | 推送 `notifications/tools/list_changed` |
| 手动刷新 diff 无变更 | 不推送 |

### 7.2 通知机制

```
ToolRegistry.applyDiff(diff) → diff 非空
    ↓
NotificationHandler.push("tools/list_changed")
    ↓
对每个已 initialize 连接的客户端，通过 SSE channel 推送：
  event: notifications/tools/list_changed
  data: {"jsonrpc":"2.0","method":"notifications/tools/list_changed","params":{}}
```

> 客户端收到后重新调用 `tools/list` 刷新本地 tool 缓存。

## 8. 命名空间分组

### 8.1 设计目标

系统 API 多达上百个，每个 tool 的 `name + description + inputSchema` 平均 ~500 tokens。全量注入 LLM 上下文会导致严重 token 浪费和响应延迟。参考 OpenAI Agents SDK `tool_namespace()` 和 Anthropic MCP 代码执行模式（文件树探索），自动将工具分组为命名空间。

### 8.2 分组策略

```
全部注册的 tool
    ↓
NamespaceBuilder.build(tools)
    ↓
聚合规则：同一 OpenAPI tag 的 tool 归入同一命名空间
  - tag "predict" → namespace "image_processing"
  - tag "evaluation" → namespace "evaluation"
  - tag "algorithm" → namespace "algorithm"
  ...
  - 无 tag 或 tag 不匹配已知分组 → namespace "other"
    ↓
每个命名空间生成摘要：
  - name: 简短标识（如 image_processing）
  - description: 命名空间能力的一句话概括（从 tag description 提取）
  - tool_count: 该分组下 tool 数量
```

### 8.3 摘要描述生成

| 策略 | 来源 | 示例 |
|------|------|------|
| OpenAPI tag description | 配置优先 | `mcp.namespaces.image_processing.description` |
| 自动生成 | 从 tool 描述聚合提取关键词 | "图像处理工具：去雾、增强、超分辨率等" |

### 8.4 分组变更

- 定时同步发现 API 变更后，NamespaceBuilder 重新计算分组
- 分组变化（新增/删除命名空间、或某命名空间的 tool 列表变化）同样触发 `notifications/tools/list_changed`
- AI 对话模块收到通知后重新调用 `tools/list`（无 expand）获取最新命名空间摘要

## 9. tools/search 实现

### 9.1 搜索流程

```
LLM 调用 tools/search（query="评估图像质量 指标 PSNR"）
    ↓
ToolSearchEngine.search(query, userId)
    ↓
Step 1: 获取当前用户可见的全部 tool 列表（含命名空间、name、description）
    ↓
Step 2: ES BM25 文本检索
  - 搜索字段：tool.name + tool.description + tool.namespace
  - 查询：query 关键字（分词后多字段匹配）
    ↓
Step 3: 同命名空间扩展
  - 匹配的 tool 所属命名空间内的其他 tool 一并返回（语义相关工具在同一命名空间）
    ↓
Step 4: 按 relevance score 排序，取 top N（默认 5，上限 10）
    ↓
Step 5: 按 detail 级别返回结果
  - name_only: [{name, namespace}]
  - summary: [{name, namespace, description}]
  - full: [{name, namespace, description, inputSchema}]
```

### 9.2 搜索依赖

- **无 LLM 依赖**：`tools/search` 是纯文本检索，不调 LLM——它是给 LLM 用的工具发现 API，本身不走 LLM
- **ES 依赖**：依赖 ES 做 BM25 全文检索。ES 不可用时降级为内存遍历 + 关键词匹配（Jaccard 相似度）

### 9.3 使用时机

AI 对话模块的 LLM 在以下场景应调用 `tools/search`：
- 命名空间摘要不能覆盖用户需求时（跨命名空间任务）
- 不确定某个工具归属哪个命名空间时
- 需要发现特定能力但不知道工具精确名称时
