# AI 对话模块需求规格（定时与兼容）

> 功能域定位：本功能域将两个体量较小但定位各异的能力合并管理——§2.10 定时调度（F-M08-009）将对话中的处理流程固化为定时任务，满足企业自动化流程需求；§2.12 第三方兼容 API（F-M08-010）对外提供 OpenAI/Anthropic 协议兼容接口，供第三方生态复用平台对话与计费能力。
>
> 本版在对齐既有实现的基础上，依据业界主流 AI Agent 调度系统（OpenClaw Cron、Hermes Agent、通用 Scheduler/Queue/Worker 架构）与 API 网关/中转站（OneAPI、NewAPI、TraceHub）的最佳实践，补齐两方面能力：**定时调度的执行可靠性**（幂等防重入、并发控制、失败熔断、执行观测，§2.10.5）与 **兼容 API 的接入治理**（API Key 全生命周期、模型白名单、限流、调用审计，§2.12.4），并将**自然语言创建定时任务**（§2.10.3）列为待确认的 UX 增强。新增需求是否一期落地见 §2.10.6 / §2.12.5 待确认事项。

## 2.10 定时调度 (F-M08-009)

### 2.10.1 功能描述

支持用户将对话中调度的处理流程固化为定时任务，按设定的时间规则自动触发对话执行，满足企业用户自动化流程需求（如每日定时去雾监控截图并分发）。

定时调度遵循业界通用认知——**Cron 只是触发方式，不是调度系统的全部**。生产级定时任务除"到点触发"外，还必须解决三件事：任务会不会重复执行（幂等防重入）、任务会不会互相挤压（并发控制）、任务反复失败怎么办（失败熔断）。本功能域以"无人值守的自动化流程"为目标，将这三项可靠性能力纳入设计（§2.10.5）。

### 2.10.2 定时任务管理

| 操作 | 说明 | 业务规则 |
|------|------|---------|
| 创建定时任务 | 用户在对话中确认流程后"保存为定时任务" | 需指定触发规则（Cron 表达式或常用频率）、输入来源（固定/动态拉取）、输出目标 |
| 任务列表 | 展示用户的定时任务，支持启停、编辑、删除 | 按下次触发时间排序，展示最近执行结果与下次触发预览 |
| 任务执行 | 到达触发时间自动以系统身份发起对话执行 | 复用多步推理能力，执行结果通过消息推送/回调通知用户；同一任务上一次执行未完成时，本次触发跳过（防任务重叠，见 §2.10.5） |
| 执行历史 | 记录每次执行的结果、消耗、耗时、失败原因 | 保留 30 天，支持回溯查看；展示最近一次执行摘要（成功/失败/跳过/熔断） |
| 手动触发 | 用户手动触发一次任务执行 | 用于验证任务配置或补跑遗漏执行；不改变原定时规则 |

### 2.10.3 交互规范

| 场景 | 交互行为 |
|------|---------|
| 创建引导 | 对话中完成一次处理流程后，界面提供"保存为定时任务"入口；创建时以表单引导设置触发规则、输入来源与输出目标 |
| 触发规则设置 | 提供常用频率快捷项（每天/每周/每月，含小时、分钟选择）与自定义 Cron 表达式两种方式；两种方式均实时展示 Cron 的人类可读解释与**下一次执行时间预览**，避免配置错误 |
| 执行通知 | 每次执行完成后通过站内消息通知用户执行结果；失败或配额不足时通知中说明原因；连续多次失败时通知升级（提示任务可能配置异常，见 §2.10.5） |
| 结果查看 | 任务列表可展开查看最近一次执行结果（成功/失败/跳过、消耗积分、耗时），并可跳转查看生成的对话记录 |
| 时区归属 | 任务按用户所在时区（Asia/Shanghai）计算触发时间，与配额重置时区一致；不随平台服务器时区漂移 |
| 自然语言创建（待确认项） | 用户可直接以自然语言描述触发规则（如"每天早上 9 点拉取监控截图并去雾分发"），由 LLM 解析为 Cron 表达式 + 执行动作，创建后展示解析结果供用户确认；解析失败时提示手动设置 |

### 2.10.4 业务规则

| 规则 | 说明 |
|------|------|
| 权限限制 | 定时调度仅 VIP2 及以上用户可用，普通用户不可创建 |
| 配额占用 | 定时任务执行消耗的积分计入用户配额，配额不足时跳过本次执行并通知用户 |
| 失败重试 | 任务执行失败时按失败类型区分处理：临时错误（网络/限流/超时）按指数退避重试 3 次；不可重试错误（参数/权限/配置问题）不重试直接记录（见 §2.10.5） |
| 任务上限 | 单用户定时任务数上限 20 个，防止资源滥用 |
| 输入来源 | 支持固定输入（用户预设图片集）与动态输入（通过 MCP 拉取监控截图/指定目录新文件） |
| 任务重叠 | 同一任务的两次触发不得并发执行，上一次执行未结束时本次触发跳过并记录 |
| 连续失败熔断 | 同一任务连续失败达阈值（如 5 次）时自动停用任务并通知用户，避免无效重试消耗成本 |

### 2.10.5 执行可靠性

> 新增需求（对齐 Scheduler/Queue/Worker 与 OpenClaw concurrency:forbid 等实践）。现有实现仅具备"到点触发 + 指数退避重试"，本小节补齐生产级调度缺的可靠性能力。

| 能力 | 说明 |
|------|------|
| 幂等防重入 | 每次触发生成唯一执行批次（任务 ID + 触发窗口），数据库唯一约束防重：服务重启、多实例并发扫描、时钟漂移均不会导致同一窗口任务重复执行；不依赖内存记录"上次执行时间" |
| 并发控制 | 单任务串行执行（上一次未完成则本次跳过，防任务重叠）；平台级全局并发上限，防止任务风暴打爆推理服务 |
| 失败分级重试 | 可重试错误（网络瞬断、429 限流、5xx、超时）→ 指数退避重试 3 次；不可重试错误（权限、参数、配置错误）→ 不重试，直接记录失败原因并通知 |
| 连续失败熔断 | 同一任务连续失败 ≥ 5 次自动停用（类似调度级熔断），通知用户检查配置；用户修复后可手动重新启用 |
| 执行观测 | 每次触发、跳过、执行、失败均记录：触发窗口、跳过原因（禁用/配额/并发/幂等）、执行耗时、失败原因；支持统计任务延迟（计划触发 vs 实际执行）与失败分布，便于排查"为什么没跑/重复跑/成本异常" |
| 执行历史保留 | 执行历史保留 30 天（与现有规则一致），熔断与跳过记录一并归档 |

### 2.10.6 待确认事项

| 事项 | 说明 |
|------|------|
| 幂等防重入（§2.10.5） | 新增需求。是否一期落地取决于调度引擎是否多实例部署；若为单实例内存调度可暂缓，但需在任务执行前写运行态标记防重叠 |
| 连续失败熔断（§2.10.5） | 新增需求。建议一期落地（成本保护），熔断阈值默认 5 次可配置 |
| 自然语言创建（§2.10.3） | UX 增强项。涉及 LLM 解析 Cron 的稳定性，需先建立校验兜底（解析失败回退手动设置），是否一期落地待定 |
| 手动触发（§2.10.2） | 轻量增强项，建议一期提供，便于用户验证任务配置 |

## 2.12 第三方兼容 API (F-M08-010)

### 2.12.1 功能描述

提供与 OpenAI Chat Completions / Anthropic Messages 协议兼容的 API，供第三方外部接入。第三方应用通过标准协议复用平台的 LLM 对话能力与积分计费体系，无需对接内部自定义 API。本系统前端不依赖兼容 API，统一走内部 API。兼容 API 的接口契约见 [API接口.md](./API接口.md)。

兼容 API 的本质是**协议适配层**（Adapter）：对外对齐 OpenAI/Claude 官方协议（请求/响应/流式格式、错误码、模型列表），对内复用内部会话、消息、推理与计费链路。第三方接入的核心诉求是"最小改动 + 行为一致"，因此兼容层必须做到协议细节对齐（如流式 `[DONE]`、usage 统计、tool_calls 格式）与**可治理**（接入方有独立凭证、配额、可审计），详见 §2.12.3 / §2.12.4。

### 2.12.2 使用场景（外部接入）

| 场景 | 说明 | 接入方式 |
|------|------|---------|
| OpenAI SDK 生态接入 | 使用 OpenAI SDK 的应用/脚本直接调用平台对话能力 | OpenAI 兼容端点 |
| Claude SDK 生态接入 | 使用 Anthropic SDK 的应用/脚本直接调用平台对话能力 | Claude 兼容端点 |
| 第三方对话客户端 | Chatbox、Open WebUI 等标准客户端配置 Base URL + API Key 接入 | OpenAI 兼容端点 |
| 企业自有系统集成 | 内部工具/自动化流程以标准协议调用对话与图像处理能力 | OpenAI / Claude 兼容端点 |

### 2.12.3 业务规则

| 规则 | 说明 |
|------|------|
| 认证 | 使用平台签发的 API Key 认证（OpenAI 端点 `Authorization: Bearer dhak_xxx`，Claude 端点 `x-api-key`），密钥由用户在个人设置中创建/吊销；创建时明文仅展示一次，库中仅存哈希 |
| 会话管理 | 请求可传会话标识（自定义扩展字段）复用已有会话，不传则自动创建新会话；会话列表/删除/归档等管理操作通过内部 API 完成 |
| 能力边界 | 兼容协议不暴露推理过程（thought 事件）；工具调用按各协议原生格式透传（OpenAI `tool_calls` / Claude 原生格式） |
| 计费 | 与内部 API 共用同一积分计费与配额体系，按实际使用模型计量 |
| 模型选择 | 请求中可指定模型，须为启用状态且满足能力要求；未指定时使用会话默认模型 |
| 模型可见性 | `/v1/models` 返回该用户/Key 有权调用的模型列表，与内部 API 的 VIP 过滤一致；请求无权模型返回 403（权限不足），余额/配额不足返回 402 语义错误，限流返回 429——错误语义与官方协议对齐，便于 SDK 正确处理 |
| 协议细节 | 流式响应以 `[DONE]` 结束；usage 字段按实际 Token 计量返回（含缓存命中 Token）；`stream`、`temperature`、`max_tokens`、`tool_calls` 等标准参数按官方语义透传 |

### 2.12.4 接入治理

> 新增需求（对齐 API 网关/中转站实践）。现有实现已具备"API Key 创建/吊销 + 双轨认证 + 共用计费"，本小节补齐第三方接入的可治理能力——凭证管理、模型白名单、限流、审计。

| 治理项 | 说明 |
|--------|------|
| Key 生命周期 | 多 Key 支持（按项目/环境隔离，可命名）；Key 状态（启用/禁用）、有效期、吊销；Key 明文仅创建时展示一次，哈希存储 + 前缀展示（`dhak_xxx...`） |
| Key 级配额 | 每个 Key 可设置日/月调用额度与频率上限（RPM），超限返回 429 并提示；配额与用户积分配额双轨控制（Key 配额防止单个接入方滥用） |
| 模型白名单 | Key 可绑定可用模型范围（默认继承用户可见模型）；`/v1/models` 按 Key 白名单动态返回，请求白名单外模型返回 403 |
| 调用审计 | 记录每次调用：Key、模型、输入/输出 Token、积分消耗、状态码、耗时、来源 IP；敏感字段（API Key）脱敏后记录；调用日志可按 Key/模型/时间筛选，支撑对账与异常排查 |
| 来源管控（可选） | Key 可绑定 IP 白名单，仅允许指定来源调用；超出范围的来源请求拒绝 |

### 2.12.5 数据存储决策

> 明确"后端实现是否需要新增表"：定时调度与兼容 API 的接入治理在既有表基础上演进，**仅调用审计新增一张表**。

| 功能域 | 数据落点 | 是否新增表 |
|--------|---------|-----------|
| 定时调度（§2.10） | `sys_ai_schedule`（配置）+ `sys_ai_schedule_run`（执行历史）已落地，幂等键/熔断计数/执行观测均基于此实现 | 否 |
| 兼容 API-Key 级配额 | 扩展 `sys_api_key` 增加 `daily_quota`/`monthly_quota`/`rpm_limit` 字段，计数走 Redis | 否 |
| 兼容 API-模型白名单 | 扩展 `sys_api_key` 增加白名单 JSON 字段 | 否 |
| 兼容 API-调用审计 | 新增 MongoDB 集合 `ai_api_call_log`（Key、模型、Token、积分、状态码、耗时、来源 IP、request_id），与 `login_log`/`audit_log` 同属审计日志库 | **是（MongoDB 集合，非 MySQL 表）** |

**定时任务两张表（`sys_ai_schedule`/`sys_ai_schedule_run`）不冗余的论证**：

xxl-job 自带 `xxl_job_info`（任务配置）与 `xxl_job_log`（调度日志），但它们是**通用调度平台表**（独立 `xxl_job` 库，不感知业务），与业务表职责互补而非重复：

| 业务需求 | 业务表承载 | xxl-job 表能否承载 |
|---------|-----------|------------------|
| 任务归属用户 | `sys_ai_schedule.user_id` | ❌ 无用户概念，全局运维视角 |
| 业务输入/输出 | `sys_ai_schedule.input`/`output`（JSON：固定图片集/动态 MCP 拉取） | ❌ `executor_param` 仅 `varchar(512)` 字符串 |
| 用户启停 | `sys_ai_schedule.enabled`（用户前端启停） | ❌ `trigger_status` 为运维控制台启停 |
| 熔断状态 | `sys_ai_schedule.status`/`circuit_streak`（连续失败≥5 自动停用） | ❌ 无业务级成本保护 |
| 按用户时区 | `sys_ai_schedule.timezone` | ❌ cron 为全局时区 |
| 业务跳过原因 | `sys_ai_schedule_run.skip_reason`（overlap/quota/circuit/idempotent） | ❌ 仅 `trigger_code`/`handle_code` 数字码 |
| 积分消耗 | `sys_ai_schedule_run.credits` | ❌ 无计费字段 |
| 关联对话 | `sys_ai_schedule_run.conversation_id` | ❌ 无 |
| **幂等防重入** | `sys_ai_schedule_run` 的 `(schedule_id, window_start)` 唯一索引 | ❌ 无业务幂等键 |

> 幂等键必须落在业务表：XXL-Job 多实例重复执行的三大诱因（心跳快照、路由策略、时间轮并发）最终防线是**业务幂等键**（业界共识"调度层只负责触发，业务层永远可幂等"）。xxl-job 日志表无法提供该能力。

**调用审计独立存储的理由**（对齐 OneAPI/NewAPI 中转站实践——OneAPI 以独立 `logs` 表记录每次请求的 user_id/token_name/model_name/quota/tokens/elapsed_time/client_ip/request_id）：

1. 审计需记录**所有调用**（含 401/403/429 被拒绝、限流的调用），而 `sys_ai_billing` 仅记录成功计费的调用——被拒绝的调用无计费记录但必须可审计
2. 审计字段（`key_id`、`ip`、`status_code`、`duration_ms`、`request_id`）与计费表字段不同
3. 职责分离：`sys_ai_billing` 为财务记录（只追加不逻辑删除），审计为运营/对账数据，保留策略独立
4. 审计按 Key/模型/时间筛选对账，独立存储索引更清晰

**为何用 MongoDB 而非 MySQL**：调用审计是"只追加、无 JOIN、schema 可演化"的日志数据，符合项目存储分层原则（"是否需要和业务表做 JOIN 查询？需要 → MySQL；不需要 → MongoDB"），与既有 `login_log`/`audit_log` 审计日志架构一致；TTL 索引原生支持 30 天自动过期，无需定时清理任务；三端 mongo 客户端/异步写入/监控已就绪，复用成本低。**注意：`sys_ai_credit_log`（积分流水）是财务数据，需与 `sys_ai_billing` JOIN、与余额扣减同事务、按用户/月份聚合生成账单，必须保留 MySQL，不随审计迁移。**

### 2.12.6 待确认事项

| 事项 | 说明 |
|------|------|
| 兼容 API 的权限范围 | 第三方经兼容 API 发起的对话能力边界与内部 API 保持一致，不额外开放管理类能力 |
| 接入治理一期范围（§2.12.4） | Key 级配额与调用审计建议一期落地（防滥用 + 可对账）；模型白名单（Key 绑定模型范围）与 IP 白名单为增强项，视接入方规模评估 |
| 错误码对齐 | 429/403/402 语义对齐官方协议需后端落地，一期先保证 429（限流）与 403（模型不可用）正确返回 |
