# AI 对话模块 - 后端实现设计（消息反馈）

## 1. 文档概述

本文档描述 F-M08-008 消息反馈的后端实现，包括反馈数据模型、反馈提交流程、反馈查询、反馈撤销、反馈修改、反馈数据统计、反馈驱动闭环。

### 1.1 设计思想

#### 设计动机

在模型推理链路中，平台内部有大量"主观"的质量判断（如自评、指标），但缺乏真正来自用户的**客观服务质量信号**。消息反馈正是补上这一环：用户对某条 assistant 消息的点赞/点踩，是平台唯一能直接获取的、反映真实体验的信号。它不依赖任何 LLM 自我评估，也不受中间指标波动影响。

反馈的价值不止于"统计好看"，而是驱动系统的持续改进：把用户偏好写入记忆、把高频负反馈转化为提示词优化、把工具负反馈沉淀为选择策略调整，从而让整个 AI 对话系统在真实使用中不断收敛质量。

#### 核心设计原则

| 原则 | 说明 |
|------|------|
| 信号客观 | 反馈来自用户真实使用，是独立于 LLM 自评的质量信号，作为记忆提取与提示词优化的驱动源（详见 §2.7） |
| 单条唯一 | 同一用户对同一消息仅一条反馈（唯一索引 + upsert），点赞→取消→再点赞不产生脏数据，保证统计准确（详见 §2.2） |
| 反馈时效 | 仅可对 30 天内的 assistant 消息反馈，保证信号与当前系统状态相关，避免陈旧反馈误导优化 |
| 闭环驱动 | 点踩不是终点而是起点：提取偏好入记忆、高频负反馈触发提示词优化、工具负反馈调整选择策略（详见 §2.7） |

#### 关键架构取舍

| 取舍点 | 方案对比 | 选择与理由 |
|--------|---------|-----------|
| 反馈存储 | 每条反馈独立记录 vs upsert 单条 | 选 upsert。唯一索引（用户+消息）保证一条反馈，撤销后再次反馈走复活，避免"点赞→取消→再点赞"产生多条脏数据（详见 §2.2） |
| 反馈作用范围 | 仅统计展示 vs 驱动系统改进 | 选后者。反馈不仅用于质量统计，还异步驱动记忆提取、提示词优化与工具选择策略调整，形成改进闭环（详见 §2.7） |

#### 总体规划

消息反馈是 AI 对话"地基层"上的质量信号层：

```
模型推理（消费模型能力）→ 消息反馈（质量信号）→ 记忆/提示词优化 → 闭环
```

反馈闭环是 Reflexion 范式的被动触发版——不等待推理过程中的自我评估，而是从用户反馈中学习改进。

## 2. 消息反馈管理 (F-M08-008)

### 2.1 数据模型

消息反馈表结构详见 [数据库设计 §4.7](../../../../02-系统架构/03-数据库设计.md)：

| 实体 | 职责 | 服务层关键用途 |
|------|------|-------------|
| `sys_ai_message_feedback` | 消息反馈（点赞/点踩 + 预设标签 + 改进建议） | 反馈 upsert、唯一性校验、质量统计、闭环处理状态 |

唯一索引保证同一用户对同一消息只有一条反馈。逻辑删除类别①：撤销后再次反馈走 upsert 复活，upsert 时回填原行 ID。

**字段演进（对齐需求规格 §2.9.5 反馈数据完整性）**：在既有 `message_id/user_id/rating/tags/comment` 基础上新增以下字段，支撑按模型/会话维度统计与闭环处理，**不新增表**：

| 新增字段 | 类型 | 说明 |
|---------|------|------|
| `conversation_id` | bigint | 消息所属会话 ID，冗余存储避免统计时多表 JOIN |
| `model` | varchar(64) | 生成该消息的模型标识，按模型统计满意度与归因 |
| `source` | varchar(16) | 反馈来源（`internal`：内部 API；`compat`：第三方兼容 API） |
| `processed` | tinyint | 闭环处理状态（0：待处理；1：已处理），点踩反馈由 XXL-Job 定时扫描处理 |
| `process_time` | datetime | 闭环处理完成时间，支撑闭环时效统计 |

> 反馈上下文快照（question/answer/citations/retrieval）不落反馈表——消息正文与推理步骤已存于 `sys_ai_message`/`sys_ai_agent_thought`，通过 `message_id` 关联即可回溯，避免冗余大字段。

**标签体系**（对齐需求规格 §2.9.3，服务层校验白名单）：

| 反馈类型 | 标签（key） | 是否必选 |
|---------|------------|---------|
| 点赞（rating=1） | `accurate`/`detailed`/`concise`/`creative` | 可选，可多选 |
| 点踩（rating=-1） | `incorrect`/`irrelevant`/`incomplete`/`too_long`/`bad_citation`/`harmful` | 必选其一 |

> 点踩标签贴近问题归因（错误/答非所问/不完整/太长/引用错误/有害），每类标签对应明确的优化方向，支撑 §2.7 闭环的针对性处理。

### 2.2 反馈提交流程

```
用户对 assistant 消息提交反馈
    ↓
校验：
  - 消息存在且属于当前用户的会话
  - 消息 role = assistant（仅助手消息可反馈）
  - 消息发送时间在 30 天内（反馈时效）
    ↓
upsert 反馈记录（存在则更新，不存在则插入；撤销后再次反馈走 upsert 复活）：
  - 写入 message_id, user_id, conversation_id, model, source, rating, tags, comment
  - 唯一索引命中时更新 rating, tags, comment 并复活（deleted=0）
    ↓
校验标签（白名单，见 §2.1）：
  - rating=1（点赞）：tags 可选，仅允许 accurate/detailed/concise/creative
  - rating=-1（点踩）：tags 必选其一，仅允许 incorrect/irrelevant/incomplete/too_long/bad_citation/harmful
  - 非法标签 → 拒绝，返回"不支持的标签类型"
    ↓
如果 rating = -1（点踩）：
  - comment 可选（改进建议，不强制填写，避免降低反馈率）
  - 标记 processed=0（待闭环处理，见 §2.7）
    ↓
返回反馈记录 ID
```

### 2.3 反馈查询

```
查询消息反馈状态
    ↓
查询当前用户对指定消息的未删除反馈记录
    ↓
返回反馈状态（rating, comment）
  - 无记录 → 未反馈
  - 有记录 → 返回 rating 和 comment
```

### 2.4 反馈撤销

```
用户撤销反馈
    ↓
标记当前用户对指定消息的反馈记录为逻辑删除
    ↓
撤销后可重新反馈（走 upsert 复活）
```

### 2.5 反馈修改

用户修改反馈类型（点赞改点踩或反之）：

```
用户提交新的反馈（rating 与现有不同）
    ↓
走 upsert 更新（唯一索引命中时更新 rating, comment 并复活）
    ↓
原记录被更新，不插入新记录
```

### 2.6 反馈数据统计

反馈数据用于质量分析，不直接展示给用户：

| 统计维度 | 说明 |
|---------|------|
| 消息点赞率 | 某条消息的点赞数 / 总反馈数 |
| 模型满意度 | 按模型维度统计点赞率，评估模型效果 |
| 标签分布 | 统计各预设标签出现频率（如"too_long"占比高 → 提示词需精简输出；"bad_citation"占比高 → 引用链路需校验；"incomplete"占比高 → 提示词补充约束） |
| 工具调用效果 | 关联推理步骤，统计工具调用后的消息反馈 |
| 负反馈分析 | 点踩的 tags + comment 内容分析，识别常见问题 |
| 反馈覆盖率 | 有反馈的会话 / 总会话数，衡量反馈入口触达（对齐需求规格 §2.9.7 衡量口径） |
| 反馈采纳率 | 被采纳的反馈 / 总反馈数，衡量反馈实际价值（对齐需求规格 §2.9.7 衡量口径） |

### 2.7 反馈驱动闭环

用户反馈不仅用于统计，还驱动系统改进后续推理质量。闭环处理复用项目 XXL-Job 基础设施（`app/infrastructure/job/`），由定时任务批量扫描未处理的点踩反馈（`processed=0`），**不新增表、不依赖 MQ**：

```
用户提交点踩反馈（rating=-1, tags=["too_long"], comment="回复太冗长"）
    ↓
写入反馈记录，processed=0（待处理）
    ↓
XXL-Job 定时任务 processFeedbackLoop（如每 5 分钟）：
  扫描 processed=0 且未删除的点踩反馈（分批，每批 N 条）
    ↓
逐条处理：
1. 记忆提取：
   - 从点踩内容和 tags 提取用户偏好
   - 如 tags=["too_long"] → 语义记忆："用户偏好简洁回复"
   - 写入 sys_ai_memory，importance 加权（反馈来源 +10）
    ↓
2. 提示词优化建议（高频率反馈，建议 + 人工审批）：
   - 仅处理**非安全类**负反馈标签累计超过阈值（如"too_long"出现 10 次）
   - 异步生成优化建议（LLM 产出差异说明，如"增加'回复保持简洁'指令"），**不直接修改**
   - 平台管理员审批（确认应用 / 编辑后应用 / 拒绝，编辑支持部分采纳）后应用至提示词模板（新会话生效，经评测门禁，见 [上下文管理/后端实现.md §3.3.5](../上下文管理/后端实现.md#335-提示词模板库可运维)）
   - **安全红线**：`harmful`（有害/不安全）等安全类反馈**不进入自动优化**，直接触发安全告警并人工介入——防止恶意点踩诱导削弱安全护栏
    ↓
3. 工具选择策略调整：
   - 当某工具调用后频繁收到 negative 反馈（如"incorrect"）
   - 降低该工具在类似场景下的选择优先级
   - 或在工具描述中增加使用限制说明
    ↓
处理完成标记 processed=1、process_time=当前时间
（处理失败不标记，下次扫描自动重试）
```

**闭环处理可靠性**：

| 能力 | 实现要点 |
|------|---------|
| 幂等防重 | 以 `processed` 状态位标记，处理成功才置 1；服务重启/多实例并发扫描不会重复处理（`UPDATE ... WHERE processed=0` 原子抢占） |
| 失败重试 | 处理失败不置 processed=1，下次扫描自动重试；连续失败记录日志告警 |
| 批量处理 | 分批扫描（每批 N 条），避免一次处理过多触发 LLM 调用风暴 |
| 闭环时效 | `process_time` 记录处理完成时间，支撑闭环时效统计（需求规格 §2.9.7） |

**闭环扩展环节**（对齐需求规格 §2.9.7）：

| 环节 | 实现要点 |
|------|---------|
| 评测集回流 | 高价值差评（高频、关键业务、可确认根因）脱敏后转成回归用例，复用评测样本接口写入回归集（`sys_ai_agent_eval_sample`），防止问题复发 |
| 改进可见性 | 反馈驱动的改进（如提示词精简）在后续对话中自然生效，用户可感知"回复更简洁"，形成"反馈→改进→更多反馈"的良性循环 |
| 闭环时效分级 | 紧急错误（`harmful`/`incorrect`）24 小时内处理，普通问题 3 天内处理，避免反馈闭环过慢 |

**隐性反馈信号**（对齐需求规格 §2.9.6，作为显性反馈的补充质量维度）：

| 信号 | 采集方式 | 含义 |
|------|---------|------|
| 复制回答 | 前端埋点上报 | 用户采纳回答，正向信号 |
| 继续追问 | 会话内下一条 user 消息 | 用户基于回答继续深入，正向信号 |
| 重新生成 | 复用 F-M08-001 重新生成接口埋点 | 用户对回答不满意，负向信号 |
| 转人工/离开 | 会话结束/长时间无操作 | 用户放弃 AI 回答，负向信号 |

> 隐性信号不落反馈表、不展示给用户，仅作为质量分析的补充维度，与显性反馈交叉验证。

**隐私脱敏**（对齐需求规格 §2.9.4）：

- 反馈中的敏感信息（手机号、身份证、银行卡等）在存储与分析前脱敏
- 评测集回流前对差评样本脱敏，避免敏感信息进入评测集
