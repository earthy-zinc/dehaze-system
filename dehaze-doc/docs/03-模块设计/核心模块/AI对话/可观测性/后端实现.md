实现补充说明（与设计条文的差异点）：
- **调用粒度**：一条 `sys_ai_llm_call` 对应一次 `stream_chat` 调用（记录最终结果）；Key/供应商重试的多次物理尝试聚合为一条 span，经 `attempts` 还原每次物理尝试（逐 Key 重试/路由降级/熔断跳过，见 §2.3 采集要点），重试细节不再只走供应商健康与日志链路。
- **上下文快照构成项**：仅记录当前实现实际注入的项（system/summary/history/memory + summarize 事件）；工具定义与工具结果在 LLM 调用级 `input_snapshot`/`tool_call` 逐轮采集，用户信息记 `user_id`。
- **中断与 resume**：quota/confirm/async_wait 中断本轮以 status=3 + error_type=中断类型 落库；resume 由新请求的 trace_id 记独立过程链，消息详情取最新一条（`get_latest_by_message_id`）。
- **旁路硬约束**：任何采集失败仅 warning 日志，不影响对话/计费/推理主链路。

### 1.1 技术选型

#### 设计动机

对话式 AI 的故障形态与传统接口不同：一次"答错了"可能源于上下文缺失、工具参数错误、模型理解偏差或提示词问题，且错误会在多步推理中层层放大。排查依赖完整的过程记录——AI 当时看到了什么、调用了什么、每次模型调用输入输出如何、缓存命中多少、走了几步、花了多少。可观测性要做的不是"再记一份日志"，而是把散落在消息表、推理步骤表、计费记录里的执行过程**按会话串成一条可检索、可回放、可审计的过程链**，并在**每次 LLM 调用**的粒度上记录输入/输出/token/耗时。

#### 关键架构取舍

| 取舍点 | 方案对比 | 选择与理由 |
|--------|---------|-----------|
| 可观测平台 | 自建（复用现有 trace_id 日志体系 + 结构化表 + Prometheus/Grafana）vs 引入 Langfuse/Arize Phoenix | 选自建。平台已具备完整观测基建（`07-日志架构设计` 的 trace_id 全链路、Prometheus→Grafana→Alertmanager、ES 检索），引入外部平台需双写同步、三端适配与数据出境成本；本模块诉求是"对话过程记录 + 审计"，与通用 LLM 平台核心能力重叠且定制绑定会话/计费/权限，自建更内聚 |
| 过程记录存储 | MySQL 结构化表（`sys_ai_trace` + `sys_ai_llm_call` + 复用 message/thought）vs 写入 ES | 选 MySQL。过程记录与消息/会话同库，事务一致、按会话/消息索引查询足够；保留周期到期归档至日志链路（ES）。ES 仅承载现有日志采集，不承担过程记录检索 |
| 指标采集 | 扩展三端 `/metrics`（Prometheus）vs 自建计数器服务 | 选 Prometheus 扩展。三端 `/metrics` + Grafana 面板 + Alertmanager 告警链路已就绪（见 `06-部署架构 §7.1`），新增 AI 指标与告警规则零新组件 |
| 上下文快照 | 生成时快照（落 JSON）vs 运行时重算 | 选生成时快照。推理时的上下文构成不可复现（记忆/检索可能已变化），快照保证可审计、可回放；重算既贵又不可信 |
| 观测粒度 | 每次 LLM 调用独立记录 + 消息级汇总 vs 仅消息级汇总 | 选双粒度。多步推理中错误在每轮模型调用间传播，消息级汇总无法回答"哪一轮调用输入/缓存/耗时异常"；LLM 调用级记录支撑逐轮归因（对齐业界 GenAI Trace 的 span 模型） |
| 观测时机 | 全量记录 vs 采样 | 全量记录。会话量级（相对系统级日志）可控，且审计要求全量留痕；仅告警指标的实时聚合走 Prometheus |

#### 总体规划

可观测性分层复用现有数据，不重复落盘已有信息：

```
现有数据（单一信息源）
├── sys_ai_message        # 消息正文/角色/状态（输出正文）
├── sys_ai_agent_thought  # 推理步骤（thought/tool/observation/耗时/状态）
├── sys_ai_artifact       # 中间产物
├── sys_ai_billing        # Token/积分消耗
└── 日志链路（trace_id）  # 异常详情/堆栈
新增（本功能域）
├── sys_ai_trace          # 消息级过程链汇总（上下文快照 + 状态 + 消耗汇总 + 首 Token）
└── sys_ai_llm_call       # 每次 LLM 调用明细（输入/输出/token/缓存命中/耗时）
指标/告警（Prometheus + Grafana + Alertmanager）
```

### 1.2 设计思想

| 原则 | 说明 |
|------|------|
| 复用优先 | 推理步骤、消息、计费均为既有数据，本功能域只补充"上下文快照 + 过程链汇总 + LLM 调用明细"，不复制正文明细 |
| 调用级留痕 | 每次 LLM 调用独立记录（trace → 调用 → 步骤），逐轮可归因：输入构成、输出、token 缓存命中、耗时 |
| 生成时快照 | 上下文构成在生成时不可变落盘，保证"AI 当时看到什么"可审计可回放 |
| 旁路采集 | 过程记录与指标采集不阻塞对话主流程，失败不影响会话 |
| 权限收敛 | 过程记录查询按角色收敛（用户看自己、管理员看全量、审计导出需权限） |

## 2. 可观测性实现 (F-M08-013)

### 2.1 数据模型

表结构详见 [数据库设计 §4.7](../../../../02-系统架构/03-数据库设计.md)，新增 `sys_ai_trace` 与 `sys_ai_llm_call`（DDL 见 `config/sql/schema/`）。

#### 2.1.1 过程链汇总表 `sys_ai_trace`

一次助手回复一条记录（成功/失败/中断/超时均写），承载消息级汇总：

| 字段 | 类型 | 说明 |
|------|------|------|
| `trace_id` | varchar(64) | 过程链 ID（复用日志链路 trace_id，前后端可串联） |
| `conversation_id` | bigint | 所属会话 |
| `message_id` | bigint | 关联的助手回复消息（summary/memory_extraction 旁路过程链为 null；suggestion/step_summary 旁路关联触发消息，见 §2.3.1） |
| `trace_type` | varchar(32) | 过程链类型：`conversation` 主对话（默认）/`summary` 会话摘要压缩/`memory_extraction` 记忆提取/`suggestion` 类似问题推荐/`step_summary` 步骤摘要；旁路调用独立过程链标注（见 §2.3.1） |
| `agent_code` | varchar(64) | 执行智能体（含版本快照信息） |
| `model` | varchar(64) | 实际使用模型 |
| `status` | tinyint | 1成功/2失败/3中断/4超时 |
| `error_type` | varchar(32) | 失败类型（工具失败/模型异常/超时/配额拒绝） |
| `error_detail` | JSON | 异常详情 `{message, stack}`（失败/中断时填充；message 截断 500 字符、stack 截断 4000 字符） |
| `duration_ms` | int | 整条回复总耗时 |
| `first_token_ms` | int | 首 Token 延迟（首个输出 token 到达耗时） |
| `llm_call_count` | int | 本次回复的 LLM 调用次数 |
| `total_tokens` / `prompt_tokens` / `completion_tokens` / `cached_tokens` | int | 消耗汇总（含缓存命中 token，与计费口径一致） |
| `step_count` | int | 推理步数（防循环观测） |
| `context_snapshot` | JSON | 上下文构成快照（见 §2.2） |
| `create_time` | datetime | 记录时间 |

#### 2.1.2 每次 LLM 调用明细表 `sys_ai_llm_call`

多步推理中每次模型调用一条记录（span 级），承载"每次调用的输入/输出/token/缓存命中/耗时"，经 `seq` 串联成调用链路：

| 字段 | 类型 | 说明 |
|------|------|------|
| `trace_id` | varchar(64) | 关联过程链 |
| `seq` | int | 调用序号（1 起递增，贯穿推理步骤链路） |
| `step_position` | int | 关联推理步骤序号（`sys_ai_agent_thought.position`，可为空：模型调用不总落在 thought 步骤边界） |
| `model` | varchar(64) | 本次调用模型（多步推理中可能切换模型） |
| `status` | tinyint | 1成功/2失败/3超时 |
| `error_type` | varchar(32) | 失败类型 |
| `attempts` | JSON | 物理调用尝试明细 `[{provider_id, key_id, model, status, error_code, latency_ms}]`（status 1成功/2失败/3跳过-熔断）；一条 llm_call 对应一次 `stream_chat`（候选路由序列），`attempts` 还原内部逐 Key 重试/路由降级/熔断跳过全过程（此前仅 Redis 健康数据与日志可见） |
| `duration_ms` | int | 本次调用总耗时 |
| `first_token_ms` | int | 本次调用首 Token 延迟 |
| `prompt_tokens` / `completion_tokens` / `cached_tokens` | int | 本次调用消耗（含缓存命中） |
| `tool_call` | JSON | 是否发起工具调用：`{has_tool_call, tool_name, args_summary}` |
| `input_snapshot` | JSON | 本次调用输入构成（见 §2.3） |
| `output_snapshot` | JSON | 本次调用输出摘要（文本摘要截断 + tool_calls 参数，见 §2.3） |
| `create_time` | datetime | 记录时间 |

|----|---------|

### 2.2 上下文快照采集（输入侧）

推理开始时组装上下文，生成时快照到 `sys_ai_trace.context_snapshot`。构成项覆盖"AI 当时看到什么"的全部输入：

| 构成项 | 说明 | 快照字段 |
|--------|------|---------|
| 系统提示词 | Agent/会话系统提示 | `{type, name, content, tokens}` |
| 用户信息 | 注入的用户上下文（user_id、会员等级、语言/偏好等） | `{type, user_id, level, tokens}` |
| 会话摘要 | 历史超长被摘要后注入的摘要原文 | `{type, tokens, source: 'summarized', content}` |
| 对话历史 | 注入的历史消息窗口，**按角色统计**（user/assistant/tool） | `{type, counts: {user, assistant, tool}, tokens, source: 'raw'\|'summarized'}` |
| 长期记忆 | 检索注入的记忆条数与逐条原文 | `{type, count, tokens, items: [{memory_id, memory_type, source, content}]}` |
| 知识库检索 | RAG 命中片段数 | `{type, count, tokens}` |
| 工具定义 | 命名空间预筛选后的工具定义 | `{type, tool_count, tokens}` |
| 工具结果 | 上一步工具调用的返回结果注入 | `{type, tool_results, tokens}` |

快照同时记录**压缩事件**：历史过长被摘要/裁剪时标记 `{event: 'summarize'\|'truncate', before_tokens, after_tokens}`，供"AI 忘了前文"类问题的归因。

正文类构成项快照存原文而非仅 token 数，保证"AI 当时看到什么"可审计：system 存系统提示正文（限长 `SYSTEM_PROMPT_MAX_CHARS` = 5000 字符）、summary 存会话摘要原文（同限长），memory 在 `items` 中逐条存注入记忆原文（每条限长 `MEMORY_CONTENT_MAX_CHARS` = 1000 字符），超出均截断。

**推理期事件扩展**：`context_events` 除压缩/截断事件外，同步记录推理过程中的关键事件——`guardrail`（护栏命中，`{event, rule, detail}`，rule 取 `prompt_injection`/`sensitive_topic`/`unauthorized_access`/`pii_mask`）、`plan`（Plan-and-Execute 计划快照，`{event, phase, plan_summary}`）、`resume`（中断恢复，`{event, interrupt_type, decision, from_trace_id}`）。决策内容（confirm 的 confirmed/algorithmId、plan_approve 的 plan_edit）随事件留痕，支撑"AI 为何被拦/绕行"的归因审计。

### 2.3 LLM 调用明细采集

每次模型调用（`llm_client` 发起）记录一条 `sys_ai_llm_call`，逐轮采集输入/输出/token/耗时：

```
每次 LLM 调用（llm_client 包装层，对调用方无侵入）
  ├─ 输入：本轮组装完成的 prompt 构成（input_snapshot）
  │    system 段正文 system_content（限长）/ system 段 token
  │    messages 完整消息原文 items（role+content，逐条限长）/ 消息按角色计数
  │    tools 工具定义清单（name+description，description 限长）/ 工具数 tool_count / 用户信息 user_id
  ├─ 输出：文本输出摘要 + tool_calls 参数（output_snapshot，超长截断）
  ├─ 消耗：usage（input/output/**cached** tokens，LlmClient 已返回）
  ├─ 耗时：first_token_ms（首个 delta 到达）+ duration_ms（完整返回）
  ├─ 状态：成功/失败/超时（error_type）
  └─ 链路：seq 递增；关联推理步骤 step_position
```

**采集要点**：

| 要点 | 说明 |
|------|------|
| 无侵入 | 在 `LlmClient` 统一包装层采集，调用方零改动（复用架构公共层 LlmClient，见 [后端实现-架构与公共.md](../后端实现-架构与公共.md) §4.1.1） |
| 缓存命中 | `cached_tokens` 取流式结束 usage 的 cached tokens；未提供缓存统计的模型置 0 |
| 输出脱敏 | `output_snapshot` 仅存摘要（文本截断 N 字符）与 tool_calls 参数，不存完整输出正文 |
| 输入原文限长 | `input_snapshot.messages.items` 逐条存本轮实际发送消息原文（每条限长 `MESSAGE_CONTENT_MAX_CHARS` = 2000 字符）、`tools` 存工具定义清单（`description` 限长 `TOOL_DESC_MAX_CHARS` = 500 字符），截断防重复大字段撑爆观测表 |
| 多模型 | 每次调用记录实际 `model`，多步推理中模型切换可逐轮归因 |
| 物理尝试明细 | `attempts` 逐次记录候选路由内的物理调用尝试：成功/失败/无 Key 处由 `_stream_with_key_retry` 采集，熔断跳过处由 `stream_chat` 采集（status=3）；经 `LlmCallRecord.observe_attempt` 采集，call 为 None（无采集器/旁路）时防护跳过，还原此前仅 Redis 健康数据与日志可见的内部重试/降级/熔断全过程 |
| 幂等 | 同一次调用重复上报按 `(trace_id, seq)` 唯一去重 |

#### 2.3.1 旁路调用采集（B 类改造，2026-08-29）

主对话推理链路之外的旁路 LLM 调用（会话摘要压缩、记忆提取、类似问题推荐、步骤摘要）此前不产生过程链，计费与调用明细不对称。新增 `bypass_span` async context manager（`trace_collector`）：with 块内开启独立采集器（独立 trace_id），块内 LLM 调用自动采集，退出自动结算（`finalize_success` 回退 LLM 调用聚合口径）；异常路径 `finalize_unsettled` 后 re-raise，不改变原业务兜底行为。

| 项 | 说明 |
|----|------|
| 覆盖调用 | summary_service（会话摘要）/ memory_extraction（记忆提取）/ suggestion_service（类似问题推荐）/ step_summarizer（步骤摘要）四处 |
| trace_type | 旁路 trace 以 `trace_type` 标注类型（`summary`/`memory_extraction`/`suggestion`/`step_summary`），主对话为 `conversation` |
| 归属 | summary/memory_extraction 旁路 trace 的 `message_id` 为 null（无 thoughts/billing/artifacts 关联）；suggestion/step_summary 旁路 trace 关联触发消息的 `message_id`，与主对话过程链经 `trace_type` 区分 |
| 隔离 | 旁路采集器经 ContextVar 独立设置，with 块内 LLM 调用记录在旁路 trace 下，退出恢复原上下文（清理 ContextVar），主对话采集不受影响 |

### 2.4 过程记录写入

消息回复结束时聚合写入一条 `sys_ai_trace`（成功/失败均写），由推理编排层在 `after_agent` 钩子完成：

```
推理结束（after_agent 钩子）
  ├─ 聚合：总耗时/首 Token/步数/LLM 调用次数/消耗（含缓存命中，复用计费回填）
  ├─ 状态：正常结束/异常（error_type）
  ├─ 快照：上下文构成（推理入口已记录）
  └─ 写入 sys_ai_trace（幂等，按 trace_id 唯一）
```

**防循环观测**：推理步数超过阈值（如 40 步）在过程链中显著标注，指标侧提供"循环会话"告警（对齐业界对 Agent 循环"蜻蜓翅膀"Span 树的治理）。

**中断恢复采集**：resume 续流（`POST /messages/{id}/resume`）开启独立采集器（新 trace_id），与被中断轮的过程链经 resume 事件的 `from_trace_id` 关联；`context_events` 记录 `resume` 事件（`interrupt_type`/`decision`/`from_trace_id`），决策内容（confirm 的 confirmed/algorithmId、plan_approve 的 plan_edit）随事件留痕，中断—恢复两段过程链可完整串联审计；续流结束正常路径 `finalize_success`、异常路径 `finalize_unsettled` 均落库收尾。

### 2.5 指标与告警

三端 `/metrics` 新增 AI 对话指标（与 Prometheus 命名规范一致），Grafana 面板与告警规则见 `config/prometheus/rules/dehaze-alerts.yml`：

| 指标 | 类型 | 说明 |
|------|------|------|
| `ai_conversation_duration_seconds`（直方图） | 延迟 | 首 Token / 完整回复延迟，分模型/智能体 |
| `ai_conversation_total{status}` | 计数 | 成功/失败/中断/超时会话数 |
| `ai_llm_call_total{model, status}` | 计数 | LLM 调用数（分模型/状态） |
| `ai_llm_call_duration_seconds`（直方图） | 延迟 | 单次调用耗时/首 Token，分模型 |
| `ai_tool_call_total{status, tool}` | 计数 | 工具调用成功/失败数 |
| `ai_token_total{model, type}` | 计数 | Token 消耗（input/output/cached） |
| `ai_token_cache_hit_ratio{model}` | 计数比 | 缓存命中率（cached / prompt），成本优化观测 |
| `ai_step_count` | 直方图 | 推理步数分布（循环检测） |

**告警规则**（新增）：

| 告警 | 表达式要点 | 通知 |

| 失败率突增 | 5 分钟失败率 > 阈值（环比） | 平台管理员 |

| 推理循环 | 步数超过阈值的会话数突增 | 平台管理员 |

#### 2.6.1 查询端点实现（2026-08-29）

全部挂载 `/api/v1/ai/observability/*`（路由 `ai_observability.py`，标签「AI可观测性」）：

| 端点 | 权限 | 实现要点 |
|------|------|---------|
| `GET /summary` | `ai:conversation:audit` | 状态分布复用 `count_by_status`；配额拒绝按采集链路实际写入的拒绝类 `error_type` 统计（`quota`/`quota_exceeded`/`precharge_blocked`/`arrears`/`balance_exceeded`）；高风险调用计数 `step_count ≥ 40`（代码常量 `_HIGH_RISK_STEP_THRESHOLD`）**或存在失败的工具调用**（`sys_ai_llm_call.tool_call` 非空且调用未成功，见 §2.6.2 risky_tool 口径） |
| `GET /traces` | `ai:conversation:audit` | 会话/用户（经会话表关联归属）/状态/智能体/模型/失败类型（`errorType` 精确）/关键词（`keyword` 匹配 `trace_id` 或会话标题模糊）/能力维度（`capability=memory\|kb\|tools`，按 `context_snapshot.items[].type` 构成项匹配，MySQL `JSON_SEARCH`）/时间多维筛选分页，`create_time` 倒序 |
| `GET /traces/{traceId}` | 登录用户（管理员全量） | 普通用户仅可查自己会话的 trace，跨会话与不存在一律 404（`A0401`）不暴露存在性；返回 trace 汇总 + `contextSnapshot` + `llmCalls`（按 seq 正序回放）+ `thoughts`（推理步骤，复用 `sys_ai_agent_thought`，元素透出 `agentCode`/`isSubagent` 归属）+ `messages`（该会话完整消息，复用 `sys_ai_message`）+ `billing`（计费明细，按 `request_id`=trace_id 或 `message_id` 关联 `sys_ai_billing`，含 billType/model/actualModel/providerId/tokens/credits/creditsSaved/latencyMs/errorCode/requestId）+ `artifacts`（中间产物，按 `message_id` 关联 `sys_ai_artifact`）+ `errorDetail`（失败/中断轮异常详情 `{message, stack}`），支撑审计完整回放 |
| `GET /traces/export` | `ai:conversation:audit` | 按检索条件全量导出 CSV（UTF-8 BOM 便于 Excel 打开），复用 traces 筛选条件；超 `MAX_ROWS`（100000）返回 `A0709`；路由先于 `/{traceId}` 注册避免路径参数吞并 |
| `GET /costs` | `ai:conversation:audit` | 按 model/agent/user 维度分页聚合 `traceCount` 与 total/prompt/completion/cached tokens（与计费口径一致，直接汇总 trace 表字段）+ 按日消耗趋势 |
| `GET /trends` | `ai:conversation:audit` | 按 model/agent 维度 + 日期聚合调用量/成功率/平均总耗时；平均首 Token 延迟仅统计有值（成功）调用 |

聚合查询基于 `sys_ai_trace` 现有字段在 service 层直查（与 `cost_stat_service` 等聚合实践一致），未引入 ES/MongoDB 等额外存储。

#### 2.6.2 risky_tool 判定口径（2026-08-29 检索扩展）

**工具执行异常不落 `error_type`**：工具失败经恢复中间件（§6.4）兜住转为 ToolMessage 返回 LLM，过程链 `error_type` 仅承载整条推理的失败类型（异常类名/错误码/中断类型/配额拒绝类）。故工具调用失败的查询侧口径为：

> `sys_ai_llm_call.tool_call` 非空（仅发起工具调用的轮次非空）**且** `status != 1`（失败/超时）

该口径（`_risky_tool_call_exists` 谓词）被两处消费：

| 消费点 | 行为 |
|--------|------|
| summary `highRiskCalls` | `step_count ≥ 40` 或存在失败的工具调用（EXISTS 子查询） |
| 会话审计 `anomalyType=risky_tool` | 会话的过程链存在失败的工具调用（`ai_trace_repository.list_risky_tool_conversation_ids` 批查），优先级 `failed` > `quota` > `risky_tool` > `canceled` |

**能力维度筛选**（`capability`）基于 `context_snapshot.items[].type`（MySQL `JSON_SEARCH`，路径 `$.items[*].type`）。当前采集侧实际写入的构成项为 system/summary/history/memory（见 §2.2 差异说明），`kb`/`tools` 构成项待采集侧补写后该筛选自然生效；工具调用痕迹已可在 LLM 调用级（`tool_call`/`input_snapshot.tool_count`）逐轮归因，不重复做筛选入口。
