## 1. 问题：现状为什么不满足审计要求

用户审计一条会话时，要回答的问题是：**"这次会话的每一轮交互，系统到底给大模型发了什么（完整报文），大模型到底回了什么（完整报文），中间系统做了什么（上下文组装/工具执行/护栏拦截/计费）"**。现状有四层差距：

| # | 差距 | 现状表现 | 根因 |
|---|------|---------|------|
| 1 | **入口组织错误**：审计以"单条消息/单条 trace"为单位 | 会话审计页链路追踪是单消息抽屉（`GET /messages/{id}?view=admin`）；可观测中心 traces 列表按 traceId 平铺 | 缺少"会话 → 轮次 → 事件"的层级读模型。一次审计要人工点开几十条消息逐条拼凑，无法按时间序看到完整交互流 |
| 2 | **非 wire 级留痕**：看不到发给 LLM 的完整请求与 LLM 返回的完整响应 | `input_snapshot` 是采集器重构的摘要视图（messages 逐条 role/content + tools 仅 name/description）；`output_snapshot` 只有 `text` 字段 | 采集层从未留存实际请求体（temperature/max_tokens/tool_choice/stream_options、tools 完整 JSON Schema）与响应原文（finish_reason、tool_calls 的 arguments 原文、usage 原始字段、provider 响应 id/model）。审计要求"不可抵赖的原始报文"，重构摘要无法满足 |
| 3 | **无时间线叙事**：每轮内部的事件交织关系不可见 | 详情把 llmCalls / thoughts / messages / billing 分块平铺，靠读者脑补时序 | `sys_ai_llm_call` 只有 `create_time + duration_ms`（结算时刻），无 `start_time`，无法把"第 2 次 LLM 调用"与"第 1 次工具执行"在时间轴上精确排序 |
| 4 | **旁路过程不可见**：摘要压缩/记忆提取等旁路调用混在 trace 列表里 | 旁路 trace 有 `trace_type` 标注，但在会话视图里没有挂到触发轮次下 | 会话级读模型缺失（同 #1） |

**数据底座评价**：`sys_ai_trace`（轮次汇总）+ `sys_ai_llm_call`（调用级明细）+ `sys_ai_agent_thought`（工具/步骤）+ 复用 message/billing/artifact 的双粒度模型**方向正确、无需推翻**——它已对齐业界 span 模型。缺的是 wire 级原始留痕（#2）与面向审计的读模型/视图（#1/#3/#4）。本次重构**不新建核心表、不迁移已有数据**，做的是"补字段 + 补读模型 + 重构展示"。

## 2. 业界最佳实践对标

对标三类主流方案：Langfuse（开源 LLM 观测平台）、LangSmith（LangChain 官方）、OpenTelemetry GenAI 语义约定（v1.28+，行级标准）。

### 2.1 三层追踪模型（业界共识）

```
Session（会话）           —— 审计一等公民，按时间序回放整条线程
└── Trace（一轮交互）      —— 一次用户输入 → 推理 → 助手回复的自包含工作单元
    ├── Event  上下文组装 / 护栏命中 / 计划快照 / 中断恢复
    ├── Generation  单次 LLM 调用（每次模型调用独立记录，绝不把 agent 循环包成一条）
    │     ├─ input：实际发送的完整消息列表（OpenAI 格式，含 tool_calls）
    │     ├─ output：模型完整响应（含 tool_calls arguments 原文、finish_reason）
    │     ├─ model / modelParameters（temperature、max_tokens、tool_choice…）
    │     └─ usage（input/output/cached tokens）+ startTime/endTime
    ├── Span  工具执行（入参/出参/耗时/状态，嵌套归属）
    └── 计费 / 产物等业务关联
```

| 业界实践 | 要点 | 本平台现状 |
|---------|------|-----------|
| 每轮一个 trace，整个会话一个 session（Langfuse/LangSmith） | 事先不知道会话何时结束，按轮拆分保持 trace 小巧，session 视图按序回放 | ✅ `sys_ai_trace` 一轮一条；❌ 无 session 视图 |
| Generation 存完整 wire JSON，而非摘要（OTel `gen_ai.content.prompt/completion` 事件、Langfuse input/output 任意 JSON） | prompt/completion 以 OpenAI messages 格式 JSON 全文留存；tool_calls 必须保留在 assistant 消息的 `tool_calls` 数组中（arguments 为原始 JSON 字符串）才能完整回放 | ❌ 只有重构摘要 |
| Span 带 startTime/endTime（OTel 标配） | 事件按时间轴交织排序的前提 | ❌ llm_call 无 start_time |
| 命名/类型稳定，动态值进 metadata（Langfuse "把名称当作 API"） | trace 结构会被评估器、仪表盘、导出引用，字段口径不可漂移 | ✅ 表结构稳定，本次只增不改 |
| 敏感信息脱敏 + 体积上限（OTel 明确要求 prompt/completion 捕获可关闭、防超大上下文） | 留痕与隐私/体积平衡 | 部分（各上限已有，raw 层新增上限） |

### 2.2 结论

重构三条主线：**① 补 wire 级原始报文留痕（Generation 级）；② 建会话审计时间线读模型（Session 级）；③ 前端改时序回放展示（Timeline 视图）**。traces 检索列表保留作为跨会话检索入口，不再是审计主路径。

## 3. 目标设计

### 3.1 审计信息全景（一轮交互的事无巨细清单）

时间线上每轮交互完整可回放以下内容，**可见与不可见、系统内部与外部交互全部留痕**：

| 层 | 内容 | 留痕形态 |
|----|------|---------|
| 用户输入 | 用户消息原文、触发方式（普通发送/resume）、附件/产物引用 | `sys_ai_message`（已有） |
| 上下文组装 | 系统提示全文、历史窗口（哪些消息被纳入/被截断）、注入记忆、会话摘要、上下文压缩事件、范式路由结果 | `context_snapshot`（已有，保持） |
| **LLM 调用（每次）** | **完整请求体**（model、messages 全文、tools 完整 JSON Schema、temperature、max_tokens、tool_choice、stream 等）与**完整响应**（content、tool_calls 完整结构与 arguments 原文、finish_reason、usage 原始字段、provider 响应 id/model）、首 token/总耗时、物理路由尝试（attempts：逐 Key 重试/降级/熔断） | `raw_request`/`raw_response`（**新增**）+ `input_snapshot`/`output_snapshot`（保留为摘要） |
| 工具执行（每步） | 工具名、AI 思考原文、完整入参、完整返回、耗时、状态、子 Agent 归属 | `sys_ai_agent_thought`（已有） |
| 系统内部事件 | 护栏命中（规则/详情）、计划快照、中断与恢复决策、错误与堆栈 | `context_events` + `error_detail`（已有） |
| 产出与计费 | 助手消息全文、中间产物、计费明细（token/积分/缓存节省/误差对账） | `sys_ai_message`/`sys_ai_artifact`/`sys_ai_billing`（已有） |
| 旁路调用 | 会话摘要压缩、记忆提取、建议生成等旁路 LLM 调用（同样 wire 级） | 旁路 trace + `raw_request`/`raw_response` |

### 3.2 审计主视图：会话时间线

```
会话审计页
├── 左栏：轮次导航（每轮 = 用户消息 → 助手回复）
│     ├── 轮次 5  「你是谁」→「我是助手…」  ✅ 1.2s · 502 tok · 1 次调用
│     ├── 轮次 6  「帮我总结…」→ ⚠️ 工具失败  ❌ 3 次调用 · 2,140 tok
│     └── 轮次 7  …
└── 右栏：选中轮次 · 时序回放时间线（垂直时间轴，事件按 startTime 交织排序）
      ├── ● 10:53:09.120  用户输入（全文）
      ├── ● 10:53:09.131  上下文组装（构成项占比 + 截断/压缩事件 + 系统提示全文）
      ├── ● 10:53:09.140  LLM 调用 #1  qwen3-0.6b · 666ms · TTFT 431ms · 478/24 tok
      │     ├── 摘要卡：输入构成 / 输出预览 / 是否发起工具调用 / attempts
      │     ├── [查看完整请求 JSON]  ← raw_request，语法高亮、复制、下载
      │     └── [查看完整响应 JSON]  ← raw_response（含 tool_calls/finish_reason/usage）
      ├── ● 10:53:11.002  工具执行 #1  enhance_image（完整入参/返回/耗时/子Agent归属）
      ├── ● 10:53:12.880  LLM 调用 #2  …（同上）
      ├── ● 10:53:14.100  计费  预扣/结算/误差
      └── ● 10:53:14.130  助手输出（全文 + 产物）
```

旁路 trace（摘要压缩/记忆提取）挂到**触发轮次**的时间线尾部，标注类型，不混入主调用序列。

## 4. 后端设计

### 4.1 数据层：`sys_ai_llm_call` 补三列（唯一 DDL 变更）

| 新增列 | 类型 | 说明 |
|--------|------|------|
| `start_time` | datetime(3) | 调用发起时刻。时间线交织排序的锚点（`create_time` 语义改为"结算落库时刻"，两者并存不迁移） |
| `raw_request` | JSON | 实际发给 provider 的**完整请求体**（wire 原文） |
| `raw_response` | JSON | 流式 chunk 聚合后的**完整响应**（等价非流式结构） |

`raw_request` 采集内容（以 OpenAI 兼容协议为例，Anthropic 协议按实际 body）：

```json
{
  "model": "qwen3-0.6b",
  "messages": [ {"role": "system", "content": "..."}, {"role": "user", "content": "..."} ],
  "tools": [ {"type": "function", "function": {"name": "...", "description": "...", "parameters": {完整 JSON Schema}} } ],
  "tool_choice": "auto",
  "temperature": 0.7,
  "max_tokens": 2048,
  "stream": true,
  "stream_options": {"include_usage": true}
}
```

`raw_response` 采集内容（流式聚合为等价非流式结构）：

```json
{
  "id": "chatcmpl-...", "model": "qwen3-0.6b",
  "choices": [ {
    "index": 0,
    "finish_reason": "tool_calls",
    "message": { "role": "assistant", "content": "...",
                 "tool_calls": [ {"id": "...", "type": "function",
                                  "function": {"name": "...", "arguments": "{原始 JSON 字符串}"}} ] }
  } ],
  "usage": {"prompt_tokens": 478, "completion_tokens": 24, "total_tokens": 502, "cached_tokens": 0}
}
```

**采集规则**：

| 规则 | 说明 |
|------|------|
| 采集点 | `openai_compat_client` / `anthropic_client` 的 `stream_chat` 构建请求处与流聚合处，经 `LlmCallRecord` 旁路上报（对调用方无侵入，失败仅告警不影响主链路，沿用既有旁路硬约束） |
| 与 snapshot 关系 | `input_snapshot`/`output_snapshot` 保留，定位为**轻量摘要视图**（列表/卡片渲染、低带宽）；`raw_*` 为**审计原文**，仅详情/时间线接口透出。两份数据由采集层一次生成，`raw_request.messages` 与 `input_snapshot.messages.items` 同源 |
| 体积上限 | `raw_request`/`raw_response` 各上限 256KB，超限截断并以 `{"_truncated": true, "_original_bytes": N}` 标注（防病态载荷，正常对话远达不到） |
| 脱敏 | 仅存请求体，不存 headers/URL/API Key；`attempts` 里的 key 维度沿用现有 key_id（不落明文），与既有隐私口径一致 |
| 失败调用 | 物理尝试全失败时 `raw_request` 照存，`raw_response` 存最后一条错误响应（或 `{"error": {...}}`），状态与 attempts 还原全过程 |
| ~~兼容~~ 老数据 | **不做兼容**（项目规范"禁止兼容历史烂逻辑"）：重构上线前的存量调用 `raw_*` 为 NULL，前端按自然空态显示"无原始报文记录"，不设 snapshot 全文兜底路径、不区分新旧数据形态 |

### 4.2 读模型：会话审计时间线 API（新增）

**`GET /api/v1/ai/observability/conversations/{conversationId}/timeline`**

权限：管理员（`ai:conversation:audit`）全量；普通用户仅自己会话（跨会话 404 不暴露存在性，沿用 A0401 口径）。

返回结构（按轮次组织，轮内事件按 `startTime` 排序）：

```json
{
  "conversation": {"id": 2, "title": "...", "userId": 2, "agentCode": "...", "createTime": "..."},
  "rounds": [
    {
      "userMessage":      {"id": 35, "role": "user", "content": "...", "createTime": "..."},
      "assistantMessage": {"id": 36, "role": "assistant", "content": "...", "status": 2, "model": "...", "inputTokens": 478, "outputTokens": 24},
      "traces": [
        {
          "traceId": "...", "traceType": "conversation", "status": 1,
          "errorType": null, "model": "...", "durationMs": 4200, "createTime": "...",
          "errorDetail": null,
          "events": [
            {"kind": "input",        "ts": "...", "message": {...}},
            {"kind": "context",      "ts": "...", "snapshot": {"items": [...], "events": [...]}},
            {"kind": "llm_call",     "ts": "...", "seq": 1, "model": "...", "status": 1,
                                     "durationMs": 666, "firstTokenMs": 431,
                                     "promptTokens": 478, "completionTokens": 24, "cachedTokens": 0,
                                     "toolCall": {...}, "attempts": [...],
                                     "rawRequest": {...}, "rawResponse": {...},
                                     "summary": {"inputSnapshot": {"messages": {"counts": {"user": 1, "assistant": 2, "tool": 1}, "tokens": 502},
                                                                   "system_tokens": 800, "tool_count": 8, "user_id": 2},
                                                 "outputSnapshot": {"text": "...", "tool_calls": null}}},
            {"kind": "tool_exec",    "ts": "...", "position": 1, "tool": "...", "thought": "...",
                                     "toolInput": {...}, "observation": "...", "latencyMs": 800,
                                     "agentCode": "...", "isSubagent": 0},
            {"kind": "system_event", "ts": "...", "event": "guardrail|plan|resume|...", "detail": {...}},
            {"kind": "billing",      "ts": "...", "billType": "...", "credits": 1,
                                     "tokens": {"input": 478, "output": 24, "cached": 0}}
          ]
        }
      ]
    }
  ]

```

查询参数：`include=raw`（默认包含 raw 报文；传空则省略，供轻量预览）。

**实现要点**：

| 要点 | 说明 |
|------|------|
| 数据拼装 | 单次会话读：messages（轮次边界）→ traces（含旁路按触发轮次归属）→ llm_calls/thoughts/billing/artifacts 按 trace_id 批量取回，service 层织入 events 按 ts 排序；全部走既有 repository，无新增写路径 |
| 事件 ts 来源 | llm_call 用新 `start_time`（NULL 的事件排序沉底，**不做近似估算**）；thought/billing 用 `create_time`；context 组装事件用 trace 的 `create_time` 减 duration 近似（trace 表无精确起始时刻字段，此为既有锚点口径，不精确处标注顺序而非时刻） |
| 轮次切分 | 沿消息链（parent_message_id 分支链）配对 user→assistant；resume 多 trace 挂同一轮次，按 traceId 并列展示 |
| 旁路归属 | suggestion/step_summary 类旁路 trace（有 message_id）挂触发轮次尾部；summary/memory_extraction（无 message_id）挂"触发时点的最新轮次"尾部，前端标注类型徽标 |

### 4.3 既有接口调整

**summary 字段口径（llm_call 事件）**：恒为轻量计数摘要（消息角色计数/tool_count/user_id/输出预览文本），**单一形状无降级分支**——messages/tools 全文唯一通道是 `rawRequest`，与 `input_snapshot` 不双份传输；`include` 传空（轻量预览）时 summary 照常返回、raw 字段省略。

| 接口 | 变更 |
|------|------|
| ~~`GET /ai/messages/{id}?view=admin`~~ | ~~llmCalls 增补 raw 字段~~ **已否决**：ChainTracePanel 下线后该视图的 llmCalls/contextSnapshot 已无前端消费者，按"禁止兼容历史烂逻辑/不保留已废弃旧代码路径"一并移除组装（thoughts 保留——用户端过程透明在用） |
| `GET /ai/observability/traces` | 列表行增加 `conversationId`/`conversationTitle` 返回（已有会话关联，透出即可）；行内"查看会话时间线"跳转由前端用 conversationId 构造 |
| `GET /ai/observability/traces/{traceId}` | `llmCalls[]` 增补 `startTime`/`rawRequest`/`rawResponse` |
| 导出 | 时间线会话支持整体导出（JSON 全量含 raw），复用既有导出权限口径 |

### 4.4 不做的事（明确边界）

- **不引入** Langfuse/OTel SDK 或外部观测平台（选型结论不变，见后端实现.md §1.1）
- **不迁移/重写** 既有 `sys_ai_trace`/`sys_ai_llm_call` 数据与口径
- **不改** `input_snapshot`/`output_snapshot` 语义（避免双写漂移；raw 层为唯一新增原文）
- Prometheus 指标与保留策略（§2.5/§2.7）仍按原计划独立排期，不混入本次

## 5. 前端设计

### 5.0 页面合并决策（2026-09-13 用户确认）

管理端现有两处职责重合的入口：会话管理页（`ai-conversations` 管理端）的链路追踪抽屉与 AI 可观测中心（`/admin/ai-observability`）。**决策：只保留可观测中心一个入口**，功能点全部集中：

| 变更 | 说明 |
|------|------|
| 保留并扩展 `/admin/ai-observability` | 唯一管理端 AI 观测/审计入口，页面重组为三个 Tab：**会话审计**（会话列表 → 会话时间线回放，新主 Tab）、**总览**（异常总览 + 性能趋势 + 资源透视，复用现有组件）、**检索导出**（trace 跨会话检索，行内跳转会话时间线） |
| 移除会话管理页链路追踪 | `ChainTracePanel` 组件及单消息链路追踪抽屉下线；会话管理页保留会话/消息管理与异常标注，链路查看入口改为跳转可观测中心（携 conversationId 定位会话时间线） |
| 用户端不动 | 对话页"查看过程"组件（ProcessPanel）面向用户过程透明，保留现状，不透出 raw 报文 |

### 5.1 会话时间线视图（可观测中心 · 会话审计 Tab）

| 区块 | 组件 | 说明 |
|------|------|------|
| 会话列表 | `ConversationAuditTable`（新，吸收原会话审计检索） | 会话维度检索（用户/时间/状态/异常类型），行内异常标注，点击进入时间线 |
| 轮次导航 | `RoundNavigator`（新） | 左栏轮次列表：用户消息摘要、状态徽标（成功/失败/中断/工具异常）、耗时、token、调用次数；异常轮显著标注 |
| 时序回放 | `RoundTimeline`（新，核心） | 右栏垂直时间轴，按 3.2 全景图渲染；轮次内事件节点按 kind 分色 |
| LLM 调用节点 | `LlmCallNode`（新） | 默认摘要卡（模型/耗时/TTFT/token/tool_call/attempts），展开两块：`查看完整请求 JSON` / `查看完整响应 JSON` |
| 工具节点 | 复用既有 `ToolCallEntry` 增强 | 完整入参/出参（JSON 视图） |
| 原始报文 | `JsonViewer`（公共组件） | 语法高亮、按节点折叠、复制、下载；raw 为空显示中性空态"无原始报文记录" |
| 旁路徽标 | traceType 徽标 | summary/memory_extraction/suggestion/step_summary 在时间线尾部以次要样式展示，点开同样有 raw 回放 |

### 5.2 可观测中心页（`ai-observability`）

- `TraceDetailDrawer`（现有 25KB 抽屉）**拆解重构为复用 `RoundTimeline`**：trace 详情 = 单轮时间线的子集（同一组件、同一数据形状），消除两套展示逻辑漂移
- `TraceSearchTable` 保留跨会话检索定位价值；行操作增加"跳转会话时间线"（携 conversationId 路由到会话审计页并定位轮次）
- 会话审计页与可观测中心共享 `RoundTimeline`/`JsonViewer`/`LlmCallNode` 组件与 TS 类型（`adminAudit.ts` store 扩展）

### 5.2 可观测中心页重组（唯一管理端入口）

- 页面重组为三 Tab：**会话审计**（ConversationAuditTable → RoundNavigator + RoundTimeline，审计主路径）、**总览**（AnomalyOverview/PerformanceTrendPanel/CostPanel 复用保留）、**检索导出**（TraceSearchTable 保留跨会话检索定位价值；行操作"跳转会话时间线"携 conversationId 切到会话审计 Tab 并定位）
- `TraceDetailDrawer`（现有 25KB 抽屉）**拆解重构为复用 `RoundTimeline`**：trace 详情 = 单轮时间线的子集（同一组件、同一数据形状），消除两套展示逻辑漂移
- 共享 `RoundTimeline`/`JsonViewer`/`LlmCallNode` 组件与 TS 类型（`adminAudit.ts` store 扩展）
- 会话管理页（`ai-conversations` 管理端）移除 `ChainTracePanel` 与单消息链路追踪，链路入口跳转可观测中心

### 5.3 交付形态

- 路由：`/admin/ai-observability` 三 Tab；会话管理页链路追踪入口替换为跳转链接
- 权限：`ai:conversation:audit`（管理端）；用户端"查看过程"组件不展示 raw 报文（用户侧仅过程透明，原文审计属管理端能力）

## 7. 风险与决策点

| 项 | 风险/决策 | 建议 |
|----|----------|------|
| raw 双份存储体积 | `raw_request.messages` 与 `input_snapshot.messages.items` 内容重叠，单调用约 2 倍消息正文存储 | 保留双份：snapshot 供轻量渲染与既有筛选（capability 检索走 JSON_SEARCH 依赖它），raw 供审计原文；180 天保留策略不变，成本可控 |
| datetime(3) 精度 | 时间线交织排序需要毫秒 | 新列 datetime(3)；thought/billing 沿用秒级 create_time，同秒内按业务序（llm_call.seq/thought.position）稳定排序 |
| 前端重构幅度 | TraceDetailDrawer 25KB 单文件重构 + 两页合并 | 拆为时间线组件族，一次性 P2 交付，不做中间态 |
| 用户端是否透出 raw | raw 含系统提示与工具定义全文，可能含提示词保护诉求 | 用户端不透出（§5.3 已定），管理端与审计导出可见 |
| 入口合并迁移 | 移除会话管理页链路追踪后，既有用户习惯路径变化 | 会话管理页保留跳转入口（携 conversationId 直达时间线），路由层面平滑迁移 |
