# AI 对话模块 - 后端实现设计（能力扩展）

## 1. 文档概述

本文档描述 F-M08-006 能力扩展的后端实现，包括工具执行体系（deepagents 内置工具 + dehaze 业务工具）、工具调用生命周期与可见性、高风险操作确认、MCP 工具命名空间预筛选、搜索与代码执行、虚拟文件系统与任务清单约束、Skills 管理。

### 1.1 设计思想

#### 设计动机

能力扩展是 AI 对话从"会聊天"走向"能干活"的桥梁，本功能域的根本矛盾是：**Agent 能力的可获得性**与**上下文资源的有限性**之间的张力。

一方面，Agent 要能干平台的所有活（去雾、评估、推荐、搜索、执行代码），工具种类注定越来越多；另一方面，LLM 上下文窗口有限，数万个 token 的工具定义塞进每一轮调用，既贵又挤占对话空间。若全量注入工具，简单问题被工具定义淹没，Token 成本失控；若不全量注入，复杂任务又找不到可用工具。

本功能域的设计目标：**让 Agent 在需要时能发现任何能力，但只在需要时加载对应的工具——能力无限可得，上下文按需供给**。

#### 核心设计原则

| 原则 | 说明 |
|------|------|
| 能力工具化 | 所有系统能力（业务 API、文件操作、搜索、代码执行、工作流指令、子 Agent）统一以"工具"形态接入，由 LLM Function Calling 统一调度。推理核心不感知具体能力，新增能力不改推理循环 |
| 按需加载 | 工具定义不全量注入：MCP 按命名空间预筛选、Skills 渐进式加载（只加载名称描述，需要时再加载指令）。上下文只承载"当前任务相关"的工具 |
| 多源统一 | deepagents 内置工具（虚拟文件系统/TodoWrite/task）与 dehaze 业务工具（推荐/批量/MCP/Skills）在同一个工具列表中供 LLM 决策，来源透明 |
| 高频直连 | 算法推荐、批量处理等高频路径绕开 MCP 网络开销直接调用业务服务；低频通用 API 走 MCP 动态发现。性能与扩展性按使用频率分层取舍 |

#### 关键架构取舍

| 取舍点 | 方案对比 | 选择与理由 |
|--------|---------|-----------|
| 工具注入策略 | 全量注入所有工具定义 vs 命名空间预筛选 | 选预筛选。全量注入数万个 token 的工具定义会挤占上下文预算；`before_model` 钩子按用户意图预筛选 1-2 个命名空间，典型请求节省 83%-99% 上下文（详见 §3.2） |
| 工具接入方式 | 直接服务调用 vs MCP 网关调用 | 两者并存。高频路径（算法推荐、批量处理）绕开 MCP 网络开销直接调用业务服务；通用路径走 MCP 动态发现，换取"新增 API 零改动"的扩展性 |
| Skill 加载粒度 | 全量注入完整指令 vs 渐进式加载（名称→指令） | 选渐进式。启动只注入名称+描述（几十 tokens），LLM 判断需要时通过 `skill_load` 工具加载完整指令，避免无关 Skill 挤占上下文 |
| 工具来源组织 | 本地维护工具注册表 vs MCP 网关作为注册表 | 选后者。MCP 网关读取后端 OpenAPI 自动解析所有 API，AI 对话模块只需调用 MCP 的 3 个元 tool，无需本地维护注册表，新增 API 后 MCP 自动发现（详见 §3.3） |

#### 总体规划

能力扩展是"能力层（工具）"，位于推理引擎与底层业务系统之间：

```
多步推理（LLM Function Calling 决策调用哪个工具）
    ↓
能力扩展（工具执行体系）
    ├── deepagents 内置工具（虚拟文件系统/TodoWrite/task）
    ├── dehaze 业务工具（推荐/批量/评估，高频直连）
    ├── MCP 工具（通用 API 动态发现，命名空间预筛选）
    └── Skills（工作流指令包，渐进式加载）
    ↓
底层系统（图像处理/指标评估/算法推荐/文件/搜索/沙箱）
```

推理引擎只负责"决策"，能力扩展只负责"分发"，底层系统只负责"执行"，三层职责互不侵入。

## 2. 工具执行体系

工具调用通过 LLM Function Calling 统一调度。deepagents 内置虚拟文件系统工具（`read_file`/`write_file`/`edit_file`/`ls`/`glob`/`grep`）、TodoWrite（`write_todos`）、子 Agent 调用（`task`）等工具，dehaze 业务工具（`algorithm_recommend`/`batch_process`/`mcp_*`/`skill_load`）通过 `DehazeToolsBuilder` 按 Agent 配置装载，与 deepagents 内置工具合并：

| 工具来源 | 工具名 | 执行器 | 说明 |
|---------|--------|--------|------|
| deepagents 内置 | `read_file`/`write_file`/`edit_file`/`ls`/`glob`/`grep` | `FilesystemMiddleware` + `StateBackend` | 虚拟文件系统，基于 LangGraph State，不操作真实磁盘；工作区容量限制见 §6.1 |
| deepagents 内置 | `write_todos` | `TodoListMiddleware` | 维护结构化任务清单（pending/in_progress/completed）；数量上限与粒度约束见 §6.2 |
| deepagents 内置 | `task` | `SubAgentMiddleware` | 调用子 Agent 执行隔离子任务，返回结果摘要 |
| dehaze 业务 | `algorithm_recommend` | `RecommendationService`（直接服务调用） | 算法推荐 + interrupt 等待用户确认 |
| dehaze 业务 | `batch_process` | `prediction_service`（直接服务调用，SSE 推送进度） | 批量处理 |
| dehaze 业务 | `skill_load` | `SkillManager`（加载指令注入 system_prompt） | Skills 渐进式加载 |
| dehaze 业务 | `mcp_lookup_tool` / `mcp_execute_tool` | `McpGatewayClient`（连接 MCP 网关） | MCP 工具动态发现与执行 |

**工具装载策略**：
- dehaze 业务工具通过 `DehazeToolsBuilder` 按 Agent 配置（Skills/MCP 命名空间）装载，与 deepagents 内置工具合并
- deepagents 内置工具默认全部可用，通过 `HarnessProfile.excluded_tools` 移除不需要的工具
- 工具定义采用 OpenAI Function 定义格式，Anthropic 适配在 `DehazeChatModel` 内完成

**直接服务调用 vs MCP 调用**：算法推荐、批量处理是高频路径，绕开 MCP 网络开销直接调用业务服务；其余通用 API 调用通过 MCP 网关动态发现，新增后端 API 后 MCP 自动同步，无需修改 AI 对话模块代码。

**Skills 渐进式加载**：
- 启动时只加载 Skills 的名称和描述（几十 tokens），不加载完整指令
- LLM 判断需要某个 Skill 时，通过 `skill_load` 工具加载完整指令
- Skill 指令中可引用其他工具（如"调用 MCP 的评估工具获取指标"），形成 Skills + 工具的协同

### 2.1 工具调用生命周期与可见性

工具调用让用户"看到 AI 在做什么"，其生命周期记录通过现有 SSE 事件承载，不新增事件类型：

| 阶段 | 承载方式 | 说明 |
|------|---------|------|
| 调用发起 | `content_block` type=`tool_use` | 记录工具名与参数流式增量，前端渲染 ToolMessage（默认折叠） |
| 执行状态 | `thought` 事件 `status` 字段 | `running` / `success` / `error`，前端按状态更新徽标与结果摘要 |
| 完成记录 | `thought` 事件完整字段 | `{tool, toolInput, observation, status, latencyMs}` 作为工具调用审计记录持久化到消息推理步骤 |

**工具调用审计**：每次工具调用的完整记录（工具名、参数、结果摘要、状态、耗时）随消息的推理步骤持久化，用户可在消息详情回看"AI 刚才做了什么"，同时供安全审计与问题排查。

### 2.2 高风险操作确认

对影响范围大或不可逆的操作（批量删除、覆盖写文件、执行任意命令等），执行前须征求用户确认。复用多步推理的中断确认机制（interrupt 事件 type=`confirm`，详见 [后端实现-多步推理](./后端实现-多步推理.md)）：

```
工具被判定为高风险（按操作类型 + Agent 权限配置判定，见智能体管理文件权限规则）
    ↓
execute_tools 节点不直接执行，改为抛出 interrupt(type=confirm)
    ↓
前端渲染确认卡片（操作内容 + 影响范围 + 修改参数入口）
    ↓
用户确认/修改 → 复用消息发送接口 resume 参数恢复推理，按确认后的参数执行
用户拒绝 → 中断取消，LLM 收到"用户拒绝"反馈，调整方案或说明
```

> 判定规则：写操作（覆盖已有文件）、批量/删除类操作、任意命令执行（Shell）默认需确认；只读查询类操作（读文件、检索、计算）不触发确认。

### 2.3 连续失败保护

同一工具连续调用失败达到上限后停止调用，避免无效重试消耗资源（对齐 Claude Code 重试退避实践）：

| 规则 | 说明 |
|------|------|
| 单次失败 | 记录失败原因并作为 tool 消息反馈给 LLM，由 LLM 决策重试 / 换工具 / 跳过 |
| 连续失败上限 | 同一工具同一推理内连续失败达 3 次，将该工具从当前可用工具列表临时剔除，并提示 LLM 更换能力 |
| 恢复 | 会话级恢复（新推理轮次重置失败计数），或用户明确要求后恢复该工具 |

## 3. MCP 工具命名空间预筛选

### 3.1 机制说明

MCP 工具预筛选由 `before_model` 钩子承担（钩子机制详见 [架构与公共 §4.5 生命周期钩子](./后端实现-架构与公共.md#45-生命周期钩子agenthooks)），负责按用户意图预筛选工具的加载范围：

```
每次 LLM 调用前（before_model 钩子）：
    ↓
Step 1: 调用 MCP 网关 tools/list（无 expand）获取命名空间摘要
  - 返回 8 个分组摘要（name + description + tool_count），总共 ~160 tokens
  - 缓存摘要结果 5 分钟（MCP 网关定时同步间隔）
    ↓
Step 2: 意图匹配（规则预判，不调 LLM）
  - 从用户消息提取关键词
  - 匹配命名空间：{"去雾/处理/增强" → image_processing, "评估/PSNR/SSIM" → evaluation, "算法/推荐" → algorithm, ...}
  - 匹配 1-2 个命名空间
    ↓
Step 3: 展开匹配的命名空间
  - 调用 MCP 网关 tools/list（expand=[matched_namespaces]）
  - 获取匹配命名空间内 tool 的完整定义（name + description + inputSchema）
  - 典型：1-2 组 × 5-8 个工具 × 500 tokens = 2,500-8,000 tokens
    ↓
Step 4: 组装上下文（注入展开后的工具定义到 system prompt 的 tools 部分）
    ↓
如果意图无法匹配任何命名空间（模糊请求）：
  - 只注入命名空间摘要 + tool_search 工具的完整定义
  - LLM 需要时自行调用 tools/search 发现工具
```

### 3.2 效果对比

| 场景 | 全量注入 | 预筛选后 | 节省 |
|------|---------|---------|------|
| "PSNR是什么" | 50,000 | 160（仅摘要） | 99.7% |
| "帮这张图去雾" | 50,000 | 160 + 4,000 = 4,160 | 91.7% |
| "去雾并评估" | 50,000 | 160 + 8,000 = 8,160 | 83.7% |

### 3.3 MCP 调用流程

1. LLM 通过 function calling 决定调用 `mcp_lookup_tool` 工具（参数：`query`）
2. `execute_tools` 节点调用 `mcp_gateway_client.lookup_tool(query)` 搜索匹配的后端 API，结果作为 tool 消息回传给 LLM
3. LLM 决定调用具体 MCP 工具时，通过 `mcp_execute_tool` 工具（参数：`tool_name`、`arguments`）触发 `mcp_gateway_client.execute_tool(tool_name, arguments)` 调用后端 API

**为什么不需要本地工具注册表**：

MCP 网关本身就是工具注册表，它读取后端 OpenAPI 文档自动解析所有 API。AI 对话模块只需调用 MCP 的 3 个元 tool 即可，无需在本地维护工具注册表。新增后端 API 后 MCP 自动发现，无需修改 AI 对话模块代码。

## 4. Skills 管理（SkillManageService）

SkillManager 承担 Skill 的执行职责（渐进式加载、按步骤执行工作流，见 §2 工具执行体系）。SkillManageService 负责管理侧（F-M08-006 中的 Skills 管理部分）：

| 管理操作 | 职责 | 业务规则 |
|---------|------|---------|
| Skills 列表查询 | 返回可用 Skills（名称、描述、适用场景、启用状态） | 所有用户可查询；加载到 Agent 时仅返回启用项 |
| Skill 创建 | 管理员创建自定义 Skill（Markdown 指令 + 可选脚本/模板） | 需管理员权限；指令内容校验（长度限制、危险操作拦截） |
| Skill 启停 | 管理员启用/禁用 Skill | 禁用后不再加载到 Agent 工具列表；运行中的实例不受影响 |
| Skill 更新 | 管理员更新 Skill 指令内容 | 更新后新会话生效，进行中的会话沿用旧版本 |

**Skill 管理与执行的关系**：

| 关注点 | 归属 |
|--------|------|
| Skill 的存储、CRUD、启停 | SkillManageService（本节） |
| Skill 的渐进式加载、按步骤执行 | SkillManager（§2 工具执行体系） |

SkillManageService 维护 Skill 元数据，SkillManager 启动时从 SkillManageService 获取启用列表（仅名称+描述），LLM 判断需要时通过 `skill_load` 工具向 SkillManager 请求加载完整指令。

## 5. 搜索与代码执行

### 5.1 搜索工具与配额

| 能力 | 执行器 | 说明 |
|------|--------|------|
| 网络搜索 | `WebSearchTool` | 调用外部搜索服务，返回标题 + 摘要 + 来源链接；单次返回 Top 5-10 条 |
| 知识库检索 | `KnowledgeBaseTool` | 调用 AI 知识库 RAG 检索，结果带来源引用；命中内容注入上下文 |
| 本地文件检索 | `FilesystemMiddleware`（grep/ls） | 仅检索虚拟文件系统工作区与授权的文件范围 |

**搜索配额与降级**：

| 规则 | 说明 |
|------|------|
| 频率限制 | 网络搜索按用户维度限频（如 30 次/小时），超限返回错误提示用户 |
| 结果截断 | 单次返回条数受限（Top 5-10），避免输出泛滥占用上下文 |
| 失败降级 | 网络搜索不可用/超限时，降级为知识库检索；两者都不可用时告知用户并给替代建议（见需求规格 §2.6.4） |
| 引用溯源 | 检索结果的来源随 tool 消息返回 LLM，回答引用时标注来源 |

### 5.2 代码执行沙箱

代码执行在隔离沙箱中运行，与用户真实系统隔离，安全边界是产品红线：

| 维度 | 实现 |
|------|------|
| 隔离环境 | 容器级隔离（每会话独立实例），不共享宿主机文件系统与网络 |
| 环境支持 | Python、Shell（沙箱内）等常见执行环境 |
| 超时与资源 | 单次执行超时（默认 60s）+ 资源上限（CPU/内存/进程数），防止失控执行与资源耗尽 |
| 安全约束 | 沙箱内无真实磁盘访问、无内网敏感服务访问；高风险命令触发确认（见 §2.2） |
| 结果封装 | 标准输出/错误码/产物文件引用返回给 LLM；错误信息结构化（不暴露内部堆栈） |

**执行流程**：

```
LLM 决定调用沙箱执行工具（传入代码/命令 + 超时参数）
    ↓
高风险命令（Shell 任意命令/删除等）→ 触发 §2.2 确认流程
    ↓
沙箱执行（限时 + 限资源）
    ↓
返回 {stdout, stderr, exitCode, artifacts} 作为 tool 消息
    ↓
执行结果以工具调用条目展示（§2.1），LLM 汇总呈现
```

## 6. 虚拟文件系统与任务清单约束

### 6.1 虚拟文件系统容量限制

| 规则 | 说明 |
|------|------|
| 容量上限 | 单会话工作区默认上限 100MB（`/workspace/**`），由 Agent 配置的文件权限规则约束读写范围 |
| 超限处理 | 写入超限时工具返回错误，提示 Agent 清理（删除临时文件）或压缩后再写入 |
| 生命周期 | 随会话结束清除；推理中断恢复时工作区内容随执行状态保留（不丢失） |
| 与持久化产物的关系 | 工作区是推理临时区；有价值的最终结果经产物引用化（见 [后端实现-上下文管理](./后端实现-上下文管理.md)）持久化为用户可见产物 |

### 6.2 任务清单约束

`write_todos` 工具按 Claude Code Todo 实践增加约束：

| 约束 | 说明 |
|------|------|
| 数量上限 | 单次任务列表不超过 32 项，超出返回错误提示合并或精简 |
| 描述约束 | 每个任务项一句话描述、包含完成标准（校验规则：描述长度 ≤ 50 字，含"完成/验证/确认"等验收语义引导，不强制校验） |
| 状态流转 | pending / in_progress / completed 三态；已完成项保留在列表底部作为过程记录 |
| 更新时机 | 每完成一个步骤即更新；任务清单状态随推理步骤持久化，用户可回看执行轨迹 |
| 计费边界 | 任务清单是规划辅助能力，不单独计费，Token 消耗并入推理 |

## 7. 模块间协作

| 集成点 | 说明 |
|--------|------|
| 多步推理 | 工具调用由推理循环调度，`before_model` 钩子触发 MCP 命名空间预筛选；高风险操作确认复用 interrupt 机制，详见 [后端实现-多步推理](./后端实现-多步推理.md) |
| 智能体管理 | 工具按 Agent 配置（Skills/MCP 命名空间/文件权限）装载，详见 [后端实现-智能体管理](./后端实现-智能体管理.md) |
| 智能调度 | 算法推荐、批量处理工具直接调用业务服务，详见 [后端实现-智能调度](./后端实现-智能调度.md) |
