# AI 对话模块 - 后端实现设计（能力扩展）

## 1. 文档概述

本文档描述 F-M08-006 能力扩展的后端实现，包括工具执行体系（deepagents 内置工具 + dehaze 业务工具）、工具调用生命周期与可见性、高风险操作确认、MCP 工具命名空间预筛选、搜索与代码执行、虚拟文件系统与任务清单约束、Skills 管理。

### 1.1 设计思想

#### 设计动机

能力扩展是 AI 对话从"会聊天"走向"能干活"的桥梁，本功能域的根本矛盾是：**Agent 能力的可获得性**与**上下文资源的有限性**之间的张力。

一方面，Agent 要能干平台的所有活（去雾、评估、推荐、搜索、执行代码），工具种类注定越来越多；另一方面，LLM 上下文窗口有限，数万个 token 的工具定义塞进每一轮调用，既贵又挤占对话空间。若全量注入工具，简单问题被工具定义淹没，Token 成本失控；若不全量注入，复杂任务又找不到可用工具。

本功能域的设计目标：**让 Agent 在需要时能发现任何能力，但只在需要时加载对应的工具——能力无限可得，上下文按需供给**。

#### 核心设计原则

| 原则 | 说明 |
|------|------|
| 能力工具化 | 所有系统能力（业务 API、文件操作、搜索、代码执行、工作流指令、子 Agent）统一以"工具"形态接入，由 LLM Function Calling 统一调度。推理核心不感知具体能力，新增能力不改推理循环 |
| 按需加载 | 工具定义不全量注入：MCP 按命名空间预筛选、Skills 渐进式加载（只加载名称描述，需要时再加载指令）。上下文只承载"当前任务相关"的工具 |
| 多源统一 | deepagents 内置工具（虚拟文件系统/TodoWrite/task）与 dehaze 业务工具（推荐/批量/MCP/Skills）在同一个工具列表中供 LLM 决策，来源透明 |
| 高频直连 | 算法推荐、批量处理等高频路径绕开 MCP 网络开销直接调用业务服务；低频通用 API 走 MCP 动态发现。性能与扩展性按使用频率分层取舍 |

#### 关键架构取舍

| 取舍点 | 方案对比 | 选择与理由 |
|--------|---------|-----------|
| 工具注入策略 | 全量注入所有工具定义 vs 命名空间预筛选 | 选预筛选。全量注入数万个 token 的工具定义会挤占上下文预算；`before_model` 钩子按用户意图预筛选 1-2 个命名空间，典型请求节省 83%-99% 上下文（详见 §3.2） |
| 工具接入方式 | 直接服务调用 vs MCP 网关调用 | 两者并存。高频路径（算法推荐、批量处理）绕开 MCP 网络开销直接调用业务服务；通用路径经内部 MCP 能力网关动态发现，换取"新增 API 零改动"的扩展性 |
| Skill 加载粒度 | 全量注入完整指令 vs 渐进式加载（名称→指令） | 选渐进式。启动只注入名称+描述（几十 tokens），LLM 判断需要时通过 `skill_load` 工具加载完整指令，避免无关 Skill 挤占上下文 |
| 工具来源组织 | 本地维护工具注册表 vs MCP 网关作为注册表 | 选后者。内部 MCP 能力网关读取后端 OpenAPI 自动解析所有 API，AI 对话模块只需调用 MCP 的 3 个元 tool，无需本地维护注册表，新增 API 后重启网关即自动发现（详见 §3.3） |

#### 总体规划

能力扩展是"能力层（工具）"，位于推理引擎与底层业务系统之间：

```
多步推理（LLM Function Calling 决策调用哪个工具）
    ↓
能力扩展（工具执行体系）
    ├── deepagents 内置工具（虚拟文件系统/TodoWrite/task）
    ├── dehaze 业务工具（推荐/批量/评估，高频直连）
    ├── MCP 工具（通用 API 动态发现，命名空间预筛选）
    └── Skills（工作流指令包，渐进式加载）
    ↓
底层系统（图像处理/指标评估/算法推荐/文件/搜索/沙箱）
```

推理引擎只负责"决策"，能力扩展只负责"分发"，底层系统只负责"执行"，三层职责互不侵入。

## 2. 工具执行体系

工具调用通过 LLM Function Calling 统一调度。deepagents 内置虚拟文件系统工具（`read_file`/`write_file`/`edit_file`/`ls`/`glob`/`grep`）、TodoWrite（`write_todos`）、子 Agent 调用（`task`）等工具，dehaze 业务工具（`algorithm_recommend`/`batch_process`/`mcp_*`/`skill_load`）通过 `DehazeToolsBuilder` 按 Agent 配置装载，与 deepagents 内置工具合并：

| 工具来源 | 工具名 | 执行器 | 说明 |
|---------|--------|--------|------|
| deepagents 内置 | `read_file`/`write_file`/`edit_file`/`ls`/`glob`/`grep` | `FilesystemMiddleware` + `StateBackend` | 虚拟文件系统，基于 LangGraph State，不操作真实磁盘；工作区容量限制见 §6.1 |
| deepagents 内置 | `write_todos` | `TodoListMiddleware` | 维护结构化任务清单（pending/in_progress/completed）；数量上限与粒度约束见 §6.2 |
| deepagents 内置 | `task` | `SubAgentMiddleware` | 调用子 Agent 执行隔离子任务，返回结果摘要 |
| dehaze 业务 | `algorithm_recommend` | `RecommendationService`（直接服务调用） | 算法推荐 + interrupt 等待用户确认 |
| dehaze 业务 | `batch_process` | `prediction_service`（直接服务调用，SSE 推送进度） | 批量处理 |
| dehaze 业务 | `skill_load` | `SkillManager`（加载指令注入 system_prompt） | Skills 渐进式加载 |
| dehaze 业务 | `mcp_lookup_tool` / `mcp_execute_tool` | `McpGatewayClient`（连接内部 MCP 能力网关） | MCP 工具动态发现与执行 |

**工具装载策略**：
- dehaze 业务工具通过 `DehazeToolsBuilder` 按 Agent 配置（Skills/MCP 命名空间）装载，与 deepagents 内置工具合并
- deepagents 内置工具默认全部可用，通过 `HarnessProfile.excluded_tools` 移除不需要的工具
- 工具定义采用 OpenAI Function 定义格式，Anthropic 适配在 `DehazeChatModel` 内完成

**直接服务调用 vs MCP 调用**：算法推荐、批量处理是高频路径，绕开 MCP 网络开销直接调用业务服务；其余通用 API 调用经内部 MCP 能力网关动态发现，新增后端 API 后重启网关（重新加载 OpenAPI）即自动发现，AI 对话模块无需修改代码。

**图片地址归属校验**：`algorithm_recommend` / `batch_process` 的 `image_url(s)` 由 LLM 给出，预测侧会按该地址下载图片。`validate_owned_image_url` 只放行本系统存储 baseUrl 下、且 `sys_file` 归属当前用户的地址，其余一律拒绝——否则 LLM 可诱导服务端请求任意（含内网）地址或处理他人图片。

**Skills 渐进式加载**：
- 启动时只加载 Skills 的名称和描述（几十 tokens），不加载完整指令
- LLM 判断需要某个 Skill 时，通过 `skill_load` 工具加载完整指令
- Skill 指令中可引用其他工具（如"调用 MCP 的评估工具获取指标"），形成 Skills + 工具的协同

### 2.1 工具调用生命周期与可见性

工具调用让用户"看到 AI 在做什么"，其生命周期记录通过现有 SSE 事件承载，不新增事件类型：

| 阶段 | 承载方式 | 说明 |
|------|---------|------|
| 调用发起 | `content_block` type=`tool_use` | 记录工具名与参数流式增量，前端渲染 ToolMessage（默认折叠） |
| 执行状态 | `thought` 事件 `status` 字段 | `running` / `success` / `error`，前端按状态更新徽标与结果摘要 |
| 完成记录 | `thought` 事件完整字段 | `{tool, toolInput, observation, status, latencyMs}` 作为工具调用审计记录持久化到消息推理步骤 |

**工具调用审计**：每次工具调用的完整记录（工具名、参数、结果摘要、状态、耗时）随消息的推理步骤持久化，用户可在消息详情回看"AI 刚才做了什么"，同时供安全审计与问题排查。

### 2.2 高风险操作确认

对影响范围大或不可逆的操作（批量删除、覆盖写文件、执行任意命令等），执行前须征求用户确认。复用多步推理的中断确认机制（interrupt 事件 type=`confirm` + `data.confirmKind` 子类型，详见 [后端实现-多步推理 §8.1](../多步推理/后端实现.md)）：

```
工具被判定为高风险（按操作类型 + Agent 权限配置判定，见智能体管理文件权限规则）
    ↓
工具执行节点不直接执行，改为抛出 interrupt(type=confirm, data.confirmKind=tool_permission|dangerous_op)
    ↓
前端渲染确认卡片（操作内容 + 影响范围 + 修改参数入口）
    ↓
用户确认/修改 → 复用消息发送接口 resume 参数恢复推理，按确认后的参数执行
用户拒绝 → 中断取消，LLM 收到"用户拒绝"反馈，调整方案或说明
```

**confirm 子类型（`ConfirmKind`，决定 resume 的恢复动作）**：

| confirmKind | 触发方 | resume 恢复动作 |
|-------------|--------|----------------|
| `tool_permission` | `DehazeHooksMiddleware` 工具权限不足 | 确认通过后**重放该工具调用**（否则 LLM 视为失败重试会再次触发中断形成循环）；拒绝则返回拒绝说明 |
| `dangerous_op` | `dehaze_tools_builder` Shell / 高风险 Python 代码执行 | 确认通过后重放沙箱执行；拒绝则返回"用户拒绝了该命令/代码的执行" |
| `algorithm_recommend` | `algorithm_recommend_service` 算法推荐 | 确认后提交推荐正向反馈，确认结果透传给中断点（见会话与消息 §5.5） |

> 中断点**只在 resume 成功后清理**（`ReasoningService.resume` 末尾 `clear_interrupt`）：子类型 handler 不得提前清理，否则 resume 中途失败时中断点已丢，消息永久挂起、用户无法再次确认重试。

> 判定规则：写操作（覆盖已有文件）、批量/删除类操作、任意命令执行（Shell）默认需确认；Python 命中网络访问、子进程/系统命令、沙箱外文件读写时按 Shell 同等级确认；只读查询类操作（读文件、检索、计算）不触发确认。

### 2.3 连续失败保护

同一工具连续调用失败达到上限后停止调用，避免无效重试消耗资源（对齐 Claude Code 重试退避实践）：

| 规则 | 说明 |
|------|------|
| 单次失败 | 记录失败原因并作为 tool 消息反馈给 LLM，由 LLM 决策重试 / 换工具 / 跳过 |
| 连续失败上限 | 同一工具同一推理内连续失败达 3 次，将该工具从当前可用工具列表临时剔除，并提示 LLM 更换能力 |
| 跳过不计数 | 工具未真正执行（`_dehaze_status=3`，服务不可用等）不计入连续失败，避免可用工具被误剔除 |
| 恢复 | 会话级恢复（新推理轮次重置失败计数），或用户明确要求后恢复该工具 |

计数按会话隔离：`conversation_id` 优先，缺失时退回 `message_id`/`agent_id` 独立键——中间件实例随图缓存共享，统一兜底桶会让互不相关的调用互相禁用工具。

#### 2.3.1 工具返回校验

工具返回数据在进入推理上下文前做格式与完整性校验（对齐需求规格 §2.6.10 工具返回校验），防止脏数据/格式错误污染推理：

| 校验 | 实现要点 |
|------|---------|
| 格式校验 | 按工具声明的返回 schema 校验结构，格式不符返回标准化错误（`RETURN_SCHEMA_ERROR`） |
| 完整性 | 必填字段缺失校验、超大返回截断保护（复用 ResponseTruncator） |
| 注入拦截 | 返回内容过注入检测（与上下文管理注入内容安全校验衔接，命中截断该片段） |
| 失败处理 | 校验失败以标准化错误作为 tool 消息回传，LLM 决策重试/换工具/跳过，与连续失败保护（§2.3）衔接 |

## 3. MCP 工具命名空间预筛选

### 3.1 机制说明

MCP 工具预筛选由 `before_model` 钩子承担（钩子机制详见 [架构与公共 §4.4 生命周期钩子](../后端实现-架构与公共.md)），负责按用户意图预筛选工具的加载范围：

```
每次 LLM 调用前（before_model 钩子）：
    ↓
Step 1: 调用 MCP 网关 tools/list（无 expand）获取命名空间摘要
  - 返回 8 个分组摘要（name + description + tool_count），总共 ~160 tokens
  - 缓存摘要结果 5 分钟（网关工具清单在启动时从 OpenAPI 一次性加载，无定时同步）
    ↓
Step 2: 意图匹配（规则预判，不调 LLM）
  - 从用户消息提取关键词
  - 匹配命名空间：{"去雾/处理/增强" → image_processing, "评估/PSNR/SSIM" → evaluation, "算法/推荐" → algorithm, ...}
  - 匹配 1-2 个命名空间
    ↓
Step 3: 展开匹配的命名空间
  - 调用 MCP 网关 tools/list（expand=[matched_namespaces]）
  - 获取匹配命名空间内 tool 的完整定义（name + description + inputSchema）
  - 典型：1-2 组 × 5-8 个工具 × 500 tokens = 2,500-8,000 tokens
    ↓
Step 4: 组装上下文（注入展开后的工具定义到 system prompt 的 tools 部分）
    ↓
如果意图无法匹配任何命名空间（模糊请求）：
  - 只注入命名空间摘要 + tool_search 工具的完整定义
  - LLM 需要时自行调用 tools/search 发现工具
```

### 3.2 效果对比

| 场景 | 全量注入 | 预筛选后 | 节省 |
|------|---------|---------|------|
| "PSNR是什么" | 50,000 | 160（仅摘要） | 99.7% |
| "帮这张图去雾" | 50,000 | 160 + 4,000 = 4,160 | 91.7% |
| "去雾并评估" | 50,000 | 160 + 8,000 = 8,160 | 83.7% |

### 3.3 MCP 调用流程

1. LLM 通过 function calling 决定调用 `mcp_lookup_tool` 工具（参数：`query`）
2. 工具执行节点调用 `mcp_gateway_client.lookup_tool(query)` 搜索匹配的后端 API，结果作为 tool 消息回传给 LLM
3. LLM 决定调用具体 MCP 工具时，通过 `mcp_execute_tool` 工具（参数：`tool_name`、`arguments`）触发 `mcp_gateway_client.execute_tool(tool_name, arguments)` 调用后端 API

**命名空间授权落到目标工具名**：`mcp_execute_tool` 以网关 M2M 密钥可调用网关任意工具，护栏（`GuardrailMiddleware.awrap_tool_call`）按其入参 `tool_name` 的命名空间前缀校验 Agent 已授权命名空间，越权直接拦截；`mcp_lookup_tool` 仅做检索，不参与校验。

**为什么不需要本地工具注册表**：

内部 MCP 能力网关本身就是工具注册表，它读取后端 OpenAPI 文档自动解析所有 API（网关启动时一次性加载，无定时同步）。AI 对话模块只需调用 MCP 的 3 个元 tool 即可，无需在本地维护工具注册表。新增后端 API 后重启网关即自动发现，无需修改 AI 对话模块代码。

## 4. Skills 管理（SkillManageService）

Skill 遵循**业界 Agent Skills 规范**（对齐 Anthropic Agent Skills / agentskills 开放规范）：一个 Skill 是一个目录，至少含 `SKILL.md`（YAML frontmatter + Markdown 指令正文），可选 `reference/`、`script/`、`assets/`、`README.md`；**通过压缩包（zip）上传**，前端不再逐字段表单创建。规范详见需求规格 §2.6.11.1。

SkillManager 承担 Skill 的执行职责（三级渐进披露：元数据→指令→资源，见 §2 工具执行体系）。SkillManageService 负责管理侧（F-M08-006 中的 Skills 管理部分）：

| 管理操作 | 职责 | 业务规则 |
|---------|------|---------|
| Skills 列表查询 | 返回可用 Skills（名称、描述、适用场景、启用状态） | 所有用户可查询；加载到 Agent 时仅返回启用项 |
| Skill 上传 | **zip 压缩包上传**，自动解析 SKILL.md frontmatter + 校验 | 需管理员权限；frontmatter/命名/目录名一致性/脚本同源策略/容量校验通过后入库，**入库即禁用态** |
| Skill 创建 | 创建自定义 Skill（遵循规范的最小目录：SKILL.md） | 与上传等效，走同一套校验；**入库即禁用态** |
| Skill 启停 | 管理员启用/禁用 Skill | 禁用后不再加载到 Agent 工具列表；运行中的实例不受影响 |
| Skill 更新 | 管理员更新名称/描述/场景/指令（`PUT /{id}` JSON） | 名称变更校验唯一性；更新后新会话生效，进行中的会话沿用旧版本；资源文件不改由前端重传压缩包 |
| Skill 删除 | 管理员删除 Skill（软删除） | 校验是否被 Agent 关联，有则提示先解绑；级联清理对象存储资源与文件清单 |
| Skill 试运行 | 输入测试数据，**以 Skill 指令为系统提示词真实推理一次** | 需管理员权限；独立调试会话，不入库不推送；需先启用 |
| Skill 市场 | 查看市场目录（预设/共享 Skill），将自建 Skill 共享至市场 | 市场目录由平台维护；共享需先启用 |

**Skill 管理与执行的关系**：

| 关注点 | 归属 |
|--------|------|
| Skill 的存储、CRUD、启停 | SkillManageService（本节） |
| Skill 的渐进式加载、按步骤执行 | SkillManager（§2 工具执行体系） |

SkillManageService 维护 Skill 元数据与文件内容，SkillManager 启动时从 SkillManageService 获取启用列表（仅名称+描述），LLM 判断需要时通过 `skill_load` 工具向 SkillManager 请求加载 SKILL.md 指令（及按需的资源文件）。

**数据模型**：`sys_ai_skill` 主表承载元数据（`name`/`description`/`scene`/`status`/`source`/`market_shared` + frontmatter 可选字段 `license`/`compatibility`/`metadata`/`allowed_tools`）；`sys_ai_skill_file` 子表只承载清单（`skill_id`/`path`（相对 SKILL 根目录）/`file_size`/`file_type`），`SKILL.md` 正文存入 `sys_ai_skill.instruction`，其余文件（`reference/`、`script/`、`assets/`、`README.md`）内容写对象存储、按 path 存清单行。

**资源对象 key 策略**：对象 key = `skills/{skill_id}/{相对路径}`。key 用 `skill_id` 而非 `name`——`name` 可通过更新接口修改，按 name 定位会让改名后的资源与 Skill 脱钩。历史存量按 name 存的对象由启动期 `migrate_legacy_object_keys` 一次性迁移（幂等，迁完即删旧对象；name 恰为纯数字且等于 id 时新旧 key 重合，跳过以免自删）。

**zip 上传解析流程**：
```
接收 zip（multipart） → 成员预检（防路径穿越：规范化路径，禁止 .. 与绝对路径）
  + zip 炸弹防护：文件数 ≤200、解压后总量 ≤10MB（读内容前判定）、压缩包 ≤2MB
    ↓
定位 SKILL.md（根目录或唯一子目录，取其目录名作为 skill name 候选；正文 ≤100KB）
    ↓
解析 YAML frontmatter → 校验：
  - name：≤64 字符、小写字母数字连字符、非首尾连字符、无连续连字符
  - name 与目录名一致
  - description：非空且 ≤1024 字符
  - 危险操作拦截（SKILL.md 正文 + 脚本资源）
    ↓
脚本资源同源策略扫描（script/*.sh|*.bash|*.py|*.js）——命中即**整包拒绝**：
  - 统一过破坏性命令正则（与 SKILL.md 正文同源）
  - .sh/.bash 逐行过沙箱 check_command_policy（白名单 + 解释器禁令）
  - .py 过沙箱 check_python_risk（网络/子进程/沙箱外文件）
    ↓
入库：sys_ai_skill（元数据 + SKILL.md 正文，status=0 禁用） + 对象存储资源 + sys_ai_skill_file 清单
    ↓
skill_manager.refresh_index 刷新（元数据 + 指令缓存；禁用项不入索引）
```
越过单文件上限（500KB）、不在 SKILL 根目录内的成员不计入失败，以 `skippedFiles`（文件路径 + 原因）随详情返回；前端展示部分失败清单，其余文件正常入库。

**渐进披露（三级）**：`SkillManager.discover_skills()` 只返回启用项 `name`+`description`（~100 tokens）；`load_skill(name)` 返回 SKILL.md 指令全文（激活时）；`load_skill_file(name, path)` 按需返回 `reference/`/`script/`/`assets/` 文件内容（脚本可直接执行或返回给 LLM 引用）。

> **Python 端实现**：路由 `app/router/ai_skill.py`（prefix=`/api/v1/ai/skills`）——列表/详情（`GET /{id}`）/**上传**（`POST /upload`，multipart zip）/更新字段（`PUT /{id}`，JSON）/删除/启停（`PATCH /{id}/status`）+ 试运行（`POST /{id}/test`）+ 市场（`GET|POST /market`）+ 资源文件读取（`GET /{id}/file?path=`）。管理操作均需 `ai:skill:manage`。核心服务 `app/service/ai_skill_service.py`（`SkillManageService`）：`create_skill_from_zip`（解析+校验+入库）/`get_skill`/`get_skill_file`/`test_skill`/`list_market`/`share_to_market`/`migrate_legacy_object_keys`。市场共享由 `sys_ai_skill.market_shared`（0/1）承载。试运行复用 Agent 测试预览通路（`DeepAgentBuilder.build_from_snapshot` + 独立 `thread_id`）：Skill 指令作为 system_prompt，模型取 `AI_DEFAULT_MODEL`、配置取系统默认，返回 `{output, usage}`，不落库不推送。列表/详情含 `scene` 适用场景与 `agentCount` 被关联数。实体/仓储/表结构见 [数据库设计](../../../../02-系统架构/03-数据库设计.md) `sys_ai_skill` / `sys_ai_skill_file`。

## 5. MCP Server 管理（McpServerManageService）

McpServerManageService 承担外部 MCP Server 的接入与管理（F-M08-006 §2.6.13）。外部 Server 的工具经管理接入并配置命名空间后，在 **Agent 图构建时装载为原生 function calling 工具**（`McpExternalToolLoader` 按 Agent 关联命名空间过滤启用的外部 Server，装载为 StructuredTool，含参数 schema 映射、凭据鉴权头、SSRF 守卫与调用审计；单 Server 失败/超时降级为空，不阻塞构图）。§3 的命名空间预筛选文本块仅覆盖内部能力网关工具；外部工具以原生工具列表供 LLM 直接决策，不参与文本注入预筛选。

| 管理能力 | 职责 | 业务规则 |
|---------|------|---------|
| Server 注册 | 注册外部 MCP Server（名称/描述/传输协议/端点/鉴权方式），注册后可手动拉取工具清单 | 需管理权限 `ai:mcp:manage`；传输协议**仅支持 URL 型（streamable-http/sse）**，端点 URL 必填——stdio 无网络端点，拉取/运行时装载/健康探测三处均无法支持，注册入口已关闭（存量 stdio 行置禁用并在管理端提示改用 URL 型协议） |
| Server 启停 | 启用/禁用已接入 Server | 禁用后不参与运行时装载；进行中会话不受影响 |
| 工具与命名空间 | 查看 Server 工具清单，工具分组为命名空间供 Agent 关联 | 命名空间覆盖式更新（名称须字母开头、仅含字母/数字/下划线/连字符，≤64 字符）；组内工具名必须在该 Server 已拉取的清单内，否则拒绝并回显可用工具（拼错的工具名装载期静默失效、无法自查）；Agent 仅可访问关联命名空间（最小权限） |
| 凭据管理 | 外部服务 API Key 配置 | 加密存储（AES），合并式更新（未传字段保留原值）、不回显；不暴露给 LLM、不进日志；支持 `clear` 整体清除（凭据轮换/吊销） |
| 健康探测 | Server 连通性与延迟探测 | 探测请求携带 Server 凭据鉴权头（需鉴权的 Server 裸探测恒被 401 判离线）；结果写 `health` + `last_check_time`，异常显著标注，供管理端健康看板展示；另有 10 分钟周期巡检刷新启用中 Server（见下） |
| 调用审计 | 外部 MCP 工具调用记录持久化 | 复用工具调用审计机制（§2.1），记录谁/何时/调用什么/结果/耗时 |
| 市场 | 内置 MCP Server 预设目录，一键接入 | 市场预设由平台维护；接入即注册并拉取工具清单，拉取失败（异常/守卫拦截/空清单）置禁用 + offline 并保留原工具快照，不以"已启用"姿态出现 |

**传输协议取值校验（三端口径）**：`protocol_type` 合法集 `{streamable-http, sse}`，缺省 `streamable-http`。python 由 pydantic `Literal` 在请求校验阶段拒绝非法字面量（A0400）；go 无该层，由 `McpServerService.CreateServer/UpdateServer` 在 **service 层**白名单拦截 A0400；java 由 `AiMcpServiceImpl.createServer/updateServer` 同样在 service 层拦截 A0400。白名单保持 service 层单一信息源，不搬 `@Pattern` 到 DTO——否则拼错的协议名会直接落库，只在拉取/运行时装载/健康探测阶段静默失败（脏数据且难定位）。

**图缓存失效**：外部工具在 **Agent 图构建时**装载，而推理图按 `(agent_id, version_no, model_id)` 缓存。Server 启停、端点/协议/名称更新、凭据轮换与清除、命名空间变更、删除操作提交成功后统一清空图缓存（`defer_after_commit` 登记，回滚不失效）——否则已构建的图仍持旧工具集与旧凭据，禁用/删除的 Server 依旧可被调用。图可重建，全清代价可接受，不做按 Server 精确失效。

**跨端图缓存失效协议**：推理图是 python 运行面的进程内缓存，java/go 原生修改 MCP（共享 `sys_ai_mcp_*` 库）不会触发 python 重建图，已构图仍持旧工具集与旧凭据。三端约定：变更提交后向 Redis 频道 `cache:invalidation` 发布 `{type:"ai_graph_invalidate", senderId:"..."}`（无 `key` 字段，与 L1 失效消息共用频道、按 `type` 区分）——java 经 `AiCacheInvalidator.evictReasoningGraphs`（事务提交后回调）、go 经 `invalidateReasoningGraphs`；python 订阅端识别该 `type` 即清空本实例图缓存（多实例各自失效自己的图，`senderId` 自消费忽略）。python 自身变更除本地直接清图外同样广播，保证多 Worker 下各实例图缓存一致。

**与内部能力网关的关系**：系统内部 MCP 能力网关（元工具，读取后端 OpenAPI 自动发现内部 API）不通过本服务管理，作为内置工具来源保留（§3）；外部 Server 与内部网关并存为 Agent 的两类工具来源——外部工具图构建时装载为原生 function calling 工具，内部网关工具经命名空间预筛选文本注入 + 元工具动态发现，两者互不替代。

**安全约束**：外部 Server 的凭据与内部网关一致遵循最小权限、凭据保护、调用审计基线（需求规格 §2.6.10）；删除 Server 前校验是否被 Agent 关联，有则提示先解绑。端点访问统一 SSRF 守卫（市场预设白名单放行，其余仅 https 且禁内网，防 DNS 解析绕过）；健康探测禁止跟随重定向（30x 跳转目标未经校验，跟随即绕过端点防护），仅 2xx 判在线。外部工具运行时命名 `<namespace>_<tool>`（命名空间与远端工具名均净化为合法工具名片段），与 Guardrail 命名空间越权校验约定一致。

**Python 实现（mcp-core）**：Server 注册表/启停/健康/凭据承载于 `app/service/ai_mcp/ai_mcp_server_service.py`（`AiMcpServerService`），命名空间配置亦在此（覆盖式删旧插新）；工具拉取/市场/调用审计由 `app/service/ai_mcp/mcp_manage_service.py`（`McpManageService`）承载；运行时装载由 `app/service/ai_mcp/mcp_external_tool_loader.py`（`McpExternalToolLoader`）承载。凭据复用 `app/infrastructure/crypto/aes_cipher.py` 的 `encrypt` 做 AES 密文存储（`credentials` 存 JSON，键值均为密文，不落明文、不进日志，合并式更新：未传字段保留原值，`clear=true` 整体清除），Server 视图对象返回派生布尔 `credential_configured`（`credentials` 非空即已配置，凭据本身不回显）；健康探测走 `httpx`（超时 5s、禁内网 SSRF 防护、禁止跟随重定向、仅 2xx 判在线），**探测头复用 `build_mcp_auth_headers` 携带凭据**，失败降级 `health=offline` 不阻断管理流程；`app/service/ai_mcp/mcp_health_checker.py`（`McpHealthChecker`）为进程内 asyncio 周期任务（10 分钟，仅主 Worker 启动，与 GPU 指标采集器同口径——巡检频率低、无跨实例协调需求，不引入 XXL-Job），对启用中 Server 重跑探测刷新 `health`/`last_check_time`，单 Server 失败仅记 warning；删除 Server 前校验 Agent 命名空间关联，有则提示先解绑。实体/仓储/表结构见 [数据库设计](../../../../02-系统架构/03-数据库设计.md) §4.7 `sys_ai_mcp_*`。

| 能力 | 执行器 | 说明 |
|------|--------|------|
| 网络搜索 | `WebSearchTool` | 调用外部搜索服务，返回标题 + 摘要 + 来源链接；单次返回 Top 5-10 条 |

**搜索配额与降级**：

| 规则 | 说明 |
|------|------|
| 频率限制 | 网络搜索按用户维度限频（如 30 次/小时），超限返回错误提示用户 |

### 5.2 代码执行沙箱

代码执行在隔离沙箱中运行，与用户真实系统隔离，安全边界是产品红线：

| 维度 | 实现 |
|------|------|
| 隔离环境 | 受限子进程：工作目录为临时目录 + 资源限制（CPU/内存/进程数）；**容器级隔离（每会话独立实例）为部署演进项**，当前未实现 |
| 环境支持 | Python、Shell（沙箱内）等常见执行环境 |
| 环境隔离 | 子进程只继承运行必需环境变量（PATH/LANG 等），宿主 DB/Redis/对象存储/MCP 凭据一律不传入——Python 模式可 exec 任意代码，继承环境等于交出凭据 |
| 超时与资源 | 单次执行超时（默认 60s）+ 资源上限（CPU/内存/进程数），防止失控执行与资源耗尽 |
| 安全约束 | Shell 走**命令白名单**（白名单外、沙箱外路径——含引号包裹的绝对路径、输出重定向、命令替换、段首变量赋值一律拒绝）；白名单**不含解释器类命令**（`python`/`python3`/`awk`/`sed`，`python -c` 与 awk `system()` 可起子进程，放行即任意代码执行），执行代码一律走 python 通道；Python 的网络访问/子进程/沙箱外文件读写与 Shell 同级触发确认（见 §2.2） |
| 结果封装 | 标准输出/错误码/产物文件引用返回给 LLM；错误信息结构化（不暴露内部堆栈） |

**执行流程**：

```
LLM 决定调用沙箱执行工具（传入代码/命令 + 超时参数）
    ↓
Shell 命令 / Python 高危能力（网络、子进程、沙箱外文件）→ 触发 §2.2 确认流程
    ↓
沙箱执行（限时 + 限资源）
    ↓
返回 {stdout, stderr, exitCode, artifacts} 作为 tool 消息
    ↓
执行结果以工具调用条目展示（§2.1），LLM 汇总呈现
```
