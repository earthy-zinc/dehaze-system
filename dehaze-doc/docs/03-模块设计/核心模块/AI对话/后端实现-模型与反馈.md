## 2. 模型配置管理 (F-M06-007)

### 2.1 数据模型

#### sys_ai_model（AI 模型配置）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | bigint | 主键 |
| `provider` | varchar(32) | 模型提供商（openai;anthropic;deepseek;zhipu;qwen;other） |
| `model_id` | varchar(64) | 模型标识（如 gpt-4o;claude-3-5-sonnet;deepseek-chat） |
| `display_name` | varchar(128) | 显示名称 |
| `input_rate` | decimal(10,4) | 输入 Token 计费比例（以输入单价为基准 1.0） |
| `output_rate` | decimal(10,4) | 输出 Token 计费比例 |
| `cached_rate` | decimal(10,4) | 缓存命中 Token 计费比例（折扣价） |
| `max_context_tokens` | int | 最大上下文 Token 数 |
| `max_output_tokens` | int | 最大输出 Token 数 |
| `supports_multimodal` | tinyint | 是否支持多模态（图片视觉/文档理解/音视频理解） |
| `supports_tool_call` | tinyint | 是否支持工具调用 |
| `supports_streaming` | tinyint | 是否支持流式输出 |
| `supports_prompt_cache` | tinyint | 是否支持 Prompt 缓存（OpenAI/Anthropic 缓存优化） |
| `supports_structured_output` | tinyint | 是否支持结构化输出（JSON Schema 约束） |
| `fallback_model_id` | varchar(64) | 降级模型标识（主模型限流/宕机时自动切换） |
| `prompt_cache_prefix_len` | int | Prompt 缓存稳定前缀长度（用于 prompt 结构优化） |
| `status` | tinyint | 状态（1:启用;0:禁用） |
| `deleted` | tinyint | 逻辑删除标识 |

**索引设计**：
- `uk_model_id(model_id)`：唯一索引，model_id 为业务引用键
- `idx_provider(provider)`：优化按提供商筛选

**逻辑删除类别②**：model_id 为业务引用键，删除后不可复用。新建/改名查重必须绕过软删过滤查全表，命中即报"已被历史记录占用"。

### 2.2 模型 CRUD

#### 新增模型

```
管理员提交模型配置
    ↓
校验 model_id 唯一性（绕过软删过滤查全表）
  - 命中已删除记录 → 报"model_id 已被历史记录占用，不可复用"
    ↓
插入 sys_ai_model 记录
    ↓
清除模型缓存（ai:model:list, ai:model:{modelId}）
```

#### 更新模型

```
管理员更新模型配置（计费比例、能力标识等）
    ↓
更新 sys_ai_model 记录
    ↓
清除模型缓存
    ↓
注意：已使用该模型的会话和消息保持原记录，不影响历史
```

#### 删除模型

```
管理员删除模型
    ↓
校验是否有活跃会话正在使用该模型
  - 有 → 建议先禁用（status=0）而非删除，避免影响活跃会话
    ↓
软删除（deleted=1）
    ↓
清除模型缓存
    ↓
model_id 保留，后续不可复用
```

### 2.3 模型列表查询

```
查询可用模型列表
    ↓
SELECT * FROM sys_ai_model WHERE deleted = 0 AND status = 1 ORDER BY provider, display_name
    ↓
返回模型信息：
  - model_id, display_name, provider
  - 能力标识（supports_multimodal, supports_tool_call, supports_streaming）
  - 积分单价（input_rate, output_rate, cached_rate）
  - max_context_tokens, max_output_tokens
    ↓
根据用户 VIP 等级过滤：
  - 基础模型：所有用户可用
  - 进阶模型：VIP1+
  - 高端模型：VIP2+
```

### 2.4 模型选择与切换

#### 会话级模型绑定

```
用户在会话设置中选择模型
    ↓
更新 sys_ai_conversation.model = 新 model_id
    ↓
下一条消息使用新模型
    ↓
历史消息保持原 model 记录（每条消息记录实际使用的模型）
    ↓
积分按新模型的计费比例扣减
```

#### 模型能力校验

```
发送消息前校验模型能力
    ↓
如果消息包含文件附件（多模态输入）：
  - 校验模型 supports_multimodal = 1
  - 图片附件需模型支持视觉能力，文档/音视频附件需模型支持对应模态理解
  - 不支持 → 返回 A0601（模型不可用）
    ↓
如果消息需要工具调用：
  - 校验模型 supports_tool_call = 1
  - 不支持 → 返回 A0601
    ↓
校验通过 → 使用该模型发起推理
```

#### 默认模型

```
新建会话时确定默认模型：
  - 优先使用用户偏好默认模型（用户设置中配置）
  - 未配置偏好 → 使用平台默认模型
    ↓
平台默认模型从配置读取：ai.model.default = "gpt-4o-mini"
```

### 2.5 模型路由与降级

主模型不可用（限流 429、服务端错误 5xx、超时）时自动切换到 fallback 模型，保证可用性：

```
LLM 调用失败（429/5xx/超时）
    ↓
检查 sys_ai_model.fallback_model_id
    ↓
有降级模型：
  - 校验降级模型状态（status=1 且 supports 能力匹配）
  - 切换到 fallback_model_id 重新调用
  - 消息记录实际使用的降级模型（model 字段）
  - 积分按降级模型计费比例扣减
    ↓
无降级模型 或 降级模型也失败：
  - 推送 error 事件，消息标记为 status=3（失败）
  - error 记录"主模型和降级模型均不可用"
```

**降级链**：支持多级降级（A → B → C），每级模型的 `fallback_model_id` 指向下一级。降级时逐级尝试，全部失败才报错。

**能力匹配校验**：降级模型必须满足原模型的能力要求（多模态/工具调用/流式输出），不满足则跳过该降级模型继续寻找下一级。

### 2.6 Prompt Caching 优化

利用 OpenAI/Anthropic 的 Prompt Caching 能力降低成本和延迟。`cached_input_tokens` 字段记录缓存命中的 token 数，按 `cached_rate`（折扣价）计费：

```
组装 prompt 时优化结构（稳定前缀 + 动态后缀）：
    ↓
稳定前缀（可缓存部分，放在 prompt 头部）：
  - system_prompt（会话级，不变）
  - 长期记忆注入（低频变化）
  - 工具定义（工具列表 schema，不变）
  - 长度参考 sys_ai_model.prompt_cache_prefix_len
    ↓
动态后缀（不可缓存部分，放在 prompt 尾部）：
  - 会话摘要（偶尔更新）
  - 最近 N 轮消息（每轮变化）
  - 当前用户消息
    ↓
模型 supports_prompt_cache = 1 时：
  - 调用 API 时自动启用缓存（OpenAI 自动缓存，Anthropic 需 cache_control 标记）
  - 稳定前缀命中缓存，按 cached_rate 计费
  - 响应中返回 cached_input_tokens（缓存命中的 token 数）
    ↓
模型 supports_prompt_cache = 0 时：
  - 正常调用，cached_input_tokens = 0
```

### 2.7 结构化输出校验

工具调用参数和推理结果通过 JSON Schema 校验，防止 LLM 输出格式错误：

```
LLM 返回工具调用参数（tool_input）
    ↓
模型 supports_structured_output = 1 时：
  - 调用 API 时传入 JSON Schema 约束输出格式
  - API 保证返回的 JSON 符合 schema
    ↓
模型 supports_structured_output = 0 时：
  - LLM 自由输出 JSON 字符串
  - 服务端解析后用 JSON Schema 校验
  - 校验失败 → 记录错误，LLM 重试或降级处理
    ↓
校验通过 → 存入 sys_ai_agent_thought.tool_input
```

**应用场景**：
- 工具调用参数：按工具的参数 schema 校验
- 推理结果：按预期输出格式 schema 校验（如算法推荐结果的结构化格式）
- 批量处理摘要：按摘要 schema 校验

### 2.8 计费比例应用

```
推理完成后获取 token 用量
    ↓
从 sys_ai_model 读取模型的计费比例：
  - input_rate, output_rate, cached_rate
    ↓
换算积分：
  credits = inputTokens × inputRate
          + cachedInputTokens × cachedRate
          + outputTokens × outputRate
    ↓
示例：
  - 模型 GPT-4o：input_rate=1.0, output_rate=4.0, cached_rate=0.5
  - inputTokens=1000, cachedInputTokens=200, outputTokens=500
  - credits = 1000×1.0 + 200×0.5 + 500×4.0 = 1000 + 100 + 2000 = 3100
```

## 3. 消息反馈管理 (F-M06-008)

### 3.1 数据模型

#### sys_ai_message_feedback（消息反馈）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | bigint | 主键 |
| `message_id` | bigint | 消息 ID（仅 assistant 消息可反馈） |
| `user_id` | bigint | 用户 ID |
| `rating` | tinyint | 评分（1:点赞;-1:点踩） |
| `tags` | json | 预设标签（点赞:accurate/detailed/concise/creative;点踩:too_long/incorrect/irrelevant/harmful） |
| `comment` | TEXT | 反馈内容（可选） |
| `deleted` | tinyint | 逻辑删除标识 |
| `create_time` | datetime | 创建时间 |
| `update_time` | datetime | 更新时间 |

**索引设计**：
- `uk_message_user(message_id, user_id)`：唯一索引，保证同一用户对同一消息只有一条反馈

**逻辑删除类别①**：撤销后再次反馈走 upsert 复活（`INSERT ... ON DUPLICATE KEY UPDATE`），upsert 时需 `id=LAST_INSERT_ID(id)` 回填原行 ID。

### 3.2 反馈提交流程

```
用户对 assistant 消息提交反馈
    ↓
校验：
  - 消息存在且属于当前用户的会话
  - 消息 role = assistant（仅助手消息可反馈）
  - 消息发送时间在 30 天内（反馈时效）
    ↓
upsert 反馈记录：
  - INSERT INTO sys_ai_message_feedback (message_id, user_id, rating, tags, comment, deleted=0)
  - ON DUPLICATE KEY UPDATE rating=VALUES(rating), tags=VALUES(tags), comment=VALUES(comment), deleted=0, id=LAST_INSERT_ID(id)
    ↓
如果 rating = -1（点踩）：
  - comment 必填（改进建议）
  - 异步触发反馈驱动闭环（见 §3.7）
    ↓
返回反馈记录 ID
```

### 3.3 反馈查询

```
查询消息反馈状态
    ↓
SELECT * FROM sys_ai_message_feedback
WHERE message_id = ? AND user_id = ? AND deleted = 0
    ↓
返回反馈状态（rating, comment）
  - 无记录 → 未反馈
  - 有记录 → 返回 rating 和 comment
```

### 3.4 反馈撤销

```
用户撤销反馈
    ↓
UPDATE sys_ai_message_feedback SET deleted = 1
WHERE message_id = ? AND user_id = ?
    ↓
撤销后可重新反馈（走 upsert 复活）
```

### 3.5 反馈修改

用户修改反馈类型（点赞改点踩或反之）：

```
用户提交新的反馈（rating 与现有不同）
    ↓
走 upsert 更新：
  - ON DUPLICATE KEY UPDATE rating=VALUES(rating), comment=VALUES(comment), deleted=0
    ↓
原记录被更新，不插入新记录
```

### 3.6 反馈数据统计

反馈数据用于质量分析，不直接展示给用户：

| 统计维度 | 说明 |
|---------|------|
| 消息点赞率 | 某条消息的点赞数 / 总反馈数 |
| 模型满意度 | 按模型维度统计点赞率，评估模型效果 |
| 标签分布 | 统计各预设标签出现频率（如"too_long"占比高 → 提示词需精简输出） |
| 工具调用效果 | 关联推理步骤，统计工具调用后的消息反馈 |
| 负反馈分析 | 点踩的 tags + comment 内容分析，识别常见问题 |

### 3.7 反馈驱动闭环

用户反馈不仅用于统计，还驱动系统改进后续推理质量：

```
用户提交点踩反馈（rating=-1, tags=["too_long"], comment="回复太冗长"）
    ↓
异步触发反馈处理：
    ↓
1. 记忆提取：
   - 从点踩内容和 tags 提取用户偏好
   - 如 tags=["too_long"] → 语义记忆："用户偏好简洁回复"
   - 写入 sys_ai_memory，importance 加权（反馈来源 +10）
    ↓
2. 系统提示词优化（高频率反馈）：
   - 当某类负反馈标签累计超过阈值（如"too_long"出现 10 次）
   - 异步分析是否需要调整系统提示词
   - 如在 system_prompt 中增加"回复保持简洁"指令
   - 更新 sys_ai_conversation.system_prompt
    ↓
3. 工具选择策略调整：
   - 当某工具调用后频繁收到 negative 反馈（如"incorrect"）
   - 降低该工具在类似场景下的选择优先级
   - 或在工具描述中增加使用限制说明
```

> 反馈驱动闭环是 Reflexion 范式的被动触发版——不等待推理过程中的自我评估，而是从用户反馈中学习改进。

## 4. 计费集成

### 4.1 计费流程

```
消息推理完成
    ↓
MessageService 统计 token 用量
  - input_tokens, output_tokens, cached_input_tokens
    ↓
ModelService 换算积分
  - credits = inputTokens × inputRate + cachedInputTokens × cachedRate + outputTokens × outputRate
    ↓
更新 sys_ai_message.credits
    ↓
调用 BillingIntegration.record():
  - 写入 sys_ai_billing 记录
  - 扣减用户日/月配额
    ↓
推送 message.end 事件（含 token 统计、积分消耗）
```

### 4.2 配额校验

```
推理前预校验配额
    ↓
查询用户当前 VIP 等级
    ↓
获取日限额和月限额
    ↓
查询今日已用积分：ai:quota:daily:{userId}:{date}
查询本月已用积分：ai:quota:monthly:{userId}:{month}
    ↓
预估本次积分消耗（基于输入 token 估算）
    ↓
今日已用 + 预估 > 日限额？
  - 是 → interrupt（type=quota, data={已用, 限额, 提示="今日配额已用尽"}）
    ↓
本月已用 + 预估 > 月限额？
  - 是 → interrupt（type=quota, data={已用, 限额, 提示="本月配额已用尽，请升级 VIP"}）
    ↓
校验通过 → 继续推理
```

### 4.3 配额不足处理

```
配额不足触发 interrupt
    ↓
LangGraph 暂停 Agent，保存检查点
    ↓
推送 interrupt 事件：
  {
    "type": "quota",
    "data": {
      "used": 500000,
      "limit": 500000,
      "period": "monthly",
      "message": "本月 AI 对话配额已用尽（500,000/500,000 积分），请升级 VIP 以继续使用"
    }
  }
    ↓
前端展示配额不足提示 + 升级引导
    ↓
用户升级 VIP → 配额刷新 → 调用 resume 接口恢复推理
```

### 4.4 工具调用配额

工具调用的配额由底层 API 统一扣减，不在 AI 计费中重复记录：

| 工具调用 | 配额扣减位置 | 说明 |
|---------|------------|------|
| `process_image` | 预测 API | 扣处理次数（会员月度配额） |
| `evaluate_metrics` | 评估 API | 扣评估次数（会员月度配额） |
| 查询类工具 | 无 | 不扣配额 |

MCP 网关透传用户身份，底层 API 自行校验和扣减配额。配额不足时返回 4xx 错误，LLM 决定是否 interrupt 提示用户。
