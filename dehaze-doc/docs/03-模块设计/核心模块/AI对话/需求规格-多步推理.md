# AI 对话模块需求规格（多步推理）

## 功能域概述

多步推理是 AI 对话模块的核心执行引擎，Agent 根据任务复杂度自动选择最合适的推理范式（ReAct / Plan-and-Execute / Reflexion），通过理解-执行-观察-反思循环完成复杂任务，并配套成本、安全与中断恢复控制。

### 2.2 多步推理 (F-M08-002)

#### 2.2.1 功能描述

支持开放式对话的多步推理，Agent 根据任务复杂度自动选择最合适的推理范式（ReAct 边想边做 / Plan-and-Execute 先想后做 / Reflexion 反思迭代），通过理解-执行-观察-反思循环完成任务。

#### 2.2.2 推理能力

| 能力 | 说明 |
|------|------|
| 复杂度感知 | Agent 启动时评估任务复杂度，自动选择推理范式（简单问答直接回复、动态任务用 ReAct、多步任务用 Plan-and-Execute、高精度任务用 Reflexion） |
| 子任务分解 | 将复杂需求分解为多个子任务，标注依赖关系，独立子任务可并行执行 |
| 工具调用 | 通过能力扩展体系调用系统能力（系统工具、文件操作、搜索、代码执行、Skills、子智能体等） |
| 结果观察 | 观察工具返回结果，决定下一步操作 |
| 自我评估 | Reflexion 范式下评估结果质量（LLM 自评 + 规则校验 + 工具验证），不达标时反思改进 |
| 反思重试 | 工具调用失败或结果不理想时，分析根因修正策略重试 |
| 错误恢复 | 参数错误修正重试、超时降并行度、服务不可用切换备用工具或跳过 |
| 人工中断 | 需要用户确认时暂停（如算法选择确认、危险操作确认、VIP 付费确认） |
| 异步等待 | 长耗时任务（如图像处理）提交后中断等待，完成后恢复继续推理 |
| 子智能体协作 | 复杂任务委派给专用子智能体执行，支持并行执行和 Agent 团队协作 |

#### 2.2.3 推理范式

| 范式 | 核心思想 | 适用场景 |
|------|---------|---------|
| ReAct（边想边做） | Thought → Action → Observation 循环，每步只决定下一步 | 步骤不确定需动态调整的任务、实时问答 |
| Plan-and-Execute（先想后做） | 先规划完整计划再执行，支持并行和动态重规划 | 步骤可预见的多步骤任务、批量处理 |
| Reflexion（反思迭代） | 执行 → 评估 → 反思 → 改进循环，从错误中学习 | 需高精度输出的任务、可迭代优化的任务 |

> 三种范式可混合使用：顶层 Plan-and-Execute 分解任务，子任务按特性选择 ReAct 或 Reflexion。

> 设计依据：三种范式来源于大模型 Agent 领域已被业界验证的成熟工作（ReAct / Plan-and-Solve / Reflexion），本系统不做学术创新，而是工程化适配——通过复杂度评估自动路由范式，用配置化参数（步数/预算/阈值）控制成本，用能力扩展体系接入业务能力。三种范式各自的适用边界与已知局限是本系统设置步数护栏、动态重规划、提前终止等参数的依据。

#### 2.2.4 推理循环

```
用户描述需求
    ↓
评估任务复杂度，选择推理范式
    ↓
按选定范式执行（ReAct 循环 / Plan-and-Execute 规划执行 / Reflexion 迭代优化）
    ↓
观察结果，判断是否完成
    ↓
完成 → 生成响应返回用户
未完成 → 继续下一步（循环）
需要确认 → 暂停等待用户确认（确认/修改/拒绝后继续）
用户干预 → 修订剩余计划后继续（见 §2.2.6）
失败 → 错误恢复策略（修正重试 / 降级 / 跳过），失败与降级对用户可见
质量不达标（Reflexion）→ 反思改进，重新执行
```

#### 2.2.5 推理过程展示

推理过程展示帮助用户理解 LLM 的决策逻辑、建立信任。主流产品（ChatGPT / Claude / DeepSeek）的共识是**分层透明**：主窗口只呈现"简明步骤摘要"，详细推理链放入可展开的次级区域——既避免信息过载，又满足深度审查诉求（对齐 ChatGPT 推理轨迹可视化的"主窗口摘要 + 侧边栏/展开面板详情"模式）。

**展示内容**（用户可看到 LLM 的推理过程）：

| 内容 | 说明 |
|------|------|
| 推理范式 | 当前使用的推理范式（ReAct / Plan-and-Execute / Reflexion） |
| 思考内容 | 每一步 LLM 的思考内容（thinking 块），与正式回复分开展示 |
| 工具调用 | 调用的工具名称、输入参数、返回结果摘要（详见 [需求规格-能力扩展](./需求规格-能力扩展.md) §2.6.5 工具调用可见性） |
| 步骤信息 | 步骤序号和耗时 |
| 任务计划 | Plan-and-Execute 的任务计划（子任务列表、依赖关系、执行进度） |
| 反思过程 | Reflexion 的评估结果和反思内容（迭代改进过程） |
| 并行进度 | 并行执行的子任务进度（含子智能体） |

**展示层级（两级展开）**：

| 层级 | 默认状态 | 内容 |
|------|---------|------|
| 一级：步骤摘要 | 默认展开 | 简明步骤列表（每步一句话概括：做了什么、结果如何），让用户快速理解结论依据 |
| 二级：完整推理链 | 默认折叠 | 思考内容全文、工具调用详情、反思记录等，展开查看；标注"模型思考过程，非最终结论" |

**思考与正式回复的双流分离**：

- 推理模型的回复分为"思考过程"与"正式回复"两段内容流，在数据流与 UI 上完全分离
- 思考过程默认折叠为可展开条目（可标注思考耗时），正式回复直接展示
- 思考过程不参与复制、引用、朗读等操作；正式回复为主操作对象
- 思考内容按模型真实输出时间序渲染，不做"思考在前、回复在后"的强行重排（对齐 Claude thinking 块保序渲染实践）

**交互与合规**：

| 交互 | 说明 |
|------|------|
| 折叠/展开 | 思考过程默认折叠，提供"显示思考过程"快捷键；全局可在会话设置关闭思考过程展示（企业合规与隐私需求） |
| 成本透明 | 思考过程 Token 计入该条回复的 usage 展示，前端呈现消耗时包含思考 Token，避免用户困惑 |
| 展示边界 | 思考过程展示的是"过程摘要"，不暴露模型内部敏感策略；思考内容默认不写入共享日志 |
| 计划不等于承诺 | 任务计划展示标注"计划可能随执行修订"，避免用户将初始计划误解为最终承诺（对齐 Plan-and-Execute 的 Replanner 动态重规划） |

#### 2.2.6 任务计划展示与用户干预

Plan-and-Execute 范式下，任务计划不仅是内部状态，更应是用户可感知、可干预的协作对象——用户对"AI 接下来要做什么"有知情权与修正权（对齐 Plan-and-Execute 架构的规划器/执行器/重规划器设计，将 Replanner 的能力开放给用户参与）。

| 交互 | 说明 |
|------|------|
| 计划展示 | 任务计划以结构化清单呈现（子任务 + 依赖关系 + 预计执行顺序），执行中实时更新各子任务状态（待执行/执行中/已完成） |
| 计划可干预 | 执行前用户可查看并调整计划：删除不想要的步骤、调整步骤顺序、补充约束；调整后按新计划执行 |
| 动态重规划可见 | 执行中因失败/结果异常触发重规划时，新旧计划变更对用户可见（"计划已调整：因 xxx 失败，改为 yyy"） |
| 中途改需求 | 长任务执行中用户可提出新指令（如"跳过评估步骤"），Agent 据此修订剩余计划 |

**业务规则**：

| 规则 | 说明 |
|------|------|
| 干预窗口 | 计划生成后、执行前提供干预入口；执行开始后默认不再允许整体修改（可中途改需求） |
| 干预不阻塞 | 用户不干预时按初始计划自动执行，不强制等待确认（区别于 §2.2.8 的强制中断） |
| 计划修订记录 | 计划变更（用户干预或动态重规划）记录在推理过程中，用户可回看"计划是如何演变的" |

#### 2.2.7 成本与安全控制

| 限制 | 说明 |
|------|------|
| 最大推理步数 | 按推理范式差异化限制（ReAct: 20 步、Plan-and-Execute: 30 步、Reflexion: 15 步×3 次迭代），防止无限循环 |
| Token 预算 | 单会话累计 Token 超限后拒绝继续推理 |
| 配额预校验 | 每步执行前（含子智能体派发前）校验剩余配额并预扣本步预估消耗；剩余配额不足时触发中止策略 |
| 工具超时 | 单工具调用超过阈值自动失败，触发错误恢复策略 |
| 工具白名单 | Agent 只能调用注册的工具，防止未授权操作 |
| 危险操作确认 | 删除文件、执行危险命令前需用户确认 |
| 沙箱隔离 | 代码执行在受限环境中进行，有资源配额和路径白名单控制 |
| 并行度限制 | 并行执行子任务数上限（默认 5），防止资源耗尽 |

**配额不足中止策略与降级体验**：

| 场景 | 处理方式 |
|------|---------|
| 单步预扣失败 | 立即暂停推理，已完成步骤保留；前端展示"积分不足"卡片，支持升级 VIP 后从当前步骤继续 |
| 推理中途累计超额 | 停止后续步骤，已生成部分结果以摘要形式返回，避免用户白等 |
| 子智能体并行超额 | 召回未启动的子智能体，已完成子智能体结果保留并参与汇总；前端提示"部分子任务因配额不足未执行" |
| 降级继续 | 用户可选择跳过非关键步骤、切换积分单价更低的模型或减少并行度，按剩余配额完成核心目标 |

**子智能体并行计费呈现**：
- 主会话计费明细按子智能体维度分项展示（子智能体名称 + Token 数 + 积分），与主 Agent 消耗汇总为会话总消耗
- 前端推理过程面板实时展示各并行子智能体的累计消耗与配额占用
- 子智能体消耗归集到主会话配额，不单独占用额外配额

#### 2.2.8 中断与恢复

中断与恢复是 Human-in-the-Loop（人在回路）的产品化落地：Agent 在关键决策前"暂停"征询用户，用户掌控方向，Agent 负责执行。

| 场景 | 用户体验 |
|------|---------|
| 算法选择确认 | LLM 推荐算法后暂停，展示推荐理由供用户确认或修改 |
| 危险操作确认 | 高风险操作（删除、覆盖写、任意命令）执行前暂停，展示操作内容与影响范围供用户确认（详见 [需求规格-能力扩展](./需求规格-能力扩展.md) §2.6.5） |
| 配额不足 | 积分/配额耗尽时暂停，按 §2.2.7 中止策略处理（升级 VIP 或降级继续） |
| 异步任务等待 | 图像处理提交后暂停，前端展示处理进度，完成后自动恢复推理 |
| 用户主动中断 | 用户点击"停止"按钮，立即终止当前推理，已完成的步骤保留 |
| 断线重连 | 用户网络中断后重连，自动恢复到中断前的推理状态 |

**恢复体验**：

- 中断原因在中断点明确标注（等待确认 / 配额不足 / 任务处理中），用户离开页面后再次进入自动恢复到中断环节
- 用户确认、修改参数或拒绝后，推理从当前步骤继续，不重复已完成的步骤、不重复计费

**错误透明的用户告知**：

推理中的失败与降级对用户可见可解释，不静默吞错（对齐 Agent 错误处理的分层防御实践——重试/降级/断路器，且每层都向用户说明）：

| 场景 | 用户告知 |
|------|---------|
| 工具调用失败 | 推理链中展示失败原因与 Agent 的应对（重试/换工具/跳过），用户了解发生了什么以及系统如何应对 |
| 步骤降级 | 某步骤降级执行（如换模型、减并行度）时，向用户说明降级原因 |
| 整体失败 | 推理最终失败时，明确告知失败原因并给出下一步选项（重新生成 / 简化需求重试 / 联系支持） |
| 部分完成 | 配额不足等导致部分完成时，以摘要形式返回已完成结果，并说明未完成部分及原因 |

#### 2.2.9 设计依据

本功能域的产品交互设计对齐业界主流 Agent 产品的推理实践，做工程化取舍：

| 设计点 | 对标实践 |
|--------|---------|
| 推理范式 | ReAct / Plan-and-Solve / Reflexion 等业界验证的 Agent 范式，本系统通过复杂度评估自动路由、配置化参数控制成本，不重复学术创新 |
| 分层透明展示 | ChatGPT 推理轨迹可视化的"主窗口简明步骤摘要 + 侧边栏/展开面板详细审计轨迹"模式：兼顾快速消费与深度审查 |
| 思考与回复双流分离 | Claude Extended Thinking 的 thinking 块设计：thinking 与 text/tool_use 独立内容流，UI 层独立折叠区、保序渲染、思考不进入复制/引用 |
| 思考过程克制展示 | Claude Code 的 thinking 块 UI 策略：默认折叠 + "显示思考过程"快捷键 + 演示模式隐藏 + 企业可全局关闭；标注"非最终结论" |
| 计划可干预 | Plan-and-Execute 架构的 Replanner 理念产品化：把"动态重规划"开放为"用户可干预计划"，让用户对执行路径有知情权与修正权 |
| 人工中断恢复 | Human-in-the-Loop（人在回路）模式：Agent 在关键决策前暂停征询，中断原因明确标注、恢复不重复计费 |
| 错误透明告知 | Agent 错误处理的分层防御实践（重试/降级/断路器）：每一层降级都对用户可见可解释，不静默吞错 |
| 思考成本透明 | 思考 Token 计入 usage 展示（对齐 Claude thinking 计费实践），避免用户对消耗产生困惑 |

> 本功能域聚焦推理的范式选择、过程展示与中断控制；工具调用可见性与高风险操作确认见 [需求规格-能力扩展](./需求规格-能力扩展.md)，推理范式的后端实现（状态机、钩子、中断恢复机制）见 [后端实现-多步推理](./后端实现-多步推理.md)。
