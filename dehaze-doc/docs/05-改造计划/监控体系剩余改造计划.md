## 一、阶段 3：业务指标命名全面对齐

### 背景
当前三端业务指标命名各自独立，跨端聚合面板需要写多套 PromQL，不利于统一观测。

### 现状

| 维度 | Java | Python | Go |
|------|------|--------|-----|
| HTTP 请求耗时 | `http_server_requests_seconds` | `http_request_duration_seconds` | `http_server_requests_seconds`（已对齐） |
| 预测 | `dehaze_prediction_total` | `inference_*` | 未埋点 |
| 评估 | `dehaze_evaluation_total` | 未埋点 | 未埋点 |
| 缓存 | 未埋点 | `cache_metrics` | `multilevel/metrics` |
| GPU | 未埋点 | `gpu_metrics` | 未埋点 |
| 任务 | `dehaze_task_total` | `task_metrics` | 未埋点 |

### 改造内容
1. 统一前缀规范为 `dehaze_*`
2. Python 端 `inference_*` → `dehaze_prediction_*`、`dehaze_inference_*`
3. Go 端补齐业务指标埋点（预测、评估、任务）
4. 三端缓存指标统一为 `dehaze_cache_*`
5. GPU 指标仅在 Python 端保留（算法服务独有），不强制对齐

### 涉及文件
- `dehaze-java/src/main/java/com/pei/dehaze/config/MetricsConfig.java`
- `dehaze-python/app/metrics/` 全部模块
- `dehaze-go/pkg/server/gin/middleware/prometheus.go` 及业务 Service 层
- `dehaze-doc/docs/02-系统架构/06-部署架构.md` 监控指标章节

### 优先级
中。当前各端指标独立可用，跨端聚合是高级需求，可后置。

## 二、阶段 4.1：告警体系（AlertManager + Grafana Alerting）

### 背景
[06-部署架构.md](../02-系统架构/06-部署架构.md#L197-L209) 已定义告警阈值，但未实际配置告警规则和通知通道。

### 改造内容

#### 1. 部署 AlertManager
- docker-compose.yml 新增 `alertmanager` 服务
- prometheus.yml 新增 `alerting` 配置指向 AlertManager
- 新增 `config/alertmanager/alertmanager.yml` 通知规则

#### 2. 告警规则
按 [06-部署架构.md](../02-系统架构/06-部署架构.md) 已定义的阈值配置：

| 指标 | 阈值 | 持续 | 级别 |
|------|------|------|------|
| CPU 使用率 | > 85% | 5min | warning |
| 内存使用率 | > 90% | 5min | critical |
| 磁盘使用率 | > 85% | 10min | warning |
| Java 5xx 错误率 | > 5% | 2min | critical |
| P99 延迟 | > 5s | 5min | warning |
| MySQL 连接数 | > 80% max | 3min | warning |
| Redis 内存 | > 80% maxmemory | 5min | warning |
| 服务宕机 | up == 0 | 1min | critical |

#### 3. 通知通道
- 邮件（SMTP 配置）
- 可选：钉钉/企业微信 Webhook

### 涉及文件
- `docker-compose.yml`
- `config/prometheus/prometheus.yml`
- `config/prometheus/rules/*.yml`（新增告警规则）
- `config/alertmanager/alertmanager.yml`（新增）

### 优先级
低。个人/小团队项目告警噪音 > 价值，建议在实际负载下校准阈值后再配置。

### 启动方式

```powershell
# 启动新增的 exporter + 重启 Grafana
docker compose up -d node-exporter mysqld-exporter redis-exporter
docker compose restart grafana prometheus
```

启动后访问 `http://localhost:3001`（admin/12345678），在 Dehaze 文件夹下可看到 3 个自动加载的 Dashboard。

## 三、阶段 4.2：ELK 结构化日志接入

### 背景
ELK 容器已部署（docker-compose.yml 中 elasticsearch + kibana + logstash），但三端日志未结构化，无法有效检索分析。

### 改造内容

#### 1. 三端日志 JSON 化

| 端 | 当前 | 改造 |
|----|------|------|
| Java | logback 文本格式 | logback-spring.xml 配置 `LogstashEncoder` 输出 JSON |
| Python | loguru 文本格式 | loguru sink 配置 `serialize=True` 输出 JSON |
| Go | zap 文本格式 | zap 配置 `JSONEncoder`（可能已是 JSON，需确认） |

#### 2. Logstash Pipeline
- 新增 `config/logstash/pipeline/dehaze.conf`
- 输入：filebeat 或 syslog
- 过滤：解析 JSON，提取 trace_id、user_id 等字段
- 输出：Elasticsearch，按 `dehaze-logs-{yyyy.MM.dd}` 索引

#### 3. Filebeat 采集
- docker-compose.yml 新增 `filebeat` 服务
- 挂载三端日志目录
- 配置 `config/filebeat/filebeat.yml` 多输入源

#### 4. Kibana Index Pattern
- 创建 `dehaze-logs-*` 索引模式
- 可选：预置 Dashboard（错误日志趋势、慢请求 TopN）

### 涉及文件
- `dehaze-java/src/main/resources/logback-spring.xml`
- `dehaze-python/app/core/logger.py`
- `dehaze-go/pkg/logger/` 
- `config/logstash/pipeline/dehaze.conf`（新增）
- `config/filebeat/filebeat.yml`（新增）
- `docker-compose.yml`

### 优先级
低。日志和指标分离演进，先跑稳指标体系再上日志栈。

## 六、安全加固

### 背景
当前 `/metrics` 端点去鉴权靠网络层隔离，生产环境需更严格的安全保障。

### 改造内容

#### 1. /metrics 端点访问控制
- 方案 A：Prometheus 拉取时携带 Basic Auth 或 Bearer Token
- 方案 B：通过网络策略（NetworkPolicy）限制仅 Prometheus 容器可访问
- 方案 C：使用 docker network internal 限制仅监控网络可达

#### 2. Grafana 权限
- 配置 OAuth/SSO 登录
- 按角色分配 Dashboard 查看权限
- 敏感面板（如用户数据）单独权限控制

#### 3. 数据保留策略
- Prometheus: 配置 `--storage.tsdb.retention.time=30d`
- Grafana: 配置快照长期存储
- Elasticsearch: 配置 ILM 策略自动清理过期日志

### 优先级
中。生产环境上线前必须完成方案 A 或 B。
