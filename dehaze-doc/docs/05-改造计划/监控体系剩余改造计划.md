## 一、阶段 3：业务指标命名全面对齐 ✅

> **完成状态（2026-07-30）**：已完成。三端业务指标统一 `dehaze_` 前缀，Go 端补齐预测/评估/任务埋点，Java 端计数器接入服务层，Python HTTP 指标前缀修正。

### 背景
当前三端业务指标命名各自独立，跨端聚合面板需要写多套 PromQL，不利于统一观测。

### 最终命名（三端统一 `dehaze_` 前缀）

| 维度 | 指标 | 埋点端 |
|------|------|--------|
| HTTP 请求耗时 | `http_server_requests_seconds`（Java/Go）、`http_request_duration_seconds`（Python） | 三端 |
| 预测 | `dehaze_prediction_total{status}`、`dehaze_prediction_duration_seconds` | Java、Go |
| 推理（算法侧） | `dehaze_inference_requests_total{algorithm,status}`、`dehaze_inference_duration_seconds` | Python |
| 评估 | `dehaze_evaluation_total{status}`、`dehaze_evaluation_duration_seconds` | Java、Go |
| 缓存 | `dehaze_cache_hits_total`、`dehaze_cache_misses_total`、`dehaze_cache_loader_total` | Go、Python |
| GPU | `dehaze_gpu_*` | Python（算法服务独有，不强制对齐） |
| 任务 | `dehaze_task_total{task_type,status}`、`dehaze_task_duration_seconds` | Java、Go、Python |
| 文件上传 | `dehaze_file_upload_total` | Java |

### 实际改动

1. **Go**（新增 `dehaze-go/pkg/metrics/business.go`）
   - `PredictionService.executeAsync` 三个失败终态 + 成功终态 + 缓存命中路径 → `dehaze_prediction_*`
   - `EvaluationService.executeAsync` 三个失败终态 + 成功终态 → `dehaze_evaluation_*`
   - `TaskService.UpdateTaskResult/UpdateTaskStatus/CancelTask` → `dehaze_task_total{task_type,status}`、`dehaze_task_duration_seconds`
2. **Java**（服务层通过 `MeterRegistry` 直接创建计数器）
   - `PredLogAsyncTask` / `SysPredLogServiceImpl`（缓存命中）→ `dehaze_prediction_total`
   - `EvalLogAsyncTask` → `dehaze_evaluation_total`
   - `TaskServiceImpl.updateTaskCompleted/updateTaskFailed` → `dehaze_task_total`
   - `SysFileServiceImpl.saveFile` → `dehaze_file_upload_total`
   - `MetricsConfig` 删除未接入的冗余计数器 Bean，保留 `pythonCallTimer`
3. **Python**
   - `PrometheusMiddleware` 显式设置 `prefix="http"`（原默认 `starlette` 前缀导致 Grafana 面板查不到数据）
   - `dehaze_task_processing_total` → `dehaze_task_total`、`dehaze_task_processing_time_seconds` → `dehaze_task_duration_seconds`（与 Java/Go 对齐）
4. 文档：[06-部署架构.md 7.3 业务指标命名规范](../02-系统架构/06-部署架构.md)

## 三、阶段 4.2：ELK 结构化日志接入 ✅

> **完成状态（2026-07-30）**：已完成采集链路配置。**待办**：Kibana 中手动创建 `dehaze-logs-*` 索引模式（一次性操作）。

### 实际改动

1. **Logstash Pipeline**：`config/logstash/pipeline/dehaze.conf`（beats:5044 输入 → JSON 解析 → 字段归一化 → ES `dehaze-logs-{yyyy.MM.dd}` 索引），替换旧的 grok 版 `config/logstash/logstash.conf`（已删除）
   - 字段归一化：`error` 字符串转对象、`taskID`/`thread` 数值转字符串（避免 ES 动态映射冲突）；Go/Python `timestamp` 字段对齐为事件时间
2. **Filebeat 采集**：`docker-compose.yml` 新增 `filebeat` 服务，`config/filebeat/filebeat.yml` 三个 filestream 输入（挂载三端 logs 目录，NDJSON 解析并注入 `service` 字段）
   - 部署踩坑：部分云内核（如腾讯云）`/proc/stat` 的 `processes` 计数溢出为负数，go-sysinfo 解析失败导致 filebeat 无法启动，已通过容器内 bind 清洗快照（`config/filebeat/proc-stat`）规避，详见 docker-compose.yml 注释
3. Logstash 管道改为从仓库 bind mount，不再使用外部卷

# 2. 重建配置变更的服务（rabbitmq 插件 / minio 环境变量 / logstash 管道 / prometheus 规则）
docker compose up -d --force-recreate rabbitmq minio logstash prometheus

# 3. GPU 监控（需 NVIDIA GPU + nvidia-container-toolkit）
docker compose --profile gpu up -d dcgm-exporter

# 4. 验证
