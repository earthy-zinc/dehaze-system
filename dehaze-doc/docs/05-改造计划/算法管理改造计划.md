# 算法管理模块文件存储路径架构分析

## 一、现状核查（实现 vs 文档承诺）

在评估前必须澄清一个关键事实：**文档承诺的架构与实际代码实现严重不一致**，这是后续所有问题的根因。

### 1.1 文档承诺（[后端实现.md](file:///e:/DehazeSystem/dehaze-doc/docs/03-模块设计/核心模块/算法管理/后端实现.md#L74) 第 74 行、第 383-389 行）

> 模型文件存储委托给文件管理模块的 `FileService`，存储路径通过 `PathBuilder` 生成（传入自定义前缀 `/models/{algorithmId}/{version}/`）
>
> | 文件类型 | 路径格式 | 说明 |
> | 模型文件 | `/models/{algorithmId}/{version}/{filename}` | 按算法/版本分目录 |

### 1.2 实际实现

| 维度 | 文档承诺 | 实际代码 |
|------|---------|---------|
| 模型文件存储 | 委托 `FileService` → `StorageService`（MinIO） | 直接读本地 `trained_model/` 目录，**未走 FileService** |
| 路径生成 | `PathBuilder` 生成 `/models/{id}/{version}/{file}` | 硬编码 `MODEL_PATH = PROJECT_PATH/trained_model`（[algorithm/config.py:21](file:///e:/DehazeSystem/dehaze-python/algorithm/config.py#L21)） |
| `path` 字段用途 | 存储对象键 | **实际被预测流程忽略**，仅 CRUD 中做 `isFile()` 检查 |
| `import_path` | 代码导入路径 | 实际承担了"定位模型文件"的职责（通过模块名推导目录） |
| 版本隔离 | 路径含 `{version}` | 完全无版本隔离，同算法多版本会覆盖 |

## 二、核心缺陷分析

### 2.1 致命缺陷：`path` 字段在预测链路中是死字段

这是最严重的问题。查看 [prediction_service.py:474-516](file:///e:/DehazeSystem/dehaze-python/app/service/prediction_service.py#L474-L516) 的 `_run_dehaze` 方法：

```python
module_name = import_path  # algorithm.AECRNet.run
# ...剥离前缀后缀得到 AECRNet
model_dir = Path(algorithm_config.MODEL_PATH) / module_name  # trained_model/AECRNet
model_files = list(model_dir.glob("*.pth")) + list(model_dir.glob("*.pt"))
model_path = str(model_files[0]) if model_files else ""  # 取第一个！
```

**`algorithm.path` 字段（如 `AECR-Net/NH_train.pk`）在整个预测流程中从未被读取**。Python 通过 `import_path` 反推模块名，再到 `MODEL_PATH/{模块名}/` 下 glob 取第一个 `.pth/.pt` 文件。

**直接后果**：
- 数据库 `path` 字段对预测无任何约束力，运维改了它不会生效
- `.pk` 后缀的模型（如 AECR-Net 的 `DH_train.pk`、`ITS_train.pk`、`NH_train.pk`）根本不会被 glob 匹配到，依赖 `path` 字段才能区分的算法在当前实现下要么靠运气，要么靠 `ALGORITHM_REGISTRY` 硬编码兜底

### 2.2 致命缺陷：多模型变体算法会加载错误权重

种子数据中 CMFNet 有 3 个子算法（[data.sql:397-414](file:///e:/DehazeSystem/config/sql/data.sql#L397-L414)）：

| id | name | path | import_path |
|----|------|------|-------------|
| 7 | 去雾模型 | `CMFNet/dehaze_I_OHaze_CMFNet.pth` | `algorithm.CMFNet.run` |
| 8 | 去模糊模型 | `CMFNet/deblur_GoPro_CMFNet.pth` | `algorithm.CMFNet.run` |
| 9 | 去雨模型 | `CMFNet/deraindrop_DeRainDrop_CMFNet.pth` | `algorithm.CMFNet.run` |

三者 `import_path` 完全相同，`_run_dehaze` 会 glob 到同一目录下的 3 个 `.pth` 文件并取 `[0]`，**去雾/去模糊/去雨任务可能加载到同一权重文件**。这是真实存在的 bug，不是潜在风险。DehazeFormer、LKDNet、MixDehazeNet、MB-TaylorFormer、MSFNet、WPXNet、CFEN-ViT-Dehazing 等都有类似的多变体结构。

### 2.3 可靠性缺陷：CRUD 路径校验形同虚设

Java [SysAlgorithmServiceImpl.java:119](file:///e:/DehazeSystem/dehaze-java/src/main/java/com/pei/dehaze/service/impl/SysAlgorithmServiceImpl.java#L119) 与 Python [algorithm_service.py:105](file:///e:/DehazeSystem/dehaze-python/app/service/algorithm_service.py#L105)：

```java
if (FileUtil.isFile(sysAlgorithm.getPath())) { ... }
```
```python
if await asyncio.to_thread(os.path.isfile, data["path"]): ...
```

种子数据 `path` 存的是 `AECR-Net/NH_train.pk` 这类相对路径，`isFile()` 是否为 true 完全取决于**进程当前工作目录**。Java 后端 cwd 与 Python 后端 cwd 不同，且都不在 `trained_model/` 下，导致：
- 创建算法时 `size` 字段几乎永远为 null（校验失败，跳过赋值）
- 校验逻辑形同虚设，无法发现真正无效的路径

### 2.4 跨环境部署缺陷：本地文件系统强耦合

[algorithm/config.py:20-21](file:///e:/DehazeSystem/dehaze-python/algorithm/config.py#L20-L21)：

```python
PROJECT_PATH: str = path.dirname(path.dirname(path.abspath(__file__)))
MODEL_PATH: str = path.join(PROJECT_PATH, "trained_model")
```

问题：
1. `MODEL_PATH` 硬编码为本地路径，**未通过 `app/config.py` 的 `Settings` 暴露为环境变量**，无法通过 `.env` 覆盖
2. Python 服务必须与 `trained_model/` 目录部署在同一主机，**无法横向扩缩容**（多副本时每个副本都要挂载模型库）
3. 项目记忆中已记录 "Python 后端必须通过 start.bat 启动" —— 这正是本地路径耦合的副作用：CUDA 环境、模型文件、Python 服务三者被绑定在同一台机器上
4. MinIO 已部署且 `FILE_STORAGE_TYPE=minio`，但模型文件却**不在** MinIO 中，造成"半云半地"的分裂架构：预测结果上传 MinIO，模型权重读本地盘

### 2.5 可维护性缺陷：`import_path` 与文件系统路径双向耦合

`import_path`（如 `algorithm.AECRNet.run`）同时承担两个职责：
1. Python 模块导入路径（`importlib.import_module`）
2. 模型文件目录推导（`MODEL_PATH / module_name`）

这导致：
- **目录名即模块名**的隐式约束：`trained_model/AECRNet/` 必须对应 `algorithm.AECRNet.run`， rename 一处另一处必坏
- `ALGORITHM_REGISTRY`（[prediction_service.py:69-78](file:///e:/DehazeSystem/dehaze-python/app/service/prediction_service.py#L69-L78)）成为必要的"别名补丁层"，因为目录名（`DCP`）与导入名（`DarkChannelPrior`）不一致 —— 这本身就是设计恶味的信号
- Java/Go 后端无法理解 `import_path`，三端语义不对齐

### 2.6 可扩展性缺陷：版本控制与存储路径脱节

schema 有 `version` 字段，但 `path` 不含版本信息。当算法版本升级时：
- `trained_model/AECRNet/` 目录下无法并存 v1 和 v2 权重
- 版本回滚（`rollback_version`）只改 DB 的 `version` 字段，**模型文件无法回滚**（已被覆盖）
- 文档承诺的 `/models/{algorithmId}/{version}/{filename}` 路径方案能解决此问题，但从未落地

### 2.7 数据完整性缺陷：`path` 字段语义二义

种子数据中 `path` 字段存在三种不同语义：
- **文件相对路径**：`AECR-Net/NH_train.pk`、`AODNet/dehazer.pth`（多数情况）
- **目录名**：`CMFNet`（[data.sql:394](file:///e:/DehazeSystem/config/sql/data.sql#L394)，id=6 的父节点）
- **空字符串**：部分算法

同一字段三种含义，缺乏约束，任何消费方都难以可靠解析。

## 三、根因总结

| 根因 | 表现 |
|------|------|
| **文档先行、实现未跟上** | PathBuilder/FileService 方案停留在文档，实际代码是"读本地目录 + glob"的原始方案 |
| **字段职责设计含糊** | `path` 与 `import_path` 职责重叠且互相矛盾，最终 `import_path` 篡夺了 `path` 的定位职责 |
| **存储架构分裂** | 通用文件走 MinIO，模型权重走本地盘，两套体系并行 |
| **配置逃逸** | `MODEL_PATH` 藏在 `algorithm/config.py` 而非 `app/config.py`，绕开了环境变量体系 |

## 四、系统性改进方案

### 4.1 存储架构统一：模型文件纳入 Nginx 静态文件服务

E:\DehazeSystem\docker-compose.yml 中的 `nginx` 服务，挂载 `trained_model/` 目录到 `/models/` 路径。

**目标**：消除"半云半地"，模型权重与预测结果、评估图片统一走 `StorageService`。

**路径规范**（落地文档承诺的方案）：

```
models/{algorithmId}/{version}/{filename}
```

例如：`models/7/1.0.0/dehaze_I_OHaze_CMFNet.pth`

**实施要点**：
1. 在 `app/config.py` 的 `Settings` 中新增 `ALGORITHM_MODEL_PREFIX = "models"`，可环境变量覆盖
2. Python `StorageService` 已存在（MinIO 实现），算法模块复用之，不再独立读盘
3. 模型加载流程：`storage.download(objectName) → 临时文件 → torch.load`，加载后清理临时文件
4. 提供"本地缓存层"优化：首次下载后缓存到 `MODEL_CACHE_DIR`（可配置），二次加载直接读缓存，避免每次预测都走 MinIO

### 4.2 字段语义重构

#### 方案 A（推荐）：废除 `path` 字段的定位职责，改用 `model_file_id` 关联 `sys_file`

| 字段 | 调整 | 说明 |
|------|------|------|
| `path` | **删除** | 职责被 `model_file_id` 取代 |
| `model_file_id` | **新增** bigint | 外键关联 `sys_file.id`，模型权重文件的元数据由文件管理模块统一管理 |
| `import_path` | **保留但重新定义为纯 Python 模块路径** | 仅用于 `importlib`，不再承担文件定位职责 |

**收益**：
- 模型文件元数据（MD5、大小、上传时间、存储对象键）全部由 `sys_file` 承载，复用现有去重、清理机制
- 多变体算法（CMFNet 去雾/去模糊/去雨）通过不同 `model_file_id` 自然区分，彻底解决 2.2 的 bug
- 版本控制：`sys_algorithm_version` 表已有 `model_file_id` 字段（见 [后端实现.md 5.1](file:///e:/DehazeSystem/dehaze-doc/docs/03-模块设计/核心模块/算法管理/后端实现.md#L334)），主表对齐即可

### 4.3 配置机制优化

将 `MODEL_PATH` 从 `algorithm/config.py` 移除，统一到 `app/config.py` 的 `Settings`：

```python
# app/config.py Settings 新增
ALGORITHM_MODEL_PREFIX: str = "models"           # MinIO 对象键前缀
ALGORITHM_MODEL_CACHE_DIR: str = ""              # 本地缓存目录，空则不缓存
ALGORITHM_MODEL_CACHE_TTL: int = 86400           # 缓存有效期（秒）
```

`algorithm/config.py` 仅保留 `DEVICE` 等运行时配置，删除 `MODEL_PATH`。这样：
- 环境变量 `ALGORITHM_MODEL_PREFIX` 可覆盖
- 与 `FILE_STORAGE_TYPE`、`MINIO_*` 配置同层，存储策略一致

### 4.4 消除 `ALGORITHM_REGISTRY` 补丁层

当前 `ALGORITHM_REGISTRY`（`DarkChannelPrior → DCP` 等）存在的原因是：目录名与导入模块名不一致。改进后：
- `import_path` 仅负责 `importlib.import_module`，不再反推目录
- 模型文件位置由 `model_file_id`（方案 A）或 `path` 对象键（方案 B）明确指定
- `ALGORITHM_REGISTRY` 可完全删除，去除一层隐式映射

### 4.5 迁移与兼容策略

由于项目规则明确"禁止兼容历史烂逻辑"，建议：

1. **数据迁移脚本**：扫描 `trained_model/` 目录，按 `算法名/版本` 映射到 Nginx 静态文件服务的 `models/{algorithmId}/{version}/`，并在 `sys_file` 建元数据记录，回填 `sys_algorithm.model_file_id`
2. **schema 同步**：修改 `config/sql/schema.sql` 中 `sys_algorithm` 表，删除 `path`、新增 `model_file_id`，同步三端实体类
3. **种子数据重写**：`config/sql/data.sql` 中所有 `path` 值替换为 `model_file_id` 引用
4. **文档更新**：将 [后端实现.md 6.3](file:///e:/DehazeSystem/dehaze-doc/docs/03-模块设计/核心模块/算法管理/后端实现.md#L381) 的"路径规则"改为已落地的真实描述，删除"委托 FileService"这类未实现的承诺，或将其改为已实现的事实

### 4.6 跨环境部署收益

完成上述改造后：
- Python 服务可横向扩缩容，无需每个副本挂载 `trained_model/`
- 模型文件统一在 MinIO，具备副本、版本、生命周期管理能力
- `start.bat` 的本地路径依赖减弱（CUDA 仍需本地，但模型文件不再本地）
- 算法导入导出（F-M05-007）可实现真正的"配置 + 权重 ZIP 包"，因为权重已在对象存储中，打包下载即可
