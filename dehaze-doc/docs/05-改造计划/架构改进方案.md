## 数据层面架构综合分析与推荐方案

基于对三端 MySQL schema、MongoDB、Redis 的全面调研，从业务和架构双视角给出整合方案。

---

### 一、核心发现：架构与实现的严重背离

#### 1.1 MongoDB 是"纸面架构"，三端零实现

| 端 | 依赖 | 配置 | 实际代码 |
|----|------|------|---------|
| Java | ✅ pom.xml 有依赖 | ✅ 3 处 yml 配置 | ❌ 零代码 |
| Go | ❌ | ❌ | ❌ |
| Python | ❌ | ❌ | ❌ |

[01-总体架构设计.md](file:///E:/DehazeSystem/dehaze-doc/docs/02-系统架构/01-总体架构设计.md#L347) 声称"操作日志、处理记录入 MongoDB"，但**生产环境从未真正使用 MongoDB**。这是一个被搁置了 3 年的设计意图。

#### 1.2 Redis 三端实现严重碎片化

| 问题维度 | 具体表现 |
|---------|---------|
| **Key 前缀不一致** | `role_perms:` vs `role:perms:`、`pred:` vs `prediction:`、`member:benefits:all` vs `member:benefit:all` |
| **能力缺失不对齐** | ~~Python 缺限流/防重提交/登录失败锁定~~（已补齐）；Go 缺菜单缓存/未读消息/延迟推送；~~Go 限流未挂载~~（已挂载全局兜底 + login/register 严格限流） |
| **分布式锁实现不统一** | Java 用 Redisson（有锁续期）；Go/Python 用 `SET NX EX`（无续期，长任务风险） |
| **多实例缓存一致性** | 仅 Go 有 `cache:invalidation` Pub/Sub；Java/Python 仅靠 TTL |
| **存储型数据混放** | Session（不可丢失）+ 缓存（可丢失）+ 分布式锁全在同一个 Redis db=0 |

#### 1.3 四个 log 表的本质差异被混淆

| 表名 | 本质 | 特征 | 正确归属 |
|------|------|------|---------|
| `sys_pred_log` | **业务任务记录** | 有状态机、有外键、有索引查询、有分页 API | MySQL ✅ |
| `sys_eval_log` | **业务任务记录** | 有 JSON 结果、有外键、有缓存查询 | MySQL ✅ |
| `sys_login_log` | **安全审计日志** | 只追加、无关联查询、高频写入 | MongoDB |
| `sys_operation_record` | **过度记录的 HTTP 审计** | 无业务语义、全量记录、无人消费 | 删除 |

### 二、推荐方案：三层存储架构

```
┌──────────────────────────────────────────────────────────────┐
│  L1 业务数据层 (MySQL) - 有状态机/外键/事务/JOIN 需求         │
│  ├── 系统管理：sys_user/role/menu/dept/dict                  │
│  ├── 业务任务：sys_pred_log/eval_log/task（有状态机/外键）   │
│  ├── 商业化：sys_member/order/package/coupon                 │
│  └── 消息通知：sys_message/announcement                     │
├──────────────────────────────────────────────────────────────┤
│  L2 审计日志层 (MongoDB) - 只追加/无 JOIN/schema 可演化       │
│  ├── login_log   登录审计（由 sys_login_log 迁移）           │
│  └── audit_log   业务操作审计（新建，白名单驱动，含变更前后）│
├──────────────────────────────────────────────────────────────┤
│  L3 缓存与会话层 (Redis) - 统一规范 + 分库隔离               │
│  ├── db=0 业务缓存（可丢失）                                 │
│  ├── db=1 Session + 分布式锁（不可丢失，存储型）             │
│  └── db=2 限流计数器                                         │
└──────────────────────────────────────────────────────────────┘
```

**分层判断原则（一句话）**：是否需要和业务表做 JOIN 查询？需要 → MySQL；不需要 → MongoDB。
- `sys_pred_log`/`sys_eval_log` 需要与 `sys_rating`、`sys_algorithm` JOIN → MySQL
- `login_log`/`audit_log` 独立查阅无 JOIN 需求 → MongoDB

### 三、关键决策与理由

#### 3.1 `sys_pred_log` / `sys_eval_log`：**保留 MySQL**

**业务角度**：每次推理/评估都是一次付费用户行为，有状态机（processing → completed/failed）、有评分关联（`sys_rating.pred_log_id` 唯一索引）、有缓存查询需求。

**架构角度**：
- 有强外键关联（algorithm_id / file_id / user_id）
- 有索引查询（`idx_algorithm_id + idx_origin_md5`）
- 有分页 API（`/api/v1/prediction/logs`）
- 数据量可控（每次推理一条，不是海量日志）
- `sys_eval_log.result` 用 MySQL 8.0 原生 JSON 类型即可

**调研证据**：三端都完整实现了 CRUD + 异步任务 + 僵尸任务清理 Job，是核心业务能力，不是"日志"。

#### 3.2 `sys_login_log`：**迁 MongoDB**

**业务角度**：付费 SaaS 的账号安全是合规底线，登录记录是用户纠纷的凭证。

**架构角度**：
- 只追加、无更新
- 无外键关联查询（仅 user_id 弱关联）
- 高频写入（每次登录一条）
- schema 可能演化（新增 browser/os/location 字段不影响历史）

**实现**：三端等价实现 MongoDB Repository，以 Python 现有 [login_log_repository.py](file:///E:/DehazeSystem/dehaze-python/app/repository/login_log_repository.py) 为蓝本。

#### 3.3 `sys_operation_record`：**删除全量审计，在 MongoDB 新建 `audit_log`**

**业务角度**：当前 [operation_log.py](file:///E:/DehazeSystem/dehaze-python/app/middleware/operation_log.py) 记录所有 HTTP 请求，但**没有任何业务场景消费它**——既不能回答"谁改了用户 X 的会员等级"，也不能对账。

**架构角度**：全量 HTTP 审计违反"禁止过度设计"规则。正确的审计是**白名单驱动**，只记录关键业务写操作。

**为什么放 MongoDB 而不是 MySQL**：
- `before_value`/`after_value` 是 JSON 快照，不同业务模块（会员/订单/数据集/权限）的快照结构不同——schema-free 正是 MongoDB 的典型场景
- 放 MySQL 用 JSON 字段虽然可行，但 schema 演化时会遇到历史数据不兼容问题（ALTER TABLE 影响在线业务）
- 审计日志**不需要和业务表 JOIN**：查"谁改了会员等级"时，审计记录本身已包含 `operator_id`/`target_id`/`before`/`after`，无需再 JOIN `sys_member`
- 审计日志是独立查阅的，不参与业务流程，只是事后追溯
- 与 `login_log` 同属审计层，统一存储 backend 便于一致管理

**新建 MongoDB collection `audit_log` 设计**：

```javascript
// collection: audit_log
// 业务操作审计（白名单驱动，仅记录关键写操作）
{
    _id: ObjectId,
    operator_id: Long,            // 操作人ID
    target_type: String,          // 操作目标类型(member/order/dataset/role/user)
    target_id: Object,            // 操作目标ID（Long/String/List<Long>，因动作而异）
    action: String,               // 动作(create/update/delete/level_change/refund/...)
    module: String,               // 业务模块(member/order/dataset/role/user)
    before_value: Document,       // 变更前快照（schema 因 module 而异）
    after_value: Document,        // 变更后快照（schema 因 module 而异）
    ip: String,
    user_agent: String,
    create_time: Date
}
// 索引（MongoDB 创建语句）
// db.audit_log.createIndex({ operator_id: 1, create_time: -1 })
// db.audit_log.createIndex({ target_type: 1, target_id: 1, create_time: -1 })
// db.audit_log.createIndex({ module: 1, create_time: -1 })
```

**审计白名单**（约 15-20 个 Service 方法）：
- 会员：`adjustLevel` / `deductQuota` / `deductGrowth`
- 订单：`createOrder` / `refund` / `cancelOrder`
- 数据集：`batchDelete` / `moveItems`
- 权限：`assignRoles` / `updateMenu` / `updateRolePerms`
- 用户：`disable` / `enable` / `resetPassword`

#### 3.5 Redis 统一规范

| 维度 | 当前问题 | 推荐规范 |
|------|---------|---------|
| **Key 前缀** | `role_perms:` / `role:perms:` | 统一为 `role:perms:`（冒号分隔） |
| **预测缓存** | `pred:` / `prediction:` | 统一为 `prediction:{algoId}:{md5}` |
| **会员权益全量** | `benefits:all` / `benefit:all` | 统一为 `member:benefit:all`（单数） |
| **任务状态** | `task:{id}` / `task:running:{id}` | 统一为 `task:running:{id}`（Python 方案更清晰） |
| **分布式锁** | Redisson / SETNX | 三端统一 `SET NX EX` + Lua 释放（无 Redisson 依赖，跨语言一致） |
| **多实例一致性** | 仅 Go 有失效广播 | 三端都引入 `cache:invalidation` Pub/Sub |
| **db 隔离** | 全在 db=0 | db=0 缓存 / db=1 Session+锁 / db=2 限流 |

**能力补齐**：
- Python 补：登录失败锁定（`login:fail:{username}`）、限流、防重复提交
- Go 补：菜单缓存（`menu:routes`）、字典缓存（`dict:options:{type}`）、未读消息计数（`msg:unread:{userId}`）

### 五、总结判断

| 问题 | 根因 | 解决方案 |
|------|------|---------|
| MongoDB 纸面化 | 架构设计未落地 | 真正落地，承载 `login_log` + `audit_log` 两个 collections |
| Redis 碎片化 | 三端独立演进 | 统一 Key 规范 + db 隔离 + 补齐能力 |
| 操作日志无业务价值 | 中间件全量记录 | 改为白名单驱动的 MongoDB `audit_log`（含变更前后快照） |
| 预测/评估日志存疑 | 被误判为"日志" | 保留 MySQL，它们是业务任务记录 |

**核心原则**：业务数据入 MySQL（有状态机/外键/索引/分页），审计日志入 MongoDB（只追加/无 JOIN/schema 可演化），缓存与会话入 Redis（统一规范/db 隔离）。
