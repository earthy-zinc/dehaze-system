# 新增模块剩余问题修复计划

> 本文记录订单、反馈、会员、套餐、消息五个模块在三端代码评审后的剩余中/轻微问题。
> 严重问题已在首轮修复中完成，本文仅涉及剩余的性能优化、三端对齐、功能补全、规范清理等。
>
> 基准时间：2026-07-29，首轮严重问题修复已完成。

## 分类原则

按**修复涉及的文件层和修复类型**分类为 7 个批次，确保不同批次可完全并行执行：

| 批次 | 名称 | 主要涉及文件层 | 可并行 |
|------|------|---------------|--------|
| 批次1 | 统计接口性能优化 | repository/mapper + service 统计方法 | 与其他批次无冲突 |
| 批次2 | 定时任务补全 | job 目录新增 + service 新增方法 | 与其他批次无冲突（仅新增） |
| 批次3 | WebSocket 实时推送 | websocket 模块 + message service 推送调用 | 仅与批次4有交叉，见注意事项 |
| 批次4 | 三端业务逻辑对齐 | service 层非统计方法 | 与批次1按方法隔离 |
| 批次5 | 表单校验补全 | form/schema 层 | 与其他批次无冲突 |
| 批次6 | 代码规范清理 | vo/util/enum 层 | 与其他批次无冲突 |
| 批次7 | 文档与 schema 同步 | dehaze-doc + config/sql | 与其他批次无冲突 |

### 并行执行注意事项

- **批次1 vs 批次4**：都改 service 文件。批次1仅改统计方法（getStats/calcStats/listRefunds等），批次4仅改非统计方法。同一 service 文件如同时涉及两个批次，建议同一人处理或按方法严格隔离，git 合并时按方法级别冲突解决。
- **批次2 vs 批次4**：批次2在 service 新增方法（如 processRefundRetry），批次4修改 service 现有方法。新增方法不修改现有方法体，无冲突。
- **批次3 vs 批次4**：都改 message service。批次3仅改推送相关调用点（send/dispatch方法），批次4不改推送方法。如同一文件涉及两个批次，建议同一人处理。

## 执行建议

### 优先级排序

| 优先级 | 批次 | 理由 |
|--------|------|------|
| P0 | 批次4 | 安全与数据正确性（并发竞态、状态机、缓存） |
| P1 | 批次1 | 性能（万级数据内存统计） |
| P1 | 批次3 | 功能需求（3s 内消息推送） |
| P2 | 批次2 | 功能补全（定时任务） |
| P2 | 批次5 | 输入校验 |
| P3 | 批次6 | 代码规范 |
| P3 | 批次7 | 文档同步 |

### 并行分配建议

以下分配方案确保无文件冲突：

| 人员 | 负责批次 | 涉及模块 |
|------|---------|---------|
| 人员A | 批次1 | 全部模块的 repository/mapper + 统计方法 |
| 人员B | 批次2 | 全部模块的 job 新增 |
| 人员C | 批次3 | message 模块推送 + websocket |
| 人员D | 批次4 | 全部模块的 service 非统计方法 |
| 人员E | 批次5 | 全部模块的 form/schema |
| 人员F | 批次6 | 全部模块的 vo/util/enum |
| 人员G | 批次7 | 全部文档与 SQL schema |

**冲突协调**：
- 人员A（批次1）与人员D（批次4）都改 service 文件：A 只改统计方法，D 只改非统计方法。同一文件如同时涉及，按方法级别 git 合并。
- 人员C（批次3）与人员D（批次4）都改 message service：C 只改推送方法，D 不改推送方法。如 MessageServiceImpl.java 同时涉及，建议同一人处理。
- 人员B（批次2）在 service 新增方法，不影响人员D（批次4）修改现有方法。
