# 前端日志监控改造计划

> 本文规划前端（Web/移动端）日志监控体系的改造方案，复用后端已有 ELK 基础设施，建立「前端采集 → 后端接收 → ELK 检索」的轻量链路，与后端日志通过 `trace_id` 串联，实现端到端问题定位。
> 状态：规划中（2026-08-05）

---

## 一、背景与目标

### 1.1 背景

后端已建立完整日志监控体系（见 [07-日志架构设计.md](../02-系统架构/07-日志架构设计.md)）：

- 三端后端（Java/Go/Python）统一 NDJSON 日志 → Filebeat → Logstash → ES(`dehaze-logs-*`) → Kibana
- `trace_id` 贯穿请求链路，文档 §4.3 明确设计意图：**「优先从上游请求头 `X-Trace-Id` 透传」「响应头回写 `X-Trace-Id`，供前端/SDK 关联」**

但前端侧存在系统性缺口：

| 缺口 | 现状 | 影响 |
|------|------|------|
| trace_id 未透传 | SDK 请求拦截器未注入 `X-Trace-Id` 头 | 后端日志 trace_id 与前端无法关联，端到端追踪断裂 |
| 全局错误未捕获 | React/Vue/Flutter 等入口均无 `window.onerror` / `FlutterError.onError` | JS/Dart 未捕获异常静默丢失，用户遇到白屏/崩溃无法定位 |
| 日志无上报通道 | 三端后端均无前端日志接收 API | 前端错误只能写本地文件（如 `flutter_02.log`），开发可见、运维不可见 |
| ELK 不覆盖前端 | logstash 仅 beats input，索引仅 `dehaze-logs-*` | Kibana 检索不到前端日志，监控面板缺失前端维度 |

### 1.2 设计原则

1. **不重建监控系统**：复用后端 ELK（Filebeat + Logstash + ES + Kibana），只新增前端采集 + 接收 API + 索引
2. **SDK 层统一封装**：`dehaze-sdk-js` 提供核心能力（trace_id 生成 + 错误捕获 + 批量上报），JS 系前端通过 SDK 接入；移动端（Flutter/Android/RN）各自实现等价模块，对接同一接收 API
3. **trace_id 双向透传**：前端生成 → 请求头 `X-Trace-Id` → 后端复用；前端日志带同一 `trace_id`，Kibana 可串联前端报错与后端处理日志
4. **采样 + 限流**：仅上报 ERROR/WARN + 关键操作，避免日志风暴拖垮后端
5. **离线缓存**：本地缓存 + 网络恢复后批量上报，避免丢日志

### 1.3 目标

| 目标 | 含义 |
|------|------|
| **可追踪** | 前端日志带 `trace_id`，与后端日志在 Kibana 串联同一请求 |
| **可观测** | JS/Dart 未捕获异常、API 失败自动上报，运维无需用户复现即可定位 |
| **可检索** | 前端日志入 ES 独立索引 `dehaze-client-logs-*`，Kibana 字段级过滤 |
| **零侵入** | SDK 统一封装，前端项目接入仅需初始化调用，不污染业务代码 |

## 三、改造方案（分阶段）

### 3.1 总体架构

```
┌─────────────────────────────────────────────────────────────────┐
│ 前端（SDK / 原生模块）—— Logger 多 transport 架构                 │
│  ├─ trace_id 生成 → 请求头 X-Trace-Id（透传后端）                  │
│  ├─ 全局错误捕获（window.onerror / FlutterError.onError / ...）    │
│  ├─ API 失败拦截（SDK 响应错误拦截器）                             │
│  ├─ 本地队列 + 离线缓存（localStorage / 文件）                     │
│  └─ transport 按环境选择（见 §3.6）：                              │
│     ├─ 生产：批量上报 → POST /api/v1/logs/client                  │
│     ├─ 移动端开发：写本地文件 logs/{date}/{level}.log              │
│     └─ Web 开发：console（DevTools 接管，不落盘）                  │
└────────────────────────┬────────────────────────────────────────┘
                         │ （生产环境 transport）
┌────────────────────────▼────────────────────────────────────────┐
│ 后端接收（三端同步实现，复用现有限流）                              │
│  ├─ POST /api/v1/logs/client                                     │
│  │   ├─ 限流（复用各端现有限流：@RateLimit / RateLimitMiddleware） │
│  │   ├─ 鉴权（匿名也允许上报 ERROR，但需带 trace_id）              │
│  │   └─ NDJSON 写入 dehaze-java/logs/{date}/client.log           │
│  └─ 复用后端日志存储/切割/保留策略（与后端日志架构一致）            │
└────────────────────────┬────────────────────────────────────────┘
                         │
┌────────────────────────▼────────────────────────────────────────┐
│ 复用现有 ELK 链路                                                │
│  ├─ Filebeat：新增 filestream 采集 client.log                    │
│  ├─ Logstash：按 fields.service 分流到不同 ES 索引                 │
│  │   ├─ service=client → dehaze-client-logs-{yyyy.MM.dd}        │
│  │   └─ service=java/python/go → dehaze-logs-{yyyy.MM.dd}       │
│  └─ Kibana：新建 dehaze-client-logs-* 索引模式                    │
└─────────────────────────────────────────────────────────────────┘
```

**架构选型理由**：后端接收 API 写文件 + filebeat 采集（而非直接写 ES）：
- 复用现有采集链路（filebeat + logstash），字段归一化能力可复用
- 后端 API 只负责接收 + 写文件，不引入 ES 客户端依赖
- 与后端日志架构完全一致（落盘 + filebeat 采集），运维心智统一
- 复用后端日志存储/切割/保留策略（[07-日志架构设计.md §2](../02-系统架构/07-日志架构设计.md)）

### 3.2 trace_id 透传机制

```
前端 SDK 请求拦截器
  └─ 生成 trace_id（uuid hex 32 位无连字符，与后端 §4.3 一致）
        │
        └─ 写入请求头 X-Trace-Id
              │
              └─ 后端 TraceIdFilter 读取 X-Trace-Id 复用（无则生成，已有逻辑）
                    │
                    └─ 后端响应头回写 X-Trace-Id
                          │
                          └─ 前端响应拦截器读取响应头 X-Trace-Id
                                │
                                └─ 与本地 trace_id 对齐，写入日志条目 trace_id 字段
                                      │
                                      └─ 上报到 ELK，Kibana 可串联前后端日志
```

**关键点**：
- 前端生成的 `trace_id` 与后端复用同一份，Kibana 中 `trace_id:xxx` 可同时检索到前端报错日志 + 后端处理日志
- 后端 `TraceIdFilter` 已支持「优先从上游请求头透传」（§4.3），前端只需写入请求头即可，无需后端改动

### 3.3 前端日志字段规范（NDJSON）

与后端日志字段对齐 + 前端特有字段：

#### 3.3.1 基础字段（所有日志）

| 字段 | 类型 | 说明 |
|------|------|------|
| `timestamp` | string | ISO8601 UTC 时间戳（与后端一致） |
| `level` | string | `ERROR` / `WARN` / `INFO`（INFO 默认不上报） |
| `message` | string | 人读描述，仅放业务语义 |
| `service` | string | 固定 `client`（filebeat 注入，区分后端日志） |

#### 3.3.2 前端上下文字段（所有日志）

| 字段 | 类型 | 说明 |
|------|------|------|
| `app` | string | 前端项目标识：`react`/`vue`/`taro`/`uniapp`/`rn`/`flutter`/`android` |
| `app_version` | string | 应用版本号（构建时注入） |
| `env` | string | `dev` / `prod` |
| `url` | string | 当前页面 URL / 路由路径（Web 端） |
| `user_agent` | string | 浏览器/设备 User-Agent |
| `trace_id` | string | 与后端日志串联（见 §3.2） |
| `user_id` | int | 登录用户 ID（登录后注入，未登录为空） |

#### 3.3.3 错误上下文字段（错误日志）

| 字段 | 类型 | 说明 |
|------|------|------|
| `error_type` | string | 错误类型：`js`/`dart`/`native`/`promise`/`api` |
| `error_source` | string | 错误来源：`window.onerror`/`unhandledrejection`/`FlutterError`/`api_interceptor` |
| `error_stack` | string | 完整堆栈字符串（与后端 `exc_info` 风格一致） |

#### 3.3.4 API 上下文字段（API 失败日志）

| 字段 | 类型 | 说明 |
|------|------|------|
| `method` | string | HTTP 方法（与后端访问日志对齐） |
| `path` | string | 请求路径（不含 query） |
| `status` | int | HTTP 状态码 |
| `duration` | float | 请求耗时（毫秒） |
| `code` | string | 业务错误码（响应体 `code` 字段） |

#### 3.3.5 性能指标字段（性能日志 `type: performance`）

| 字段 | 类型 | 说明 |
|------|------|------|
| `metric_name` | string | 指标名：`lcp`/`inp`/`cls`/`fcp`/`fp`/`ttfb`/`dom_ready`/`load`/`long_task`/`resource_error`/`route_switch` |
| `metric_value` | float | 指标值（毫秒；`cls` 无量纲，`resource_error` 固定 0） |
| `navigation_type` | string | 导航类型：`navigate`/`reload`/`back_forward`（仅页面加载类指标） |
| `resource_url` | string | 资源 URL（仅 `resource_error` / 资源加载耗时） |

**采集的指标说明**：

| 指标 | 含义 | 采集方式 |
|------|------|---------|
| `lcp` | 最大内容绘制时间（感知加载速度，Web Vitals 核心） | `PerformanceObserver` entryType `largest-contentful-paint` |
| `inp` | 交互到下次绘制延迟（响应性，Web Vitals 核心，替代 FID） | `PerformanceObserver` entryType `event` |
| `cls` | 累积布局偏移（视觉稳定性，Web Vitals 核心，无量纲） | `PerformanceObserver` entryType `layout-shift` |
| `fcp` | 首次内容绘制 | `PerformanceObserver` entryType `paint`（name `first-contentful-paint`） |
| `fp` | 首次绘制 | `PerformanceObserver` entryType `paint`（name `first-paint`） |
| `ttfb` | 首字节时间 | `PerformanceObserver` entryType `navigation`（`responseStart - requestStart`） |
| `dom_ready` | DOM Ready 耗时 | `performance.timing.domContentLoadedEventEnd - navigationStart` |
| `load` | 页面 Load 耗时 | `performance.timing.loadEventEnd - navigationStart` |
| `long_task` | 长任务（>50ms 阻塞主线程） | `PerformanceObserver` entryType `longtask` |
| `resource_error` | 资源加载失败（img/script/css/link） | `window.addEventListener('error', ..., true)` 捕获 |
| `route_switch` | SPA 路由切换耗时 | history pushState/replaceState + popstate 钩子计时 |

> 移动端（Flutter/Android）阶段 3 采集各自平台指标（Flutter `Timeline` / Android `FrameMetrics`），字段名对齐 `metric_name`/`metric_value`。

### 3.4 采样与限流策略

| 级别 | 采样率 | 说明 |
|------|--------|------|
| `ERROR` | 100% | 全量上报，含 JS 异常、API 失败、崩溃 |
| `WARN` | 50% | 采样上报，如慢请求、资源加载失败 |
| `INFO` | 0% | 不上报（本地 console 即可） |

**限流**（单设备）：
- 60 秒内最多上报 20 条，超限丢弃（防日志风暴）
- 本地队列最多缓存 100 条（Web）/ 500 条（移动端），超出丢弃最旧

### 3.5 离线缓存策略

| 平台 | 缓存载体 | 容量 | 持久化 |
|------|---------|------|--------|
| Web（React/Vue/Taro/UniApp/RN） | `localStorage` key=`dehaze_logs` | 100 条 | 浏览器关闭后保留 |
| Flutter | `path_provider` 应用文档目录文件 | 500 条 | App 卸载才清除 |
| Android | 应用内部存储文件 | 500 条 | App 卸载才清除 |

**上报时机**：
- 队列满 10 条 → 立即批量上报
- 网络恢复事件（`online` / 连接回调）→ 批量上报
- App 进入后台（移动端）→ 批量上报
- 定时器 30 秒一次 → 批量上报

**上报成功**：清除已上报条目
**上报失败**：保留队列，下次重试（指数退避，最长 60s）

### 3.6 Logger 多 transport 架构与开发环境本地日志

Logger 模块采用多 transport 设计：日志条目产生后，由 transport 按环境决定输出通道。生产环境上报后端走 ELK；移动端开发环境额外写本地文件，方便出错后翻日志定位（与后端 `dehaze-java/logs` 排查体验一致）；Web 端开发环境直接用浏览器 DevTools，不落盘。

#### 3.6.1 transport 选择矩阵

| 平台 | 开发环境 | 生产环境 |
|------|---------|---------|
| Web（React/Vue/Taro/UniApp/RN） | `console`（DevTools 接管） | `remote`（上报 API） |
| Flutter | `file`（本地文件）+ `console` | `remote`（上报 API）+ `file`（崩溃兜底） |
| Android | `file`（本地文件）+ `console`（logcat） | `remote`（上报 API）+ `file`（崩溃兜底） |

**Web 端开发环境不落盘的理由**：浏览器无文件系统，落盘需经 dev server 中转写文件，配置复杂且收益低；DevTools 的 console（支持 Preserve Log）+ Network + Sources 已覆盖开发排查需求，强行做本地文件是过度设计。

**移动端开发环境必须落盘的理由**：真机调试 logcat 刷屏严重，异步/后台错误一闪而过；用户反馈问题本地无法复现时，本地日志文件是唯一回溯手段；已有痛点证据（`flutter_02.log` 仅记录 crash，覆盖面不够）。

#### 3.6.2 移动端本地日志文件设计

与后端日志存储架构对齐（[07-日志架构设计.md §2](../02-系统架构/07-日志架构设计.md)）：

| 维度 | 规格 | 说明 |
|------|------|------|
| 目录结构 | `logs/{yyyy-MM-dd}/{level}.log` | 与后端一致 |
| 文件级别 | `info.log`（INFO+）/ `error.log`（仅 ERROR，是 info 子集） | 与后端一致 |
| 格式 | NDJSON（每行一个 JSON） | 与后端一致，便于复用解析逻辑 |
| 切割 | 单文件 100MB 归档为 `{level}.{n}.log` | 与后端一致 |
| 保留 | 7 天 | 移动端存储敏感，比后端 30 天短 |

**存储路径**：

```
Flutter:
  {app_flutter_dir}/logs/{yyyy-MM-dd}/{level}.log
  # app_flutter_dir 由 path_provider getApplicationDocumentsDirectory() 获取

Android:
  {files_dir}/logs/{yyyy-MM-dd}/{level}.log
  # files_dir 由 context.filesDir 获取
```

**查看方式**：

```bash
# Flutter
adb shell run-as com.dehaze.app cat app_flutter/logs/{date}/error.log

# Android
adb shell run-as com.dehaze.android cat files/logs/{date}/error.log

# 或 App 内置「开发者面板」提供导出按钮（分享/上传）
```

#### 3.6.3 环境驱动 transport 配置示例

```dart
// Flutter 示例
Logger(
  transports: [
    ConsoleTransport(),                          // 始终开启
    if (kDebugMode) FileTransport(),             // 开发：写本地文件
    if (kReleaseMode) RemoteTransport(),         // 生产：上报后端 API
    if (kReleaseMode) FileTransport(retentionDays: 3),  // 生产：崩溃兜底，短期保留
  ],
)
```

```ts
// Web SDK 示例
Logger.install({
  transports: [
    new ConsoleTransport(),                      // 始终开启（DevTools 接管）
    if (import.meta.env.PROD) new RemoteTransport(),  // 生产：上报 API
  ],
})
```

> 生产环境移动端保留 `FileTransport`（3 天短期）作为崩溃兜底：App 崩溃后 `RemoteTransport` 可能无法上报，下次启动时从本地文件补报（与 §3.5 离线缓存策略协同）。

### 3.7 后端接收 API 设计

#### 3.7.1 接口契约

```
POST /api/v1/logs/client
Content-Type: application/json

Request Body:
{
  "logs": [
    {
      "timestamp": "2026-08-05T08:30:00.000+00:00",
      "level": "ERROR",
      "message": "...",
      "app": "react",
      "app_version": "1.2.0",
      "env": "prod",
      "url": "/prediction/history",
      "user_agent": "...",
      "trace_id": "a1b2c3...",
      "user_id": 42,
      "error_type": "js",
      "error_source": "window.onerror",
      "error_stack": "..."
    }
  ]
}

Response:
{
  "code": "00000",
  "data": null,
  "msg": "success",
  "traceId": "a1b2c3..."
}
```

**约束**：
- 单次请求最多 50 条日志
- 单条日志 `message` 最长 2000 字符，`error_stack` 最长 8000 字符（超长截断）
- `user_id` 从当前会话解析（已登录则带，未登录为空）

#### 3.7.2 三端同步实现（复用现有限流机制）

三端同步实现，**不重新定义限流逻辑，复用各端现有限流注解/中间件/配置**：

| 端 | 实现位置 | 限流复用方式 | 写入目录 |
|----|---------|------------|---------|
| **Java** | `dehaze-java` 新增 `ClientLogController` + `ClientLogService` | `@RateLimit` 注解（复用 [RateLimitAspect](../../../dehaze-java/src/main/java/com/pei/dehaze/plugin/ratelimit/aspect/RateLimitAspect.java) AOP），`@RateLimit(key="client-log", timeWindow=60, maxRequests=1000)` | `dehaze-java/logs/{date}/client.log` |
| **Python** | `dehaze-python` 新增 `ClientLogRouter` | 全局 `RateLimitMiddleware` 自动生效（按 path+ip 限流，复用 `settings.RATE_LIMIT_MAX_REQUESTS`），无需额外配置 | `dehaze-python/logs/{date}/client.log` |
| **Go** | `dehaze-go` 新增 `ClientLogController` + 路由 | `PathRateLimiter(period, max)` 中间件（复用 [rate_limit.go](../../../dehaze-go/pkg/server/gin/middleware/rate_limit.go)），dev 环境复用全局 `ip-limit-count=100000` 的宽松策略 | `dehaze-go/logs/{date}/client.log` |

**写入逻辑**：复用后端日志存储架构（[07-日志架构设计.md §2](../02-系统架构/07-日志架构设计.md)）：
- 目录：`logs/{yyyy-MM-dd}/client.log`
- 格式：NDJSON（每行一个 JSON 对象）
- 切割：单文件 100MB 归档为 `client.{n}.log`
- 保留：30 天（与后端应用日志一致）

**鉴权**：
- 已登录用户：从会话解析 `user_id` 注入日志
- 未登录用户：允许上报（匿名 ERROR 也需可观测），`user_id` 为空，但必须带 `trace_id`

**限流**（复用各端现有限流配置，不新增限流组件）：
- **Java**：`@RateLimit` 注解直接配置 `maxRequests`，dev/prod 差异化通过 `application-dev.yml` / `application-prod.yml` 中限流桶配置或注解参数实现
- **Python**：全局 `RateLimitMiddleware` 自动按 `rate:limit:{path}:{ip}` 限流，复用 `settings.RATE_LIMIT_MAX_REQUESTS`（dev 宽松、prod 严格，由各环境 config 控制）
- **Go**：`PathRateLimiter` 或全局 `IPRateLimiter()`，复用 `config.yaml` 的 `system.ip-limit-count` / `ip-limit-time`（dev 已是 100000/3600s 宽松值）
- 三端均 Redis 不可用时降级放行（与现有限流降级策略一致）

### 3.8 filebeat 配置扩展

## 六、验收标准

### 阶段 1 验收

1. 前端发起任意 API 请求，请求头携带 `X-Trace-Id`，后端日志 `trace_id` 与之一致
2. 浏览器控制台手动触发 `throw new Error('test')`，30 秒内 Kibana `dehaze-client-logs-*` 索引可检索到该错误
3. Kibana 中以 `trace_id:xxx` 检索，可同时查到前端错误日志 + 后端处理日志（端到端串联）
4. SDK 接口测试覆盖率 ≥ 80%（trace_id 透传、错误捕获、批量上报、离线缓存、限流）
5. 三端接收 API 限流生效：复用各端现有限流机制（Java `@RateLimit` / Python `RateLimitMiddleware` / Go `PathRateLimiter`），超限返回 429
6. 离线场景：断网触发错误 → 恢复网络后日志成功上报

### 阶段 2 验收

7. API 失败请求 30 秒内可在 Kibana 检索到（含 method/path/status/duration/code）
8. Kibana Dashboard 展示前端错误趋势、API 失败率、Web Vitals（LCP/INP/CLS）、首屏耗时、长任务 TopN

### 阶段 3 验收

9. Flutter 端触发未捕获异常，Kibana 可检索到（`error_type: dart`）
10. Android 端触发未捕获异常，Kibana 可检索到（`error_type: native`）
11. Flutter 开发环境触发 ERROR，本地日志文件 `logs/{date}/error.log` 可通过 `adb shell run-as` 查阅，格式为 NDJSON
12. Android 开发环境触发 ERROR，本地日志文件可查阅，格式为 NDJSON
13. 生产环境 App 崩溃后重启，本地 `FileTransport` 兜底日志成功补报到后端

## 七、风险与权衡

| 风险 | 应对 |
|------|------|
| 前端日志量爆炸 | 采样 + 限流（§3.4）+ 后端 API 复用各端现有限流（Java `@RateLimit` / Python 中间件 / Go 中间件） |
| 离线缓存占用用户存储 | 队列上限（Web 100 条 / 移动端 500 条），超出丢弃最旧 |
| 上报 API 被恶意刷 | 限流 + 必须带 trace_id + 匿名上报仅允许 ERROR 级别 |
| trace_id 与后端不一致 | 前端生成后写入请求头，后端复用（不重新生成），响应头回写确认 |
| 移动端崩溃导致上报失败 | 本地文件持久化，下次启动后批量上报 |
| ES 索引膨胀 | 前端日志独立索引 `dehaze-client-logs-*`，保留 30 天（与后端一致），可单独配置 ILM 策略 |
