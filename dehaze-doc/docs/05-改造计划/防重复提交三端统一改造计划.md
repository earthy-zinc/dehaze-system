# 防重复提交（A0002）三端统一改造计划

> 本文是「A0002 防重复提交跨端统一」的设计与决策点单一信息源。**第 3 节决策点已于 2026-10-04 全部裁定并实施完毕**，实施结果见第 8 节。
>
> 事实基准：2026-10-04 磁盘代码——python `app/middleware/anti_repeat.py`、java `plugin/dupsubmit/`、go `pkg/server/gin/middleware/anti_repeat.go`；三端共享同一 Redis。

## 1. 现状（实测）

| 维度           | python（全局 ASGI 中间件）                                                                                             | java（AOP 注解）                                                                 | go（路由级挂载）                                                                                                     |
| -------------- | ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 触发面         | **仅 POST**，且排除 19 个业务前缀（`/api/v1/ai`、`/api/v1/orders`、`/api/v1/files`、`/api/v1/users` 等）+ 精确路径名单 | 注解 `@PreventDuplicateSubmit`，**仅 6 处**（dept/dict×2/menu/role/user 的创建） | 逐个路由显式挂载 `middleware.AntiRepeat(...)`（dataset_item、menu、sys_dict、input_history、file、import_export 等） |
| 键             | `anti_repeat:{identity}:{method}:{path}:{query}:{bodyHash}`，identity ∈ `user:{id}` / `session:{sid}` / `ip:{ip}`      | `LOCK:RESUBMIT:{sessionId}:{method}-{uri}`                                       | `anti_repeat:{jti 或客户端 IP}:{method}:{path}`（`IncludeBody` 时追加 body 摘要）                                    |
| 身份口径       | userId（会话可取时），退化 session/IP                                                                                  | **sessionId**（每次重新登录都变）                                                | **JWT jti**（token 刷新即变），无 claims 时 IP                                                                       |

### 1.1 三类缺陷

1. **跨端互不设防（漏防）**：键前缀/身份/构成三段都不同 ⇒ 同一用户在 A 端提交后立即在 B 端提交同一请求，两端各写各的键，**谁都不拦**。共享 Redis 的设计意图（跨端防重）未生效。
2. **同一 URL 连续不同内容被误判（误伤）**：java 完全不参与 body、go 多数路由不参与 ⇒ 5s 内对同一 URL 提交两份**不同内容**（典型：连续创建两个不同字典/菜单）会被当重复拦掉。
3. **语义漂移**：java 用 sessionId、go 用 jti ⇒ "同一用户的重复提交"只在同一登录态内生效，重新登录或换端即绕过。

HTTP 状态码三样（429/400/200）是各端**既有错误信封约定**的体现，本身不算缺陷，见决策点 D3。

## 2. 目标与非目标

- **目标**：键与语义统一（跨端互设防、body 参与一致、TTL 一致、身份口径一致），并让"哪些端点参与防重"可预期、可守卫。
- **非目标**：不改前端交互与提示文案；不改 A0002 的业务码值与中文文案；不要求三端 HTTP 状态码一致。

## 3. 决策点（已裁定并实施，2026-10-04）

### D1 键格式与身份口径（推荐：以 python 为基准，身份收窄为 userId）

统一为：`anti_repeat:{identity}:{METHOD}:{path}:{query}:{bodyHash}`

- `identity`：统一 **`user:{userId}`**；无有效会话时退化为 `ip:{clientIp}`。
  - 理由：防重的业务语义是"同一用户重复提交"；java 的 sessionId 与 go 的 jti 都会随登录态变化，导致换登录态即绕过。
- `bodyHash`：统一 `md5(rawBody).hexdigest()`，空 body 记 `""`（沿用 python 现状，零迁移成本）。
- `query`：保留参与，但**要求参数排序归一**（`sorted(kv pairs)` 后再拼）——python 现状未归一，`?a=1&b=2` 与 `?b=2&a=1` 会算出不同键而绕过，属顺手修复项。
- 前缀统一 `anti_repeat:`；java 现行 `LOCK:RESUBMIT:` 前缀废弃。

### D2 TTL（推荐：统一 5s，三端同一常量口径）

python 为 `settings.ANTI_REPEAT_TTL_SECONDS`、java 为锁租约、go 为路由参数。统一为 **5s**：go 的 `Expire:3` 改 5；java 的锁租约与键 TTL 分开表达（锁租约可保持实现细节，但键 TTL 必须 5s）。

### D3 HTTP 状态码（推荐：各端保持 + 文档写死）

- 保持 python 429 / java 400 / go 200（业务码统一 A0002 不变）。
- 理由：把 go 改成 429 会破坏"go 错误信封恒 HTTP 200"的全局约定（影响所有客户端拦截器与既有测试）；把 python 改成 400 会丢 429 的标准语义（`Retry-After`、客户端退避）。
- 落地：在 `02-系统架构/04-API规范.md` 的 A0002 条目写明分端口径；跨端脚本**分端断言状态码**、只对 `code` 做统一断言。

### D4 触发面（推荐：三端"防重端点白名单"逐端点对齐，并由守卫锁定）

现状三端生效端点集合差异很大（go 括及上传/数据集创建，python 排除 `/api/v1/ai`、`/api/v1/orders` 等）。推荐：

1. 以**现状并集**为基础，逐端点确认归属，产出一份"防重端点白名单"（含三端各自的挂载方式：python 排除表 / java 注解 / go 路由挂载）。
2. 白名单作为**单一信息源**落 docs（本节后续版本），并由新增跨端守卫测试对拍三端的白名单集合（见 D7）。
3. 本期不新增端点；仅消除"同一端点在 A 端拦、B 端不拦"的不一致。

### D5 java 实现形态（推荐：保留注解 + 统一键 + 补 body 缓存）

- 保留 `@PreventDuplicateSubmit` 显式声明（与 go 的路由挂载同类：显式白名单，优于全局过滤器）。
- 改造 `DuplicateSubmitAspect`：①键改 D1 格式；②身份从 sessionId 改 userId；③**必须补 body 摘要**（`ContentCachingRequestWrapper` 或复用项目既有可重复读包装），否则误伤（缺陷 2）不消失。

### D6 go 实现形态（推荐：参数收敛 + 键对齐）

- `AntiRepeatConfig` 调用处收敛为统一值：`Expire:5`、`IncludeBody:true`（去掉逐路由 3s/5s 与 IncludeBody 差异）。
- 键生成改用与 D1 相同的 identity（`user:{userId}`）+ 排序归一后的 query + body 摘要；不再用 jti/IP 作为主身份。

### D7 机制化（推荐：新增跨端契约守卫）

新增源码级守卫测试（免库，参照 `dehaze-python/tests/test_pagination_default_contract.py` 的模式）：

- 三端"防重端点白名单"集合相等；
- 三端键模板字符串一致（含 TTL 常量、`md5` + 排序 query 的口径）；
- 变异自证（改一端即红）。

## 4. 回归与验收口径

每条用例必须**用差异化 body 构造**（A0002 会遮蔽精确业务码，见 skill 02 §2）：

1. 单端：5s 内同 body 重复提交 → A0002；5s 内**不同 body** 同 URL → **不应拦截**；>5s 后同 body → 放行。
2. 跨端互拦：A 端提交后 <5s 内 B 端提交同 body 同路径 → B 端应返回 A0002。
3. 状态码分端断言：python 429 / java 400 / go 200；`code` 一律 A0002。
4. 身份口径：同一用户重新登录后再提交（<5s）→ 仍应被拦（回归 D1）。

## 5. 影响面

- **键格式变更**：旧键在 5s 窗口内自然过期，无迁移动作。
- **java 补 body 摘要**：从"同 URL 一律拦"变为"同 URL 同 body 才拦"——**拦截面收窄**，是修复误伤；需回归"确实想防重的快速重复点击"仍被拦（同 body 两次点击 → 拦）。
- **go TTL 3s→5s、IncludeBody 全开**：拦截面变化，需按白名单逐端点回归。
- **三端白名单对齐**：部分端点从"被拦"变"不拦"（或反之），需按业务确认（尤其上传/数据集创建/订单类端点）。
- **文档**：`04-API规范.md` A0002 条目补分端口径；本节产出白名单。

## 6. 实施步骤（决策后）

1. 产出"防重端点白名单"（三端逐点确认）→ 落 docs + 评审。
2. python：docstring 修正（现写"POST/PUT/DELETE"但实现仅 POST）、query 排序归一、identity 口径注释。
3. java：aspect 键改造 + body 缓存 + userId。
4. go：调用处参数收敛 + 键生成改造。
5. 新增 D7 跨端守卫测试（含变异自证）。
6. 三端回归（第 4 节口径）+ 跨端互拦实测。
7. 同步 `04-API规范.md` 与 skill `02-跨端契约与一致性.md` 的 A0002 条目。

## 7. 风险

- 防重面扩大（go 全开 body 参与后，白名单内端点的"不同 body"请求不再被拦，属预期）与白名单对齐可能改变个别端点的既有拦截行为 ⇒ 需按业务逐点确认，不做"一刀切"。
- java 引入 body 缓存包装需确认不与既有 multipart 转发（`multipartResolver` 覆盖）冲突。

## 8. 实施结果（2026-10-04）

**结论**：D1–D7 按推荐方案全部实施，白名单三端完全一致，键格式与身份口径统一。

### 8.2 各决策点落地

- **D1**：键统一 `anti_repeat:{identity}:{METHOD}:{path}:{sortedQuery}:{bodyHash}`（五段固定，空段保留）；身份统一 `user:{userId}`、退化 `ip:{clientIp}`；java 旧前缀 `LOCK:RESUBMIT:` 废弃。
- **D2**：TTL 统一 5s；go 调用点不再逐路由覆盖 `Expire`（统一走 `middleware.DefaultAntiRepeat()`）。
- **D3**：状态码各端保持（python 429 / java 400 / go 200），已在 `02-系统架构/04-API规范.md` 写死分端口径。
- **D4**：**白名单化**。python 由"全局拦截 + 排除前缀"改为**显式精确白名单**——这是三端集合能严格相等、可守卫的前提，同时消除"排除整个前缀"连带放过该域其他 POST（如 `/api/v1/users` 域下的改密/改状态）的误伤。
- **D5**：java 保留注解；键改造 + 身份改 userId + **补 body 摘要**（新增 `RepeatableBodyFilter` + `RepeatableBodyRequestWrapper`：切面在 `@RequestBody` 参数解析**之后**执行，原始请求流已读空，必须由前置过滤器缓存）；机制由 Redisson 锁（业务完成即 unlock，等价"仅并发去重"）改为 `RBucket.trySet` + 5s TTL，与 python/go 的 SET NX EX 同构。
- **D6**：go `defaultKeyGenerator` 重写（改前 `IncludeBody` 是**死配置**——`defaultKeyGenerator` 无条件读 body，multipart 也读；现改为 multipart/超大请求体不进摘要）；`IncludeBody`/`CustomKeyGenerator`/`CustomAntiRepeat` 死代码删除。
- **D7**：新增跨端契约守卫（见 8.1），含变异自证用例（删注解/删挂载/改前缀均会红）。

### 8.3 行为变更（"是否误伤"的裁决依据）

**移出防重**（改前 go 挂载、python 不拦，现三端一致不拦）：

| 端点                                                                 | 移除理由                                                                                  |
| -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `POST /{module}/_export`                                             | 只读查询，重复提交无副作用                                                                |
| `POST /api/v1/files`、`/api/v1/item-files`、`/api/v1/dataset-items*` | multipart 请求体无法有效摘要（改前每次 boundary 不同 ⇒ 实际未生效），且"连续上传多个"合法 |
| `POST /api/v1/image-input/history`                                   | 输入建议类高频写入，5s 内连续创建合法                                                     |
| `POST /api/v1/dataset-items`（创建空数据项）                         | 请求体常为空 `{}`，连续建项必被误伤                                                       |

**纳入防重**（改前 python 排除 / java 无注解，现三端一致拦）：`POST /api/v1/announcements`、`POST /api/v1/{module}/_import`、`POST /api/v1/roles`（go 补挂载）。

**未纳入**：`POST /api/v1/announcements/{id}/_send`（状态变更，防重语义不适用，三端均不拦）。
